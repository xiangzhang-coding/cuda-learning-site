## SRC-CUDA-065：选定版本的 libcu++ 合同

**相关 ID：** M05、M13、L05。**访问与复核日期：** 2026-09-05。**坐标：** 独立选定 CCCL/libcu++ v3.4.2，提交为 `d36012203ef73ac7f966e848dd88482273e91e02`，2026-08-05 发布。本记录支撑 [L05](/libraries/libcu-plus-plus-synchronization/)、原创 PB-R4-005/006 审查与 TERM-185/186；它是源码检查，不是 API 调用、构建或运行报告。

所审查的库以仅头文件（header-only）形式分发。它的 `cuda::std` 是面向标准、可用于主机与设备（host/device）的不完整子集，并非 `std` 的替代品；`cuda::` 扩展另行提供作用域（scope）。L05 只使用受支持的 32 位原子类型。默认系统作用域（system scope）不会自动提供 CPU/GPU 内存可访问性（accessibility），也不保证系统原子操作受支持；块作用域（block scope）不覆盖不同线程块；设备作用域（device scope）要求双方处于同一内存同步域（memory synchronization domain）。内存序（Memory Order）中的 `relaxed` 操作不发布非原子载荷（payload）；`acquire` 必须观察到相应 `release`，且双方作用域都足够。`atomic_ref` 所指的对象（referent）必须有效、正确对齐，并在所有引用存活期间保持存活；这段期间只能通过原子引用访问该对象。

参与者使用屏障（barrier）前，必须先初始化屏障并发布初始化结果。`arrive` 不等待；`arrive_and_drop` 同时减少当前剩余计数（countdown）和未来预期计数（expected count），不是跳过参与。消费者须等待相应屏障阶段（Barrier Phase）完成；共享缓冲区复用还须有“消费结束后才能覆写”的依赖边。流水线（pipeline）按以下顺序交接：生产者（producer）获取阶段（acquire）、发起复制（issue）、提交（commit），消费者（consumer）再等待（wait）、消费（consume）、释放（release）。调用者仍须负责共享状态（shared state）的集体构造（collective construction）、角色分工、收敛（convergence）和生命周期（lifetime）。`quit` 只放弃所有权（ownership），不等待未完成工作结束（drain），也不取消工作（cancel）。

组（group）形式的 `cuda::memcpy_async` 要求参与者提供相同参数，源区域与目标区域不重叠，载荷可平凡复制（trivially copyable）。非组（nongroup）形式则由每个调用者各自发出一次复制。`aligned_size_t` 断言源地址、目标地址和字节数都满足对齐（alignment）要求；错误断言会导致未定义行为（undefined behavior），不是性能提示。SM 70 的 API 能力下限、本站与 CCCL 的 CC 7.5 支持下限，以及 CC 8.0+ 中符合条件的 `cp.async` 加速路径，必须分开判断。实际指令映射（instruction mapping）、复制与计算重叠（overlap）和加速（speedup）都不能自动推得。同步回退（synchronous fallback）仍须保留完成、数据发布和复用的同步边界。命名空间与主机/设备注解不能证明仅用 GCC 就能编译：所审查的屏障绑定（barrier-bound）`memcpy_async` 定义受 CUDA 编译条件保护（CUDA-compilation guards）；这一结论不覆盖所有流水线绑定（pipeline-bound）重载。主机分派器（host dispatcher）则执行同步复制。

张量核心（Tensor Core）的输入存储、实际乘数精度、累加器类型（Accumulator Type）、收尾计算与 D 存储分别记录。FP32 累加无法修复先前输入转换；float 输出也不证明 FP32 乘法。FP16 的三个 C++ WMMA 瓦片为 `16x16x16/32x8x16/8x32x16`，累加片段可为 half 或 float，API 起点 SM70；BF16 使用相同瓦片、float 累加和 SM80；TF32 为 `16x16x8`、float 累加和 SM80，需显式 `__float_to_tf32` 转换；double 为 `8x8x4`、double 累加和 SM80。这里是 C++ WMMA 的线程束瓦片，不是所有 MMA 指令形状，也不是应用矩阵必须整除的规则。

有符号或无符号 INT8 的 A/B 符号必须匹配，累加与输出片段为 int，三个瓦片同 FP16，整数 WMMA 的 API/PTX 下限是 **SM72**。这不是本站 CC 7.5 基线以下的新支持承诺，也不是 CUDA 13 可生成的 `sm_72` 目标。INT8 最终输出须另行定义缩放、零点、舍入与限幅。当前原生类型表在列出的 CC 7.5 及之后各行列出 FP16/INT8，BF16/TF32 从 CC 8.0 开始；原生 FP64 仅列在 **CC 8.0、9.0、10.0**，不列在 8.6、8.7、8.9、10.3、11.0 或 12.x。不能将“SM80 或更高”的 double API 资格当作所有更高 CC 的原生 FP64 加速证明，也不推测未检查的编译器实现。

PTX 对 FP16 乘法规定至少单精度；有 FP32 C 或 D 时至少单精度累加，两者均 half 时至少半精度。BF16/TF32 使用规定的输入精度并至少单精度累加；这些路径的累加顺序、舍入及次正规输入处理未指定。C++ double WMMA 使用 `.rn`；PTX 的其他 double 舍入修饰符不成为额外 C++ 参数。整数未加 `.satfinite` 时按有符号 32 位溢出回绕，加上它则钳制至 int32 极值；不要与浮点 C++ `satf` 混同。后者默认 false，开启后将正负无穷映射到相应最大有限正规值、NaN 映射到正零；PTX 已移除浮点 `wmma.mma .satfinite`，不能机械翻译。

全部线程束成员须以一致参数参与且无人提前退出；条件须线程束一致。加载起点须 **256 位即 32 字节对齐**，`ldm` 按元素计；文档明确给出 half/float 的 8/4 元素倍数要求，不能悄悄推广给其他类型。边缘须形成完整有效瓦片，不能把 WMMA 当任意掩码加载。float 片段不能直接存入 half 指针；`x[i]` 不是可移植坐标。线程束同步不替代块内发布、复用或主机完成。独立 double 参考分别面向原输入和已舍入输入；有限值、范围、抵消、尾部及近零容差由测试问题决定，不继承 EX18 的 FP32 容差作为通用低精度保证。
