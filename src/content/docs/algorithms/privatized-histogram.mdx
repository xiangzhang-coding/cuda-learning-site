直方图（histogram）把每个合法 sample 映射到一个箱（bin）并增加对应计数。直接全局原子更新（global atomic update）可用 `atomicAdd` 实现；原子正确性（atomic correctness）、争用（contention）、私有化（privatization）、共享内存（shared memory）与合并（merge）是不同问题：atomic 决定并发更新是否正确，privatization 改变更新位置，而性能结论仍需要观测。

## 学完本单元，你应该能

- 写出 histogram 的 exact-count、range、overflow 与 sum-of-bins contracts。
- 解释 global `atomicAdd` 如何防止 lost update，以及为什么正确性不消除 contention。
- 根据 input distribution 识别 same hot bin 上的竞争，而不伪造性能结论。
- 证明 shared privatization 的 `zero -> barrier -> update -> barrier -> merge` phase order。
- 区分教学用手写 kernel、CUB `DeviceHistogram` production baseline 与 runtime evidence。

## Histogram 合同

令 `bin_of(x)` 把一个合法 sample 映射到 `[0, bin_count)`。输出必须满足：

```text
histogram[b] = count of valid samples x for which bin_of(x) == b
sum(histogram[0..bin_count-1]) = valid sample count
```

合同还要声明 lower/upper bound 是 inclusive 还是 exclusive、越界 sample 是丢弃、clamp 还是报错，以及 counter type 在最大输入规模下是否溢出。对于整数 bins，CPU reference 应逐 sample 计算 exact counts；容差不适用于整数计数错误。

Input ownership 与 output ownership 不对称：每个 sample 可以由一个 thread 唯一读取，但许多 threads 可能更新同一个 output bin。因此普通 `histogram[b] += 1` 是 read-modify-write race。

## Global atomics：先保证 correctness

最直接的 baseline 是先把 global bins 清零，再让每个合法 sample 执行 `atomicAdd(&global_bins[b], 1)`。Atomic read-modify-write 防止 lost update，因此 atomic correctness 解决的是多个 threads 同时增加同一 counter 时的精确计数。

这个结论有边界：bin index 必须合法，初始化必须在 kernel 读取前完成，counter 不能溢出，host 必须等待 kernel 完成后再验证。`atomicAdd` 不会修复错误的 `bin_of`、漏掉的 samples 或错误的 memory lifetime。

## Contention：正确但可能竞争

若许多 samples 映射到 same hot bin，它们的 atomic updates 会在同一 address 上 contention，并可能 serialize。较均匀的 distribution 会产生不同的 address pattern。两种输入都可得到完全正确的 histogram；atomic correctness 与 contention cost 必须分别讨论。

从 distribution 或 atomic count 可以提出测量假设，不能直接写 speedup。Hardware、counter type、bin count、block shape、input ordering 与 architecture 都可能影响 observation，因此本页不声称某个 variant 更快。

## Shared privatization：zero、barrier、update、barrier

Block-private shared histogram 把大部分 sample updates 指向该 block 自己的 bins。Minimum correctness sequence 是：

1. **Zero:** threads 以 stride 清零所有 shared bins；`bin_count` 可以大于 `blockDim.x`。
2. **Barrier:** initialization barrier `__syncthreads()`，确保任何 update 前所有 bins 已定义为 0。
3. **Update:** 每个 thread 处理自己的合法 samples，并对 shared bin 执行 `atomicAdd`；shared 仍然需要 atomic，因为 block 内 threads 可能命中同一 bin。
4. **Barrier:** update barrier `__syncthreads()`，确保 merge 不会读取尚未完成的 shared updates。
5. **Merge:** threads 以 stride 把 private counts 合并到 global histogram。

所有 participating threads 都要到达两个 barriers。Bounds-invalid thread 可以跳过 sample update，却不能在 initialization barrier 或 update barrier 前 return。Privatization 是 per-block，不是 per-thread；不同 blocks 拥有不同 shared histogram instances。

## Merge：把 private counts 合到 global bins

多个 blocks 最终写同一 global bins，所以 merge 通常仍要 `atomicAdd(&global_bins[b], shared_bins[b])`。只处理非零 private bins 可以是一个 implementation choice，但必须保持 exact counts，并避免把 zero-test 当作跨 thread synchronization。

Merge 后的 proof obligation 是：对每个 bin，global value 等于所有 block-private values 的和；再对所有 bins 求和，应等于 valid sample count。Kernel completion 后再和 CPU reference 做 exact comparison。Shared privatization 改变了更新分层，不会自动授予 speedup evidence。

## Production baseline：CUB DeviceHistogram

CCCL v3.4.2 的 CUB `DeviceHistogram` 是 device-wide histogram 的 production baseline 和 comparison point。生产代码应先检查 `HistogramEven` 或 `HistogramRange` 的 level boundaries、sample layout、counter、temporary storage 与 stream contracts，而不是默认维护教学 kernel。

手写（hand-written）教学 kernel 用于学习和理解 atomic correctness、contention、shared privatization 与 merge。它不因为展示更多内部 phase 就成为更好的 production default；`DeviceHistogram` 也不进入 `M03,M05` prerequisite list。

本页的 compilation、runtime、expected observations 与 recorded observations 均为空。Exact CPU counts、sum-of-bins invariant 与 phase proof 可以发现 correctness defect，但没有执行 EX13，也没有观察 throughput、bandwidth、timing 或 speedup。

## 离开前检查

1. 为什么 `atomicAdd` 能保证 histogram correctness，却不能消除 same hot bin 的 contention？
2. Shared privatization 为什么仍需要 shared atomic updates？
3. Zero 与 update 后各自的 barrier 保护哪一条 read/write relation？
4. 为什么 merge 回 global bins 通常仍需要 atomic operation，如何验证最终 exact counts？
