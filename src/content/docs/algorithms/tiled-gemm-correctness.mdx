[通用矩阵乘法（general matrix multiplication，GEMM，TERM-147）](/glossary/#term-147)不是从 tile size 开始，而是从 shape、layout、标量、累加顺序与验收规则开始。A08 先建立一个明显正确的 naive GEMM，再把重复 global reads 改为 block-local [K tile（TERM-148）](/glossary/#term-148)复用；每一步都保留同一数学合同。

## 学完本单元，你应该能

- 为 row-major `A[M,K]`、`B[K,N]` 与 `C[M,N]` 写出完整 address contract。
- 解释 naive GEMM 中一个 output owner 为什么执行 K 次乘加。
- 推导 shared-memory tiling 的 load、barrier、compute、barrier、reuse phases。
- 对 partial M、N、K tiles 分别写 guard，并证明所有 block threads 参加 barrier。
- 用 independent double CPU reference、非有限值策略与绝对加相对容差检查 FP32 output。
- 把教学 kernel、未来 cuBLAS/CUTLASS comparison 与实际 performance evidence 分开。

## 先修关系

严格先修项是 `A05, M03, M04, A02`。A05 提供二维 tile 与 layout reasoning；M03/M04 提供 shared-memory ownership 与 physical-layout 审查；A02 提供 reduction order。EX15 是 canonical Runnable Example，VIS12 是 related Visual Explainer，不增加先修边。

## GEMM 合同先于 kernel

本站冻结一个 row-major、非转置、FP32 教学子集：

`C[row * N + col] = alpha * sum(A[row * K + p] * B[p * N + col]) + beta * C[row * N + col]`

合法域是 `0 <= row < M`、`0 <= col < N`、`0 <= p < K`。A 的 leading dimension 是 K，B/C 的 leading dimensions 是 N。每个 `(row,col)` 只有一个 writer；K 只描述 reduction extent，不增加 output tile 数量。

## Naive GEMM：先得到可解释 baseline

Correct naive GEMM 让一个 thread 拥有一个 output coordinate，顺序读取 A 的一行和 B 的一列，累加 K 个 products，再写一次 C。它可能重复读取相同 A/B values，但 one-writer、bounds 和 arithmetic order 都清楚，因此适合作为 tiled implementation 的 correctness baseline，而不是性能结论。

先用 `2x3x2` 手算 fixture 得到 `[22,28,49,64]`，再用 rectangular 与 nonzero-beta fixtures。Square-only、beta-zero-only 或 tile-aligned-only cases 都不能覆盖完整合同。

## Shared-memory tiling：复用 K slices

对 `TM x TN x TK` tile，一个 block 拥有一个 `TM x TN` output footprint。每次 K-loop cooperative load 一个 `TM x TK` A tile 和 `TK x TN` B tile，统一 barrier 后，每个 output owner 从 shared memory 累加 TK 个 products。第二个 barrier 保证任何 thread 重写 shared arrays 前，旧 slice 的 reads 已全部结束。

这改变数据路径，不改变 GEMM equation。`threadblockCount = ceil(M/TM) * ceil(N/TN)`；每个 block 自己循环 `ceil(K/TK)` 个 slices，不能把 K slices 误算成额外 blocks。

## Partial M/N/K tiles 与 barrier

M/N guards 决定 output owner 和 final store。K-tail guards 决定 shared loads；out-of-bounds A/B slots 必须写 neutral zero，避免读取上一次 iteration 的值。Invalid output thread 仍可以负责合法 shared load，也必须到达两个 `__syncthreads()`。因此不能在 K-loop barrier 前 early return。

EX15 的 portable baseline 固定 `16x16x16`，每个 block 256 threads，两块 shared arrays 共 2,048 bytes。普通 FP32 multiply-add、shared memory 与 block barriers 在声明的 CC 7.5 baseline 上可用；没有需要 gated variant 的教学理由，所以 architecture-specific variants 为空，单一路径同时是 portable fallback。

## 数值检查：reference 与 tolerance 是合同

CPU reference 使用 double 累加，并与 device FP32 accumulation 保持独立。每个 finite candidate 必须满足 `absolute_error <= atol + rtol * abs(reference)`；也就是验收阈值 `atol + rtol * abs(reference)`。NaN、infinity 与负 tolerance 被拒绝。Mismatch report 至少包含 linear index、row、column、reference、candidate、absolute error 与 allowed error。

不同合法 operation order 或 FMA contraction 可能改变低位，因此 bitwise equality 不是这里的通用合同。Tolerance 必须在观察 CUDA output 前根据 bounded fixture 声明；它不能在失败后随意放宽。

## 离开前检查

1. `A[M,K] * B[K,N]` 的三个 row-major leading dimensions 分别是什么？
2. Correct naive GEMM 的 one-thread/one-output contract 为什么适合做 tiled baseline？
3. 一个 output block 为什么循环 K slices，而不是为每个 K slice 增加 output block？
4. Partial M、N 与 K 各自影响哪些 guards，为什么 zero-fill 不能替代 barrier？
5. 第二个 `__syncthreads()` 防止哪种 shared-storage reuse hazard？
6. 为什么 double CPU reference、finite policy 与 abs-plus-rel tolerance 必须在运行前声明？
