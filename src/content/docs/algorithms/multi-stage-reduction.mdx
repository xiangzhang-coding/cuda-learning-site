多阶段归约（multi-stage reduction）把许多 values 组合成较少的 partial values，直到只剩一个结果。本学习单元（Learning Unit）把它拆成 block 内归约树（reduction tree）和跨 kernel 的 stage sequence，并分别证明 inactive lane、屏障（barrier）、`__syncthreads()`、kernel boundary 与 operation order。每个 stage 后 active lane 数量减半，更少的参与 lanes 做 combine，但所有 block participants 仍遵守 barrier contract。

## 学完本单元，你应该能

- 声明 reduction operation、identity、input domain 和 result contract。
- 画出每个 stage 的 active/inactive lanes 与 partial ownership。
- 证明每轮 shared-memory write、barrier、下一轮 read 的 happens-before phase。
- 用多个 kernel launches 把 per-block partials 继续归约，而不假设普通 grid 内存在全局 barrier。
- 解释 parallel tree order 为什么可能与 serial sequential order 得到不同 floating-point result。
- 在 production 中先选择 CUB `DeviceReduce` baseline，再用手写 teaching kernel 学习机制。

## Reduction 合同：先定义 combine，再安排线程

设输入为 `x[0..n)`，binary operation 为 `combine(a, b)`，identity 为 `e`。抽象合同是：所有合法 inputs 按声明的 operation order 被组合，empty padding 使用 `e` 且满足 `combine(x, e) = x`。

Integer sum 的教学实例可用 0 作为 identity。对一般 parallel regrouping，数学 operation 应满足 associativity；floating-point addition 在有限精度下不满足严格结合律，因此“正确”不能只写成与某个 serial bit pattern 完全相同。必须同时声明 tree order、reference policy 和 acceptance tolerance，细节由相关单元 [Q02](/correctness/floating-point-order-reproducibility/)继续建立。

## Tree shape：每个 stage 缩小 active set

一个 8-lane 教学 reduction tree 可以这样表示：

```text
stage 0: lanes 0..7 own [x0 x1 x2 x3 x4 x5 x6 x7]
stage 1: lanes 0..3 own [x0+x4, x1+x5, x2+x6, x3+x7]
stage 2: lanes 0..1 own [(x0+x4)+(x2+x6), (x1+x5)+(x3+x7)]
stage 3: lane 0 owns the block partial
```

每个 stage 把 logical partial count roughly halved。Tree edge 定义 operation order；同一 leaves 使用不同 pairings 就是不同算法变体。图只表达 dependency，不声称 warp scheduler 采用某个时间顺序。

## Inactive lanes：不 combine 仍可参与

当 stride 变小时，`threadIdx.x >= stride` 的 lane 对本轮 combine 是 inactive lane。Inactive 不等于退出 kernel：如果后面仍有 block barrier，它必须沿 uniform control flow 到达 barrier。Edge block 中没有合法 input 的 lane 先把自己的 shared slot 写成 identity，同样不能在初始 barrier 前 return。

可将每轮状态分成两列：

| lane role | combine action | participation action |
| --- | --- | --- |
| active | read two declared partials, write one partial | reach the stage barrier |
| inactive | perform no combine | still reach the same stage barrier |

这个分离避免把 data predicate 误当成 synchronization predicate。

## Barriers：写、屏障、再读

Block-local invariant 是：active lanes 先写本 stage 的 shared partial，所有 participating threads 到达 barrier `__syncthreads()`，下一 stage 才读这些 slots。也就是“写 -> 屏障 -> 读”；barrier 不能被 `if (tid < stride)` 包住。

```text
initial guarded load or identity write
all lanes: barrier
for each stride:
  active lanes: read declared pair and write partial
  all lanes: barrier
```

这份 baseline 可能保留最后一个并非最小化所需的 barrier，以换取一致、容易审查的 phase shape。任何删除都要重新证明最后 consumer、storage reuse 和 participating group，而不能靠“inactive lanes 不工作”推断安全。

## Multi-stage：kernel boundary 连接 grid-wide partials

普通 thread blocks 可以独立调度，不能在一个普通 kernel 中用 block-local `__syncthreads()` 建立 grid-wide rendezvous。第一 kernel 的每个 block 把一个 partial store 到 global memory；host 在同一 stream 中 launch 下一 kernel，再把 partial array 当 input。Separate kernel boundary 与 stream order 让下一 launch 在读取 global partials 前等待上一 stage 完成。

```text
input array
  -> kernel stage 0 -> global partial array P0
  -> kernel stage 1 -> smaller global partial array P1
  -> ...
  -> final scalar
```

因此 kernel 边界承担跨 grid 的全局 stage boundary，而 block barrier 只承担一个 block 内的 shared-memory phase boundary。两者不能互换。每次 launch 仍要 guard final partial block，并为 invalid slots 注入 identity。

## Operation order：parallel tree 不是 serial fold

Serial left fold 的顺序可以写成 `(((x0 + x1) + x2) + x3)`；一种 tree order 是 `(x0 + x1) + (x2 + x3)`。数学实数加法给出同一结果，floating-point 每次 combine 都 rounding，树形并行顺序因此可能不同于串行 sequential 顺序。

这不允许忽略 mismatch。应记录 type、compiler options、tree shape、block/grid shape、identity、reference accumulation 和 tolerance。Determinism、acceptable numerical variation 与 bitwise reproducibility 是不同要求；本页只建立 operation-order dependency，完整 contract 在 Q02。

## Production baseline：先用 CUB DeviceReduce

Production 开发先把 CUB `DeviceReduce` 作为生产基线和 comparison point，再决定是否有理由维护 custom kernel。它封装了被广泛维护的 device-wide reduction primitive；调用者仍负责 operation、type、temporary storage、stream、input/output lifetime 和 numerical acceptance contract。

手写 teaching reduction 的目的，是学习和理解 tree ownership、inactive lanes、barriers、kernel stages 与 operation order。它不是 prerequisite，不从 CUB source 复制 implementation，也不因为“更接近硬件”就自动胜过 production baseline。只有在 correctness parity、Environment Manifest 和 measurement method 都固定后，observed evidence 才能支持替换决策。

## Visual Explainer：VIS10

[VIS10：Reduction Stages](/visuals/reduction-stages/)把 lanes、partials、stage transitions 和 inactive-lane set 表示为 deterministic browser model。它帮助检查 algorithm variant 与 barrier placement，但不执行 CUDA、不模拟 scheduler，也不生成 measured performance。

使用它时先选定 tree variant，再逐 stage 回答三个问题：谁读、谁写、谁必须到达 barrier。Visual Explainer（可视化讲解）的 static fallback 与交互状态都只是 expected reasoning aid。

## 证据边界：推理结果与观察结果分栏

| expected reasoning | observed performance 或 runtime evidence |
| --- | --- |
| 每个 stage 的 active/inactive ownership | 某个 Reference Environment 中实际输出与错误状态 |
| write -> barrier -> read phase proof | Sanitizer、trace 或其他实际 tool observation |
| kernel stages 逐步缩小 partial count | 实际 launch count、duration、traffic 或 throughput |
| tree operation order 不同于 serial fold | 记录输入、配置后观察到的 numerical difference |

本页四个 evidence arrays 全为空。Source review、diagram 和 host-side reasoning 不能证明 EX11 已编译或运行，更不能证明 custom reduction 比 CUB 更快。

## 离开前检查

3. 为什么普通 block barrier 不能替代 multi-stage kernel boundary？
