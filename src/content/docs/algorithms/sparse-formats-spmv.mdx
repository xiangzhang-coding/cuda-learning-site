[坐标格式（coordinate format，COO，TERM-171）](/glossary/#term-171)为每个 stored entry 保留行、列和值；[压缩稀疏行（compressed sparse row，CSR，TERM-172）](/glossary/#term-172)把重复的行号压缩为 row offsets。[稀疏矩阵-向量乘法（sparse matrix-vector multiplication，SpMV，TERM-173）](/glossary/#term-173)随后按这些位置读取 `x` 并对每行归约。三者是表示和算法合同，不是“稀疏一定更快”的口号。

## 学完本单元，你应该能

- 从一个二维矩阵构造零基、row-sorted、无重复坐标的 COO 与 CSR 数组。
- 用 `m`、`n`、`nnz`、value width 和 index width 核算 dense、COO 与 CSR payload。
- 用重复 row offset 表示空行，并从 offsets 恢复每行的 half-open entry range。
- 手算 `y=A x`，区分矩阵值的连续扫描、索引读取、`x` gather 与 row reduction。
- 说明为什么 format、index base/type、ordering 和 duplicate policy 必须先于 library call 固定。
- 把静态 payload/operation 账本与 actual traffic、timing 和 speedup 证据分开。

## 稀疏表示合同

先冻结逻辑矩阵 shape `m x n`、stored-entry count `nnz`、value type、index type、index base、entry ordering 与 duplicate policy。本页使用 `m=4`、`n=5`、`nnz=6`、FP32 values、32-bit indices、零基索引、按行再按列排序，并要求每个 coordinate 唯一。

“Nonzero”在这个 fixture 中表示被存储的六个数学非零项。实际数据管线若保留 explicit zero、按阈值剪枝或允许 duplicate coordinates，必须另写转换与数学语义；不能默认为 library 会合并重复项。cuSPARSE v13.3 的 storage-format 页面说明支持零基与一基索引，并警告同一行重复 column indices 时计算正确性并非总能保证。

## COO：每项保留完整坐标

按 row-major coordinate order 扫描六个 stored entries：

- `row_indices = [0, 0, 2, 2, 3, 3]`
- `column_indices = [0, 2, 1, 4, 0, 3]`
- `values = [4, -1, 2, 3, 5, 7]`

三个数组长度都是 `nnz=6`。第 `k` 个 stored entry 是三元组 `(row_indices[k], column_indices[k], values[k])`。COO 直接表达坐标，便于组装和交换，但每项付出两个 index。当前 owner 文档把 COO 说明为 row-sorted，同时允许行内 column indices 有序或无序；这种格式级说明不能被扩写成所有 operation、algorithm 和 version 的通用性能结论。

## CSR：把行号压缩为 offsets

CSR 保留相同的 `column_indices` 与 `values`，把六个 row indices 换成长度 `m+1=5` 的：

`row_offsets = [0, 2, 2, 4, 6]`

Row `r` 使用 half-open range `[row_offsets[r], row_offsets[r+1])`。因此 row 0 读取 entries `[0,2)`，row 1 读取 `[2,2)` 而为空，row 2 读取 `[2,4)`，row 3 读取 `[4,6)`。末项等于 `nnz`；offsets 单调不减。重复的 `2,2` 不是 duplicate coordinate，而是零长度 row range。

## 存储账本：index metadata 也占空间

令 value width 为 `b_v`，index width 为 `b_i`，且只计矩阵 A 的 payload，不计 allocator、alignment、descriptor 或 workspace：

- Dense：`mn b_v`
- COO：`nnz (b_v + 2b_i)`
- CSR：`nnz (b_v + b_i) + (m+1)b_i`

代入 `m=4,n=5,nnz=6,b_v=b_i=4 B`，dense 是 `80 B`，COO 是 `72 B`，CSR 是 `68 B`。这个小矩阵只相差 8 B 或 12 B，正好说明 density 不能单独决定表示；shape、index width、row count、explicit zeros、conversion cost 与后续 operation 都属于决策。这里的 storage footprint 也不是某次 GPU transferred-byte observation。

## SpMV：按 stored entries 做 row reduction

取 `x=[1,2,3,4,5]`，定义 `y=A x`。CSR row ranges 给出：

- `y_0 = 4*x_0 + (-1)*x_2 = 4*1 - 1*3 = 1`
- `y_1 = 0`，因为 `[2,2)` 没有 stored entry
- `y_2 = 2*x_1 + 3*x_4 = 2*2 + 3*5 = 19`
- `y_3 = 5*x_0 + 7*x_3 = 5*1 + 7*4 = 33`

所以 `y = [1, 0, 19, 33]`。这包含六个 value-vector products 和六次对相应 row accumulator 的贡献，而 dense row traversal 会检查 20 个 matrix positions。Sparse traversal 还读取 indices，并按 `column_indices` gather `x`；row lengths `[2,0,2,2]` 又决定可用并行工作。较少的数学 contributions 不自动意味着较少的 hardware transactions 或较短时间。

## 到 cuSPARSE 的高层边界

cuSPARSE v13.3 的 Generic API 把 format、shape、index base/type、stored data type 和 arrays 放入 descriptors；operation、compute type 与 algorithm 是分开的 call-level contract。Caller 按 exact combination 查询 external device workspace，并只在返回大小非零时分配 buffer。当前 SpMV 文档还给出可选 preprocessing 和 algorithm-specific determinism/performance 取舍；这些都是 current owner facts，不是本页运行结果。

A12 只要求学习者能解释为何 library 需要完整表示 metadata，以及为何 repeated sparsity pattern 可能让 preprocessing 有意义。Exact descriptor constructors、buffer-size query、algorithm enums、lifetime/error handling 与 Runnable Example EX20 全部延后到 L13。不要从 A12 推断固定 workspace bytes、某个 algorithm 最快、observed determinism、structured-sparsity support 或当前 hardware winner。

## 离开前检查

1. COO 的三个数组各保存什么，为什么每个长度都是 `nnz`？
2. CSR 为什么需要 `m+1` 个 row offsets，空行如何出现？
3. `row_offsets=[0,2,2,4,6]` 中两个连续的 2 与 duplicate coordinate 有何不同？
4. 本 fixture 的 dense、COO、CSR 为什么分别是 80 B、72 B、68 B？
5. `y_2=19` 使用哪些 stored entries 与 `x` positions？
6. 为什么 `nnz` 较小仍不足以推出更少 actual traffic 或更快运行？
