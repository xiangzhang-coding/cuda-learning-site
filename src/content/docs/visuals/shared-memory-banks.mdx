## 学习目的

VIS05 是与 [M04](/memory/bank-conflicts-layouts/) 和 [EX06](/examples/shared-memory-tile-bank-padding/) 相关的确定性 address-to-bank mapper。它先展示每个 lane 选择的 4-byte word、byte address 与 bank，再允许学习者讨论优化主张。

## 映射模型

默认 source-backed fixture 位于本站 CC 7.5+ 基础 GPU 能力层级内，并固定 `32` 个 lane、`32` 个 bank 和 4-byte word。对 lane `L`、stride `S`、padding `P` 和 bank count `B`，抽象 layout 为：

```text
laneStep  = S + P
wordIndex = L * laneStep
byte      = wordIndex * 4
bank      = wordIndex mod B
```

Bank count 可调，便于直接检查算术。只有默认的 `32` banks、连续 4-byte word fixture 被描述为已复核 CUDA 规则；其他有界 bank count 只是抽象比较，不声明对应某个受支持 architecture。

## 分类

Mapper 先按 bank 对 lane 分组，再计算每个 bank 内的**不同 word address**数量。Conflict degree 是这些数量中的最大值。如果每个被访问 bank 只有一个不同 word，则 degree 为一，属于 conflict-free。

这个 fixture 建模一次 shared-memory **read**。如果所有 lane 请求同一个 word，结果单独分类为 **same-address broadcast**，只含一个不同地址，而不是 32-way conflict。Same-address write 不属于 VIS05，因为它不是 read broadcast 情景。

Conflict degree 只是所选地址列表的结构属性。它不是 elapsed time、serialization duration、bandwidth 或 speedup；浏览器也不能判断完整 kernel 的性能。

## Stride 与 padding 案例

在 `32` banks、padding `0` 下，stride `1` 每个 bank 访问一次，属于 conflict-free。Stride `2` 访问 16 个 bank，每个 bank 有两个不同地址，因此是 two-way。Stride `32` 把 32 个不同地址映射到 bank zero，因此是 32-way。

把 stride `32`、padding `0` 改为 stride `32`、padding `1`，lane step 会从 `32` 变为 `33`。因为 `33 mod 32 = 1`，连续 lane 会轮转经过全部 32 个 bank，映射出的 read 变为 conflict-free。这是地址算术，不是 padding 能改进所有 kernel 的承诺。

## 静态回退

五张卡片保留 stride `1`、stride `2`、stride `32`、padding 后的 stride `33` 与 same-address broadcast。它们和交互 table 来自同一个纯模型，在禁用 JavaScript 和打印时仍然完整。

## 证据边界

VIS05 不编译或运行 CUDA、不读取 GPU，也不测量 latency。其 mapping 与 conflict label 不会授予 **Compile-Checked**、**Community-Observed** 或 **Runtime-Verified**。Compilation、runtime、expected-observation 与 recorded-observation metadata 全部为空。
