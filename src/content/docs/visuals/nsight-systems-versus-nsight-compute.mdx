## 学习目的

完成 Q07 与 Q08 后，用 VIS14 把一个可观察症状转换为下一种证据来源。Bounded rule 是 timeline first：application latency、CPU/launch gaps、copy/compute overlap、依赖不清楚，以及尚未选定 kernel，都先进入 Nsight Systems。只有代表性 timeline 已选定一个精确 kernel instance，而且学习者写出了一个 kernel-level question 时，Nsight Compute 才成为下一步。

## 确定性决策规则

规则只问一个问题：**代表性 application timeline 是否已经选定一个精确 kernel instance，而且当前问题是否属于 kernel level？**

- **否**：先收集或检查 Nsight Systems application timeline。
- **是**：下一步使用 Nsight Compute；在收集前声明 kernel filter、question、section/metric set、replay behavior、tool version 与 counter permission。

Recommendation 由 symptom 推导。模型没有独立 tool selector，因此不能把“尚未选定 kernel”与 Nsight Compute 配对，也不能靠点击偏爱的产品绕过 timeline gate。

## 工具边界

Nsight Systems 在 application timeline 中关联 CPU threads、CUDA API activity、kernels、copies、streams、dependencies、gaps 与 overlap。`.nsys-rep` 和 owner-supported export 可以定位工作并选出下一问题，但本身不会证明详细 kernel bottleneck。

Nsight Compute 分析 selected kernels，并把 sections 或 individual metrics 收集到 `.ncu-rep`。Metric 名称与 availability 随 GPU/tool version 变化；collection 可能需要 multi-pass 或 replay，可能扰动或序列化工作，并需要 reviewed performance-counter policy。应先查询 availability，只收集回答 declared question 所需的证据；metric dump 不是诊断。

两个工具在适用 trace/counter 路径上都使用包括 CUPTI 在内的 CUDA profiling infrastructure，但 reports 来自两次独立 instrumented executions。任何一个都不应被描述成未修改的 application run；kernel report 也不能替代选中它的代表性 application timeline。

## 静态回退

Server 永久渲染 gate 与全部六个 leaves：四个 Nsight Systems leaves，两个 Nsight Compute leaves。每个 leaf 都保留稳定的 symptom、tool、scope、artifact、decision gate 与 next gate data。文字、heading、solid/double border 与 branch order 承担区分，不只依赖颜色。禁用 JavaScript、390-pixel viewport、reduced motion、forced colors 与 print 时，完整 tree 仍然可见。

## 证据边界

VIS14 不启动 `nsys` 或 `ncu`，不打开 profiler report，不查询 GPU、CUPTI activity、metric 或 performance counter，也不发布 timeline、timing、bottleneck、throughput 或 speedup observation。Compilation、runtime、expected-observation 与 recorded-observation arrays 全为空，不授予 Compile-Checked、Community-Observed 或 Runtime-Verified Evidence Status。
