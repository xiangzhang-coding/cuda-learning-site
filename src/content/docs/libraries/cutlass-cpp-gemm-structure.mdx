通用矩阵乘法（general matrix multiplication，GEMM）的模板里，也可能藏着与手写内核（kernel）相同的输出归属（output ownership）和同步（synchronization）错误。读类型时，要看它选择了由谁负责输出、操作数如何到达、部分和何时写成最终结果，而不是把类型本身当作正确性或速度的保证。

## 学习目标

预留约 40 分钟阅读源码、完成纸面推导与检索检查。你将沿一条保留至今的 C++ 层次追踪职责，区分三个层面的布局（layout），重建两阶段依赖时间线，并说清未来的构建必须证实什么。本学习单元（Learning Unit）不要求 GPU，也不要求安装 CUTLASS。

## 前置知识

前置依赖严格按 `A08, L06, M17` 排列：[A08：分块 GEMM 正确性](/algorithms/tiled-gemm-correctness/)提供输出归属与 K 维归约（reduction）不变量；[L06：cuBLAS GEMM](/libraries/cublas-gemm/)提供形状、主维度（leading dimension）和数值类型；[M17：选择编译器架构目标](/toolchain/compiler-architecture-targets/)区分源码架构标签、编译器目标与产物（artifact）。L08 和 VIS12 是相关资源，不是额外的前置依赖。

## 为什么这套层次跨越了 API 代际

库调用通常隐藏实现，CUTLASS 则把可复用的 C++ 构件暴露出来。保留的 2.x 风格按设备（device）、内核、线程块（thread block）、线程束（warp）和指令（instruction）组织工作。单指令多线程（single instruction, multiple threads，SIMT）与张量核心（Tensor Core）实现遵循同一 GEMM 公式，但需要不同的运算策略和数据搬运策略。随着协作方式与架构专用调度变得更复杂，较新的 3.x API 显式引入了集体协作（collective）主循环（mainloop）与收尾操作（epilogue）；它并不是给旧层次逐层改名。

本单元固定使用 **CUTLASS C++ v4.7.0**，提交为 **`dcf215af68a2d08d305076c152a06f201728cd53`**，阅读的是**该版本内保留的 2.x 风格 API**，不是另加一个 2.x 依赖。[提交](https://github.com/NVIDIA/cutlass/commit/dcf215af68a2d08d305076c152a06f201728cd53)日期为 `2026-08-06T14:31:22Z`；[版本](https://github.com/NVIDIA/cutlass/releases/tag/v4.7.0)发布于 `2026-08-13T09:43:47Z`。变更日志条目标注的是 2026-08-04，这是另一个日期。版本宏给出 4/7/0；未经生成、值为空的修订宏不能替代 SHA。

## 布局与收尾操作是不同的契约

全局内存布局（global layout）把逻辑坐标映射为元素偏移。[`cutlass::layout::RowMajor`](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/layout/matrix.h#L57-L110)采用行主序（row-major），公式为 `row*stride+column`；步长不自动等于逻辑列数。共享内存布局可能为访问模式重新组织暂存的操作数，寄存器片段也有自己的线程/值组织方式。全局 RowMajor 声明不提供这两种内部映射中的任何一种。CUTLASS 布局类型不是 cuBLAS 转置标志。

[线性组合收尾操作（linear-combination epilogue）](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/epilogue/thread/linear_combination.h#L219-L249)在累加后处理缩放、源矩阵 C 与目标类型转换。要分别记录累加器、计算/标量、源和输出类型。为存储重排累加器数据也是收尾工作，不是再遍历一遍 K。即使采用 FP32 累加和输出，A/B 转成 FP16 时仍可能丢失输入信息；[L08](/libraries/tensor-core-precision-contracts/)进一步讨论这一数值契约。

## 推导一个尺寸不整齐的原创分块模型

考虑 `D=0.5*A*B+C`，其中 `M=150,N=90,K=40`。A/B 为 FP16；C/D、累加与收尾计算均为 FP32。所有全局矩阵都采用 RowMajor：A 的步长为 48，B/C/D 的步长为 96，分配范围覆盖完整的物理行。拟定线程块分块为 `64x64x16`、线程束分块为 `32x32x16`，并以 SM75 的 `16x8x8` 作指令层比较。这是原创的几何模型，不是复制的测试、已实例化的模板，也不是已证明合法的特化。

| 推导 | 结果 | 它不能证实什么 |
| --- | --- | --- |
| 输出网格（grid） | `ceil(150/64)*ceil(90/64)=3*2=6` 个线程块 | 不是 18 个独立线程块：K 在各输出线程块内部归约 |
| K 维遍历 | 每个线程块有 `ceil(40/16)=3` 个切片 | 不是三个各自覆写 D 的独立收尾操作 |
| 输出的线程束分块 | `(64/32)*(64/32)=4` 个线程束分块，不沿 K 划分 | 不是观察到的调度或占用率（occupancy） |
| 右下角输出分块 | 起点为 `(128,64)`，有效范围为 `22x26` | 不允许边缘线程在必要的同步之前退出 |
| 最后一个归约切片 | `k=32..39`，有八个有效位置 | 不允许越界读取剩余八个位置 |
| 指令层覆盖 | 每个线程束分块在每个完整 K 切片中有 `(32/16)*(32/8)*(16/8)=16` 次几何意义上的运算 | 不是实际生成或执行的指令计数 |

对有效输出 `(i,j)`，A08 的不变量是：累加器包含此前所有已完成 K 切片的贡献，不含任何后续切片的贡献。第三个切片完成后，**只执行一次** `0.5*acc+C[i,j]`。[API 循环嵌套](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/gemm_api.md#L8-L63)表达的是外层 M/N 网格的并发，而不是设备端的串行循环。若采用 Split-K，就需要另一套合并证明，以及 C 恰好计入一次的证明。

沿用 L06 的步长推理，A 的偏移为 `i*48+k`，B 为 `k*96+j`，C/D 为 `i*96+j`。D 的最后一个逻辑元素位于 `149*96+89=14393`，在 `150*96=14400` 个元素的范围内。使用 `i*90+j` 会忽略填充（padding）。每个操作数的分配范围与子视图（subview）对齐都要独立证明；这些算术推导不能证明它满足模板的对齐要求。

一个理想化的 FP16 暂存槽位容纳 `(64*16+16*64)*2=4096` 字节的 A/B 有效载荷（payload）；两个槽位共 8192 字节。这没有计入布局填充及内核的其他存储，因此既不是内核的共享内存分配量，也不是占用率估计。暂存过程必须检查边界，或通过显式填充提供合法、完整的操作数；最终存储只能选取有效输出。

## 流水线需要两种不同的许可

选定的 `MmaPipelined` 继承自一个**两阶段**基类。流水线（pipeline）中的阶段（pipeline stage）是可复用的存储槽位，并不意味着所有 CUTLASS 内核都采用双缓冲（double buffering）。下面的原创时间线规定的是依赖关系，不是实测的执行重叠，也不是逐条指令的实际调度。

| 切片 | 槽位内容 | 必须满足的顺序 |
| --- | --- | --- |
| 第一个 | 阶段 0 接收 `k=0..15` | 消费者（consumer）读取之前，必须完成并发布写入 |
| 第二个 | 阶段 1 接收 `k=16..31` | 消费之前，必须独立确认该阶段已就绪 |
| 第三个 | 阶段 0 接收 `k=32..39`，其余补零 | 覆写之前，等待上一轮阶段 0 的所有消费者完成，再发布新内容 |

“可以读取”和“可以安全覆写”是两件不同的事。分配了两个缓冲区并不能证明其中任何一件。边缘处没有有效数据的线程仍须参加必要的同步。[高效 GEMM 讨论](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/efficient_gemm.md#L110-L151)说明了采用缓冲与收尾重排的动机，但不保证本模型能够隐藏延迟、达到某种占用率或获得加速。这次源码阅读也不能证明使用了 L05 中单独标注版本的 `cuda::pipeline` API。

[VIS12](/visuals/gemm-tiling-hierarchy/)串联矩阵、分块、线程块与线程束。它的指令面板仍是**源码层的标量 `1x1x1` 槽位**，不是 FMA、MMA、WMMA、SASS，也不是实测的 CUTLASS 执行。进一步的指令与流水线推理应使用本单元另行标明的几何模型和时间线，不要更改现有可视化所表达的含义。

## 限定 3.x 比较的范围

[3.x 阅读路径](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/gemm_api_3x.md#L83-L195)是 **Device -> Kernel -> Collective -> Tiled MMA/Copy -> Atom**。Collective 为主循环或收尾操作协调协作线程及其数据依赖。生产者（producer）线程束与消费者线程束可以承担不同角色。Tiled MMA/Copy 表达分块后的线程/值工作，原子构件（atom）描述基础操作（primitive operation）。“collective = warp”和“atom = thread”都不是有效的对应关系。

内核组合 collective 主循环与收尾操作；[`device::GemmUniversalAdapter`](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/gemm/device/gemm_universal_adapter.h#L123-L137)仍是面向主机的接口。[代际兼容性说明](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/cutlass_3x_backwards_compatibility.md#L11-L49)解释的是如何共存，不是说配置类型可以互换。列出的 Hopper 3.x 内核要求 SM90a 和 CUDA 12.0+，但这不代表每个 3.x 概念都只能用于 Hopper。CuTe **C++** 不是 CuTe **Python DSL**；这里不需要领域专用语言（domain-specific language，DSL）。

## 保留普通 FP32 替代路径

保留一条不使用 Tensor Core 的 FP32 SIMT GEMM，A/B/C/D、累加器与收尾计算全部采用 FP32。无论实现标签有多旧，它在学习站的硬件基线都是 CC 7.5 或更新，且问题规模受限、内存需求小于 8 GB。布局、尾部处理与 `alpha,beta` 语义都要明确。把 FP16 乘数换成 FP32 会改变数值算法；它既不是逐位等价的回退，也不是精确实数运算的判定基准。L08 解释了独立的更高精度参考与针对具体测试数据（fixture）的容差。性能比较要求数值结果已通过验收，且测量边界一致，不能从分块大小预测加速比。

## 证据边界

本单元只有原创推理与源码引用：没有导入规范 CUDA 源文件，没有 CUTLASS 实例化、构建、PTX/SASS 产物检查、GPU 输出或计时。四个证据数组全部为空；不授予任何证据状态（Evidence Status），也不从 A08、L06、上游测试或链接的示例继承状态。原生 Linux 是唯一的受支持环境（Supported Environment），浏览器从不执行 CUDA。

未来的编译记录需要精确源码 SHA、操作系统/编译器/组件版本、语言方言与目标标志、命令、产物哈希、诊断信息和退出状态。未来的运行记录还需要环境清单（Environment Manifest）、完成/错误检查、独立数值参考、验收标准，以及在已声明的基准环境（Reference Environment）中的实际结果。拟议的兼容性与源码可见的指令封装，都不能替代这些记录。
