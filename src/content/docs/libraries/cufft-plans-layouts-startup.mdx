## 为什么先有计划再执行

离散傅里叶变换（Discrete Fourier Transform，DFT）把信号表示为不同频率的加权组合。快速傅里叶变换（Fast Fourier Transform，FFT）是求解它的一类算法，不是另一种数学运算。Cooley-Tukey 分解把工作拆成较小变换；cuFFT 对难以分解的长度还会选择其他算法。小素数幂往往有利于实现，但因式分解不是速度测量。

cuFFT 的计划接口借鉴 FFTW。**计划（plan）**为选定 GPU 准备特定变换配置，可能涉及算法决策、内核模块和临时内存。保留计划，可以在兼容的数据集之间摊销准备成本。历史边界也有意义：CUDA 12.0 增加了以 PTX 交付的内核，12.4 加入可选的链接时优化（Link-Time Optimization，LTO）内核，12.6 Update 2 引入 LTO 回调。这是三个不同的变化，不能回推给每个历史计划。

## 先定义变换，再定义缓冲区

对 `n,k = 0..N-1`，正向变换为 `X[k] = sum_n x[n] * exp(-2*pi*i*k*n/N)`，指数使用**负号**。C2C 逆向使用正号。cuFFT 两个方向都**不归一化**，因此 inverse(forward(x)) 在一维是 `N*x`，多维是 `product(n)*x`。只乘一次逻辑大小的倒数，不要用分配大小或批次数的倒数。

例如 `N=4`、`x=[0,1,0,0]`，正向得到 `X=[1,-i,-1,i]`，未归一化逆向为 `[0,4,0,0]`。只做往返可能掩盖成对的符号或布局错误。EX19 针对逻辑样本，用独立累加的 CPU DFT 比较每个正向系数，使用有界且批次不同的输入、拒绝非有限结果，并声明容差，而不要求不同实现逐位相同。具体可执行约定和验收条件只由 EX19 页面定义。

## 逻辑形状不等于物理存储

一维实数变换令 `K=floor(N/2)+1`。实输入的厄米共轭对称（Hermitian symmetry）满足 `X[k]=conj(X[(N-k) mod N])`，因此只需保存非冗余的一半；它不表示所有已存系数都是实数。

| 类型 | 逻辑输入 | 逻辑输出 | 方向 |
| --- | --- | --- | --- |
| `C2C` | `N` 个复数 | `N` 个复数 | `CUFFT_FORWARD` 或 `CUFFT_INVERSE` |
| `R2C` | `N` 个实数 | `K` 个复数 | 正向 |
| `C2R` | `K` 个厄米复数 | `N` 个实数 | 逆向 |

异地（out-of-place）实数变换分别分配上述范围。原地（in-place）实数变换则需要 `2*K` 个实数，等价于 `K` 个复数：偶数 N 需要 `N+2` 个实数，奇数 N 需要 `N+1` 个实数。这是存储填充，**不是改变 N，也不是对数学信号补零**。多维行优先数据只压缩或填充每行最后一个、变化最快的维度。形状 `[N1,N2,N3]` 产生 `N1*N2*(floor(N3/2)+1)` 个复数，不是把每个轴都减半。

C2R 要求厄米输入。一维的直流（DC）项与偶数 N 的奈奎斯特（Nyquist）项虚部为零。多维要满足完整的共轭坐标关系，不能要求 DC 平面上每个点单独为实数。R2C/C2R 指针，包括实数类型的指针，都必须满足对应复数类型的对齐要求。分配大小无法证明偏移后指针的对齐。

**异地 C2R 会覆盖输入缓冲区。** 重用前应保留或恢复独立频谱。非单位步幅的原地 C2R 还可能覆盖任意输入点的虚部。不要把间隙不变或频谱保留当成一般实数变换保证。这些是[上游存储规则](https://docs.nvidia.com/cuda/cufft/index.html#data-layout)，不是 EX19 执行的模式。

## 推导步幅和批次距离

`cufftPlanMany` 与 `cufftMakePlanMany` 将逻辑维度和存储嵌入（embedding）分开。`istride`/`ostride` 前进一个最内层元素，`idist`/`odist` 前进到下一批变换。单位都是**对应输入或输出类型的元素**，不是字节。一维地址为 `b*idist+x*istride` 与 `b*odist+x*ostride`；二维输入映射为 `b*idist+(x*inembed[1]+y)*istride`；三维为 `b*idist+((x*inembed[1]+y)*inembed[2]+z)*istride`。

嵌入数组按各自元素单位描述包含填充的物理存储，最外层嵌入项不能取代批次距离。原地批量 R2C 中，相同的字节起点可以要求不同数值的距离：`idist=2*K` 个实数，`odist=K` 个复数；C2R 则交换两侧角色。

**空嵌入数组会选择默认布局，并忽略高级步幅。** 不能传空嵌入，却期待自定义 `istride` 仍生效。自定义布局时应提供两个嵌入数组，并正确填写所有高级参数。正步幅的一维访问范围为 `1+(batch-1)*dist+(N-1)*stride` 个元素；还须独立证明没有非预期重叠，且坐标映射正确。足够大的分配也可能装着错误的样本。参见[高级数据布局](https://docs.nvidia.com/cuda/cufft/index.html#advanced-data-layout)。

## 一次构建，有条件地复用

调用者自管工作区（workspace）的路径要分阶段理解：

| 阶段 | 责任 |
| --- | --- |
| `cufftCreate` | 在目标设备和上下文中创建句柄，检查状态 |
| `cufftSetAutoAllocation(plan, 0)` | 在规划前关闭自动临时空间分配 |
| `cufftMakePlanMany` | 固定类型、秩、长度、嵌入、步幅和批次数，取得临时空间需求 |
| `cufftGetSize` | 规划后取得真实需求；可能改变需求的设置之后再次查询 |
| `cufftSetWorkArea` | 绑定有效且足够大的调用者工作区 |
| `cufftSetStream` | 关联执行流，关联会一直保留到更改为止 |
| `cufftExecC2C` | 用当前合法的输入输出指针提交已配置的变换 |
| `cufftDestroy` | 必要工作完成后释放计划拥有的资源，不代替释放调用者缓冲区 |

更换数据指针而复用计划，仍要求类型、布局、范围、设备和上下文、生命周期满足原约定。逻辑配置改变应新建计划，而不是在已完成规划的句柄上再次 make-plan。检查每次分配、规划、执行和完成状态；失败后停止，保留阶段诊断，只清理确实取得的资源。较新的 `CUFFT_PLAN_NULL` 是 CUDA 13.0 才加入的标识，不能无条件用于 11.8。EX19 拥有唯一规范源码，本单元不放另一份代码。

## 工作区所有权跟随完成边界

默认情况下，每个计划独立分配工作区。`cufftSetWorkArea` 替换指针，并释放原来自动分配的区域；新绑定的调用者内存仍由调用者负责。查询大小不会分配内存，查询失败也不能解释为零临时空间。执行完成前保持输入、输出和工作区存活；主机读取、复用、释放之前检查完成。

足够大的同一工作区可供**顺序执行**的计划共享。每个**并发执行**都需要独占工作区，包括同一句柄的重叠执行。不同主机线程的文档安全边界是不同计划和互不重叠的输出，不是无协调地修改同一句柄。优先让每个并发工作者拥有独立的计划、流和工作区；也可通过显式完成依赖把复用串行化。cuFFT 可能使用内部私有流，但只保证相对于用户关联流的顺序。未关联时使用流 `0`，这不是全局顺序证明。来源：[流执行](https://docs.nvidia.com/cuda/cufft/index.html#streamed-cufft-transforms)、[工作区所有权](https://docs.nvidia.com/cuda/cufft/index.html#caller-allocated-work-area-support)、[线程安全](https://docs.nvidia.com/cuda/cufft/index.html#thread-safety)。

## 拆开启动和稳定执行

规划包含主机启发式、模块加载、分配，以及可能发生的即时编译（Just-In-Time compilation，JIT）。CUDA 12.0 起，更多 cuFFT 内核以 PTX 交付，在计划初始化时由驱动编译。这不表示 11.8 永远不会 JIT。初始化 cuFFT 时应保留足够空闲显存；首次调用可能初始化内核，甚至在应用分配大数组之前就失败。

| 账本 | 计时边界 | 应记录而非假设 |
| --- | --- | --- |
| 主机准备 | 用主机时钟包围明确声明的创建、规划和分配阶段 | 是否计入设备和上下文初始化 |
| 冷缓存条件 | 受控的缓存状态，不等于进程重启 | 驱动、路径、容量与缓存开关 |
| 首次执行 | 在已准备计划上的第一次已完成执行 | 是否计入传输和预热 |
| 热执行 | 显式预热后，在执行流上使用设备事件 | 重复次数、完成检查、输入恢复和原始结果 |

驱动缓存生成的二进制，新进程可能继续使用它。升级驱动会使其计算缓存失效；关闭缓存或淘汰也可能触发重编译。必要时记录 `CUDA_CACHE_PATH`、`CUDA_CACHE_MAXSIZE` 和 `CUDA_CACHE_DISABLE`。nvJitLink 的运行时 LTO 缓存另有责任，不是应用计划缓存。这里没有耗时、加速比、热执行必然更快的保证或盈亏平衡次数。来源：[cuFFT 启动](https://docs.nvidia.com/cuda/cufft/index.html#plan-initialization-time)和[驱动 JIT 与缓存](https://docs.nvidia.com/cuda/archive/12.9.2/cuda-c-programming-guide/index.html#just-in-time-compilation)。

| 工具包通道 | cuFFT 组件 | 通用下限 | FP16 下限 | Bfloat16 下限 | 清单发布日期 |
| --- | --- | --- | --- | --- | --- |
| `11.8.0` | `10.9.0.58` | `SM35` | `SM53` | `SM80` | `2022-10-03` |
| `12.9.2` | `11.4.1.4` | `SM50` | `SM53` | `SM80` | `2026-05-14` |

这些组件固定项同时得到上游发布表和再分发清单确认。CUDA 12.9 弃用 Maxwell/Pascal/Volta，13.0 移除支持。最低架构不是老工具包支持所有未来 GPU 的承诺。学习站（Learning Site）保留 SM75 基础 GPU 能力层级（Baseline GPU Capability Tier），不因历史库下限而降低标准。原生 Linux 仍是唯一受支持环境（Supported Environment）。

`cufftGetProperty` 查询动态链接库的 `MAJOR_VERSION`、`MINOR_VERSION` 和 `PATCH_LEVEL`，即 `10.9.0`、`11.4.1` 或 `12.3.0`，没有已文档化的第四段构建号属性。`cufftGetVersion` 给出整数，不证明完整软件包后缀；完整安装与加载的组件身份要另行记录。`cudaRuntimeGetVersion` 编码为 `1000*major+10*minor`，得到 `11080`、`12090`、`13030`，无法区分 Toolkit 更新号。CUDA 12.0 起它返回编译时常量，不初始化 CUDA。`cudaDriverGetVersion` 报告驱动支持的 CUDA 版本，不是驱动软件包版本。参见[库属性](https://docs.nvidia.com/cuda/cufft/index.html#cufftgetproperty)和[运行时版本管理](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART____VERSION.html)。

发布表分别关联 Linux 驱动 `520.61.05`、`575.57.08`、`610.43.02`。更低的主版本族次版本兼容下限，不能单独证明 PTX JIT 支持；应使用适当匹配或更新的驱动，并记入环境清单（Environment Manifest）。[NVIDIA 兼容性指南](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)明确警告旧驱动上的 PTX 问题。编译证据和运行证据始终分开。

## 低精度不进入可执行范围

FP16 与 bfloat16 要求二次幂长度，R2C/C2R 的实数一侧不能使用步幅，只支持单 GPU，不支持跨越超过 40 亿个元素的变换。当前参考明确实数变换按实数元素计长度。Bfloat16 内部结合 FP32 与 bfloat16 运算，不允许随意混搭 `cufftXtMakePlanMany` 的输入、输出和执行类型。有限输入的 FP16 直流求和也可能溢出。这些限制用于纸面推理，不是 EX19 已测试模式。

12.9.2 的发布历史指出，FP16 长度为一且 `istride/ostride > 1` 的变换，在 12.1 或更早版本存在内存问题，12.2 起以 `CUFFT_INVALID_SIZE` 拒绝。13.0 的另一项 FP16/bfloat16 长度为一的带步幅 R2C/C2R 正确性问题已在 **13.1 修复**，不能仍列为 13.3.1 未解决问题。异地 R2C 自定义输出步幅覆盖用户数据的问题在 12.4 修复，这不证明 11.8 的任意带步幅实数变换正确。因此共同可执行路径保持为 C2C。

## 回调有构建和正确性门槛

传统回调（legacy callback）需要分别编译的设备代码、设备链接、静态 cuFFT 及其 `libculibos` 依赖，并限于 64 位 Linux。它从 CUDA 11.4 起弃用，但 11.8 不会因此自动拥有替代接口。规划后用 `cufftXtSetCallback` 注册。架构选择须匹配库中提供的代码；12.9.2 发布历史保留了 12.8 引入的 SM120 传统回调仅支持 PTX 的要求。

LTO 回调在 CUDA 12.6 Update 2 引入，可用于 Linux/Windows 动态 cuFFT，以及提供静态库的平台；回调必须由 NVCC/NVRTC 生成 LTO-IR。在 create 之后、**规划之前**调用 `cufftXtSetJITCallback` 注册；移除 LTO 回调需要新建计划。nvJitLink 必须与 cuFFT 来自同一 Toolkit 主版本，且工具包版本相同或更新；NVRTC 也必须属于该主版本，并且不新于 nvJitLink。12.9 参考解释了 NVRTC 为回调符号生成包装的用途。13.2 起，一般 cuFFT LTO 内核也要求 NVRTC。跨 Toolkit 主版本要重建 LTO-IR；链接器不得早于其输入。来源：[LTO 要求](https://docs.nvidia.com/cuda/cufft/index.html#lto-load-and-store-callback-routines)和 [nvJitLink 兼容性](https://docs.nvidia.com/cuda/nvjitlink/index.html#compatibility)。

回调覆盖 FP32/FP64，不是低精度回调 API。LTO 偏移类型是 `unsigned long long`，传统回调是 `size_t`。LTO C2R 加载回调可能针对同一输入元素调用多次，不能依赖仅发生一次的副作用。不能依赖线程块执行顺序，不能因回调筛选就缩小输出容量，也不能在原地存储回调中覆盖别的元素。`__syncthreads()` 的文档安全尺寸限于 2/3/5/7 因子，且仍要求控制流收敛。11.8 起，异地加载传统回调不能参与 CUDA Graphs 捕获；LTO 回调从 12.6 Update 2 起消除了这一特定限制。

**CUDA 13.3 Update 1 仍列有已知正确性问题**，问题在 13.3 中发现：R2C/C2R 的实数侧 LTO 回调、**偶数长度**、**FP32 长度至少 8192 或 FP64 长度至少 4096**、以及**最大素因子至少 127**，这些条件必须同时成立。实数侧指 R2C 的实数加载或 C2R 的实数存储侧。这不是针对所有大 FFT 或所有回调的警告。未找到已确认修复版本；固定 13.3.1 不能消除该问题。练习只分类这些合取条件，不尝试执行受影响内核。

当前通用回调概述仍写有较早的素因子限制，而明确的 [13.3 LTO 覆盖说明](https://docs.nvidia.com/cuda/cufft/index.html#cufft-link-time-optimized-kernels)与发布说明扩展了单 GPU FP32/FP64 LTO 覆盖，包括更大素因子。应把版本限定说明与已知问题一起使用，不能扩大到 12.9、传统回调或多 GPU。EX19 不包含回调、LTO 主动启用或图捕获。

## 限定多 GPU 讨论

cuFFT Xt 在单进程、单主机连接的多个 GPU 间分配工作；多节点 cuFFTMp 是另一范围。文档上限为 16 个 GPU，超过八个要求 NVLink。设备须具有相同 CUDA 架构级别并支持统一虚拟寻址（UVA）。不支持带步幅输入输出、低精度或 LTO 回调。单批分布式变换只支持原地模式；单批一维实数变换不受支持。一维 C2C 要求二次幂长度和 2/4/8/16 个 GPU，相应最小长度为 64/64/128/1024。

一个分布式变换可以在 GPU 上留下置换顺序结果，需要理解描述符的拷贝操作恢复文档定义的自然顺序，主机输出也按自然顺序返回。即使关联了流，`cufftXtMemcpy` 在参与 GPU 之间仍同步执行。通信可能让更多 GPU 反而更慢。11.8 参考排除了多 GPU 的 Driver API 应用；较新参考允许主上下文，12.2 则放宽了关联流所属 GPU 上下文的条件。二维和三维描述符及尺寸表也存在版本差异，不能对所有通道给出无条件统一保证。参见[当前限制](https://docs.nvidia.com/cuda/cufft/index.html#supported-functionality)。这里不新增多 GPU 实验（Lab）。
