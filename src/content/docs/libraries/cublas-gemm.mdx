写出正确的分块矩阵乘法后，下一步不是默认它已经值得优化，而是为同一个问题建立一个可信的库实现对照。cuBLAS 不知道指针背后是几行几列；它只知道你声明的形状、步长和运算。参数合法但解释错误，仍可能得到一个尺寸正常、数值错误的结果。

## 学习目标

用约 25 分钟完成正文、纸面检查和检索问题。你应能从存储图推导调用参数，而不是背下一组 `m,n,k`：解释句柄（handle）的状态，处理全部转置组合，分开精度与标量位置，并说明何时可以读取或释放结果。外部实验时间另计。

## 前置知识

严格只依赖 [A08：正确的分块矩阵乘法](/algorithms/tiled-gemm-correctness/)和 [Q01：CPU 参考、容差与不变量](/correctness/cpu-references-tolerances-invariants/)，顺序为 `A08, Q01`。后面的 EX15、EX18、LAB12 和 VIS12 是相关资源，不增加前置依赖。

## 为什么还保留列主序接口

基础线性代数子程序（Basic Linear Algebra Subprograms，BLAS）把常用运算与实现分开。矩阵乘矩阵属于第三级运算，能在大量算术中重复使用同一数据。cuBLAS 在 GPU 上提供这些运算，同时保留方便 Fortran 程序接入的列主序（column-major）约定。

CUDA 4.0 引入的显式句柄接口让设备、流和标量传递状态不再藏在旧式全局接口中。本单元使用 `cublas_v2.h`，不使用已弃用的 `cublas.h` 接口。`cublasSgemm` 是同型 FP32 的专用入口；`cublasGemmEx` 可以分别声明存储与计算类型。库可能改变内核实现，所以库名不是特定指令、性能或逐位结果的证明。

## 先写清数学问题

通用矩阵乘法（General Matrix Multiplication，GEMM）的合同是 `C_out = alpha * op(A) * op(B) + beta * C_in`。`op(A)` 为 `m x k`，`op(B)` 为 `k x n`，C 为 `m x n`。`m,n,k` 描述**运算之后**的形状，不总是分配时 A、B 的行列数。

`CUBLAS_OP_N` 不变换，`CUBLAS_OP_T` 作转置（transpose），`CUBLAS_OP_C` 作共轭转置（conjugate transpose）。实数中 T 与 C 数值等价；复数中不能混为一谈。转置标志改变读取方式，不搬运数据，不修改物理步长。

`beta != 0` 时必须保留并正确初始化 `C_in`。`beta == 0` 时不要求旧 C 是有效输入，但 C 仍必须提供足够的可写输出空间。不要把“无需读取旧值”理解成“可传空输出指针”。本单元采用正维度、合法整数范围和互不重叠的 A、B、C 存储，避免把退化问题与别名规则混入第一份调用证明。

## 地址与主维度

主维度（leading dimension，`ld`）是相邻物理列或行起点之间的**元素数**，不是字节数。对零起点坐标 `(i,j)`，列主序元素偏移为 `i + j*ld`；行主序（row-major）为 `i*ld + j`。分配字节数还需要乘元素大小，并检查乘法溢出。

考虑列主序 `3 x 2` 矩阵，`ld=5`。第一列有效元素在偏移 0、1、2，第二列在 5、6、7；3、4 是填充（padding）。`(2,1)` 的偏移为 7，不是 5。若截取较大矩阵的子矩阵，只移动起始指针，仍使用原分配的列间距；把 `ld` 改成子矩阵行数会读到别的元素。

NVIDIA 文档所说的 BLAS 一起点索引，不意味着 C++ 指针前要空出一个元素。GEMM 接收的是存储起点，本单元主机端计算一直使用零起点。相反，`cublasIsamax` 等**返回位置**的 BLAS 例程使用一起点结果；在合法非空向量、正 `incx` 下，返回位置 p 对应的零起点元素偏移为 `(p-1)*incx`。应在接口边界转换位置，而不是对每个 GEMM 地址加一。

## 从转置推导所有主维度

下面是列主序下的推导表，不是性能推荐。为缩短表格，`M=max(1,m)`、`N=max(1,n)`、`K=max(1,k)`；形状是**未变换的存储形状**。每一行都要求 `ldc >= M`，C 分配覆盖 `ldc*n` 个元素。

| `transa,transb` | A 存储形状 | B 存储形状 | `lda` 下界 | `ldb` 下界 |
| --- | --- | --- | --- | --- |
| N,N | `m x k` | `k x n` | M | K |
| N,T | `m x k` | `n x k` | M | N |
| N,C | `m x k` | `n x k` | M | N |
| T,N | `k x m` | `k x n` | K | K |
| T,T | `k x m` | `n x k` | K | N |
| T,C | `k x m` | `n x k` | K | N |
| C,N | `k x m` | `k x n` | K | K |
| C,T | `k x m` | `n x k` | K | N |
| C,C | `k x m` | `n x k` | K | N |

A 的分配覆盖 N 情况的 `lda*k` 或 T/C 情况的 `lda*m`；B 则覆盖 N 情况的 `ldb*n` 或 T/C 情况的 `ldb*k`。下界合法不代表分配足够，更不代表数值正确。检查最后一个有效元素和全部分配范围，是与 API 参数检查分开的责任。

纸面检查：`m=3,n=5,k=2`，A 使用 T，B 使用 N。A 的存储为 `2 x 3`，不是 `3 x 2`；可取 `lda=4`。B 为 `2 x 5`，可取 `ldb=3`。选择 `ldc=6` 时，三份完整存储分别覆盖 12、15、30 个元素。只观察方阵或紧密布局，容易漏掉这类错误。

## 行主序不一定需要搬运

设应用真正需要行主序 `C = A*B`，A 为 `m x k`、B 为 `k x n`。同一块行主序 A 的字节，可解释成列主序 `A^T`。对等式作普通转置得到 `C^T = B^T*A^T`，因此交换操作数，调用尺寸改为 `n,m,k`，输出字节就仍是应用需要的行主序 C。

对于带填充、行步长分别为 `ra,rb,rc` 的 N,N 问题，cuBLAS 的第一个矩阵是 B，`lda=rb`；第二个矩阵是 A，`ldb=ra`；输出 `ldc=rc`。两项操作仍为 N。紧密布局时分别为 `n,k,n`。EX18 固定的 FP32 路径使用这一解释，不是在调用前偷偷转置数据。

更一般地，行主序目标 `op_a(A)*op_b(B)` 转成列主序调用时，交换 A/B、交换 `m/n`，并把标志顺序从 `op_a,op_b` 改成 `op_b,op_a`。保持各自物理行步长不变，再按上表审核交换后的调用。对于复数，外层使用普通转置而不是共轭转置，因此不要额外共轭 `alpha`、`beta`。这是一条代数映射，不是允许任意混合行列布局的捷径。

[VIS12：矩阵乘法的分块层次](/visuals/gemm-tiling-hierarchy/)可以帮助你指出一个输出元素沿 K 方向需要哪些输入。把视图上的逻辑坐标代入地址式即可；它既不展示 cuBLAS 的内部算法，也不证明本次调用会选用某个分块。

## 三种类型与两种标量位置

`GemmEx` 的存储类型说明如何解释 A、B、C 的字节；计算类型（compute type）说明运算精度政策；缩放标量类型（scale type）决定 `alpha`、`beta` 指针指向什么。它们必须组成官方支持表中的一行，不能自由拼接。

| 本单元审核的组合 | A/B/C 存储 | 计算类型 | `alpha,beta` 对象 |
| --- | --- | --- | --- |
| EX18 固定对照 | 全部 `CUDA_R_32F` | `CUBLAS_COMPUTE_32F_PEDANTIC` | `float` |
| 混合精度的静态对照 | A/B 为 `CUDA_R_16F`，C 为 `CUDA_R_32F` | `CUBLAS_COMPUTE_32F` | `float`，不是半精度 |

第二行只是阅读合同，不扩大 EX18。`CUBLAS_COMPUTE_32F_FAST_TF32` 允许使用 TF32 计算，而不是把存储自动改成新的数组类型；它也不是固定 FP32 对照的同义词。Pedantic 模式约束计算政策，但不保证与 CPU 串行累加顺序相同，也不授予任意数据规模的误差上界。

指针模式（pointer mode）与精度独立。主机模式 `CUBLAS_POINTER_MODE_HOST` 下，普通 GEMM 输入标量值在调用时被取用，标量对象可在返回后结束生命；矩阵工作仍可能异步。设备模式 `CUBLAS_POINTER_MODE_DEVICE` 下，标量必须可由设备访问，保持有效且不被改写直到计算完成。不能传 `double*` 冒充 `float*`，也不能用主机地址满足设备模式。输出标量例程的主机阻塞规则不要误套到 GEMM。

## 显式流与资源生命周期

流（stream）决定提交顺序；句柄保存流、指针模式和数学模式等可变状态。先选设备，再创建 `cublasHandle_t`，并在后续使用中保持对应 CUDA 上下文有效和当前。句柄不随一次 `cudaSetDevice` 自动迁移；不同设备需要对应句柄。多个主机线程同时改同一个句柄，可能让别人的下一次调用读到你的配置。

为第一份对照选择一个明确命名的非默认流和一个专用句柄，按下列顺序审核。表格是生命周期计划，不是运行日志。

| 阶段 | 必须成立的条件 |
| --- | --- |
| 准备 | 创建流和句柄；分配 A、B、C；在主机上保留输入与独立参考所需数据 |
| 配置 | `cublasSetStream` 绑定该流；显式设主机指针模式和所选数学政策；逐项检查状态 |
| 初始化 | 输入复制与需要的 C 初始化排在该流的 GEMM 之前；异步主机缓冲区在复制完成前保持有效 |
| 提交 | 调用 GEMM，检查 `cublasStatus_t`；成功返回不等于主机已能读结果 |
| 观察 | 在同一流提交结果复制，显式等待该流完成并检查 CUDA 返回值，然后作 CPU 比较 |
| 回收 | 确认所有使用者完成后释放缓冲区、销毁句柄、销毁流；部分初始化失败时只回收已创建资源 |

若后续消费者在另一条流上，增加事件记录与等待边；仅在主机上“先调用生产者，再调用消费者”不足以建立跨流依赖。既要检查库调用状态，也要检查复制和同步边界暴露的异步错误。发生执行错误后，不得把旧输出当成本轮结果。

工作区（workspace）是额外临时存储。传统 cuBLAS 可以使用其默认池；若自行设置，先 `cublasSetStream`，再 `cublasSetWorkspace`，因为前者**无条件重置**用户工作区配置。用户工作区须满足文档规定的 256 字节对齐并保持到使用结束。不要把销毁当成计时终点：12.9 文档说明 `cublasDestroy` 内部会触发设备同步，频繁创建与销毁也会把设置开销混入比较。

## 库结果仍需独立参考

库实现不是测试预言机（test oracle）的替代品。先从应用的逻辑坐标计算双精度 CPU 参考，不要复用待验证的 cuBLAS 参数变换来解释同一份错误。对每个逻辑输出检查有限性，并检查 `abs(got-ref) <= 1e-4 + 2e-5*abs(ref)`；这里的 `atol=1e-4, rtol=2e-5` 是 EX18 有界 FP32 测试数据的合同，不是 NVIDIA 对 GEMM 的普遍承诺。

[EX18](/examples/cublas-gemm/)是本单元库对照的规范可运行示例（Runnable Example），固定 FP32 pedantic、行主序交换操作数和双精度参考，并沿用 [EX15](/examples/tiled-gemm/)的测试数据，其中包括非零 beta 情况。不要手抄第二份 CUDA 实现到学习单元。一般带 `beta` 的练习必须把原始 C 保留下来；EX18 的固定行为以其项目文件为准，不能从本页的推广推导它已经覆盖所有转置、填充或混合精度情况。

小型非方阵、可辨识行列的输入、K 尾部和填充布局各能揭露不同错误。恒等矩阵和全零输入有用途，但单独使用容易掩盖交换与步长错误。首个失败应记录逻辑坐标、参考值、所得值、阈值和环境；不能通过放宽容差消除布局错误。

[LAB12](/labs/compare-gemm-with-cublas/)再把正确结果带入外部计时。与手写内核比较前，必须对齐输入、输出语义、精度、重复次数和计时范围；不能把一边的内核时间与另一边含分配、复制和句柄创建的时间比较。没有原始测量就不写“库更快”或加速比。
