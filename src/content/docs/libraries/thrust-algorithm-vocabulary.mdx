这里把 Thrust 用作算法词汇：先命名 transformation、scan、ordering 或 composition contract，再讨论 backend。[执行策略（execution policy，TERM-181）](/glossary/#term-181)选择 system，并可为 CUDA policy 绑定 stream；[花式迭代器（fancy iterator，TERM-182）](/glossary/#term-182)表示 generated、transformed 或 zipped range，无需为每个逻辑输入物化数组。

## 学习成果

- 把 `thrust::transform`、inclusive/exclusive scan 与 sorting APIs 映射回 A01、A03 与 A09 的合同。
- 选择 explicit 或 iterator-derived dispatch，同时不假设 pointer 会被验证或迁移。
- 组合 counting、transform 与 zip iterators，并声明 system、extent、value/reference 和 lifetime boundaries。
- 区分 `thrust::cuda::par.on(stream)` 与 `par_nosync.on(stream)`，放置必要 completion edges。
- 避开 v3.4.2 deprecations 与 known-issue boundaries，同时不声称本地 compilation、runtime behavior、fusion 或 speedup。

## 算法映射

| 既有合同 | v3.4.2 Thrust 词汇 | 仍由调用者负责的合同 |
| --- | --- | --- |
| A01：每元素一个 output owner | `thrust::transform`、`transform_if`、`transform_n` | Range extents、overlap、functor validity、system、output lifetime |
| A03：prefix semantics | `inclusive_scan`、`exclusive_scan` 与 by-key forms | Identity/init、associative operation、overlap、numerical acceptance |
| A09：ordering 与 movement | `sort`、`stable_sort`、`sort_by_key`、`stable_sort_by_key` | Key range、strict weak ordering、stability need、value extent/overlap |
| Generated index range | `cuda::counting_iterator` | Start、extent、arithmetic range、composition 选择的 system |
| Lazy projection | `cuda::transform_iterator` | Base lifetime、callable return semantics、system、consumer requirements |
| Lockstep fields | `cuda::zip_iterator` | Equal logical extents、references/values、component lifetimes/systems |

## Transform 命名 A01 的 ownership contract

`thrust::transform` 对元素应用 unary/binary callable 并返回 output-end iterator；这是 [A01](/algorithms/elementwise-map/)的 library vocabulary。Exact input/output range 可以 in place，其他 partial overlap 违反 tagged interface precondition。Binary form 要求两个输入 range 都覆盖 requested extent。不能让正确性依赖 functor argument 的 identity/address；这种用法已 deprecated。

Explicit policy 选择 system；policy-free overload 从 iterators 推导 systems 并寻找 compatible common system。两种形式都不会验证 logical extents、object lifetime 或 numerical acceptance。

## Scan 命名 A03 的 prefix contract

`thrust::inclusive_scan` 与 `thrust::exclusive_scan` 暴露 [A03](/algorithms/inclusive-exclusive-scan/)的 prefix operations。Inclusive output 包含 current item；exclusive output 从 declared initial value 开始，或使用默认 zero form。Custom operator 必须 associative，不要求 commutative。Exact in-place input/output 可用，partial overlap 不可用。

Tagged interface 警告：floating-point addition 等 pseudo-associative operation 可能在不同执行中产生不同结果。因此 parallel floating-point scan 必须使用 problem-specific acceptance rule，不能假设它与 serial left fold 逐位相同。

## Sort 命名 A09 的 ordering 与 movement contract

`thrust::sort` 与 `thrust::stable_sort` 对 mutable random-access ranges 排序并要求严格弱序（strict weak ordering）；这些名称直接连接 [A09](/algorithms/sorting-selection-compaction/)。`sort` 不保持 equivalent elements 的原顺序，`stable_sort` 保持。By-key forms 随 key range 移动 value range，tagged contract 禁止 key/value overlap。

Stability、comparator semantics、range extent、mutability 与 movement 仍是应用决策。Tagged CUDA implementation 选择 radix 或 merge path 属于 version-specific implementation detail，不是 public promise 或 performance evidence。

## Execution policy、dispatch 与 stream

| 形式 | v3.4.2 决策边界 |
| --- | --- |
| `thrust::seq` | 选择 sequential execution |
| `thrust::host` | 选择 configured host system；invocation/dereference order 仍 unspecified |
| `thrust::device` | 选择 configured device system；CUDA backend 不验证或迁移 supplied memory |
| 无 explicit policy | 从 iterators 推导 systems；incompatible host/device systems 通常 compile-time failure |
| `thrust::cuda::par.on(stream)` | 使用 supplied stream；tagged transform、scan、sort backend 返回前执行 optional synchronization |
| `thrust::cuda::par_nosync.on(stream)` | 允许省略 optional synchronization，可能在完成前返回；它是 hint，不承诺绝不同步 |

Same-stream work 按 enqueue order 排序，因此 no-sync producer 可供 same-stream consumer 使用而不等待 host。Host access、memory release 或另一 stream 需要有效 completion/dependency edge。返回 host value 的算法仍可能需要完成。Asynchronous CUDA error 可在后续 synchronization point 暴露。Allocation 与 callable 必须活到 unfinished work 完成。

Tagged v3.4.2 `temporary_buffer.h` 的默认 no-sync path 先尝试 `cudaMallocAsync`/`cudaFreeAsync`，失败后可回退 synchronous allocation；`util.h` 根据 compilation mode 选择 legacy/per-thread default stream。这些是 source-derived implementation facts，不是学习站环境中 observed allocation、synchronization 或 latency behavior。

## 不物化每个 range 的 iterator composition

当前 v3.4.2 `<cuda/iterator>` surface 提供 `cuda::counting_iterator`、`cuda::transform_iterator`、`cuda::zip_iterator` 与 `cuda::zip_transform_iterator`。Counting iterator 表示连续值；transform iterator 在 dereference 时应用 callable；zip iterator 同步推进 components，并暴露 tuple-like values/references；zip-transform iterator 合并 lockstep dereference 与 n-ary transformation。

一种 composition 可用 counting iterator 表示 indices，用 value-returning transform iterator 把 index 映射为 segment key，再让 scan-by-key 消费 virtual key range。另一种可 zip 等长 keys/payloads 做 lockstep transform。Virtual range 可以避免存储 intermediate range 并允许优化，但不保证 kernel 融合、更少 traffic 或加速。

组合前写出四份合同：

- **Extent：** 每个 consumed range 覆盖相同 declared logical interval；zip 不会安全地停在最短 component。
- **System：** Component iterators 与 explicit policy 选择 compatible host/device path。
- **Value/reference：** 对 temporary value 的 transformation 返回 value，不返回 dangling reference。
- **Lifetime：** Containers、callable state、stream 与 output 保持有效，直到 required work 完成。

## 一个 composition packet

对于“平方每个 value，做 inclusive scan，再按 prefix stable-sort records”，先声明三个 stage，而不是写 opaque chain。Stage one 是 `N` inputs/outputs 的 A01 transform；stage two 是 A03 inclusive scan，其 FP32 tolerance 接受合法 parallel order difference；stage three 是 A09 stable by-key sort，包含 `N` keys、`N` records 与 strict weak ordering。记录每个 range 的 system、extent、overlap、lifetime、stream 与 completion edge。

只有核对 scan consumer 的 iterator contract 与 callable lifetime 后，才可用 transform iterator 替代 materialized square array。没有在 exact environment 检查并测量 selected artifact，就不能声称 fusion 或更少 transactions。

## 当前 pin 的 deprecations

这里教授的 core algorithms，包括 `transform`、scans 与 sorts，在 v3.4.2 中没有 deprecated。Legacy `thrust::counting_iterator`、`thrust::transform_iterator` 与 `thrust::zip_iterator` 在该 pin 也没有正式 deprecated，尽管 current owner guidance 通常偏好新的 `cuda::` counterparts。

CCCL 3.4 deprecated `thrust::constant_iterator` 与 `thrust::strided_iterator`，替代项是 `cuda::constant_iterator` 与 `cuda::strided_iterator`。Tagged source 还把若干 `thrust::tuple`、functional aliases、iterator traits 与 standard-like iterator helpers 标为 deprecated，建议使用 `cuda::std` 或 `cuda::` forms。必须检查 exact tagged declaration，不能泛化为“所有 fancy iterators 都 deprecated”。

## v3.4.2 的限定已知问题

- Issue [#10684](https://github.com/NVIDIA/cccl/issues/10684)记录 legacy host `reverse` 与 `thrust::zip_iterator` 的问题，包括 descending sort-by-key path。Fix 在 immutable v3.4.2 之后落地，因此本 pin 不把该 composition 发布为已验证。
- Open issue [#10965](https://github.com/NVIDIA/cccl/issues/10965)报告 optional-stride legacy `make_counting_iterator(start, stride)` 的 distance behavior 错误。当前边界使用 unit-stride counting 或另行检查的 modern composition。
- Open issue [#1155](https://github.com/NVIDIA/cccl/issues/1155)强调 legacy zip equality/distance 依赖一个 component。应要求 aligned extents，不能期待 shortest-range termination。
- Issue [#2747](https://github.com/NVIDIA/cccl/issues/2747)跟踪 tagged `stable_sort` 文档示例实际调用 `sort`。不要复制这些 examples；textual stable-order contract 仍是权威。

这是一份限定教学 ledger，不是完整 defect list。v3.4.2 之后的 issue state 不会改变 pinned release。
