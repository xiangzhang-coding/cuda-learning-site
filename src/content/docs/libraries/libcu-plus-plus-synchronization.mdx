同步对象不知道自己保护的是哪份应用数据。程序员必须把对象操作与载荷（payload）、读者以及下一次存储复用联系起来。libcu++ 为这份证明提供面向标准的词汇，却不会补上缺失的证明。本单元只做纸面合同审查，不执行 CUDA，也不要求硬件。

## 学习成果

- 区分主机（host）`std`、已实现的 `cuda::std` 子集与带作用域的 `cuda::` 扩展。
- 为普通 32 位发布标志分别选择同步作用域（synchronization scope）与内存序（memory order）。
- 在获取（acquire）读取实际观察到释放（release）写入的前提下，证明载荷的内存可见性（memory visibility），并说明对象生命周期和复用边界。
- 计算屏障（barrier）初始化、到达、等待和退出的效果，以及下一个屏障阶段（barrier phase）的预期计数。
- 跟踪流水线（pipeline）中各流水线阶段（pipeline stage）从获取到释放的所有权变化，并选择正确回退而不虚构加速结论。

## 先修关系

精确先修顺序为 [M05：同步作用域](/memory/synchronization-scopes/)、[M13：异步复制（asynchronous copy）与流水线](/memory/asynchronous-copy-pipelines/)和 [M19：C++ 方言（C++ dialect）边界](/toolchain/cpp-dialect-boundaries/)，即 `M05, M13, M19`。它们同时列为相关单元，供读者回顾心智模型、存储协议和编译坐标。作用域从来不替代 M05 对原子性（atomicity）、顺序（ordering）、会合（rendezvous）、可见性和进展（progress）的区分。

## 为什么需要异构标准库？

传统 CUDA 内建函数（intrinsics）明确暴露执行层级，但一次原子更新并不能表达完整的生产者/消费者协议。C++11 提供了标准原子与内存序词汇；C++20 又加入原子引用、可复用屏障等设施。把这些推理带入异构程序时，还必须回答：跨越内存与执行边界后，哪些线程能够参与？libcu++ 沿用熟悉的概念，同时暴露 CUDA 特有的作用域与异步操作合同。

| 接口范围 | 含义 | 不承诺的事情 |
| --- | --- | --- |
| 主机 `std`，如主机编译器的 `<atomic>` | 主机标准库及其支持的方言 | 任意设施都可在设备（device）上调用，或任意对象都能在 CPU/GPU 间互操作 |
| `cuda::std`，如 `<cuda/std/atomic>` | libcu++ 已实现、面向标准的主机/设备设施 | 完整实现全部标准库设施，或在每种编译模式下具有相同可用性 |
| `cuda::`，如 `<cuda/atomic>` | 显式线程作用域与 CUDA 同步对象等扩展 | 覆盖存储可访问性、生命周期或调度约束的新内存模型 |

不能改一个命名空间就宣称移植完成。一些熟悉的较新标准设施可以在受支持的较早语言模式中提供，但这不等于支持整个新方言。可用性由选定版本和精确头文件决定，而不是由当前 C++ 标准草案的日期决定。

## 原子作用域：明确通信线程

[同步作用域（synchronization scope，TERM-077）](/glossary/#term-077)决定原子协议覆盖的线程。它既不选择内存位置，也不决定周围访问的顺序。本次固定版本中，`cuda::atomic` 和 `cuda::atomic_ref` 都默认使用**系统作用域（system scope）**；应显式写出实际需要的作用域，而不是依赖默认值。

| 显式作用域 | 本单元覆盖的通信 | 独立条件 |
| --- | --- | --- |
| `cuda::thread_scope_block` | 同一个线程块（thread block）的线程 | 每个访问者均属于该线程块，且能够访问对象 |
| `cuda::thread_scope_device` | 同一设备、同一内存同步域（memory synchronization domain）的线程 | 跨线程块存储可访问，且协议不假设所有线程块同时驻留 |
| `cuda::thread_scope_system` | 潜在的 CPU/GPU 或跨设备参与者 | 内存分配类型、设备和操作确实支持所需的系统作用域原子通信 |

两个处理器都能使用某个指针，不足以证明系统作用域原子支持。统一或映射存储仍需检查内存分配类型与设备能力。不要对同一对象混用不同作用域合同的并发原子访问。两个线程都在一块 GPU 上，也不能让设备作用域（device scope）的标志授权不同内存同步域之间的通信。

扩大作用域不能让尚未获调度的生产者开始运行。任意网格（grid）自旋屏障（spin barrier）可能让等待中的线程块占满设备，而释放它们所需的线程块无法执行。应使用有文档合同的执行边界，例如阶段间有序的内核完成，或另行证明的协调机制。系统作用域与最强内存序都不保证程序取得进展。

## 内存序：证明发布边

[内存序（memory order，TERM-185）](/glossary/#term-185)描述原子操作如何约束周围访问。非原子载荷的[内存可见性（memory visibility，TERM-078）](/glossary/#term-078)需要完整关系，而不是附近恰好存在一个原子标志。

考虑一个写者、一个读者、双方使用前已初始化为零的标志，以及单次交换期间不会被覆盖的载荷。写者先写载荷，再以 release 顺序向标志存入一；读者以 acquire 顺序读取标志。**只有当该读取的值来自这次 release 写入**，且两次操作具有足够且兼容的作用域时，写者此前的载荷写入才先发生于（happens before）读者此后的载荷读取。读到初始零不授予消费权限。复用协议中，数值一自身也不能表明是哪一代数据发布了它。

| 操作选择 | 适合的用途 | 没有建立的保证 |
| --- | --- | --- |
| 宽松（relaxed）标志操作 | 标志本身的原子访问 | 发布独立的非原子载荷写入 |
| Release 写入，及读取该写入的 acquire 读取 | 让载荷生产先于消费 | 消费者已完成、安全覆盖或生产者能够取得进展 |
| Acquire-release 读改写（read-modify-write） | 合法操作同时需要两个方向的顺序 | 对普通读取或写入使用 acquire-release 的许可 |
| 顺序一致（sequentially consistent）操作 | 为作用域合适的操作提供更强顺序 | 修复过窄作用域或不可访问存储 |

普通原子读取不能使用 release 或 acquire-release；普通原子写入不能使用 acquire、consume 或 acquire-release。本单元使用 release/acquire，不构造依赖 consume 的协议。独立内存栅栏（memory fence）或 `volatile` 标志都不能替代已证明的读取来源（reads-from）发布关系。

若要复用，需要增加反向所有权移交：读者消费后以 release 发布一次确认，写者以 acquire 读取该确认后才能再次修改载荷。应标识每一代，或用其他方式证明旧标志不会被误认成新发布。这是第二份顺序证明，不是任意轮询都会取得进展的承诺。静态证明可以说明“观察发生时什么是安全的”，而不实现等待循环。

## `atomic_ref`：借用对象，不延长生命周期

`cuda::atomic` 拥有自身原子对象；`cuda::atomic_ref` 对已有对象施加原子操作，不会分配、初始化、移动对象，也不会延长其生命周期。初始化必须先于向使用者发布；被引用对象必须活得比所有引用和通过引用进行的访问更久。

对这里的普通 32 位整数，v3.4.2 的 `required_alignment` 为 `sizeof(T)`，因此对象地址必须满足四字节对齐。应检查实际被引用地址，而不只看分配器返回的基地址，因为字段偏移可能破坏对齐证明。该标签下的实现排除带填充位的表示。这些结论不授权任意结构体或对象大小。

引用仍在使用时，所有对象访问都必须遵守原子引用的访问纪律。不要让普通读取或写入与原子引用竞争，不要对重叠子对象建立不兼容引用，也不要并发混用作用域。销毁一个引用既不会等待其他线程，也不能安全结束被引用对象的生命周期。对象销毁或恢复普通访问都应位于已证明没有在途访问的边界之后。

## 屏障阶段：先数到达，再等待

[屏障阶段（barrier phase，TERM-186）](/glossary/#term-186)是一轮预期到达及其完成，不等于可复用缓冲区，也不等于流水线阶段。共享内存声明只保留存储，**不会**初始化屏障。一个指定初始化者设置正的预期到达计数（expected arrival count），随后由独立的可见性边，例如全线程块同步，保证其他使用者先看见初始化。屏障不能用自己来引导自己的初始化。

| 操作或边界 | 当前阶段 | 后续阶段或存储 |
| --- | --- | --- |
| 初始化 | 使用前建立预期计数 | 对象在全部参与阶段中保持存活 |
| `arrive` | 贡献指定到达计数，并取得阶段令牌（phase token） | 单纯到达不授权读取其他参与者的数据 |
| 使用匹配令牌的 `wait` | 等待对应阶段完成 | 此后才能消费该完成边界保护的数据 |
| `arrive_and_wait` | 合并一次到达及其等待 | 不证明所有消费者已经读完 |
| `arrive_and_drop` | 贡献该参与者的本轮到达 | 减少未来预期计数；不是跳过本轮再任意加入的许可 |

对本单元采用的普通等待者与默认完成行为，阶段边界让到达前的工作先于等待后被授权的读取。到达与等待之间可以安排独立工作，但不能读取尚依赖完成的数据。令牌属于相应屏障阶段，不是可无限复用的通行证。未来预期计数按屏障合同重置，并计入永久退出，而不是由调用者在每块数据块（tile）后重新初始化。

设四个参与者为 A、B、C、D。A、B、C 各自到达并等待，D 使用 `arrive_and_drop`。当前轮仍收到**四次**到达，下一轮则期待**三次**。直接省略 D 会让当前轮少一次到达；让 D 又在三人轮到达则会过量贡献。如果 D 只是想临时跳过某次迭代，应重设参与协议，不能把退出当成暂停按钮。

共享数据块有两条所有权边界：**可以读取**与**可以覆盖**。完成就绪阶段（ready phase）允许消费者开始读取；较快生产者从该阶段返回，并不意味着较慢消费者已经读完。复用前需要消费完成阶段（consumed phase），或等价的、具有明确合同的移交。绑定屏障的 `memcpy_async` 还会把复制完成绑定到该屏障阶段；应将复制完成与声明的线程到达分开记账，不能把发出复制当成线程到达。本单元不承诺自定义完成行为或没有等待者的特殊情况。

练习采用交替的就绪/消费完成协议：A、B、C 在**每个**就绪阶段和消费完成阶段都调用 `arrive_and_wait`。每个继续参与的线程必须等待当前阶段完成，才能开始下一阶段或再次到达。A 在就绪阶段到达前写完；B/C 在就绪等待返回后读取，在消费完成阶段到达前读完；A 只在消费完成等待返回后覆盖。阶段名称只是账本标签，不是将到达送往指定阶段的参数：提前到达即使标作“下一轮就绪”，也仍会递减屏障的当前倒计数。因此，只让 A 等待并不足够。D 只通过 `arrive_and_drop` 向第一轮就绪阶段贡献一次，以后不再加入。

## Pipeline 生命周期：消费者释放后才能归还 stage

[流水线（pipeline，TERM-109）](/glossary/#term-109)管理由有限个[流水线阶段（pipeline stage，TERM-110）](/glossary/#term-110)组成的先进先出队列。阶段跟踪在途工作的所有权，实际数据缓冲区仍由应用拥有。对使用共享状态的流水线，`make_pipeline` 是其声明线程组上的集体操作（collective）：成员使用同一共享状态，并按选定重载提交一致的构造参数，包括所需的生产者数量或角色分配。

统一角色（unified participation）让每个成员兼任生产者和消费者；分离角色（partitioned participation）将指定成员分为生产者或消费者。角色计划与参与者计数必须同时匹配构造和每个阶段的操作；只负责生产的成员不能替代缺失的消费者释放操作。

| 步骤 | 所有权事实 | 存储责任 |
| --- | --- | --- |
| 生产者获取：`producer_acquire` | 等待并获得可复用阶段 | 不覆盖仍由消费者持有的阶段 |
| 发出复制 | 将工作附着到该阶段 | 源区和目标区保持有效；复制可能读取源区时不得修改它 |
| 生产者提交：`producer_commit` | 提交该生产者的批次 | 提交不证明目标区已经可读 |
| 消费者等待：`consumer_wait` | 确认待消费阶段已经就绪 | 必须先经过所需完成边界才能读取 |
| 消费 | 使用已完成的载荷 | 目标区在最后一次被授权读取结束前保持稳定 |
| 消费者释放：`consumer_release` | 放弃消费者对该阶段的所有权 | 复用须等待所需消费者释放，再由生产者重新获取 |

共享状态的生命周期必须覆盖所有使用它的流水线对象；缓冲区则必须存活到尚未完成的复制与消费者访问全部结束。`quit` 只释放流水线所有权，不是排空（drain）或取消（cancellation）操作，也不会补上缺失的到达。结束参与时应逐项处理尚未完成的工作，不能退出后立即释放共享状态。

在相关加速路径上，线程束（warp）内分歧的提交可能造成线程束纠缠（warp entanglement），让消费者等待比其局部推理更多的批次。应在提交前让相关线程束参与者重新汇合（reconverge）。这与协作复制（cooperative copy）要求声明线程组的全部成员调用同一复制是两项独立责任；两者都不允许用“当前恰好活跃的线程束通道（lanes）”临时发明另一个线程组。

## 复制合同：回退仍需完成边界

[异步复制（asynchronous copy，TERM-108）](/glossary/#term-108)是 API 合同，不是硬件一定让它与计算重叠的承诺。选择绑定屏障或流水线的操作后，应保留它的完成协议。

- 源区和目标区必须有效、不重叠，并适合平凡字节复制（trivial byte copy）。这不是对象构造，也不会调用非平凡复制构造函数。
- 线程组重载（group overload）要求该组全体成员以相同参数调用；非线程组重载（nongroup overload）中每个调用者各自发出复制，应划分不重叠的目标区工作，不能重复向同一数据块发出重叠复制。
- `cuda::aligned_size_t<N>` 断言**两个地址和字节数**都是对应对齐值的整数倍。它是调用者提交的证明，不是要求库四舍五入长度或重新对齐存储。错误证明属于未定义行为（undefined behavior）。
- 无法证明对齐时，应选择能处理该情况的普通大小参数重载，或使用带显式生产者/消费者移交的同步复制。两种选择都不取消就绪与安全复用责任。

符合条件的全局内存到共享内存（global-to-shared）`cp.async` 加速路径要求 SM80 或更新架构，并满足其他前提。在语义受支持但不能采用该加速的路径上，回退可以同步搬运数据，同时保留 API 的完成协议。不能因某次观察中分派到的实现恰好同步，就删除等待或释放操作。可选的 SM90+ TMA 能力需要单独审查事务 API，本单元不教授。

精确 v3.4.2 复制定义还存在编译模式边界：绑定屏障的 `memcpy_async` 重载定义受 `_CCCL_CUDA_COMPILATION` 保护。库面向主机和设备，不代表仅由 GCC 编译的翻译单元能看见全部异步复制接口。经 CUDA 编译的主机路径可以同步复制，这不说明设备上的执行是否重叠。当前文档与标签下头文件展示的签名有差异，所以本页不展示函数签名；以标签为准，包括 `producer_commit` 返回 `void`，而不是想象中的完成凭证。

## 可移植性是交集，不是 namespace 属性

标签下的 README 声明支持 C++17/C++20，一般最低要求 GCC 7 / Clang 7；C++20 将下限提高到 GCC 10+ / Clang 11+。将这些要求与 NVCC 主机编译器范围、选定的 [C++ 方言（C++ dialect，TERM-125）](/glossary/#term-125)取交集，再检查实际操作系统、编译器、头文件与目标架构。原生 Linux 是学习站唯一的受支持环境（Supported Environment）。

| 选定工具包通道（Toolkit Lane） | 取交集前的 NVCC Linux 主机编译器范围 | L05 政策边界 |
| --- | --- | --- |
| 12.9.2 | GCC 6-14；Clang 7-19 | 选择 C++17 或 C++20；GCC 6 不满足 CCCL 最低要求，C++20 还会进一步提高下限 |
| 13.3.1 | GCC 6-15；Clang 7-21 | 选择 C++17 或 C++20，且 CCCL 不得早于该工具包所附版本 |
| 11.8.0 | 不属于选定 v3.4.2 的合格组合 | 回退到较旧的随附库时，需单独复核 API 和源码，不能自动继承本合同 |

CUDA 12.9 主机编译器政策来自 **12.9.1 Update 1** 归档指南，用于选定的 12.9.2 通道；13.3 政策来自 2026-09-05 访问的当前 **13.3 Update 1** 指南。CCCL 政策接受 CUDA 12.x 的最新补丁版本，对 CUDA 13.x 则要求 CCCL 不早于随附版本；只有主版本标签不满足任何一项政策。EX10 的窄范围 GCC 14 C++23 探测不授予 libcu++ C++23 支持。

屏障与流水线 API 的最低要求为 SM70+，与学习站及选定支持政策的 **SM75+** GPU 下限不同。因此 SM75 可以进入语义回退审查，却不能据此声称 SM80 加速。标签下的持续集成（CI）矩阵将 `12.X` 映射为 **12.9**，将 `13.X` 映射为 **13.2**。读到该配置既不证明实际覆盖了 13.3，也不提供本地编译结果。支持政策、测试配置、生成指令、正确执行与实测执行重叠是不同结论。
