练习题库（Practice Bank）收录跨课程反复出现的原创问题。每个条目都说明先修学习单元（Learning Unit）、硬件门槛（Hardware gate）、验收条件、提示、解答和来源依据；它不是复制来的问答清单。

## 如何使用

先按条目的先修链接复习，再不看参考解答完成自己的产物。提示按层展开；参考解答用于复核边界，不替代作答。当前页面只发布下面五十个完整条目，不用空白题目预告未来内容。

## PB-R0-001：修复证据状态（Evidence Status）记录

- **ID 与双语发布对（Publication Pair）：** PB-R0-001；位于 `practice-bank` Publication Pair。
- **类型与难度：** 核心心智模型；基础。
- **先修条件：** [O02：诚实记录证据状态](/start/evidence-status/)。
- **硬件门槛（Hardware gate）：** 无；只分析文本记录。
- **相关学习单元：** O02。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份发布说明写道：“Linux 构建因容器仓库超时而跳过。贡献者在自己的 GPU 上贴出 `PASS`，所以项目已经 Compile-Checked 和 Runtime-Verified。网页测试也证明浏览器演示可以算 CUDA 运行。”请重写成一条诚实记录。

**约束：**

- 只能使用 O02 的受控 Evidence Status。
- 不能虚构 manifest、构建日志、观察日期或维护者复现。
- 必须把预期观察和已记录观察分开。

**预期证据：** 一条逐句修订的状态记录，明确每项声明已有的证据、仍缺的材料和保留的状态。

**验收条件：**

- blocked build 没有 Compile-Checked。
- 社区 `PASS` 在缺少完整 Environment Manifest、日志、标准和日期时不能授予 Community-Observed。
- 维护者复现前不能授予 Runtime-Verified；若活动需要 GPU 行为，则保留 Pending Hardware Verification。
- 网页测试和浏览器模型不授予任何 CUDA Evidence Status。

<details><summary>提示 1</summary>逐句问“谁做了什么，留下了什么可复核材料”。</details>

<details><summary>提示 2</summary>blocked 不是 passed；一句 `PASS` 也不是完整社区报告。</details>

**解答：** “声明的编译工作因容器仓库超时而未执行，因此没有 Compile-Checked。社区提供了未经完整记录的 `PASS` 文本，缺少 manifest、日志、标准和日期，暂不能授予 Community-Observed。维护者没有在声明的 Reference Environment 中复现；如果验收要求 GPU 行为，运行轴保持 Pending Hardware Verification。网页质量测试只验证网站，不授予 CUDA 状态。预期输出与已记录观察均未形成合格记录。”

**常见错误：** 把 blocked 写成失败后仍授予状态；为了“尊重社区”而省略 manifest；把网页 CI 当成 CUDA 编译；删除 Pending Hardware Verification 却没有维护者证据。

**来源依据（Source basis）：** 本站 [O02](/start/evidence-status/) 的原创证据合同，以及 NVIDIA `nvcc` 13.3.1 [supported phases](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#supported-phases)对编译和运行阶段的区分。

## PB-R0-002：补全 manifest 并修复支持边界

- **ID 与双语发布对：** PB-R0-002；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；基础。
- **先修条件：** [O03：读懂环境清单（Environment Manifest）](/start/environment-manifest/)。
- **硬件门槛（Hardware gate）：** 无；使用假设记录，不运行 CUDA。
- **相关学习单元：** O03。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份记录只有“8 GB GPU、CUDA 12、WSL、kernel 0.2 ms”，并声称“属于完整层级，且本站支持这个环境”。列出必须补充的 manifest 字段，并修复两条结论。

**约束：**

- 不猜 GPU 型号、compute capability、driver、Toolkit patch 或测量方法。
- 正确性和性能字段都要覆盖，但 result 保持未观察。
- 只按 O03 的 Supported Environment 和 GPU Capability Tier 定义判断。

**预期证据：** 一份待补字段清单、两条修订后的支持/层级结论，以及把无方法性能文字隔离为未审核原始记录的说明。

**验收条件：**

- manifest 分开 GPU identity、compute capability、GPU count、driver、Toolkit、component、NVCC、host compiler、OS、workload/shape、memory、permissions、exact command、correctness 和 observation date。
- 性能附录包含 baseline、hypothesis、clocks/power、warm-up、synchronization、timer/profiler version、statistics/sample method 和 interpretation boundaries。
- 结论说明 WSL 不是本站 Supported Environment；8 GB 本身不能决定 Modern Single-GPU Capability Tier。

<details><summary>提示 1</summary>先把“CUDA 12”拆成 Toolkit patch、driver 和相关 component versions。</details>

<details><summary>提示 2</summary>`0.2 ms` 没有同步、工具版本、样本和基线时不可解释。</details>

**解答：** 建立硬件、软件、工作负载、执行、正确性、日期和性能七组字段，所有未知值标成“待采集”并注明查询方法。把 `0.2 ms` 移到“未审核原始文字”，结果字段保持空。支持结论改为：“原生 Linux 是唯一 Supported Environment；WSL 只可作为非支持比较。”层级结论改为：“需要 compute capability 8.0 或更新、至少 8 GB，并同时满足 count、features 和 permissions，才能进入 Modern Single-GPU Capability Tier；现有记录无法判断。”

**常见错误：** 把“CUDA 12”当作完整软件坐标；用显存代替 compute capability；接受一个没有 synchronization 的延迟；把 NVIDIA 产品支持写成本站责任。

**来源依据（Source basis）：** 本站 [O03](/start/environment-manifest/) 的原创 manifest 和支持合同，以及 NVIDIA [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)与 [compute capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)。

## PB-R0-003：在运行前审查索引预测

- **ID 与双语发布对：** PB-R0-003；位于 `practice-bank` Publication Pair。
- **类型与难度：** 概念与实现；基础。
- **先修条件：** [F01：从预测到第一个 CUDA kernel](/foundations/first-cuda-kernel/)。
- **硬件门槛（Hardware gate）：** 无；只做静态推理。
- **相关学习单元：** F01。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 对 `N = 65`、`blockDim.x = 32` 的一维向量加法，给出 block 数、总 launch thread 数、最后一个合法 index，并判断最后一个 block 中 `threadIdx.x = 0` 和 `1` 的 bounds 状态。解释为什么 bounds check 仍然必需。

**约束：** 先写公式；不运行程序；零起始索引；不能把 launch 范围当作逻辑数据范围。

**预期证据：** 一张坐标表和一段不超过五句的所有权解释。

**验收条件：** 得到 3 个 block、96 个 launch thread、最后合法 index 64；识别最后 block 的局部 thread 0 合法、1 越界；说明 31 个越界 thread 必须跳过访问。

<details><summary>提示 1</summary>Block 数使用 `ceil(65 / 32)`。</details>

<details><summary>提示 2</summary>最后一个 block 的 `blockIdx.x = 2`，所以其全局 index 从 64 开始。</details>

**解答：** `ceil(65 / 32) = 3`，总共 launch 96 个 thread。最后一个合法元素是 index 64。最后 block 中局部 thread 0 的 global index 是 64，IN BOUNDS；局部 thread 1 的 global index 是 65，OUT OF BOUNDS。其余局部 thread 也越界，因此 kernel 必须用 `index < N` 保护访问。

**有效替代方案：** 可以用数轴或 VIS02 的静态坐标表表达，只要公式和 bounds 理由仍可复核。

**常见错误：** 向下取整成两个 block；把 index 65 当成最后元素；认为多出的 thread 没有被 launch。

**来源依据（Source basis）：** 本站 [F01](/foundations/first-cuda-kernel/) 与 [VIS02](/visuals/indexing/) 的原创索引模型，以及 NVIDIA [Introduction to CUDA C++](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html)。

## PB-R0-004：修复不完整的错误与正确性边界

- **ID 与双语发布对：** PB-R0-004；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；基础。
- **先修条件：** [F01](/foundations/first-cuda-kernel/)。
- **硬件门槛（Hardware gate）：** 无；审查假设流程。
- **相关学习单元：** F01、O02。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个程序只检查 `cudaMalloc` 和最终输出文字，然后声称“无报错且 GPU 正确”。写出缺失边界，并定义一个元素的接受规则。

**约束：** 使用 EX02 已声明的 Runtime 流程和容差；不得虚构输出；必须区分 API 成功与数值正确。

**预期证据：** 按执行顺序排列的检查清单，以及一条可计算的数值接受条件。

**验收条件：** 包含三次 allocation、两次 H2D copy、launch error、synchronization、D2H copy、CPU comparison 和三次 free；绝对 `1e-5` 或相对 `1e-5` 满足其一即接受；指出一行输出不能替代这些检查。

<details><summary>提示 1</summary>Launch 返回与 kernel 完成是两个边界。</details>

<details><summary>提示 2</summary>失败条件是绝对和相对标准都不接受，而不是任一不接受。</details>

**解答：** 在三次 `cudaMalloc` 后检查两次 H2D copy；launch 后先查 `cudaGetLastError`，再用 `cudaDeviceSynchronize` 等待并检查执行；检查 D2H copy；逐元素与独立 CPU reference 比较；最后检查三次 `cudaFree`。若 `abs(expected-actual) <= 1e-5` **或**该差值 `<= 1e-5 * max(abs(expected), abs(actual))`，元素通过。API 全部成功和数值全部通过缺一不可。

**有效替代方案：** 可以用状态机或时序图代替清单，但必须保留相同顺序和两个独立验收层。

**常见错误：** 只同步不检查 launch；把两个容差写成 AND；把 host test 当作 GPU 结果。

**来源依据（Source basis）：** 本站 [F01](/foundations/first-cuda-kernel/) 与 [EX02](/examples/vector-addition/) 的 canonical error/correctness contract，以及 NVIDIA [CUDA Runtime API](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html)。

## PB-R0-005：审查一份 LAB02 证据申请

- **ID 与双语发布对：** PB-R0-005；位于 `practice-bank` Publication Pair。
- **类型与难度：** 证据审查与实验准备；基础。
- **先修条件：** [F01](/foundations/first-cuda-kernel/)；结合 [O02](/start/evidence-status/)和 [O03](/start/environment-manifest/)。
- **硬件门槛（Hardware gate）：** 无；审查文本记录，不运行 CUDA。
- **相关学习单元：** F01、O02、O03。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份 LAB02 申请只有“CUDA 13、vector add PASS、0.01 ms”，要求标记 Runtime-Verified。判断目前能授予什么状态，并列出补全路径。

**约束：** 不猜环境 patch、GPU 或日志；不把性能数字当作正确性；Compile-Checked 只能引用 canonical EX02 的既有 Lane 记录。

**预期证据：** 状态判断、缺口清单和一份执行前记录模板。

**验收条件：** Runtime 保持 Pending Hardware Verification；不授予 Community-Observed 或 Runtime-Verified；要求完整 manifest、精确命令、原始日志、日期和 criteria result；把未经方法支持的 `0.01 ms` 标为不可解释原始文字。

<details><summary>提示 1</summary>一句 `PASS` 缺少主体、标准、环境、日志和日期。</details>

<details><summary>提示 2</summary>Runtime-Verified 还要求维护者在已声明 Reference Environment 中复现。</details>

**解答：** 现有申请不能授予 Community-Observed 或 Runtime-Verified；运行轴保持 Pending Hardware Verification。补全时记录 GPU identity、compute capability、count、driver、Toolkit patch、NVCC、host compiler、原生 Linux、workload、memory、permissions、精确命令、CPU/tolerance 标准、日期、退出状态和原始日志。`0.01 ms` 在没有同步、工具版本、样本和基线时移入“不可解释原始文字”。只有维护者在声明的 Reference Environment 中按预定标准复现后，才评估 Runtime-Verified。

**有效替代方案：** 社区先提交完整记录并满足标准时，可评估 Community-Observed，同时保留 Pending Hardware Verification；这仍不是维护者复现。

**常见错误：** 因为 EX02 Compile-Checked 就升级 runtime；把未知 CUDA 13 环境当作 13.3.1 Lane；保留一个没有方法的性能数字作为观察。

**来源依据（Source basis）：** [LAB02](/labs/vector-addition/)、[O02](/start/evidence-status/)和 [O03](/start/environment-manifest/)的原创证据合同。

## PB-R1-001：修复生命周期、构建与错误边界

- **ID 与双语发布对：** PB-R1-001；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；中级。
- **直接先修条件：** [O04：面向 CUDA 学习者的 C++17 复习](/start/cpp17-for-cuda/)。
- **硬件门槛（Hardware gate）：** 无；只做源码与构建设计审查，不需要 GPU。
- **相关学习单元：** O04。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份 `.cu` 补丁把局部 `std::vector<float>` 的 `data()` 保存到异步复制任务中，函数在任务完成前返回；一个管理 CUDA 分配（allocation）的资源获取即初始化（Resource Acquisition Is Initialization, RAII）所有者（owner）在析构函数里因 `cudaFree` 失败而 `throw`；一个 `__host__ __device__` helper 调用只允许主机（host）执行且会抛异常的函数。CI 只用 host compiler 编译调用方，就宣称 host 与设备（device）路径都已构建；运行路径用 `try/catch` 包住 kernel launch，却忽略 `cudaError_t`、launch check 和 completion check。写出最小修复方案。

**约束：**

- 不执行构建、sanitizer 或 CUDA，也不虚构诊断与输出。
- 把被指对象生命周期（pointee lifetime）、所有权（ownership）、构建边界（build boundary）和错误边界（error boundary）分开处理。
- 裸指针只能作为非拥有型视图（non-owning view）；修复必须说明 owner 何时才可销毁。

**预期证据：** 一条覆盖异步完成点的所有权时间线、一张 host/device 构建阶段表，以及按执行顺序排列的错误检查清单。

**验收条件：**

- 指出局部 `vector` 先销毁会让保存的 view 悬空，并让 owner 覆盖异步操作完成点，或在作用域退出前建立明确 completion boundary。
- CUDA owner 的析构函数保持不抛异常；若 cleanup failure 必须可观察，则提供显式 `close` 或 `reset` 路径。
- 把 host-only throwing code 与 device-safe helper 分开，让 device 所需定义对 `nvcc` 路径可见，并分别记录 compilation、按需 device linking 和 host linking；host object 成功不证明 device path 或执行。
- 检查每个相关 `cudaError_t`，把 launch error 与 completion error 分开；host exception adapter 只能在保存 CUDA 失败信息后转换错误。

<details><summary>提示 1</summary>复制 raw pointer 只复制地址值，不会延长 `vector` 或 allocation 的生命周期。</details>

<details><summary>提示 2</summary>`try/catch` 观察 host exception；CUDA Runtime failure 先通过返回值、launch boundary 和 completion boundary 暴露。</details>

**解答：** 把 staging buffer 和 CUDA allocation 放进一个 operation owner，使它们至少活到 stream event 或显式 synchronization 确认任务完成；另一种最小修复是在局部 owner 销毁前同步。所有 raw pointer 都标成 view，并携带 extent 与 address-space 含义。析构函数只做不抛异常的 best-effort cleanup，要求报告 cleanup failure 时调用显式 `close`。把 throwing host adapter 与 device helper 分开，确保 `.cu` 和 device 所需定义由 `nvcc` 编译，并单独记录可能的 device link 与最终 host link。逐项检查 allocation、copy 和其他 Runtime API 返回值，launch 后检查 launch error，再在同步或 event 边界检查 completion；只有 host adapter 在保留 error name、message 和调用位置后才可以抛异常。任何构建产物都不证明 GPU 路径已执行。

**有效替代方案：** 可以选择拥有异步状态的 operation object，也可以把复制改成在当前作用域内完成的同步操作；两种方案都必须让 owner 覆盖最后一次合法访问，并保留同样的构建与错误边界。

**常见错误：** 只把一个 pointer 副本设成 `nullptr`；让 non-owning view 负责 `free`；从析构函数抛异常；让 host-only `throw` 进入 device path；把 host compilation、linking 或零 warning 当作 CUDA 执行证据。

**来源依据（Source basis）：** 本站 [O04](/start/cpp17-for-cuda/) 的原创生命周期、构建与错误合同，以及 [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)、NVIDIA [CUDA Runtime API Error Handling](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__ERROR.html)和 [`nvcc` compilation trajectory](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#the-cuda-compilation-trajectory)。

## PB-R1-002：修复隐藏生产者失败的构建记录

- **ID 与双语发布对：** PB-R1-002；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与可复现性；中级。
- **直接先修条件：** [O05：可复现的 Linux 命令行工作](/start/linux-command-line/)。
- **硬件门槛（Hardware gate）：** 无；只设计记录流程，不需要 GPU。
- **相关学习单元：** O05。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个脚本通过管道（pipeline）执行 `make -C "$build_dir" all 2>&1 | tee "$record_dir/build.log"`，随后把 `$?` 写进 `build.exit`，并因其中为零而报告 build success。它还保存完整 `env` 和 xtrace，却没有字面命令（literal command）、独立标准输出（stdout）与标准错误（stderr）、实际开始/结束时间或封存哈希。修复失败判断，并设计一份可公开的最小记录。

**约束：**

- 不运行命令，不填写实际退出状态、时间戳、日志内容或哈希，也不虚构任何输出。
- 不记录秘密（secret）、令牌（token）、凭据（credential）或未经允许的完整环境；xtrace 不能替代字面输入。
- 规范记录必须保留 command、stdout、stderr、退出状态（exit status）、UTC 时间戳（timestamp）和 SHA-256 哈希（hash）的边界。

**预期证据：** 一段失败传播解释，以及按采集顺序列出的产物清单（artifact manifest），说明每个文件何时写入、何时关闭、何时参与哈希。

**验收条件：**

- 说明原脚本中的 `$?` 默认属于 `tee`，成功的消费者（consumer）会隐藏失败的生产者（producer）；`2>&1` 还会丢失通道身份。
- 执行前保存固定 `command.sh` 与 NUL 分隔的 argv，记录逻辑/物理工作目录和允许列表环境（allowlisted environment），不保存 secret。
- 在阶段前后采集 UTC 时间；把 stdout 与 stderr 写入独立文件，并在任何其他简单命令前复制 producer status。
- 日志关闭后，对固定 artifact 清单计算 SHA-256；`SHA256SUMS` 不把自己列为输入，hash 不证明命令正确。
- 若保留 pipeline，则启用 `pipefail` 并立即复制 `PIPESTATUS`，分别保存 producer 与 `tee` 状态；combined log 只能是便利视图。

<details><summary>提示 1</summary>管道的默认状态来自最后一段，不是你最关心的 `make`。</details>

<details><summary>提示 2</summary>先把 `$?` 或 `PIPESTATUS` 复制到 shell variable，再执行 `printf`、timestamp 或 hash 命令。</details>

**解答：** 规范路径可以直接移除 `tee`：先保存不可变 `command.sh`、`argv.nul`、路径与 allowlisted environment，写入 `started-at.txt`，再把 `make` 的 stdout 和 stderr 分别重定向到两个文件。命令返回后立即执行 `build_status=$?`，之后才把该值写入 `build.exit`，并采集 `ended-at.txt`。所有 stream 关闭后，对明确列出的 command、argv、路径、环境、时间、stdout、stderr 和 exit 文件生成 `SHA256SUMS`，且不包含该清单自身。记录模板只定义文件和顺序，不填任何未观察值。完整 `env` 与可能展开 credential 的 xtrace 从公开记录中移除。

**有效替代方案：** 若交互显示必须使用 `tee`，可用 `pipefail` 并在下一条简单命令前复制 `PIPESTATUS`，分别记录 `make` 与 `tee`；但合并流不能恢复 stdout/stderr 身份，所以仍需独立的规范通道产物或明确降低记录范围。

**常见错误：** 在 `printf` 之后才读取 `$?`；只记录 pipeline 的整体状态；把 combined log 当作两个通道；hash 尚未关闭的文件；把完整 environment 或 xtrace 当作“更可复现”而泄露 secret；为模板填入猜测的 `0` 或时间。

**来源依据（Source basis）：** 本站 [O05](/start/linux-command-line/) 的原创命令记录合同，以及 [GNU Bash 5.3 Reference Manual](https://www.gnu.org/software/bash/manual/bash.html)和 [GNU Coreutils 9.11](https://www.gnu.org/software/coreutils/manual/coreutils.html)。

## PB-R1-003：分类架构声明并计算有边界的算术强度

- **ID 与双语发布对：** PB-R1-003；位于 `practice-bank` Publication Pair。
- **类型与难度：** 架构推理与定量分析；中级。
- **直接先修条件：** [O06：架构回顾：速率、延迟与数据移动](/start/architecture-refresher/)。
- **硬件门槛（Hardware gate）：** 无；只做静态分类与算术。
- **相关学习单元：** O06。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 把以下五条待审核草稿分别归入延迟（latency）、吞吐量（throughput）、带宽（bandwidth）、并发（concurrency）或占用率（occupancy），并修复越界结论：A.“kernel latency 是 40 us”；B.“一个批次完成 2,000,000 items/s”；C.“64 MB requested bytes 在 4 ms 内经过 device DRAM 到 SM，所以这是 actual bandwidth”；D.“两个 kernel 位于不同 stream，所以已经并发执行”；E.“occupancy 为 75%，所以达到 peak throughput 的 75%”。然后计算一个独立静态模型：`N = 4096`，每个元素明确计数一次 multiply 和一次 add；在声明的 device-DRAM boundary 上，每个元素恰有一次 4-byte read 与一次 4-byte write，模型不计其他 traffic。

**约束：**

- 这些草稿不是 recorded observation；不补写 timer、profiler、timeline、device 或 workload 事实。
- 算术强度（arithmetic intensity）必须同时声明 operation-count rule、memory boundary、read/write byte 口径和 workload 范围。
- 不从计算结果推出实际性能、内存受限（memory-bound）、加速比（speedup）、重叠（overlap）或利用率（utilization）。

**预期证据：** 一张五行声明分类表（claim-classification table）、一条完整的 intensity 等式，以及一段明确不保证哪些结论的边界说明。

**验收条件：**

- A 只有在命名起止事件和单位后才是 latency；B 是需要工作量与时间窗口的 throughput。
- C 的形式属于带路径与方向的 requested/effective bandwidth，不是 profiler 归属的 actual bandwidth；还要固定 MB 口径和 elapsed boundary。
- D 只说明不同 stream 中的独立工作可能具备 overlap 资格；观察 concurrency 需要 timeline。E 是 active warp 与最大 active warp 的比率，不等于 throughput 百分比。
- 得到 `8192 operations / 32768 bytes = 0.25 operations/byte`，并把结论严格限制在给定计数与 device-DRAM boundary。
- 不作 bottleneck、runtime、bandwidth ceiling 或性能排名声明。

<details><summary>提示 1</summary>先为每条声明写清“一个事件”“时间窗口”“数据路径”“时间重叠”或“resident warp ratio”中的哪一个。</details>

<details><summary>提示 2</summary>每个元素有 2 个 counted operations 和 8 个 boundary bytes。</details>

**解答：** A 是缺少起止边界的 latency 草稿；B 是缺少明确窗口与 workload scope 的 throughput 草稿；C 使用 requested bytes，只能在路径、方向、时间和 MB 定义完整时形成 effective-bandwidth 算式，不能称为 actual bandwidth；D 是 overlap eligibility，不是 observed concurrency；E 是 occupancy 数值，不能换算成 achieved throughput。静态模型中，operation count 为 `4096 * 2 = 8192`，声明边界上的 byte count 为 `4096 * (4 + 4) = 32768`，所以 `I = 8192 / 32768 = 0.25 operations/byte`。这个比值没有测量 traffic 或时间，也没有给出 compute 或 bandwidth ceiling，因此不支持任何性能结论。

**有效替代方案：** 可以用“对象、边界、单位、可证明内容、不可证明内容”五列 claim map 代替分类表，只要五个术语和 intensity 口径仍彼此分开。

**常见错误：** 把 throughput 当作单次 latency；省略 bandwidth path；从不同 stream 推断实际 overlap；把 occupancy 当作 utilization；用 cache traffic 替换题目声明的 DRAM boundary；从 intensity 单独宣布 memory-bound。

**来源依据（Source basis）：** 本站 [O06](/start/architecture-refresher/) 的原创术语与模型边界，CUDA C++ Best Practices Guide v13.3 的 [Bandwidth](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#bandwidth)和 [Occupancy](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#occupancy)，以及 Williams、Waterman 与 Patterson 的 [Roofline primary technical report](https://www.osti.gov/biblio/1407078)。

## PB-R1-004：把产品年表改写成抽象演进

- **ID 与双语发布对：** PB-R1-004；位于 `practice-bank` Publication Pair。
- **类型与难度：** 历史与架构解释；中级。
- **直接先修条件：** [O07：GPU 为什么变得可编程](/start/programmable-gpus/)。
- **硬件门槛（Hardware gate）：** 无；只做概念改写与来源归属。
- **相关学习单元：** O07。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 把这句话改写成由抽象压力驱动的解释：“每一代新 GPU 都让上一代过时；shader 让图形芯片变成通用处理器，Brook 和 CUDA 只是继续让 GPU 在所有任务上比 CPU 更快。”改写必须按固定功能状态（fixed-function state）、可编程图形阶段（programmable graphics stage）、图形处理器通用计算（general-purpose computing on graphics processing units，GPGPU）和 CUDA 的顺序展开，并为具体历史事实建立原始来源归属（primary-source attribution）。

**约束：**

- 每一步都写出上一层的表达压力、接口回应和仍保留的边界。
- 不写产品排名、普遍加速、完全替代 CPU、无来源的“首次”或仅由日期驱动的因果关系。
- 声明到来源映射（claim-to-source map）只能使用 O07 已引用的权威来源（owner source），并让每项具体事实可回查。

**预期证据：** 一个四阶段因果段落，后接一张 claim-to-source map；两者都要把接口能力与性能结论分开。

**验收条件：**

- Fixed-function state 只能配置预定义操作；表达新效果的压力促成有限 programmable stage，而图形 invocation、输入输出和周围 pipeline 仍保留。
- GPGPU 把 array、computation 和 result 映射到 texture、fragment invocation 与 render target；Brook 提供 stream/kernel 表面，但底层仍经过图形机制。
- CUDA 让 heterogeneous kernel、grid、thread block、memory locality 和 scheduling 成为主要模型，并把 block independence 与可扩展调度联系起来。
- 不声称 CUDA 或 GPU 对所有 workload 更快；具体事实分别归属 Khronos 规范、Brook 项目或论文、CUDA Programming Guide 与 2008 CUDA 论文。

<details><summary>提示 1</summary>不要先问“哪一年有什么产品”，先问“程序员还不能自然表达什么”。</details>

<details><summary>提示 2</summary>“可编程”不等于“通用”：检查谁控制 invocation、input、output 和周围 stage。</details>

**解答：** 固定功能图形接口擅长让大量图形项目通过预定义状态进入专用 pipeline，但新效果只能从既有菜单中选择，表达压力因此集中在允许应用提交受控指令。Vertex 与 fragment program 开放了选定 stage，Cg 又改善了源码表达，但 invocation、资源限制和周围图形语义仍由 pipeline 决定。GPGPU 随后把非图形问题编码成 texture、fragment 和 render target；Brook 用 stream 与 kernel 隐藏部分映射，却仍建立在图形机制上。CUDA 把问题改写为 host/device 分工以及 kernel、grid、thread block 和显式 memory locality，block independence 允许 runtime 在不同资源规模上安排工作。这个抽象转变扩大了可表达范围，不证明任何 workload 的普遍 speedup。来源归属为：programmable stage 对照 Khronos ARB 规范与 programmable vertex engine 论文，Brook 层对照 Stanford BrookGPU 与 Brook 论文，CUDA 模型对照 CUDA Programming Guide Introduction 和 Nickolls 等 2008 年论文。

**有效替代方案：** 可以使用“压力、回应、保留边界、来源”四列表格代替连续段落，但不能退化成产品与日期列表。

**常见错误：** 把 shader 写成不受约束的 general-purpose interface；混淆 Cg 与 Brook 的目标表面；把 graphics-mediated GPGPU 直接称为 CUDA；用发布日期代替因果关系；附加“GPU 总是更快”的无证据结论。

**来源依据（Source basis）：** 本站 [O07](/start/programmable-gpus/) 的原创抽象压力框架，以及 [Khronos ARB_vertex_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_vertex_program.txt)与 [ARB_fragment_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_fragment_program.txt)规范、[Stanford BrookGPU 项目](https://graphics.stanford.edu/projects/brookgpu/)、[CUDA Programming Guide v13.3 Introduction](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/introduction.html)和 [Nickolls 等 2008 年 CUDA 论文](https://doi.org/10.1145/1365490.1365500)。

## PB-R1-006：预测二维 partial launch 的 thread 所有权与层次身份

- **ID 与双语发布对：** PB-R1-006；位于 `practice-bank` Publication Pair。
- **类型与难度：** 执行层次推理与正确性；中级。
- **直接先修条件：** [F02：理解 CUDA 执行层次](/foundations/execution-hierarchy/)。
- **硬件门槛（Hardware gate）：** 无；只做静态计算，不运行 CUDA。
- **相关学习单元与资源：** [F02](/foundations/execution-hierarchy/)、[VIS01](/visuals/kernel-journey/)、[VIS02](/visuals/indexing/)和 [EX03](/examples/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个 x 最快、行主序的逻辑数组宽 `19`、高 `9`，使用 `blockDim = (8, 5)`，`gridDim` 由每轴向上取整得到。对边界 block `blockIdx = (2, 1)` 中的 `threadIdx = (2, 3)`、`(3, 3)`、`(2, 4)`和 `(7, 4)`，分别计算 global 坐标、x 最快的线性 block ID、block 内局部线性 thread ID、`warpInBlock`、lane 和数据所有权；只为拥有数据的 thread 计算 row-major `dataIndex`。最后说明这些身份为什么既不是调度顺序，也不自动授予数据所有权。

**约束：**

- 先写逐轴 ceiling division、global 坐标、线性 block、局部 thread、warp 与 lane 公式。
- 必须分别检查 x 与 y，再决定是否计算可访问的 `dataIndex`；不能 clamp 坐标或把 launch 范围当作逻辑范围。
- 不执行 CUDA，不虚构输出或性能，也不从 block、warp 或 lane 数值推断开始或完成顺序。

**预期证据：** 一张四行表，包含 block/global/local/warp/lane 身份、逐轴 bounds、所有权和可选 `dataIndex`，再附一段身份与调度边界说明。

**验收条件：**

- 得到 `gridDim = (3, 2)`、每个 block 40 个 thread，以及边界 block 的 `linearBlock = 2 + 3 * 1 = 5`。
- `(2, 3)` 映射到 global `(18, 8)`、local `26`、warp `0`、lane `26`，拥有最后一个逻辑元素，`dataIndex = 170`。
- `(3, 3)` 映射到 `(19, 8)`、local `27`、warp `0`、lane `27`，仅 x 越界；`(2, 4)` 映射到 `(18, 9)`、local `34`、warp `1`、lane `2`，仅 y 越界；`(7, 4)` 映射到 `(23, 9)`、local `39`、warp `1`、lane `7`，x 与 y 都越界。三者都不产生可访问的 `dataIndex`。
- 指出该边界 block 只有 `3 * 4 = 12` 个 thread 拥有数据，其余 28 个仍被 launch 但必须跳过访问；任何身份编号都不承诺调度顺序。

<details><summary>提示 1</summary>这个 block 的 global 起点是 `(2 * 8, 1 * 5) = (16, 5)`；合法局部 x 只有 `0..2`，合法局部 y 只有 `0..3`。</details>

<details><summary>提示 2</summary>使用 `localThread = threadIdx.x + 8 * threadIdx.y`，再分别计算 `floor(localThread / 32)` 与 `localThread % 32`。</details>

**解答：** 逐轴向上取整得到 `gridDim = (ceil(19 / 8), ceil(9 / 5)) = (3, 2)`。二维 x-fastest block 展开给出 `linearBlock = blockIdx.x + gridDim.x * blockIdx.y = 5`，四个 thread 都属于这个 block，但局部身份分别是 26、27、34 和 39，对应 `(warp, lane)` 为 `(0, 26)`、`(0, 27)`、`(1, 2)`和 `(1, 7)`。Global 坐标依次是 `(18, 8)`、`(19, 8)`、`(18, 9)`和 `(23, 9)`。只有 `(18, 8)` 同时满足 `gx < 19` 与 `gy < 9`，所以只有它拥有数据，且 `dataIndex = 18 + 19 * 8 = 170`；其余三项在展平和访问前停止。边界 block 的有效局部区域是 3 列乘 4 行，因此 12 个 thread 拥有数据、28 个不拥有数据。Block、local thread、warp 与 lane 编号描述层次身份，不描述 block 调度、warp 完成顺序或数据合法性。

**有效替代方案：** 可以用标注坐标的 `8 x 5` block 图或 identity ledger 代替表格，只要四个 thread 的公式、逐轴 bounds、warp/lane 和唯一合法 `dataIndex` 都可复核。

**常见错误：** 把 `gridDim` 向下取整；把二维 `threadIdx` 直接相加；让 local ID 34 变成 data index 34；认为 warp 1 的 thread 自动越界；从 block ID 5 或 warp ID 0 推断执行先后；为无效坐标展平并访问数组。

## PB-R1-007：修复过早展平的三维 bounds 缺陷

- **ID 与双语发布对：** PB-R1-007；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与多维正确性；中级。
- **直接先修条件：** [F03：把多维索引与边界写成正确性合同](/foundations/multidimensional-indexing/)。
- **硬件门槛（Hardware gate）：** 无；只审查和修复源码，不运行 CUDA。
- **相关学习单元与资源：** [F03](/foundations/multidimensional-indexing/)、[VIS02](/visuals/indexing/)和 [EX03](/examples/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个三维 kernel 先计算 `gx`、`gy`、`gz`，但只检查 x，随后就在 y 与 z 尚未通过 bounds 前展平并访问：

```cpp
if (gx >= width) {
  return;
}

const std::size_t index = ((gz * height) + gy) * width + gx;
output[index] = input[index];
```

在保持 x 最快行主序布局的前提下修复顺序。再对 `width = 13`、`height = 6`、`depth = 5`、`blockDim = (5, 4, 2)` 的 launch 计算 `gridDim`，并分类边界 block `blockIdx = (2, 1, 2)` 中的 `threadIdx = (2, 1, 0)`、`(3, 1, 0)`、`(2, 2, 0)`和 `(2, 1, 1)`。只为合法坐标给出线性索引。

**约束：**

- 保留逐轴 global 坐标、逻辑 extent 和 `((gz * height) + gy) * width + gx` 映射；不能 clamp、修改 extent 或缩小 launch 来隐藏 fringe。
- 任一活动轴越界都必须在展平和任何数组访问之前停止；索引类型必须足以容纳完整元素计数。
- 不执行 CUDA，不填写输出或性能，也不把静态补丁、host-only 检查或浏览器模型写成 CUDA Evidence Status。

**预期证据：** 一份最小源码补丁、一张四行逐轴 bounds 表，以及一句说明这份静态审查没有产生编译或运行证据的话。

**验收条件：**

- 修复使用 `gx >= width || gy >= height || gz >= depth` 的 early return，或只在三个 `<` 谓词同时成立时包围展平和访问。
- 得到 `gridDim = (3, 2, 3)`；四个局部坐标分别映射到 global `(12, 5, 4)`、`(13, 5, 4)`、`(12, 6, 4)`和 `(12, 5, 5)`。
- 只有 `(12, 5, 4)` 合法，且 `dataIndex = ((4 * 6) + 5) * 13 + 12 = 389`；其余三项分别仅因 x、y、z 越界，并在展平前停止。
- 不把得到整数的 flattening 表达式当作合法访问证明，也不从修复本身声明 Compile-Checked 或 Runtime-Verified。

<details><summary>提示 1</summary>Early return 连接的是三个“无效”谓词，所以任一为真就必须返回。</details>

<details><summary>提示 2</summary>边界 block 的 global 起点是 `(10, 4, 4)`；最后一个合法元素的三维坐标是 `(12, 5, 4)`。</details>

**解答：** 最小修复是把完整保护放在展平之前：

```cpp
if (gx >= width || gy >= height || gz >= depth) {
  return;
}

const std::size_t index = ((gz * height) + gy) * width + gx;
output[index] = input[index];
```

逐轴向上取整得到 `gridDim = (ceil(13 / 5), ceil(6 / 4), ceil(5 / 2)) = (3, 2, 3)`。所选 block 从 `(10, 4, 4)` 开始，四个 global 坐标依次是 `(12, 5, 4)`、`(13, 5, 4)`、`(12, 6, 4)`和 `(12, 5, 5)`。第一项通过全部三轴检查并映射到 390 个元素中的最后一个 index 389；后三项分别在 x、y、z 上失败，不能计算可访问索引或触及数组。代码审查和手算只建立修复理由，没有编译或执行 CUDA，也没有产生 Evidence Status。

**有效替代方案：** 可以用正向条件 `gx < width && gy < height && gz < depth` 包围展平和全部访问；只要条件外没有 flatten 或数组操作，合同与 early return 等价。

**常见错误：** 用 `&&` 连接三个越界谓词；保留只检查 x 的 guard；先 flatten 再检查 y/z；对越界坐标求模或 clamp；把 CUDA geometry 当作 row-major 布局来源；把 host-only 或 VIS02 结果当作 device 执行。

**来源依据（Source basis）：** 本站 [F03](/foundations/multidimensional-indexing/) 的原创逐轴 bounds 与应用布局合同、[VIS02](/visuals/indexing/)的静态索引模型和 [EX03](/examples/multidimensional-indexing/)的 canonical indexing 与证据边界，以及 NVIDIA [Writing CUDA SIMT Kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

**验收条件：**

<details><summary>提示 2</summary>Launch check 只检查提交边界；completion check 成功后 device input 才越过最后使用，D2H 成功后 device output 才越过最后使用。</details>

## PB-R1-009：修复 stale、immediate 与 deferred error 归因

- **ID 与双语发布对：** PB-R1-009；位于 `practice-bank` Publication Pair。
- **类型与难度：** Error-lifecycle 调试；中级。
- **直接先修条件：** [F05：CUDA 错误为何常常延后暴露](/foundations/asynchronous-errors/)。
- **硬件门槛（Hardware gate）：** 无；只审查静态 error-lifecycle 记录，不运行 CUDA。
- **相关学习单元与资源：** [F05](/foundations/asynchronous-errors/)、[VIS19 错误暴露时间线](/foundations/asynchronous-errors/#vis19)、[EX04](/examples/error-handling-lifecycle/)和 [LAB03](/labs/break-and-repair-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个 host thread 先记录到某项 Runtime 操作失败，却没有消费它的 last-error state。Launch 前的 `cudaPeekAtLastError` 观察到这项未指定的旧失败，但记录忽略了它。随后该 thread 提交一个已预先确认 configuration 合法的 no-op launch；紧邻的 `cudaGetLastError` 返回相同的 non-success state，reviewer 却归咎于新 launch。因为 getter 随后 reset 了 state，第二个区间从 clean state 开始：一个包含故意 device access 缺陷的 launch 被接受，紧邻的 `cudaGetLastError` 返回 success，之后 `cudaDeviceSynchronize` 返回 failure。Reviewer 又声称缺陷由 synchronization 引起。用正确的 origin、observation、state transition 与 control-flow 标签重建两个区间。

**约束：**

- 把直接 `cudaError_t` return 与 last-error state 分开，并说明每项操作是否读取、reset 或等待。
- 不为任何假设失败指定固定 enum value 或 diagnostic string。
- Launch 或 completion boundary 失败后停止依赖它的 D2H 与 verification；不得虚构 runtime output 或 Evidence Status。

**预期证据：** 一张双区间 ledger，包含 prior state、operation、direct return 或 queried state、reset effect、completion effect、attributed origin 和 permitted next step，再附两条修复后的 reviewer 结论。

**验收条件：**

- 第一项邻接 getter 读取的是 stale state，因为同一失败在合法目标 launch 前已经可见；不能把它归因给该 launch。
- 说明 `cudaPeekAtLastError` 观察但不 reset，`cudaGetLastError` 观察并 reset 为 `cudaSuccess`；两者都不建立 device completion。
- 第二项 immediate success 只描述 launch boundary；故意 access defect 的 origin 在 device execution，host observation 位于 synchronization return。
- 把 `cudaDeviceSynchronize` 视为 reporting/completion boundary，而不是自动视为 origin；不能从静态修复声明 compilation 或 runtime evidence。

<details><summary>提示 1</summary>如果 non-success value 在目标 launch 前已经可见，launch 后的源码距离就不能建立新的归因。</details>

<details><summary>提示 2</summary>为 launch submission、邻接 getter、device execution 与 synchronization 分别画一行；只有其中一行等待此前 device work。</details>

**解答：** 在第一个区间，旧 Runtime 操作产生 state；launch 前的 peek 证明 state 早于目标 launch，并保持它不变。合法 no-op launch 没有建立新失败，邻接 getter 读取仍然 stale 的项目并 reset state。正确结论是：“较早失败尚未消费，这份 trace 不能归咎于目标 launch。”第二个区间中，clean starting state 与邻接 getter 的 success 只说明没有观察到 immediate launch failure。接受的 kernel 随后在 device execution 期间触发故意 invalid access；`cudaDeviceSynchronize` 等待此前工作并返回这项 deferred failure，因此不得继续 D2H 或 host verification。正确结论是：“execution defect 起源于 device，并在 completion boundary 对 host 可见。”两个区间都没有提供实际 run record。

**有效替代方案：** 按 EX04/LAB03 要求把每个诊断场景放进独立 process，同时仍记录 preflight state 与直接 synchronization return。Process isolation 能收窄归因，但不能把 immediate getter 变成 completion check。

**常见错误：** 静默丢弃 preflight error；把 last-error state 当成每个 kernel 一条 queue；声称 `cudaGetLastError` 会同步；把 immediate success 当作 execution success；把 device defect 归咎于 synchronization call；completion 失败后仍 copy 或 verify output。

**来源依据（Source basis）：** 本站原创的 [F05 error-state 与 observation 合同](/foundations/asynchronous-errors/)、[EX04 scenario contract](/examples/error-handling-lifecycle/)和 [SRC-CUDA-015 记录](/sources-and-versions/#src-cuda-015)，以及 NVIDIA Runtime API [Error Handling](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__ERROR.html)与 [API synchronization behavior](https://docs.nvidia.com/cuda/cuda-runtime-api/api-sync-behavior.html)。

## PB-R1-010：重建 capability 到 compiler target 的决策

- **ID 与双语发布对：** PB-R1-010；位于 `practice-bank` Publication Pair。
- **类型与难度：** Capability 与 compiler-target 审查；中级。
- **直接先修条件：** [F06：Compute capability 是功能合同](/foundations/compute-capability/)。
- **硬件门槛（Hardware gate）：** 无；不探测 GPU，只审查 capability、limit 与 compiler record。
- **相关学习单元与资源：** [F06](/foundations/compute-capability/)、[VIS20 计算能力合同筛选器](/foundations/compute-capability/#vis20)、[O03](/start/environment-manifest/)和 [F08](/foundations/launch-geometry/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份 packet 直接识别了一个 selected GPU，并记录 compute capability 9.0。Kernel 需要一项 architecture-specific 9.0 feature；capability table 记录 device maximum threads per block 为 1024，候选 block 是 `(32, 32, 1)`。Packet 选择 baseline `compute_90` 加 `sm_90`，声称同一 pair 必然可用于 NVCC 11.8.0、12.9.2 archive 和 selected Toolkit 13.3.1，还因为 block product 等于 maximum 就宣布它“recommended and faster”。修复 feature、limit、target 与未解决 environment 决策。

**约束：**

- 把 GPU identity、compute capability、required feature set、numeric limits、Toolkit、NVCC、virtual target、real target、driver、artifact 与 runtime result 保持为独立字段。
- 只使用 F06 复核的 selected target rows；不能从 GPU 或数值大小推断 compiler support。
- 不能从 maximum 或 documentation lookup 产生 performance、compatibility、compilation 或 runtime 声明。

**预期证据：** 一张覆盖三个 NVCC 坐标的 decision ledger、一条 block-limit clause，以及进入 build、launch、correctness 或 measurement 前仍需补充的事实清单。

**验收条件：**

- 因为 source requirement 使用 architecture-specific 9.0 set，把 baseline pair 改为 `compute_90a` / `sm_90a`，并把这份 code 限定到 exact capability 9.0。
- 记录 selected NVCC 11.8.0 subset 没有 qualified target pair，而 12.9.2 archive 与 selected Toolkit 13.3.1 坐标列出 `compute_90a` / `sm_90a`；拒绝一份不变的 three-Lane plan。
- 把 1024 分类为 device validity maximum；`(32, 32, 1)` 达到该总量，只有在每轴、function-specific limit、register/shared-memory requirement 与 launch boundary 都通过时才合法，且它不是 recommendation。
- Driver loading、embedded artifact code、host compiler、OS、permissions、build result、correctness 与 performance 保持 unresolved。

<details><summary>提示 1</summary>`compute_90` 表示 baseline virtual contract；suffix 属于 feature scope，不是装饰拼写。</details>

<details><summary>提示 2</summary>先按 compiler row 阅读 target matrix，再读取 device limit；compiler accepted targets 与 GPU thread maximum 回答不同问题。</details>

**解答：** Direct query 只为 selected GPU 建立 capability 9.0，并选择适用的 feature/limit row，不会识别 compiler。因为 kernel 要求 architecture-specific set，baseline `compute_90` / `sm_90` 在语义上不足；可复核计划是 exact 9.0 的 `compute_90a` / `sm_90a`。F06 selected matrix 没有为 NVCC 11.8.0 列 qualified pair，却为 12.9.2 archive 和 selected Toolkit 13.3.1 列出该 pair，所以这份 source 不能在三条 Lane 中保持同一个 target plan。1024-thread device maximum 只让 `(32, 32, 1)` 的 product 暂时通过 device gate；function attributes 与其他 resources 仍可能让它非法，等于 ceiling 也不能预测速度。每个可行 compiler plan 仍需要 build record、artifact/driver 审查、实际 launch/completion checks、result verification 与独立 measurement contract。

**有效替代方案：** 移除或替换 architecture-specific source dependency，再分别在每个 exact compiler 中审查 baseline `compute_90` / `sm_90` plan。这通过改变程序需求扩大 scope，并不是原程序去掉 suffix 后的等价拼写。

**常见错误：** 从 product name 猜 capability；把 feature row 当成 compiler target list；把 `compute_90a` 与 baseline `sm_90` 配对；认为更大的 capability number 自动接受 exact-9.0 feature；把 `maxThreadsPerBlock` 变成 preferred block size；因为读过文档就声称所有 Toolkit Lane 已构建。

**来源依据（Source basis）：** 本站原创的 [F06 decision chain](/foundations/compute-capability/)与 [SRC-CUDA-016 记录](/sources-and-versions/#src-cuda-016)，NVIDIA [Compute Capabilities and Feature Set Compiler Targets](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html#feature-set-compiler-targets)，以及精确 [NVCC 11.8.0](https://docs.nvidia.com/cuda/archive/11.8.0/cuda-compiler-driver-nvcc/index.html)、[12.9.2 archive](https://docs.nvidia.com/cuda/archive/12.9.2/cuda-compiler-driver-nvcc/index.html)和 [current NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html) owner pages。

## PB-R1-011：修复 Runtime/Driver 所有权与错误边界

- **ID 与双语发布对：** PB-R1-011；位于 `practice-bank` Publication Pair。
- **类型与难度：** Mixed-API lifecycle 调试；中级。
- **直接先修条件：** [F07：区分 CUDA Runtime API 与 Driver API 的角色](/foundations/runtime-driver-api/)。
- **硬件门槛（Hardware gate）：** 无；只审查 mixed-API design，不运行 CUDA。
- **相关学习单元与资源：** [F04](/foundations/host-device-lifecycle/)、[F05](/foundations/asynchronous-errors/)、[F07](/foundations/runtime-driver-api/)、[VIS21 Runtime/Driver API 边界](/foundations/runtime-driver-api/#vis21)和 [EX04](/examples/error-handling-lifecycle/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份 mixed design 先调用 `cudaSetDevice` 与 `cudaMalloc`，再调用 `cuInit(0)`，通过 `cuCtxGetCurrent` 取得 current context，加载 `CUmodule`、解析 `CUfunction` 并调用 `cuLaunchKernel`。Helper 把取得的 context 标为“owned”，忽略每个 `CUresult`，理由是后续 `cudaGetLastError` 会统一覆盖；随后它 unload module，对取得的 context 调用 `cuCtxDestroy`，最后才调用 `cudaDeviceSynchronize` 与 `cudaFree`。修复 initialization、current-context ownership、module/function lifetime、direct status checks、asynchronous completion 与 teardown authority。

**约束：**

- 把 Runtime `cudaError_t`、Driver `CUresult` 与 Runtime last-error state 作为不同 observation channels。
- 不能因为查询到 handle 就授予 context destruction authority；每项 release 必须匹配显式 acquisition/ownership rule。
- Allocation、module、function 与 context 必须在 launch completion boundary 前保持有效；不得虚构 output 或 performance result。

**预期证据：** 一张 context、allocation、module 与 function 的 owner/lifetime ledger；一条修复后的有序 flow；以及独立的 submission、completion 与 attribution clauses。

**验收条件：**

- 检查 `cuInit(0)` 与每个 Driver call 自己的 `CUresult`，检查每个 Runtime call 自己的 `cudaError_t`；不能用 `cudaGetLastError` 替代 `cuLaunchKernel` direct return。
- 把 `cuCtxGetCurrent` 返回的 context 当成 current handle；packet 没有证明 teardown authority。保持其 current/valid，除非有匹配的 context-creation ownership path，否则不能调用 `cuCtxDestroy`。
- Application-owned `CUmodule` 与其 `CUfunction` 在 completion 前保持有效；通过同一 context 中一个有文档依据的 boundary 同步并直接检查 return，随后才 unload module，并在最后使用后 free Runtime-owned allocation。
- 说明 Driver submission 之后仍可能在 context、stream 或 event completion 观察到 deferred execution error；API 选择不会移除 F05 attribution boundary。

<details><summary>提示 1</summary>查询 current handle 回答“哪个 context 适用”，不回答“哪个 helper 可以销毁共享状态”。</details>

<details><summary>提示 2</summary>在 `cuLaunchKernel` 旁放一个 status cell，在所选 synchronization call 旁再放一个；两者覆盖不同阶段。</details>

**解答：** 先建立 Runtime-selected device 并调用、检查 `cudaMalloc`，再调用、检查 `cuInit(0)`。查询并记录这个 host thread 当前的 context，但不声称 packet 从未取得的 ownership。在该 context 下 load module、resolve function，并检查每个 `CUresult`。调用 `cuLaunchKernel` 时 allocation、context、module 与 function 都必须有效，其 direct return 是 submission result，Runtime last-error getter 不能替代它。保持同一 context current，使用 `cuCtxSynchronize` 等有文档依据的 completion operation 并检查自己的 `CUresult`；这里的 failure 可能报告更早的 asynchronous device work，而不是起源于 synchronization。只有 successful completion 以及需要的 result transfer/verification 结束后，application 才能 unload 自己的 module，并通过记录的 Runtime owner free allocation；不能销毁 borrowed current context。这份静态 design review 不产生 CUDA evidence。

**有效替代方案：** 显式 retain primary context 或创建 Driver-managed context，再把 acquisition 与精确文档中的 release path 配对，并写清全部 Runtime interoperability clauses。只用 Runtime 或只用 Driver 的实现也有效，只要保留同样的 ownership、completion 与 correctness boundaries。

**常见错误：** 把两个 API 当成不同 device stack；认为每个 Runtime call 都一对一映射到 Driver call；销毁由其他 owner 管理的 primary/current context；work 完成前 unload module；用 `cudaGetLastError` 检查 `CUresult`；把 successful launch return 当成 successful execution。

**来源依据（Source basis）：** 本站原创的 [F07 role/ownership contract](/foundations/runtime-driver-api/)、[F05 asynchronous-error contract](/foundations/asynchronous-errors/)与 [SRC-CUDA-015 记录](/sources-and-versions/#src-cuda-015)，以及 NVIDIA [Driver versus Runtime API](https://docs.nvidia.com/cuda/cuda-driver-api/driver-vs-runtime-api.html)、[Runtime/Driver interactions](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DRIVER.html)和 [Driver synchronization behavior](https://docs.nvidia.com/cuda/cuda-driver-api/api-sync-behavior.html)。

## PB-R1-012：在测量前选择合法 block shape

- **ID 与双语发布对：** PB-R1-012；位于 `practice-bank` Publication Pair。
- **类型与难度：** Launch-geometry 正确性与 resource 审查；中级。
- **直接先修条件：** [F08：Launch geometry 是先于速度的正确性与资源决策](/foundations/launch-geometry/)。
- **硬件门槛（Hardware gate）：** 无；只做静态 geometry 与 resource 检查。
- **相关学习单元与资源：** [F03](/foundations/multidimensional-indexing/)、[F06](/foundations/compute-capability/)、[F08](/foundations/launch-geometry/)、[VIS22 线程块形状约束探索器](/foundations/launch-geometry/#vis22)和 [LAB03](/labs/break-and-repair-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 固定 logical extent 是 `width = 1000`、`height = 513`。Selected device record 给出 `maxThreadsDim = (1024, 1024, 64)`、`maxThreadsPerBlock = 1024`，grid limits 大于下列全部 grid。Selected kernel 报告 `maxThreadsPerBlock = 768`；在不超过该 function limit 的候选中，其声明的 register 与 shared-memory needs 都能放入限制。分类 A `(32, 32)`、B `(48, 16)`、C `(64, 8)`与 D `(1025, 1)`。为每个合法候选推导 overflow-safe grid、coverage 与 fringe count，同时保留相同双轴 bounds check。Packet 因为 B 的 fringe 略少于 C 就声称 B 最快。判断哪些候选可以进入 correctness verification，以及 measurement 前还缺什么。

**约束：**

- 不能 round/pad logical extent、删除任一 axis bound，也不能计算未经检查的 product。
- 把 positive input、per-axis device limit、aggregate device limit、function-specific limit 与 grid limit 作为独立 gates。
- 不产生 latency、occupancy、throughput 或 fastest-shape 声明；本题不运行 kernel。

**预期证据：** 一张四行 legality ledger、B/C 的精确 grid/coverage/fringe 算术、保留后的 kernel guard，以及 pre-measurement checklist。

**验收条件：**

- A 的 1024 threads 虽通过 device aggregate limit，却超过 function-specific limit 768，必须拒绝；D 的 x 超过 axis limit，aggregate 也超过 device limit，必须拒绝。
- B 暂时合法，grid 为 `(21, 33)`，coverage 为 `1008 x 528`，launched threads 为 532,224，fringe threads 为 19,224。
- C 暂时合法，grid 为 `(16, 65)`，coverage 为 `1024 x 520`，launched threads 为 532,480，fringe threads 为 19,480。
- 在 flatten/access 前保留 `gx < 1000 && gy < 513`；每个候选都要通过 launch/completion 与相同 result verification；在实际执行 controlled measurement contract 前拒绝“B fastest”。

<details><summary>提示 1</summary>Device legality 不是最后一个 block gate；逐轴检查后，还要把每个 product 与 768 比较。</details>

<details><summary>提示 2</summary>对正整数 `n` 与 `d` 使用 `1 + floor((n - 1) / d)`；coverage 不是替代 logical extent。</details>

**解答：** A 有 `32 * 32 = 1024` 个 thread，所以 axis 与 device aggregate 都通过，但 function limit 失败。D 违反 `block.x <= 1024` 且含 1025 个 thread，因此在推导 grid 前失败。B 有 768 个 thread，得到 `grid = (1 + floor(999 / 48), 1 + floor(512 / 16)) = (21, 33)`；coverage 是 `1008 x 528`，checked products 得到 532,224 launched 减 513,000 logical，等于 19,224 fringe。C 有 512 个 thread，grid 为 `(16, 65)`，coverage 为 `1024 x 520`，launched 为 532,480，fringe 为 19,480。两者仍只是 provisional，因为 actual launch/completion checks 仍然必要；kernel 必须保持 logical extent 不变，并在 flatten 前用两个谓词拒绝 fringe。B 少 256 个 fringe thread 是 geometry fact，不是 runtime verdict。只有相同 inputs、成功边界、独立 result comparison，以及已声明 warm-up/timing/synchronization/repetition 方法后，B/C 才能测量。

**有效替代方案：** 可以按同一 gates 与 logical extent 把合法的 `(16, 16)` 候选加入 ledger；合法仍不代表 preferred 或 faster。

**常见错误：** 只检查 `maxThreadsPerBlock`；检查 overflow 前先相乘；忽略 `cudaFuncAttributes.maxThreadsPerBlock`；把 width/height 改成 coverage；使用 x-only bounds；把更少 fringe 称为更快；把浏览器或手算当成 GPU execution。

**来源依据（Source basis）：** 本站原创的 [F08 feasibility/measurement contract](/foundations/launch-geometry/)、[F03 bounds contract](/foundations/multidimensional-indexing/)与 [SRC-CUDA-016 记录](/sources-and-versions/#src-cuda-016)，以及 NVIDIA [Compute Capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)、[`cudaDeviceProp`](https://docs.nvidia.com/cuda/cuda-runtime-api/structcudaDeviceProp.html)和 [`cudaFuncAttributes`](https://docs.nvidia.com/cuda/cuda-runtime-api/structcudaFuncAttributes.html)。

## PB-R1-013：按所有权、作用域与生命周期分类六种 memory object

- **ID 与双语发布对：** PB-R1-013；位于 `practice-bank` Publication Pair。
- **类型与难度：** Memory model 分类；中级。
- **直接先修条件：** [M01：地址空间、所有权、作用域与生命周期](/memory/address-spaces/)。
- **硬件门槛（Hardware gate）：** 无；只审查静态 object inventory，不运行 CUDA。
- **相关学习单元与资源：** [M01](/memory/address-spaces/)、[VIS06](/visuals/memory-hierarchy-lifetime/)、[F04](/foundations/host-device-lifecycle/)和 [F06](/foundations/compute-capability/)。
- **最后复核（Last reviewed）：** 2026-08-27。

**题目：** 分类这六项对象：A. host 上的 `std::vector<float> input`；B. `cudaMalloc` 成功后由 host variable `d_input` 指向的 device allocation；C. module scope 的 `__constant__ float coefficients[64]`；D. 某个 block 的 `__shared__ float tile[32]`；E. compiler 为某个 thread 的动态索引 `scratch[96]` 建立的 local-memory slot；F. selected compilation 把该 thread 的 scalar `sum` 分配到一个 register。逐项记录 creator/owner、accessibility 与 shared-instance scope、有效 lifetime 以及 release/end action。修复 reviewer 的三条结论：“local 就是在片上”“global memory 是一定绕过 cache 的一个 cache level”“每种对象都需要 `cudaFree`”。

**约束：**

- 把 host pointer value `d_input` 与它指向的 device allocation 分开；不能因为 pointer 作为 argument 传给 kernel 就转移 ownership。
- 把地址空间（address space）、物理位置、cache path、capacity 与预期 access cost 作为独立字段；不能推出固定 latency 或速度顺序。
- 不运行 compiler 或 GPU 命令，不在题目陈述以外虚构 placement，也不授予 CUDA Evidence Status。

**预期证据：** 一张六行 ledger，包含 owner/allocation、accessibility/scope、lifetime 和 release/end 四列，再附三条修正后的 local placement、cache behavior 与 release responsibility 结论。

**验收条件：**

- A 属于 host C++ scope，由 language-managed destruction 结束。B 是显式 global allocation，release obligation 属于 host 控制流；持有合法 device pointer 的 thread 可以跨 block 或 launch 访问它，直到 owner 证明最后使用并调用 `cudaFree`，或到达另一项有文档依据的 teardown boundary。
- C 是 module/context lifetime 的 constant symbol，对 kernel 只读、由 host symbol operation 更新，不使用 `cudaFree` 释放。D 是每个 block 一个 shared instance，只允许该 block 的 thread 访问，并在 block execution 结束时自动退役。
- E 与 F 都是一次 thread invocation 内 thread-private、compiler-managed 的 storage。Local memory 可以物理位于 device memory；register assignment 也可能 spill 到 local memory。两者都不产生跨 thread access，也不需要 `cudaFree`。
- 拒绝全部 cache rank 或速度结论。Address space 定义 naming、sharing 与 lifetime semantic；cache use 和 physical resource behavior 需要 selected architecture、compiler 与 access pattern 才能判断。

<details><summary>提示 1</summary>每行先写创建 storage 的事件：C++ construction、Runtime allocation、module declaration、block launch、thread invocation 或 compiler placement。</details>

<details><summary>提示 2</summary>“Local”回答谁可以命名对象，不回答 backing bytes 是否物理靠近执行 core。</details>

**解答：** A 的 owner 是 host C++ scope，CPU 可直接访问，vector 在 scope exit 时销毁。`d_input` 只是 host handle；成功的 `cudaMalloc` 建立 B，也给 host 建立责任：保留 allocation 直到所有 user 完成，再调用 `cudaFree`。C 属于 module/context interval，对 device kernel grid 只读，通过 symbol API 初始化或更新，而不是作为 allocation 释放。每个 block 各自创建 D，只让本 block thread 共享，并在 block completion 时自动退役。E 在逻辑上只属于一个 thread，即使它的 physical backing 位于 device memory。F 同样是 thread-private 且由 compiler 管理；题目给定的 register placement 只持续这次 invocation，但另一次 compilation 可能把它 spill 到 local memory。因此 local 不是 on-chip 的同义词，global 不是 cache level，而且 inventory 中只有显式 Runtime allocation 带有配对的 `cudaFree` 责任。

**有效替代方案：** 可以用六条 swim lane 的 lifecycle diagram 代替表格，但每条 lane 仍须写明 creator、permitted accessor、最后合法使用或自动 endpoint、release authority，并单独标记未知的 cache/placement facts。

**常见错误：** 把 host pointer 当成 allocation owner；让 kernel free 借来的 storage；释放 constant symbol 或 shared tile；因为 local storage 物理位于 device memory 就认为它可跨 thread 共享；承诺 source scalar 一定留在 register；把 address space 排成 cache level。

## PB-R1-014：推导 aligned、offset 与 stride 的 segment set

- **ID 与双语发布对：** PB-R1-014；位于 `practice-bank` Publication Pair。
- **类型与难度：** Address set 推导与 claim 审查；中级。
- **直接先修条件：** [M02：把合并访问理解为事务塑形](/memory/coalescing-transactions/)。
- **硬件门槛（Hardware gate）：** 无；只做静态 address 与 segment 算术。
- **相关学习单元与资源：** [M02](/memory/coalescing-transactions/)、[VIS04](/visuals/memory-transactions/)、[EX05](/examples/coalesced-strided-access/)和 [F03](/foundations/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-27。

**题目：** 在 M02 限定的 CC 6.0+ 模型中，一条 warp instruction 的 32 个 lane 全部 active，每个 lane 请求一个 4-byte word，base byte address 在 128 自然对齐。分别推导 A. `128 + 4 * lane`、B. `132 + 4 * lane`、C. `128 + 8 * lane` 所需的 naturally aligned 32-byte segment-start set，并包含每个 requested word 的全部 byte。Reviewer 随后写道：“A 用 4 个 segment、B 用 5 个、C 用 8 个，所以 A 比 B 快 1.25 倍、比 C 快 2 倍；EX05 已经证明。”修复这条结论。

**约束：**

- 计数 distinct segment start 前，先写 lane-address formula、第一/最后 requested byte，以及 `segment_start = 32 * floor(byte_address / 32)`。
- 把 logical source index、requested bytes、modeled segment coverage、actual issued transaction、cache reuse、runtime 与 speedup 分开。
- 不执行 EX05 或 profiler；不虚构 timing、throughput、cache event 或 Evidence Status。

**预期证据：** 三个明确的 segment-start set 及其 cardinality、一段 offset/stride effect 解释，以及一条修订后的 EX05 evidence statement。

**验收条件：**

- A 请求 byte 128 到 255，得到 `{128, 160, 192, 224}`，cardinality 为 4。
- B 请求 byte 132 到 259，得到 `{128, 160, 192, 224, 256}`，cardinality 为 5；4-byte offset 跨入一个额外 segment。
- C 的 lane word start 从 128 到 376，最后一个 byte 是 379，得到 `{128, 160, 192, 224, 256, 288, 320, 352}`，cardinality 为 8；stride two 让每个 covered segment 含 4 个 requested word。
- 拒绝两项 speedup ratio。这些 set 只是对一条 warp instruction 的静态 coverage 预测，不是 timing。EX05 compilation evidence 为空、runtime 为 Pending Hardware Verification，因此其 source 和 host reference 都没有提供 GPU execution result 或 speed claim。

<details><summary>提示 1</summary>B 中 lane 31 从 byte 256 开始，并触及 256 到 259，所以不能省略从 256 开始的 segment。</details>

<details><summary>提示 2</summary>C 中 word start 每隔 8 byte；按 `floor(address / 32)` 分组后，每个 segment 对应 4 个 lane，共 8 个 segment。</details>

**解答：** A 中 lane `l` 请求 `[128 + 4l, 131 + 4l]`，union 覆盖 128 到 255，并映射到 128、160、192、224 四个 start。B 把每个 interval 平移 4 byte，成为 `[132 + 4l, 135 + 4l]`；lane 0 仍位于 start 128 的 segment，但 lane 31 触及 byte 256 到 259，因此 set 新增 256，共 5 项。C 请求 `[128 + 8l, 131 + 8l]`；start 128 到 376 覆盖从 128 到 352 的 8 个 aligned 32-byte segment。Cardinality 只能说明 requested byte 的分散方式，不含 elapsed time、cache observation、issued-transaction record 或 controlled comparison，因此任何比例都不能改写为 speedup。EX05 的 pure-host checks 可以验证 indexing logic，但 compilation axis 为空，runtime 仍是 Pending Hardware Verification。

**有效替代方案：** 可以用 lane-to-segment table 或 VIS04 风格的 set diagram，只要覆盖全部 32 个 lane、保留 byte range 而不只写 word start，并在没有性能语言的前提下推导出同样三个 ordered set。

**常见错误：** 因为 offset pattern 仍只有 32 个 word 就计为 4 个 segment；省略一个 word 的末尾 3 byte；stride case 按每 lane 一个 segment 计数；用 logical index 替代 byte address；把 browser model、source listing 或 host reference 当成 GPU timing。

**来源依据（Source basis）：** 本站原创的 [M02 segment model](/memory/coalescing-transactions/)、[VIS04 确定性可视化](/visuals/memory-transactions/)、[EX05 canonical indexing case 与当前证据记录](/examples/coalesced-strided-access/)和 [SRC-CUDA-018](/sources-and-versions/#src-cuda-018)，以及 NVIDIA CUDA C++ Best Practices Guide [Coalesced Access to Global Memory](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#coalesced-access-to-global-memory)。

## PB-R1-015：修复 edge tile early return 与缺失的 reuse barrier

- **ID 与双语发布对：** PB-R1-015；位于 `practice-bank` Publication Pair。
- **类型与难度：** Shared-memory 正确性调试；中级。
- **直接先修条件：** [M03：共享内存分块](/memory/shared-memory-tiling/)。
- **硬件门槛（Hardware gate）：** 无；只审查和修复源码，不运行 CUDA。
- **相关学习单元与资源：** [M03](/memory/shared-memory-tiling/)、[EX06](/examples/shared-memory-tile-bank-padding/)、[M01](/memory/address-spaces/)和 [M02](/memory/coalescing-transactions/)。
- **最后复核（Last reviewed）：** 2026-08-27。

**题目：** 一个 32-thread block 循环处理 `n = 45` 的 input，并反复使用同一个 shared tile。第二次 iteration 只有 13 个 input lane 合法。修复这份 review draft 中的两个缺陷：

```cpp
for (std::size_t tile_base = 0; tile_base < n; tile_base += blockDim.x) {
  const std::size_t input_index = tile_base + threadIdx.x;
  if (input_index >= n) {
    return;
  }
  tile[threadIdx.x] = input[input_index];
  __syncthreads();
  output[input_index] = tile[(threadIdx.x + 1) % blockDim.x];
  // 下一次 iteration 会立即覆盖 tile。
}
```

**约束：**

- 保留 portable C++17 synchronous `load -> __syncthreads() -> use/reuse -> __syncthreads()` baseline 和 32-thread block。
- Block 中 participating 的每个 thread 都必须在同一次 loop iteration 到达每个 barrier；bounds 可以保护 memory access，不能保护 barrier participation。
- Invalid edge load 使用明确的 neutral value；不运行 build 或 kernel，也不虚构 output、timing 或 Evidence Status。

**预期证据：** 一份最小 source repair、一张覆盖两次 iteration 的 valid/invalid lane participation ledger，以及一段分别说明两个 barrier 作用的解释。

**验收条件：**

- 删除依赖 lane 的 early return。Edge iteration 中 lane 0 到 12 load input，lane 13 到 31 在 first barrier 前各自把 neutral value 写入自己的 tile slot，32 个 lane 全部参与。
- 用 `input_index < n` 保护 output write；invalid loader 虽然不执行 global input/output access，仍参与两个 barrier。
- First barrier 位于 tile write 与任何 tile read 之间；在最后一次 tile read 之后、任何 lane 可以在下一次 iteration 覆盖 shared storage 之前加入 second barrier。
- 明确静态修复不产生 compilation 或 runtime observation；EX06 compilation evidence 保持为空，runtime 保持 Pending Hardware Verification。

<details><summary>提示 1</summary>把“invalid lane 退出”改成“invalid lane 提供 neutral value”，再只把 global access 放进 bounds condition。</details>

<details><summary>提示 2</summary>First barrier 防止读取尚未完成的 write；second barrier 防止下一轮 write 覆盖本轮仍在进行的 read。</details>

**解答：** 一份完整修复是：

```cpp
for (std::size_t tile_base = 0; tile_base < n; tile_base += blockDim.x) {
  const std::size_t input_index = tile_base + threadIdx.x;
  const bool valid = input_index < n;

  tile[threadIdx.x] = valid ? input[input_index] : 0.0f;
  __syncthreads();

  if (valid) {
    output[input_index] = tile[(threadIdx.x + 1) % blockDim.x];
  }
  __syncthreads();
}
```

Iteration zero 中 32 个 lane 都 load 合法 input；iteration one 中 13 个 lane load input，19 个 lane 写 `0.0f`。全部 32 个 lane 随后到达 first barrier，所以任何 read 开始前每个 tile slot 都已建立。只有 13 个 valid output owner 写 global output；全部 32 个 lane 再到达 second barrier，阻止较快 lane 在其他 lane 仍读取当前 tile 时开始下一轮 load。这份 review 没有编译或执行 EX06；其 compilation axis 为空，runtime 为 Pending Hardware Verification。

**有效替代方案：** 如果改变算法，并证明每个 block 恰好只处理一个 tile、之后不会再写这个 shared object，则 final reuse barrier 可能不需要。这个 single-iteration contract 不能作为删除上述 loop 中 second barrier 的理由；neutral edge load 与 first barrier 仍然必需。

**常见错误：** 在 block-wide barrier 前 return；把 `__syncthreads()` 放进 `if (valid)`；让 invalid tile slot 未初始化；保护 barrier 而不是 memory access；认为 warp lockstep 可以替代 block barrier；因为 first barrier 已保护 load 就省略 second barrier。

**来源依据（Source basis）：** 本站原创的 [M03 load、participation 与 reuse 合同](/memory/shared-memory-tiling/)、[M01 address-space lifetime model](/memory/address-spaces/)、[EX06 canonical synchronous implementation 与当前证据记录](/examples/shared-memory-tile-bank-padding/)和 [SRC-CUDA-019](/sources-and-versions/#src-cuda-019)，以及 NVIDIA [Writing CUDA SIMT Kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

## PB-R1-016：区分 broadcast、bank conflict 与 32x33 padding

- **ID 与双语发布对：** PB-R1-016；位于 `practice-bank` Publication Pair。
- **类型与难度：** Shared-memory bank 与 layout 推理；中级。
- **直接先修条件：** [M04：Bank conflict 与布局变换](/memory/bank-conflicts-layouts/)。
- **硬件门槛（Hardware gate）：** 无；只做静态 word-address 与 bank mapping。
- **相关学习单元与资源：** [M04](/memory/bank-conflicts-layouts/)、[VIS05](/visuals/shared-memory-banks/)、[EX06](/examples/shared-memory-tile-bank-padding/)和 [M03](/memory/shared-memory-tiling/)。
- **最后复核（Last reviewed）：** 2026-08-27。

**题目：** 使用 M04 selected fixture：32 个 bank、连续 32-bit word，并且 `bank(word_index) = word_index mod 32`。分类 A. 32 个 lane 都从 `float tile[32][32]` 读取同一个 `tile[0][5]`；B. lane `i` 从这份 unpadded tile 读取 `tile[i][5]`；C. declaration 改为 `float tile[32][33]` 后，lane `i` 读取 `tile[i][5]`。逐项推导 row stride、word-index formula、bank set、每个 bank 的 distinct-word count 和 classification。修复声明：“A 与 B 都是 32-way conflict，而 C 快 32 倍。”

**约束：**

- 把同地址读取广播（same-address read broadcast）与多个 distinct word 映射到同一 bank 分开。
- 从 declaration 推导 unpadded/padded row stride；保留 logical `32 x 32` payload，并计算 padding bytes。
- 不运行 EX06 build、CUDA kernel、timer 或 profiler；不推出 latency、throughput 或 speedup。

**预期证据：** 一张三行 bank ledger、padded layout 的 modulo 推导、padding capacity 算术，以及一条修订后的 evidence/performance statement。

**验收条件：**

- A 的 declaration stride 为 32，但每个 lane 都请求相同 word index 5 和 bank 5；这是 same-address read broadcast，不是 32-way bank conflict。
- B 使用 word index `32i + 5`；`(32i + 5) mod 32 = 5`，所以 bank 5 收到 32 个 distinct word，在 selected fixture 中属于 32-way conflict。
- C 使用 word index `33i + 5`；`(33i + 5) mod 32 = (i + 5) mod 32`，恰好遍历全部 32 个 bank，因此该 instruction conflict-free。额外一列使每 tile 增加 32 个 float，即 128 byte，不改变 logical payload。
- 拒绝“快 32 倍”。Mapping 只预测 conflict classification。EX06 compilation evidence 为空、runtime 为 Pending Hardware Verification；VIS05 与 host arithmetic 都不是 timing evidence。

<details><summary>提示 1</summary>统计每个 bank 内 distinct requested word index 的数量；对一个 word 的 32 次请求与对 32 个不同 word 的请求不是同一情况。</details>

<details><summary>提示 2</summary>因为 `33 mod 32 = 1`，padding 后 successive row 会让 selected column 每次前进一个 bank。</details>

**解答：** A 把全部 lane 都送到 bank 5 的 word 5，但 distinct requested word 只有一个，因此使用 selected model 的 broadcast exception。B 的 row stride 为 32 word，lane `i` 选择 `32i + 5`，32 个 distinct word 全部约简为 bank 5，所以在该 fixture 中是 32-way conflict。Padding 把 physical row stride 改为 33，同时保留 32 个 logical column；C 因此把 lane `i` 映射到 `33i + 5`，其 bank 为 `(i + 5) mod 32`。32 个 lane 构成 bank 0 到 31 的一个 permutation，所以 modeled instruction conflict-free。Physical allocation 增加 `32 * 1 * 4 = 128` byte。这些事实不能预测 elapsed-time ratio 或 end-to-end speed：EX06 没有合格 compile record 或 GPU runtime observation，仍是 Pending Hardware Verification。

**有效替代方案：** 可以 transpose 或 remap cooperative load/use index，让同一组 logical value 以与 32 互质的 stride 被读取。替代方案必须完整推导 word index 与 bank，保留 bounds/synchronization，并在测量前计算 storage 或 indexing cost。

**常见错误：** 因为一个 bank 被命名 32 次就把 broadcast 称为 conflict；统计 request 而不是 distinct word；声明 33 列后仍使用 stride 32；认为 padding 改变 logical matrix；忘记 128-byte capacity cost；把 conflict degree 直接换算成 speedup。

**来源依据（Source basis）：** 本站原创的 [M04 selected bank fixture 与 padding 推导](/memory/bank-conflicts-layouts/)、[VIS05 确定性 mapper](/visuals/shared-memory-banks/)、[EX06 canonical layout 与当前证据记录](/examples/shared-memory-tile-bank-padding/)和 [SRC-CUDA-019](/sources-and-versions/#src-cuda-019)，以及 NVIDIA CUDA C++ Best Practices Guide [Shared Memory and Memory Banks](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#shared-memory-and-memory-banks)。

- **ID 与双语发布对：** PB-R1-018；位于 `practice-bank` Publication Pair。

**验收条件：**

<details><summary>提示 1</summary>分别写出两个 `__activemask()` 返回的集合，再检查 lane 4 请求的 source lane 3 是否属于同一 collective contract。</details>

<details><summary>提示 2</summary>把“谁需要结果”与“谁必须执行 collective 才能提供结果”分成两列。</details>

**解答：** 原程序让 lane 0 至 3 保存 lower mask，让 lane 4 至 7 保存 upper mask。Closing brace 只给出共同 source successor，不会让不同 mask 变成同一个 synchronization group。修复时先由当前 warp participants 一致计算 `participants = ballot(lane < 8)`；lane 0 至 7 可以执行各自 scalar branch，之后在共同 region 全部调用 `__shfl_sync(participants, value, lane == 0 ? 0 : lane - 1)`，再只让 lane 1 至 7 消费 predecessor value。这样 source lane 0 至 6 都属于 mask 且执行同一 collective，lane 0 的 self-source 结果被忽略。CC 7.0+ 允许 per-thread execution state 和 sub-warp regrouping，但不提供可移植的 path order 或 instruction trace。

**有效替代方案：** 八个 lane 可以先写 shared storage，执行 `__syncwarp(participants)`，再让 lane 1 至 7 读取 predecessor slot。这个版本仍需相同 mask proof，而且 barrier 必须位于 write 与 peer read 之间。

**常见错误：** 在 branch 内用 `__activemask()` 推导 intended group；在 mask 中命名不会到达 collective 的 lane；读取 inactive source lane；把 closing brace 当 barrier；认为同一 warp 天然 lockstep；把 VIS03 的确定性绘制顺序当硬件 schedule。

## PB-R1-019：修复两条 stream 的 partial order 与 lifetime

- **ID 与双语发布对：** PB-R1-019；位于 `practice-bank` Publication Pair。
- **类型与难度：** Stream-order 与 lifetime correctness debugging；中级。
- **直接先修条件：** [M07：用流取代全局顺序心智模型](/memory/stream-ordering/)。
- **硬件门槛（Hardware gate）：** 无；只审查静态 stream graph 与 allocation lifetime。
- **相关学习单元与资源：** [M07](/memory/stream-ordering/)、[VIS07](/visuals/stream-event-dependencies/)、[F05](/foundations/asynchronous-errors/)和 [M01](/memory/address-spaces/)。
- **最后复核（Last reviewed）：** 2026-08-28。

**题目：** 两条显式 `cudaStreamNonBlocking` stream 承载 `stream_prepare: H2D(h_input -> d_input) -> prepare(d_input, d_stage)` 与 `stream_consume: consume(d_stage, d_output) -> D2H(d_output -> h_output)`。Host 按这个文字顺序提交全部操作，随后立即销毁 `h_input` 并释放三个 device allocation。Reviewer 声称“host submission order 已经形成全局队列，而且两条 stream 证明 kernels 并发”。修复 partial-order graph、data dependency 与所有 object lifetime。

**约束：**

- 只自动添加每条 stream 内的 enqueue-order edge；跨 stream edge 必须有 documented mechanism。
- 分别记录 `h_input`、`h_output`、`d_input`、`d_stage` 与 `d_output` 的 last asynchronous user 和 release boundary。
- 不借助 default-stream implicit rule，不声明 observed overlap、duration 或 performance。

**预期证据：** 两条 stream lane、完整 same-stream edge set、一个 missing cross-stream edge、五行 lifetime ledger，以及修复后的 host completion/release sequence。

**验收条件：**

- 初始图只有 `H2D -> prepare` 与 `consume -> D2H`；host call order 不建立 `prepare -> consume`。
- 在 prepare completion 与 consume eligibility 之间加入最窄的 explicit dependency，或把 dependent chain 放入同一 stream。
- `h_input` 至少保留到 H2D 完成；`d_input` 保留到 prepare 完成；`d_stage` 保留到 consume 完成；`d_output` 与 `h_output` 保留到 D2H 完成和 host verification boundary。
- 不把 unordered 改写为 concurrent；静态 graph 和 lifetime repair 不授予 CUDA Evidence Status。

<details><summary>提示 1</summary>先画两条互不连接的 horizontal chain，再问哪个 consumer input 没有 predecessor edge。</details>

<details><summary>提示 2</summary>对每个 object 写“最后一次可能仍在使用它的 asynchronous operation”，不要把 enqueue return 当作 last use。</details>

**解答：** 初始 partial order 只有两条 lane 内边。`consume` 读取 `prepare` 产生的 `d_stage`，因此需要 `prepare -> consume` 的显式跨流依赖，例如在 producer stream 的 prepare 后 record event，再让 consumer stream 在 consume 前 wait；event generation 细节由 M08 继续约束。这个 edge 使 consumer 不会过早 eligible，但不证明两条 stream 曾重叠。修复后的 host 还要让 `h_input` 活到 H2D 完成，让 `d_input` 活到 prepare 完成，让 `d_stage` 活到 consume 完成，并让 `d_output` 与 `h_output` 活到 D2H 完成。覆盖最终 D2H 的 host completion boundary 通过后，host 才能验证 `h_output` 并释放对应 storage；每项 release 仍需遵守实际 API 的 documented contract。

**有效替代方案：** 把 H2D、prepare、consume 与 D2H 全部放进一条 non-default stream，可以用 per-stream order 表达同一 correctness graph。Device-wide host synchronization也能建立更宽的 completion boundary，但不应在只需一条 dependency edge 时被描述成唯一方案。

**常见错误：** 把 host source order 当 device global order；因为 stream 名称不同就宣布 concurrency；忘记 asynchronous copy 的 host-buffer lifetime；在 consumer last use 前释放 `d_stage`；只同步 producer stream 就读取 `h_output`；用 default-stream 行为补上未声明 edge。

## PB-R1-020：审查 event dependency 与 device-time evidence

- **ID 与双语发布对：** PB-R1-020；位于 `practice-bank` Publication Pair。
- **类型与难度：** Event generation 与计时证据审查；中级。

- **硬件门槛（Hardware gate）：** 无；只审查 event generation、dependency 与 timing evidence。

- **最后复核（Last reviewed）：** 2026-08-28。

**题目：** 一个 producer stream 在 `P1` 后 record handle `E`，consumer 随后提交 `W1 = wait(E)`；producer 又执行 `P2` 并 re-record 同一 handle，随后提交 `W2`。另外，`ready` event 以 `cudaEventDisableTiming` 创建，却被 reviewer 当作 elapsed-time 的 start endpoint。Review 还把 VIS07 的 browser pacing 写成“实测 0.8 ms 且两条 stream 已并发”。给出 generation、dependency、timing 与 Evidence Status 四部分修订。

**约束：**

- 用教学标签 `E1`、`E2` 表示同一 handle 的两次 captured state，不能虚构两个 handle。
- 区分 non-blocking query、host-blocking synchronize、stream wait 与 elapsed-time calculation。
- 不提供任何替代数值，不把 browser animation、静态 formula 或 owner documentation 当作 runtime observation。

**预期证据：** 一张 API-call/generation 表、两条 wait edge、三-event flag table、合法 timing bracket 与一条 evidence-neutral review conclusion。

**验收条件：**

- `W1` 绑定调用时的 `E1`，后来 re-record 不会把它改绑到 `E2`；`W2` 使用 re-record 后的 `E2`。
- `ready` 可以用于 documented dependency/query/synchronize operation，但因禁用 timing，不能作为 `cudaEventElapsedTime` endpoint。
- 合法计时使用 timing-enabled `start`/`stop`，明确 included work，等待 recorded endpoints 完成，检查 API result，并只在真实运行后报告值和 Environment Manifest。
- 删除 0.8 ms 与 observed-concurrency claim；VIS07 与本题都没有 CUDA Evidence Status。

<details><summary>提示 1</summary>在每个 Runtime API call 旁写下“此调用当时 handle 最近捕获的是哪一代”。</details>

<details><summary>提示 2</summary>Creation flag 是 event contract 的一部分；dependency-capable 不等于 timing-capable。</details>

**解答：** 第一条 record 建立 `E1 = work through P1`，所以随后提交的 W1 只让其后 consumer work 等待 E1。第二条 record 把 handle 的 future selection 更新为 `E2 = work through P2`；W2 绑定 E2，而 W1 不会 retroactively retarget。`cudaEventQuery` 只报告 selected captured state 是否完成，不阻塞 host；`cudaEventSynchronize` 等待 host；`cudaStreamWaitEvent` 约束 wait 后提交到该 stream 的 work。Dependency-only `ready` 保持合法 dependency object，却不能进入 elapsed calculation。若要计时，必须创建 timing-enabled start/stop、在声明的 stream order 中 record、等待 stop 完成，再检查 `elapsed_ms = timestamp(stop) - timestamp(start)`；这个 symbolic formula 没有提供 value。Browser interval 只控制可读性，因此 0.8 ms 与 overlap 两项都必须删除。

**有效替代方案：** 为 `E1` 与 `E2` 使用两个不同 handle 可以让 generation ownership 更容易审查；也可以扩大 timing bracket，但必须重新声明 included work、completion boundary 与 measurement method。

**常见错误：** 让 earlier wait 跟随 re-record；认为 record host call return 表示 event 已完成；把 query 当 blocking wait；把 timing-disabled event 传给 elapsed API；从 browser cadence 抄一个 duration；把 dependency edge 当 concurrency observation。

## PB-R1-021：设计独立 CPU reference、容差与不变量

- **ID 与双语发布对：** PB-R1-021；位于 `practice-bank` Publication Pair。
- **类型与难度：** Correctness oracle 设计与调试；中级。
- **直接先修条件：** [Q01：CPU reference、容差与不变量](/correctness/cpu-references-tolerances-invariants/)。
- **硬件门槛（Hardware gate）：** 无；只设计和审查静态 correctness oracle，不运行 CUDA。
- **相关学习单元与资源：** [Q01](/correctness/cpu-references-tolerances-invariants/)、[F04](/foundations/host-device-lifecycle/)和 [O04](/start/cpp17-for-cuda/)。
- **最后复核（Last reviewed）：** 2026-08-28。

**题目：** 一个 GPU histogram 同时输出 16 个 floating-point probability、16 个 integer count 和一个 `max_bin`。Reviewer 把 kernel 的 flattening 与 loop 顺序逐行复制到 CPU reference，在看到一次 mismatch 后把 `epsilon` 调大到通过，只检查 probability sum，并开始计时。设计一套能发现 CPU/GPU 共同索引缺陷的 layered correctness oracle。

**约束：**

- CPU reference 必须从 input/output contract 独立推导，不能复用 kernel indexing helper 或 launch geometry。
- Floating-point field 使用预先声明的 absolute-plus-relative rule；count 和 `max_bin` 精确比较，并单独声明 NaN/infinity 与 tie policy。
- 至少加入两个从问题规范推导、而不是从 candidate output 推导的不变量；任何 gate 失败时禁止计时。

**预期证据：** 一份 oracle ledger，列出独立 reference path、每种 field 的 comparator、阈值依据、exact checks、不变量、first-failure report 和 timing gate；这是设计产物，不是运行记录。

**验收条件：**

- CPU reference 重新推导 bin ownership 与 bounds，且在显式 GPU completion 和 copy-back 后才比较。
- 每个 finite probability 使用 `abs(g - r) <= atol + rtol * abs(r)`，`atol`/`rtol` 在查看结果前固定并有 scale/precision/error-budget 理由。
- Count、`max_bin` 与 tie rule 精确；`sum(counts) == sample_count`、count 非负和 normalization 等独立不变量与 reference agreement 分开判定。
- 删除 universal epsilon 与 premature timing；host-only oracle 测试不授予 GPU runtime evidence。

<details><summary>提示 1</summary>先写 CPU 与 GPU 都必须满足的 input/output contract，再用不同 loop nesting 重建 host path。</details>

<details><summary>提示 2</summary>把“数组相同”和“样本没有丢失或重复”放在两个独立判定栏。</details>

**参考解答（Reviewed solution）：** CPU 实现直接遍历输入 sample，按规范计算 bin，并在 host 上独立累积 count；它不读取 grid、block 或 thread 公式。完成 GPU 工作并复制结果后，probability 先经过 non-finite policy，再按 `error <= atol + rtol * abs(reference)` 比较；count 和按既定 tie rule 得出的 `max_bin` 逐项精确比较。独立 invariants 至少检查 count 总和、非负、probability range/normalization，以及 `max_bin` 与 count 最大值一致。CPU/GPU 数组一致但 invariant 失败仍拒绝，反之只满足 invariant 也不足以替代 reference。全部 gate 通过前没有合法 timing input。

**有效替代方案：** 可以用第二种独立 host library path 或 property-based fixtures 增加覆盖，但每个 comparator、不变量与生成 seed 都必须显式记录。

**常见错误：** 逐行翻译 kernel；看到 mismatch 后调阈值；对 integer 使用 tolerance；让 NaN 意外通过；只检查 sum；把 host-only pass 写成 Runtime-Verified。

**来源依据（Source basis）：** 本站原创的 [Q01 layered oracle contract](/correctness/cpu-references-tolerances-invariants/)与 [SRC-CUDA-022](/sources-and-versions/#src-cuda-022)，以及 NVIDIA CUDA C++ Best Practices Guide [Verification](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#verification)和 [Floating Point and IEEE 754：Verifying GPU Results](https://docs.nvidia.com/cuda/floating-point/index.html#verifying-gpu-results)。

## PB-R2-001：审查分块传输重叠声明

- **ID 与双语发布对：** PB-R2-001；位于 `practice-bank` Publication Pair。
- **类型与难度：** Transfer-overlap evidence review；高级。
- **直接先修条件：** [M09：Pinned memory 与传输重叠](/memory/pinned-memory-transfer-overlap/)。

**题目：** 一个 two-slot pipeline 用普通 `malloc` 得到 `h_in[2]` 与 `h_out[2]`，在两条 non-default stream 中提交 `cudaMemcpyAsync(H2D) -> kernel -> cudaMemcpyAsync(D2H)`。Host 在 enqueue 后立即重填同一 input slot，并在没有等待 D2H completion 时读取 output。Reviewer 看到 `asyncEngineCount > 0` 和两条 stream，就发布“42% transfer overlap、1.8x speedup”。修复 lifetime/dependency graph 和证据声明，不提供新的性能数值。

**约束：**

- 保留与 serialized baseline 相同的 logical input、kernel work、tail handling、output oracle 和 error checks；为 allocation 与 registration 两条 page-lock path 写出匹配 release action。
- 每个 chunk 必须有 `host fill -> H2D -> kernel -> D2H -> output-ready` 顺序，并为 ring-slot overwrite/read/release 标出 completion edge。

**预期证据：** 一份 two-slot ownership/dependency ledger、一张 serialized/pipelined correctness-equivalence checklist，以及 capability-to-observation decision table；所有 runtime value 与 timeline observation fields 保持为空。

**验收条件：**

- Host ranges 改为由 `cudaMallocHost`/`cudaHostAlloc` 创建并以 `cudaFreeHost` 释放，或由 `cudaHostRegister` 注册、在 last async use 后 `cudaHostUnregister`，再由原 allocator 释放。

- `asyncEngineCount` 与 graph eligibility 只允许结论 “eligible”、“unsupported”或“under-specified”；没有 exact-run timeline 时 overlap 为 unobserved。
- 删除 42% 与 1.8x；即使 capability 不满足，serialized baseline 仍可独立通过 correctness。

<details><summary>提示 1</summary>把每个 slot 当作有上一位 owner 和下一次 overwrite point 的资源，而不是只画三项 device work。</details>

<details><summary>提示 2</summary>问 `asyncEngineCount` 回答的是“可能有什么资源”，还是“这次两个 interval 是否相交”。</details>

**参考解答（Reviewed solution）：** 在 steady-state 前创建 bounded page-locked input/output slots。每个 stream 保持本 chunk 的 H2D、kernel 与 D2H same-stream order；在 D2H 后 record `output_ready[slot]`。Host 在重填或读取 slot 前等待该 slot 上一代的 completion，tail chunk 使用实际 byte count，所有 API/launch/completion result 与 output oracle 都通过后才进入 observation gate。Manifest 保存 exact page-lock path、device query/value、transfer directions 和 stream/event graph。此静态产物最多证明 graph 正确且配置可被分类；没有 device timeline 就写 “eligible but unobserved”，没有任何 performance claim。

**有效替代方案：** 使用单条 serialized stream 和同一组 page-locked buffers 是合法 fallback；也可以使用三 slot ring，但每个新增 slot 必须拥有同样完整的 generation、completion 与 reuse ledger。

**常见错误：** 把 pageable copy 写成 overlap contract；host enqueue 后立刻改 input；只等待 kernel 而漏掉 D2H；把 event timestamp 当 interval overlap；由 nonzero capability 推断 engine use；先报告 speedup 再补 correctness。

## PB-R2-002：修复无条件 page-migration 叙述

- **ID 与双语发布对：** PB-R2-002；位于 `practice-bank` Publication Pair。
- **类型与难度：** Managed-memory evidence review；高级。
- **直接先修条件：** [M10：Unified Memory 与 page migration](/memory/unified-memory-page-migration/)。
- **硬件门槛（Hardware gate）：** 静态建模无需硬件；runtime migration claim 要求 Native Linux、支持 managed memory 的 CUDA GPU，以及记录适用 memory paradigm、capability attributes 与 topology 的 Environment Manifest。
- **相关学习单元与资源：** [M01](/memory/address-spaces/)、[M02](/memory/coalescing-transactions/)、[M10](/memory/unified-memory-page-migration/)、[VIS08](/visuals/page-migration/)和 [EX08](/examples/unified-memory-migration/)。
- **最后复核（Last reviewed）：** 2026-08-29。

**题目：** 一段程序用 `cudaMallocManaged` 分配数组，CPU 写 A/B pages，GPU 读 B/C 并写 C，随后 CPU 读 C。它调用一次 prefetch，但没有记录 destination semantics、capability attributes、kernel completion、page size、fault 或 residency data。Reviewer 根据 VIS08 的颜色宣称“每次 cross-processor first touch 都迁移一个 4 KiB page，prefetch 会把数据永久固定在 GPU 上”。把这段话改成 conditional access ledger 与诚实结论。

**约束：**

- 区分 accessibility、residency、migration、remote/coherent access 与 limited-support coarse movement；不能为未知 system model 选择唯一分支。
- 保留 `CPU writes A/B -> order edge -> GPU reads B/C and writes C -> completion edge -> CPU reads C`，并在每次 access 前记录 prior known state 与 permitted behaviors。
- Prefetch/advice 只能作为 ordered request/hint；不得发明 page size、migration count、migrated bytes、duration、bandwidth 或 placement history。

**预期证据：** 一张按 access episode 展开的 conditional ledger，包含 capability-query schema、correctness synchronization、possible cost terms、blank runtime observations 和最窄 allowed claim。

**验收条件：**

- `cudaMallocManaged` 被描述为 ownership/access/lifetime contract，allocation 在所有 CPU/GPU users 完成后以 `cudaFree` 释放；stable pointer 不等于 stable physical locality。
- Ledger 分别允许 software-coherent fault-and-migrate、hardware-coherent/direct remote access 与 limited coarse movement，且每个 “migration candidate” 都附带 premise。
- Manifest 至少预留 concurrent managed access、pageable-memory access、host-page-table 与 direct-host-access attributes，以及 OS/kernel、driver、Toolkit、device/topology、access order 和 synchronization。
- 删除 4 KiB universal page 与 permanent placement 结论；VIS08、source order 和 prefetch call 都不构成 migration observation。

<details><summary>提示 1</summary>先问“这个 processor 能否合法访问”，再问“当时 backing 在哪里”，最后才问“系统可否通过 migration 服务”。</details>

<details><summary>提示 2</summary>把 `cudaMemPrefetchAsync` 写成 stream-ordered request，而不是 residence lock。</details>

**参考解答（Reviewed solution）：** 修订后的 ledger 从 unknown residency 开始。CPU 写 A/B 后建立进入 kernel 的 order；GPU 对 B/C 的 access 在 software-coherent model 下可能触发 migration，在 hardware-coherent/direct-access model 下可能远程服务，在 limited model 下 movement 可能位于 launch/synchronization boundary。GPU completion 后 CPU 读 C 也使用同样的 conditional branching。Prefetch 只把可能的 placement work 前移，并在消费前需要正确 stream/event order；advice 是 hint。没有 recorded attributes、fault/migration trace 或 range query 时，唯一诚实结论是 “managed access contract defined; migration behavior unobserved”。

**有效替代方案：** 为 on-demand、advised 和 prefetched 三种 mode 保留同一 correctness oracle 与分别的 observation rows；也可以改用 M09 explicit-copy baseline，但必须明确这是不同 data-movement contract。

**常见错误：** 把 one pointer 当作 one memory；把 accessibility 当 residency；假定所有 Linux GPU 都 fault-migrate；用 M02 的 32-byte segment 推导 page size；把 prefetch 当永久 pin；用 VIS08 transition count 充当 profiler output。

## PB-R2-003：修复跨 stream 分配生命周期与 pool 声明

- **ID 与双语发布对：** PB-R2-003；位于 `practice-bank` Publication Pair。
- **类型与难度：** Allocation-lifetime correctness debugging；高级。
- **直接先修条件：** [M11：Stream-ordered allocation 与 memory pool](/memory/stream-ordered-allocation-memory-pools/)。
- **硬件门槛（Hardware gate）：** 静态 lifetime 审查无需硬件；后续 allocator run 要求 Native Linux CUDA system，并先检查成功的 `cudaDevAttrMemoryPoolsSupported != 0` observation。
- **相关学习单元与资源：** [M07](/memory/stream-ordering/)、[M08](/memory/event-dependencies-timing/)、[M11](/memory/stream-ordered-allocation-memory-pools/)和 [M14](/memory/cuda-graphs/)。
- **最后复核（Last reviewed）：** 2026-08-29。

**题目：** Host 在 `s_alloc` 中调用 `cudaMallocAsync(&p, n, s_alloc)`，紧接着在 `s_use_a` 与 `s_use_b` 提交两个访问 `p` 的 kernel，却没有 allocation-completion edge。它随后按 host submission order 在 `s_alloc` 调用 `cudaFreeAsync(p)`。Pool 开启全部 reuse attributes，并把 release threshold 设为最大值；测试要求下一次 allocation 必须返回同一 pointer，由此声称“没有 allocation overhead 且一定更快”。修复 lifetime graph、pool policy 与 acceptance。

**约束：**

- 先检查 memory-pool support query 的 API result 与 value；header 中存在 enum 不能替代 device observation。
- 从 allocation operation completion 到每个 first use 建 edge，从每个 last use 到 free 建 edge；host call return/submission order 不能替代 cross-stream dependency。
- 把 logical pointer lifetime、pool backing-resource retention、reuse permission、pointer identity 与 performance 分成独立 columns。

**预期证据：** 一张含 allocation、two consumers、join-before-free、pool attributes 和 release policy 的 DAG，以及不使用 pointer equality 或 speedup 的 static acceptance checklist。

**验收条件：**

- `ready` event 在 `s_alloc` 中 allocation 后 record，两个 use streams wait；每条 use stream 的 last-use event 都进入 release stream 的 join，free 只在两项完成后执行。
- Pointer 只有在 allocation operation 完成后且 free operation 执行前可访问；pool 保留 backing resource 不延长 stale pointer lifetime。
- Follow-event、opportunistic 与 internal-dependency settings 被写成 allocator permissions；internal dependency 可能添加 ordering，不能视为 free concurrency。
- Release threshold 不是 hard cap 或 exact retained-byte guarantee；删除 same-address、zero-overhead 与 faster acceptance。

<details><summary>提示 1</summary>画两道 lifetime boundary：allocation completion 到 first use，以及所有 last uses 到 free。</details>

<details><summary>提示 2</summary>Pool 可以保留 backing bytes，同时 logical allocation 已经死亡；这两件事并不冲突。</details>

**参考解答（Reviewed solution）：** 在 support gate 通过后，`s_alloc` 提交 allocation 并 record `ready`。`s_use_a` 与 `s_use_b` 都 wait `ready` 后访问 `p`，各自在最后一次访问后 record `done_a`/`done_b`。Release stream 同时 wait 两代 done event，随后提交 `cudaFreeAsync`。Pool selection 单独记录 default/current 或 explicit path；reuse attributes 只描述 permitted relationships，release threshold 只描述后续 synchronization point 附近尝试释放 excess backing 的 policy。Acceptance 检查 DAG reachability、API returns 与 pointer-use interval，不检查下次 address。没有 allocation trace 或 timing records，因此没有 footprint、latency 或 speedup 结论。

**有效替代方案：** 把 allocation、所有 uses 和 free 放在同一 stream 可由 same-stream order 给出最小合法 lifetime；也可在 allocation 后或 join 前使用明确 host/device synchronization，但它会改变 concurrency contract，必须记录。

**常见错误：** 把 `cudaMallocAsync` return 当 completion；只让一个 consumer 进入 free；依赖 host enqueue order；认为 pool 缓存让 stale pointer 复活；要求 address equality；把最大 threshold 当 unlimited physical memory。

**来源依据（Source basis）：** 本站原创的 [M11 lifetime/policy contract](/memory/stream-ordered-allocation-memory-pools/)、[M07](/memory/stream-ordering/)、[M08](/memory/event-dependencies-timing/)与 [SRC-CUDA-027](/sources-and-versions/#src-cuda-027)，以及 NVIDIA [CUDA Programming Guide v13.3 Stream-Ordered Memory Allocation](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html)和 [CUDA Runtime API v13.3.1 Memory Pools](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY__POOLS.html)。

## PB-R2-004：修复 group participant 与 cooperative-launch 缺陷

- **ID 与双语发布对：** PB-R2-004；位于 `practice-bank` Publication Pair。
- **类型与难度：** Cooperative-group correctness debugging；高级。
- **直接先修条件：** [M12：Cooperative Groups 与可组合同步](/memory/cooperative-groups/)。
- **硬件门槛（Hardware gate）：** 静态 participant 审查无需硬件；后续 block/tile run 使用 Native Linux CC 7.5+ baseline，grid sync 另要求 cooperative-launch capability、合法 resident grid 与 `cudaLaunchCooperativeKernel`。
- **相关学习单元与资源：** [M05](/memory/synchronization-scopes/)、[M06](/memory/warp-divergence-reconvergence/)、[M12](/memory/cooperative-groups/)和 [M13](/memory/asynchronous-copy-pipelines/)。

**题目：** 一个 256-thread block 只让 `threadIdx.x < 128` 的 threads 调用 `cg::tiled_partition<32>(block)`；每个 tile 又只让 even ranks 调用 `cg::reduce(tile, value, op)`。同一 kernel 取得 `this_grid()` 并调用 `grid.sync()`，但 host 使用普通 `<<<grid, block>>>` launch，既不查询 cooperative support，也不验证 resident-grid limit。修复 group contracts；不得用“同一 warp 大概 lockstep”解释。

**约束：**

- 为每个 construction/collective 写出 handle、membership、scope、required participants 与 argument-agreement rule。
- Parent partition construction、tile collective 与 grid collective 分开修复；dynamic active set 不能被命名成永久 warp。
- Grid path 必须显式 query capability、计算 legal cooperative grid、使用 cooperative host launch，并让全部 grid members 参与；否则改用不需要 grid barrier 的方案。

**预期证据：** 一张三行 group-contract ledger、修订后的 control-flow skeleton、cooperative-launch decision table，以及 empty runtime observations。

**验收条件：**

- 完整 block 在 divergence 前取得 `block` 并共同构造 tile；同一 tile 的全部 members 到达同一 reduce instance，只有 per-thread `value` 按 API 允许不同。
- Branching 若只需要部分结果，发生在 collective 完成之后；任何 tile/block sync 的 participant set 与 accessible shared storage scope 对齐。
- Grid sync 只在 checked nonzero cooperative capability、满足 occupancy-derived size limit 且由 `cudaLaunchCooperativeKernel` launch 的 separate path 中出现。
- 当前 CUDA 13 baseline 不使用 archive-only multi-device Cooperative Groups API；静态修复不授予 compilation/runtime evidence。

<details><summary>提示 1</summary>`tiled_partition` 本身就是 parent-group collective，不只是生成一个 local object 的 helper。</details>

<details><summary>提示 2</summary>`this_grid()` 只命名 group；host cooperative launch 才让 grid-wide synchronization contract 成立。</details>

**参考解答（Reviewed solution）：** 所有 256 threads 先取得 `block` 并执行 `tiled_partition<32>(block)`。每个 tile 的 32 members 都调用相同 `reduce(tile, value, cg::plus<int>())`；leader-only store 位于 collective 之后。若只需前四个 tiles，则仍可让全部 parent members 完成 partition，并让不用结果的 tiles 遵守其 own selected collective/control contract。Grid path 在 host 端检查 `cudaDevAttrCooperativeLaunch`，按 active blocks per SM 与 SM count 限制 grid，使用 `cudaLaunchCooperativeKernel`，并证明所有 grid threads 到达 sync。若任一 gate 不成立，删除 grid barrier，改成 kernel boundary 或 block-local algorithm。

**有效替代方案：** 将 inter-block phase 拆成两个 kernels，以 kernel-completion boundary 代替 `grid.sync()`；这保持更宽 hardware coverage，但要重新声明 intermediate storage 与 launch/completion edges。

**常见错误：** 在 branch 内构造 parent tile；只让 leaders 调 collective；把 same call text 当 participation；把 `coalesced_threads()` 当固定 32-lane warp；普通 launch 调 grid sync；从 archive multi-device example 推断 CUDA 13 support。

## PB-R2-005：审查 staged async-copy participant 与证据

- **ID 与双语发布对：** PB-R2-005；位于 `practice-bank` Publication Pair。

<details><summary>提示 2</summary>Target capability、alignment annotation 和 source API name 都不是 disassembly 或 timeline。</details>

## PB-R2-006：审查 graph capture、replay、lifetime 与 update

- **ID 与双语发布对：** PB-R2-006；位于 `practice-bank` Publication Pair。
- **类型与难度：** CUDA Graph lifecycle evidence review；高级。
- **直接先修条件：** [M14：CUDA Graphs 与 repeated launch structure](/memory/cuda-graphs/)。

- **最后复核（Last reviewed）：** 2026-08-29。

**题目：** Capture 从 `s0` 开始，经 captured event fork 到 `s1`，但 `s1` 没有 rejoin `s0`。Library 在 active capture 中同步 captured event，使 capture invalid。程序忽略 `cudaStreamEndCapture` error，尝试 instantiate null graph，提交三次 async launch 后立刻释放 host/device buffers，并假定 topology-changing update 已成功；Reviewer 由“三次 replay”宣布 launch overhead 降低。写出完整 repair 与 allowed claims。

**约束：**

- 先画 intended acyclic nodes/edges，再分别审查 explicit Graph API 与 stream capture；construction mechanism 不能与 execution 混合。
- Capture ledger 必须包含 origin stream、fork/rejoin、prohibited operations、invalidation unwind、end-capture result 与 null-graph handling。
- Definition、instantiation、launch、completion、external-resource lifetime、template/exec destruction 与 bounded update 分开；不得提供 performance 数值。

**预期证据：** 一份 corrected DAG、capture state machine、graph/executable/external-resource lifecycle table、update decision matrix，以及 blank compilation/runtime/performance observations。

**验收条件：**

- `s1` 通过 captured event dependency 加入同一 capture，并在 `cudaStreamEndCapture(s0)` 前把 dependency rejoin origin；active capture 内删除 prohibited query/synchronize call。
- 若 operation invalidates capture，程序仍在 origin 调 end capture 退出，检查 error/null graph，丢弃 capture，且绝不 instantiate/launch invalid result。
- Successful graph 只有在 checked instantiation 后 replay；每次 launch 是 asynchronous stream work，final event/stream completion 保护 output consumption、resource release 与 teardown。
- Update result 按 topology/node/context/parameter restrictions 检查；不兼容 change 创建新 graph 并重新 instantiate；三次 submission 不证明 overhead、concurrency 或 speedup。

<details><summary>提示 1</summary>Capture failure 不是立即忘记 stream state；仍需通过 origin end-capture boundary 完成 unwind。</details>

<details><summary>提示 2</summary>Graph handle、executable handle 与 node 指向的 external storage 有三条不同 lifetime。</details>

**参考解答（Reviewed solution）：** 先定义 expected DAG，并选择 capture 作为 construction path。`s0` begin capture，record captured fork event；`s1` wait 后提交支持的 work，再 record rejoin event；`s0` wait rejoin 后 end capture。任何 prohibited operation 都让路径进入 invalidated state：在 `s0` end capture，检查 failure 与 null result，跳过 instantiate。Success path 检查 instantiate，随后按 contract replay；每次 launch 的 immediate error 与覆盖 final work 的 completion 分开观察。Host/device buffers、callbacks、events 与其他 pointees 至少活到最后相关 node 完成。Update 先分类，checked API 拒绝时重新定义并 instantiate。静态 review 没有执行 graph，因此唯一结论是 lifecycle repaired，performance unobserved。

**有效替代方案：** 使用 explicit Graph API 直接创建同一 DAG，避免 capture-state restrictions；或在 topology 改变时 recapture 并重新 instantiate。两种方案仍需相同 external-resource 与 completion ledger。

**常见错误：** Auxiliary stream 不 rejoin；capture 中 device/event synchronize；忽略 end-capture failure；instantiate null graph；把 instantiate 当 launch；async launch 后立即 free；假设 update 成功；由 replay count 推断 speedup。

- **类型与难度：** Device-link correctness debugging；高级。

- **最后复核（Last reviewed）：** 2026-08-29。

**题目：** `caller.cu` 中的 kernel 调用只在 `device_math.cu` 定义的 external `__device__` function。Build 只对 caller 使用 `-dc`，对 definition 使用普通 `--compile`，把唯一 device definition 放进 `.so`，跳过 explicit device link 后直接 host link；两份 object 还因不同 `__CUDA_ARCH__` branch 生成同名 template 的不同语义。作者由 final artifact existence 宣称 device symbols 已解析且 kernel 可运行。修复完整 graph 与 allowed claims。

**约束：**

- 先列 declaration、definition 与 cross-translation-unit device edge，再为每个 participating CUDA source 应用 `-dc = --relocatable-device-code=true --compile`；一个 whole-program object 不能被其他 object 的 RDC mode 追溯修复。
- 分别记录 RDC compile、explicit `--device-link`、device-link output 与 final host link 的完整 input/output；static archive 与 shared library 在 device linker/host linker 两栏分开。
- 审查 device-code ABI、pointer size、link-compatible target、linker version 和 header-defined weak/template `__CUDA_ARCH__` semantics；不得把 hash、symbol list 或 link success 当 runtime observation。

**预期证据：** 一张 `sources -> RDC objects -> device_link.o -> final host artifact` DAG、一份 phase command ledger、library-consumer matrix、object compatibility/semantic checklist，以及空白 runtime/performance rows。

**验收条件：**

- `caller.cu` 与 `device_math.cu` 都产生含 relocatable device code 的 host object；declaration 不是 definition 或 resolved-symbol observation。
- Device link 接收全部 RDC objects、eligible static archives 和完整 target set，解析 external device symbols 并产生 host object；final host link 仍接收 original CUDA objects、`device_link.o` 与所需 host/CUDA libraries。
- Device linker 可以考虑含 RDC 的 `.a`/`.lib`，但忽略 `.so`/`.dll`；只存在 shared library 中的 device definition 不能满足本次 external device reference。
- Inputs 通过 ABI、pointer-size、link-compatible SM 与 linker-version gate，并采用统一 compute target 或消除 `__CUDA_ARCH__`-dependent shared-header semantics；成功 link 仍不证明 load、launch、correctness 或 performance。

<details><summary>提示 1</summary>Device link 的 output 是给 host linker 的 object，不是最终 executable。</details>

<details><summary>提示 2</summary>分别问 device linker 与 host linker 看到了哪些 objects 和 libraries；两者不会因为同一个 `-lfoo` 就消费相同内容。</details>

**参考解答（Reviewed solution）：** 修订后的 source graph 明确 `caller.cu -> ex10_device_scale()` external edge 与 `device_math.cu` definition。两者使用相同 dialect、pointer size 与 compatible target clauses 执行 `-dc`，得到 `caller.o` 和 `device_math.o`。Explicit `--device-link` 接收这两项以及任何含 RDC 的 static archive，固定完整 target set 与 output `device_link.o`；final link 使用 `--no-device-link` 并同时传入两个 original objects、device-link object 与 required libraries，从而保持两个 boundary 可审查。`.so` 只保留为 host-link input，不能提供 device definition。Header ledger 消除不同 `__CUDA_ARCH__` behavior 或统一 compute target。没有 qualifying command/log/hash record，更没有 executable execution，因此唯一结论是“link graph repaired; build and runtime unobserved”。

**有效替代方案：** 若不需要 cross-file device edge，可把 required device definition 置于 caller 的 whole-program visibility boundary 并删除 RDC/device-link path；也可把 definition 放入含 RDC member 的 static archive，只要 archive、target 与 compatibility inputs 都被完整记录。

**常见错误：** 只对一侧使用 `-dc`；把 `extern` declaration 当 resolved definition；让 host linker 解析 device symbol；把 shared library 当 device-link input；遗漏 original CUDA object 的 host registration code；忽略 linker version 或 `__CUDA_ARCH__` semantic mismatch；由 final artifact 推断 execution。

**来源依据（Source basis）：** 本站原创的 [M18 object/link contract](/toolchain/separate-compilation-device-linking/)、[M15 phase boundary](/toolchain/nvcc-compilation-flow/)、[M16 artifact vocabulary](/toolchain/ptx-cubin-fatbinary/)、[EX10 device-link contract](/examples/ptx-fatbinary-inspection/)和 [SRC-CUDA-034](/sources-and-versions/#src-cuda-034)，以及 NVIDIA [current NVCC v13.3 Using Separate Compilation in CUDA](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#using-separate-compilation-in-cuda)、[12.9.2 archive](https://docs.nvidia.com/cuda/archive/12.9.2/cuda-compiler-driver-nvcc/index.html#using-separate-compilation-in-cuda)与 [11.8.0 archive](https://docs.nvidia.com/cuda/archive/11.8.0/cuda-compiler-driver-nvcc/index.html#using-separate-compilation-in-cuda)。

## PB-R2-012：修复逐元素 map 的所有权与数据移动账本

- **ID 与双语发布对：** PB-R2-012；位于 `practice-bank` Publication Pair。
- **类型与难度：** Ownership 与 memory-movement contract review；中级。
- **直接先修条件：** [A01：逐元素映射与一元素一所有者](/algorithms/elementwise-map/)。
- **硬件门槛（Hardware gate）：** 无；只做静态索引、所有权和流量推导，不编译或运行 EX02，也不执行 GPU。
- **版本门槛（Version gate）：** Kernel、thread hierarchy 与 memory-management 判断分别绑定 current CUDA Programming Guide v13.3/Runtime API v13.3.1、12.9.1 owner guide 或 11.8.0 archive；任一 source coordinate 都不构成 build、runtime 或 performance evidence。
- **相关学习单元与资源：** [F03](/foundations/multidimensional-indexing/)、[F04](/foundations/host-device-lifecycle/)、[M02](/memory/coalescing-transactions/)、[A01](/algorithms/elementwise-map/)和 [EX02](/examples/vector-addition/)。
- **最后复核（Last reviewed）：** 2026-08-30。

**题目：** 一份二元 map 设计令每个 thread 写 `output[i]` 和 `output[i + 1]`，对 ceiling-divided grid 删除 `i < n` guard，把 input/output alias 视为当然安全，只统计一次加法，并由相邻地址直接宣称 coalesced speedup。把它修复成 `output[i] = transform(left[i], right[i])` 的唯一所有者合同、bounds-safe launch 与分层 memory-movement ledger。

**约束：**

- 显式声明 logical domain、每个 `i` 的 read/write set、`owner(i)` 与 alias policy；不能用 barrier 或 atomic 掩盖重叠写入。
- 将每个合法 element 的 device global loads/store 与 application-level H2D/D2H movement 分开；resident input 或 downstream device consumer 只能作为具名 lifecycle variant。
- 只写 expected request counts 与待测假设，不虚构 transaction、bandwidth、duration、correctness 或 speedup observation。

**预期证据：** 一张 index-to-owner 表、一份 write-set disjointness 与 partial-block proof、一张按 `n` 和 `sizeof(T)` 展开的 kernel/transfer ledger，以及一条 compilation/runtime/performance 均未观察的 claim repair。

**验收条件：**

- 对每个 `i` in `[0,n)` 恰有一个 global index 为 `i` 的 owner，且该 thread 只写 `output[i]`；不同合法 indices 的 write sets 不相交。
- Ceiling division 与 `if (i < n)` 同时保留；最后一个 block 的 extra threads 不发出 global load/store，`n = 0` 的 launch policy 另行声明。
- 二元 map 每个合法 element 的语义请求记为两个 device loads 和一个 device store；H2D、kernel movement 与 D2H 各占独立账本行，并明确 alias 是否禁止或已证明安全。
- 连续地址只形成 M02 的 expected access reasoning；没有 Environment Manifest、实际输出与测量记录时，不发布 transaction、bandwidth 或 speedup 结论。

<details><summary>提示 1</summary>先只画一个 output index：谁读哪些 locations，谁能写这个 location？再比较两个不同 indices 的 write sets。</details>

<details><summary>提示 2</summary>把账本分成 host-to-device、kernel 内 load/store、device-to-host 三层；不要把 value request 数写成 hardware transaction 数。</details>

**参考解答（Reviewed solution）：** 修订方案使用 `i = blockIdx.x * blockDim.x + threadIdx.x`，只在 `i < n` 时读取 `left[i]`、`right[i]` 并写 `output[i]`。这样 coverage 来自 rounded-up grid，uniqueness 来自 global-index mapping，isolation 来自单一 output write；普通 out-of-place map 不需要 output atomic 或 block barrier。Alias 默认禁止；若允许 in-place，则另证每个 thread 只覆盖自己已经读取且其他 thread 不再需要的 element。账本把 resident/nonresident inputs、两个 device loads、一个 device store 与可选 D2H 分开。当前只完成静态合同，所有 observed fields 保持空白。

**有效替代方案：** 可以采用 grid-stride loop，只要每次 iteration 的 index 仍在 bounds 内、每个 output 仍只有一个 owner，并且 ledger 按每个实际处理 element 计数而不重复计算 H2D/D2H。

**常见错误：** 让相邻 threads 写重叠 outputs；认为 ceiling division 自动提供 bounds；默认 alias 安全；把 device load/store 与 PCIe movement 合并；把 request count 当 transaction count；由连续地址或较少 arithmetic 推断 speedup。

**有效替代方案：** 对 bin 数较小或 input 不适合 shared storage 的情况，可以保留简单 global-atomic baseline；也可产生 per-block global partial histograms 后用独立 kernel reduce，只要 storage、completion 与 exact merge proof 完整。

**常见错误：** Plain increment race；把 atomic correctness 等同无 contention；只清零 `blockDim.x` 个 bins；invalid thread early return；遗漏 update 后 barrier；non-atomic cross-block merge；用 global atomic count 减少直接宣称加速。

<details><summary>提示 2</summary>把 data predicate 和 barrier participant set 分成两列，再使用 `(lane*stride+column) mod 32`。</details>

- **ID 与双语发布对：** PB-R2-018；位于 `practice-bank` Publication Pair。
- **类型与难度：** Stencil correctness debugging；高级。
- **直接先修条件：** [A06：Stencil 邻域、Halo 与 Cooperative Reuse](/algorithms/stencil-neighborhood-reuse/)。

- **最后复核（Last reviewed）：** 2026-08-30。

**题目：** 一个 radius-1 square 2D stencil 同时在 edge 上混用 clamp 和 zero policy，只加载 center 与四条 side strip，遗漏 corner halos；没有 output 的 threads 在 cooperative load 前 return。报告还把 direct logical requests 除以 staged slots 直接写成 speedup。重建一个完整、可审查的 baseline。

**约束：**

- 固定一种 boundary policy，并让 CPU oracle、global loader 与 shared consumer 使用同一规则；列出 output domain 与负/越界 coordinate 处理。
- 对 `6x8` output tile 推导完整 `8x10` staged rectangle，标出 center、side halos 与四个 corners，并用 block-stride assignment 证明 coverage/uniqueness。

**预期证据：** Boundary table、80-slot owner map、corner coordinates、participant ledger、direct/staged request equations，以及空白 runtime/performance record。

**验收条件：**

- Selected policy 是唯一数学合同，不执行越界 read；corner coordinates 同时处理两个 axes。
- 48 个 center slots、28 个 non-corner side-halo slots和 4 个 corners合计覆盖 80 slots，每个 slot 恰有一个 writer。
- 没有 output 的 thread 仍可拥有 halo slot并到达 barrier；compute predicate 不包围 rendezvous。
- Direct `6*8*9=432` logical references 与 80 staged positions 只表示 reuse opportunity，不产生 transaction 或 speedup claim。

<details><summary>提示 1</summary>完整 rectangle 的 corners 是 `(0,0)`、`(0,9)`、`(7,0)`和 `(7,9)`。</details>

<details><summary>提示 2</summary>先按 staged linear index 分配 writer，再把 coordinate 映射到 global input 或 boundary value。</details>

**参考解答（Reviewed solution）：** 修订 baseline 选择 symmetric zero policy：域外 coordinate 直接生成 0，不触发 global read。`6x8` outputs 与 radius 1 需要 `8x10` staged rectangle；block-stride loop partition 80 linear slots并自然覆盖四个 corners。每个 thread 无论 load count 或 output validity 都完成 loop 并到达统一 barrier，随后只有 valid output owners读取 3x3 neighborhood。Static ledger 显示 432 logical references 可以由 80 staged slots服务，但没有 cache、transaction、barrier cost 或 environment observation，因此 performance rows 仍为 `unrecorded`。

**有效替代方案：** 可以选择 clamp、periodic 或 valid policy，只要完整重算 output domain/reference；cross-shaped stencil 可以省略 corners，但必须换成对应 sparse-footprint proof。

**常见错误：** 混合 boundary policies；漏掉 corner halos；让无 output thread early return；重复或遗漏 staged writer；把 logical request ratio 当作 hardware traffic 或 elapsed-time ratio。
