练习题库（Practice Bank）收录跨课程反复出现的原创问题。每个条目都说明先修学习单元（Learning Unit）、硬件门槛（Hardware gate）、验收条件、提示、解答和来源依据；它不是复制来的问答清单。

先按条目的先修链接复习，再不看解答完成自己的产物。提示按层展开；解答用于复核边界，不替代作答。当前页面只发布下面十三个完整条目，不用空白题目预告未来内容。

## PB-R0-001：修复证据状态（Evidence Status）记录

- **ID 与双语发布对（Publication Pair）：** PB-R0-001；位于 `practice-bank` Publication Pair。
- **类型与难度：** 核心心智模型；基础。
- **先修条件：** [O02：诚实记录证据状态](/start/evidence-status/)。
- **硬件门槛（Hardware gate）：** 无；只分析文本记录。
- **相关学习单元：** O02。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份发布说明写道：“Linux 构建因容器仓库超时而跳过。贡献者在自己的 GPU 上贴出 `PASS`，所以项目已经 Compile-Checked 和 Runtime-Verified。网页测试也证明浏览器演示可以算 CUDA 运行。”请重写成一条诚实记录。

**约束：**

- 只能使用 O02 的受控 Evidence Status。
- 不能虚构 manifest、构建日志、观察日期或维护者复现。
- 必须把预期观察和已记录观察分开。

**预期证据：** 一条逐句修订的状态记录，明确每项声明已有的证据、仍缺的材料和保留的状态。

**验收条件：**

- blocked build 没有 Compile-Checked。
- 社区 `PASS` 在缺少完整 Environment Manifest、日志、标准和日期时不能授予 Community-Observed。
- 维护者复现前不能授予 Runtime-Verified；若活动需要 GPU 行为，则保留 Pending Hardware Verification。
- 网页测试和浏览器模型不授予任何 CUDA Evidence Status。

<details><summary>提示 1</summary>逐句问“谁做了什么，留下了什么可复核材料”。</details>

<details><summary>提示 2</summary>blocked 不是 passed；一句 `PASS` 也不是完整社区报告。</details>

**解答：** “声明的编译工作因容器仓库超时而未执行，因此没有 Compile-Checked。社区提供了未经完整记录的 `PASS` 文本，缺少 manifest、日志、标准和日期，暂不能授予 Community-Observed。维护者没有在声明的 Reference Environment 中复现；如果验收要求 GPU 行为，运行轴保持 Pending Hardware Verification。网页质量测试只验证网站，不授予 CUDA 状态。预期输出与已记录观察均未形成合格记录。”

**常见错误：** 把 blocked 写成失败后仍授予状态；为了“尊重社区”而省略 manifest；把网页 CI 当成 CUDA 编译；删除 Pending Hardware Verification 却没有维护者证据。

**来源依据（Source basis）：** 本站 [O02](/start/evidence-status/) 的原创证据合同，以及 NVIDIA `nvcc` 13.3.1 [supported phases](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#supported-phases)对编译和运行阶段的区分。

## PB-R0-002：补全 manifest 并修复支持边界

- **ID 与双语发布对：** PB-R0-002；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；基础。
- **先修条件：** [O03：读懂环境清单（Environment Manifest）](/start/environment-manifest/)。
- **硬件门槛（Hardware gate）：** 无；使用假设记录，不运行 CUDA。
- **相关学习单元：** O03。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份记录只有“8 GB GPU、CUDA 12、WSL、kernel 0.2 ms”，并声称“属于完整层级，且本站支持这个环境”。列出必须补充的 manifest 字段，并修复两条结论。

**约束：**

- 不猜 GPU 型号、compute capability、driver、Toolkit patch 或测量方法。
- 正确性和性能字段都要覆盖，但 result 保持未观察。
- 只按 O03 的 Supported Environment 和 GPU Capability Tier 定义判断。

**预期证据：** 一份待补字段清单、两条修订后的支持/层级结论，以及把无方法性能文字隔离为未审核原始记录的说明。

**验收条件：**

- manifest 分开 GPU identity、compute capability、GPU count、driver、Toolkit、component、NVCC、host compiler、OS、workload/shape、memory、permissions、exact command、correctness 和 observation date。
- 性能附录包含 baseline、hypothesis、clocks/power、warm-up、synchronization、timer/profiler version、statistics/sample method 和 interpretation boundaries。
- 结论说明 WSL 不是本站 Supported Environment；8 GB 本身不能决定 Modern Single-GPU Capability Tier。

<details><summary>提示 1</summary>先把“CUDA 12”拆成 Toolkit patch、driver 和相关 component versions。</details>

<details><summary>提示 2</summary>`0.2 ms` 没有同步、工具版本、样本和基线时不可解释。</details>

**解答：** 建立硬件、软件、工作负载、执行、正确性、日期和性能七组字段，所有未知值标成“待采集”并注明查询方法。把 `0.2 ms` 移到“未审核原始文字”，结果字段保持空。支持结论改为：“原生 Linux 是唯一 Supported Environment；WSL 只可作为非支持比较。”层级结论改为：“需要 compute capability 8.0 或更新、至少 8 GB，并同时满足 count、features 和 permissions，才能进入 Modern Single-GPU Capability Tier；现有记录无法判断。”

**常见错误：** 把“CUDA 12”当作完整软件坐标；用显存代替 compute capability；接受一个没有 synchronization 的延迟；把 NVIDIA 产品支持写成本站责任。

**来源依据（Source basis）：** 本站 [O03](/start/environment-manifest/) 的原创 manifest 和支持合同，以及 NVIDIA [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)与 [compute capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html)。

## PB-R0-003：在运行前审查索引预测

- **ID 与双语发布对：** PB-R0-003；位于 `practice-bank` Publication Pair。
- **类型与难度：** 概念与实现；基础。
- **先修条件：** [F01：从预测到第一个 CUDA kernel](/foundations/first-cuda-kernel/)。
- **硬件门槛（Hardware gate）：** 无；只做静态推理。
- **相关学习单元：** F01。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 对 `N = 65`、`blockDim.x = 32` 的一维向量加法，给出 block 数、总 launch thread 数、最后一个合法 index，并判断最后一个 block 中 `threadIdx.x = 0` 和 `1` 的 bounds 状态。解释为什么 bounds check 仍然必需。

**约束：** 先写公式；不运行程序；零起始索引；不能把 launch 范围当作逻辑数据范围。

**预期证据：** 一张坐标表和一段不超过五句的所有权解释。

**验收条件：** 得到 3 个 block、96 个 launch thread、最后合法 index 64；识别最后 block 的局部 thread 0 合法、1 越界；说明 31 个越界 thread 必须跳过访问。

<details><summary>提示 1</summary>Block 数使用 `ceil(65 / 32)`。</details>

<details><summary>提示 2</summary>最后一个 block 的 `blockIdx.x = 2`，所以其全局 index 从 64 开始。</details>

**解答：** `ceil(65 / 32) = 3`，总共 launch 96 个 thread。最后一个合法元素是 index 64。最后 block 中局部 thread 0 的 global index 是 64，IN BOUNDS；局部 thread 1 的 global index 是 65，OUT OF BOUNDS。其余局部 thread 也越界，因此 kernel 必须用 `index < N` 保护访问。

**有效替代方案：** 可以用数轴或 VIS02 的静态坐标表表达，只要公式和 bounds 理由仍可复核。

**常见错误：** 向下取整成两个 block；把 index 65 当成最后元素；认为多出的 thread 没有被 launch。

**来源依据（Source basis）：** 本站 [F01](/foundations/first-cuda-kernel/) 与 [VIS02](/visuals/indexing/) 的原创索引模型，以及 NVIDIA [Introduction to CUDA C++](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html)。

## PB-R0-004：修复不完整的错误与正确性边界

- **ID 与双语发布对：** PB-R0-004；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；基础。
- **先修条件：** [F01](/foundations/first-cuda-kernel/)。
- **硬件门槛（Hardware gate）：** 无；审查假设流程。
- **相关学习单元：** F01、O02。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个程序只检查 `cudaMalloc` 和最终输出文字，然后声称“无报错且 GPU 正确”。写出缺失边界，并定义一个元素的接受规则。

**约束：** 使用 EX02 已声明的 Runtime 流程和容差；不得虚构输出；必须区分 API 成功与数值正确。

**预期证据：** 按执行顺序排列的检查清单，以及一条可计算的数值接受条件。

**验收条件：** 包含三次 allocation、两次 H2D copy、launch error、synchronization、D2H copy、CPU comparison 和三次 free；绝对 `1e-5` 或相对 `1e-5` 满足其一即接受；指出一行输出不能替代这些检查。

<details><summary>提示 1</summary>Launch 返回与 kernel 完成是两个边界。</details>

<details><summary>提示 2</summary>失败条件是绝对和相对标准都不接受，而不是任一不接受。</details>

**解答：** 在三次 `cudaMalloc` 后检查两次 H2D copy；launch 后先查 `cudaGetLastError`，再用 `cudaDeviceSynchronize` 等待并检查执行；检查 D2H copy；逐元素与独立 CPU reference 比较；最后检查三次 `cudaFree`。若 `abs(expected-actual) <= 1e-5` **或**该差值 `<= 1e-5 * max(abs(expected), abs(actual))`，元素通过。API 全部成功和数值全部通过缺一不可。

**有效替代方案：** 可以用状态机或时序图代替清单，但必须保留相同顺序和两个独立验收层。

**常见错误：** 只同步不检查 launch；把两个容差写成 AND；把 host test 当作 GPU 结果。

**来源依据（Source basis）：** 本站 [F01](/foundations/first-cuda-kernel/) 与 [EX02](/examples/vector-addition/) 的 canonical error/correctness contract，以及 NVIDIA [CUDA Runtime API](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html)。

## PB-R1-001：修复生命周期、构建与错误边界

- **ID 与双语发布对：** PB-R1-001；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与正确性；中级。
- **直接先修条件：** [O04：面向 CUDA 学习者的 C++17 复习](/start/cpp17-for-cuda/)。
- **硬件门槛（Hardware gate）：** 无；只做源码与构建设计审查，不需要 GPU。
- **相关学习单元：** O04。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份 `.cu` 补丁把局部 `std::vector<float>` 的 `data()` 保存到异步复制任务中，函数在任务完成前返回；一个管理 CUDA 分配（allocation）的资源获取即初始化（Resource Acquisition Is Initialization, RAII）所有者（owner）在析构函数里因 `cudaFree` 失败而 `throw`；一个 `__host__ __device__` helper 调用只允许主机（host）执行且会抛异常的函数。CI 只用 host compiler 编译调用方，就宣称 host 与设备（device）路径都已构建；运行路径用 `try/catch` 包住 kernel launch，却忽略 `cudaError_t`、launch check 和 completion check。写出最小修复方案。

**约束：**

- 不执行构建、sanitizer 或 CUDA，也不虚构诊断与输出。
- 把被指对象生命周期（pointee lifetime）、所有权（ownership）、构建边界（build boundary）和错误边界（error boundary）分开处理。
- 裸指针只能作为非拥有型视图（non-owning view）；修复必须说明 owner 何时才可销毁。

**预期证据：** 一条覆盖异步完成点的所有权时间线、一张 host/device 构建阶段表，以及按执行顺序排列的错误检查清单。

**验收条件：**

- 指出局部 `vector` 先销毁会让保存的 view 悬空，并让 owner 覆盖异步操作完成点，或在作用域退出前建立明确 completion boundary。
- CUDA owner 的析构函数保持不抛异常；若 cleanup failure 必须可观察，则提供显式 `close` 或 `reset` 路径。
- 把 host-only throwing code 与 device-safe helper 分开，让 device 所需定义对 `nvcc` 路径可见，并分别记录 compilation、按需 device linking 和 host linking；host object 成功不证明 device path 或执行。
- 检查每个相关 `cudaError_t`，把 launch error 与 completion error 分开；host exception adapter 只能在保存 CUDA 失败信息后转换错误。

<details><summary>提示 1</summary>复制 raw pointer 只复制地址值，不会延长 `vector` 或 allocation 的生命周期。</details>

<details><summary>提示 2</summary>`try/catch` 观察 host exception；CUDA Runtime failure 先通过返回值、launch boundary 和 completion boundary 暴露。</details>

**解答：** 把 staging buffer 和 CUDA allocation 放进一个 operation owner，使它们至少活到 stream event 或显式 synchronization 确认任务完成；另一种最小修复是在局部 owner 销毁前同步。所有 raw pointer 都标成 view，并携带 extent 与 address-space 含义。析构函数只做不抛异常的 best-effort cleanup，要求报告 cleanup failure 时调用显式 `close`。把 throwing host adapter 与 device helper 分开，确保 `.cu` 和 device 所需定义由 `nvcc` 编译，并单独记录可能的 device link 与最终 host link。逐项检查 allocation、copy 和其他 Runtime API 返回值，launch 后检查 launch error，再在同步或 event 边界检查 completion；只有 host adapter 在保留 error name、message 和调用位置后才可以抛异常。任何构建产物都不证明 GPU 路径已执行。

**有效替代方案：** 可以选择拥有异步状态的 operation object，也可以把复制改成在当前作用域内完成的同步操作；两种方案都必须让 owner 覆盖最后一次合法访问，并保留同样的构建与错误边界。

**常见错误：** 只把一个 pointer 副本设成 `nullptr`；让 non-owning view 负责 `free`；从析构函数抛异常；让 host-only `throw` 进入 device path；把 host compilation、linking 或零 warning 当作 CUDA 执行证据。

**来源依据（Source basis）：** 本站 [O04](/start/cpp17-for-cuda/) 的原创生命周期、构建与错误合同，以及 [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)、NVIDIA [CUDA Runtime API Error Handling](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__ERROR.html)和 [`nvcc` compilation trajectory](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#the-cuda-compilation-trajectory)。

## PB-R1-002：修复隐藏生产者失败的构建记录

- **ID 与双语发布对：** PB-R1-002；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与可复现性；中级。
- **直接先修条件：** [O05：可复现的 Linux 命令行工作](/start/linux-command-line/)。
- **硬件门槛（Hardware gate）：** 无；只设计记录流程，不需要 GPU。
- **相关学习单元：** O05。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个脚本通过管道（pipeline）执行 `make -C "$build_dir" all 2>&1 | tee "$record_dir/build.log"`，随后把 `$?` 写进 `build.exit`，并因其中为零而报告 build success。它还保存完整 `env` 和 xtrace，却没有字面命令（literal command）、独立标准输出（stdout）与标准错误（stderr）、实际开始/结束时间或封存哈希。修复失败判断，并设计一份可公开的最小记录。

**约束：**

- 不运行命令，不填写实际退出状态、时间戳、日志内容或哈希，也不虚构任何输出。
- 不记录秘密（secret）、令牌（token）、凭据（credential）或未经允许的完整环境；xtrace 不能替代字面输入。
- 规范记录必须保留 command、stdout、stderr、退出状态（exit status）、UTC 时间戳（timestamp）和 SHA-256 哈希（hash）的边界。

**预期证据：** 一段失败传播解释，以及按采集顺序列出的产物清单（artifact manifest），说明每个文件何时写入、何时关闭、何时参与哈希。

**验收条件：**

- 说明原脚本中的 `$?` 默认属于 `tee`，成功的消费者（consumer）会隐藏失败的生产者（producer）；`2>&1` 还会丢失通道身份。
- 执行前保存固定 `command.sh` 与 NUL 分隔的 argv，记录逻辑/物理工作目录和允许列表环境（allowlisted environment），不保存 secret。
- 在阶段前后采集 UTC 时间；把 stdout 与 stderr 写入独立文件，并在任何其他简单命令前复制 producer status。
- 日志关闭后，对固定 artifact 清单计算 SHA-256；`SHA256SUMS` 不把自己列为输入，hash 不证明命令正确。
- 若保留 pipeline，则启用 `pipefail` 并立即复制 `PIPESTATUS`，分别保存 producer 与 `tee` 状态；combined log 只能是便利视图。

<details><summary>提示 1</summary>管道的默认状态来自最后一段，不是你最关心的 `make`。</details>

<details><summary>提示 2</summary>先把 `$?` 或 `PIPESTATUS` 复制到 shell variable，再执行 `printf`、timestamp 或 hash 命令。</details>

**解答：** 规范路径可以直接移除 `tee`：先保存不可变 `command.sh`、`argv.nul`、路径与 allowlisted environment，写入 `started-at.txt`，再把 `make` 的 stdout 和 stderr 分别重定向到两个文件。命令返回后立即执行 `build_status=$?`，之后才把该值写入 `build.exit`，并采集 `ended-at.txt`。所有 stream 关闭后，对明确列出的 command、argv、路径、环境、时间、stdout、stderr 和 exit 文件生成 `SHA256SUMS`，且不包含该清单自身。记录模板只定义文件和顺序，不填任何未观察值。完整 `env` 与可能展开 credential 的 xtrace 从公开记录中移除。

**有效替代方案：** 若交互显示必须使用 `tee`，可用 `pipefail` 并在下一条简单命令前复制 `PIPESTATUS`，分别记录 `make` 与 `tee`；但合并流不能恢复 stdout/stderr 身份，所以仍需独立的规范通道产物或明确降低记录范围。

**常见错误：** 在 `printf` 之后才读取 `$?`；只记录 pipeline 的整体状态；把 combined log 当作两个通道；hash 尚未关闭的文件；把完整 environment 或 xtrace 当作“更可复现”而泄露 secret；为模板填入猜测的 `0` 或时间。

**来源依据（Source basis）：** 本站 [O05](/start/linux-command-line/) 的原创命令记录合同，以及 [GNU Bash 5.3 Reference Manual](https://www.gnu.org/software/bash/manual/bash.html)和 [GNU Coreutils 9.11](https://www.gnu.org/software/coreutils/manual/coreutils.html)。

## PB-R1-003：分类架构声明并计算有边界的算术强度

- **ID 与双语发布对：** PB-R1-003；位于 `practice-bank` Publication Pair。
- **类型与难度：** 架构推理与定量分析；中级。
- **直接先修条件：** [O06：架构回顾：速率、延迟与数据移动](/start/architecture-refresher/)。
- **硬件门槛（Hardware gate）：** 无；只做静态分类与算术。
- **相关学习单元：** O06。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 把以下五条待审核草稿分别归入延迟（latency）、吞吐量（throughput）、带宽（bandwidth）、并发（concurrency）或占用率（occupancy），并修复越界结论：A.“kernel latency 是 40 us”；B.“一个批次完成 2,000,000 items/s”；C.“64 MB requested bytes 在 4 ms 内经过 device DRAM 到 SM，所以这是 actual bandwidth”；D.“两个 kernel 位于不同 stream，所以已经并发执行”；E.“occupancy 为 75%，所以达到 peak throughput 的 75%”。然后计算一个独立静态模型：`N = 4096`，每个元素明确计数一次 multiply 和一次 add；在声明的 device-DRAM boundary 上，每个元素恰有一次 4-byte read 与一次 4-byte write，模型不计其他 traffic。

**约束：**

- 这些草稿不是 recorded observation；不补写 timer、profiler、timeline、device 或 workload 事实。
- 算术强度（arithmetic intensity）必须同时声明 operation-count rule、memory boundary、read/write byte 口径和 workload 范围。
- 不从计算结果推出实际性能、内存受限（memory-bound）、加速比（speedup）、重叠（overlap）或利用率（utilization）。

**预期证据：** 一张五行声明分类表（claim-classification table）、一条完整的 intensity 等式，以及一段明确不保证哪些结论的边界说明。

**验收条件：**

- A 只有在命名起止事件和单位后才是 latency；B 是需要工作量与时间窗口的 throughput。
- C 的形式属于带路径与方向的 requested/effective bandwidth，不是 profiler 归属的 actual bandwidth；还要固定 MB 口径和 elapsed boundary。
- D 只说明不同 stream 中的独立工作可能具备 overlap 资格；观察 concurrency 需要 timeline。E 是 active warp 与最大 active warp 的比率，不等于 throughput 百分比。
- 得到 `8192 operations / 32768 bytes = 0.25 operations/byte`，并把结论严格限制在给定计数与 device-DRAM boundary。
- 不作 bottleneck、runtime、bandwidth ceiling 或性能排名声明。

<details><summary>提示 1</summary>先为每条声明写清“一个事件”“时间窗口”“数据路径”“时间重叠”或“resident warp ratio”中的哪一个。</details>

<details><summary>提示 2</summary>每个元素有 2 个 counted operations 和 8 个 boundary bytes。</details>

**解答：** A 是缺少起止边界的 latency 草稿；B 是缺少明确窗口与 workload scope 的 throughput 草稿；C 使用 requested bytes，只能在路径、方向、时间和 MB 定义完整时形成 effective-bandwidth 算式，不能称为 actual bandwidth；D 是 overlap eligibility，不是 observed concurrency；E 是 occupancy 数值，不能换算成 achieved throughput。静态模型中，operation count 为 `4096 * 2 = 8192`，声明边界上的 byte count 为 `4096 * (4 + 4) = 32768`，所以 `I = 8192 / 32768 = 0.25 operations/byte`。这个比值没有测量 traffic 或时间，也没有给出 compute 或 bandwidth ceiling，因此不支持任何性能结论。

**有效替代方案：** 可以用“对象、边界、单位、可证明内容、不可证明内容”五列 claim map 代替分类表，只要五个术语和 intensity 口径仍彼此分开。

**常见错误：** 把 throughput 当作单次 latency；省略 bandwidth path；从不同 stream 推断实际 overlap；把 occupancy 当作 utilization；用 cache traffic 替换题目声明的 DRAM boundary；从 intensity 单独宣布 memory-bound。

**来源依据（Source basis）：** 本站 [O06](/start/architecture-refresher/) 的原创术语与模型边界，CUDA C++ Best Practices Guide v13.3 的 [Bandwidth](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#bandwidth)和 [Occupancy](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#occupancy)，以及 Williams、Waterman 与 Patterson 的 [Roofline primary technical report](https://www.osti.gov/biblio/1407078)。

## PB-R1-004：把产品年表改写成抽象演进

- **ID 与双语发布对：** PB-R1-004；位于 `practice-bank` Publication Pair。
- **类型与难度：** 历史与架构解释；中级。

- **硬件门槛（Hardware gate）：** 无；只做概念改写与来源归属。
- **相关学习单元：** O07。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 把这句话改写成由抽象压力驱动的解释：“每一代新 GPU 都让上一代过时；shader 让图形芯片变成通用处理器，Brook 和 CUDA 只是继续让 GPU 在所有任务上比 CPU 更快。”改写必须按固定功能状态（fixed-function state）、可编程图形阶段（programmable graphics stage）、图形处理器通用计算（general-purpose computing on graphics processing units，GPGPU）和 CUDA 的顺序展开，并为具体历史事实建立原始来源归属（primary-source attribution）。

**约束：**

- 每一步都写出上一层的表达压力、接口回应和仍保留的边界。
- 不写产品排名、普遍加速、完全替代 CPU、无来源的“首次”或仅由日期驱动的因果关系。
- 声明到来源映射（claim-to-source map）只能使用 O07 已引用的权威来源（owner source），并让每项具体事实可回查。

**预期证据：** 一个四阶段因果段落，后接一张 claim-to-source map；两者都要把接口能力与性能结论分开。

**验收条件：**

- Fixed-function state 只能配置预定义操作；表达新效果的压力促成有限 programmable stage，而图形 invocation、输入输出和周围 pipeline 仍保留。
- GPGPU 把 array、computation 和 result 映射到 texture、fragment invocation 与 render target；Brook 提供 stream/kernel 表面，但底层仍经过图形机制。
- CUDA 让 heterogeneous kernel、grid、thread block、memory locality 和 scheduling 成为主要模型，并把 block independence 与可扩展调度联系起来。
- 不声称 CUDA 或 GPU 对所有 workload 更快；具体事实分别归属 Khronos 规范、Brook 项目或论文、CUDA Programming Guide 与 2008 CUDA 论文。

<details><summary>提示 1</summary>不要先问“哪一年有什么产品”，先问“程序员还不能自然表达什么”。</details>

<details><summary>提示 2</summary>“可编程”不等于“通用”：检查谁控制 invocation、input、output 和周围 stage。</details>

**解答：** 固定功能图形接口擅长让大量图形项目通过预定义状态进入专用 pipeline，但新效果只能从既有菜单中选择，表达压力因此集中在允许应用提交受控指令。Vertex 与 fragment program 开放了选定 stage，Cg 又改善了源码表达，但 invocation、资源限制和周围图形语义仍由 pipeline 决定。GPGPU 随后把非图形问题编码成 texture、fragment 和 render target；Brook 用 stream 与 kernel 隐藏部分映射，却仍建立在图形机制上。CUDA 把问题改写为 host/device 分工以及 kernel、grid、thread block 和显式 memory locality，block independence 允许 runtime 在不同资源规模上安排工作。这个抽象转变扩大了可表达范围，不证明任何 workload 的普遍 speedup。来源归属为：programmable stage 对照 Khronos ARB 规范与 programmable vertex engine 论文，Brook 层对照 Stanford BrookGPU 与 Brook 论文，CUDA 模型对照 CUDA Programming Guide Introduction 和 Nickolls 等 2008 年论文。

**有效替代方案：** 可以使用“压力、回应、保留边界、来源”四列表格代替连续段落，但不能退化成产品与日期列表。

**常见错误：** 把 shader 写成不受约束的 general-purpose interface；混淆 Cg 与 Brook 的目标表面；把 graphics-mediated GPGPU 直接称为 CUDA；用发布日期代替因果关系；附加“GPU 总是更快”的无证据结论。

**来源依据（Source basis）：** 本站 [O07](/start/programmable-gpus/) 的原创抽象压力框架，以及 [Khronos ARB_vertex_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_vertex_program.txt)与 [ARB_fragment_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_fragment_program.txt)规范、[Stanford BrookGPU 项目](https://graphics.stanford.edu/projects/brookgpu/)、[CUDA Programming Guide v13.3 Introduction](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/introduction.html)和 [Nickolls 等 2008 年 CUDA 论文](https://doi.org/10.1145/1365490.1365500)。

## PB-R1-006：预测二维 partial launch 的 thread 所有权与层次身份

- **ID 与双语发布对：** PB-R1-006；位于 `practice-bank` Publication Pair。
- **类型与难度：** 执行层次推理与正确性；中级。
- **直接先修条件：** [F02：理解 CUDA 执行层次](/foundations/execution-hierarchy/)。
- **硬件门槛（Hardware gate）：** 无；只做静态计算，不运行 CUDA。
- **相关学习单元与资源：** [F02](/foundations/execution-hierarchy/)、[VIS01](/visuals/kernel-journey/)、[VIS02](/visuals/indexing/)和 [EX03](/examples/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个 x 最快、行主序的逻辑数组宽 `19`、高 `9`，使用 `blockDim = (8, 5)`，`gridDim` 由每轴向上取整得到。对边界 block `blockIdx = (2, 1)` 中的 `threadIdx = (2, 3)`、`(3, 3)`、`(2, 4)`和 `(7, 4)`，分别计算 global 坐标、x 最快的线性 block ID、block 内局部线性 thread ID、`warpInBlock`、lane 和数据所有权；只为拥有数据的 thread 计算 row-major `dataIndex`。最后说明这些身份为什么既不是调度顺序，也不自动授予数据所有权。

**约束：**

- 先写逐轴 ceiling division、global 坐标、线性 block、局部 thread、warp 与 lane 公式。
- 必须分别检查 x 与 y，再决定是否计算可访问的 `dataIndex`；不能 clamp 坐标或把 launch 范围当作逻辑范围。
- 不执行 CUDA，不虚构输出或性能，也不从 block、warp 或 lane 数值推断开始或完成顺序。

**预期证据：** 一张四行表，包含 block/global/local/warp/lane 身份、逐轴 bounds、所有权和可选 `dataIndex`，再附一段身份与调度边界说明。

**验收条件：**

- 得到 `gridDim = (3, 2)`、每个 block 40 个 thread，以及边界 block 的 `linearBlock = 2 + 3 * 1 = 5`。
- `(2, 3)` 映射到 global `(18, 8)`、local `26`、warp `0`、lane `26`，拥有最后一个逻辑元素，`dataIndex = 170`。
- `(3, 3)` 映射到 `(19, 8)`、local `27`、warp `0`、lane `27`，仅 x 越界；`(2, 4)` 映射到 `(18, 9)`、local `34`、warp `1`、lane `2`，仅 y 越界；`(7, 4)` 映射到 `(23, 9)`、local `39`、warp `1`、lane `7`，x 与 y 都越界。三者都不产生可访问的 `dataIndex`。
- 指出该边界 block 只有 `3 * 4 = 12` 个 thread 拥有数据，其余 28 个仍被 launch 但必须跳过访问；任何身份编号都不承诺调度顺序。

<details><summary>提示 1</summary>这个 block 的 global 起点是 `(2 * 8, 1 * 5) = (16, 5)`；合法局部 x 只有 `0..2`，合法局部 y 只有 `0..3`。</details>

<details><summary>提示 2</summary>使用 `localThread = threadIdx.x + 8 * threadIdx.y`，再分别计算 `floor(localThread / 32)` 与 `localThread % 32`。</details>

**解答：** 逐轴向上取整得到 `gridDim = (ceil(19 / 8), ceil(9 / 5)) = (3, 2)`。二维 x-fastest block 展开给出 `linearBlock = blockIdx.x + gridDim.x * blockIdx.y = 5`，四个 thread 都属于这个 block，但局部身份分别是 26、27、34 和 39，对应 `(warp, lane)` 为 `(0, 26)`、`(0, 27)`、`(1, 2)`和 `(1, 7)`。Global 坐标依次是 `(18, 8)`、`(19, 8)`、`(18, 9)`和 `(23, 9)`。只有 `(18, 8)` 同时满足 `gx < 19` 与 `gy < 9`，所以只有它拥有数据，且 `dataIndex = 18 + 19 * 8 = 170`；其余三项在展平和访问前停止。边界 block 的有效局部区域是 3 列乘 4 行，因此 12 个 thread 拥有数据、28 个不拥有数据。Block、local thread、warp 与 lane 编号描述层次身份，不描述 block 调度、warp 完成顺序或数据合法性。

**有效替代方案：** 可以用标注坐标的 `8 x 5` block 图或 identity ledger 代替表格，只要四个 thread 的公式、逐轴 bounds、warp/lane 和唯一合法 `dataIndex` 都可复核。

**常见错误：** 把 `gridDim` 向下取整；把二维 `threadIdx` 直接相加；让 local ID 34 变成 data index 34；认为 warp 1 的 thread 自动越界；从 block ID 5 或 warp ID 0 推断执行先后；为无效坐标展平并访问数组。

**来源依据（Source basis）：** 本站 [F02](/foundations/execution-hierarchy/) 的原创层次与所有权合同、[VIS01](/visuals/kernel-journey/)的调度边界、[VIS02](/visuals/indexing/)的坐标模型和 [EX03](/examples/multidimensional-indexing/)的应用布局边界，以及 NVIDIA [Writing CUDA SIMT Kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

## PB-R1-007：修复过早展平的三维 bounds 缺陷

- **ID 与双语发布对：** PB-R1-007；位于 `practice-bank` Publication Pair。
- **类型与难度：** 调试与多维正确性；中级。
- **直接先修条件：** [F03：把多维索引与边界写成正确性合同](/foundations/multidimensional-indexing/)。
- **硬件门槛（Hardware gate）：** 无；只审查和修复源码，不运行 CUDA。
- **相关学习单元与资源：** [F03](/foundations/multidimensional-indexing/)、[VIS02](/visuals/indexing/)和 [EX03](/examples/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一个三维 kernel 先计算 `gx`、`gy`、`gz`，但只检查 x，随后就在 y 与 z 尚未通过 bounds 前展平并访问：

```cpp
if (gx >= width) {
  return;
}

const std::size_t index = ((gz * height) + gy) * width + gx;
output[index] = input[index];
```

在保持 x 最快行主序布局的前提下修复顺序。再对 `width = 13`、`height = 6`、`depth = 5`、`blockDim = (5, 4, 2)` 的 launch 计算 `gridDim`，并分类边界 block `blockIdx = (2, 1, 2)` 中的 `threadIdx = (2, 1, 0)`、`(3, 1, 0)`、`(2, 2, 0)`和 `(2, 1, 1)`。只为合法坐标给出线性索引。

**约束：**

- 保留逐轴 global 坐标、逻辑 extent 和 `((gz * height) + gy) * width + gx` 映射；不能 clamp、修改 extent 或缩小 launch 来隐藏 fringe。
- 任一活动轴越界都必须在展平和任何数组访问之前停止；索引类型必须足以容纳完整元素计数。
- 不执行 CUDA，不填写输出或性能，也不把静态补丁、host-only 检查或浏览器模型写成 CUDA Evidence Status。

**预期证据：** 一份最小源码补丁、一张四行逐轴 bounds 表，以及一句说明这份静态审查没有产生编译或运行证据的话。

**验收条件：**

- 修复使用 `gx >= width || gy >= height || gz >= depth` 的 early return，或只在三个 `<` 谓词同时成立时包围展平和访问。
- 得到 `gridDim = (3, 2, 3)`；四个局部坐标分别映射到 global `(12, 5, 4)`、`(13, 5, 4)`、`(12, 6, 4)`和 `(12, 5, 5)`。
- 只有 `(12, 5, 4)` 合法，且 `dataIndex = ((4 * 6) + 5) * 13 + 12 = 389`；其余三项分别仅因 x、y、z 越界，并在展平前停止。
- 不把得到整数的 flattening 表达式当作合法访问证明，也不从修复本身声明 Compile-Checked 或 Runtime-Verified。

<details><summary>提示 1</summary>Early return 连接的是三个“无效”谓词，所以任一为真就必须返回。</details>

<details><summary>提示 2</summary>边界 block 的 global 起点是 `(10, 4, 4)`；最后一个合法元素的三维坐标是 `(12, 5, 4)`。</details>

**解答：** 最小修复是把完整保护放在展平之前：

```cpp
if (gx >= width || gy >= height || gz >= depth) {
  return;
}

const std::size_t index = ((gz * height) + gy) * width + gx;
output[index] = input[index];
```

逐轴向上取整得到 `gridDim = (ceil(13 / 5), ceil(6 / 4), ceil(5 / 2)) = (3, 2, 3)`。所选 block 从 `(10, 4, 4)` 开始，四个 global 坐标依次是 `(12, 5, 4)`、`(13, 5, 4)`、`(12, 6, 4)`和 `(12, 5, 5)`。第一项通过全部三轴检查并映射到 390 个元素中的最后一个 index 389；后三项分别在 x、y、z 上失败，不能计算可访问索引或触及数组。代码审查和手算只建立修复理由，没有编译或执行 CUDA，也没有产生 Evidence Status。

**有效替代方案：** 可以用正向条件 `gx < width && gy < height && gz < depth` 包围展平和全部访问；只要条件外没有 flatten 或数组操作，合同与 early return 等价。

**常见错误：** 用 `&&` 连接三个越界谓词；保留只检查 x 的 guard；先 flatten 再检查 y/z；对越界坐标求模或 clamp；把 CUDA geometry 当作 row-major 布局来源；把 host-only 或 VIS02 结果当作 device 执行。

**来源依据（Source basis）：** 本站 [F03](/foundations/multidimensional-indexing/) 的原创逐轴 bounds 与应用布局合同、[VIS02](/visuals/indexing/)的静态索引模型和 [EX03](/examples/multidimensional-indexing/)的 canonical indexing 与证据边界，以及 NVIDIA [Writing CUDA SIMT Kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html)。

## PB-R1-008：重建 host-device 生命周期并修复证据声明

- **ID 与双语发布对：** PB-R1-008；位于 `practice-bank` Publication Pair。
- **类型与难度：** 生命周期调试与证据审查；中级。
- **直接先修条件：** [F04：显式 host-device 资源生命周期](/foundations/host-device-lifecycle/)。
- **硬件门槛（Hardware gate）：** 无；只审查顺序、所有权与公开证据，不运行 CUDA。
- **相关学习单元与资源：** [F04](/foundations/host-device-lifecycle/)、[O02](/start/evidence-status/)、[O04](/start/cpp17-for-cuda/)和 [EX03](/examples/multidimensional-indexing/)。
- **最后复核（Last reviewed）：** 2026-08-26。

**题目：** 一份单 kernel review packet 把动作打乱为：`cudaFree(d_output)`、D2H copy-back、初始化 `h_input`/`h_expected` 与 `h_output` storage、kernel launch、host comparison 后立即返回、H2D transfer、`cudaDeviceSynchronize`、分配 `d_input`/`d_output`、`cudaGetLastError`、`cudaFree(d_input)`。重建 canonical 成功路径，并为 host containers、host 上的 device pointer handles 和两块 device allocations 标出 owner、取得状态、最后使用、release 责任与返回边界。Packet 还声称：“源码、网站构建和 host-only 检查足以让 EX03 成为 Compile-Checked；静态 lifecycle ledger 足以让它成为 Runtime-Verified。”修复两条声明。

**约束：**

- 不执行 build、host test 或 CUDA，不虚构日志、输出、时间或性能。
- Pointer value 与它指向的 allocation 必须分开；kernel 和 `cudaMemcpy` 都不取得 allocation ownership。
- 只能在最后使用后 release 每项已成功取得的 allocation，且恰好一次；comparison verdict 必须先保存，cleanup 后才能返回。
- Evidence Status 结论必须使用 [O02](/start/evidence-status/)和 [EX03](/examples/multidimensional-indexing/)当前公开记录，不把静态审查升级成观察。

**预期证据：** 一张按顺序排列的 lifecycle ledger，至少包含 action、owner、state before、state after、last use 和 release/return obligation，再附一张 Compile-Checked 与 runtime 声明修订表。

**验收条件：**

- 顺序为 host 初始化、检查两项 device allocation、H2D、launch、`cudaGetLastError`、`cudaDeviceSynchronize`、D2H、host comparison 并保存 verdict、释放两项已取得的 allocation、返回 verdict。
- Host C++ scope 拥有 `h_input`、`h_output` 与 `h_expected`；host pointer 变量只是 handles。Host 控制流承担每次成功 `cudaMalloc` 产生的 release 责任，kernel 使用 buffer 但不接管 ownership。
- 在题目给定路径中，`h_input` 的最后使用在成功的 H2D，`d_input` 的最后使用在成功的 completion boundary，`d_output` 的最后使用在成功的 D2H，`h_output` 与 `h_expected` 的本次最后使用在 comparison；device allocations 显式 release，host containers 在各自 C++ owner 离开作用域时 release。任何失败路径只释放已经取得的 allocation，不读取尚未建立的结果。
- EX03 的 compilation evidence 数组为空，因此不是 Compile-Checked；源码存在、网站构建或 host-only 检查都不能填充该轴。EX03 runtime 保持 Pending Hardware Verification，recorded observations 为空，没有声明 Reference Environment 或合格 GPU execution，因此不能授予 Runtime-Verified。

<details><summary>提示 1</summary>`cudaMalloc` 成功同时产生可用 allocation 与 release obligation；host pointer handle 离开作用域不会替代 `cudaFree`。</details>

<details><summary>提示 2</summary>Launch check 只检查提交边界；completion check 成功后 device input 才越过最后使用，D2H 成功后 device output 才越过最后使用。</details>

**解答：** 先在 host 建立输入、独立 expected data 和 output storage；再分别取得并检查 `d_input` 与 `d_output`。H2D 成功后，`h_input` 在这条给定路径中的最后使用结束；接着提交 kernel，立即检查 `cudaGetLastError`，再检查 `cudaDeviceSynchronize`。只有 completion 成功才执行 D2H，只有 D2H 成功才比较 `h_output` 与 `h_expected` 并保存 verdict。随后对两项已取得的 device allocation 各调用一次并检查 `cudaFree`，最后返回保存的 verdict；host containers 在各自 C++ owner 离开作用域时 release。失败安全变体在失败点停止创建依赖，只清理 ledger 中已经 acquired 的项目。Host 上的 `d_input`/`d_output` 变量只是 handles，device allocation 的 release 责任属于 host 控制流而不是 kernel。证据声明改为：“EX03 没有合格 Lane compile record，compilation axis 为空，所以不是 Compile-Checked。静态 ledger、源码、网站构建和 host-only 检查都没有执行 GPU kernel；EX03 runtime 仍是 Pending Hardware Verification，不能声明 Runtime-Verified。”

**有效替代方案：** 可以用单一 cleanup block 或 [O04](/start/cpp17-for-cuda/)所述的显式不抛异常 RAII owner 管理失败路径；两者都必须保留相同的取得状态、last-use 边界、一次 release、保存 verdict 后 cleanup 再返回，以及独立证据判断。

**常见错误：** 认为复制 pointer 会复制或转移 allocation ownership；在 synchronization 前释放 input；在 D2H 前释放 output；comparison mismatch 直接返回并跳过 cleanup；double free 未取得或已释放的资源；把网站 build、host-only test 或静态表当成 EX03 compilation/runtime 观察。

**来源依据（Source basis）：** 本站 [F04](/foundations/host-device-lifecycle/) 的原创显式 lifecycle、[O04](/start/cpp17-for-cuda/)的 lifetime/ownership 边界、[O02](/start/evidence-status/)的证据合同和 [EX03](/examples/multidimensional-indexing/)的 canonical lifecycle 与当前证据记录，以及 NVIDIA [CUDA Runtime API](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html)。
