## 冻结 workload 与 byte models

不可变坐标是：

```yaml
element_type: float
element_count: 16777216
bytes_per_element: 4
device_vector_count: 3
bytes_per_device_vector: 67108864
maximum_device_allocation_bytes: 201326592
algorithmic_fp32_additions: 16777216
algorithmic_requested_bytes: 201326592
algorithmic_intensity_operations_per_byte: 1/12 (~0.083333)
```

对于每个有效元素，canonical `vector_add` 在声明的 source-level device-memory boundary 请求两次 4-byte read 与一次 4-byte write。因此：

- counted work 为 `16,777,216 x 1 = 16,777,216` 次 FP32 additions；
- requested traffic 为 `16,777,216 x (4 + 4 + 4) = 201,326,592` bytes；
- requested-byte arithmetic intensity 为 `16,777,216 / 201,326,592 = 1/12`，约 `0.083333` operations/byte。

这是 **algorithmic requested-byte model**，不是 DRAM sectors、L2 traffic、L1/TEX traffic、cache hits、write allocation、compression、ECC effects 或其他 profiler-attributed physical traffic 的测量值。三个 allocations 的总字节数恰好等于 source-level read/read/write requests 的总字节数，只是本工作负载的算术巧合，不证明 allocation bytes 等于 transferred bytes。Profiler-owned replay storage 也不属于 canonical application 的 201,326,592-byte allocation；若工具暴露该值，必须另行记录。

## Profiling 前先通过 correctness

解释任何性能之前，下列条件必须全部通过：

1. 三次 `cudaMalloc` 与两次 H2D copy 全部通过。
2. Launch boundary 与 `cudaGetLastError` 通过。
3. Canonical path 中显式的 `cudaDeviceSynchronize` 通过，并在后续 host work 前建立 completion boundary。
4. D2H copy 与三次 `cudaFree` 全部通过。
5. Independent CPU reference 检查全部 16,777,216 个 outputs。只有 absolute difference `<= 1e-5` 或 relative difference `<= 1e-5 * max(abs(expected), abs(actual))` 时才接受该元素。
6. Process status 为零，且 retained logs 与 criterion record 一致。

任何 failure 都会阻断所有 duration、traffic、Gop/s、intensity、ceiling、roof、occupancy、stall、throughput、bottleneck 或 speedup interpretation。只看到一行 `PASS` 不足以替代 boundary records 与 independent comparison contract。

## 独立记录两个 ceilings

记录一个 compute ceiling 和一个具有精确名称的 memory path 的 bandwidth ceiling。每个 ceiling 只能独立采用以下一种 provenance class：

1. **Calibrated measured ceiling：** 一项另行通过 correctness 的 benchmark，具有公开或已保留的 source identity、source commit、binary hash、精确 method/commands、workload、repetitions、acquisition order、全部 raw samples、statistic、匹配的 device/environment 与 operation/byte convention。
2. **Modeled、theoretical 或 tool-reported ceiling：** 明确标记为非 measured value，并具有精确 NVIDIA owner-document coordinate 或 exact report field、report hash、definition、precision、path、unit 与 scope。

不得静默把 theoretical 或 tool-reported value 称为 measured。不得把 provenance class、precision convention、memory path、decimal/binary units、device scope 或 operating conditions 不同的 ceilings 合成同一个 ridge 或 roof。如果两个分别有效的记录无法对齐，就保留二者，但不计算 hybrid roofline。Tool roofline display 可以辅助检查，却不是自证 provenance。

若要合成 chart，compute ceiling 必须采用与 workload 相同的 FP32 operation-count convention。尤其不能把 FMA 计为两次 operation 的 convention 静默混入本实验每元素一次 addition 的计数。Bandwidth ceiling 必须命名与 traffic point 相同的 memory path 与 byte unit。

## 采集恰好十次独立 profiler attempts

在 attempt 01 之前冻结 batch ID、exact command、selected exact `vector_add` kernel filter、一个 queried section **或** minimal queried metrics、replay mode、cache/clock controls、device、environment 与 acquisition order。用 captured help 验证每个 option。Command shape 是：

```sh
batch_id='<填写 unique batch id>'
kernel_filter='vector_add'
collection_args=(<填写 --section NAME 或 --metrics NAME1,NAME2,... 二选一>)

for attempt in 01 02 03 04 05 06 07 08 09 10; do
  attempt_dir="lab09-evidence/batches/${batch_id}/${attempt}"
  mkdir -p "$attempt_dir"
  report_base="${attempt_dir}/vector-add"
  test ! -e "${report_base}.ncu-rep" || exit 1
  ncu --config-file off \
    --devices 0 \
    --kernel-name-base function \
    --kernel-name "$kernel_filter" \
    --launch-count 1 \
    --replay-mode kernel \
    "${collection_args[@]}" \

    ./build/ex02-vector-addition 16777216 \
    >"${attempt_dir}/profile.stdout.log" \
    2>"${attempt_dir}/profile.stderr.log"
  status=$?
  printf '%s\n' "$status" >"${attempt_dir}/profile.status"

```

这只是 command shape，不表示每个 Lane 都必然支持这里的每一种 spelling。如果 captured help 要求 owner-supported equivalent，必须在 attempt 01 前冻结并记录。每个 attempt 都是一次新的 `ncu` invocation 与新的 application process；一份 report 内的 replay passes 不是 independent attempts。

完整 batch 包含按 `01..10` 顺序尝试的恰好十次 invocations。保留所有目录，不得覆盖或删除不方便的 sample。十次 attempt 都必须分别满足 source/binary/environment identity、selected device、恰好一个 intended reported `vector_add`、correctness、zero statuses、report existence、metric availability、scope 与 replay records。任一 attempt 无效，则整个 batch 无效。保留该 batch，另采集一个具有新名称的完整十次 batch；不得替换单行、合并 batches 或缩小分母。

## 保留 report custody 与 replay effects

对每个 `.ncu-rep` 记录 report SHA-256、exact command、process/application status、selected reported kernel name、device/context/stream 与 launch filters、metric names/definitions/units/scopes、pass count、requested/actual replay mode、save/restore、cache control、clock control、serialization 与其他 perturbation。把 query/help logs 与全部 stdout/stderr/status files 保存在 report 旁边。

Nsight Compute 会插入 measurement libraries；由于 counters 不一定能在一个 pass 内同时收集，它还可能 replay selected kernel。Kernel replay 可以保存和恢复 accessible memory，collection choices 会改变 pass count 与 overhead。因此 profiled duration 必须附带 exact report definition 与 perturbation boundary，不能静默等同于 direct unprofiled process。Report 是 primary artifact；CSV exports、screenshots、copied cells 与 GUI views 都是绑定其 hash 的 derivatives。

## 只归约 qualifying batch

对每个 qualifying attempt，从 retained report 与 frozen model 取得以下对齐输入：

| Quantity | 必需 source 与 scope |
| --- | --- |

| Traffic | Declared named memory level/path 上一个 exact queried byte metric，附 definition、aggregation 与 scope |

## 只在 declared roof 内解释

- 如果 intensity 低于 aligned ridge，只能把点描述成**相对于 declared ceiling pair 与 named memory path**位于 bandwidth side。
- 如果 intensity 高于 ridge，只能在同一个 bounded model 中描述成 compute side。点位于 ridge 时，不强行归类某一侧。
- 点低于 roof 仍留下其他解释：latency、insufficient parallelism、launch shape、instruction issue、cache behavior、memory transactions、clock/power/thermal state、concurrent load、replay 或 metric mismatch 都可能存在。Roofline 本身不能从中自动选择原因。
- 点高于 roof 时启动 mismatch audit，而不是庆祝性能突破：重新检查 operation convention、byte level/path、units、ceiling provenance/precision、duration scope、report/filter identity、aggregation、replay 与 transcription。

Occupancy、stall reasons 与 throughput 是三类不同的 evidence。采集其中任何一项，都必须保留 exact metric name、definition、unit、scope、aggregation、filter 与 report hash。Occupancy 在声明的 definition 下描述 resident/active-warp capacity 或 achieved behavior；maximum occupancy 不是自动优化目标。Stall reasons 在精确定义下描述 sampled 或 aggregated scheduler states；较大 share 不会自动诊断 bottleneck。Throughput 把 achieved activity 与特定 denominator/scope 对比；percentage 不会自动指出 root cause。三者不得互换，也不能在没有独立 controlled test 时变成 bottleneck verdict。

LAB09 不进行 baseline/candidate comparison，也不报告 speedup。后续优化若要测试，必须另建 correctness-qualified contract，不能从本 chart 推导。
