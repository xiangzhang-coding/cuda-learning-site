## 实验合同

分析已安装的原始 [EX22](/examples/adjacent-energy/) wheel，在学习者副本中实现 P11 有边界的候选，不削弱语义地比较两者。预计 120 分钟，另加准备时间。网站不运行 CUDA。完成运行活动需要两个 wheel 的检查、轨迹、测量和环境清单（Environment Manifest）；仅 CPU 门禁是部分进展。当前状态为**待硬件验证（Pending Hardware Verification）**。

## 前置知识与源码

精确前置条件为 `[P11]`：[P11](/frameworks/profile-led-optimization/) 提供假设和需保留的合同。EX22 仍是规范项目；[LAB13](/labs/build-custom-operator/) 提供已说明的环境/构建/导入步骤。下面单独调用的派发扩展还要求 [P12](/frameworks/sdpa-dispatch-verification/)，它不是 LAB14 算子活动的隐藏前置条件。

使用包含 `scripts/framework-verification/check.py` 的学习站（Learning Site）干净检出。为工具和原始源码记录 `git rev-parse HEAD`；EX22 发布页保留不可变规范归档。学习者修改与 wheel 产物分别保存。不能用未跟踪工作树，却把干净提交作为完整源码标识报告。

## 准备与预测

按 LAB13 准备哈希锁环境、构建两条原生路径并验证隔离已安装导入。清除 LD_PRELOAD 和旧 PYTORCH_CUDA_ALLOC_CONF，使用已检查的加载器环境与 `PYTORCH_ALLOC_CONF=backend:native`。通过 CUDA_VISIBLE_DEVICES 选择一块 GPU。在外部保存精确命令/退出码和编译器输出。从仓库根目录把 shell 变量设置为实际干净源码标识：

```sh
SOURCE_COMMIT=$(git rev-parse HEAD)
```

运行前预测 n=258 有 257 个输出、两个 256 线程块。说明各尺寸预计由启动开销还是设备工作主导，以及什么观察能推翻预测。这些是假设，不是观察输出。

## 采集原始基线

在原始 wheel 的虚拟环境中，从仓库根目录运行：

```sh
PYTORCH_ALLOC_CONF=backend:native python -I scripts/framework-verification/check.py --mode operator --device cuda --source-commit "$SOURCE_COMMIT" --output baseline-round-1
```

输出目录必须不存在。工具调用 EX22 规范验证器，再把 float32/float64 的 n=258,1003,1000000 全部前向输出与即时表达式比较。即时组合和已安装算子读取相同、预分配的有限二进制分数输入。梯度/fake/meta/编译/流覆盖来自计时前的规范验证器，不来自前向基准。

每项操作预热 20 次。七组无分析器样本各在当前流 CUDA 事件（CUDA Event）之间执行 100 次；结束事件完成后读取时间。输入创建、验证、传输排除，输出分配包含。独立 CPU+CUDA 分析记录形状，以 wait=1、warmup=1、active=2、repeat=1 执行四次 `prof.step()`，每个诊断边界同步。分析器开销不进入无分析器中位数。

## 构建并验证候选

在新的学习者副本中，只应用 P11 从 256 到 128 的启动修改。为规范验证器的数值与梯度边界集合增加 n=128,129,130。提交学习者差异以获取不同源码标识，并在外部保留该差异。使用 LAB13 的 wheel 脚本，在独立干净匹配虚拟环境中构建/安装；重跑隔离 CPU/CUDA 检查，以及第二虚拟环境的正向/负向导入。保留两个 wheel 哈希和实际加载扩展哈希。本页不把任何修改内核发布为已测胜者。

从候选检出使用其真实 SOURCE_COMMIT 和新的 `candidate-round-1` 输出目录执行同一命令。用旧已安装 wheel 重跑原命令，不是在测试候选。EX22 的合法 dtype、CPU 路径、自动微分（Autograd）注册、fake/meta 和打包合同均须保留。

## 比较与决策

至少三轮交替基线/候选进程顺序，每次尝试使用新目录。匹配尺寸、dtype、前向/分配范围、时钟/功耗策略、竞争负载和软件。保留每项七个样本及中位数/离散程度，只对匹配且正确的用例报告比值。比较原始 **operator** 行与候选 **operator** 行；eager 行用于解释组合开销，不是原始原生基线。

在本地检查完整轨迹：连接框架区间与原始/候选内核启动，观察间隙，区分请求字节与已测内存流量。本活动不采集 DRAM 计数器。若收益淹没在波动中、小尺寸回退超出预先策略，或任一正确性检查失败，保留原始实现。候选正确但没有加速，是有效实验结论。

## 单独设门槛的 P12 派发扩展

完成 P12 后，在同一精确应用环境中启动独立进程：

```sh
PYTORCH_ALLOC_CONF=backend:native python -I scripts/framework-verification/check.py --mode sdpa --device cuda --source-commit "$SOURCE_COMMIT" --output dispatch-round-1
```

它不需要修改 EX22。对 P12 无掩码/dropout/GQA 前向夹具，使用由已舍入输入构造的 CPU float64 参考，在 AUTO 与四个强制策略间验证。FP16/BF16/FP32/FP64 使用 P12 固定容差；原生 BF16 和融合谓词为试验设门槛。不满足条件的行保留，执行/数值失败使尝试失败。要求后端事件识别与设备内核，并随后在本地检查关联。报告分别记录请求策略和观察事件，绝不只从开关推断 AUTO。不声明注意力反向结果。

若仅做无 GPU 的工具/参考检查，在所选 Linux 环境使用 `--mode sdpa --device cpu` 和新输出目录。它检查 MATH float32/float64，不产生 CUDA 计时或 GPU 清单。它不完成本实验，也不验证 CUDA 派发。
