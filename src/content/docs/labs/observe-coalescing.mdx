## 冻结测量计划

在第一次 profiler 采集前写死以下合同：

1. 固定 source commit、binary SHA-256、Lane、device、scenario order、logical work、build flags、launch geometry、`ncu` options 与 metric list。三种访问只保留 canonical `offset`/`stride` 差异。
2. 再直接运行完整 binary 一次作为 process-level warm-up；检查正确性，但把该次运行明确排除在全部统计之外。它不能消除新 profiler process 的全部启动或 replay 影响，因此不得被描述为 steady-state event warm-up。
3. 对同一未改动 binary 恰好执行 10 次独立、完整的 measured profiler invocation；按 acquisition order 保留每次尝试，不删除“看起来异常”的样本。
4. 预先声明每个 scenario/metric 的汇总为该固定 10-attempt batch 的 median 与 min/max spread，并且只有 10 次尝试全部合格时才计算。只有 nonzero tool/application status、正确性失败、缺少目标 kernel 或缺少 metric value 才可标记 invalid，并必须保留该记录和原因；数值很大或不利于结论不构成 invalid。任一次 invalid 时不发布 summary，而是记录 batch blocker；修复原因后必须在新 batch directory 中重做全部 10 次，禁止选择性补样本或覆盖旧记录。

这套冻结规则要求 equal work/build/launch；若中途改变任何固定项，废弃整个 batch 后重新开始，不能拼接前后样本。

## 解读记录

CUDA event timing 与 profiler measurement 不是同一种记录。Timing-enabled events 通过 `cudaEventRecord` 在 device timeline 上标记区间，完成后由 `cudaEventElapsedTime` 给出该区间的 elapsed time；canonical EX05 没有 event instrumentation。`ncu` 会插入 measurement library，并可能序列化、replay kernel、控制 cache/clock 或执行多 pass；它报告的是所选指标在该 collection contract 下的值，不是可互换的 event sample。

因此 LAB04 不新增 event-instrumented binary，也不把 profiler duration、host wall-clock 与 event time 合并。若另开 event 实验，必须重新声明 source/build、warm-up、完成边界与统计合同，不能冒用本 Lab 的 frozen binary 记录。

对每个 metric 只陈述其 owner 定义允许的范围。只有 10 次尝试在相同 metric、unit、collection options 与 device 下全部合格时，才报告 median、min/max spread 与每次尝试的路径；否则只报告 blocker，不给 summary。本 Lab 不预言 contiguous、misaligned、strided 的 metric ordering、latency、bandwidth、throughput 或 speedup。若结果相同、波动或与静态模型不一致，保留事实并调查，不改写预期。

## 预期观察，不是记录结果

- Contiguous、misaligned 与 strided **应当**先各自通过 256 个 output 的 CPU reference exact comparison。
- 通过版本、metric-query 与权限门槛后，每个 scenario **应当**能与自己的 raw profiler record 和退出状态关联；这不承诺指标方向或差值。
- Warm-up **应当**被排除，固定 10 次尝试都**应当**保留；只有整批合格时才报告预先声明的 median 与 min/max spread。

这些都是预期观察，不是记录结果。本页没有预填任何 GPU 数值结果、运行输出或 profiler 结果；`recordedObservations` 仍为空。

## 分开维护证据轴

| 轴 | 当前状态 | 边界 |
