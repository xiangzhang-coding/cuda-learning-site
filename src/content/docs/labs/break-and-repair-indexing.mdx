LAB03 是一个实验（Lab）：你在网站之外用四个独立进程运行 EX04，先定位 immediate launch、deferred execution 与 host verification 三种边界，再让确定性的错误 stride 被独立 host 比较（independent host comparison）拒绝，并验收修复路径。网站不执行 CUDA，也没有预先填入任何实际输出、错误码或退出码。

## 先预测

EX04 把错误与修复 kernel 放在同一个 canonical range 中：

<CanonicalCode exampleId="EX04" range="indexing-kernels" />

运行前完成一张四行预测表：

1. `launch-config`：launch expression 返回后，`cudaPeekAtLastError` 应在哪个 stage 观察状态；为什么 peek 不清除状态、后续 `cudaGetLastError` 才读取并清除；清除后才进入显式 synchronization。
2. `deferred-access`：合法 launch configuration 为什么应让 immediate check 保持 clear；故意的 invalid device access 为什么只应在 `cudaDeviceSynchronize` 建立 completion boundary 时暴露。该进程在预期 deferred failure 后不做 cleanup 或 recovery call。
3. `indexing-defect`：对 `7 x 5` 写出 row-major `y * width + x` 与 defective column-major permutation `x * height + y`，总元素数 35、allocation 140 bytes，并预测最早发生 host mismatch 的线性位置。两种映射都保持在 allocation 内，不能把逻辑 defect 预测成 illegal access。
4. `repaired-indexing`：写出与独立 host reference 相同的 row-major 映射，并预测 35 个元素都被精确接受。

四项都只是执行前标准。不要把预期 stage、status class 或 mismatch 写成已观察输出，也不要预填具体 CUDA error name 或数值错误码。

## 验证正确性与边界

独立参考、逐元素比较和 host-visible verdict 来自第二个 canonical range：

本 Lab 只有在下列条件全部成立时完成：

1. 四个 scenario 都使用同一 commit、Lane、C++17 binary 与单一 GPU，并且每个 scenario 在独立进程中运行。两个 indexing scenario 使用源码固定的 `7 x 5` extent。

7. 不从这些 correctness/error-boundary run 声明 latency、bandwidth、throughput、speedup、occupancy、coalescing 或 profiler 结论。[F08：Launch geometry 是先于速度的正确性与资源决策](/foundations/launch-geometry/)可以继续讨论 geometry 约束，但本 Lab 不测量性能。

## 预期观察，不是记录结果

- `launch-config` **应当**在 immediate-after-submission check 暴露 launch-configuration defect；`cudaPeekAtLastError` 观察但不清除，`cudaGetLastError` 读取并清除同一 launch state，随后才显式 synchronization。
- `deferred-access` 的 immediate check **应当**没有 launch error，故意 invalid device access **应当**只在 `cudaDeviceSynchronize` 建立 completion boundary 时暴露。
- `indexing-defect` **应当**不触发 illegal memory access，而在 host verification 中因 allocation 内的 column-major permutation 与 row-major reference 不一致而得到 deterministic mismatch；程序正确识别该预期 mismatch 时，scenario 本身被接受。
- `repaired-indexing` **应当**完成显式 synchronization，并与经过 overflow check 的 row-major host reference 精确匹配。

这些是运行前的预期观察（expected observations）。本站没有看到你的 GPU、日志或退出状态，frontmatter 的记录观察（recorded observations）仍为空。实际环境若偏离预期，保留偏离和 blocker，不要修改预期来迎合结果，也不要从源代码推演伪造运行记录。
