LAB11 是一个在网站之外、仅在原生 Linux（Native Linux）上完成的实验（Lab）。它通过 reviewed single-candidate runner 比较 [EX11 custom multi-stage reduction](/examples/multi-stage-reduction/) 与 [EX17 CUB Device Reduction and Scan](/examples/cub-device-reduction-scan/) 的 `DeviceReduce` path，但不预设 library 或 custom kernel 胜出。本页只发布 expected-only measurement contract：compilation evidence 为空，runtime 为待硬件验证（Pending Hardware Verification），`recordedObservations` 为空，没有实际 output bits、error、temporary-storage size、kernel mapping、metric、traffic、timing、speedup、maintenance score 或 winner。

## 实验合同

`maximumProblemMemoryBytes: 8000000000` 是基础 GPU 能力层级（Baseline GPU Capability Tier）的硬上限，不是预填的实际 allocation。因为一个 process 只执行一个 candidate，custom process 持有 16,396 input bytes 与两个 36-byte partial buffers，共 16,468 bytes；CUB process 持有相同 16,396 input bytes、一个 4-byte output 与 queried `T`，共 `16,400 + T` bytes。因此 actual preflight 是 `max(16,468, 16,400 + T) <= 8,000,000,000`；`T` 必须来自当前 device、当前 component profile、相同 API/template arguments 与 4,099-item shape。两侧 workspace 不会同时存在。Context、module、allocator、profiler replay 与工具自身所需空间另行记录，不能混入 problem-memory claim。

## 冻结 4,099-float correctness contract

两个 candidates 必须使用同一份已经生成并复制到 device 的 input bytes。对 `i = 0..4098`：

```text
centered = int((i * 37 + 11) % 101) - 50
coarse   = float(centered) * 0.125F
fine     = float((i * 13 + 3) % 17) * 0.001F
input[i] = coarse + fine
```

Oracle 按 index order 把每个 binary32 input 精确转换成 `double` 后执行 serial left fold。每个 candidate 返回一个 `float`，并独立应用：

```text
absolute_error = abs(double(candidate_result) - cpu_reference)
allowed_error  = 1.0e-4 + 2.0e-5 * abs(cpu_reference)
pass           = finite(cpu_reference) && finite(candidate_result)
                 && absolute_error <= allowed_error
```

每次 correctness、warm-up、unprofiled timing 与 profiled process 都要检查 allocation/API/launch status、checked completion、完整 4-byte result copy、finite result 与 comparator。按 candidate **分别**保留 `result_float_bits_hex`、`absolute_error`、`allowed_error` 和 `pass`；再单列 `cross_candidate_bits_equal`。Tolerance pass 不等于 CPU bitwise equality；两侧 bit pattern 相等也不能代替 double oracle；bits 不同也不自动表示失败。

## 分开 setup-inclusive 与 steady-state timing

每个 candidate process 通过同一 runner code 生成 common input、分配一个 host input 和一个 device input，并在 candidate-specific timer 之前完成一次 checked H2D copy。Pair records 要求 input bytes 与 hashes 相同；process-local addresses 与 stream handles 分别记录，不声称相等。每个 process 恰好创建一个 explicit `cudaStreamNonBlocking` stream，并传给唯一 selected candidate 的全部操作。每个 timed process 先以 `timing none` 在同一 input 和 stream 上执行一次同-candidate warm-up、完成 result copy 与 oracle check、释放该次 workspace，再执行 measured call；warm-up failure 会在读取 timer 前终止。`timing none` 本身只执行一次，所以 profiler mapping 不含额外 call。两种 timing family 都使用 `std::chrono::steady_clock`、device 0、相同 workload/compiler/binary/profile contract，并在 end clock read 紧前执行 checked `cudaStreamSynchronize(stream)`。Profiler elapsed 永远不进入这两张 timing ledger。

| Timing family | Start | Included | End | Excluded |
| --- | --- | --- | --- | --- |
| `steady-state-invocation` | process-local warm-up 已完成并通过；candidate-specific measured-call allocations 已存在且 clock 紧邻 API/launch 前 | EX11 complete `4099 -> 9 -> 1` invocation 或一个 logical EX17 `DeviceReduce` execution call，加相同 checked completion | completion 返回后立即读取 clock | process-local warm-up、storage query、allocation/free、input setup、result D2H、oracle/comparator、profiler |
| `setup-inclusive` | process-local warm-up 已完成并通过；candidate-specific measured setup 的第一条 host operation 前 | Custom partial-capacity calculation 与两个 9-float partial allocations，或 CUB 4-byte output allocation、zeroed byte count、null-storage query 与 `T`-byte temporary allocation；随后执行 selected invocation 与 checked completion | completion 返回后立即读取 clock | process-local warm-up、common input setup、result D2H、oracle/comparator、teardown；teardown status仍单独记录 |

EX17 steady-state 只能复用 measured call 在同一 current device、同一 component profile、相同 API/template arguments、4,099-item shape 与同一 explicit stream handle 查询并成功分配的 storage。Process-local warm-up 的 workspace 在 measured setup 前释放；它不与 measured workspace 共存，也不进入任何 timer。Measured query 与 allocation 永远在 steady-state timer 外；setup-inclusive timer 则明确包含它们。EX11 与 EX17 各有自己的 candidate-specific workspace，不能用 CUB temporary bytes 给 custom path收费，也不能删除 custom partial setup。

记录 clock source/resolution、timer read overhead policy、start/end source coordinates、每次 raw elapsed value 与 unit。不要预先选择更快者，不要只发布 best run，不要从 profile duration推导 unprofiled elapsed。

## 分开 logical/static traffic 与 profiler-observed traffic

EX11 source 可以给出一份静态 global-memory ledger：

| EX11 stage | Logical input reads | Logical partial writes |
| --- | ---: | ---: |
| `4099 -> 9` | 4,099 floats | 9 floats |
| `9 -> 1` | 9 floats | 1 float |
| Total | 4,108 floats = 16,432 bytes | 10 floats = 40 bytes |

因此 **16,472 bytes** 是 EX11 reduction kernels 的 source-derived logical global traffic。它不包含 input H2D、result D2H、allocation、instruction fetch、cache-line/sector overfetch、writeback policy、profiler save/restore 或任何 CUB operation。十个 launched blocks 还静态表达 2,560 次 initial shared-value writes 与 2,550 个 tree additions，但 compiler/register/shared instruction behavior 必须由 actual artifact/report决定，不能把 source count叫作 observed transaction。

CUB 的固定 user allocation 是 16,396-byte input、4-byte output 与 queried `T`-byte capacity。**Capacity 不是 bytes read/written**；不得从 `T` 推断 CUB logical traffic、DRAM traffic、cache traffic、kernel count 或 elapsed behavior。CUB traffic 只来自 exact GPU 上、exact profile binary 的 queried owner-defined profiler fields。EX11 也必须把 16,472-byte static ledger与其 observed fields分列。

若一个 logical CUB call 对应多个 reported kernels，先保存每个 launch的原始 field。只有 owner definition 明确该 field 可跨这些 launches相加时才汇总 call-level value；否则 call aggregate 保持 `unfilled/inapplicable`，不能擅自求和。

## 只归约 qualifying full batch并保留 custody

每个 profile、candidate 与 timing family仅从同一 qualifying batch 的十个 raw values计算 `count=10`、median、minimum、maximum。Exact metric若按每个 mapped kernel记录，则先保留所有 kernel rows；只按 owner-defined additive scope生成 call aggregate。数值相同仍是十个合法 samples，不能去重。不得输出 mean、删除 outlier、替换失败值、重排 acquisition order或从 profiler duration补 timing。

Custody chain 至少连接 component acquisition/header hashes、canonical-example 与 comparison-runner sources、build records、binary hashes、input hash、version/help/query/permission logs、warm-up、全部 valid/invalid pairs、correctness ledger、timing ledger、primary reports、imports、mapping ledger、traffic ledger、maintenance packet、summary 与 sanitization mapping。Sanitized derivative必须指回 private original hash，但不得公开 credentials、管理员记录、user/host identity、absolute private paths、GPU UUID/serial或network coordinates。

## 验收条件与 blockers

只有全部条件通过，一个 component profile record才完整：

1. Strict prerequisites、EX11 immutable coordinate、EX17 canonical metadata 与 reviewed-runner 或 conforming learner-alternative provenance 一致；source/build/version/include/binary hashes完整。
2. Exact Toolkit、NVCC、host compiler、Native Linux、one CC 7.5+ GPU、CUB/CCCL macros、component acquisition、Nsight Compute、CUPTI、device与permission gates全部匹配该 profile。
3. Shared 4,099-float generator/input hash、double oracle与abs+rel comparator不漂移；两侧 bits/errors/pass分别保留，全部 CUDA/status/completion/result-copy checks通过。
4. CUB query与execution使用同一 current device、API/template arguments、shape与stream；`T`、allocation/free statuses与dynamic memory preflight完整，但没有把 `T`解释成traffic。
5. Steady-state与setup-inclusive timing边界分开；每个 timed process 的同-candidate local warm-up 已检查并排除，且使用同一 clock/device/stream/workload/completion/order；profiled duration被排除。
6. 一次 profile-level excluded warm-up pair后，唯一 batch按预声明alternating order保留完整十组 pairs；任何失败触发whole-batch invalidation且没有sample deletion。
7. Exact-GPU queried profiler fields、actual EX11/EX17 call-to-kernel mappings、replay/perturbation、primary report/import/hash custody完整；CUB kernel count不是假设。
8. Statistics只使用对应同一 full batch的十个 values，报告count=10、median、minimum、maximum；static EX11 ledger、observed traffic与temporary capacity分开。
9. Maintenance五项均有owner、scope、evidence与revisit trigger；任何decision不超过correctness、measurement和compatibility evidence。
10. 完整Environment Manifest、command/log/report/result custody、blocker records与sanitization mapping通过review。

Blockers 包括：strict prerequisite未完成；EX11/EX17 commit、range、source或hash mismatch；unknown/dirty source；unsupported profile；selected/bundled headers混用；CUB/CCCL macro、include trace、package/tag/commit或binary mismatch；非Native Linux、GPU count不等于1或CC小于7.5；driver/Toolkit/compiler/NCU/CUPTI mismatch；permission denial；`sudo`或policy bypass；insufficient queried memory；query/execution device、template、shape或stream drift；allocation/API/launch/completion/copy/free failure；input/generator/oracle/tolerance drift；nonfinite result或correctness failure；missing bits/error；timing clock/boundary/order drift；missing、failed、timed、unrecorded 或 hidden warm-up；missing/reordered/deleted pair；mixed/shortened batch；concurrent-load/clock/power/thermal record缺失；unknown metric semantics、unavailable/`n/a` value或wrong unit/scope；filter/mapping ambiguity；假设CUB只有一个kernel；report/replay/import/hash failure；把static bytes或`T`当成observed traffic；non-additive field被擅自求和；incomplete maintenance/custody；或超出证据的winner/speedup claim。

处理方式只有：立即停止受影响 profile，保留完整 blocker 与 partial/invalid batch，修复允许修复的环境或方法问题，分配新 ID，并从该 profile 的 warm-up 与全部十组pairs重新执行。不得写零、猜值、删除sample、沿用其他profile、拼接batch、提升权限或弱化criteria。
