LAB01 是一项实验（Lab）。你要在网站之外采集一份环境清单（Environment Manifest），构建并运行可运行示例（Runnable Example）EX01，再把采集事实解释为基准环境候选配置（Reference Environment candidate）。本站不会执行这些命令，也没有观察到你的机器。**目前没有声明任何基准环境（Reference Environment）。**

## 实验合同

| 坐标 | 要求 |
| --- | --- |
| 预计时间 | 60 分钟 |
| 难度 | 入门（introductory） |
| 直接先修 | 完成 O03 与 O08；O08 本身已经把 O03 列为直接先修 |
| 受支持环境（Supported Environment） | 仅原生 Linux；其他平台不能形成本站的 Reference Environment 候选配置 |
| 硬件门槛 | 要形成候选配置，需要选择 1 块 compute capability 7.5 或更新的 CUDA-capable NVIDIA GPU；准备与构建可以在没有 GPU 时完成 |
| 工具包通道（Toolkit Lane） | 选择 `cuda-11.8`、`cuda-12.9` 或 `cuda-13.3`；记录实际 Toolkit、组件和 host compiler，不借用其他 Lane 的证据 |
| 问题数据 | EX01 不分配问题数据，`maximumProblemMemoryBytes` 为 `0`；Runtime 或 driver 的内部初始化不属于问题数据 |
| 权限 | 读取 OS 与 NVIDIA driver metadata；执行 shell tool、`nvidia-smi`、NVCC、host compiler、`make` 和 EX01；创建与删除本地记录；不要求 performance counter |
| 编译证据 | 空；本地成功构建和 host-only test 不会自动成为编译已检查（Compile-Checked） |
| 运行证据 | 待硬件验证（Pending Hardware Verification）；本页没有运行记录 |
| 最终判断 | 只能写 `candidate-ready`、`candidate-incomplete` 或 `candidate-rejected` |

构建、硬件资格、compatibility、expected observation、recorded observation 和证据状态（Evidence Status）是六个独立判断。任意一项成功都不能替另一项作证，也不能声明 Reference Environment。

## 先修检查

1. 完成 [O03：读懂环境清单](/start/environment-manifest/)，能把 GPU、compute capability、driver、Toolkit、组件、compiler、OS、命令和日期放进不同字段。
2. 完成 [O08：准备基准环境候选配置](/start/reference-environment-candidate/)，能区分 tier、compatibility、维护者控制和 baseline declaration gate。

4. 选择一条 Toolkit Lane 和一个专用记录目录。目录必须位于 EX01 `build/` 之外，并以默认不公开的权限创建。

## 准备项目并冻结记录

[查看固定 source commit 中的完整 EX01 项目](https://github.com/xiangzhang-coding/cuda-learning-site/tree/23382602978cf99da8e9cbfff275f5f8fb8e0f47/examples/ex01-environment-report)，或[下载同一 commit 的源码归档](https://github.com/xiangzhang-coding/cuda-learning-site/archive/23382602978cf99da8e9cbfff275f5f8fb8e0f47.zip)。这组不可变 acquisition coordinate 把页面显示 range 和 build input 绑定到同一 source tree。进入项目目录前，先记录完整 commit SHA：

```sh
git clone \

cd cuda-learning-site
git rev-parse HEAD
cd examples/ex01-environment-report
```

先创建只包含字段名、所有 observed-value cell 为空的 `manifest.md`。至少预留 source commit、Toolkit Lane、CUDART linkage、OS source path 与字段、`uname` 字段、loaded KMD、driver-supported CUDA API、Toolkit 与组件、NVCC、host compiler、build stages、visibility controls、NVIDIA-SMI inventory、EX01 inventory、identity reconciliation、tier、compatibility、candidate decision、UTC date、raw log path 和 hash 字段。这里的“空”表示 schema 已冻结，不能预填预期值。

另建 `criteria.md`，在执行前写明：

1. 每条必需命令都保存 literal argv、独立 stdout/stderr、exit status 与 UTC start/finish；非零状态或缺失字段保留为 blocker。
2. OS 记录遵守 `/etc/os-release` precedence；不合并两个 `os-release` 文件。
3. EX01 build 与 host-only test 都必须完成预先指定的 target 并零退出，才能继续运行，但这仍不授予 Compile-Checked。
4. Hardware step 必须让 EX01 看见恰好 1 个已选择设备，所有必需 CUDA query 都成功，并保留 visibility 与 MIG boundary。
5. CUDA-visible identity 必须通过 UUID 或 PCI identity 与同次 NVIDIA-SMI capture 对应；不能只按 ordinal 或 product name 猜测。
6. Tier 与 compatibility 按各自规则判断，最后只使用三种 candidate decision。

```sh
umask 077
```

## 采集 host 与软件坐标

systemd `os-release` 合同规定 `/etc/os-release` 优先。只有它不存在时才使用 `/usr/lib/os-release`，两者不能合并。把选择逻辑保存在 literal script 中，通过 capture stage 执行，并保存被选 path、resolved path、原始文件 bytes 与 exit status。至少记录 `ID`、`ID_LIKE`、`VERSION_ID`、`VARIANT_ID` 和 `PRETTY_NAME` 的实际存在状态；optional field 缺失必须保持缺失。

接着分别采集，不用某一项替代另一项：

```sh
uname -s -r -m
cat /proc/driver/nvidia/version
query_fields="name,uuid,pci.bus_id,driver_version"
query_fields+=",memory.total,memory.free,compute_cap,mig.mode.current"
nvidia-smi \
  --query-gpu="$query_fields" \
  --format=csv,noheader,nounits
nvidia-smi --version
nvcc --version
c++ --version
make --version
cuobjdump --version
```

`uname` 的 kernel name、release 与 machine 是独立字段，不替代 distribution record。`/proc/driver/nvidia/version` 和 selective NVIDIA-SMI query 用来记录 loaded driver，而 package name 只记录安装状态。若某个 selective field 不受当前 driver 支持，保留原命令、stderr 与 nonzero 或 unavailable result，再按预先声明规则标为缺口，不静默删字段。

同时保存 active `nvcc` 的 resolved path、所选 `HOST_CXX` 的精确 path，以及与本次判断相关的 Toolkit package/component record。NVIDIA-SMI 的 CUDA UMD 或旧 `CUDA Version` banner 表示 driver 支持的 API level，不能填写 installed Toolkit 字段。EX01 会另行查询 driver-supported API 与 CUDA Runtime version；仍要保留 NVCC、Runtime、library 和 tool 的 component-specific version，不能压成一个“CUDA version”。

本节只采集 host 与 software metadata。它不证明 build 成功，不证明 GPU 对 CUDA 可见，也不作 compatibility 或 Evidence Status 判断。

## 构建 EX01 并运行 host-only test

在选定 Lane 的 C++17 环境中，预先选择并记录 CUDART linkage。下面使用 canonical shared linkage，把两个 target 作为独立 capture stage 执行：

```sh
make build DIALECT=c++17 CUDART=shared BUILD_DIR=build
make host-test DIALECT=c++17 BUILD_DIR=build
```

保存每个 target 的 working directory、literal argv、UTC start/finish、stdout、stderr、exit status，以及生成 artifact 的 SHA-256。Preparation 和这两个 target 都不需要 GPU。`host-test` 只检查 EX01 的 observation model 与 formatting/invariant；它不能提供 CUDA-visible inventory。

任一 target 失败时，保存 blocker 并停止 GPU run。即使两者都成功，本页和 EX01 的 compilation Evidence Status 仍为空，因为目前没有经过审查、绑定 exact source、Lane、dialect、target、command 和 build environment 的 compile evidence record。成功 build 也不证明 hardware、compatibility 或 runtime。

EX01 不启动 workload kernel，也不分配 problem data，所以本 Lab 的 `maximumProblemMemoryBytes` 是 `0`。CUDA 初始化可能使用内部资源，这不改变 problem-memory contract。不要从执行时间、free-memory 变化或 command duration 推导性能结论。

## 核对 CUDA 与 NVIDIA-SMI 身份

把 EX01 run 与时间相邻的 selective query 放在同一 record 中，再逐项核对：

1. CUDA Runtime ordinal 受 `CUDA_VISIBLE_DEVICES` 过滤与重排，不能直接等同于 NVIDIA-SMI index。
2. 首选 UUID。EX01 把 16 个 raw bytes 编码为 lowercase hexadecimal、每 byte 两个字符且无 separator；先按这条 declared encoding 把 NVIDIA-SMI UUID 规范化，再比较 bytes。若两侧都提供 PCI bus ID，则在统一 domain、bus、device、function 格式后作第二条 identity check。
3. 当 MIG 未启用时，UUID 与 PCI identity 应指向同一 physical function。只按 name 匹配不够。
4. 当 MIG 启用时，另外保存 `nvidia-smi -L` 与必要的 MIG inventory。MIG instance UUID 用来识别 selected compute instance；多个 instance 可以共享 parent GPU 的 PCI bus ID，所以 PCI 只能核对 parent relationship，不能区分 sibling instance。
5. Container/device-node filtering、permission boundary 或 visibility setting 可能让 EX01 看见的集合小于 NVIDIA-SMI 的集合。记录这条 boundary，而不是补造缺失设备。

若 UUID/PCI normalization 后仍无法唯一对应，或 capture 之间配置已变化，把 reconciliation 标为 unresolved，并选择 `candidate-incomplete`。不要根据 product name、memory size 或 ordinal 强行匹配。Reconciliation 成功只建立 identity，不证明 tier、compatibility 或正确性 baseline。

## 分配 GPU Capability Tier

只使用 direct compute-capability query、selected visible device 的 memory、GPU count、required feature 和 permission。记录满足完整合同的最高 tier：

- **基础 GPU 能力层级（Baseline GPU Capability Tier）：** compute capability 7.5 或更新，恰好选择 1 块可用 GPU，并且稳定课程（Stable Curriculum）基础 workload 能满足低于 8 GB 的问题规模合同。EX01 的 problem-data requirement 为 0 bytes，但这只说明 EX01 自身能放下。
- **现代单 GPU 能力层级（Modern Single-GPU Capability Tier）：** compute capability 8.0 或更新，selected CUDA-visible device 至少有 8 GB total memory，并满足 single-GPU route 所需 feature 与 permission。若选择 MIG instance，按 instance 可见资源判断，不能借用 parent GPU 总内存。
- **No tier：** compute capability 低于 7.5，required fact 缺失，selected count 不是 1，或 feature/permission gate 未满足。缺失值不能按 product name 推断。

满足 Modern 时注明它也满足 Baseline 的 capability floor，但最终字段只写最高适用 tier。Tier 是课程路线资格，不是 runtime observation，也不授予 Evidence Status。

## 单独解释 compatibility

打开 [O08 Compatibility Explorer](/start/reference-environment-candidate/#解释-toolkit-与-driver-compatibility)，在 EX01 之外单独输入 loaded KMD、driver-supported CUDA API、selected Toolkit Lane、installed Toolkit/component facts、target/PTX dependency，以及 forward-package eligibility 与 installation facts。保存输入、source access date 和 explorer outcome，但不要把它合并进 EX01 stdout。

Explorer 的 `documented-path` 只表示 owner documentation 描述了一条仍带限制的路径；`not-documented` 表示当前坐标没有文档路径；`indeterminate` 表示关键输入缺失。三种结果都没有执行 workload，也不证明 build、hardware inventory、runtime correctness 或 Evidence Status。

不要复制 NVIDIA compatibility matrix，也不要把 driver floor 当作 paired driver 或 guaranteed runtime。回到当前 NVIDIA owner page 定位适用规则，记录链接、日期和限制。若配置变更，重新采集受影响字段、hash 与 explorer result，不能沿用旧结论。

| `candidate-ready` | 原生 Linux、完整 manifest、成功 build/host-test、1 个通过 hardware gate 的 selected device、成功 EX01 capture、唯一 identity reconciliation、适用 tier 和 `documented-path` 全部成立 | 把 packet 交给独立的 maintainer-control 与 baseline 流程；仍不声明 Reference Environment |

`candidate-ready` 只是通过 LAB01 capture contract，不是 Reference Environment declaration，也不是 Evidence Status。**目前没有声明任何 Reference Environment。** 声明还要求维护者控制该配置，并另外指定一项与 EX01 environment report 分开的 baseline。在 baseline 执行前必须写好 source revision、命令、输入、required API checks、correctness method 和明确 pass/fail criteria；只有完整保存的 successful baseline run 才能进入后续 declaration review。

## 分开维护观察与 Evidence Status

### 预期观察（Expected observations）

- 一份成功的 EX01 report 应在同一个 JSON document 中包含 UTC、build、environment-variable、version、count 和每个 visible device 的 observation。
- 考虑 visibility control 与任何 MIG boundary 后，所选的唯一 CUDA-visible device 应能通过 UUID 或 PCI identity 与 NVIDIA-SMI 对应。

这两条是执行前写好的 structural expectation，没有给出任何设备值或 sample output。它们不能按实际结果改写。

### 记录观察（Recorded observations）

本页的 recorded observations 为空。把自己的 raw command、stdout、stderr、exit status、UTC date、manifest、reconciliation 与 decision 存入外部 record，不要把 expected text 复制成 observed result。即使你完成 Lab，public page metadata 仍不会因此自动获得 observation。

### 证据状态（Evidence Status）

| 轴 | 当前本站状态 | 不能推出什么 |
| --- | --- | --- |
| Compilation | 空；没有 Compile-Checked | 本地 build 或 host-test 成功不能升级本站 compilation status |
| Runtime | Pending Hardware Verification | EX01 expected structure、compatibility outcome 或 candidate token 都不是 Runtime-Verified |
| Recorded observations | 空 | 没有 reviewed raw record 时不能声称 Community-Observed 或 Runtime-Verified |

一份完整 learner/community record 可以按 O02 单独接受审查，但不会自动改变本站状态。只有在已声明、maintainer-controlled Reference Environment 中针对明确 subject 满足预先声明标准，才可能评估 Runtime-Verified。LAB01 的环境盘点不能替代 separately designated baseline。

## 清理并保存记录

先清理 build artifact，不要删除位于 `build/` 外的 record：

```sh
make clean BUILD_DIR=build
```

所有 log 关闭后，对固定 allowlist 生成最终 SHA-256。至少包括 `manifest.pre-run.md`、filled `manifest.md`、`criteria.md`、capture script、每个 stage 的 argv/stdout/stderr/exit/timestamp、source commit、reconciliation 和 candidate decision；不要让 `SHA256SUMS` 包含自身。随后用 `sha256sum -c` 验证，并保存该命令的 exit status。

Raw packet 可以包含核对所需的 sensitive device identity，应放在受控位置。若需要发布，复制一份 redacted packet，移除 credential、network identity、real UUID 和不必要的 path，再为 redacted bytes 单独生成 hash。不要覆盖 raw file 后继续引用旧 hash，也不要提交 binary、build directory、完整 environment dump、performance number 或未经审查的大型 artifact。
