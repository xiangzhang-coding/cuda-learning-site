Q12 是一个以正确性和证据边界为先的归约优化案例（reduction optimization case study），不是 benchmark。它从 immutable EX11 开始，把分支发散（divergence）、同步（synchronization）、数值顺序（numerical order）与内存流量（memory traffic）的变化写进 collection 前台账；任何 candidate 都可能被拒绝、保持 unanswered，或回滚。本站没有执行 runner、CUDA 或 profiler。

## 学完本单元，你应该能

- 用 EX11 的独立 CPU reference 与 absolute-plus-relative tolerance 资格化每个 candidate。
- 在测量前写出包含 mechanism、coupling、support、reject、no-answer 与 rollback 的 hypothesis ledger。
- 分开控制 warp-tail、operation tree 与 partial-staging changes，并披露不能隔离的连带变化。
- 为每个 measured stage 声明 workload、warm-up、completion、statistics、profiler、permission、环境清单（Environment Manifest）、correctness result 与 bounded interpretation。
- 在缺少 qualifying hardware evidence 时只保留 expected observation，不命名 winner。

## 先冻结 EX11 correctness baseline

Canonical workload 是 4,099 个 `float`，block size 为 256，每个 block 最多接收 512 项，stage DAG 是 `4099 -> 9 -> 1`。最后一个 first-stage block 只有三个合法 inputs，其余 lanes 写 identity zero，但所有 threads 仍到达每个 `__syncthreads()`。普通 block barrier 不承担跨 block rendezvous；host 通过 successive kernel launches 建立 stage boundary。

独立 CPU reference 使用 `double` left fold，GPU result 使用 EX11 已发布的 finite comparator：`absolute_error <= 1e-4 + 2e-5 * abs(cpu_reference)`。通过 tolerance 只表示结果满足这项 problem-specific acceptance；它不证明逐 bit 相同、固定 operation order、determinism scope 或 performance。每个小边界 fixture 和声明的 measurement workload 都必须重新通过同一 CPU-reference/tolerance gate。

## 在 collection 前写 hypothesis ledger

每条 edge 单独保存以下字段，不能由后续 stage 追溯补齐：

| field | required declaration |
| --- | --- |
| identity | stage ID、immutable parent、candidate source/binary SHA-256、expanded build command |
| changed variables | primary intervention，以及无法隔离但已披露的 coupled changes |
| mechanism | 对 control flow、barrier/shared access、operation tree 或 partial traffic 的可证伪预测 |
| held constants | input bytes、value type、block size、oracle、tolerance、toolchain、GPU、collection method |
| evidence | correctness packet、raw unprofiled samples、exact query、report、commands、logs 与 hashes |
| decision | support、reject、no answer、rollback 与 next-question rules |
| alternatives | chosen evidence 不能排除的至少两个 competing explanations |

固定 stage IDs 为 `canonical-shared-tree`、`warp-tail-control`、`reassociated-warp-order` 与 `four-load-staging`。这些 labels 只标识 source/method，不携带结果。前一 stage 未通过 correctness 或 comparison coordinate 不匹配时，停止；不能把它静默提升为下一项 baseline。

## 冻结每个 stage 的 measurement contract

所有 stages 使用同一个 declared workload：16,777,219 个 deterministic finite `float`；固定 source parent、device ordinal、block size 256、input bytes、allocation policy 与 CPU oracle。每个 process 先执行三次 excluded warm-up，随后显式 `cudaDeviceSynchronize`，保存十次新的 unprofiled raw attempts，并在查看值前声明 median 与 minimum/maximum；不得删除 sample。Profiler run 是独立 observation，使用同一 workload、correctness cadence 与 stage identity。每项记录都要包含 complete Environment Manifest、permission result、correctness result 和 bounded interpretation。

Canonical/warp-tail/reassociated paths 的 declared stage sizes 是 `16777219 -> 32769 -> 65 -> 1`；four-load path 是 `16777219 -> 16385 -> 17 -> 1`。Input 占 67,108,876 bytes，两个按最大 baseline partial capacity 分配的 buffers 各占 131,076 bytes，conservative device problem bound 是 67,371,028 bytes。这些是 source-derived workload coordinates，不是 measured traffic 或 memory-use observation。

每个 stage 必须逐项声明：workload 是上述 fixed input；warm-up 是三次 excluded direct attempts；synchronization 是每个完整 multi-kernel reduction 后 checked `cudaDeviceSynchronize`；statistics 是十次 retained attempts 的 predeclared median 与 min/max；profiler method 是 exact-GPU query 后的一项最小 section 或 shorter exact metric list；permissions 必须记录且 denied 时停止；Environment Manifest 必须完整；correctness result 在 measurement 前由同一 comparator 得出；bounded interpretation 只能回答该 stage 的 named question。当前这些 result fields 全部是 `expected; unrecorded`。

下载的[原创 expected-only Q12 fixture](/assets/profiler-report-fixtures/q12-nsight-compute.expected.json)把这一 schema 固定为待填写 plan。它没有 Environment Manifest values、report、sample、metric、timing 或 winner。

## 阶段 1：把 divergence 与 synchronization 写成一个 disclosed bundle

`canonical-shared-tree` 是 EX11-shaped experimental baseline：每轮 `thread < stride` 的 active lanes 更新 shared partial，整个 block 在下一轮前到达 barrier。`warp-tail-control` 保留 two-load staging、block size、global stage sizes、前半段 shared tree 与 lane-0 output，但从 32-lane tail 开始改用 explicit warp synchronization 和 shuffle exchange。

这条 edge 的 primary intervention 是 warp-tail control/synchronization mechanism。它同时可能改变 branch encoding、block-barrier count、shared accesses 与 instruction mix，因此 ledger 必须把这些列为 coupled changes，不能把任何 elapsed difference 只归因于“divergence removed”或“fewer barriers”。预先声明的 synchronization hypothesis 是：相对 baseline，每个 block stage 少五个 block-wide barriers，且 stride 低于 32 后不再更新 shared partial；能回答这些 scope 的 matched queried evidence 应降低。若 matched value 不降低则 reject，若 exact GPU 没有可用且定义匹配的 field 则 no answer。

## 阶段 2：显式改变 numerical order

`reassociated-warp-order` 在已声明的 warp tail 中把 contiguous-prefix down-shuffle operand/active-lane schedule 改为 periodic XOR butterfly schedule；two-load staging、256-thread block、global stage sizes、early shared phases、五次 shuffles、31 次有效 additions、workload、oracle、tolerance 与 collection method 保持不变。该 edge 有意把 numerical order 与 divergence pattern 作为 disclosed bundle；每个 candidate 必须提交 operand-edge/participant ledger，不能只写“数学上仍是加法”。

浮点加法不满足严格结合律。相同输入集合和相同数学和，不保证不同 tree 得到逐 bit 相同结果。预先声明的 numerical hypothesis 预测 fixed workload 的 final scalar bits 与 `warp-tail-control` 不同；bits 相同就 reject 这项预测，但两侧仍必须通过 tolerance。若 exact GPU 有 owner-defined divergence field，periodic active-lane masks 预测得到更高值；相等或更低则 reject，没有定义匹配的 field 则 no answer。任何 observation 都不能推广为跨 build、跨 GPU 或跨 launch contract 的 bitwise reproducibility。

## 阶段 3：控制 intermediate memory traffic

`four-load-staging` 把每个 thread 的 guarded first-level inputs 从两项改为四项，保留 identity zero、block size、warp XOR mechanism、CPU oracle、tolerance 与 fixed workload。Source-derived stage DAG 从 `16777219 -> 32769 -> 65 -> 1` 变为 `16777219 -> 16385 -> 17 -> 1`，因此它预测更少的 intermediate partial elements 和 later-stage blocks；logical estimate 必须与 queried path traffic 分列。

这项 staging 也引入额外 thread-local additions 并改变 operation tree，所以 numerical order 是已披露 coupling。预先声明的 traffic hypothesis 只针对 intermediate partial arrays：能回答该 path/scope 的 matched queried traffic 应低于 `reassociated-warp-order`；相等或更高就 reject，没有定义匹配的 field 则 no answer。即使 traffic 降低，unprofiled elapsed result 仍可能受 instruction mix、resource use、cache state、clock/thermal state 或 system load 影响。Q12 不声明它更快，也不称它为 universal best reduction。

## Profiler method、permission 与 report custody

在 exact measurement environment 内先保留：

```bash
ncu --version
ncu --list-sections
ncu --query-metrics
```

Metric name、unit、scope 与 availability 绑定 exact Nsight Compute version 和 GPU。Hypothesis 冻结后才选择一项最小 queried section 或更短的 exact metric list，并固定 kernel-name basis/filter、launch selection、replay mode、commands 与 process environment。Baseline/candidate 各自保存 primary `.ncu-rep`、stdout/stderr、exit status、query output、expanded command、hash、observer 与 date。

Collection 前记录 performance-counter permission。Denied permission、unknown version、missing metric、ambiguous filter、report import failure 或 unmatched replay 都是 blocker：立即停止并保留记录，不使用 `sudo` 绕过 policy，不把 unavailable 写成 zero。Replay 可能重新执行 kernel、保存/恢复 memory、扰动 cache 或改变 overhead；profiled report 解释 mechanism，独立 unprofiled attempts 才回答 elapsed question。
