<a class="locale-pair" data-locale-counterpart href="/en/correctness/cpu-references-tolerances-invariants/" lang="en">Read the English counterpart</a>

可信的 CUDA 结果不能只靠一次 comparison 或一个很快的 timing 来成立。应构建分层 oracle：可独立复核的 CPU 参考实现（CPU reference）给出 expected numerical values；绝对容差（absolute tolerance）与相对容差（relative tolerance）组成预先声明的 finite floating-point comparison；discrete outputs 使用 exact checks；独立的不变量（invariant）检验两种 implementation 都必须保持的性质。Correctness first：所有适用 gate 通过后，才能开始 timing 或 optimization。

## 学完本单元，你应该能

- 设计实现同一 contract、却不照抄 GPU indexing/synchronization structure 的 CPU reference。
- 对 finite floating-point values 使用 absolute-plus-relative tolerance。
- 根据 scale、precision、operation structure 与 domain requirement 选择容差，而不是根据一次 observed mismatch 调参。
- 精确检查 index、count、flag、category 与 shape。
- 加入能够发现 CPU/GPU shared mistake 的 independent invariants。

## 先修关系

先完成 [F04：Host-Device 生命周期与显式数据移动](/foundations/host-device-lifecycle/)和 [O04：面向 CUDA 的 C++17](/start/cpp17-for-cuda/)。F04 提供 host validation 前所需 completion/copy-back boundary；O04 提供表达 reference 与 comparator 所需的 C++ types、containers 和 deterministic host-side logic。

本单元只设计 static correctness contract，不编译 CUDA、不运行 GPU，也不为某个 application 验证具体 threshold。

## Correctness 先于 performance

未验证结果的 performance number 只是在奖励错误程序。顺序应为：

```text
define the result contract
-> build and review the oracle
-> validate representative and adversarial cases
-> investigate every failure
-> only then measure or optimize
```

Optimization 可能改变 reduction order、precision 或 intermediate representation。每次此类改动后都要重跑全部 correctness gates。Speedup 不能抵消 unexplained mismatch。

## CPU reference：通往同一 contract 的第二条路径

CPU reference 是对同一 logical inputs 执行 specified operation 的小型清晰实现，应优先 auditability，而不是 speed。Serial loop 通常有用，因为它避开 GPU launch geometry、shared-memory staging 与 parallel index decomposition。

Independence 很重要。把 kernel 逐行翻译到 host 可能复制同一个 off-by-one error。应从 input/output contract 重新推导 indexing 与 boundary handling，并记录 reference precision、operation order、NaN/infinity policy 及 library functions。Higher precision 可以提供有价值的 comparison target，但不会模拟 lower-precision GPU algorithm 的每一步 rounding，也不会自动成为 mathematical truth。

还要用 hand-computable cases、identities 或第二种 trusted method 验证 reference 本身。CPU result 是 evidence，不会因为被命名为 reference 就自动正确。

## Absolute plus relative tolerance

对 finite candidate value `g` 与 finite reference value `r`，本单元使用 reference-anchored rule：

```text
error = abs(g - r)
limit = atol + rtol * abs(r)
pass  = error <= limit
```

`atol` 与 `rtol` 都必须非负，并且要在查看 candidate result 前固定。Absolute term 保护接近零的值，此时 relative ratio 不稳定或没有意义；relative term 则让 allowed difference 随 reference magnitude 增长。第一次 failure 至少报告 `g`、`r`、`error` 与 `limit`，使 decision 可复核。

使用公式前先处理 non-finite values。要明确 matching signed infinities 是否有效，以及 NaN 是否属于 expected domain result。普通 ordering comparison 遇到 NaN 会返回 false，不能因此意外让 NaN pass。

## Scale-aware policy，不是 magic constant

不存在通用 epsilon。Machine epsilon 描述 floating-point format 在 1 附近的 spacing，不是 application-wide acceptance threshold。Defensible policy 至少考虑：

- output precision 与 mixed-precision intermediates；
- operation count 与 reduction shape；
- cancellation、conditioning 与 expected numerical scale；
- 适用时的 documented library accuracy bounds；
- downstream error budget 与 domain consequences。

至少覆盖 zero/near-zero outputs、ordinary-scale outputs、large-magnitude outputs、cancellation-heavy inputs 与 boundary sizes。不同 output fields 可以采用不同 declared policies。不得把 tolerance 调大到 failing implementation 刚好通过；那会让 oracle 变成 bug 的记录。

## Discrete outputs 使用 exact checks

Tolerance 只适用于 contract 允许 numerical approximation 的 quantity。Discrete outputs 通常必须 exact equality：

- array length、tensor shape 与 element count；
- selected index、class label、boolean flag 与 status code；
- histogram bucket count 与 integer ownership metadata；
- sentinel placement 与 permutation membership。

同一 result structure 可以混合 comparators：floating values 使用 declared numerical policy，indices/counts 使用 exact checks。对 `winner_index` 使用 floating tolerance 可能接受错误 winner。

## Independent invariants

Invariant 是从 problem specification 推出的、与 implementation route 无关的 required property，例如 known-sum conservation、output bounds、monotonicity、symmetry、normalization、sortedness、uniqueness 或 permutation preservation。

每条 invariant 都应从 specification 推导，不能从 CPU output 反推。这样它才有 independent failure mode。若 CPU/GPU 都漏掉最后一个 element，两份 array 可能彼此相等，但 conservation check 会失败。反过来，invariant 单独使用又可能过弱：许多错误 array 也有正确 sum。Reference comparison 与 invariants 互补，不能互相替代。

## Correctness decision ledger

执行前写清：

1. Input domain 与 representative edge cases。
2. CPU reference algorithm、precision 与 independent derivation。
3. Exact fields 与 approximate fields。
4. 每个 approximate field 的 `atol`/`rtol` 及理由。
5. Non-finite-value policy。
6. Independent invariants 及其推导。
7. Failure diagnostics，以及所有 gate 通过后才允许 timing 的规则。

这份 ledger 让 future pass/failure 可复现，同时避免假装一个 threshold 适用于所有 CUDA programs。

## 证据边界

本页的 formula、ledgers 与 Exercises 都是 static review artifacts；它们不包含 compiled executable、GPU observation、measured error distribution 或 performance result。Compilation 与 runtime evidence axes 保持为空。未来 Lab 必须在运行前选择 thresholds，记录 Environment Manifest 与 raw results，并把 observation 与本单元分开。
