<a class="locale-pair" data-locale-counterpart href="/en/correctness/roofline-arithmetic-intensity/" lang="en">Read the English counterpart</a>

Roofline 是一个带声明的上界模型，不是 profiler verdict。算术强度（arithmetic intensity）只有在工作量（work）与流量（traffic）的计数合同完整时才有意义；同一个 kernel 在 DRAM、L2 或其他 path boundary 上可以有不同 intensity。本学习单元（Learning Unit）从单位开始构造 model，再把 workload point、region label 与 observed bottleneck 分开。

## 学完本单元，你应该能

- 声明 operation convention、declared byte boundary、read/write scope 与 traffic provenance。
- 从 `I_path = W / T_path` 推导 arithmetic intensity。
- 从 compute ceiling 与 path-bandwidth ceiling 推导 ridge intensity 与 Roofline upper bound。
- 用 achieved rate `P_achieved = W / t` 放置工作负载点（workload point）。
- 审计 above-roof mismatch，并把 modeled region 与 observed bottleneck 分开。

## 先修关系

严格先修项是 [Q05：诚实计时异步 GPU 工作](/correctness/timing-asynchronous-gpu-work/)与 [A14：用 Arithmetic Intensity 选择算法优化](/algorithms/algorithm-choice-arithmetic-intensity/)，顺序严格为 `Q05, A14`。Q05 提供 timed interval；A14 先提供 operation/traffic estimates。Q09、LAB09 与 VIS13 只是 related resources。

## 先冻结 work 与 traffic boundary

令 `W` 为 timed workload 内按已声明 convention 计数的 operations。若使用 FLOP/s，必须说明 FMA 计作 2 FLOP 还是 1 instruction；integer、special-function 或 tensor operations 不能静默塞进 FP32 FLOP ceiling。令 `T_path` 为同一 workload 穿过一个明确 path boundary 的 total bytes，包括该定义要求的 reads 与 writes。

| contract field | 必须冻结的内容 |
| --- | --- |
| workload | exact kernel/range、input shape、iterations、warm-up 与 correctness verdict |
| work | algorithmic 或 tool-derived count、operation types、FMA convention、included/excluded work |
| traffic | DRAM、L2、host-device 或其他 exact path；read/write、cache、write behavior 与 aggregation |
| time | start/end events、synchronization、repetitions、reported statistic 与 scope |
| provenance | theoretical、calibrated/measured 或 tool-reported model；不得在同一 roof 中静默混用 |

“读取两个数组并写一个数组”只是 logical compulsory traffic；transaction overfetch、cache hits/misses、intermediate arrays 与 replay 可以改变 implementation or observed traffic。Boundary 变化时必须给 intensity 加下标，而不是继续使用裸 `I`。

## 推导 intensity、ridge 与 roof

对一个 declared path：

`I_path = W / T_path`

若 `W` 用 FLOP、`T_path` 用 byte，则单位是 FLOP/byte。令 `P_compute` 是同一 operation convention 与 provenance 下的 compute ceiling，单位 FLOP/s；令 `B_path` 是同一 path/provenance 下的 bandwidth ceiling，单位 byte/s。山脊强度（ridge intensity）为：

`I_ridge = P_compute / B_path`

单位检查是 `(FLOP/s) / (byte/s) = FLOP/byte`。Roofline 上界为：

`P_roof(I) = min(P_compute, I * B_path)`

`I * B_path` 的单位也是 FLOP/s。任何 FLOP/byte、byte/s 与 FLOP/s 不闭合的 worksheet 都应停止，不应画图。

## 完整合成计算

下面的值全部是原创合成算术（synthetic arithmetic），不对应任何 GPU、report、metric 或 observation：

| input | synthetic value | unit/provenance |
| --- | --- | --- |
| work `W` | `6.0e9` | FLOP，FMA=2 FLOP convention |
| path traffic `T_path` | `3.0e9` | byte，declared path total |
| compute ceiling `P_compute` | `12.0e12` | FLOP/s，synthetic model |
| path ceiling `B_path` | `1.5e12` | byte/s，synthetic model |
| elapsed time `t` | `3.0e-3` | s，synthetic workload input |

逐步计算：

`I_path = 6.0e9 FLOP / 3.0e9 byte = 2.0 FLOP/byte`

`I_ridge = 12.0e12 FLOP/s / 1.5e12 byte/s = 8.0 FLOP/byte`

`I_path * B_path = 2.0 FLOP/byte * 1.5e12 byte/s = 3.0e12 FLOP/s`

`P_roof(2.0) = min(12.0e12, 3.0e12) = 3.0e12 FLOP/s = 3.0 TFLOP/s`

`P_achieved = W / t = 6.0e9 FLOP / 3.0e-3 s = 2.0e12 FLOP/s = 2.0 TFLOP/s`

因此合成 workload point 是 `(2.0 FLOP/byte, 2.0 TFLOP/s)`，在同一合成 roof 的 `3.0 TFLOP/s` 上界之下。两者差值不是自动可获得 speedup。

## Workload point 来自 achieved rate

横坐标来自同一 workload 与 byte boundary 的 intensity；纵坐标来自该 workload 的 achieved work rate。若 traffic 是 compulsory estimate，则点是 estimate-based；若 traffic 是 queried tool value，则必须保存 exact metric definition。不能把 estimated x-coordinate 与另一次 run 的 y-coordinate组合成 observed point。

一个点低于 roof 只说明该 matched model 还包含未解释 gap。Instruction mix、dependencies、latency hiding、issue limits、coalescing、cache behavior、occupancy、synchronization、load balance、launch size 与 model calibration 都可能与 gap 相容。

## Above-roof mismatch 是 audit trigger

保持上面的 `W`、`T_path` 与 ceilings，却把 synthetic `t` 错写为 `1.5e-3 s`，会得到：

`P_achieved,mismatch = 6.0e9 FLOP / 1.5e-3 s = 4.0 TFLOP/s`

在 `I_path = 2.0 FLOP/byte` 时，`4.0 TFLOP/s > 3.0 TFLOP/s`，所以 point 位于所声明 roof 之上。这不证明硬件违反物理上限；它证明 input set 不一致。按顺序审计：

| audit | 常见 mismatch |
| --- | --- |
| operation count | FMA 1/2 convention、batch/iteration count、algorithmic work 与 executed work 混合 |
| byte boundary | logical bytes 与 observed path bytes、read-only 与 read+write、DRAM 与 L2 混合 |
| prefixes/units | decimal versus binary bytes、ms versus s、GFLOP/s versus TFLOP/s |
| scope | one kernel versus range、one GPU versus aggregate、warm-up versus steady interval |
| ceilings | theoretical、calibrated 与 tool-reported model values来自不同 provenance/run/device |
| report | exact names、definitions、availability、filter、replay 或 aggregation 不匹配 |

只有所有 coordinates 匹配后才重建 model。不要移动 roof 来“容纳”point，也不要丢弃不方便的 traffic。

## Region labels 是 modeled regions

在这个两 ceiling model 中，`I_path < I_ridge` 的点位于 sloped path-ceiling region，`I_path > I_ridge` 的点位于 horizontal compute-ceiling region，刚好相等是 ridge。可称为 modeled path-limited region 与 modeled compute-limited region；它们从输入 ceilings 推导，**从不等于 observed bottleneck diagnosis**。

Ceiling provenance 必须成套：

| provenance family | 合法用途 | 禁止混合 |
| --- | --- | --- |
| theoretical | 由同一 exact device/spec 与 operation/path convention 建 peak model | 不与 unrelated measured bandwidth 拼成未标注 roof |
| calibrated/measured | 在声明的 Reference Environment、microbenchmark、clock state 与 method 下建 empirical roof | 不移植到另一 GPU/run 而保留“measured”标签 |
| tool-reported model | 从同一 exact report/tool/GPU 的 documented model fields 构图 | 不把 chart field 当作独立实测 peak 或跨版本常数 |

可以并排画三种 roof，但每条必须单独标注，不能从每种来源挑最大的部分组成“best” roof。

## Nsight Compute chart 仍要 query contract

Nsight Compute 2026.2.1 提供 Roofline Charts 与 UI Rooflines page，但 chart 不免除 Q08 contract。先查询 exact tool/GPU 上可用 section 与 metrics，保存 report、kernel filter、replay、name、unit、definition、scope 与 ceiling provenance。CLI 会自动缩放 SI units；review 时必须恢复明确 factor，不能把显示前缀当作原始单位。

```bash
ncu --version
ncu --list-sections
ncu --query-metrics
```

Original Roofline paper 只支持 model history 与 `min(compute, intensity * bandwidth)` 数学，不支持任何 current NVIDIA metric name、GPU value、chart implementation 或 availability claim。Context7 两个 NVIDIA indexes 只做 retrieval cross-check，exact owner pages 才是 authority。

2. 如何用单位推导 `I_path`、`I_ridge` 与 `P_roof(I)`？
3. 合成 workload point 为什么是 `(2.0 FLOP/byte, 2.0 TFLOP/s)`，且低于 `3.0 TFLOP/s` roof？
