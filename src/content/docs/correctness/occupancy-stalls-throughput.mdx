占用率（occupancy）回答“一个 SM 上有多少 warp 保持驻留”，不回答“这些 warp 是否正在做有用工作”。它是延迟隐藏资源（latency-hiding resource），不是利用率（utilization），也不是必须最大化的目标。本学习单元（Learning Unit）建立从资源上限到调度器状态再到吞吐量的解释顺序，并阻止从一个醒目的百分比直接跳到瓶颈或加速结论。

## 学完本单元，你应该能

- 用 active warps 与 exact-device maximum active warps 定义 occupancy。
- 区分理论占用率（theoretical occupancy）和实际占用率（achieved occupancy）。
- 把活跃 warp（active warp）、符合发射条件的 warp（eligible warp）、就绪 warp（ready warp）与 issued warp 放进同一个 scheduler model。
- 分开解释调度器停顿（scheduler stall）、延迟（latency）、吞吐量（throughput）与 utilization。
- 在解释任何 report 前查询 exact metric name、unit、definition、scope 与 availability。

## Occupancy 的定义与边界

对同一个 SM scope，定义为：

`occupancy = active warps per SM / maximum active warps per SM`

分子是驻留并保持 execution context 的 warps；分母是 exact GPU 在该 scope 可容纳的最大 active warps。两者必须来自兼容的 definition 与 denominator。Occupancy 不是某条 pipeline 的 busy fraction，不是 issued-instruction rate，也不是“所有 CUDA cores 都在工作”的比例。

下面的静态关系表不包含任何 GPU observation：

| quantity | 回答的问题 | 不回答的问题 |
| --- | --- | --- |
| occupancy | 有多少 warp execution contexts 驻留，相对 exact maximum 是多少 | 这些 warps 是否 eligible、是否 issued、做了多少 work |
| utilization | 某个明确资源在某个 observation interval 内的活动程度 | 驻留 warp 数量或等待原因 |
| throughput | 每单位时间完成的 declared work/traffic，或工具按其定义报告的相对 rate | 单次 operation 的 latency |
| latency | 一项 operation 或相依 instruction 间隔要等待多久 | 同期可用多少其他 work 来隐藏等待 |

## Theoretical 与 achieved 不能互换

理论 occupancy 是 launch/resource model：给定 threads per block、registers、static/dynamic shared memory 与 exact-device limits，求每个 SM 最多能同时驻留多少 blocks/warps，再除以该设备的 maximum active warps。它不需要证明 kernel 在时间上一直拥有这些 warps。

实际 occupancy 是 execution-derived quantity：在工具声明的 sampling/aggregation scope 内，实际 active warps 相对同一 maximum 的结果。Short grid、tail wave、block-duration imbalance、early completion 或其他动态行为都可能让它低于 theoretical occupancy。Exact averaging 与 denominator 必须从该 report 的定义读取；不能凭名称猜测。

一个纯代数检查是：若 queried launch model 给出 `W_model` active warps，而 exact device query 给出 `W_max` maximum active warps，则 `O_theoretical = W_model / W_max`。若 report 用兼容 scope 给出 `W_observed`，才可写 `O_achieved = W_observed / W_max`。这里没有为三个变量填值，因此没有虚构 hardware ceiling 或 observation。

## Hardware 与 resource limits 共同限制 residency

一个 block 能否驻留以及同时驻留多少 blocks，受 threads/warps per block、register allocation、static plus dynamic shared memory、maximum resident blocks/warps 与其他 documented hardware resources共同限制。限制按 allocation granularity 生效，不能只用源码变量个数手算。使用 exact binary 的 compiler/resource record、launch configuration、`cudaGetDeviceProperties`/owner-supported occupancy API 或 exact report，而不是记忆中的设备表。

| input family | 必须记录 | 可能改变的结果 |
| --- | --- | --- |
| launch | grid、block、dynamic shared bytes | warps per block、waves、resident-block candidate |
| kernel resource | exact binary、registers、static shared memory | register/shared-memory limiter |
| device resource | exact GPU/CC 与 queried limits | maximum resident blocks/warps、available registers/shared memory |
| runtime context | cache/shared configuration 或 documented attributes（如适用） | 可用 resource partition 或 launch validity |

降低 register 或 shared-memory use 可能增加 theoretical occupancy，也可能引入 spill、额外 instructions 或较差 locality。只有正确、受控的 before/after measurement 才能判断性能结果；“更高 occupancy”本身不是 acceptance criterion。

## 从 active 到 eligible 再到 issued

调度器从自己的 resident pool 选择 work。Active/resident 只表示 warp 已分配到 scheduler/subpartition。Eligible 表示该 active warp 已准备发射下一条 instruction：所需 instruction 可用、input dependencies 已满足，并且所需 function unit 可接受它。本文把 ready 作为普通描述词；解释 profiler report 时保留 owner tool 的 exact “eligible” definition。

| scheduler state | 静态含义 | 与下一状态的差距 |
| --- | --- | --- |
| active/resident | execution context 在 SM/subpartition 上 | 可能等待 fetch、dependency、barrier 或 resource |
| eligible/ready-to-issue | 下一 instruction 满足工具所列发射条件 | scheduler 仍需从 eligible set 选择 |
| issued | scheduler 在该 issue opportunity 发射 instruction | 不等于 instruction 已完成，也不等于 whole-SM peak throughput |

Scheduler stall 描述 warp 为什么在某个定义下不能发射下一条 instruction。Stall reasons 可以重叠于复杂 causal chain，sampling/normalization 也由工具决定。只有在 scheduler 未能持续 issue 时，stall breakdown 才成为后续线索；最大的 stall share 仍不是自动 bottleneck。

## Occupancy 隐藏 latency，但不缩短 latency

当一个 warp 等待 memory dependency、execution dependency、instruction fetch 或 synchronization 时，调度器可以选择另一个 eligible warp。更多 resident warps扩大“可能有别的 ready work”的池，因此可以帮助隐藏 latency；它不会让原 operation 更快返回。若所有 active warps 同时等待同一 dependency，high occupancy 仍可伴随低 issue progress。

Throughput 衡量 declared work/traffic per time；Nsight Compute 的 Speed Of Light 类 percentage 则按 exact section definition，把 achieved throughput 与某个 theoretical maximum 比较。这个 percentage 不是“剩余百分比就是可获得 speedup”，也不能跨不同 units、pipelines、clock domains 或 reports 直接相加。

## 三条禁止推断

- **High occupancy 不是 bottleneck verdict。** 它既不证明 latency 已隐藏，也不证明增加 occupancy 会加速。
- **One stall share 不是 causal verdict。** 先确认 scheduler issue gap、sampling denominator、scope 与 competing explanations，再设计改变一个 mechanism 的实验。
- **Throughput percentage 不是 speedup forecast。** 它依赖特定 resource ceiling 与 normalization；靠近一个 ceiling 不证明 whole kernel 只有该限制，远离 ceiling 也不说明提高到 100% 可行。

同一 report 中，theoretical/achieved occupancy、eligible warps、issue activity、stall reasons 与 resource throughput 可以组成证据链，但不能互相替代。跨 report comparison 还必须冻结 workload、kernel occurrence、correctness、binary、GPU、tool version、filter、replay 与 clocks/cache controls。
