A bank conflict is not global-memory coalescing. It describes active threads in one warp shared-memory instruction requesting **distinct words** that map to the same bank. A layout transform can change word stride without changing the logical tile. Same-address read broadcast is an explicit exception and must not be mislabeled as a conflict.

## What you should be able to do

- Map aligned 32-bit shared words to 32 banks in the selected CC 7.5+ fixture.
- Distinguish a distinct-word same-bank conflict from same-word read broadcast.
- Derive bank sets and conflict degrees for strides 1, 2, and 32.
- Prove that a column read from a row-major 32x32 tile is a 32-way conflict while 32x33 padding makes this fixture conflict-free.
- Keep bank prediction, logical correctness, shared footprint, profiler observation, and timing separate.

## Prerequisite

Complete [M03: Shared-Memory Tiling](/en/memory/shared-memory-tiling/) first. M03 already proves per-block tile ownership, load/B1/use/B2 phases, edge neutral values, and the reuse boundary. M04 changes only shared addresses in the use phase. It cannot remove M03 barriers, change the logical matrix, or let invalid threads return early.

This page requires no CUDA-capable system. Bank tables and padding proofs are static expected models, not GPU runtime observations. EX06 and VIS05 are related, but do not automatically populate this page's empty evidence axes.

## Selected fixture: 32 banks and 32-bit words

This site's Baseline GPU Capability Tier is CC 7.5+. This unit freezes an explicit fixture for that path: shared memory has **32 banks**, and successive 32-bit words map to successive banks. For a word whose relative shared byte offset is divisible by 4:

```text
word_index = byte_offset / 4
bank(word_index) = word_index mod 32
```

The model applies to one shared-memory instruction from one warp. Active lanes, access width, exact word addresses, and read/write role are inputs. Do not combine another instruction or inactive lane. Wider types, subword accesses, or future architectural details need their own explicit contract.

## Conflict and broadcast

When active lanes in one instruction access **distinct word indices** that share a bank index, a bank conflict occurs. Those same-bank distinct-word accesses serialize into multiple bank service steps. N-way means the maximum number of distinct words one bank must serve for that instruction; it is not an exact cycle count.

When multiple lanes **read the same shared word address**, the value can be broadcast to requesters, which is not a bank conflict. Deduplicate same-address reads first, then group distinct words by bank. Looking only at “all 32 lanes map to bank 0” would misclassify a valid broadcast as a 32-way conflict.

This unit freezes only the same-address **read** rule. Do not generalize it into a deterministic concurrent-write value contract.

## Stride fixtures

Let lane `i` read `word_index(i) = i * strideWords`:

| stride | bank sequence | distinct words per busiest bank | classification |
| ---: | --- | ---: | --- |
| 1 | `0,1,2,...,31` | 1 | conflict-free |
| 2 | `0,2,4,...,30,0,2,...,30` | 2 | 2-way conflict |
| 32 | `0,0,...,0` | 32 | 32-way conflict |

Stride two uses 16 even-numbered banks, each with two distinct words. At stride 32, lanes request distinct words `0,32,64,...,992`, all mapped to bank 0. If all 32 lanes instead read word 0, the bank sequence looks the same but the exact address is shared, so the operation is broadcast rather than a stride-32 conflict.

## 32x32 tile: why a column read conflicts

For row-major `float tile[32][32]`, word index is:

```text
word(row, column) = row * 32 + column
```

Let warp lane `i` hold column `c` fixed and read row `i`. Its bank is `(i * 32 + c) mod 32 = c`. The 32 lanes request 32 distinct words in bank `c`, producing a **32-way bank conflict** in the selected fixture. Holding row fixed and advancing column with lane gives stride one and is conflict-free.

This is a shared-layout analysis, not global coalescing. A kernel can have different address patterns in global load/store and shared use phases, which must be reviewed separately.

## 32x33 padding: change storage stride, not logical shape

Change storage declaration to `float tile[32][33]`. The logical tile remains 32 rows x 32 columns; the 33rd column is padding and not part of the logical matrix. The column-read word index becomes `i * 33 + c`, with bank:

```text
(i * 33 + c) mod 32 = (i + c) mod 32
```

For `i = 0..31`, those bank indices form a permutation of 0..31, so the column read is **conflict-free** in this fixture. Storage grows from 1024 to 1056 32-bit words: 32 extra words, or 128 bytes per tile. That footprint belongs in kernel resource-feasibility review.

Padding removes the bank conflict from this particular column-access fixture. It does not prove that the whole kernel is faster. Extra shared footprint, other instructions, occupancy/resource effects, and timing require measurement.

## Measurement boundary: conflict-free is not a speedup

The static bank model predicts conflict degree for a named instruction. A profiler metric records tool/version, metric definition, kernel/source range, tile shape, and Environment Manifest. Timing also requires correctness, warm-up, synchronization boundary, repetitions, and samples. Observed bank conflicts may come from other unmodeled instructions.

The allowed conclusion is therefore: “Under the selected 32-bank, 32-bit-word fixture, this column access changes from an expected 32-way conflict to an expected conflict-free mapping.” Without runtime logs, there is no elapsed-time, bandwidth, occupancy, or speedup claim.

2. Why do distinct words in one bank conflict while several lanes reading one word receive a broadcast?
3. Why are strides 1, 2, and 32 respectively conflict-free, 2-way, and 32-way?
4. Why does a row-major 32x32 tile map a warp's column read to one bank?
5. Why does 32x33 padding make that column read conflict-free without establishing speedup?
