In this unit, coalescing is a transaction-shaping analysis: for the active-address set of one warp memory instruction, count the naturally aligned 32-byte segments needed to cover every requested word. This static segment count explains an address pattern. It is not necessarily a profiler's final transaction count and creates no speed claim by itself.

## What you should be able to do

- Construct requested byte ranges from the instruction, active lanes, word width, base alignment, offset, and stride.
- Apply the CC 6.0+ 32-byte segment model within this site's Baseline GPU Capability Tier of CC 7.5+.
- Derive segment counts for aligned contiguous, one-word-offset, and stride-two patterns with 32 lanes reading one 4-byte word each.
- Explain why a tail warp, inactive lanes, and a different instruction require a new address set.
- Keep static prediction, cache reuse, actual issued transactions, correctness, and timing in separate evidence fields.

## Prerequisites

Complete [M01: Address Spaces, Ownership, Scope, and Lifetime](/en/memory/address-spaces/) and [F03: Make Multidimensional Indexing and Bounds a Correctness Contract](/en/foundations/multidimensional-indexing/) first. M01 establishes that this is global-memory access, not a cache-level ranking. F03 supplies lane/thread indices, logical extent, and bounds, which decide which lanes are active for an instruction and which addresses they request.

This page requires no CUDA-capable system. Hand-calculated segments are an expected model, not Compile-Checked, Runtime-Verified, or Community-Observed evidence. EX05 and VIS04 are related resources, but they do not populate this page's empty evidence axes.

## Model: freeze one instruction first

For compute capability 6.0 and newer, this site uses the following teaching model inside its supported CC 7.5+ tier:

1. Take only byte addresses requested by active lanes in **one global-memory instruction from one warp**.
2. List the bytes covered by each requested word.
3. Cover those bytes with naturally aligned 32-byte segments `[32k, 32k + 31]`.
4. The count is the size of the distinct segment set; address order does not change that set.

For an aligned base `B mod 32 = 0`, lane `i` requesting one 4-byte word has:

```text
address(i) = B + offsetBytes + i * strideWords * 4
segment(i) = floor(address(i) / 32)
```

If a word crosses a segment boundary, both segments count. The frozen fixtures below use naturally aligned 4-byte words, so each word lies within one segment.

## Aligned contiguous: four segments

All 32 lanes are active, `offsetBytes = 0`, and `strideWords = 1`. Lanes 0..31 request `B + 4i`, giving requested bytes `[B, B + 127]`. They cover:

```text
[B + 0,  B + 31]
[B + 32, B + 63]
[B + 64, B + 95]
[B + 96, B + 127]
```

The aligned contiguous fixture therefore needs **4 naturally aligned 32-byte segments**. Four segments covering 128 requested bytes is an address-accounting conclusion, not a kernel duration.

## Offset by one word: five segments

Keep 32 active lanes and stride 1, but move the first word to `B + 4`. Requested bytes become `[B + 4, B + 131]`, touching **5 segments**, from `[B, B + 31]` through `[B + 128, B + 159]`. The first and last are only partly used.

This fixture shows that alignment relative to 32-byte boundaries changes the coverage set. It does not say how much slower a real run must be. Cache-line reuse across nearby warps, architecture state, and issued requests require measurement.

## Stride two words: eight segments

Restore `offsetBytes = 0` and set `strideWords = 2`. Lane `i` requests `B + 8i`, with starting addresses from `B` through `B + 248`. Each 32-byte segment receives four lanes' 4-byte words, so 32 lanes touch **8 segments**.

The stride-two payload remains 128 requested bytes while segment coverage is 256 bytes. That difference describes transaction shaping. It proves no cache miss, DRAM traffic, latency, bandwidth, or speedup.

## Active lanes, word width, and instruction boundaries

A tail warp may have only some lanes pass F03 bounds. An inactive lane requests no word and must not be added merely to make 32 lanes. For example, lanes 0..4 reading 4-byte words from an aligned base touch only the first segment. A wider word can cover more bytes and can cross a segment boundary.

Two source-level accesses may also compile to separate instructions. Apply the model per instruction with that instruction's active mask and request width; do not combine every address from a whole kernel into one segment set.

## Measurement boundary: prediction is not observation

The static model predicts a required segment set. Hardware and profilers can report requests or transactions at different layers; cache hits, reuse between nearby warps, load/store paths, replay, and metric definitions affect observations. Actual issued transactions and cache reuse require an exact Environment Manifest, metric name, tool version, and run log.

The values 4, 5, and 8 therefore cannot be rewritten as 1.25x or 2x runtime, nor must a profiler counter equal these integers. First verify that every mode requests the intended logical payload and produces correct results, then compare prediction with observation. Without timing and metric evidence, write neither “faster” nor “speedup.”

## Retrieval check

1. Why must the coalescing model be scoped to one memory instruction from one warp?
2. Why do 32 active lanes reading aligned contiguous 4-byte words require four rather than one 32-byte segment?
3. Why does a one-word base offset expand coverage from four segments to five?
4. Why does stride two touch eight segments, while inactive tail lanes must not count?
5. Why must expected segment count, actual issued transactions, cache reuse, and elapsed time remain separate records?
