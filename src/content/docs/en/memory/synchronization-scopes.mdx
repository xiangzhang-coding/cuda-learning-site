A synchronization scope is chosen from the participants that must coordinate and the communication scope that carries their data. Warp, block, device, and system are not four strengths of one universal operation. They name different participant sets and available protocols. A correct protocol states separately whether it needs rendezvous, ordering, memory visibility, or atomicity.

## What you should be able to do

- Name every producer, consumer, and memory location before selecting a synchronization primitive.
- Choose warp, block, device, or system coordination from participant and communication scope.
- Distinguish rendezvous from memory ordering and visibility.
- Distinguish an atomic access from a barrier or memory fence.
- Explain why a fence alone neither makes peers arrive nor publishes a completion flag.

## Prerequisites

Complete [F02: Build an Execution-Hierarchy Mental Model](/en/foundations/execution-hierarchy/) and [M01: Address Spaces, Ownership, Scope, and Lifetime](/en/memory/address-spaces/) first. This unit does not teach a catalog of every CUDA synchronization interface. It establishes the selection proof that later interfaces must satisfy. It requires no CUDA-capable system and grants no compilation, runtime, or performance Evidence Status.

## Scope ledger: who communicates with whom?

Start with a ledger rather than a primitive name:

| coordination scope | possible participants | communication location | minimum question |
| --- | --- | --- | --- |
| warp | named lanes in one warp | registers via collectives, or shared/global memory | Which lanes are in the mask, and do all named lanes execute the operation? |
| block | threads in one thread block | usually shared or global memory | Do all required block participants reach the same barrier phase? |
| device | threads in different blocks on one device | global memory plus a device-scope protocol | What orders publication and observation without assuming block scheduling? |
| system | GPU and CPU threads, or participants spanning devices | memory accessible to all named participants | Does the allocation and primitive actually support system-scope communication? |

The table is a selection map, not a promise that every row has one built-in global barrier. In particular, ordinary blocks cannot wait on each other by assuming they are resident together. Device- and system-scope communication needs an interface whose documented scope includes every participant and whose progress conditions are valid.

## Rendezvous: participant progress at a phase

Rendezvous answers, “Which participants must reach this phase before any of them proceed?” A block barrier such as `__syncthreads()` is a rendezvous for participating threads in a block and also carries documented memory effects. A warp operation such as `__syncwarp(mask)` names participating lanes through a mask. The mask is part of the contract; “same warp” is not a substitute for naming participants.

Rendezvous does not follow from source proximity. Two blocks reaching adjacent source lines are not thereby joined, and a host call appearing after a launch does not imply that the device work completed unless the API contract creates that boundary.

## Ordering and visibility: before, after, and observable

Ordering constrains how operations relate, such as a producer's data write preceding publication of a ready flag. Memory visibility asks whether the intended consumer can observe those writes after following the protocol. Both questions must be answered at a scope that includes producer and consumer.

A useful producer-consumer proof is:

```text
producer writes payload
-> release publication
   at sufficient scope
-> consumer observes publication
   with matching acquire at sufficient scope
-> consumer reads payload
```

This is a relation between operations, not a claim that caches are “flushed everywhere.” A smaller scope does not cover a participant outside that scope. A larger scope does not repair a missing publication or an inaccessible memory location.

## Atomicity: one indivisible access is not the whole protocol

Atomicity means the specified access cannot be observed as a torn read-modify-write within its documented scope. It does not automatically provide a rendezvous, and a relaxed atomic can provide atomicity without ordering unrelated payload accesses. Conversely, a barrier may coordinate participants and establish visibility while not turning an arbitrary conflicting update into an atomic read-modify-write.

For a counter, atomicity may be the central requirement. For message passing, the flag needs both suitable atomicity and ordering, while the payload needs the visibility relation created by that publication protocol. Name those obligations separately.

## Barriers versus memory fences

A barrier coordinates a declared participant set at a phase. A memory fence orders memory operations performed by the calling thread according to its documented scope. A fence does **not** make another thread execute a matching line, wait for a phase, or learn that the producer is finished. A separate synchronization action, often a suitable atomic publication, must connect producer and consumer.

This distinction prevents two common errors:

- replacing a missing block rendezvous with `__threadfence()`;
- inserting `__syncthreads()` and assuming it coordinates a different block or the host.

Use each primitive only for the guarantees its contract supplies.

## Selection procedure

For each communication edge, write six fields:

1. **Participants:** exact producers and consumers.
2. **Location:** the address space and allocation visible to them.
3. **Progress:** whether any participant may wait safely.
4. **Rendezvous:** whether a phase requires every named participant.
5. **Ordering and visibility:** the before/after relation and observation mechanism.
6. **Atomicity:** which conflicting access, if any, must be indivisible.

Only then select the narrowest documented scope that includes every participant. If no available primitive satisfies all six fields, redesign the communication pattern rather than widening a fence and guessing.

## Evidence boundary
