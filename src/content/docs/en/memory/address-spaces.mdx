An address space says where an object can be addressed, but a complete decision also records ownership, scope, lifetime, and release responsibility. Host memory, global memory, constant memory, shared memory, local memory, and registers are semantic and resource contracts, not rungs in a cache-level ranking from “fast” to “slow.”

## What you should be able to do

- Record an object's allocator or creator, permitted accessors, sharing scope, valid interval, and release action as separate facts.
- Distinguish grid-accessible global/constant storage, per-block shared instances, and per-thread local/register storage.
- Explain why local memory is logically thread-private but physically in device memory, and how register pressure can spill values to local memory.
- Assign the correct release responsibility to explicit Runtime allocations, language-managed objects, and compiler-managed objects.
- Reject fixed latency, cache path, capacity, or speed rankings inferred only from an address-space name.

## A four-axis classification model

Do not ask only where a variable “lives.” Answer four questions in order:

1. **Owner/allocation:** Which host allocator, Runtime API, module declaration, kernel launch, or compiler decision creates storage?
2. **Accessibility/scope:** Can the host, a whole grid, one block, or one thread name or access the same object instance?
3. **Lifetime:** Across which host scope, kernel launch, block execution, thread execution, or context/application interval is the object valid?
4. **Release:** Must the program call a matching release API, or does host language scope, module/context teardown, block/thread completion, or the compiler retire it automatically?

Giving every thread the same pointer does not make their local objects shared. Declaring a value in a kernel does not guarantee a register. Source-level scope, CUDA address-space semantics, and compiler placement remain separate records.

## Host, global, and constant

| space | owner / allocation | accessibility and sharing scope | lifetime | release |
| --- | --- | --- | --- | --- |
| host | a host-language allocator or a Runtime host allocator such as `cudaMallocHost` | directly accessible to the CPU; device access requires an explicit copy or mapping contract | defined by the host object/allocation contract | match the host allocator; use `cudaFreeHost` for page-locked Runtime allocations |
| global | a host-side device allocation such as `cudaMalloc`, or a corresponding device/global object | kernel threads holding a valid device pointer can access it; an allocation can cross blocks and kernel launches | until `cudaFree`, device reset, or owning context/application teardown | explicit allocations use `cudaFree`, after work still using the allocation is complete |
| constant | a module-scope C++ `__constant__` symbol established with its module/context; host code updates it through symbol APIs | read-only to kernels, grid-visible on one device, and accessible to the host through Runtime symbol operations | valid with the C++ symbol's creating context/module | do not call `cudaFree` on the symbol; module/context lifetime manages it |

“Read-only to kernels” does not prevent the host from initializing or updating constant storage. A host operation such as `cudaMemcpyToSymbol` and a kernel read have different roles. Likewise, “global” does not make an ordinary device pointer directly dereferenceable by the CPU.

## Shared, local, and register

| space | owner / allocation | accessibility and sharing scope | lifetime | release |
| --- | --- | --- | --- | --- |
| shared | each block's static `__shared__` declaration or dynamic shared storage requested at launch | threads in the owning block share one instance; different blocks own different instances | the corresponding block/kernel execution interval | automatic at block completion; never `cudaFree` |
| local | compiler storage for one thread's automatic object, non-constant-indexed array, large object, or spill | only the owning thread under source semantics | the owning thread's kernel invocation | compiler/thread completion manages it |
| register | finite register resources assigned by the compiler to one thread's values | only the owning thread; there is no cross-thread register object | the owning thread's kernel invocation | compiler/thread completion manages it |

The word **local** describes logical scope, not physical proximity. Local memory is thread-private but physically resides in device memory. Register allocation is not promised by a source declaration either; compiler, target, and resource pressure determine placement. A register spill places values in local memory but does not make them accessible to another thread.

## Address spaces are not cache levels

A cache answers whether recently used data is retained in a hardware cache. An address space answers how a program names, shares, and keeps an object alive. Global and local accesses can use caches, constant storage has its own read behavior, and shared memory can share a physical resource configuration with L1 on selected architectures. None of these facts turns global, local, constant, and shared storage into cache levels of one another.

The table therefore cannot support a universal `register > shared > constant > global` speed order. Capacity, cache organization, shared/L1 configuration, register availability, spilling, and access cost vary with architecture, kernel, compiler target, and access pattern. M01 issues a semantics-and-responsibility contract, not a latency or speed verdict.

## Release ledger: the creator proves the endpoint

For an explicit allocation, record the allocation API, returned object, completion boundary for every user, and matching release. For block/thread/compiler-managed storage, record the automatic lifetime endpoint and do not invent a free operation. A compact review is:

```text
object -> creator -> permitted accessors -> shared instance scope
       -> last permitted use -> completion proof -> release owner/action
```

A `cudaMalloc` buffer cannot be freed while a kernel may still use it. A host cannot free a `__shared__` tile. A local array does not gain a cross-thread pointer-sharing contract merely because its physical storage is device memory. Prove ownership and last use before discussing placement or optimization.

## Retrieval check

1. Why can an address space not serve as a cache hierarchy ordered from fast to slow?
2. Who creates and releases a global allocation, a `__constant__` symbol, and a `__shared__` tile?
3. How can local memory have thread-private scope and a physical device-memory location at the same time?
4. Why does a source-level scalar not guarantee register placement, and why does a register spill preserve thread ownership?
5. Before releasing a `cudaMalloc` allocation, why must a ledger name both the last user and completion proof?
