Warp divergence occurs when lanes of one warp follow different control-flow paths. Reconvergence describes lanes becoming eligible to execute a common region again; it does not reveal the exact instruction schedule. Warp-safe reasoning therefore names active lanes, an intended participation mask, and every required synchronization edge instead of relying on implicit lockstep.

## What you should be able to do

- Trace active and inactive lanes through a divergent branch.
- Distinguish the current active mask from an intended participation mask.
- Explain what changed with Independent Thread Scheduling on CC 7.0+.
- Reject code whose correctness relies on unsafe implicit lockstep.
- State why a source-level join is not synchronization and why the exact hardware schedule is unknown.

## Active masks and participation masks

An active mask answers, “Which lanes are executing this instruction now?” A participation mask answers, “Which lanes are required to take part in this collective protocol?” They can differ. A lane can be inactive at one path instruction yet still belong to a collective that occurs after the paths join.

`__activemask()` reports the lanes active at the call. It does not recover an intended group omitted by earlier divergence. If a protocol needs all lanes satisfying predicate `p`, derive that participation set at a point where the required voters are active, for example with a documented ballot, then carry the mask into later warp collectives.

For every mask-sensitive operation, prove:

```text
mask members = intended participants
every named lane reaches the operation under its contract
every consumed source lane is named and supplies a value
```

## Divergence: paths and disabled lanes

When a data-dependent branch splits a warp, each taken path executes with lanes not on that path disabled. Divergence occurs within a warp; different warps already execute independently. A source trace may represent path A followed by path B for explanation, but that diagram is not a promise of which path hardware issues first or how instructions interleave.

The correctness question is not “Which branch wins?” It is whether each lane's own scalar semantics are correct and whether any cross-lane exchange uses a valid participant set plus required synchronization.

## Reconvergence: common eligibility, not a clock tick

Reconvergence is a control-flow concept: lanes that followed different paths can later be eligible for a common region. It does not mean every lane completed at the same instant, nor does it create memory ordering merely because the source has one closing brace.

A reconvergence diagram can show masks by source region. It cannot prove an exact program-counter stack, issue order, or cycle count. Those implementation details are outside the portable source contract.

## Independent Thread Scheduling on CC 7.0+

For devices with compute capability below 7.0, a warp used one shared program counter plus an active mask. On CC 7.0+, Independent Thread Scheduling maintains execution state per thread and permits divergence and reconvergence at sub-warp granularity. A schedule optimizer groups active threads into SIMT units.

The practical compatibility rule is direct: code written around implicit warp-synchronous behavior must be revisited. CC 7.0+ does not make every intra-warp communication incorrect; it makes implicit lockstep an invalid correctness argument. Use documented synchronized warp operations and explicit masks.

## Unsafe implicit lockstep

This argument is unsafe:

```text
lane i writes shared[i]
lane i immediately reads shared[i - 1]
there is no race because lanes are in one warp
```

“One warp” identifies an execution group, not the memory ordering edge required by the exchange. The repair must define participating lanes, place a documented warp synchronization where shared-memory visibility is needed, and guard any source lane that does not exist. A suitable shuffle collective can instead move register values when its mask and source-lane contracts are satisfied.

## A source-level join is not synchronization

After both arms of an `if` reach the statement following the branch, the source has a join. The statement `source-level join is not synchronization` remains true: the join alone is neither a barrier nor a memory fence. If path A writes data consumed by a lane from path B, the program still needs a documented cross-lane protocol.

This also prevents a subtler mistake: taking `__activemask()` independently inside each branch and later pretending both branch-local masks name one group. Capture the intended participation mask at the protocol's valid formation point.

## Schedule boundary

Portable reasoning may state lane predicates, active masks at modeled source regions, required participation masks, and documented synchronization relations. It must leave path issue order, instruction interleaving, reconvergence-stack details, and timing unspecified. In short, the exact hardware schedule is unknown.

That boundary is not ignorance about the program. It is a deliberate separation between guarantees needed for correctness and implementation freedom retained by the GPU.
