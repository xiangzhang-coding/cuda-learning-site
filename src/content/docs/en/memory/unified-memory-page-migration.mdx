Unified Memory lets managed memory be addressed by CPU and GPU code, but one pointer does not imply one physical memory, zero movement, or free concurrent sharing. Page migration is one possible way a system changes locality. Residency, accessibility, migration, remote access, and coherence must remain separate records whose behavior depends on the operating system, driver, device, and interconnect.

## What you should be able to do

- State the owner, lifetime, and access contract of a `cudaMallocManaged` allocation.
- Distinguish legal accessibility from current or inferred residency.
- Trace a page access sequence with conditional migration, remote-access, and no-migration branches.
- Model the possible cost of faults and data movement without assigning an invented duration or migration count.
- Treat `cudaMemAdvise`, prefetch, and VIS08 as guidance or models, not proof of runtime placement.

## Prerequisites

Complete [M01: Address Spaces, Ownership, Scope, and Lifetime](/en/memory/address-spaces/) and then [M02: Coalescing as Transaction Shaping](/en/memory/coalescing-transactions/). M01 supplies allocation ownership, valid accessors, last use, and matching release. M02 supplies the discipline of freezing an access set before reasoning about movement, while its 32-byte transaction model must not be confused with page-level placement.

M10 is related to [M09: Pinned Memory and Transfer Overlap](/en/memory/pinned-memory-transfer-overlap/), but managed access is not an implicit version of M09's explicit-copy pipeline. M10 asks where touched data may be serviced and what movement could cost; it does not claim that migration or direct access is faster.

## Managed memory is an allocation contract

`cudaMallocManaged` creates an allocation managed by the Unified Memory system and released with `cudaFree` after every user completes. CPU and GPU code can use the managed pointer under the applicable system contract. The allocation still has one owner, a finite lifetime, data dependencies, and synchronization requirements.

“Accessible from both processors” does not mean that CPU and GPU may race on the bytes, that both have equally local access, or that no transfer occurs. A kernel launch remains asynchronous, so the host establishes a completion boundary before reading GPU-produced values unless a documented concurrent-access and synchronization design says otherwise. Unified Memory removes some explicit copy bookkeeping; it does not remove correctness bookkeeping.

## Accessibility is not residency

Accessibility answers whether a processor may legally address a managed range. Residency describes where physical backing is local at a stated time. A stable virtual address can refer to pages resident in CPU memory, pages resident in GPU memory, or data reached through a coherent or remote mapping, depending on the system.

On a software-coherent full-support system, an access to a page local to another processor may fault and trigger migration. On a hardware-coherent system, a processor may access remotely without moving the page. Limited-support systems can move managed data at coarser execution boundaries. These are conditional branches, not three stages every allocation traverses.

A source pointer and an allocation API establish accessibility and ownership facts. They do not reveal the physical locality of every page during execution.

## Trace an access sequence, not a universal migration story

Start with symbolic pages and an unknown residency state. Consider this ordered workload:

```text
CPU writes pages A and B
completion/order edge
GPU reads B and C, then writes C
GPU completion edge
CPU reads C
```

For each access, record the accessor, touched pages, required synchronization, prior known state, and permitted system behaviors. Under a software-coherent fault-and-migrate model, the GPU access to B may migrate a host-local page and the later CPU read of C may migrate a device-local page back. Under hardware coherence or documented direct access, either access may be serviced without migration. Under a limited model, movement may happen at launch or synchronization rather than at each first GPU touch.

The ledger therefore says “migration candidate” only when locality and capability premises support that branch. It never turns the browser's colored page or the source access order into a recorded migration.

## Model page-migration cost conditionally

When page migration occurs, its work can include fault detection and service, mapping or ownership updates, coherence actions, and moving the backing data. The transfer granularity can exceed the few bytes that triggered the access, so alternating CPU and GPU writes to the same pages can create repeated movement or thrashing on a fault-and-migrate system.

Use a symbolic cost decomposition:

```text
access episode = useful memory access
               + possible fault/coherence work
               + possible data movement
```

Each “possible” term requires an Environment Manifest and runtime evidence before becoming an observation. Page size, migration granularity, remote-access policy, caching, and interconnect vary. M02's segment count predicts neither page faults nor migrated bytes.

## Prefetch and advice are not placement proofs

`cudaMemPrefetchAsync` requests that a range be prefetched toward a declared location using stream ordering. Put the consuming work after that operation in the same stream or connect it with a documented event edge. The call can move work earlier and may reduce demand faults on a suitable system, but it has a cost and does not promise that the range remains resident there forever.

`cudaMemAdvise` communicates usage hints such as preferred location, read-mostly behavior, or expected access. Hints can help or hurt depending on the real pattern and platform. Neither advice nor prefetch replaces synchronization, output verification, or a measurement of actual faults, movement, or residency behavior.

Keep on-demand, advised, and prefetched modes under one correctness oracle. Compare them only after recording the selected Toolkit API contract, destination semantics, capability attributes, and run evidence.

## The applicable system model must be recorded

Current owner documentation distinguishes full support for explicit managed allocations, full support for all allocations with software coherence, full support for all allocations with hardware coherence, and limited support. Native Linux is this site's only Supported Environment, but native Linux systems can still differ by kernel, driver, GPU, and interconnect.

Record at least the selected device and the results for `cudaDevAttrConcurrentManagedAccess`, `cudaDevAttrPageableMemoryAccess`, and `cudaDevAttrPageableMemoryAccessUsesHostPageTables`. Record `cudaDevAttrDirectManagedMemAccessFromHost` when a host-direct-access claim depends on it. Add operating-system and kernel versions, driver, Toolkit Lane, CPU-GPU topology, allocation API, access sequence, and synchronization boundaries.

Those facts select a permissible model. They do not supply a migration timeline or guarantee that a particular page moved.
