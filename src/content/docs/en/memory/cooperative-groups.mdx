[Cooperative Groups (TERM-105)](/en/glossary/#term-105) makes a collaborating [thread group (TERM-106)](/en/glossary/#term-106) an explicit handle. Every [collective operation (TERM-107)](/en/glossary/#term-107) is interpreted against that handle's membership, scope, participants, and argument contract. This representation makes synchronization composable without turning an assumed warp or the whole grid into the default scope.

## What you should be able to do

- State a group handle's membership, synchronization scope, and required participants before using it.
- Use `this_thread_block` as the stable block-wide baseline and partition it with `tiled_partition` collectively.
- Apply `sync`, reduce, scan, and related collectives only when the named group participates correctly.
- Enforce the group-wide argument contract while recognizing arguments explicitly allowed to vary by thread.
- Keep `coalesced_threads` within its dynamic active-set boundary and grid synchronization behind a cooperative-launch gate.

## The four-part group contract

Before calling a group operation, write four fields:

| Field | Review question |
| --- | --- |
| handle | Which object names the group at this call site? |
| membership | Which threads belong to that exact group instance? |
| scope | Which threads and memory effects can this operation coordinate? |
| participants | Which members must reach this construction or collective call? |

Passing the handle into a helper exposes the contract at the function boundary:

```cpp wrap
template <class Group>
__device__ void publish_then_sync(const Group& group, int* shared_value, int value) {
  if (group.thread_rank() == 0) *shared_value = value;
  group.sync();
}
```

The caller must supply a group whose members can legally access `shared_value`, and every required participant must call the helper. A templated signature makes the algorithm composable; it does not make every group type semantically interchangeable.

## `this_thread_block`: the stable baseline

`cooperative_groups::this_thread_block()` returns a `thread_block` handle containing all threads in the caller's block. Its `thread_rank()` and `num_threads()` describe membership. Its `sync()` is a block-group collective: all member threads must participate, all reach the point before any proceeds, and documented pre-sync memory accesses become visible to group members after the point.

```cpp wrap
namespace cg = cooperative_groups;
cg::thread_block block = cg::this_thread_block();
block.sync();
```

This block-wide handle is the baseline for M12 because launch geometry already defines its membership and ordinary kernels can use it. Explicitly passing `block` to a helper is safer to review than hiding a block barrier inside a function whose caller contract says nothing about participation.

## `tiled_partition`: collective construction of subgroups

`cg::tiled_partition<32>(block)` partitions the parent block into fixed-size, one-dimensional row-major tiles and returns each caller's tile handle. The partition operation is itself collective over the parent group. Every member of `block` must participate; constructing the tile only in a branch reached by some block threads can deadlock or corrupt data.

```cpp wrap
cg::thread_block block = cg::this_thread_block();
auto tile = cg::tiled_partition<32>(block); // reached by the complete parent block

if (tile.thread_rank() == 0) {
  // one leader per tile
}
tile.sync(); // all members of this tile participate
```

Review tile size against the documented API constraints and parent size. After partitioning, `tile.sync()` names only the tile, not the parent block. The handle changes both membership and synchronization scope.

## Synchronization and collectives use the named group

`group.sync()` is a collective barrier for the threads named by `group`. Cooperative Groups also supplies collectives such as reduce and inclusive/exclusive scan for supported group types. In every case, the group handle identifies the participant set; source proximity, warp membership, or matching branch text does not enlarge it.

For a tile reduction:

```cpp wrap
int tile_sum = cg::reduce(tile, value, cg::plus<int>());
```

Every tile member participates in the same collective instance. Each thread may provide its own `value` because that parameter is explicitly the per-thread reduction input. The group and operation must still agree across the collective.

## The group-wide argument contract

For a collective call, all threads in the group must pass the same corresponding argument values unless that API explicitly permits differences. Violating this rule is undefined behavior. Apply the contract argument by argument rather than saying vaguely that "threads call the same function."

For `reduce(tile, value, cg::plus<int>())`:

- `tile` must name the same group instance for all participants.
- `value` may differ because the reduce API explicitly accepts one contribution per thread.
- The operation object must describe the same reduction operation across the group.
- Every tile member must execute that collective instance.

The same-call-site appearance is insufficient if divergent control causes only part of the group to arrive. Participation and argument agreement are separate review columns.

## `coalesced_threads`: a dynamic set boundary

`coalesced_threads()` discovers a `coalesced_group` from threads active at that point in a warp. Construction is opportunistic: the returned members are active, but the API does not guarantee a particular active subset or that those threads remain coalesced throughout later execution. They are brought together for a collective and may diverge again afterward.

Treat the returned handle as a point-specific dynamic set:

```text wrap
branch path -> coalesced_threads() captures active members -> collective on that handle
```

Do not rename it "the warp," assume 32 members, or reuse a membership claim from a different control-flow point. A fresh call after divergence or reconvergence may represent a different group.

## Grid synchronization requires a cooperative-launch gate

A `grid_group` from `this_grid()` can name all threads in one grid, but grid-wide `sync()` is legal only for a cooperatively launched kernel. The host path must:

1. Query `cudaDevAttrCooperativeLaunch` and check a nonzero result.
2. Choose a grid that satisfies the cooperative launch residency/size constraints.
3. Launch with `cudaLaunchCooperativeKernel`.
4. Ensure every grid-group participant reaches each grid collective.

A normal `<<<...>>>` launch is not a substitute for this gate. The Runtime contract also limits the total block count using active blocks per multiprocessor times multiprocessor count. Because this path adds hardware, launch, occupancy, and full-grid participation obligations, M12 does not use grid groups as its baseline. Start with block and tile groups; select a grid group only when an algorithm genuinely requires inter-block synchronization and the gate is reviewable.

## CUDA 13 version boundary

Current CUDA 13 Cooperative Groups supports single-device cooperative grid synchronization, but multi-device Cooperative Groups launch APIs and related references were removed. CUDA 12.9.1 and 11.8 archive pages still contain the already-deprecated `cudaLaunchCooperativeKernelMultiDevice` and multi-grid material. Those archive sections are historical coordinates, not current CUDA 13 guidance.

Do not infer a current multi-device synchronization path from an archived example. This Learning Unit teaches no multi-device Cooperative Groups baseline.
