A CUDA event captures a stream's submitted-work state at a record point. That captured state can become a cross-stream dependency, a host completion observation, or one endpoint of a device-time measurement. Those roles share an event handle but have different API and flag contracts.

## What you should be able to do

- State exactly what `cudaEventRecord` captures and what later stream work it excludes.
- Draw the dependency created by `cudaStreamWaitEvent`.
- Distinguish non-blocking `cudaEventQuery` from host-waiting `cudaEventSynchronize`.
- Track re-record behavior by the event state used at each API-call time.
- Reject elapsed-time use with timing-disabled events and publish only a symbolic formula here.

## Prerequisites

Complete [M07: Streams Replace a Global-Order Mental Model](/en/memory/stream-ordering/) first. You should already draw one ordered chain per explicitly named stream, leave different streams unordered without an edge, and distinguish eligibility from an execution observation.

M08 adds selective edges and device-time semantics. It does not execute CUDA, report a measured duration, or claim a concurrency result.

## Event record: capture one stream prefix

`cudaEventRecord(event_ready, stream_producer)` captures the contents of `stream_producer` at that call. Query, wait, and synchronize operations can then refer to completion of that captured work. Work submitted to the producer stream after the record call does not modify that event state.

In a ledger:

```text
stream_producer: P1 -> record(event_ready) -> P2
captured by event_ready: P1 and the record point
not captured: P2
```

Before its first record, an event represents an empty set of work. A record is asynchronous with respect to the host; calling it is not itself proof that the captured stream prefix has completed.

## Stream wait: add a device dependency

`cudaStreamWaitEvent(stream_consumer, event_ready, 0)` makes work added later to `stream_consumer` wait for the event state selected by that API call. It does not make the host wait, and it does not order producer work submitted after the captured record point.

```text
stream_producer: P1 -> record(event_ready) -> P2
                                      |
                                      v
stream_consumer: wait(event_ready) -> C1
```

The new edge is `P1 -> C1`; there is no inferred `P2 -> C1`. This precision is why an event can express a narrower dependency than a device-wide host synchronization.

## Query and synchronize: two host observations

`cudaEventQuery(event_ready)` is a non-blocking status check. It returns success when all work currently captured by the event has completed and not-ready while captured work remains incomplete, subject to normal error handling.

`cudaEventSynchronize(event_ready)` waits on the host until the event's currently captured work completes. Neither API expands the capture to later producer work. Query asks; synchronize waits. Both must still be checked for returned errors.

## Re-record: replace captured state

Each event API call binds the event snapshot selected for that handle when the call is submitted. A later `cudaEventRecord` updates the handle's snapshot for future calls, but it cannot rewrite a wait that is already queued.

Use a versioned ledger even though the handle name is reused:

```text
E1 = event E recorded after P1
wait W1 refers to E1
E2 = event E re-recorded after P2
query Q2, synchronize S2, and later wait W2 refer to E2
```

The labels `E1` and `E2` are teaching names for states, not separate CUDA handles.

## Timing-disabled events

Dependency-only events can be created with `cudaEventDisableTiming`. Such timing-disabled events still support documented wait, query, and synchronize uses, but they are not valid endpoints for `cudaEventElapsedTime`. If either elapsed endpoint was created with timing disabled, the elapsed call returns an invalid-resource-handle error under the owner contract.

Choose flags from purpose: dependency marker or timing endpoint. Do not create every event as a timing event by habit, and do not attempt to extract time from an event that explicitly disabled it.

## Elapsed time: a device-time measurement

For timing-enabled `start` and `stop` events recorded around an intended region, wait until the stop event is complete and then call `cudaEventElapsedTime`. The only result published here is the formula:

```text
elapsed_ms = timestamp(stop) - timestamp(start)
```

The result is a device-time measurement between the event timestamps, not host wall-clock time. Asynchronous recording means unrelated operations inserted between endpoints can enlarge the measured interval, so endpoint stream, order, and included work belong in the timing contract. This page provides no measured duration and does not turn the formula into concurrency evidence.

## Dependency and timing ledger

For every event use, record:

1. Event handle and creation flags.
2. Recording stream and captured prefix.
3. Record generation when the handle is reused.
4. API-call point for each wait, query, or synchronize.
5. Work ordered after each stream wait.
6. Timing endpoints, included region, and completion boundary when timing is enabled.

This ledger prevents an old wait from silently moving to a later record and prevents a dependency-only event from entering an elapsed-time formula.

## Retrieval check

1. Which producer operations are captured when an event is recorded between `P1` and `P2`?
2. What work does `cudaStreamWaitEvent` delay, and does it block the host?
3. How do `cudaEventQuery` and `cudaEventSynchronize` differ?
4. Which event generation does a wait use if the same handle is re-recorded later?
5. Why can a `cudaEventDisableTiming` event not appear in the elapsed-time formula?
