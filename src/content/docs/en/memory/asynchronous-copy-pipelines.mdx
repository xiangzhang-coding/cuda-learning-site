An [asynchronous copy (TERM-108)](/en/glossary/#term-108) changes how a copy is submitted and completed; it does not remove the shared-memory ownership and synchronization proof learned earlier. A [pipeline (TERM-109)](/en/glossary/#term-109) adds a finite FIFO of reusable [pipeline stages (TERM-110)](/en/glossary/#term-110). Correctness still begins with a simple synchronous phase order, then replaces each boundary deliberately.

## What you should be able to do

- Write the portable synchronous `global load -> shared store -> barrier -> use -> barrier before reuse` baseline first.
- Map one logical batch to `producer_acquire -> cuda::memcpy_async -> producer_commit -> consumer_wait -> use -> consumer_release`.
- State every producer and consumer participant, including bounds-invalid and early-exit behavior.
- Separate CC 7.0+ API availability from the CC 8.0+ hardware-accelerated global-to-shared path and its alignment/type constraints.
- Refuse to infer a particular hardware instruction or copy/compute overlap from source code alone.

## Portable synchronous baseline first

Begin with one shared buffer and an explicit phase ledger:

```cpp
for (int batch = 0; batch < batch_count; ++batch) {
  shared[threadIdx.x] = load_valid ? global[input_index] : neutral;
  __syncthreads();

  if (output_valid) {
    consume(shared);
  }

  __syncthreads();
}
```

The first barrier orders all participating loads before cross-thread use. The second orders all uses before the next iteration overwrites the same storage. Bounds select a value or output action; they do not silently remove a thread from a block-wide barrier. This baseline is portable across the Stable Curriculum's C++17 lanes and remains the fallback when an asynchronous path is unavailable, ineligible, or not justified.

Do not optimize an unproved protocol. First record the source range, destination range, assigned writer for every shared slot, readers of each slot, neutral or validity rule, participants, and next-overwrite point.

## Replace the copy, not the proof

With a pipeline completion mechanism, one batch has this abstract order:

```text wrap
acquire stage -> submit cuda::memcpy_async -> commit stage
              -> wait for that stage -> use completed data -> release stage
```

`producer_acquire()` reserves the pipeline head. Copies submitted after acquire belong to that stage. `producer_commit()` advances the head and publishes that batch to the pipeline sequence. `consumer_wait()` waits for completion of the oldest committed stage selected by the pipeline contract. Only then may the consumer read that stage. `consumer_release()` returns the oldest stage for later acquisition and reuse.

The word “asynchronous” does not authorize early access. Reading or writing the destination, or modifying source data still needed by the copy, before the documented completion boundary creates a race. If threads consume shared values copied by other threads, the design must also include the group synchronization required to make all peer-produced values safe to use; a thread-local completion wait must not be inflated into a block-wide guarantee.

## Stage lifecycle and reuse

For each logical batch, keep a stage ledger:

| state | owner action | permitted shared-buffer action |
| --- | --- | --- |
| available | producer completes `producer_acquire()` | producer may submit copies into the acquired stage |
| committed | producer completes `producer_commit()` | stage is pending; consumers must not read it yet |
| ready | consumer completes the applicable `consumer_wait()` and required group synchronization | declared consumers may read the stage |
| released | all declared consumers finish and collectively complete `consumer_release()` where required | stage may be acquired and overwritten for a later batch |

Multiple stages separate the stage being filled from the stage being consumed. They create an opportunity for overlap, not proof that hardware performed overlap. Prologue, steady-state rotation, and drain must preserve the same batch-to-stage mapping; the final committed batches still need waits, uses, and releases.

Completion before **use** prevents reading an unfinished copy. Completion of all declared reads before **release/reuse** prevents a later producer from overwriting a live stage. These are distinct edges, just as M03's first and second barriers protect different hazards.

## Full participant and convergence contract

For a shared, block-scope pipeline, declare whether it is unified or partitioned, the stage count, the producer set, the consumer set, and each thread's fixed role. Producer operations are collective across the producer set, and consumer operations are collective across the consumer set. Every participant must execute the same required acquire/commit or wait/release sequence for each logical stage. A bounds-invalid participant can submit no useful bytes or choose a neutral/validity path under the selected overload, but it cannot simply return through a collective sequence. A participating thread that must exit early follows the documented `pipeline.quit()` contract before exit.

Pipeline submission is also warp-entangled on the relevant implementation path. Converged threads can coalesce a commit into one actual batch; divergent commits can advance the warp-shared actual sequence more times than each thread's perceived sequence. A later wait can therefore wait for more recent batches than intended. Keep commit operations converged; if preceding control flow diverged, reconverge with a correctly scoped `__syncwarp` before commit. This is a convergence and performance contract, not permission to omit the pipeline's full participant contract.

## Capability, alignment, and type constraints

The `cuda::memcpy_async` overloads using `cuda::barrier` or `cuda::pipeline` are available on CC 7.0+. The hardware-accelerated global-to-shared asynchronous copy path requires CC 8.0+. On eligible CC 8.x paths, copy sizes of 4, 8, or 16 bytes and matching source/destination alignment can enable the asynchronous instruction path; the copied element type must be trivially copyable for that path.

`cuda::aligned_size_t<N>` is a programmer-supplied proof that both pointers meet alignment `N` and that the byte count is a multiple of `N`. Supplying a false proof is undefined behavior. Without a valid compile-time proof, the implementation may need a runtime alignment check or may use a fallback. API spelling, a CC 8.0+ target, and an aligned-looking declaration therefore do not independently prove which instruction was emitted.

This Learning Unit stays with the portable baseline and the `cuda::memcpy_async` plus `cuda::pipeline` staged path. Architecture-specific bulk-copy systems are outside its teaching scope.

## Evidence boundary

Source review can prove participant sets, stage rotation, completion edges, and declared alignment assumptions. It cannot prove that the compiler emitted a hardware asynchronous-copy instruction. That claim requires a pinned build and artifact inspection. It also cannot prove copy/compute overlap or speedup; those require Runtime-Verified measurements with an Environment Manifest, a correctness oracle, explicit timing boundaries, and retained observations.

This page, its visual, and its Exercises execute no CUDA. Compilation, runtime, expected-observation, and recorded-observation arrays remain empty.
