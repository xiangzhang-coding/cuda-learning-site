Page-locked host memory is the CPU-side storage contract required for genuinely asynchronous CPU-GPU copies in this unit. Transfer overlap is a separate execution observation: pinned buffers, asynchronous APIs, independent stream work, and copy-engine capability can make overlap eligible, but only a recorded device timeline can show that intervals actually overlapped.

## What you should be able to do

- Pair each page-locked allocation or registration API with the correct release action and lifetime.
- State why `cudaMemcpyAsync` plus pageable host memory is not an overlap contract.
- Draw a chunk pipeline whose copy, kernel, and buffer-reuse dependencies are correct before asking whether it is faster.
- Separate source-level eligibility, queried copy/compute capability, and observed transfer overlap.
- Preserve a serialized correctness baseline even when the selected hardware cannot overlap copy and compute.

## Page-locked host memory

`cudaMallocHost` and `cudaHostAlloc` create page-locked host allocations that are released with `cudaFreeHost`. `cudaHostRegister` page-locks an eligible existing host range; its matching action is `cudaHostUnregister`, followed by the original allocator's release when that allocation is no longer needed. Allocation and registration are different ownership paths even though both can produce pinned transfer buffers.

Pinning prevents the operating system from paging or relocating the covered physical storage while CUDA uses it. That makes direct asynchronous CPU-GPU transfer possible, but it consumes a bounded host resource. Allocate a reviewed working set before the steady-state pipeline, keep each range valid until its last asynchronous user completes, and release it exactly once. A page-locked allocation issued between otherwise independent work can also introduce synchronization, so it does not belong inside the hot enqueue sequence.

Pinned does not mean device-resident, automatically mapped for every intended access, or already in flight. It is a host-memory property and a prerequisite for this transfer path, not an overlap result.

## Asynchronous copy contract

`cudaMemcpyAsync` adds a transfer to a stream and returns before the transfer necessarily completes. For copies involving CPU memory, the current Programming Guide requires page-locked host buffers for asynchronous behavior. A pageable host buffer may still produce a correct copy, but this unit treats that path as ineligible for an overlap claim because it can fall back to synchronous staging behavior.

Every asynchronous copy therefore carries five records: source and destination ranges, byte count and direction, owning stream, completion boundary, and the earliest legal reuse or release of both buffers. Successful API submission proves none of those buffers are ready for host reuse. Same-stream order or an M08 event edge must connect each producer to its consumer, and the host must wait for the completion that protects verification and cleanup.

## Overlap eligibility is not observation

Copy and kernel intervals are eligible to overlap only when all relevant ordering and resource gates permit it:

1. The operations have no required edge that serializes them.
2. CPU-side transfer ranges are page-locked and remain valid.
3. Copies and kernels are placed in named streams with every real data dependency expressed.
4. The selected device reports compatible asynchronous copy/compute capability.
5. No allocation, default-stream relationship, host wait, or other synchronization point closes the intended window.
6. The runtime has enough applicable resources to schedule the operations.

Passing these gates proves only that the submitted graph permits overlap on a capable system. It does not prove that a transfer used a copy engine, that the kernel left the needed resources available, or that their execution intervals intersected. A profiler or equivalent device timeline from the exact run is the observation boundary.

## Build a correct chunk pipeline first

Partition one logical workload into chunks without changing its result. For each chunk `i`, preserve the data path:

```text
H2D(i) -> kernel(i) -> D2H(i) -> output-ready(i)
```

Place complete chunk chains in a bounded set of named non-default streams. Different chunks may become eligible together, while each chunk remains ordered internally. If a ring slot is reused, add a dependency from that slot's previous `output-ready` event to the next host fill or transfer that overwrites it. The host must not mutate an input chunk before its H2D copy completes or read an output chunk before its D2H copy completes.

The serialized path and the pipeline must use the same logical input, kernel work, output oracle, and error checks. Chunking is correct only if every element is covered once, the tail size is bounded, and buffer ownership is unambiguous. Smaller chunks can expose more pipeline stages but also change launch and transfer overhead; no optimal chunk count follows from the graph.

## Copy engines are capability-bearing resources

A copy engine is a hardware resource that may execute data movement independently of SM compute. Device properties such as asynchronous-engine information describe capability available to the selected device and path. The number and usable directions of engines vary, and current owner documentation does not guarantee that every `cudaMemcpy*` call uses a copy engine.

Record the exact device query and returned value in the Environment Manifest. Treat it as a gate for what could happen, not a timestamped account of what did happen. Even a device with eligible engines can serialize a particular workload because of dependencies, transfer direction, resource contention, staging, or runtime decisions.

## Hardware gate: correctness before overlap

Baseline correctness targets native Linux and the Baseline GPU Capability Tier, compute capability 7.5 or newer with the bounded workload below 8 GB. A device that serializes copies and kernels can still satisfy the correctness contract. The output oracle, API error checks, event dependencies, and release order must pass without assuming overlap.

An overlap observation has an additional gate: page-locked host buffers, a graph that leaves the intended copy and kernel unordered, compatible asynchronous copy/compute capability for the selected device and path, and timeline evidence from that exact run. If any gate is absent, report the correct serialized result and leave overlap unobserved.
