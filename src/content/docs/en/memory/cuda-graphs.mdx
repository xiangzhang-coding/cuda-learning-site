A [CUDA Graph (TERM-111)](/en/glossary/#term-111) records operations and their dependencies separately from execution. Each [graph node (TERM-112)](/en/glossary/#term-112) is an operation, directed edges are dependencies, [stream capture (TERM-113)](/en/glossary/#term-113) is one construction mechanism, and an [executable graph (TERM-114)](/en/glossary/#term-114) is the instantiated object submitted for execution.

## What you should be able to do

- Draw a repeated workload as a directed acyclic graph of operation nodes and dependency edges.
- Keep the explicit Graph API and stream capture as separate graph-construction mechanisms.
- Audit capture prohibitions, invalidation, origin-stream ownership, and cross-stream rejoin boundaries.
- Follow `definition -> instantiate executable -> repeated launch` while preserving external resource lifetimes and explicit completion.
- Classify an update as permitted, restricted, or requiring re-instantiation without making a performance claim.

## Graph model: nodes, edges, and a DAG

A CUDA graph is a directed acyclic graph (DAG). Nodes represent operations such as kernels, memory copies, memory sets, host functions, event records or waits, and child graphs. An edge `A -> B` means B depends on A under that edge's documented semantics. Acyclic means following directed dependencies can never return to the same node.

Edges constrain execution; source layout and node numbering do not. Once all dependencies of a node are complete, the CUDA system may schedule it. Two nodes with no path between them are unordered by the graph. That is eligibility, not evidence that they ran concurrently.

For review, record each node's type, parameters, external resources, incoming edges, outgoing edges, and completion consumer. Reject a cycle, a missing producer-to-consumer edge, or an accidental edge that serializes otherwise independent work before instantiation.

## Ordinary repeated launches as the baseline

Start with the ordinary stream-based loop. On every iteration, the host submits the workload's copies, kernels, event edges, and completion boundary again. Stream order and event waits define correctness for that iteration; repeated source order alone does not create a reusable graph object.

| Submission path | How structure is defined | What the host repeats |
| --- | --- | --- |
| ordinary stream launches | enqueue calls, stream order, and event dependencies made during each iteration | every operation submission and the required completion observation |
| stream capture | execute the stream-based authoring path once in capture mode, then instantiate its derived DAG | `cudaGraphLaunch` of the executable graph plus the selected completion observation |
| explicit Graph API | add typed nodes and dependency edges directly, then instantiate that DAG | `cudaGraphLaunch` of the executable graph plus the selected completion observation |

All three paths need the same external-resource lifetime and output oracle. Graph construction can move repeated setup out of the per-iteration submission path, but this source-level comparison records no launch-overhead reduction or end-to-end speedup.

## Explicit Graph API: construct the DAG directly

The explicit Graph API creates a `cudaGraph_t`, adds typed nodes, and supplies dependencies at node creation or through edge APIs. The program keeps node handles, so it can inspect or update selected node parameters under the API's restrictions. This mechanism is appropriate when the application owns the graph structure and can describe node parameters directly.

Graph definition is not graph execution. Adding a kernel node does not launch the kernel, adding a memory node does not move bytes, and a valid DAG does not establish that its external pointers or callback data will remain live through a future launch.

## Stream capture: derive a graph from stream-based work

Stream capture brackets an existing stream-based sequence with `cudaStreamBeginCapture()` and `cudaStreamEndCapture()`. While a stream is in capture mode, supported operations submitted to it are appended to a capture graph rather than enqueued for execution. Ending capture successfully returns a `cudaGraph_t` template.

Capture is a different construction mechanism, not a second execution mode. It derives nodes and edges from stream order and captured event dependencies. Explicit Graph API calls and capture may produce equivalent DAGs, but their authoring, error, and ownership boundaries differ.

## Capture prohibitions, invalidation, and rejoin

The stream that begins capture is the **origin stream**, and capture must end on that same stream. A captured event can fork work into another stream through an event wait. Every additional stream joined to the same capture graph must be joined back to the origin stream before `cudaStreamEndCapture()`; otherwise the overall capture fails.

During active capture, it is invalid to query or synchronize a captured stream or captured event, or a broader device/context handle that encompasses the capture. Prohibited legacy-stream interactions, synchronous APIs such as `cudaMemcpy()` in the documented capture context, attempts to merge separate capture graphs, and unsupported capture operations must not be hidden inside a captured library call.

An invalid operation invalidates the associated capture graph. Further use of its capturing streams or captured events is invalid until the program calls `cudaStreamEndCapture()` to leave capture mode. That end call reports an error and returns a null graph. Error handling must therefore preserve the origin stream, finish the failed capture boundary, discard the null result, and avoid instantiation.

## Definition, instantiation, and repeated launch

Graph work submission has three distinct stages:

1. **Definition:** create a graph template with either the explicit API or stream capture.
2. **Instantiation:** validate and snapshot the template with `cudaGraphInstantiate()`, producing a `cudaGraphExec_t` executable graph.
3. **Execution:** submit that executable with `cudaGraphLaunch(graphExec, stream)` as often as the application contract permits.

Instantiation is not a launch, and launch is asynchronous with respect to the host. Repeated launch reuses the instantiated structure; it does not re-run capture and does not imply that previous launches have completed. Every API result still needs its immediate error check, and asynchronous work still needs a declared completion observation.

## Resource lifetimes and explicit completion

Graph and executable handles do not make external resources immortal. A node's device allocations, host buffers, kernel/module state, event or semaphore objects, host-function callback data, and pointer pointees must satisfy the selected node API's lifetime and accessibility contract through every launch that can use them. Capture-only objects must also remain valid until capture ends successfully or is unwound after invalidation.

Treat each `cudaGraphLaunch` as submitted stream work. Record an event after the launch or synchronize the containing stream at the intended host boundary. Only after that completion may the host consume copied-back data, release resources used by the launch, or destroy the executable under the chosen teardown contract. Destroying a graph template or executable handle is not a substitute for proving completion of external resource use.

Use a lifecycle ledger:

| object | created/selected | last graph use | completion boundary | release action |
| --- | --- | --- | --- | --- |
| `cudaGraph_t` template | explicit construction or successful capture | instantiation or later update source | host API completion | `cudaGraphDestroy` when no longer needed |
| `cudaGraphExec_t` | successful instantiation | final graph launch | final launch's explicit stream/event completion | `cudaGraphExecDestroy` |
| external storage/handles | allocation or creation | last node use in the final relevant launch | completion covering that node | matching free/destroy API |

## Updates are bounded

An executable graph is a snapshot, not a freely mutable workflow. Whole-graph `cudaGraphExecUpdate()` is bounded by topology identity, dependency ordering, node-type, context, and parameter restrictions. Individual executable-node update APIs support only their documented node types and parameter changes. Updates affect subsequent launches, not launches already submitted.

Classify each requested change before applying it. A compatible parameter update may use a documented update API. A topology change, node-type change, or rejected update requires a new valid graph and re-instantiation. Always inspect the returned update status; never assume an attempted update succeeded or silently broaden its contract.

Neither a reusable executable nor a successful update is a performance result. Launch-overhead, end-to-end time, and any concurrency claim require separate measurement.
