## PB-R0-001: Repair an Evidence Status record

- **ID and Publication Pair:** PB-R0-001 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Core mental models; foundational.
- **Prerequisite:** [O02: Recording Evidence Honestly](/en/start/evidence-status/).
- **Hardware gate:** None; analyse a text record only.
- **Related Learning Unit:** O02.
- **Last reviewed:** 2026-08-26.

**Prompt:** A release note says: “The Linux build was skipped after the container registry timed out. A contributor pasted `PASS` from a personal GPU, so the project is Compile-Checked and Runtime-Verified. Web tests also prove that the browser explainer counts as a CUDA run.” Rewrite it as an honest record.

**Constraints:**

- Use only O02's controlled Evidence Status values.
- Invent no manifest, build log, observation date, or maintainer reproduction.
- Keep expected observations separate from recorded observations.

**Expected evidence:** A sentence-by-sentence status repair naming the evidence available for each claim, the missing material, and the status that remains.

**Acceptance criteria:**

- A blocked build has no Compile-Checked.
- A community `PASS` without a complete Environment Manifest, logs, criteria, and date grants no Community-Observed.
- No Runtime-Verified appears before maintainer reproduction; Pending Hardware Verification remains when GPU behavior is required.
- Web tests and browser models grant no CUDA Evidence Status.

<details><summary>Hint 1</summary>For every sentence, ask who did what and which reviewable artifact remains.</details>

<details><summary>Hint 2</summary>Blocked is not passed, and one `PASS` line is not a complete community report.</details>

**Solution:** “The declared compile work did not run because the container registry timed out, so there is no Compile-Checked. The community supplied an incompletely recorded `PASS` with no manifest, logs, criteria, or date, so Community-Observed cannot yet be assigned. Maintainers have not reproduced the subject in a declared Reference Environment; if acceptance requires GPU behavior, the runtime axis remains Pending Hardware Verification. Web-quality tests validate the site and grant no CUDA status. Neither expected nor recorded observations have a qualifying record.”

**Common errors:** Assigning status after calling the job blocked; omitting a manifest to be polite to a contributor; treating web CI as a CUDA compile; removing Pending Hardware Verification without maintainer evidence.

**Source basis:** The site's original [O02 contract](/en/start/evidence-status/) and the separation of compile and run phases in NVIDIA `nvcc` 13.3.1 [supported phases](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#supported-phases).

## PB-R0-002: Complete a manifest and repair a support claim

- **ID and Publication Pair:** PB-R0-002 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Debugging and correctness; foundational.
- **Prerequisite:** [O03: Reading an Environment Manifest](/en/start/environment-manifest/).
- **Hardware gate:** None; use a hypothetical record and run no CUDA.
- **Related Learning Unit:** O03.
- **Last reviewed:** 2026-08-26.

**Prompt:** A record contains only “8 GB GPU, CUDA 12, WSL, kernel 0.2 ms” and claims “complete tier; this site supports the environment.” List the missing manifest fields and repair both conclusions.

**Constraints:**

- Do not guess GPU model, compute capability, driver, Toolkit patch, or measurement method.
- Cover correctness and performance fields, but leave result unobserved.
- Apply only O03's Supported Environment and GPU Capability Tier definitions.

**Expected evidence:** A missing-field checklist, two repaired support and tier conclusions, and a note that isolates the method-free performance text as unreviewed raw input.

**Acceptance criteria:**

- The manifest separates GPU identity, compute capability, GPU count, driver, Toolkit, components, NVCC, host compiler, OS, workload and shape, memory, permissions, exact command, correctness, and observation date.
- The performance appendix has baseline, hypothesis, clocks or power, warm-up, synchronization, timer or profiler version, statistics and sample method, and interpretation boundaries.
- The conclusion states that WSL is not this site's Supported Environment and 8 GB alone cannot select the Modern Single-GPU Capability Tier.

<details><summary>Hint 1</summary>Split “CUDA 12” into Toolkit patch, driver, and relevant component versions.</details>

<details><summary>Hint 2</summary>`0.2 ms` is uninterpretable without synchronization, tool version, samples, and baseline.</details>

**Solution:** Create hardware, software, workload, execution, correctness, date, and performance groups. Mark every unknown “to collect” and name a query method. Move `0.2 ms` to unreviewed raw text and leave result empty. Repair support to: “Native Linux is the only Supported Environment; WSL is an unsupported comparison.” Repair the tier to: “Modern Single-GPU requires compute capability 8.0 or newer, at least 8 GB, and the required count, features, and permissions; the current record cannot decide.”

**Common errors:** Treating “CUDA 12” as a complete software coordinate; replacing compute capability with memory capacity; accepting latency without synchronization; converting NVIDIA product support into this site's responsibility.

**Source basis:** The site's original [O03 contract](/en/start/environment-manifest/), NVIDIA [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html), and the CUDA Programming Guide [compute capabilities](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html).

## PB-R0-003: Review an indexing prediction before execution

- **ID and Publication Pair:** PB-R0-003 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Concepts and implementation; foundational.
- **Prerequisite:** [F01: From Prediction to a First CUDA Kernel](/en/foundations/first-cuda-kernel/).
- **Hardware gate:** None; use static reasoning only.
- **Related Learning Unit:** F01.
- **Last reviewed:** 2026-08-26.

**Prompt:** For one-dimensional vector addition with `N = 65` and `blockDim.x = 32`, give the block count, total launched thread count, final valid index, and bounds state of `threadIdx.x = 0` and `1` in the final block. Explain why a bounds check remains necessary.

**Constraints:** Write equations first, run no program, use zero-based indices, and do not equate launch extent with logical data extent.

**Expected evidence:** A coordinate table and an ownership explanation of no more than five sentences.

**Acceptance criteria:** Derive 3 blocks, 96 launched threads, and final valid index 64; identify local thread 0 in the last block as valid and 1 as out of bounds; explain that 31 out-of-bounds threads must skip access.

<details><summary>Hint 1</summary>Use `ceil(65 / 32)` for block count.</details>

<details><summary>Hint 2</summary>The final block has `blockIdx.x = 2`, so its global indices start at 64.</details>

**Solution:** `ceil(65 / 32) = 3`, giving 96 launched threads. The final valid element is index 64. Local thread 0 in the final block has global index 64 and is IN BOUNDS; local thread 1 has global index 65 and is OUT OF BOUNDS. Every remaining local thread is also out of bounds, so the kernel must guard access with `index < N`.

**Valid alternative:** A number line or VIS02-style static coordinate table is valid when equations and bounds reasons remain reviewable.

**Common errors:** Rounding down to two blocks, treating index 65 as the final element, or believing surplus threads were not launched.

**Source basis:** The original indexing model in [F01](/en/foundations/first-cuda-kernel/) and [VIS02](/en/visuals/indexing/), plus NVIDIA [Introduction to CUDA C++](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/intro-to-cuda-cpp.html).

## PB-R0-004: Repair incomplete error and correctness boundaries

- **ID and Publication Pair:** PB-R0-004 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Debugging and correctness; foundational.
- **Prerequisite:** [F01](/en/foundations/first-cuda-kernel/).
- **Hardware gate:** None; review a hypothetical flow.
- **Related Learning Units:** F01 and O02.
- **Last reviewed:** 2026-08-26.

**Prompt:** A program checks only `cudaMalloc` and final output text, then claims “no error and GPU-correct.” Write the missing boundaries and define the acceptance rule for one element.

**Constraints:** Use EX02's declared Runtime flow and tolerances, invent no output, and separate API success from numerical correctness.

**Expected evidence:** An execution-ordered checklist and one computable numerical acceptance condition.

**Acceptance criteria:** Include three allocations, two H2D copies, launch error, synchronization, D2H copy, CPU comparison, and three frees; accept when absolute `1e-5` or relative `1e-5` passes; explain why one output line cannot replace these checks.

<details><summary>Hint 1</summary>Launch return and kernel completion are separate boundaries.</details>

<details><summary>Hint 2</summary>Failure requires both absolute and relative criteria to reject, not either one.</details>

**Solution:** After three `cudaMalloc` calls, check both H2D copies. After launch, call `cudaGetLastError`, then wait and check execution with `cudaDeviceSynchronize`. Check D2H copy, compare each element with an independent CPU reference, and check all three `cudaFree` calls. An element passes when `abs(expected-actual) <= 1e-5` **or** that difference is `<= 1e-5 * max(abs(expected), abs(actual))`. API success and numerical acceptance are both required.

**Valid alternative:** A state machine or sequence diagram may replace the checklist when it preserves the same order and two independent acceptance layers.

**Common errors:** Synchronizing without checking launch, combining tolerances with AND, or treating the host test as a GPU result.

**Source basis:** The canonical error/correctness contract in [F01](/en/foundations/first-cuda-kernel/) and [EX02](/en/examples/vector-addition/), plus NVIDIA [CUDA Runtime API](https://docs.nvidia.com/cuda/cuda-runtime-api/index.html).

## PB-R0-005: Review a LAB02 evidence request

- **ID and Publication Pair:** PB-R0-005 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Evidence review and Lab preparation; foundational.
- **Prerequisite:** [F01](/en/foundations/first-cuda-kernel/), with [O02](/en/start/evidence-status/) and [O03](/en/start/environment-manifest/).
- **Hardware gate:** None; review a text record and run no CUDA.
- **Related Learning Units:** F01, O02, and O03.
- **Last reviewed:** 2026-08-26.

**Prompt:** A LAB02 request contains only “CUDA 13, vector add PASS, 0.01 ms” and asks for Runtime-Verified. Decide which status can be assigned now and list the completion path.

**Constraints:** Do not guess environment patch, GPU, or logs. Do not treat a performance number as correctness. Compile-Checked may refer only to the existing canonical EX02 Lane records.

**Expected evidence:** A status decision, gap list, and pre-run record template.

**Acceptance criteria:** Keep runtime Pending Hardware Verification; grant neither Community-Observed nor Runtime-Verified; require a complete manifest, exact commands, raw logs, date, and criterion result; label unsupported `0.01 ms` as uninterpretable raw text.

<details><summary>Hint 1</summary>A bare `PASS` lacks subject, criteria, environment, logs, and date.</details>

<details><summary>Hint 2</summary>Runtime-Verified also requires maintainer reproduction in a declared Reference Environment.</details>

**Solution:** The request grants neither Community-Observed nor Runtime-Verified; the runtime axis remains Pending Hardware Verification. Completion requires GPU identity, compute capability, count, driver, Toolkit patch, NVCC, host compiler, native Linux, workload, memory, permissions, exact commands, CPU/tolerance criteria, date, exit status, and raw logs. Move `0.01 ms` to uninterpretable raw text without synchronization, tool version, samples, and baseline. Evaluate Runtime-Verified only after maintainers reproduce the predefined criteria in a declared Reference Environment.

**Valid alternative:** A complete community record that meets its criteria may qualify for Community-Observed while Pending Hardware Verification remains. It is still not maintainer reproduction.

**Common errors:** Upgrading runtime because EX02 is Compile-Checked, treating unknown CUDA 13 as the 13.3.1 Lane, or preserving an unsupported performance number as an observation.

**Source basis:** The original evidence contracts in [LAB02](/en/labs/vector-addition/), [O02](/en/start/evidence-status/), and [O03](/en/start/environment-manifest/).

## PB-R1-001: Repair lifetime, build, and error boundaries

- **ID and Publication Pair:** PB-R1-001 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Debugging and correctness; intermediate.
- **Direct prerequisite:** [O04: C++17 Refresher for CUDA Learners](/en/start/cpp17-for-cuda/).
- **Hardware gate:** None; review source and build design only. No GPU is required.
- **Related Learning Unit:** O04.
- **Last reviewed:** 2026-08-26.

**Prompt:** A `.cu` patch saves `data()` from a local `std::vector<float>` in an asynchronous copy task, then returns before the task completes. An RAII owner for a CUDA allocation throws from its destructor when `cudaFree` fails. A `__host__ __device__` helper calls a throwing host-only function. CI compiles only the caller with a host compiler and declares that both host and device paths built. The runtime path wraps a kernel launch in `try/catch` but ignores `cudaError_t`, the launch check, and the completion check. Write the smallest complete repair.

**Constraints:**

- Run no build, sanitizer, or CUDA command, and invent no diagnostic or output.
- Treat pointee lifetime, ownership, build boundaries, and error boundaries independently.
- A raw pointer is a non-owning view. The repair must say when its owner may be destroyed.

**Expected evidence:** An ownership timeline through asynchronous completion, a host/device build-stage table, and an execution-ordered error checklist.

**Acceptance criteria:**

- Identify that destroying the local vector first leaves the saved view dangling. Keep the owner alive through asynchronous completion or establish an explicit completion boundary before scope exit.
- Keep the CUDA owner's destructor non-throwing. Supply an explicit `close` or `reset` path when cleanup failure must remain observable.
- Separate host-only throwing code from the device-safe helper, expose device definitions to the `nvcc` path, and record compilation, optional device linking, and host linking separately. A successful host object proves neither the device path nor execution.
- Check every relevant `cudaError_t` and separate launch error from completion error. A host exception adapter may convert an error only after preserving the CUDA failure details.

<details><summary>Hint 1</summary>Copying a raw pointer copies an address value. It does not extend the vector or allocation lifetime.</details>

<details><summary>Hint 2</summary>`try/catch` observes host exceptions. CUDA Runtime failures first cross return-value, launch, and completion boundaries.</details>

**Solution:** Put the staging buffer and CUDA allocation in an operation owner that lives until a stream event or explicit synchronization confirms completion. The other minimal repair is to synchronize before the local owner is destroyed. Mark every raw pointer as a view and carry its extent and address-space meaning. Make the destructor perform non-throwing best-effort cleanup and expose explicit `close` when cleanup failure must be reported. Split the throwing host adapter from the device helper, compile the `.cu` file and device-visible definitions with `nvcc`, and record any device link separately from the final host link. Check allocation, copy, and other Runtime API results, inspect launch error after launch, and inspect completion at a synchronization or event boundary. Only a host adapter may throw, after retaining the error name, message, and call site. No build artifact proves that a GPU path ran.

**Valid alternative:** Use an operation object that owns asynchronous state, or make the copy complete synchronously within the current scope. Either choice must keep the owner alive through the final legal access and preserve the same build and error boundaries.

**Common errors:** Nulling only one pointer copy; making a non-owning view call `free`; throwing from a destructor; letting host-only `throw` enter the device path; treating host compilation, linking, or zero warnings as CUDA execution evidence.

**Source basis:** The site's original [O04 contract](/en/start/cpp17-for-cuda/), the [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines), NVIDIA [CUDA Runtime API Error Handling](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__ERROR.html), and the [`nvcc` compilation trajectory](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html#the-cuda-compilation-trajectory).

## PB-R1-002: Repair a build record that hides producer failure

- **ID and Publication Pair:** PB-R1-002 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Debugging and reproducibility; intermediate.
- **Direct prerequisite:** [O05: Reproducible Linux Command-Line Work](/en/start/linux-command-line/).
- **Hardware gate:** None; design the record only. No GPU is required.
- **Related Learning Unit:** O05.
- **Last reviewed:** 2026-08-26.

**Prompt:** A script runs `make -C "$build_dir" all 2>&1 | tee "$record_dir/build.log"`, writes the following `$?` to `build.exit`, and reports build success because that value is zero. It also saves the complete `env` and xtrace, but has no literal command, separate stdout and stderr, actual start and end times, or sealing hash. Repair the failure decision and design a minimal public record.

**Constraints:**

- Run no command and fill in no exit status, timestamp, log content, hash, or other invented output.
- Record no secret, token, credential, or unapproved full environment. Xtrace cannot replace literal input.
- The canonical record must preserve command, stdout, stderr, exit status, UTC timestamps, and SHA-256 hash boundaries.

**Expected evidence:** A failure-propagation explanation and an ordered artifact manifest stating when each file is written, closed, and included in hashing.

**Acceptance criteria:**

- Explain that the original `$?` belongs to `tee` by default, so a successful consumer can hide a failed producer. `2>&1` also discards channel identity.
- Before execution, preserve a fixed `command.sh`, NUL-delimited argv, logical and physical working directories, and an allowlisted environment with no secrets.
- Capture UTC time before and after the stage, write stdout and stderr separately, and copy producer status before any other simple command.
- After logs close, hash a fixed artifact list with SHA-256. Do not include `SHA256SUMS` in itself, and do not claim that a hash proves command correctness.
- If the pipeline remains, enable `pipefail`, immediately copy `PIPESTATUS`, and preserve producer and `tee` status separately. A combined log is only a convenience view.

<details><summary>Hint 1</summary>A pipeline's default status comes from its final stage, not from the `make` command you care about.</details>

<details><summary>Hint 2</summary>Copy `$?` or `PIPESTATUS` into a shell variable before running `printf`, timestamp, or hash commands.</details>

**Solution:** The canonical path may remove `tee`. First preserve immutable `command.sh`, `argv.nul`, paths, and the allowlisted environment, then write `started-at.txt`. Run `make` with stdout and stderr redirected to separate files. Immediately execute `build_status=$?`; only then write that value to `build.exit` and capture `ended-at.txt`. After every stream closes, generate `SHA256SUMS` over an explicit list containing command, argv, paths, environment, times, stdout, stderr, and exit files, excluding the checksum file itself. The template defines names and ordering without supplying any unobserved value. Remove complete `env` and any xtrace that could expand credentials from the public record.

**Valid alternative:** If interactive display requires `tee`, use `pipefail` and copy `PIPESTATUS` before the next simple command, recording `make` and `tee` independently. A merged stream cannot recover stdout/stderr identity, so retain separate canonical channel artifacts or explicitly narrow the record's scope.

**Common errors:** Reading `$?` after `printf`; retaining only the aggregate pipeline status; treating a combined log as two channels; hashing files before they close; leaking secrets because a full environment or xtrace seems “more reproducible”; filling a template with a guessed `0` or time.

**Source basis:** The site's original [O05 contract](/en/start/linux-command-line/), the [GNU Bash 5.3 Reference Manual](https://www.gnu.org/software/bash/manual/bash.html), and [GNU Coreutils 9.11](https://www.gnu.org/software/coreutils/manual/coreutils.html).

## PB-R1-003: Classify architecture claims and calculate bounded arithmetic intensity

- **ID and Publication Pair:** PB-R1-003 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Architecture reasoning and quantitative analysis; intermediate.
- **Direct prerequisite:** [O06: Architecture Refresher: Rate, Delay, and Data Movement](/en/start/architecture-refresher/).

```cpp
  output[input_index] = tile[(threadIdx.x + 1) % blockDim.x];
  // The next iteration immediately overwrites tile.
}
```

**Constraints:**

- Preserve a portable C++17 synchronous `load -> __syncthreads() -> use/reuse -> __syncthreads()` baseline and the 32-thread block.
- Every thread participating in the block must reach each barrier in the same loop iteration. Bounds may guard memory access but not barrier participation.
- Use a declared neutral value for an invalid edge load. Run no build or kernel and invent no output, timing, or Evidence Status.

**Expected evidence:** A minimal source repair, a two-iteration participation ledger for valid and invalid lanes, and an explanation assigning a separate role to each barrier.

**Acceptance criteria:**

- Remove the lane-dependent early return. In the edge iteration, lanes 0 through 12 load input and lanes 13 through 31 write the neutral value to their own tile slots before all 32 lanes reach the first barrier.
- Guard the output write with `input_index < n`; an invalid loader still participates in both barriers even though it performs no global input or output access.
- Keep the first barrier between tile writes and any tile read. Add a second barrier after the final tile read and before any lane can overwrite shared storage in the next iteration.
- State that the static repair creates no compilation or runtime observation. EX06's compilation evidence remains empty and runtime remains Pending Hardware Verification.

<details><summary>Hint 1</summary>Replace “invalid lane exits” with “invalid lane contributes the neutral value,” then place the bounds condition only around global accesses.</details>

<details><summary>Hint 2</summary>The first barrier protects reads from incomplete writes; the second protects current reads from next-iteration writes.</details>

**Solution:** One complete repair is:

```cpp
for (std::size_t tile_base = 0; tile_base < n; tile_base += blockDim.x) {
  const std::size_t input_index = tile_base + threadIdx.x;
  const bool valid = input_index < n;

  tile[threadIdx.x] = valid ? input[input_index] : 0.0f;
  __syncthreads();

  if (valid) {
    output[input_index] = tile[(threadIdx.x + 1) % blockDim.x];
  }
  __syncthreads();
}
```

In iteration zero, all 32 lanes load valid input. In iteration one, 13 lanes load input and 19 lanes write `0.0f`; all 32 then reach the first barrier, so every tile slot is established before any read. Only the 13 valid output owners write global output. All 32 reach the second barrier, preventing a fast lane from beginning the next load while another lane still reads the current tile. This review does not compile or execute EX06, whose compilation axis is empty and whose runtime is Pending Hardware Verification.

**Valid alternative:** If the algorithm is changed and proved to process exactly one tile per block with no later write to that shared object, the final reuse barrier may be unnecessary. That single-iteration contract is not a justification for omitting the second barrier from the loop above; the neutral edge load and first barrier remain required.

**Common errors:** Returning before a block-wide barrier; placing `__syncthreads()` inside `if (valid)`; leaving invalid tile slots uninitialized; guarding the barrier instead of the memory access; assuming lockstep warp progress replaces a block barrier; omitting the second barrier because the first protected the load.

## PB-R1-016: Distinguish broadcast from conflict and derive 32x33 padding

- **ID and Publication Pair:** PB-R1-016 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Shared-memory bank and layout reasoning; intermediate.

**Prompt:** Use M04's selected fixture of 32 banks, successive 32-bit words, and `bank(word_index) = word_index mod 32`. **Constraints:**

- Derive the unpadded and padded row strides from the declarations. Preserve the logical `32 x 32` payload and account for padding bytes.
- Run no EX06 build, CUDA kernel, timer, or profiler. Infer no latency, throughput, or speedup.

**Expected evidence:** A three-row bank ledger, the modulo derivation for the padded layout, padding-capacity arithmetic, and a corrected evidence/performance statement.

**Acceptance criteria:**

- A has stride 32 in the declaration but every lane requests the identical word index 5 and bank 5. It is a same-address read broadcast, not a 32-way bank conflict.
- B uses word index `32i + 5`; `(32i + 5) mod 32 = 5`, so bank 5 receives 32 distinct words and the selected fixture classifies it as a 32-way conflict.
- C uses word index `33i + 5`; `(33i + 5) mod 32 = (i + 5) mod 32`, which visits all 32 banks exactly once and is conflict-free for this instruction. The extra column adds 32 floats, or 128 bytes, per tile while leaving the logical payload unchanged.
- Reject “32x faster.” The mapping predicts conflict classification only. EX06 has empty compilation evidence and Pending Hardware Verification runtime; neither VIS05 nor host arithmetic is timing evidence.

<details><summary>Hint 1</summary>Count distinct requested word indices inside each bank. Thirty-two requests for one word and thirty-two requests for different words are not the same case.</details>

<details><summary>Hint 2</summary>Because `33 mod 32 = 1`, each successive row advances the selected column by one bank after padding.</details>

**Solution:** A sends every lane to word 5 in bank 5, but there is only one distinct requested word, so the read uses the selected model's broadcast exception. B's row stride is 32 words; lane `i` selects `32i + 5`, and all 32 distinct words reduce to bank 5, giving a 32-way conflict in this fixture. Padding changes the physical row stride to 33 while preserving 32 logical columns. C therefore maps lane `i` to `33i + 5`, whose bank is `(i + 5) mod 32`; the 32 lanes form a permutation of banks 0 through 31, so the modeled instruction is conflict-free. The physical allocation gains `32 * 1 * 4 = 128` bytes. These facts predict neither an elapsed-time ratio nor end-to-end speed: EX06 has not produced a qualifying compile record or GPU runtime observation and remains Pending Hardware Verification.

**Valid alternative:** Transpose or remap the cooperative load/use indices so the same logical values are consumed with a stride relatively prime to 32. The alternative must show its complete word-index and bank derivation, preserve bounds and synchronization, and account for any storage or indexing cost before measurement.

**Common errors:** Calling broadcast a conflict because one bank is named 32 times; counting requests instead of distinct words; keeping stride 32 after declaring 33 columns; claiming padding changes the logical matrix; forgetting the 128-byte capacity cost; converting conflict degree directly into speedup.

## PB-R2-015: Separate histogram atomic correctness, contention, and privatization

- **ID and Publication Pair:** PB-R2-015 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Atomic and privatization correctness review; advanced.
- **Direct prerequisite:** [A04: Privatized Histogram](/en/algorithms/privatized-histogram/).
- **Hardware gate:** None. This reviews exact-count and phase contracts only; it neither compiles nor runs EX13 and executes no GPU.
- **Version gate:** Atomic, shared-memory, and barrier semantics bind separately to the current CUDA Programming Guide v13.3, the 12.9.1 owner guide, or the 11.8.0 archive. The CUB comparison is pinned to CCCL v3.4.2 tagged `DeviceHistogram` source.
- **Related Learning Units and resources:** [M03](/en/memory/shared-memory-tiling/), [M05](/en/memory/synchronization-scopes/), [A04](/en/algorithms/privatized-histogram/), and [EX13](/en/examples/privatized-histogram/).
- **Last reviewed:** 2026-08-30.

**Prompt:** A histogram optimization calls plain `bins[b] += 1` a safe update and then claims global `atomicAdd` eliminates contention. It has only one thread clear one shared bin, lets bounds-invalid threads return before both barriers, performs a non-atomic global merge, and infers speedup from “fewer global atomics.” Repair the correctness and evidence contracts.

**Constraints:**

- Declare the `bin_of` range, out-of-range policy, counter-overflow boundary, exact CPU counts, and sum-of-bins invariant.
- Separate global-atomic correctness, same-address contention, per-block shared privatization, and cross-block merge. Shared updates can still need atomics after privatization.
- Prove the complete `zero -> barrier -> update -> barrier -> merge` sequence, and treat the input distribution only as a contention hypothesis to measure.

**Expected evidence:** An exact histogram oracle, global/shared update-address map, five-stage participant ledger, per-bin merge proof, and a repaired claim with no timing or speedup observation.

**Acceptance criteria:**

- Every valid sample contributes exactly once and the sum of all bins equals the valid sample count. Bin bounds, discard/clamp/reject policy, and counter capacity are explicit.
- The direct baseline uses `atomicAdd` for concurrent global updates to one destination to prevent lost updates. Atomic correctness does not mean hot-bin contention vanished or performance is known.
- Threads clear every shared bin with a stride, and all participants reach the initialization and update barriers. An invalid sample skips only its update and cannot leave the synchronization path early.
- Merging per-block counts into shared global bins retains an atomic cross-block update or uses another proven merge stage. Only an exact match, Environment Manifest, and measurement record can support a performance conclusion.

<details><summary>Hint 1</summary>First ask what a plain read-modify-write loses when two threads hit one bin, then place correctness and waiting cost in separate columns.</details>

<details><summary>Hint 2</summary>Check whether every shared bin is zeroed, who reaches both barriers, and whether multiple blocks ultimately write the same global address.</details>

**Reviewed solution:** The repaired global baseline completes bin initialization before each valid sample atomically increments one valid global bin. In the privatized variant, all block threads stride over and zero shared bins, reach one uniform barrier, perform shared atomic updates to block-private bins, reach a second uniform barrier, and stride over the merge. Because blocks still share global outputs, the merge uses global atomic increments unless a separate merge kernel is proven. The CPU oracle supplies exact per-bin counts and the total-count invariant. Skewed and uniform distributions enter only the future-input ledger; without a runtime record there is no contention-cost or speedup claim.

**Valid alternative:** Retain the simple global-atomic baseline when the bin count is small or shared storage is unsuitable. Per-block partial histograms may instead live in global memory and be reduced by a separate kernel when storage, completion, and the exact merge proof are complete.

**Common errors:** A plain-increment race; equating atomic correctness with no contention; clearing only `blockDim.x` bins; early return by an invalid thread; omitting the post-update barrier; a non-atomic cross-block merge; declaring acceleration directly from fewer global atomic opportunities.

**Source basis:** The site's original [A04 histogram and privatization contract](/en/algorithms/privatized-histogram/), [M05 synchronization boundary](/en/memory/synchronization-scopes/), and [SRC-CUDA-039](/en/sources-and-versions/#src-cuda-039), plus NVIDIA's [CUDA Programming Guide v13.3 Writing SIMT Kernels](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html) and CCCL v3.4.2 tagged [`device_histogram.cuh`](https://github.com/NVIDIA/cccl/blob/v3.4.2/cub/cub/device/device_histogram.cuh).

## PB-R2-016: Repair numerical-order, FMA, tolerance, and reproducibility claims

- **ID and Publication Pair:** PB-R2-016 in the `practice-bank` Publication Pair.
- **Type and difficulty:** Numerical-contract and reproducibility review; advanced.
- **Direct prerequisite:** [Q02: Floating-point Order, Determinism, and Bitwise Reproducibility](/en/correctness/floating-point-order-reproducibility/).
- **Hardware gate:** None. This is a static operation-graph and claim review only; it does not compile EX11, produce observed bits, or execute a GPU.
- **Version gate:** Associativity, FMA, compiler-option, and deterministic-result decisions bind separately to current CUDA v13.3, the 12.9.1 archives, or the 11.8.0 archives. Product-specific determinism binds only to the CCCL v3.4.2 tagged policy and is not projected onto a custom kernel.
- **Related Learning Units and resources:** [Q01](/en/correctness/cpu-references-tolerances-invariants/), [A02](/en/algorithms/multi-stage-reduction/), [Q02](/en/correctness/floating-point-order-reproducibility/), and [EX11](/en/examples/multi-stage-reduction/).
- **Last reviewed:** 2026-08-30.

**Prompt:** A report sees the final few bits differ between a GPU reduction and CPU serial reference and declares a race. It describes FMA as identical to separate multiply and add with two roundings, chooses one universal epsilon after seeing the candidate, and labels a single tolerance pass both deterministic and bitwise reproducible across GPUs. Rebuild the numerical and evidence contracts.

**Constraints:**

- Draw exact operation graphs for the CPU fold and GPU tree, recording type, rounding, and operand order at every node. Diagnose nonassociativity separately from a race.
- Separate one-rounding FMA `rn(a*b+c)`, the two-rounding sequence `rn(rn(a*b)+c)`, contraction policy, explicit intrinsics, and compiler flags.
- Justify problem-specific `atol` and `rtol` before inspecting the candidate, then issue three independent verdicts for numerical acceptance, same-scope determinism, and bitwise reproducibility over a named scope.

**Expected evidence:** Two operation graphs annotated with rounding, a compiler and environment ledger, an FMA and contraction decision table, a tolerance rationale, and a blank evidence plan for repeated and cross-scope bit comparisons.

**Acceptance criteria:**

- `(1e20f + -1e20f) + 3.14f` and `1e20f + (-1e20f + 3.14f)` illustrate binary32 nonassociativity. Their difference alone proves neither a race nor that either result satisfies the application contract.
- Rounding counts for FMA and separate multiply/add, implicit contraction, and explicit FMA are recorded separately. `--use_fast_math` is not abbreviated as “turn on FMA only.”
- Finite comparison uses `abs(g-r) <= atol + rtol*abs(r)`. Thresholds are chosen in advance from scale, precision, reduction length and tree, conditioning, and error budget, with separate NaN, infinity, and signed-zero policy.
- A tolerance pass grants numerical acceptance only. Determinism fixes same-input, build, device, launch, library, run scope, and equality predicate; bitwise reproducibility separately names exact bits, environment, and comparison scope and is not projected automatically across Toolkits or GPUs.

<details><summary>Hint 1</summary>Draw the parentheses around every addition and multiply-add first. The same inputs do not imply the same floating-point operation sequence.</details>

<details><summary>Hint 2</summary>Write one predicate and artifact set for each of “numerically acceptable,” “same over repeated runs,” and “bit-identical across the declared environments.”</details>

**Reviewed solution:** The repaired report preserves the differing pairings in the CPU left fold and GPU tree and records rounding at every step; it reports a race only if a separate memory-order defect exists. The FMA row records one rounding and the separate row records product and sum roundings while preserving `--fmad`, `--use_fast_math`, target, and explicit-intrinsic fields. The comparator fixes its abs-plus-rel rationale and non-finite policy before the candidate. The final table separates one numerical pass, repeated-run bit equality for one executable, and bitwise comparison across named builds and devices. No repeated output or cross-environment artifact exists, so the last two remain unobserved.

**Valid alternative:** If requirements need only numerical correctness, stop at the problem-specific tolerance verdict. If a narrower bitwise claim is required, fix one operation graph, explicit FMA policy, exact build, device, input, and bit comparator, then verify that scope with retained repeated-run records.

**Common errors:** Calling nonassociativity a race; assuming a parallel tree equals a serial fold; treating FMA as two roundings; ignoring compiler defaults; tuning epsilon afterward; treating tolerance acceptance as determinism; projecting one-device repetition across architectures; applying a CCCL policy to any kernel.

**Source basis:** The site's original [Q02 order, FMA, and reproducibility contract](/en/correctness/floating-point-order-reproducibility/), [Q01 comparator contract](/en/correctness/cpu-references-tolerances-invariants/), [A02 tree-order model](/en/algorithms/multi-stage-reduction/), and [SRC-CUDA-040](/en/sources-and-versions/#src-cuda-040), plus NVIDIA's [Floating Point and IEEE 754 v13.3 Operations and Accuracy](https://docs.nvidia.com/cuda/floating-point/index.html#operations-and-accuracy) and CCCL v3.4.2 tagged [`DeviceReduce` determinism contract](https://github.com/NVIDIA/cccl/blob/v3.4.2/cub/cub/device/device_reduce.cuh).
