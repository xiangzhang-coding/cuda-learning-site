LAB07 is a Lab. Outside the website, you inspect four EX16 defect/corrected executable pairs in isolation. Each process lets one Compute Sanitizer tool observe one scenario. The site executes no CUDA and publishes no sanitizer transcript.

## Lab contract

| Coordinate | Requirement |
| --- | --- |
| Difficulty and time | Intermediate, about 120 minutes |
| Prerequisites | Q03 and Q04 |
| Supported Environment | Native Linux only; exactly one CUDA GPU with compute capability 7.5 or newer |
| Toolkit Lane | CUDA 11.8.0, 12.9.2, or 13.3.1 under C++17; use that Lane's `compute-sanitizer` |
| Workload | One executable in each process; no process exceeds 128 bytes of problem memory |
| Tool order | Run memcheck first, then racecheck, initcheck, and synccheck; each tool runs only its matching pair |
| Permissions | Execute build tools, eight binaries, shell, and Compute Sanitizer; permit tool launch/instrumentation of a learner-owned child; write separated logs/statuses; no profiler performance counter required |
| Acceptance | A defect produces its predeclared targeted report class; corrected passes exact host reference and has no such targeted report |
| Evidence | Compilation is empty; runtime is Pending Hardware Verification; recorded observations are empty |

## Prerequisite check

1. Complete [Q03](/en/correctness/memcheck-invalid-memory-access/) and explain memcheck's executed-path scope and why a clean report does not prove the absence of other defects.
2. Complete [Q04](/en/correctness/racecheck-initcheck-synccheck/) and distinguish a shared-memory hazard, uninitialized device global memory, and synchronization primitive misuse.
3. Confirm that you can enforce **one scenario per process** and retain separate tool/application logs and statuses.

Save raw stdout/stderr and exit status for every command; record a blocker and stop on failure. `make host-test` checks only the host metadata/reference utility and runs no GPU or sanitizer. A local build does not populate empty compilation evidence.

## Verify correctness

Before interpreting any sanitizer report, directly run the four corrected executables as separate processes:

```sh
for scenario in \
  memcheck-corrected racecheck-corrected \
  initcheck-corrected synccheck-corrected
do
  ./build/"$scenario" \
    >"lab07-evidence/direct-${scenario}.stdout.log" \
    2>"lab07-evidence/direct-${scenario}.stderr.log"
  status=$?
  printf '%s\n' "$status" \
    >"lab07-evidence/direct-${scenario}.status"
done
```

Every corrected process must pass exact comparison against its independent host reference, all required CUDA boundaries, and zero application status. A printed `PASS` alone cannot replace raw stdout/stderr, status, and criterion-by-criterion review. Correctness is a precondition before interpretation; a failing corrected path is not repair evidence.

A defect process is not promised to exit zero because its fault may make completion fail. Preserve its application status without treating nonzero as the targeted tool report or zero as a clean tool run.

Fill variables and run this template separately for each row. `--log-file` retains tool output; the child shell separates application stdout/stderr and application status; the outer shell saves tool status:

```sh
tool='<fill matching tool>'
scenario='<fill scenario>'
binary="./build/${scenario}"
prefix="lab07-evidence/${scenario}"

compute-sanitizer --target-processes all --tool "$tool" \
  --log-file "${prefix}.tool.log" -- \
  sh -c '
    binary=$1
    stdout_path=$2
    stderr_path=$3
    status_path=$4
    "$binary" >"$stdout_path" 2>"$stderr_path"
    application_status=$?
    printf "%s\n" "$application_status" >"$status_path"
    exit "$application_status"
  ' sh "$binary" "${prefix}.application.stdout.log" \
  "${prefix}.application.stderr.log" \
  "${prefix}.application.status"
tool_status=$?
printf '%s\n' "$tool_status" >"${prefix}.tool.status"
```

## Interpret defect/corrected records

Accept each pair only when the defect log contains the predeclared targeted report class, the matching corrected application again passes exact host correctness, and its corrected tool log has no targeted report. A missing defect class is a failure to reproduce; a targeted class in corrected means the correction failed. Exit status alone decides neither outcome because tool `--error-exitcode` policy and application status are separate coordinates.

“No targeted report in corrected” is scoped to this tool, version, build, input, device, and executed path. It does not prove all defects absent and does not let racecheck, initcheck, or synccheck stand in for memcheck. Preserve every additional report class and blocker rather than filtering for a clean table.

This Lab promises no exact diagnostic text, error count, address, thread coordinate, source line, tool exit number, or defect application exit number. It records no timing or performance result.

## Expected observations, not recorded results

- The memcheck defect should fall in the predeclared global-memory bounds report class; corrected should exactly preserve 32 intended writes and have no targeted report.
- The racecheck defect should fall in the shared-memory data access hazard class; corrected should exactly preserve the produced value and have no targeted report.
- The initcheck defect should fall in the uninitialized device-global-memory class; corrected should exactly preserve the initialized increment result and have no targeted report.
- The synccheck defect should fall in the synchronization primitive misuse class; corrected should exactly preserve phase-copy outputs and have no targeted report.

These are expected observations, not recorded results. There is no prefilled or invented runtime output or sanitizer output on this page; `recordedObservations` remains empty.
