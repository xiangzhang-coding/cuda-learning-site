LAB01 is a Lab. You will capture an Environment Manifest outside the website, build and run Runnable Example EX01, and interpret the collected facts as a Reference Environment candidate. The site executes none of these commands and has observed none of your machine. **No Reference Environment is currently declared.**

## Lab contract

| Coordinate | Requirement |
| --- | --- |
| Estimated time | 60 minutes |
| Difficulty | Introductory |
| Direct prerequisites | Complete O03 and O08; O08 already lists O03 among its own direct prerequisites |

Build, hardware eligibility, compatibility, expected observations, recorded observations, and Evidence Status are six independent decisions. Success in any one cannot stand in for another or declare a Reference Environment.

4. Select one Toolkit Lane and a dedicated record directory. It must be outside EX01 `build/` and created with private-by-default permissions.

## Prepare the project and freeze the record

[View the complete EX01 project at its pinned source commit](https://github.com/xiangzhang-coding/cuda-learning-site/tree/5fa2284a3493fc1a51c6ccc5ba709be096e862b8/examples/ex01-environment-report), or [download the source archive for that same commit](https://github.com/xiangzhang-coding/cuda-learning-site/archive/5fa2284a3493fc1a51c6ccc5ba709be096e862b8.zip). This immutable acquisition coordinate binds the displayed ranges and build inputs to one source tree. Record the full commit SHA before entering the project directory:

```sh
git clone \
  https://github.com/xiangzhang-coding/cuda-learning-site.git
cd cuda-learning-site
git rev-parse HEAD
cd examples/ex01-environment-report
```

First create `manifest.md` with field names present and every observed-value cell empty. Reserve fields for source commit, Toolkit Lane, CUDART linkage, OS source path and fields, `uname` fields, loaded KMD, driver-supported CUDA API, Toolkit and components, NVCC, host compiler, build stages, visibility controls, NVIDIA-SMI inventory, EX01 inventory, identity reconciliation, tier, compatibility, candidate decision, UTC date, raw-log paths, and hashes. Empty means the schema is frozen without expected values filled in.

Create `criteria.md` separately and declare before execution that:

1. Every required command retains literal argv, separate stdout/stderr, exit status, and UTC start/finish; a nonzero status or missing field remains a blocker.
2. The OS record follows `/etc/os-release` precedence and never merges the two `os-release` files.
3. The specified EX01 build and host-only targets must complete and exit zero before the GPU run may continue, but this still grants no Compile-Checked status.
4. The hardware stage must make exactly one selected device visible to EX01, every required CUDA query must succeed, and visibility plus any MIG boundary must be retained.
5. The CUDA-visible identity must match the same capture's NVIDIA-SMI identity by UUID or PCI identity, never by ordinal or product name alone.
6. Tier and compatibility are judged by their own rules, followed by exactly one of the three candidate decisions.

Freeze the empty manifest and criteria, then make a working manifest that may receive observations:

```sh
umask 077
: "${LAB01_RECORD_DIR:?set LAB01_RECORD_DIR}"
record_dir="$LAB01_RECORD_DIR"
mkdir -p -- \
  "$record_dir/capture"
cp -- \
  "$record_dir/manifest.md" \
  "$record_dir/manifest.pre-run.md"
sha256sum -- \
  "$record_dir/manifest.pre-run.md" \
  "$record_dir/criteria.md" \
  >"$record_dir/pre-run.sha256"
```

Put collection commands in a fixed script and preserve argument boundaries as NUL-separated argv. Each stage should call `date -u +%Y-%m-%dT%H:%M:%SZ` before and after execution, write stdout and stderr to separate files, and write `$?` immediately after the command. Shell history and xtrace are not literal commands, and a complete inherited environment is not a safe manifest. If command arguments, environment variables, or logs could contain credentials, change the collection design instead of relying on later deletion. Keep the raw record private and hash any publishable redacted copy separately.

## Capture host and software coordinates

The systemd `os-release` contract gives `/etc/os-release` precedence. Use `/usr/lib/os-release` only when the former does not exist, and never merge the two. Save that selection logic as a literal script, execute it as a capture stage, and retain the selected path, resolved path, original file bytes, and exit status. Record the actual presence of at least `ID`, `ID_LIKE`, `VERSION_ID`, `VARIANT_ID`, and `PRETTY_NAME`; an absent optional field must remain absent.

Then capture these separately, never using one to fill another:

```sh
uname -s -r -m
cat /proc/driver/nvidia/version
query_fields="name,uuid,pci.bus_id,driver_version"
query_fields+=",memory.total,memory.free,compute_cap,mig.mode.current"
nvidia-smi \
  --query-gpu="$query_fields" \
  --format=csv,noheader,nounits
nvidia-smi --version
nvcc --version
c++ --version
make --version
cuobjdump --version
```

The kernel name, release, and machine from `uname` are separate fields and do not replace the distribution record. `/proc/driver/nvidia/version` and the selective NVIDIA-SMI query record the loaded driver, while a package name records only installed state. If the current driver does not support a selective field, retain the original command, stderr, and nonzero or unavailable result, then mark the gap under the predeclared rule instead of silently dropping the field.

Also retain the resolved path of the active `nvcc`, the exact path selected by `HOST_CXX`, and Toolkit package/component records relevant to this assessment. NVIDIA-SMI's CUDA UMD value or legacy `CUDA Version` banner describes the API level supported by the driver, not the installed Toolkit. EX01 separately queries the driver-supported API and CUDA Runtime version. Keep NVCC, Runtime, libraries, and tools as component-specific versions rather than compressing them into one "CUDA version."

This section captures host and software metadata only. It proves no build, CUDA-visible hardware, compatibility path, or Evidence Status.

## Reconcile CUDA and NVIDIA-SMI identities

Keep the EX01 run and a time-adjacent selective query in one record, then reconcile them field by field:

1. A CUDA Runtime ordinal is filtered and reordered by `CUDA_VISIBLE_DEVICES`; it is not automatically the NVIDIA-SMI index.
2. Prefer UUID. EX01 encodes the 16 raw bytes as lowercase hexadecimal with two characters per byte and no separators. Normalize the NVIDIA-SMI UUID under that declared encoding before comparing bytes. When both sides expose PCI bus IDs, normalize domain, bus, device, and function format and use that as a second identity check.
3. With MIG disabled, UUID and PCI identity should point to the same physical function. Product-name matching alone is insufficient.
4. With MIG enabled, additionally retain `nvidia-smi -L` and the needed MIG inventory. A MIG instance UUID identifies the selected compute instance. Several instances can share their parent GPU's PCI bus ID, so PCI establishes only the parent relationship and cannot distinguish sibling instances.
5. Container or device-node filtering, permission boundaries, and visibility settings can make EX01's set smaller than NVIDIA-SMI's set. Record that boundary instead of inventing missing devices.

If UUID/PCI normalization still cannot produce one unique match, or the configuration changed between captures, mark reconciliation unresolved and choose `candidate-incomplete`. Never force a match from product name, memory size, or ordinal. Successful reconciliation establishes identity only; it proves no tier, compatibility, or correctness baseline.

## Assign a GPU Capability Tier

Use only the direct compute-capability query, selected visible-device memory, GPU count, required features, and permissions. Record the highest tier whose complete contract is met:

- **Baseline GPU Capability Tier:** compute capability 7.5 or newer, exactly one usable selected GPU, and Stable Curriculum fundamental workloads constrained below 8 GB. EX01 itself needs 0 bytes of problem data, which says only that EX01 fits.
- **Modern Single-GPU Capability Tier:** compute capability 8.0 or newer, at least 8 GB total memory on the selected CUDA-visible device, and the features and permissions required by the single-GPU route. For a selected MIG instance, assess its visible resources rather than borrowing the parent GPU's total memory.
- **No tier:** compute capability below 7.5, a missing required fact, selected count other than one, or an unmet feature or permission gate. Never infer a missing value from the product name.

When Modern applies, note that it also clears the Baseline capability floor, but write only the highest applicable tier in the final field. A tier is curriculum-route eligibility, not a runtime observation or Evidence Status.

Only a completely retained successful baseline run may enter later declaration review.

## Keep observations and Evidence Status separate

### Expected observations

- A successful EX01 report should contain UTC, build, environment-variable, version, count, and per-visible-device observations in one JSON document.
- The one selected CUDA-visible device should reconcile with NVIDIA-SMI by UUID or PCI identity after visibility controls and any MIG boundary are accounted for.

These are pre-run structural expectations with no device values or sample output. Never rewrite them to fit an actual result.

### Recorded observations

This page's recorded observations are empty. Put your raw commands, stdout, stderr, exit statuses, UTC date, manifest, reconciliation, and decision in the external record instead of copying expected text into an observed-result field. Completing the Lab does not automatically add an observation to public-page metadata.

### Evidence Status

| Axis | Current site status | What cannot be inferred |
| --- | --- | --- |
| Compilation | Empty; no Compile-Checked status | A local successful build or host-test cannot upgrade the site's compilation status |
| Runtime | Pending Hardware Verification | EX01's expected structure, a compatibility outcome, or a candidate token is not Runtime-Verified |
| Recorded observations | Empty | Without a reviewed raw record, neither Community-Observed nor Runtime-Verified may be claimed |

A complete learner or community record may be reviewed separately under O02, but it does not automatically change the site's status. Runtime-Verified can be considered only for a named subject that meets predeclared criteria in an already declared, maintainer-controlled Reference Environment. LAB01's environment inventory cannot replace the separately designated baseline.

## Clean up and retain the record

Clean build artifacts without deleting the record outside `build/`:

```sh
make clean BUILD_DIR=build
```

After every log is closed, generate final SHA-256 hashes over a fixed allowlist. Include at least `manifest.pre-run.md`, the filled `manifest.md`, `criteria.md`, capture scripts, every stage's argv/stdout/stderr/exit/timestamps, source commit, reconciliation, and candidate decision. Do not include `SHA256SUMS` in itself. Verify with `sha256sum -c` and retain that command's exit status.

The raw packet can contain sensitive device identity needed for reconciliation and belongs in controlled storage. For publication, create a redacted copy that removes credentials, network identity, real UUIDs, and unnecessary paths, then hash the redacted bytes separately. Never edit the raw files while continuing to cite their old hashes. Do not submit binaries, build directories, complete environment dumps, performance figures, or unreviewed large artifacts.
