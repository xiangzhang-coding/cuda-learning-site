## Lab contract

Implement the row normalization developed in [T03](/en/triton/fused-softmax/), validate it against an independent reference and native framework operation, and record a fair forward-only comparison. Allow 90 minutes plus installation. This activity runs on external Linux, never inside the website. It remains **Pending Hardware Verification**.

## Prerequisites and workload

Exact edges: **[T02, A10, Q05]** — [pointer masks](/en/triton/masked-vector-addition/), [stable softmax](/en/algorithms/numerically-stable-softmax/), [timing asynchronous work](/en/correctness/timing-asynchronous-gpu-work/). T03 is the companion explanation, not an additional hidden edge.

Contract: contiguous rank-2 finite FP32 input/output, FP32 intermediates, forward only, no gradients or semantic attention masks. The host validator rejects wrong rank/dtype/layout, nonfinite values and axes outside 1–4096 rows / 1–2048 columns. Fixed cases are `(1,1), (3,31), (7,32), (5,33), (17,257), (257,1003), (512,2048)`. The four repeating row patterns are equal 1000s, −1000 plus quarter increments, a final 80 among −80s, and mixed half increments. These stored inputs are binary-exact. Do not generalize this gate to BF16, FP16, arbitrary strides or all-masked rows.

CPU oracle objects, CUDA context, compiler, libraries, allocator and `do_bench` cache storage are additional. The 2 GB free gate provides headroom, not an observed peak-memory report. An out-of-memory failure must still stop the run.

## Prepare the source and environment

Use a clean checkout containing `scripts/softmax-verification/`. Record `git rev-parse HEAD`, `git status --short`, and any learner diff. Follow [EX23 setup](/en/examples/triton-vector-add/) to install its hash-locked **full** runtime environment with CPython 3.14.7; its `.venv` can be reused without modifying EX23 source. `compiler.lock` alone cannot run CPU framework or GPU checks. All commands below run from the repository root. Choose an unused external directory:

```sh
PYTHON=examples/ex23-triton-vector-add/.venv/bin/python
RUN_ROOT=$(mktemp -d)
export CUDA_VISIBLE_DEVICES=0
"$PYTHON" -I examples/ex23-triton-vector-add/ex23.py check-environment
"$PYTHON" -m unittest discover -s scripts/softmax-verification -p 'test_*.py'
"$PYTHON" -I scripts/softmax-verification/check.py --mode cpu --output "$RUN_ROOT/cpu"
```

Save every command and exit status. Remove inherited Triton/ptxas overrides and `CUDA_LAUNCH_BLOCKING` before these gates; the checker rejects debugging launch synchronization before CUDA initialization. Do not use interpreter/debug/profiler modes to obtain benchmark evidence. CPU mode checks the independent oracle against FP64 `torch.softmax` without querying CUDA; it is partial progress, not completion of this Lab.

## Implement and predict

In a learner copy, implement `normalize_rows` in `kernel.py` using one program per row. Build power-of-two column offsets, load valid values with negative-infinity fill, subtract the row maximum, exponentiate, sum and divide, then mask stores. Keep its signature and the runner's acceptance rules unchanged. Work from [T03 Exercises](/en/triton/fused-softmax/exercises/) before comparing with the reviewed implementation rendered in T03.

Predict width 33 → tile 64 → 31 masked positions, and `[1000,1000]` → `[0.5,0.5]`. Derive the materialized `4*(8*R*C+4*R)` and fused `8*R*C` logical byte ledgers. Write a hypothesis per shape and a rule for rejecting an inconclusive performance claim. No predicted value is a recorded observation.

## Compile separately

```sh
"$PYTHON" -I scripts/softmax-verification/check.py --mode compile --output "$RUN_ROOT/compile-4" --warps 4
```

This phase checks the compiler subset of the same lock and compiles every fixture width for explicit sm_80, saving TTIR, TTGIR, LLVM IR, PTX and cubin plus hashes. It does not initialize the driver or launch a GPU. A successful command is a local build gate; published compilation evidence remains empty until qualified review. GPU mode later compiles for the actual target, which can differ from sm_80.

## Verify every output before timing

```sh
"$PYTHON" -I scripts/softmax-verification/check.py --mode verify --output "$RUN_ROOT/verify-4" --warps 4
```

The runner checks environment/device/free memory, prepares exact CPU inputs, requests JIT compilation separately, launches each row grid, synchronizes, then copies results for checking. The scalar double oracle uses stored values and compensated summation. Both Triton and native `torch.softmax` must satisfy `abs(error) <= 2e-6 + 2e-5*abs(reference)`, finite probabilities in `[0,1]`, and row sums within `2e-5` of one. Every output is checked. NaN-filled output catches missing stores; an extra 2048-float NaN tail must remain untouched, and input must be unchanged. A guard is not a proof of safe loads.

Failures preserve phase and error in `report.json`, return nonzero and stop the attempt. Inspect masks and reduction order rather than accepting NaN equality or relaxing tolerances. Compiler artifacts and the Linux CPU gate cannot establish this GPU correctness result.

## Measure a fixed candidate fairly

```sh
"$PYTHON" -I scripts/softmax-verification/check.py --mode benchmark --output "$RUN_ROOT/benchmark-4" --warps 4
```

Benchmark mode reruns all correctness gates in its own process before timing. It records the host wall time of each `kernel.warmup` compile request separately, with a new harness-owned cache. No autotuning runs; four warps is a candidate. Twenty device warm-up calls per provider precede synchronization and `do_bench(fn, warmup=25, rep=100, return_mode='all')`. Here warmup/rep are millisecond budgets, not iteration counts. The helper estimates repetitions, clears its benchmark cache before measured calls, records current-stream device events and synchronizes before reading them.

Three rounds run Triton/native, native/Triton, Triton/native. Preserve every raw millisecond sample, median, min/max, shape, dtype, tile and warp count. Both use preallocated outputs and the same input; transfers, allocations, validation, JIT and profiler collection are excluded. Native softmax is already an optimized baseline, not the five-stage materialized ledger. Tiny cases can reflect launch/submission overhead. Repeat the whole experiment under comparable load before making a decision; do not pool unlike shapes or report only the best round.

Optional candidate: repeat compile, verify and benchmark with `--warps 8` into new directories. Record search cost separately and compare all shapes; no configuration is automatically declared a winner. If variability hides a difference, report it as inconclusive. No DRAM counters are collected, so ledger bytes and logical throughput are never measured memory traffic.

After timing, recheck both outputs against the preserved original CPU oracle, input immutability and tail integrity. The report retains these checks and marks a round incomplete until both providers finish; a second-provider failure preserves the first provider's completed samples. An incomplete or failed run cannot support a speedup claim.
