LAB03 is a Lab executed outside the website. You run EX04 in four isolated processes, first locating immediate launch, deferred execution, and host-verification boundaries, then making a deterministic broken stride fail an independent host comparison and accepting the repaired path. The website executes no CUDA and supplies no prefilled runtime output, error code, or numeric exit code.

## Predict first

EX04 places the broken and repaired kernels in one canonical range:

<CanonicalCode exampleId="EX04" range="indexing-kernels" />

Complete a four-row prediction table before running:

1. `launch-config`: identify the stage where `cudaPeekAtLastError` should observe state after the launch expression returns; explain why peek does not clear that state and the later `cudaGetLastError` retrieves and clears it; explicit synchronization follows only after that clear.
2. `deferred-access`: explain why a valid launch configuration should leave the immediate check clear and why the deliberate invalid device access should surface only when `cudaDeviceSynchronize` establishes the completion boundary. The process makes no cleanup or recovery call after the expected deferred failure.
3. `indexing-defect`: for `7 x 5`, write row-major `y * width + x` and the defective column-major permutation `x * height + y`, the total 35 elements, and the 140-byte allocation, then predict the earliest linear host mismatch. Both maps remain inside the allocation, so do not predict an illegal access for this logical defect.
4. `repaired-indexing`: write the row-major map shared with the independent host reference and predict exact acceptance of all 35 elements.

All four rows are pre-run criteria. Do not present an expected stage, status class, or mismatch as observed output, and do not prefill a CUDA error name or numeric error code.
