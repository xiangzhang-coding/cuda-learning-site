LAB11 is a Lab performed outside the website on Native Linux. It compares the [EX11 custom multi-stage reduction](/en/examples/multi-stage-reduction/) with EX17's CUB `DeviceReduce` path through a reviewed single-candidate runner, without assuming that either the library or custom kernel wins. This page publishes only an expected-only measurement contract: compilation evidence is empty, runtime is Pending Hardware Verification, and `recordedObservations` is empty. It contains no actual output bits, error, temporary-storage size, kernel mapping, metric, traffic, timing, speedup, maintenance score, or winner.

| Coordinate | Frozen requirement |
| --- | --- |
| Strict prerequisites | Exactly `Q12, L03`, in that order |
| Related, not prerequisite | `A02, Q01, Q02, Q06, Q08, Q10, L01, L04, EX11, EX17, VIS10` |
| Supported Environment | Native Linux only; exactly one CUDA GPU with compute capability 7.5 or newer |

| Component matrix | Bundled CUB 1.15.1 / 2.8.2 / 3.3.4; selected CCCL 3.4.2 checked only with 12.9.2 / 13.3.1 |
| Workload | EX11 and EX17 share exactly 4,099 deterministic finite `float` values and one `double` oracle |
| Process / stream / completion | One process executes exactly one selected candidate. Each process creates exactly one explicit `cudaStreamNonBlocking` stream, passes that handle to every selected-candidate operation, and uses checked `cudaStreamSynchronize(stream)` for completion. Candidate processes share the policy, not a cross-process handle. |
| Repetition | One excluded warm-up pair per component profile, then ten retained paired attempts; odd pairs run EX11→EX17 and even pairs run EX17→EX11 |
| Permissions | Administrator-approved non-admin performance-counter access; no `sudo`, elevation, driver-policy modification, or bypass |
| Evidence | Compilation `[]`; runtime Pending Hardware Verification; recorded observations `[]` |

`maximumProblemMemoryBytes: 8000000000` is the hard Baseline GPU Capability Tier ceiling, not a prefilled actual allocation. Because one process executes one candidate, the custom process owns 16,396 input bytes plus two 36-byte partial buffers, or 16,468 bytes. The CUB process owns the same 16,396 input bytes, one four-byte output, and `T` queried temporary bytes, or `16,400 + T`. The actual preflight is therefore `max(16,468, 16,400 + T) <= 8,000,000,000`, where `T` comes from the current device, component profile, identical API/template arguments, and 4,099-item shape. Candidate workspaces never coexist. Context, module, allocator, profiler replay, and tool memory are recorded separately and do not enter the problem-memory claim.

## Freeze the 4,099-float correctness contract

Both candidates consume the same input bytes generated once and copied to the device. For `i = 0..4098`:

```text
centered = int((i * 37 + 11) % 101) - 50
coarse   = float(centered) * 0.125F
fine     = float((i * 13 + 3) % 17) * 0.001F
input[i] = coarse + fine
```

The oracle converts each binary32 input exactly to `double` and performs a serial left fold in index order. Each candidate returns one `float` and independently applies:

```text
absolute_error = abs(double(candidate_result) - cpu_reference)
allowed_error  = 1.0e-4 + 2.0e-5 * abs(cpu_reference)
pass           = finite(cpu_reference) && finite(candidate_result)
                 && absolute_error <= allowed_error
```

Every correctness, warm-up, unprofiled-timing, and profiled process checks allocation, API, and launch status; checked completion; a complete four-byte result copy; finite output; and the comparator. Preserve `result_float_bits_hex`, `absolute_error`, `allowed_error`, and `pass` **separately by candidate**, then record `cross_candidate_bits_equal` in its own field. A tolerance pass is not CPU bitwise equality. Equal candidate bit patterns do not replace the double oracle, and different bits are not automatically a failure.
