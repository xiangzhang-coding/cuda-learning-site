This Lab compares the educational EX15 kernel with the EX18 cuBLAS reference **outside the website**. It supplies an executable measurement procedure, not a benchmark result. Compilation evidence is empty; runtime remains **Pending Hardware Verification**; recorded observations are empty.

## Lab contract

Allow **60–90 minutes** with the toolchain already installed: 15 minutes for source and environment checks, 20 for correctness, 20 for measurement, and 15–30 for interpretation. Native Linux is the only Supported Environment. Use one selected GPU with compute capability (CC) at least 7.5 and a problem-memory budget of 8 GB. Tensor Cores are not required.

The required comparison is row-major FP32 `C = alpha*A*B + beta*C`. It covers three small fixtures, not the full production GEMM workload space. The largest fixture needs only `4*(33*31 + 31*35 + 33*35) = 13,052` bytes for device A/B/C. This source-derived capacity excludes the CUDA context and library-managed workspace; record those separately and stop on insufficient memory. The problem fits within 8 GB without claiming a measured process footprint.

Complete exactly [Q13: GEMM Optimization Case Study](/en/correctness/gemm-optimization-case-study/) and [L06: cuBLAS GEMM](/en/libraries/cublas-gemm/), in order. You should be able to explain a partial tile, the double oracle, and why a faster value is not yet an optimization conclusion.

## Match the entire numerical problem

Shape order is **M,K,N**: `A[M,K] * B[K,N] -> C[M,N]`, with contiguous row-major storage and no transpose operation in the mathematical problem.

| Fixture | M,K,N | alpha | beta | Purpose |
| --- | --- | --- | --- | --- |
| `2x3x2-hand` | `2,3,2` | `1` | `0` | Hand-check indexing and operand order |
| `33x31x35-partial` | `33,31,35` | `0.75` | `0.25` | Partial M/N/K tiles and initial C |
| `32x32x32-aligned` | `32,32,32` | `1` | `0` | Aligned control, not a preferred workload |

Use the EX15 generator, not a new random seed. The hand case has A and B flattened as `[1,2,3,4,5,6]` and initial C all zero. Its mathematical result is `[22,28,49,64]`, **a worked oracle value, not recorded GPU output**. The other fixtures use `A[i]=(int(i%7)-3)/8.0F`, `B[i]=(int(i%5)-2)/7.0F`, and initial `C[i]=(int(i%3)-1)/5.0F`. Shape equality alone is insufficient: compare all A/B/initial-C bytes and scalars with EX18 before executing. Both candidates then consume the same device A/B and receive the same initial C before each operation.

cuBLAS interprets those bytes column-major. The adapter computes `C^T = alpha*B^T*A^T + beta*C^T` without materializing transposes: `cublasGemmEx` uses `(transa,transb)=(CUBLAS_OP_N,CUBLAS_OP_N)`, dimensions `(N,M,K)`, first operand `(B,lda=N)`, second `(A,ldb=K)`, and `(C,ldc=N)`. Keep A/B/C `CUDA_R_32F`, compute type `CUBLAS_COMPUTE_32F_PEDANTIC`, handle math mode `CUBLAS_DEFAULT_MATH`, algorithm `CUBLAS_GEMM_DEFAULT`, and host-resident FP32 alpha/beta in `CUBLAS_POINTER_MODE_HOST`. Default math mode alone does not freeze the compute precision; the explicit pedantic compute type matters.

Verify **each full output matrix independently** against double CPU accumulation using `abs(actual-reference) <= 1e-4 + 2e-5*abs(reference)`. Reject non-finite input, reference, or output. A cross-candidate match cannot replace the oracle; a tolerance pass does not promise bitwise identity or reproducibility across library versions. Restore initial C even during warm-up. With nonzero beta, feeding a previous result back as C silently changes the problem.

## Measure and verify every operation

The standalone examples print correctness, not timing. Do not time those processes with `time` and compare the result to events. First run their canonical executables as directed on EX15/EX18, then use the runner:

```bash
date -u +%FT%TZ > "$run_dir/start-utc.txt"
set +e
"$run_dir/lab12-gemm-comparison" > "$run_dir/samples.txt" 2> "$run_dir/errors.txt"
status=$?
set -e
printf '%s\n' "$status" > "$run_dir/exit-status.txt"
date -u +%FT%TZ > "$run_dir/end-utc.txt"
nvidia-smi > "$run_dir/gpu-after.txt"
sha256sum "$run_dir"/*.txt > "$run_dir/logs.sha256"
test "$status" -eq 0
```

For each fixture the runner preallocates A/B/C, creates one explicit `cudaStreamNonBlocking` stream, and binds one cuBLAS handle to it before acquisition. It runs **three excluded warm-up pairs**, then **ten measured pairs**: odd measured pairs EX15 then EX18, even pairs EX18 then EX15. It completes and verifies every operation, including warm-ups. A/B are uploaded once per fixture; C is reset before every candidate.

| Boundary | Required sequence |
| --- | --- |
| Outside timing | Copy original C to the existing device allocation on the selected stream; check `cudaStreamSynchronize` before starting |
| Event interval | Record start on that stream; launch one EX15 GEMM or call one EX18 GEMM adapter; check immediate status; record stop on the same stream |
| Completion | Check `cudaEventSynchronize(stop)`, then `cudaEventElapsedTime`; event creation uses timing-enabled events |
| Outside timing | Copy all C back on the same stream, check completion, run the double oracle comparator, retain the candidate's result status |

The runner emits each raw sample in **milliseconds**, preserving fixture, candidate, pair and order. Summaries use count=10, minimum, median (mean of the sorted fifth and sixth values), and maximum, separately for each fixture/candidate. Warm-up lines carry no elapsed value. A failed API, completion, cleanup, or numerical check makes the run nonzero; retain the failed run and do not use partial summaries. Start a new run after correction, never delete a slow sample or combine runs.

These are **unprofiled GPU event intervals**, not CPU call latency, process wall time, transfer-inclusive latency, or a sum of individually reported kernel durations. cuBLAS may dispatch multiple kernels. Host submission gaps and competing GPU work can affect the interval. The owner API describes roughly 0.5-microsecond event resolution, so these tiny shapes may not resolve a meaningful difference. Keep zeros if actually observed, but do not divide by zero or claim a winner from resolution-limited data. This runner reports no setup-inclusive family: handle creation, allocation, H2D/reset, D2H, verification, and teardown are excluded. Measuring those later requires a separate, identically bounded host-clock experiment for both candidates.

## Optional profiling and precision extensions

Profiling is **not required** to finish the 60–90-minute lab. If timing leaves a mechanism question, follow [Q13's profiling boundary](/en/correctness/gemm-optimization-case-study/) and the matching owner manual in a **separate run**. Query available fields on the actual GPU, obtain authorized counter access, discover actual cuBLAS launches, and preserve the original report plus hashes. Never assume one library call is one kernel or invent a cuBLAS kernel name, occupancy, traffic metric, or Tensor Core result. Profiler durations cannot replace the raw unprofiled event samples. A denied counter is a profiling blocker, not zero; do not use `sudo` or change security policy.

TF32, FP16, BF16, FP8, FP4, emulation, Tensor Core paths, cuBLASLt heuristics, workspace tuning, fusion, and larger shapes are **separate experiments**. Each requires its own hardware/version gate, fallback, numerical contract and matched baseline. The CC 7.5 FP32 gate does not authorize them. L07 is a follow-on for library control, not permission to silently substitute another API here.

## Make a conditional maintenance decision

| Question | Educational EX15 responsibility | EX18/cuBLAS responsibility |
| --- | --- | --- |
| Who owns correctness? | Indexing, tails, barriers, accumulation and epilogue, plus deployment tests | Layout/leading dimensions, precision, scalar/handle/stream lifetime, errors, and the same application oracle tests |
| Who owns upgrades? | Kernel, compiler and architecture regression review | Integration plus exact header/library pins, release-note review and retesting; NVIDIA owns library implementation |
| Who handles incidents? | Source-level diagnosis, tuning and fallback ownership | Reproduce with complete manifest, separate adapter from library issues, upstream escalation and fallback ownership |
| When is extra code justified? | A measured application need that the library contract cannot satisfy, with a funded test/maintenance plan | A matching library contract and acceptable integration cost, not merely a recognizable library name |

Record both candidates' actual ownership costs; the table supplies questions, not scores. If both pass and a resolved timing difference repeats in the declared environment, conclude only that one is faster **for those fixtures under this event boundary**. If results overlap or are resolution-limited, report no resolved winner. Even a local custom-kernel win does not justify replacing a production library, and a cuBLAS win does not make layout, precision or upgrade tests optional.
