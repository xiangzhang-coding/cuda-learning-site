## Lab contract

Profile the installed original [EX22](/en/examples/adjacent-energy/) wheel, implement P11's bounded candidate in a learner copy, and compare both without weakening semantics. Allow 120 minutes plus setup. The website never runs CUDA. Successful runtime completion needs both wheels' checks, traces, measurements and manifest; a CPU-only gate is partial progress. Current runtime status is **Pending Hardware Verification**.

## Prerequisites and source

The exact prerequisite is `[P11]`: [P11](/en/frameworks/profile-led-optimization/) supplies the hypothesis and preserved contracts. EX22 remains canonical; [LAB13](/en/labs/build-custom-operator/) supplies the already-described environment/build/import procedure. The separately invoked dispatch extension below additionally requires [P12](/en/frameworks/sdpa-dispatch-verification/); it is not a hidden prerequisite for LAB14's operator activity.

Use a clean checkout of this Learning Site containing `scripts/framework-verification/check.py`. Record `git rev-parse HEAD` for the harness and original source; EX22's published page retains its immutable canonical archive. Keep learner modifications and wheel outputs separate. Do not substitute an untracked working tree while reporting its clean commit as the full source identity.

## Prepare and predict

Follow LAB13 to prepare the hash-locked environment, build both native paths, and verify isolated installed imports. Unset LD_PRELOAD and legacy PYTORCH_CUDA_ALLOC_CONF; use the checked loader environment and `PYTORCH_ALLOC_CONF=backend:native`. Select one GPU with CUDA_VISIBLE_DEVICES. Preserve exact commands/exits and compiler output externally. From the repository root, set a shell variable to the actual clean source identity:

```sh
SOURCE_COMMIT=$(git rev-parse HEAD)
```

Before running, predict that n=258 has 257 outputs and two 256-thread blocks. State whether you expect launch overhead or device work to dominate at each size, and what would refute that prediction. These are hypotheses, not observed outputs.

## Capture the original baseline

From the repository root in the original wheel's venv:

```sh
PYTORCH_ALLOC_CONF=backend:native python -I scripts/framework-verification/check.py --mode operator --device cuda --source-commit "$SOURCE_COMMIT" --output baseline-round-1
```

The new output directory must not already exist. The harness invokes EX22's canonical verifier, then checks every forward result for n=258,1003,1000000 in float32/float64 against the eager expression. It compares both eager composition and the installed operator; both read the same preallocated finite binary-fraction inputs. Gradients/fake/meta/compile/stream coverage comes from the canonical verifier before timing, not from the forward benchmark.

Each operation warms up 20 calls. Seven unprofiled samples each run 100 calls between current-stream CUDA events; the end event completes before elapsed time is read. Input creation, validation and transfers are excluded, output allocation is included. A separate CPU+CUDA profile records shapes with wait=1, warmup=1, active=2, repeat=1 over four `prof.step()` calls, synchronizing at each diagnostic boundary. Keep profiler overhead out of the unprofiled medians.

## Build and verify the candidate

In a fresh learner copy, apply only P11's 256-to-128 launch change. Extend the canonical verifier with n=128,129,130 in its numerical and gradient boundary set. Commit the learner diff to obtain a distinct source identity, and retain that diff externally. Build/install in a separate clean matching venv using LAB13's wheel script; rerun isolated CPU/CUDA checks and second-venv positive/negative import verification. Preserve both wheel hashes and actual loaded-extension hashes. No changed kernel is published here as a measured winner.

Run the same command from the candidate checkout with its real SOURCE_COMMIT and a new `candidate-round-1` output directory. Repeating the original run with the old installed wheel does not test the candidate. The EX22 source has not changed its accepted dtype, CPU path, autograd registration, fake/meta or packaging contracts.

## Compare and decide

Alternate baseline/candidate process order over at least three rounds, using new directories for every attempt. Match size, dtype, forward/allocation scope, clocks/power policy, competing load and software. Retain all seven samples per case and median/spread; report the ratio only for matched, correct cases. Compare original **operator** rows to candidate **operator** rows. Eager rows explain composition overhead but are not the original native baseline.

Inspect full traces locally: connect framework ranges and original/candidate kernel launches, note gaps, and distinguish requested bytes from measured memory traffic. This activity does not collect DRAM counters. If improvement is lost in variability, smaller shapes regress outside your predeclared policy, or any correctness check fails, keep the original. A correct candidate with no speedup is a valid experimental conclusion.

## Separately gated P12 dispatch extension

After P12, in the same exact application environment, invoke a separate process:

```sh
PYTORCH_ALLOC_CONF=backend:native python -I scripts/framework-verification/check.py --mode sdpa --device cuda --source-commit "$SOURCE_COMMIT" --output dispatch-round-1
```

This does not require modifying EX22. It validates P12's no-mask/dropout/GQA forward fixture against a CPU float64 oracle from rounded inputs, across AUTO and four forced policies. FP16/BF16/FP32/FP64 use P12's fixed tolerances; native BF16 and fused predicates gate trials. Ineligible rows are retained, while execution/numerical failures fail the attempt. Backend event recognition plus device kernels is required, followed by local correlation inspection. It reports requested policy separately from observed events and never derives AUTO from flags alone. No attention backward is claimed.

For a GPU-free tool/oracle check only, use `--mode sdpa --device cpu` in the selected Linux environment with a fresh output directory. It checks MATH float32/float64 and emits no CUDA timings or GPU manifest. It does not complete this Lab or verify CUDA dispatch.
