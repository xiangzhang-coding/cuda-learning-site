EX05 is a standalone, original coalesced-and-strided-access Runnable Example. One C++17 CUDA kernel and one scenario loop cover contiguous, one-element-offset, and stride-two gathers. The website never executes CUDA, and the project reports correctness rather than performance.

## Purpose

Complete M02 first. EX05 turns its global-memory access model into a controlled executable comparison, while VIS04 is the related browser-only Visual Explainer. Neither the host test nor VIS04 executes the kernel or grants CUDA Evidence Status.

The experiment holds element type, logical count, launch geometry, input values, output layout, and verification constant. Only `offset` and `stride` change. That isolation makes the source-index sequence explicit without treating an unmeasured transaction count or runtime difference as a result.

## Scenario contract

All scenarios fix `logicalCount=256` and apply `output[logicalIndex] = input[offset + logicalIndex * stride]`.

| Scenario | Offset | Stride | First warp's source indices | Required input elements |
| --- | ---: | ---: | --- | ---: |
| `contiguous` | 0 | 1 | 0 through 31 | 256 |
| `misaligned` | 1 | 1 | 1 through 32 | 257 |
| `strided` | 0 | 2 | 0, 2, 4, ..., 62 | 511 |

Here, “misaligned” means shifted by one four-byte element relative to the base access sequence; it does not mean an improperly aligned C++ `std::uint32_t` load. The table describes deterministic indices, not measured memory transactions.

For each scenario, the loop computes the independent host result, launches the shared kernel, checks submission, synchronizes, copies all outputs back, and compares each `std::uint32_t`. Its normal output is only `scenario=<identity> result=PASS|FAIL`. There is no event, clock, profiler invocation, or derived rate.

## Host reference boundary

`include/coalesced_strided_access_reference.hpp` is pure C++17. It defines the ordered scenario table, checks multiplication and addition before deriving required input size, rejects an undersized allocation without mutating the caller's source-index destination, writes each reference output, and compares exactly.

`make host-test` validates required counts 256, 257, and 511; representative source indices including lane 31 and logical index 255; out-of-range, undersized, zero-stride, and overflowing cases; and all three complete output arrays. It includes no CUDA header or device annotation. Passing it does not establish that device code compiled or ran.

## Build contract

From the project directory on Native Linux, run:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The first four stages require the selected CUDA Toolkit. Host-test needs only a host C++17 compiler. The CUDA stages create `build/coalesced_strided_access.ii`, `build/coalesced_strided_access.o`, and `build/ex05-coalesced-strided-access`. Inspection checks a native `sm_75` cubin and PTX generated from `compute_75`.

`scripts/compile-check.sh c++17 ex05 <result-dir>` performs those stages and retains sanitized logs plus inspection artifacts. It never runs `build/ex05-coalesced-strided-access`, so a successful build gate supplies no GPU observation.

## Compilation and runtime evidence

EX05's compilation array is empty, so **EX05 is not Compile-Checked**. Build-gate logs are ephemeral workflow artifacts and do not become public Evidence Status records. Runtime remains **Pending Hardware Verification**, and recorded observations are empty.

The page claims no GPU output, transaction count, timing, latency, bandwidth, throughput, profiler result, or speedup. A future runtime record must identify a Reference Environment, include its Environment Manifest, preserve all scenario identities, and satisfy exact output acceptance before any observed behavior can be published.

## Expected observations, not runtime records

1. All three scenarios should report `PASS` only when all 256 outputs exactly match the pure host reference.
2. Per warp, contiguous source indices should be `logicalIndex`, while the misaligned scenario should use `logicalIndex + 1` at the same unit stride.
3. Per warp, the strided scenario should use `2 * logicalIndex`, selecting every second value while staying inside 511 inputs.

These are declared correctness and address-sequence expectations. They contain no performance ordering and remain unobserved by the Learning Site.
