EX04 is a standalone, original error-handling-lifecycle Runnable Example. One C++17 project separates the immediate-after-submission check, the deferred-at-synchronization check, pure host logical verification, and repaired indexing into four single-scenario processes. The website never executes CUDA.

## Purpose

Complete [F05: Separate Immediate Launch Errors from Deferred Execution Errors](/en/foundations/asynchronous-errors/) first. EX04 turns F05's asynchronous-error timeline into the sole executable implementation. [F03](/en/foundations/multidimensional-indexing/) supplies the two-dimensional row-major indexing contract, [F04](/en/foundations/host-device-lifecycle/) supplies the allocation, submission, synchronization, and cleanup order, and [LAB03](/en/labs/break-and-repair-indexing/) then guides learners through the defective and repaired scenarios.

The project deliberately does not place every fault in one long-lived process. Each invocation runs one scenario, preventing an earlier asynchronous error from contaminating the next `cudaPeekAtLastError` and avoiding attempted CUDA-context reuse after a potentially fatal device fault.

## Scenario contract

| CLI scenario | Deliberate condition | First expected classification | Safety boundary |
| --- | --- | --- | --- |
| `launch-config` | A launch configuration exceeding the block thread limit | `immediate-after-submission` | Read and clear last-error state after rejection, then synchronize explicitly |
| `deferred-access` | A valid launch that deliberately dereferences an invalid device address | `deferred-at-synchronization` | Allocate no device buffer; terminate the process immediately after synchronization reports the fault |
| `indexing-defect` | Store `(x,y)` through a column-major permutation of the same allocation | `host-verification` | Keep every position inside 35 elements; do not manufacture the mismatch with illegal access |
| `repaired-indexing` | Use the declared `y * width + x` row-major map | `none` | Compare exactly with the pure host reference after successful synchronization |

These classifications are acceptance directions, not runtime output observed by this site. The executable checks success versus failure at each boundary without treating one specific `cudaError_t` value as a cross-environment guarantee.

## Error lifecycle

This range holds the host-side observation boundaries and cleanup decisions for all four scenarios:

<CanonicalCode exampleId="EX04" range="error-lifecycle" />

`launch-config` calls `cudaPeekAtLastError` immediately after triple-chevron submission. That API reads the last-error state visible to the calling thread without clearing it. `cudaGetLastError` then retrieves and clears the same state, and another peek checks the cleared state. A final `cudaDeviceSynchronize` remains explicit, so the immediate check is not confused with a completion boundary.

`deferred-access` has valid launch geometry. The code first performs the non-clearing immediate peek, then calls `cudaDeviceSynchronize` to wait for preceding work; synchronization is the intended reporting point for the deliberate device access. Because an execution fault may leave the current CUDA context unsuitable for further work, the function terminates after recording the returned status and performs no `cudaFree`, reset, or subsequent kernel launch.

The two indexing paths reach host verification only after `cudaMalloc`, the launch check, explicit synchronization, and D2H copy all succeed. They call `cudaFree` only after successful synchronization and copy-back. Any CUDA failure exits the process and leaves allocation reclamation to process termination rather than attempting cleanup through a potentially damaged context.

## Indexing kernels

The same device source contains the launch-configuration probe, deferred invalid access, and paired defective/repaired indexing kernels:

<CanonicalCode exampleId="EX04" range="indexing-kernels" />

`indexing_defect` is not an out-of-bounds kernel. For every valid `(x,y)` in `width=7,height=5`, `x * height + y` lies in `[0,35)` and forms a complete permutation. The defect is that this map violates the application's declared x-fastest row-major layout. Host verification can therefore isolate a logical mapping disagreement without simultaneously contaminating CUDA error state with an illegal memory access.

`repaired_indexing` changes only the map to `y * width + x`; coordinates, bounds, grid, block, and allocation remain the same. That controlled change lets a host mismatch be attributed to the mapping repair rather than a changed problem size or launch geometry.

## Host verification boundary

The pure host C++17 header defines scenario parsing, stable stage labels, first-failure classification, overflow-safe element counting, both 2D maps, deterministic reference values, and exact verification:

<CanonicalCode exampleId="EX04" range="host-verification" />

`try_element_count` rejects zero extents and checks `std::size_t` overflow before multiplication. Each indexing function validates the extent product and each coordinate before computing an index, leaving the caller's destination unchanged on failure. The host test traverses the `7 x 5` extent, simulates the in-bounds defect and repair, and confirms that the mismatch begins at a deterministic position.

`make host-test` includes no CUDA header, `__host__`, `__device__`, or GPU dependency. It can verify parsing, arithmetic, reference, and classification contracts, but it cannot establish that the CUDA source compiled or that device execution reports a fault at the expected stage.

## Build contract

From the project directory on native Linux, run these stages in fixed order:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The first four stages require the selected CUDA Toolkit. Host-test needs only a host C++17 compiler on the x86-64 CPU. CUDA stages create `build/error_handling_lifecycle.ii`, `build/error_handling_lifecycle.o`, and `build/ex04-error-handling-lifecycle`. Inspection uses `cuobjdump` to confirm a native `sm_75` cubin and forward-compatible PTX generated from `compute_75`.

`scripts/compile-check.sh c++17 ex04 <result-dir>` runs clean, preprocess, compile, link, inspect, and host-test in order, preserving logs and inspection artifacts. It never runs `build/ex04-error-handling-lifecycle`; even a successful build flow creates no immediate, deferred, or host-verification runtime observation.
