EX16 is a standalone, original Compute Sanitizer defect-suite Runnable Example. Eight C++17 CUDA binaries each run exactly one case: four contain one deliberately isolated defect, while four retain the same intended work with a minimal correction. The website executes no CUDA and stores no tool diagnostic or runtime log.

## Purpose

Complete [Q03: Locate Invalid Memory Access with Memcheck](/en/correctness/memcheck-invalid-memory-access/) and then [Q04: Distinguish Racecheck, Initcheck, and Synccheck](/en/correctness/racecheck-initcheck-synccheck/). Q03 establishes that memcheck runs first; Q04 establishes the detection boundaries of the other three tools. [LAB07](/en/labs/diagnose-four-sanitizer-failures/) uses this same EX16 project for guided external execution and evidence capture.

One process executes one case. A CUDA-context state caused by an out-of-bounds access or invalid synchronization therefore cannot enter the next tool run. A defect and its corrected variant keep the same problem size, launch geometry, and intended output. Each pair changes only the condition or omitted operation responsible for its defect.

## Scenario contract

| Tool | Defect category | Minimal correction | Correctness check |
| --- | --- | --- | --- |
| `memcheck` | One global-memory out-of-bounds write | Change `index <= count` to `index < count` | All 32 legal elements match a deterministic sequence |
| `racecheck` | Plain shared-memory RAW ordering hazard | Add one block barrier between producer and consumer | The consumer obtains 42 |
| `initcheck` | Read uninitialized device global memory | Zero the same input allocation before launch | All 16 outputs equal 1 |
| `synccheck` | Divergent conditional `__syncthreads()` | Move the same barrier to a point reached by every thread | All 16 threads retain their phase-copy values |

Every executable checks launch submission, explicit completion, and all defined output. The application's own `PASS` does not replace a tool report. A defect producing its intended value under one schedule does not show that its hazard is absent.

## Host utility boundary

`include/sanitizer_suite_contract.hpp` is pure-host C++17 metadata. In page order, it lists each scenario ID, tool, variant, complete command, and category. `tests/host_utility_test.cpp` checks only the identity, order, uniqueness, and pairing of those five metadata fields.

`make host-test` includes no CUDA header, compiles no `.cu` file, and launches neither a GPU nor Compute Sanitizer. Passing this utility **cannot establish GPU correctness or sanitizer behavior**. It only prevents drift between documented commands and executable identities.

## Build contract

From the project directory on Native Linux, run `make preprocess DIALECT=c++17`, `make compile DIALECT=c++17`, `make link DIALECT=c++17`, `make inspect DIALECT=c++17`, and `make host-test DIALECT=c++17`. The first four stages process all eight binaries. Host-test needs only a host C++17 compiler on x86-64.

Every CUDA source produces one `.ii`, one `.o`, and one hyphenated executable of the same identity. Inspection checks every executable for a native `sm_75` cubin and forward-compatible PTX generated from `compute_75`. `scripts/compile-check.sh c++17 ex16 <result-dir>` performs only those build stages and the host utility. It never launches a CUDA executable or Compute Sanitizer.

## Compatibility and exact gates

**Hardware gate:** Building needs an x86-64 CPU, a host C++17 compiler, and the selected CUDA Toolkit. Runtime belongs only to the Native Linux Supported Environment and requires exactly one CUDA GPU with compute capability 7.5 or newer. No process uses more than 128 bytes of declared global-plus-shared problem memory, below the Baseline GPU Capability Tier's 8 GB boundary.

**Tool gate:** Use the `compute-sanitizer` delivered by the selected Toolkit Lane and record its actual version. Run `memcheck` first, then run `racecheck`, `initcheck`, and `synccheck` separately. Each tool checks only its matching defect/corrected executables, and every command starts a new process. A clean result from one tool cannot substitute for another.

## Expected observations, not recorded results

1. Memcheck should locate the defect executable's single global-memory out-of-bounds write. The corrected executable should retain all 32 intended writes without that bounds defect.
2. Racecheck should locate the defect executable's plain shared-memory RAW ordering hazard. The corrected executable should preserve the published value through a block barrier.
3. Initcheck should locate the defect executable's read of uninitialized device global memory. The corrected executable should retain the increment work after zeroing the input.
4. Synccheck should locate the defect executable's divergent conditional `__syncthreads()`. The corrected executable should give the whole block uniform participation while retaining the phase copy.

These four statements are manifest-declared acceptance directions, not sanitizer output observed by this site. The expected clean behavior of each corrected variant also needs a qualifying record and cannot be inferred from source inspection.
