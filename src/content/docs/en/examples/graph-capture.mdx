EX09 is a standalone, original CUDA Graph Capture Runnable Example. It captures a fixed two-kernel workload on a nonblocking stream, instantiates an executable graph, launches it three times, and checks every value against an independent pure-host oracle after an explicit observation boundary. The website never executes CUDA, and the project reports no timing, launch-overhead, or speedup result.

## Purpose

Complete M14 first; it is EX09's only prerequisite. M07 and M08 supply related stream-ordering and asynchronous-execution context, but they are not additional prerequisites. EX09 focuses on the capture, instantiate, launch, completion, and cleanup lifecycle rather than a performance comparison.

## Canonical project

[View the complete EX09 project at the pinned commit](https://github.com/xiangzhang-coding/cuda-learning-site/tree/fb0306db725ab960a61b50456c227545057de392/examples/ex09-graph-capture), or [download the source archive for that same commit](https://github.com/xiangzhang-coding/cuda-learning-site/archive/fb0306db725ab960a61b50456c227545057de392.zip). After extraction, enter `examples/ex09-graph-capture/`.

`project.json` declares the build inputs, two canonical ranges, fixed DAG, three replays, 64-byte device-buffer bound, Toolkit Lanes, and empty evidence axes. The implementation, host model, tests, and page prose are original, are not derived from NVIDIA samples, and use Apache-2.0 for software files.

## Workload contract

The project fixes eight `std::uint32_t` elements. Input follows `input[index] = index + 1`, and state begins at zero. Each graph launch runs two nodes in order: `accumulate-input` applies `state[index] += input[index]`, then `affine-transform` applies `state[index] = 2 * state[index] + 1`.

One complete iteration is therefore `state[index] = 2 * (state[index] + input[index]) + 1`. After three iterations, the literal expected result is `21, 35, 49, 63, 77, 91, 105, 119`. The host test checks this list directly; it is not inferred from CUDA output.

## Graph contract

The pure C++17 header explicitly declares two nodes, one directed edge, and the sole valid topological order, then validates that contract independently:

<CanonicalCode exampleId="EX09" range="graph-contract" />

Before accepting a topological order, the validator checks the known-node set, duplicate nodes, edge endpoints, self-edges, duplicate edges, sizes, and every edge's relative positions. A cycle cannot satisfy every `from`-before-`to` constraint and is rejected. The oracle validates exact buffer sizes and the iteration range before computing in local temporary state; it writes output only on success.

## Capture and replay

The CUDA source creates two device buffers and a `cudaStreamNonBlocking` stream. After initialization is complete, this canonical range contains capture, instantiation, three launches, the explicit completion boundary, complete result transfer and verification, and ordered cleanup:

<CanonicalCode exampleId="EX09" range="captured-replay" />

`cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal)` and `cudaStreamEndCapture` bracket only the two kernel launches. Each launch is followed immediately by `cudaGetLastError()`. `cudaGraphInstantiate(&graph_exec, graph, nullptr, nullptr, 0U)` uses the CUDA 11.8 five-argument signature that all three declared Lanes can compile.

All three `cudaGraphLaunch` calls are submitted to the same stream. `cudaStreamSynchronize(stream)` is the explicit observation boundary. Only after it succeeds does the program transfer all eight values and compare them exactly with the host oracle. The graph executable, graph, stream, and buffers are destroyed after completion and verification, and every CUDA Runtime call has its return value checked.

## Host model boundary

`make host-test` compiles only `tests/host_reference_test.cpp` and the pure C++17 header. It validates the fixed DAG; explicitly rejects a cycle, unknown endpoint, self-edge, duplicate edge, reversed topology, and invalid size; checks that invalid sizes or iterations do not mutate destinations; checks the literal result of three host recurrence iterations; and checks a deterministic mismatch index.

The host test cannot establish stream capture, CUDA graph instantiation or execution, executable-graph replay, or performance. It includes no CUDA header, creates no graph, and launches no kernel. Passing it grants no CUDA Evidence Status.

## Build contract

From the project directory on Native Linux, run:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The first four stages require the selected CUDA Toolkit. Host-test needs only a host C++17 compiler. CUDA stages create `build/graph_capture.ii`, `build/graph_capture.o`, and `build/ex09-graph-capture`. Inspection checks a native `sm_75` cubin and PTX generated from `compute_75`.

`scripts/compile-check.sh c++17 ex09 <result-dir>` performs those stages and retains sanitized logs plus inspection artifacts. It never runs `build/ex09-graph-capture`, so a successful build gate supplies no graph runtime observation.

The Lanes are CUDA 11.8.0 on Ubuntu 22.04 x86-64, CUDA 12.9.2 on Ubuntu 24.04 x86-64, and CUDA 13.3.1 on Ubuntu 24.04 x86-64. Their digest-pinned images are future build targets, not compilation records.

This page claims no GPU output, capture success, observed graph shape, replay result, timing, launch overhead, latency, throughput, profiler result, or speedup. A future runtime record must identify a Reference Environment, include its complete Environment Manifest, preserve the fixed DAG and three-launch identity, and first satisfy every exact-output acceptance criterion.

## Expected observations, not runtime records

1. The executable should report `PASS` only when all eight device results after three graph launches exactly match the independent pure-host oracle.
2. Stream capture should produce a graph in which `accumulate-input` precedes `affine-transform`, preserving the fixed two-node topological contract on every launch.
3. Starting from zero state with inputs 1 through 8, three replay iterations should produce the complete result `21, 35, 49, 63, 77, 91, 105, 119`.

These are correctness and ordering acceptance criteria that the Learning Site has not observed. They contain no performance judgment.
