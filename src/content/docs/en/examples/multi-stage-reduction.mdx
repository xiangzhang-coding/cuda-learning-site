EX11 is a standalone, original Multi-Stage Reduction Runnable Example. The C++17 project reduces 4,099 deterministic `float` values to one value and judges correctness with a high-precision `double` CPU reference, an explicit reduction order, and a declared tolerance contract. It contains no timer and publishes no performance conclusion.

## Purpose

Complete [A02 Multi-Stage Reduction](/en/algorithms/multi-stage-reduction/) and [Q02 Floating-Point Order and Reproducibility](/en/correctness/floating-point-order-reproducibility/) first. A02 establishes the reduction tree, inactive lanes, barriers, and kernel boundaries. Q02 explains why floating-point addition order can change low-order bits and why tolerance does not imply bitwise reproducibility.

EX11 places those contracts in one minimal standalone project. A shared-memory kernel produces one partial sum per block, and the host launches more stages until one value remains. The only verdict is whether the GPU sum passes the CPU reference comparator.

## CPU reference and tolerance

The pure C++17 header defines the 4,099-element workload, a 256-thread block, at most 512 inputs per block, deterministic `float` generation, and a CPU reference accumulated in `double` in input order:

<CanonicalCode exampleId="EX11" range="cpu-reference" />

The GPU tree order differs from the serial CPU order, so the comparator does not require bitwise equality. It checks `absolute_error <= absolute_tolerance + relative_tolerance * abs(cpu_reference)`. The absolute term protects a reference near zero; the relative term scales the allowance with reference magnitude. This rule is a predeclared acceptance contract, not a threshold adjusted after seeing a result.

The same range defines the stage-size helper. Every nonterminal stage must produce a positive output count strictly smaller than its input count.

## Multi-stage shared-memory reduction

Each thread initializes its contribution to zero and independently guards two global loads. A bounds-invalid lane still writes its shared slot and reaches every `__syncthreads()` unconditionally with the rest of the block:

<CanonicalCode exampleId="EX11" range="multi-stage-reduction" />

Only the lower lanes add a partner at each tree step, but the barrier is outside that conditional branch. One kernel can reduce only within blocks. The next launch's kernel boundary makes the prior stage's global partial sums available to the next stage.

| Stage | Input count | Output count | Valid inputs in last block |
| ---: | ---: | ---: | ---: |
| 0 | 4,099 | 9 | 3 |
| 1 | 9 | 1 | 9 |

The first eight blocks therefore cover 512 values each, while the final partial block loads only indices 4,096 through 4,098. The host loop repeats stages until the count is one, then copies back only the final `float`.

## Host reference boundary

`make host-test` includes no CUDA header. It independently reconstructs deterministic input and checks stage sizes `4,099 -> 9 -> 1`, complete nonoverlapping block coverage, the three-element partial-block invariant, agreement between the `double` reference and a wider accumulation, and near-zero, scale-aware, and rejection cases for the absolute-plus-relative comparator.

The host test also constructs a pure CPU model with the same staged float order. Passing establishes arithmetic, stage-shape, and oracle behavior only. It cannot establish that the CUDA source compiled, a GPU barrier executed, or a device result satisfied the comparator.

## Build contract

From the project directory on Native Linux, run:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The CUDA stages create `build/multi_stage_reduction.ii`, `build/multi_stage_reduction.o`, and `build/ex11-multi-stage-reduction`. Inspection checks a native `sm_75` cubin and PTX generated from `compute_75`. Host-test needs only a host C++17 compiler and ends with `host-reference: pass`.

`scripts/compile-check.sh c++17 ex11 <result-dir>` runs clean, preprocess, compile, link, inspect, and host-test, retaining logs and inspection artifacts while never executing the GPU binary.

## Expected observations, not runtime records

1. The GPU result should report `PASS` only when the absolute-plus-relative comparator accepts it against the `double` CPU reference.
2. The 4,099-element workload should converge through stage sizes `4,099 -> 9 -> 1`, with exactly three valid inputs in the final block of the first stage.
3. Bounds-invalid loads should contribute zero while every thread in the block still reaches every block-wide barrier before the next step.

These are acceptance criteria. None is a recorded GPU observation.
