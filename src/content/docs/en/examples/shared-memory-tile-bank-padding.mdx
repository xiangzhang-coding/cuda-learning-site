EX06 is a standalone, original shared-memory tile bank-padding Runnable Example. A single templated C++17 CUDA implementation instantiates explicit unpadded `float[32][32]` and padded `float[32][33]` shared layouts. The website never executes CUDA and publishes no measured bank-conflict or performance result.

## Purpose

Complete M03 and then M04 before EX06; their order is part of the prerequisite contract. EX06 makes the shared-memory layout and bank-address arithmetic executable, while VIS05 is the related browser-only Visual Explainer. The host model and VIS05 provide no GPU observation or CUDA Evidence Status.

The comparison holds the input tile, one-warp launch, cooperative load order, barrier, read column, output values, and verifier constant. Padding is the only layout variable. This isolates the address map without changing the mathematical output.

## Layout contract

One block contains exactly one 32-thread warp. The deterministic input is a row-major 32 x 32 float tile. During loading, lane `l` first writes row 0, column `l`; then row 1, column `l`; and continues by adding 32 to its linear input index. Each loop iteration therefore loads one complete row cooperatively.

After all 1,024 values are present, `__syncthreads()` establishes the block-wide barrier. Every lane then reads `tile[lane][5]` and writes one contiguous output. Both layouts must produce the same exact 32 values because padding changes storage pitch, not logical row or column.

## Tiled kernels

Both kernel variants come from one templated implementation:

<CanonicalCode exampleId="EX06" range="tiled-kernels" />

The launch instantiates `Padding=0` and `Padding=1` with the same input, fixed column 5, and separate 32-element outputs. The barrier occurs after every lane finishes its cooperative stores and before any lane begins the transposed-style column access.

Under the declared 32-bank, four-byte-word model, the unpadded access word for lane `l` is `l * 32 + 5`, so all lanes select bank 5 while naming distinct words. The padded word is `l * 33 + 5`, producing bank `(l + 5) % 32`, one bank per lane. These are host-model predictions. No profiler observation is recorded.

## Host model boundary

`include/shared_memory_tile_bank_padding_reference.hpp` is pure C++17. It validates row-major input indices, physical shared-word indices for padding zero and one, bank numbers, deterministic float values, and complete output construction through both layouts.

`make host-test` checks known tile positions and rejected coordinates, proves that the unpadded lane words are distinct but share bank 5, proves that the padded mapping visits every bank exactly once, and compares both output arrays exactly. Values end in `.25`, so every value used here is exactly representable as a binary `float`; the test needs no tolerance. It compiles and runs no CUDA.

## Build contract

From the project directory on Native Linux, run:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The first four stages require the selected CUDA Toolkit. Host-test needs only a host C++17 compiler. CUDA stages create `build/shared_memory_tile_bank_padding.ii`, `build/shared_memory_tile_bank_padding.o`, and `build/ex06-shared-memory-tile-bank-padding`. Inspection checks a native `sm_75` cubin and PTX generated from `compute_75`.

`scripts/compile-check.sh c++17 ex06 <result-dir>` performs those stages, scans the resulting logs and inspection artifacts, and never executes the CUDA binary. The compile workflow therefore supplies no shared-memory runtime observation.

## Expected observations, not runtime records

1. The unpadded and padded variants should each report `PASS` only when all 32 outputs exactly match the pure host tile reference.
2. For concurrent `tile[lane][5]` reads, the 32 x 32 host model predicts 32 distinct words in bank 5.
3. For the same logical reads, the 32 x 33 host model predicts one distinct bank per lane while preserving the same values.

The second and third statements are address-model predictions, not measured conflict counters or a promised performance ordering.
