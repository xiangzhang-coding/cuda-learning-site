EX17 is a standalone, original C++17 CUB Device Reduction and Scan Runnable Example. It calls the production `cub::DeviceReduce::Sum`, `cub::DeviceScan::InclusiveSum`, and `cub::DeviceScan::ExclusiveSum` interfaces without copying or adapting the CUB implementation. The project produces correctness verdicts only, contains no timer, and publishes no measured performance result.

## Purpose

The sole strict prerequisite is [L03: CUB Device Reduction and Scan Primitives](/en/libraries/cub-device-primitives/). L03 establishes the focused headers, operation semantics, traditional temporary-storage protocol, stream ordering, lifetimes, and version-matrix contract. This page places those contracts in one independently buildable and runnable project.

[A02 Multi-Stage Reduction](/en/algorithms/multi-stage-reduction/), [A03 Inclusive and Exclusive Scan](/en/algorithms/inclusive-exclusive-scan/), [Q02 Floating-Point Order and Reproducibility](/en/correctness/floating-point-order-reproducibility/), [L01 Choose a Library, Primitive, DSL, or Custom Kernel](/en/libraries/library-primitive-dsl-custom-kernel/), [EX11 custom reduction](/en/examples/multi-stage-reduction/), [EX12 custom scan](/en/examples/inclusive-exclusive-scan/), and [LAB11 custom/CUB comparison](/en/labs/compare-custom-reduction-with-cub/) are related resources only. They add no prerequisite edge.

## CPU references and two correctness contracts

One host-only header defines both the reduction and scan oracles without including a CUDA or CUB header:

<CanonicalCode exampleId="EX17" range="cpu-reference" />

**Reduction contract:** Exactly 4,099 stored `float` values use a deterministic generator that is byte-for-byte compatible with EX11. Every item is first represented as `float`, then converted to `double` and serially accumulated in input order. The device writes one `float`. The fixed acceptance rule is `absolute_error <= 1.0e-4 + 2.0e-5 * abs(cpu_reference)`. A parallel reduction may change the addition association, so EX17 requires neither the serial left-fold bit pattern nor bitwise reproducibility merely because the tolerance check passes.

**Scan contract:** The public reference accepts at most 4,099 `std::uint32_t` inputs and rejects any value above 7 before writing output. Every prefix is therefore at most `4,099 * 7 = 28,693`, excluding `uint32_t` overflow. The fixed input repeats 1 through 7 and totals exactly 16,390. Inclusive and exclusive references compute independently with separate serial loops. Both complete device arrays must match exactly and satisfy the recurrences, `exclusive[0] = 0`, and both last-total identities.

## DeviceReduce path

The reduction range contains only the traditional public `DeviceReduce::Sum` query, allocation, and execution plumbing:

<CanonicalCode exampleId="EX17" range="device-reduce" />

`TemporaryStorage::bytes` starts at zero. The query calls `Sum` with `nullptr`, the same input/output pointer types, the `int item_count`, and the explicit stream, then allocates the returned byte count. Execution on the same current device returns that allocation and byte count to the same overload. The source also proves statically that 4,099 fits the legacy API's `int` extent.

The GPU result is compared only with the independent `double` oracle above. Calling a production primitive does not make serial order the device order and does not itself establish cross-GPU bitwise equality.

## DeviceScan paths

The scan range owns separate storage for inclusive and exclusive operations. Capacity queried for one primitive is never reused as the other's capacity:

<CanonicalCode exampleId="EX17" range="device-scan" />

`InclusiveSum` and `ExclusiveSum` each perform a null-storage query followed by their own allocation and execution. They share the 4,099-element input and explicit stream, while their outputs and scratch allocations remain distinct. After completion, the program exact-compares each array, then checks every adjacent prefix, the inclusive/exclusive relation, and the 16,390 last total. Any failed check makes the process fail.

## Canonical headers, temporary storage, stream, and lifetimes

The CUDA source's CUB imports are exactly the focused public headers `<cub/device/device_reduce.cuh>`, `<cub/device/device_scan.cuh>`, and `<cub/version.cuh>` for the version gate. It neither hides the dependency behind aggregate `<cub/cub.cuh>` nor refers to a CUB internal symbol. This page renders only the three ranges declared by the project manifest through `CanonicalCode`; it maintains no second CUDA/C++ code fence.

All three primitives follow the same legacy two-phase protocol: query with null storage and a zeroed byte count, allocate at least that capacity on the same current device, then execute with the same API, template and argument types, 4,099-item shape, and stream. The three queried values belong separately to reduction, inclusive scan, and exclusive scan. They are not constants across versions, devices, or operations, and they are not memory-traffic measurements.

`main` creates exactly one `cudaStreamNonBlocking` stream. All six CUB calls and all five checked `cudaMemcpyAsync` calls receive that handle; the copies comprise two H2D inputs and three D2H outputs. Exactly one checked `cudaStreamSynchronize(stream)` follows the output copies and forms the sole completion boundary before host validation. Inputs, outputs, and all three scratch allocations outlive that boundary and are released afterward. Every CUDA/CUB return value, free, and stream destruction is checked. Submission success alone is not completion.

## Build, host-test, and run commands

The host test needs no CUDA headers, CUDA runtime, or GPU:

```sh
make host-test DIALECT=c++17
```

It checks the 4,099-float fixture, `double` oracle, absolute and relative tolerance boundaries, bounded-scan rejection, two independent scan references, exact comparator, recurrences, and last totals. `host-reference: pass` establishes host-contract behavior only. It establishes neither CUDA compilation nor GPU execution evidence.

For the 11.8 bundled profile, a direct staged build is:

```sh
make preprocess DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make compile DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make link DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make inspect DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
```

The profile wrapper runs clean, preprocess, compile, link, inspect, and host-test in order, but never executes the CUDA binary:

```sh
scripts/compile-check.sh c++17 cuda-11-8-bundled-cub-1-15-1 results/ex17-11-8
CCCL_ROOT=/path/to/cccl scripts/compile-check.sh c++17 cuda-12-9-selected-cccl-3-4-2 results/ex17-12-9-selected
```

Run the binary only after satisfying the runtime gate:

```sh
./build/ex17-cub-device-reduction-scan
```

The build produces preprocessed source, an object, and the executable. Inspection requires a native `sm_75` cubin plus PTX generated from `compute_75`. The binary prints the selected CUB macro and five correctness verdicts, but this page retains no actual stdout or exit status.

## Expected observations, not recorded results

1. `DeviceReduce::Sum` should pass the predeclared absolute-plus-relative comparator against the independent `double` CPU reference for exactly 4,099 EX11-compatible `float` inputs.
2. `DeviceScan::InclusiveSum` and `DeviceScan::ExclusiveSum` should each exactly match their independently computed `uint32` CPU references and pass every recurrence and last-total invariant.
3. The selected `CUB_VERSION` should equal the profile's expected macro before any executable links; a mismatch or non-unique header resolution should fail the build.

These three manifest-declared statements are acceptance directions, not build or runtime output observed by this site.
