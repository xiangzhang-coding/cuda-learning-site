EX03 is a standalone, original multidimensional-indexing Runnable Example. One C++17 implementation handles one-, two-, and three-dimensional logical extents while keeping per-axis bounds, application-declared row-major flattening, an explicit host-device lifecycle, and an independent host reference in one project. The website never executes CUDA.

## Purpose

Complete [F03: Make Multidimensional Indexing and Bounds a Correctness Contract](/en/foundations/multidimensional-indexing/) first. EX03 turns that Learning Unit's coordinate rules into the sole executable implementation. [F02](/en/foundations/execution-hierarchy/) supplies the execution hierarchy, [F04](/en/foundations/host-device-lifecycle/) explains the resource lifecycle, and [VIS02](/en/visuals/indexing/) presents the same indexing mental model only in the browser.

The same code path accepts one to three positive extents. With only x, y and z remain 1. With x and y, z remains 1. Supplying all three creates a full three-dimensional extent. These degenerate dimensions let 1D, 2D, and 3D share one implementation rather than maintaining three programs.

## Indexing contract

The kernel independently derives x, y, and z global coordinates, checks all three extents independently, and only then flattens under the application's declared x-fastest row-major layout:

<CanonicalCode exampleId="EX03" range="indexing-kernel" />

The linear position is `((z * extent_y) + y) * extent_x + x`. Adjacent x coordinates name adjacent elements, one row spans `extent_x` elements, and one layer spans `extent_x * extent_y` elements. CUDA grid/block geometry creates coordinates; it does not declare the application's memory layout.

The three early returns are independent. Any invalid coordinate must return before flattening or array access. Checking only x, or requiring all three invalid predicates at once, would let y or z fringes in partial edge blocks cross the contract. A degenerate axis has extent 1, so only coordinate 0 is valid on that axis; the same per-axis checks reject its remaining threads.

## Lifecycle

The same project orders host initialization, the independent reference, device allocation, transfer, launch, synchronization, copy-back, comparison, and release along one explicit success path:

<CanonicalCode exampleId="EX03" range="lifecycle" />

The order is: create three host-storage vectors; initialize input and compute the host expected result; allocate input and output device buffers; copy H2D; construct a ceiling-divided grid on each axis; launch the kernel; check `cudaGetLastError`, then establish completion with `cudaDeviceSynchronize`; copy D2H; save the element-by-element comparison result; and finally release both device allocations.

This range presents a fail-fast success path, not reusable partial-failure cleanup. The complete project's `CUDA_CHECK` terminates the process after a CUDA API failure, so it does not follow a structured cleanup path for allocations acquired earlier. On the success path, it saves the comparison verdict before both `cudaFree` calls. This page does not rewrite that implementation limit as a stronger resource-safety claim.

## Correctness boundary

The pure host C++17 reference defines extents, coordinates, per-axis validity, row-major mapping, and the expected integer value for each element without a CUDA header or device annotation:

<CanonicalCode exampleId="EX03" range="host-reference" />

`make host-test` checks known positions in the 1D `7 x 1 x 1`, 2D `5 x 4 x 1`, and 3D `4 x 3 x 2` extents. It also covers the `10 x 9 x 5` extent, which is not divisible by the project block shape, and submits separate out-of-range x, y, and z coordinates. The test uses exact `std::uint32_t` element comparisons and introduces no floating-point tolerance.

This host-only test can catch dimension swaps, incorrect flattening, and an incomplete host bounds contract, but it neither compiles nor executes the CUDA kernel. Passing it cannot establish agreement with the device implementation and grants no CUDA Evidence Status.

## Build contract

From the project directory on native Linux, run the stages in this fixed order:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

Preprocessing, compilation, linking, and inspection require the selected CUDA Toolkit. The host test requires only a host C++17 compiler on the x86-64 CPU. The first three CUDA stages create `build/multidimensional_indexing.ii`, `build/multidimensional_indexing.o`, and `build/ex03-multidimensional-indexing`. Inspection uses `cuobjdump` to check a native `sm_75` cubin and forward-compatible PTX generated from `compute_75`; host-test executes only the separate host executable.

These five steps define the complete acceptance path for a future compilation record. The build flow does not execute `build/ex03-multidimensional-indexing`, so even a successful build creates no GPU runtime observation.
