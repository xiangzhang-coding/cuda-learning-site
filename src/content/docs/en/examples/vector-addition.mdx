EX02 is a standalone, original vector-addition Runnable Example. It keeps grid indexing, bounds handling, the explicit memory lifecycle, CUDA error checks, and a CPU correctness reference in one small project. It is not a Lab, and the website never executes CUDA.

It is the sole canonical source displayed by [F01](/en/foundations/first-cuda-kernel/) and downloaded for [LAB02](/en/labs/vector-addition/). Neither resource maintains a second complete implementation.

## What this project is for

Learners face one canonical C++17 implementation. The CUDA 11.8.0, 12.9.2, and 13.3.1 Toolkit Lane checks all point to the same source tree. CUDA 12.9.2 and 13.3.1 also compile that same source as C++20 instead of maintaining another implementation.

The project defines correctness before any measurement. No qualifying GPU run exists yet, so this page records neither runtime output nor performance numbers.

## Correctness boundary

The CPU reference and tolerances have no CUDA dependency and can be tested with an ordinary C++ compiler:

<CanonicalCode exampleId="EX02" range="cpu-reference" />

- Absolute tolerance: `1e-5`.
- Relative tolerance: `1e-5`.
- An element passes when either the absolute or relative tolerance accepts it; it fails only when neither does.
- Default size: `1,048,576` `float` elements.
- Optional size: `1..134,217,728`; the three device vectors use about 1.5 GiB at the maximum, below the curriculum's 8 GB boundary.
- `make host-test` runs only the CPU reference and tolerance acceptance checks. It cannot establish GPU-kernel correctness.

A real GPU run must still pass `cudaMalloc`, two host-to-device copies, the launch-error check, `cudaDeviceSynchronize`, the device-to-host copy, CPU comparison, and three `cudaFree` calls. Any failure returns a nonzero status.

## Build contract

From the project directory in a supported native Linux environment, run:

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

The first four steps produce `build/vector_add.ii`, `build/vector_add.o`, and `build/ex02-vector-addition`, then use `cuobjdump` to confirm a native `sm_75` cubin and forward-compatible PTX generated from `compute_75`. The project does not use relocatable device code, so it does not invent a separate device-link phase.

CPU-only CI **never executes** `build/ex02-vector-addition`. A later learner run in a qualifying external environment must first record a complete Environment Manifest. A successful build cannot substitute for GPU correctness.

## Compatibility

| Coordinate | Declaration |
| --- | --- |
| Supported Environment | Native Linux only |
| Baseline GPU Capability Tier | Compute capability 7.5 or newer; problem sizes fit within 8 GB |
| Compiler target | `sm_75` cubin + `compute_75` PTX |
| Shared implementation | Explicit C++17; 12.9.2/13.3.1 also check the same source as C++20 |
| C++23 | GCC 13.3 in the 13.3.1 image does not support the NVCC C++23 configuration; the separate probe records `unsupported` and grants no C++23 compile claim to EX02 |

The build never uses `--allow-unsupported-compiler`. An image tag and digest are inputs, not observed environments. Every result must record the actual OS, host compiler, NVCC, and pulled image identity.

These are **expectations** for a future qualifying run, not output observed by this page:
