A multi-stage reduction combines many values into fewer partial values until one result remains. This Learning Unit separates an intra-block reduction tree from the cross-kernel stage sequence, then proves the contracts for every inactive lane, barrier, `__syncthreads()`, kernel boundary, and operation order. Each stage halves the active set, so fewer lanes participate in the combine while every block participant still follows the barrier contract.

## What you should be able to do

- Declare a reduction operation, identity, input domain, and result contract.
- Draw each stage's active and inactive lanes and partial ownership.
- Prove the happens-before phase from a shared-memory write, through a barrier, to the next read.
- Continue per-block partials through multiple kernel launches without assuming a global barrier inside an ordinary grid.
- Explain why a parallel tree order can produce a different floating-point result from a serial sequential order.
- Start production work from a CUB `DeviceReduce` baseline and use a hand-written teaching kernel to learn the mechanism.

## Reduction contract: define combine before assigning threads

Let the input be `x[0..n)`, the binary operation be `combine(a, b)`, and the identity be `e`. The abstract contract combines every valid input in the declared operation order. Padding uses `e`, with `combine(x, e) = x`.

The integer-sum teaching case can use zero as identity. General parallel regrouping expects mathematical associativity. Finite-precision floating-point addition is not strictly associative, so correctness cannot mean only an exact match to one serial bit pattern. Declare the tree order, reference policy, and acceptance tolerance; related Learning Unit [Q02](/en/correctness/floating-point-order-reproducibility/) develops that contract.

## Tree shape: shrink the active set at each stage

An eight-lane teaching reduction tree can be represented as:

```text
stage 0: lanes 0..7 own [x0 x1 x2 x3 x4 x5 x6 x7]
stage 1: lanes 0..3 own [x0+x4, x1+x5, x2+x6, x3+x7]
stage 2: lanes 0..1 own [(x0+x4)+(x2+x6), (x1+x5)+(x3+x7)]
stage 3: lane 0 owns the block partial
```

Every stage roughly halves the logical partial count. The tree edges define operation order; another pairing of the same leaves is a different algorithm variant. This diagram expresses dependencies and makes no claim about the scheduler's timing order.

## Inactive lanes: no combine does not mean no participation

As stride shrinks, a lane with `threadIdx.x >= stride` is an inactive lane for that stage's combine. Inactive does not mean exiting the kernel. If a later block barrier remains, that lane must follow uniform control flow to the barrier. In an edge block, a lane with no valid input first writes identity to its shared slot and likewise cannot return before the initial barrier.

Separate the roles at every stage:

| lane role | combine action | participation action |
| --- | --- | --- |
| active | read two declared partials, write one partial | reach the stage barrier |
| inactive | perform no combine | still reach the same stage barrier |

This separation prevents a data predicate from being mistaken for a synchronization predicate.

## Barriers: write, barrier, then read

The block-local invariant is that active lanes first write this stage's shared partial, all participating threads reach the `__syncthreads()` barrier, and only then may the next stage read those slots. The phase is `write -> barrier -> read`; the barrier cannot be enclosed by `if (tid < stride)`.

```text
initial guarded load or identity write
all lanes: barrier
for each stride:
  active lanes: read declared pair and write partial
  all lanes: barrier
```

This baseline may retain a final barrier that a more specialized proof could remove, in exchange for a uniform and reviewable phase shape. Removing one requires a new proof for the final consumer, storage reuse, and participating group. “Inactive lanes do no work” is not that proof.

## Multi-stage: connect grid-wide partials at a kernel boundary

Ordinary thread blocks may be scheduled independently. A block-local `__syncthreads()` cannot establish a grid-wide rendezvous in an ordinary kernel. Every block in the first kernel stores one partial to global memory. The host launches the next kernel in the same stream and that kernel consumes the partial array. A separate kernel boundary plus stream order ensures the next launch waits before reading the global partials from the previous stage.

```text
input array
  -> kernel stage 0 -> global partial array P0
  -> kernel stage 1 -> smaller global partial array P1
  -> ...
  -> final scalar
```

The kernel boundary is the global stage boundary across the grid, while a block barrier is only a shared-memory phase boundary inside one block. They are not interchangeable. Every launch still guards its final partial block and inserts identity for invalid slots.

## Operation order: a parallel tree is not a serial fold

A serial left fold has order `(((x0 + x1) + x2) + x3)`. One tree order is `(x0 + x1) + (x2 + x3)`. Real-number addition gives the same mathematical result, but every floating-point combine rounds, so the parallel tree order can differ from the serial sequential order.

That fact does not permit unexplained mismatches. Record the type, compiler options, tree shape, block/grid shape, identity, reference accumulation, and tolerance. Determinism, acceptable numerical variation, and bitwise reproducibility are separate requirements. This page establishes the operation-order dependency; Q02 defines the complete contract.

## Production baseline: use CUB DeviceReduce first

For production work, treat CUB `DeviceReduce` as the production baseline and comparison point before deciding to maintain a custom kernel. It provides a broadly maintained device-wide reduction primitive. The caller remains responsible for the operation, type, temporary storage, stream, input/output lifetime, and numerical acceptance contract.

The hand-written teaching reduction exists to learn and understand tree ownership, inactive lanes, barriers, kernel stages, and operation order. It is not a prerequisite, does not copy an implementation from the CUB source, and does not beat the production baseline merely by being closer to the hardware. Only observed evidence under fixed correctness parity, an Environment Manifest, and a measurement method can support replacement.

## Visual Explainer: VIS10

[VIS10: Reduction Stages](/en/visuals/reduction-stages/) represents lanes, partials, stage transitions, and inactive-lane sets as a deterministic browser model. It helps review an algorithm variant and barrier placement, but it does not execute CUDA, simulate scheduling, or produce measured performance.

Select the tree variant first, then answer three questions at every stage: who reads, who writes, and who must reach the barrier. Both the Visual Explainer's static fallback and its interactive state are expected-reasoning aids only.

## Evidence boundary: separate reasoning from observation

| expected reasoning | observed performance or runtime evidence |
| --- | --- |
| Active and inactive ownership at each stage | Actual output and error state in a Reference Environment |
| The `write -> barrier -> read` phase proof | A real sanitizer, trace, or other tool observation |
| Kernel stages progressively reduce partial count | Actual launch count, duration, traffic, or throughput |
| Tree operation order differs from a serial fold | A numerical difference observed with recorded inputs and configuration |

All four evidence arrays on this page are empty. Source review, diagrams, and host-side reasoning cannot prove that EX11 compiled or ran, and cannot prove that a custom reduction is faster than CUB.
