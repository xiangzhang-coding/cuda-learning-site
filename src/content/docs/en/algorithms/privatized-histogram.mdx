A histogram maps each valid sample to a bin and increments that bin's count. Direct global `atomicAdd`, contention, privatization, shared memory, and merge are separate concerns: atomics determine whether concurrent updates are correct, privatization changes where updates happen, and performance conclusions still require observations.

## What you should be able to do

- State exact-count, range, overflow, and sum-of-bins contracts for a histogram.
- Explain how global `atomicAdd` prevents lost updates and why correctness does not remove contention.
- Identify competition at the same hot bin from an input distribution without fabricating a performance result.
- Prove the `zero -> barrier -> update -> barrier -> merge` phase order of shared privatization.
- Separate a hand-written teaching kernel, the CUB `DeviceHistogram` production baseline, and runtime evidence.

## Prerequisites

Complete [M03: Shared-memory Tiling](/en/memory/shared-memory-tiling/) and [M05: Synchronization Scopes and Memory Visibility](/en/memory/synchronization-scopes/) first. M03 supplies per-block shared ownership, cooperative initialization, and bounds-safe participation. M05 supplies atomic scopes, `__syncthreads()` visibility, and kernel boundaries.

The prerequisite list is exactly `M03` and `M05`. CUB `DeviceHistogram` is a production comparison, not a prerequisite, and this unit requires no prior library unit.

## Histogram contract

Let `bin_of(x)` map one valid sample into `[0, bin_count)`. Output must satisfy:

```text
histogram[b] = count of valid samples x for which bin_of(x) == b
sum(histogram[0..bin_count-1]) = valid sample count
```

The contract also states whether lower and upper bounds are inclusive or exclusive, whether an out-of-range sample is discarded, clamped, or rejected, and whether the counter type can overflow at the maximum input size. For integer bins, a CPU reference should compute exact counts sample by sample. Tolerance does not excuse an integer count mismatch.

Input and output ownership are asymmetric. One thread can uniquely read each sample, while many threads may update the same output bin. A plain `histogram[b] += 1` is therefore a read-modify-write race.

## Global atomics: establish correctness first

The direct baseline first zeros global bins and then runs `atomicAdd(&global_bins[b], 1)` for each valid sample. An atomic read-modify-write prevents a lost update, so atomic correctness supplies exact counting when multiple threads increment the same counter.

That conclusion has boundaries: the bin index must be valid, initialization must complete before the kernel reads bins, counters must not overflow, and the host must wait for kernel completion before verification. `atomicAdd` does not repair a wrong `bin_of`, omitted samples, or an invalid memory lifetime.

## Contention: correct updates can still compete

When many samples map to the same hot bin, their atomic updates contend at one address and may serialize. A more uniform distribution produces a different address pattern. Both inputs can produce exactly correct histograms; atomic correctness and contention cost must be discussed separately.

Distribution and atomic counts can motivate a measurement hypothesis, not a speedup claim. Hardware, counter type, bin count, block shape, input ordering, and architecture can all affect an observation, so this page does not claim either variant is faster.

## Shared privatization: zero, barrier, update, barrier

A block-private shared histogram directs most sample updates to bins owned by that block. Its minimum correctness sequence is:

1. **Zero:** threads clear all shared bins with a stride; `bin_count` may exceed `blockDim.x`.
2. **Barrier:** an initialization barrier, `__syncthreads()`, ensures every bin is zero before any update.
3. **Update:** each thread handles its valid samples and uses `atomicAdd` on a shared bin; shared memory still needs atomics because block threads can hit one bin.
4. **Barrier:** an update barrier, `__syncthreads()`, ensures merge cannot read an unfinished shared update.
5. **Merge:** threads stride over private counts and combine them into the global histogram.

All participating threads reach both barriers. A bounds-invalid thread may skip its sample update, but it cannot return before the initialization or update barrier. Privatization is per block, not per thread; different blocks own distinct shared histogram instances.

## Merge: combine private counts into global bins

Multiple blocks ultimately write the same global bins, so merge commonly still requires `atomicAdd(&global_bins[b], shared_bins[b])`. Processing only nonzero private bins is an implementation choice, but it must retain exact counts and must not treat a zero test as cross-thread synchronization.

The post-merge proof obligation is that each global bin equals the sum of that bin's block-private values. Summing all bins must then equal the valid sample count. Compare exact values against a CPU reference only after kernel completion. Shared privatization changes the update hierarchy; it does not automatically grant speedup evidence.

## Production baseline: CUB DeviceHistogram

CUB `DeviceHistogram` in CCCL v3.4.2 is the production baseline and comparison point for a device-wide histogram. Production code should first inspect the level-boundary, sample-layout, counter, temporary-storage, and stream contracts of `HistogramEven` or `HistogramRange` rather than assume it should maintain a teaching kernel.

Hand-written teaching kernels exist to learn and understand atomic correctness, contention, shared privatization, and merge. Exposing more internal phases does not make one a better production default. `DeviceHistogram` also does not enter the exact `M03,M05` prerequisite list.

## Evidence boundary

Compilation, runtime, expected observations, and recorded observations are all empty for this page. Exact CPU counts, the sum-of-bins invariant, and a phase proof can reveal correctness defects, but they have not executed EX13 or observed throughput, bandwidth, timing, or speedup.

A future comparison of global-atomic and privatized variants must fix the input, bin contract, counter type, launch configuration, warm-up policy, timing boundary, and Environment Manifest, and first prove exact output matches. Without those records, fewer opportunities for global atomics cannot be reported as observed acceleration.

## Retrieval check

1. Why can `atomicAdd` provide histogram correctness without removing contention at the same hot bin?
2. Why does shared privatization still require atomic updates in shared memory?
3. Which read/write relation is protected by the barrier after zeroing and by the barrier after updates?
4. Why does the merge into global bins commonly remain atomic, and how are final exact counts verified?
