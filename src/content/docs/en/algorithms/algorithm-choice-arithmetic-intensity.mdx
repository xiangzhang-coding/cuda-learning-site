Optimization should begin with data-movement accounting, not with the most fashionable technique. A14 gives four familiar algorithm families an operation count, compulsory-traffic lower bound, implementation-traffic estimate, and arithmetic intensity at a declared boundary before selecting a transformation that an experiment can reject. Roofline constrains the question; it does not automatically choose a winner.

## What you should be able to do

- Declare an operation-count convention for map/vector addition, reduction, transpose, and GEMM.
- Write compulsory-traffic lower bounds separately from implementation-traffic estimates.
- Explain how caches, transactions, memory hierarchy, and boundary choice change traffic and intensity.
- Connect fusion, hierarchical reduction, tiled transpose, and tiled GEMM to testable data-reuse hypotheses.
- Choose an experiment that preserves correctness, changes one primary mechanism, and has a rejection rule.

## Prerequisites

The exact prerequisites, in order, are [A01: Elementwise Map](/en/algorithms/elementwise-map/), [A02: Multi-stage Reduction](/en/algorithms/multi-stage-reduction/), [A05: Matrix Transpose](/en/algorithms/matrix-transpose-layout/), and [A08: Tiled GEMM](/en/algorithms/tiled-gemm-correctness/): `A01, A02, A05, A08`. They supply ownership, reduction stages, layout transformation, and the GEMM reuse contract.

## One accounting contract

The static baseline uses FP32, four bytes per element, and algorithmic data arithmetic. Unless an item says otherwise, `W` excludes index and address arithmetic. GEMM counts an FMA as 2 FLOP. Every formula is an estimate, not an executed-instruction count or observed traffic.

| field | compulsory lower bound | implementation estimate |
| --- | --- | --- |
| meaning | unique logical data that must cross the declared boundary to complete the workload correctly | bytes expected to cross after algorithm, stages, tiling, and cache assumptions |
| includes | declared inputs, required outputs, and necessary reads/writes | repeated reads, intermediates, and extra passes; transaction overfetch may be a separate line |
| excludes unless declared | cache-path traffic, write allocation, metadata, and profiler replay | unmodeled cache hits, compression, eviction, and concurrency effects |
| status | static lower-bound argument | static hypothesis later tested with an exact observed definition |

One formula serves one path only. DRAM compulsory bytes, L2-to-SM requests, and shared-memory traffic cannot be added and still called `T_DRAM`. Caches can prevent repeated global requests from reaching DRAM or allow them through after eviction. Transaction granularity can make transferred bytes exceed requested bytes.

## Map and vector addition

For unary map `y[i]=f(x[i])`, if `f` performs `c` declared FLOP per element, `W_map = cN`. The out-of-place FP32 compulsory traffic reads x and writes y:

`T_map,compulsory = 8N byte`

Thus `I_map,compulsory = c / 8 FLOP/byte`. A map with more inputs, an old-output read, or multiple outputs needs a new count and cannot retain `8N`.

For `c[i]=a[i]+b[i]`, `W_vadd = N FLOP`, and out-of-place compulsory traffic is:

`T_vadd,compulsory = 12N byte`

`I_vadd,compulsory = 1/12 FLOP/byte`. Coalescing does not change logical `12N`, but it changes transaction efficiency and potentially the transferred bytes crossing the chosen path. Multiple elementwise stages that materialize intermediates read and write repeatedly. Fusion can preserve mathematical work and delete intermediate traffic, but it can also raise register use, change occupancy, or prevent other scheduling.

## Reduction

Summing N FP32 values has algorithmic work:

`W_reduce = N - 1 FLOP`

Counting one input read and one final scalar write gives the compulsory lower bound:

`T_reduce,compulsory = 4N + 4 byte`

For a materialized multi-pass implementation with `s` stages and non-final partial counts `P_1 ... P_(s-1)`, estimate:

`T_reduce,implementation = 4N + 8 * sum(P_i) + 4 byte`

Every partial is written as four bytes and read by a later stage as four more. An atomic final stage, persistent block, cooperative launch, or on-chip handoff changes this implementation formula. Compulsory intensity approaches `1/4 FLOP/byte`; materialized intermediates only increase this declared-boundary denominator. Parallel reduction also changes operation order, so correctness and tolerance precede traffic comparison.

## Transpose

For out-of-place FP32 `B[col,row]=A[row,col]`, the data-arithmetic convention gives `W_transpose = 0 FLOP`; index arithmetic is explicitly excluded. Compulsory traffic reads A and writes B:

`T_transpose,compulsory = 8MN byte`

Therefore `I_transpose = 0 FLOP/byte` under this convention. This does not mean “no performance problem.” It means FLOP-based intensity has little resolving power for a pure movement kernel.

Naive and tiled transpose share the same logical DRAM lower bound. A shared-memory tile aims to make global reads and writes use more efficient transactions; padding can avoid shared-bank conflict. This adds shared-memory traffic and barriers while potentially reducing the global transferred/requested mismatch. For a DRAM model, shared bytes do not enter `T_DRAM`. For a shared-path question, build a separate `T_shared` and a non-FLOP throughput question.

## GEMM

For row-major, non-transposed FP32 `C=A*B` with `beta=0` and FMA=2 FLOP:

`W_gemm = 2MNK FLOP`

If each unique A and B element crosses the declared DRAM boundary once and C is written once, the compulsory lower bound is:

`T_gemm,compulsory = 4(MK + KN + MN) byte`

Without cross-output cache reuse, a naive one-output-per-thread request estimate is:

`T_gemm,naive = 4(2MNK + MN) byte`

The `2MNK` elements are K A loads and K B loads per output. This estimate better describes global-load requests or an L2-to-SM boundary. It is not guaranteed DRAM traffic because caches can serve repeated requests.

For a `TM x TN` output tile, if each block loads every needed valid A/B tile value once per K slice, one block-reuse request estimate is:

`T_gemm,tiled = 4[ceil(N/TN)MK + ceil(M/TM)KN + MN] byte`

Blocks can still repeat A/B requests. L2 hits may lower DRAM traffic, while transaction overfetch and tails may raise transferred traffic. Tiling's falsifiable mechanism is reduced repeated movement at a declared boundary while preserving the GEMM equation, not “shared memory is always faster.”

## Estimate before selecting a transformation

| algorithm | low-intensity symptom in static model | candidate transformation | added cost or counterexample |
| --- | --- | --- | --- |
| map/vector add | intermediates repeatedly materialized | fuse adjacent elementwise stages; keep data resident | registers, code size, lost reuse or scheduling flexibility |
| reduction | partial arrays repeatedly written and read | block/warp aggregation, fewer stages, fused consumer | order/tolerance, synchronization, atomic contention |
| transpose | little logical work and potentially wasteful transactions | shared tile, coalesced write, padding | barriers, shared footprint, partial tiles |
| GEMM | naive A/B requests repeated across outputs | block tiling, greater reuse, an appropriate library later | resources, occupancy, tails, layout and precision contract |

The table generates candidates only. Selection also considers workload size, correctness, parallelism, resource pressure, latency, launch overhead, and production-library boundaries. Two implementations with equal arithmetic intensity can differ in coalescing, dependencies, or load balance.

## One falsifiable choice: fuse elementwise stages

Consider `tmp[i]=a[i]+b[i]` followed by `z[i]=g(tmp[i])`, where `g` performs `c` FLOP per element. The unfused baseline has `(c+1)N FLOP`. Its logical DRAM traffic estimate is `12N` for the first stage plus `8N` for the second:

`T_unfused = 20N byte`

Fusion preserves work while reading a/b and writing z directly:

`T_fused = 12N byte`

Thus `I_unfused = (c+1)/20 FLOP/byte` and `I_fused = (c+1)/12 FLOP/byte`. This is a model prediction, not a winner result.

The falsifiable experiment predeclares the same input and shape, numerical acceptance, device/software/build, and warm-up/timing scope. Baseline and candidate change only fusion and query one exact DRAM-traffic definition. The mechanism claim requires lower candidate traffic; the performance claim requires lower elapsed time. Reject the corresponding claim if cache absorbs the intermediate, register pressure rises, occupancy or issue behavior worsens, traffic does not fall, or timing does not improve. Do not alter the model after seeing a result.

## Roofline cannot choose a winner automatically

[Q10](/en/correctness/roofline-arithmetic-intensity/) places an estimate under a declared roof. A modeled path-ceiling region says only that the sloped line is below the compute ceiling in that model. It does not establish an observed bottleneck. Fusion can move a point right and still slow down. Tiling can raise modeled intensity while synchronization or resources limit progress. A library can win under a different precision, layout, or workspace contract.

The decision order is therefore correctness contract, operation and traffic estimate, one-mechanism hypothesis, controlled measurement, then accept or reject. Never deploy an optimization automatically because it lies near a particular roof.
