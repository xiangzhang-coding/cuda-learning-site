A09 does not publish an “educational sort kernel.” It derives three contracts from known primitives: [selection (TERM-150)](/en/glossary/#term-150) decides which items remain, [stream compaction (TERM-151)](/en/glossary/#term-151) writes them to a contiguous output, and [sorting (TERM-149)](/en/glossary/#term-149) establishes key order. Once the composition is understood, a production decision starts from CUB and Thrust contracts.

## What you should be able to do

- Write stable selection as `flag -> exclusive scan -> scatter`.
- Derive the compacted count from the last scan position and flag.
- Describe bounded-key stable ordering with a histogram, exclusive scan, within-bin ranks, and scatter.
- Explain why atomic slot allocation can guarantee unique destinations without guaranteeing stability or low contention.
- Write a decision packet across CUB `DeviceRadixSort`, CUB `DeviceSelect`, Thrust algorithms, and custom code.
- Separate an algorithm contract, library availability, correctness evidence, and measured performance.

## Prerequisites

The exact prerequisites are `A03, A04`. A03 supplies inclusive/exclusive scan, block totals, and offset propagation. A04 supplies histogram bins, atomics, privatization, and merge. A09 uses that vocabulary without making the CCCL API a prerequisite.

## Keep the three contracts separate

Selection emits values or indices that satisfy a predicate. Compaction additionally requires contiguous output positions `0..count-1`; with original-order prefix ranks it is stable compaction. Sorting declares key projection, direction, stability, key/value movement, equal-key policy, and output ownership. One implementation can combine these actions, but their acceptance criteria remain distinct.

## Derive compaction positions from scan

Compute a zero-or-one `flag[i]` for every input. An exclusive scan over flags gives `position[i]`. If `flag[i] == 1`, scatter the item to `output[position[i]]`. The final `count = position[n-1] + flag[n-1]`; an empty input needs a separate contract.

Because an exclusive prefix counts selected items strictly before the current item, selected positions are unique, contiguous, and increasing in input order. The central composition is **flag -> exclusive scan -> scatter**. Scan establishes destination ownership, while scatter performs movement; neither stage is optional.

## Selection is a predicate and payload contract

A predicate may inspect a value, key, stencil mask, or external flags. The payload may be a value, index, or key/value pair. In-place versus out-of-place behavior, aliasing, output capacity, selected-count type, stream, and order must be declared. `unique` additionally needs equivalence and adjacent-versus-global semantics; a similar name does not make it arbitrary predicate selection.

## Understand bounded-key sorting from histogram, scan, and movement

For a finite key domain, one counting or radix pass has four conceptual steps: histogram to count each bin; exclusive scan over counts to obtain bin starts; a within-bin rank for each item; and scatter of key/payload to `bin_start + rank`. When digit passes repeat, every pass needs stable rank and movement if it is to preserve prior-digit order.

Histogram plus scan supplies bucket boundaries, not a unique stable rank for every item in one bucket. A per-item prefix, stable partition primitive, or another declared algorithm must fill that gap. An atomic increment can assign unique slots, but arrival order is not input order, so it does not establish stable sorting.

## Atomics: correct ownership and contention are different claims

An atomic counter can assign different slots to concurrent writers and therefore support unordered compaction. It does not preserve original selected-item order and supplies no timing fact. A hot counter, key distribution, privatization, merge, and architecture affect contention behavior; a shared source-level target establishes only a hypothesis.

## Production choice: begin with the exact owner contract

CCCL v3.4.2 is this page's immutable selected owner release. Its tagged platform-support table limits CCCL 3.x to latest-patch CUDA Toolkit 12.x and 13.x and excludes the site's Toolkit 11.8 lane. A 12.9.2 or 13.3.1 decision packet may evaluate v3.4.2. The 11.8 path must use its Toolkit-bundled older CUB and Thrust or select and review a compatible CCCL 2.x coordinate; it cannot project v3.4.2 onto 11.8.

CUB `DeviceRadixSort` supplies device-wide radix sort, and CUB `DeviceSelect` supplies `Flagged`, `If`, and `Unique` production primitives. The traditional device-wide form queries and receives temporary storage and names a stream. Thrust supplies higher-level `sort`, `stable_sort`, and `copy_if` vocabulary and chooses a backend through execution-policy and iterator contracts.

The educational composition explains flags, prefix ranks, bin offsets, movement, stability, and ownership, but it is not a production implementation. A production decision compares operation semantics, types and iterators, stability, temporary storage, stream or execution policy, maintenance, Toolkit/CCCL version, correctness fixtures, and the measured workload. Without measurement, custom code, CUB, and Thrust cannot be ranked by speed.
