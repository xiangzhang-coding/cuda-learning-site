This unit uses small direct 2D [convolution (TERM-145)](/en/glossary/#term-145) as a learning vehicle for neighborhood algorithms. It reuses A06's halo, cooperative-load, and uniform-barrier reasoning while adding tensor layout, filter layout, stride, dilation, padding, channel reduction, and floating-point acceptance contracts. The teaching equation actually uses the [cross-correlation (TERM-146)](/en/glossary/#term-146) convention common in deep-learning interfaces and explicitly distinguishes it from mathematical convolution.

## What you should be able to do

- Fully declare input, filter, and output tensor shapes, physical NCHW layout, and linear addresses.
- Derive output extents and every output's input-coordinate set from stride, dilation, and padding.
- Distinguish the filter flip of mathematical convolution from this page's cross-correlation convention.
- Extend A06 center/halo staging to a small multi-channel direct 2D operation.
- Give a CPU reference the same semantics, accumulation policy, absolute/relative tolerance, and edge fixtures.
- List graph validation/build, heuristics, plan, workspace, correctness, and determinism gates for a future cuDNN Frontend/API comparison without presuming a hand-written kernel wins.

## Tensor and layout contract

The teaching contract uses dense row-major NCHW tensors: input `X` has shape `[N,C,H,W]`, filter `F` has shape `[K,C,R,S]`, and output `Y` has shape `[N,K,P,Q]`. The final dimension is contiguous, so linear indices are:

- `X[n,c,h,w] -> (((n*C + c)*H + h)*W + w)`
- `F[k,c,fy,fx] -> (((k*C + c)*R + fy)*S + fx)`
- `Y[n,k,oy,ox] -> (((n*K + k)*P + oy)*Q + ox)`

Stride `(u_h,u_w)` is the movement of adjacent output origins in input coordinates. Dilation `(d_h,d_w)` is the input spacing between adjacent filter taps. Zero padding `(p_h,p_w)` defines a virtual width of zeros on each side of each spatial axis. This page uses symmetric zero padding and does not store padding slots in the input allocation.

For positive stride/dilation and nonnegative padding, output extents are `P = floor((H + 2p_h - d_h(R-1) - 1) / u_h) + 1` and `Q = floor((W + 2p_w - d_w(S-1) - 1) / u_w) + 1`. The contract first confirms that the numerators produce legal positive output extents; a kernel cannot infer shape from launch geometry.

A layout name is not a complete contract. Also state element type, accumulation type, filter/output channel meanings, whether tensor strides really are dense NCHW, and whether buffers may alias. Changing to NHWC or a non-contiguous view changes the linear formulas, coalescing reasoning, and library descriptors together.

## Mathematical convolution and teaching cross-correlation

This page uses cross-correlation:

`Y[n,k,oy,ox] = sum over c,fy,fx of X_or_zero[n,c,oy*u_h + fy*d_h - p_h,ox*u_w + fx*d_w - p_w] * F[k,c,fy,fx]`

`X_or_zero` returns 0 for an out-of-domain spatial coordinate and performs no out-of-bounds read. Filter coordinates `fy,fx` are used in storage order without flipping. This choice matches common naming in many deep-learning convolution APIs, but the teaching contract still states it explicitly.

Mathematical discrete convolution flips the filter along both spatial axes, for example by using `F[k,c,R-1-fy,S-1-fx]`. A symmetric filter can make both operations produce the same result, so correctness fixtures include an asymmetric filter. A page cannot say only “convolution” and omit the flip convention, and CPU and GPU paths cannot silently choose different conventions.

Every output is a reduction over `C*R*S` terms. Even with correct coordinate semantics, a different accumulation order can produce floating-point variation. That belongs in the reference/tolerance contract and cannot be hidden as a terminology difference.

## Direct neighborhood reuse: extend A06

For a `T_y x T_x` output tile, `R x S` filter, stride `(u_h,u_w)`, and dilation `(d_h,d_w)`, each input channel needs a dense bounding patch with extents:

- height: `(T_y - 1)u_h + (R - 1)d_h + 1`
- width: `(T_x - 1)u_w + (S - 1)d_w + 1`

Padding changes only the patch origin and which positions generate 0; it does not change this bounding-box arithmetic. Dilation can leave holes in the mathematical footprint. A simple teaching baseline may stage the complete box, while a sparse loader needs a separate coverage proof.

The synchronous direct path keeps A06's phases: block threads cooperatively load one input-channel patch or load channels in stages, all participants reach the barrier, valid output owners accumulate over filter taps and channels, and the block establishes any required reuse boundary before overwriting storage for another channel or tile. An edge thread with no legal output may still own a halo load and cannot return before the barrier.

Adjacent outputs reuse overlapping input positions, and multiple outputs also reuse the same filter values. Reuse arithmetic compares only logical references with staged positions. Shared capacity, occupancy, extra address work, barriers, cache behavior, and the channel loop affect actual behavior, so this page derives no performance claim from reuse counts.

## CPU reference, fixtures, and tolerance responsibilities

The CPU reference shares exactly the same NCHW/filter layouts, cross-correlation convention, output-shape formula, stride, dilation, zero padding, element conversion, and accumulation contract as the teaching path. A reference is not merely a similar-looking nested loop; it is the oracle for every output coordinate.

Fixtures include at least an all-zero input, impulse input, all-one input and filter, asymmetric filter, rectangular shape, edge padding, stride greater than 1, dilation greater than 1, and channel count greater than 1. Each fixture validates output shape before every output value and any guard or sentinel region.

An integer teaching case can use exact comparison. A floating-point case declares reference accumulation type/order, absolute tolerance, relative tolerance, NaN/Inf policy, and failure report before execution. A common rule is `abs(actual-expected) <= atol + rtol*abs(expected)`, but `atol` and `rtol` must fit the problem scale rather than act as site-wide constants. Bitwise equality, determinism, and a numerically acceptable result are separate requirements.

## Production comparison: a future pinned cuDNN Frontend/API workflow

A hand-written direct kernel exists only to learn layout, neighborhood reuse, and correctness contracts. Production comparison should move to a pinned cuDNN Frontend/API workflow rather than assume the teaching kernel is faster or a better default.

Future work includes at least these gates:

1. **Component pin:** Fix the complete matrix of cuDNN library, cuDNN Frontend, CUDA Toolkit, driver, GPU, and build environment.
2. **Semantic parity:** Construct the graph with identical tensor/filter layouts, dimensions, stride, dilation, padding, data/compute types, and cross-correlation convention.
3. **Graph validation/build:** Record graph validation and build as separate outcomes; a descriptor mistake is not kernel performance.
4. **Heuristics/plan selection:** Record the heuristics mode, candidate engine configurations, filters, and selected execution plan without projecting one automatic choice as universally best.
5. **Workspace:** Query and record plan workspace bytes, alignment, allocation/lifetime, and stream ordering, with an explicit fallback policy for failure or an exceeded budget.
6. **Correctness/determinism:** Pass the same CPU oracle and tolerance before measurement; separately state determinism scope, repetition policy, and allowed numerical variation.
