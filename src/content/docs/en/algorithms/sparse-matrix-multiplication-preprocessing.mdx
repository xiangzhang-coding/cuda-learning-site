[Sparse matrix-matrix multiplication (SpMM, TERM-174)](/en/glossary/#term-174) multiplies sparse A by dense B to produce dense C. [Preprocessing (TERM-175)](/en/glossary/#term-175) can build auxiliary data for a reused sparsity pattern. [External workspace (TERM-176)](/en/glossary/#term-176) leaves temporary device storage required by an operation and algorithm under caller management. A13 explains these steps through representation and lifetime instead of jumping directly to an API recipe.

## What you should be able to do

- State shapes and element equations for sparse-times-dense `C=A B` and hand-calculate an SpMM with an empty row.
- Compare `MKN` dense contributions with `nnz*N` sparse contributions while retaining index, gather, row-imbalance, and output costs.
- Distinguish descriptor metadata for format, shape, index and stored-data types, layout, and ordering from call-level operation, compute type, and algorithm choices.
- Distinguish lifetimes of persistent matrix storage, caller-managed external workspace, and optional preprocessing data.
- Decide when pattern reuse might amortize preprocessing and list changes that invalidate acceleration data.
- Form a testable choice among workspace, determinism, algorithms, and dense GEMM rather than inventing a winner.

## SpMM contract

Freeze `A` as an `M x K` sparse matrix, `B` as a `K x N` dense matrix, and `C` as an `M x N` dense output. Begin with `C=A B`, or `C[i,j]=sum_k A[i,k]B[k,j]`. This fixture has no transpose, batch, `alpha/beta`, mixed precision, or sparse output. Every entry is a finite integer, so the hand calculation uses exact integer arithmetic.

Every stored entry `(i,k,a)` in sparse A contributes `a*B[k,j]` to N columns of C. A direct row-oriented schedule therefore contains `nnz*N` scalar product contributions rather than dense `M*K*N`; it also reads index metadata, selects a B row through k, and handles uneven row lengths.

Calculate by row:

- `C[0,:] = 4*B[0,:] - B[2,:] = [4,8]-[3,0] = [1,8]`
- `C[1,:] = [0,0]` because row 1 of A is empty
- `C[2,:] = 2*B[1,:] + 3*B[4,:] = [0,2]+[3,12] = [3,14]`
- `C[3,:] = 5*B[0,:] + 7*B[3,:] = [5,10]+[14,-7] = [19,3]`

Thus `C = A B = [[1, 8], [0, 0], [3, 14], [19, 3]]`.

## An auditable comparison with dense GEMM

Here `M=4,K=5,N=2`. The dense definition contains `M*K*N=40` scalar product contributions. Traversing six stored entries and updating two output columns contains `nnz*N=12`. A's FP32/32-bit-index payload is also `80 B` when dense and `68 B` in CSR. These values prove only that this contract skips 28 zero products and removes 12 B from A's payload.

They omit B/C traffic, row offsets beyond the stated payload, control around index decoding, cache lines, transaction overfetch, load imbalance, parallelism, conversion, workspace, preprocessing, and implementation-specific tiling. Regular dense GEMM tiles can reuse A and B predictably. A sparse schedule exchanges fewer contributions for indices, gathers, and irregularity. Choosing the faster path requires shape, density and distribution, N, format, precision, algorithm, workspace, hardware, and measurement; `12 < 40` cannot decide it.

## A descriptor is a representation contract across stages

The cuSPARSE 13.3 Generic API uses descriptors to record shape, sparse storage format, index base and type, stored value type, dense layout, and pointers. A descriptor is not a second copy of values. It is host-side metadata that references caller-owned device arrays. Operation and transposition, compute type, algorithm, and scalar or output semantics are separate call-level parameters, and all dimensions and types must be compatible.

That explains why “I have a pointer to values” is insufficient. Identical bytes mean different things in COO and CSR. Zero- and one-based indices change index meaning. Row-major and column-major layouts change dense address mapping. 32- and 64-bit indices change storage and accepted range. L13 owns exact constructors and destruction, streams, scalar location, status, and error handling.

## Workspace and preprocessing lifetimes

For an exact operation and algorithm combination, query its buffer size first. Allocate at least that much caller-managed device workspace only when the returned size is greater than zero; zero means that exact combination needs no external workspace. Workspace is temporary or acceleration storage, not part of the CSR payload. Its size cannot be guessed from `nnz` alone, and a result for one version and algorithm is not a universal constant.

That conditional requirement is itself an algorithm trade-off. The current cuSPARSE 13.3 table lists COO ALG1, ALG3, and ALG4 plus BSR ALG1 as requiring no extra storage, while COO ALG2 and the listed CSR and CSC algorithms require additional memory. This is a pinned owner-document fact, not a workspace cost measured by the site, and it cannot be reused outside its operation, format, layout, and version.

cuSPARSE 13.3 explicitly provides optional SpMM preprocessing. Current owner documentation reports a preprocessing benefit only for CSR ALG1 and CSR ALG3; preprocessing has no effect for the other listed format and algorithm combinations. Acceleration data binds to the sparse descriptor, indices or sparsity pattern, and active workspace. Preprocessing with a different buffer makes the former buffer inactive. Repeated calls can amortize preparation only while the exact reuse contract remains intact.

This still does not mean “always preprocess.” A one-shot operation may offer no reuse. A workspace budget may exclude an algorithm. Required determinism, transpose, batch, format, layout, or data type can change allowed choices. A13 does not reproduce the enumerator support table and does not turn an owner performance note into a local observation.

## Decision ledger

Record at least these axes before choosing sparse SpMM or dense GEMM:

| axis | freeze or query | do not infer |
| --- | --- | --- |
| representation | `M,K,N,nnz`, row distribution, format, base, index/value types, ordering, duplicates | “sparse” automatically saves space or time |
| operation | transpose, batch, dense layouts, compute type, output semantics | B/C traffic from A density alone |
| algorithm | exact cuSPARSE/component version, supported combination, determinism requirement | an eternal default or bitwise identity across environments |
| workspace | exact buffer-size query, budget, owner, and lifetime | fixed bytes or that more is faster |
| preprocessing | exact support, pattern reuse count, invalidation and lifetime | one preparation benefits every call |
| evidence | independent reference, tolerance, warm-up, retained attempts, Environment Manifest | timing, speedup, or a winner from a static ledger |

The output should be a falsifiable candidate such as “for a fixed CSR pattern and larger N, test whether a supported algorithm with reusable preprocessing beats a matched dense baseline,” not a production recommendation.
