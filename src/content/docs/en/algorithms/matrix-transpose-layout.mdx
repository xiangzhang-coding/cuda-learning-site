A [matrix transpose (TERM-140)](/en/glossary/#term-140) moves input coordinate `(row, col)` to output coordinate `(col, row)`. It is a useful vehicle for learning layout transformations: the mathematical work is small, but row-major addresses, coalesced global access, shared-memory rearrangement, barriers, edge tiles, and bank mapping must all be correct together.

## What you should be able to do

- State the shape, address, and one-writer contract of a rectangular row-major transpose.
- Judge the global reads and writes of a thread traversal separately for adjacent addresses.
- Explain how a shared-memory tile converts a contiguous load direction into a contiguous store direction.
- Prove that every block participant reaches `__syncthreads()` uniformly between edge guards.
- Explain how physical `T x (T + 1)` tile padding changes bank mapping without changing the logical `T x T` matrix.
- Separate layout-based expected observations, an actual EX14 execution record, and any timing claim.

## Transpose contract: shape and addresses before kernels

The input has `rows` rows and `cols` columns in row-major storage, so coordinate `(row, col)` has linear address `row * cols + col`. The transposed output has `cols` rows and `rows` columns, with this contract:

`output[col * rows + row] = input[row * cols + col]`

The valid domain is `0 <= row < rows` and `0 <= col < cols`. This mapping is a bijection from the input index set to the output index set: every input element is read once, and every output element has exactly one owner. A square matrix is only a special case. A rectangular fixture immediately exposes the error of using `cols` as the output leading dimension.

The CPU reference applies the same shape and mapping to construct expected output. Because transpose copies values element by element, verification exact-compares every element and also checks that the output allocation contains `cols * rows` elements. Transpose changes coordinates and physical order, not values.

## Global access: review reads and writes separately

Suppose adjacent `threadIdx.x` values increase `col` along one input row. Their reads of `input[row * cols + col]` visit adjacent global addresses, which is the expected address pattern for [coalescing (TERM-073)](/en/glossary/#term-073). If those threads directly write `output[col * rows + row]`, however, their addresses differ by `rows`. A contiguous read does not automatically imply a contiguous write.

Reversing the thread assignment can make output stores contiguous while making input reads strided. The useful question is not whether “transpose is coalesced,” but what `lane -> address` mapping each global phase has:

| phase | fixed coordinate | coordinate changed by adjacent lanes | row-major address delta |
| --- | --- | --- | ---: |
| direct input read | `row` | `col` | `1` |
| direct output write | output `col` | output `row` | `rows` |

This table is expected access reasoning, not a transaction trace, bandwidth result, or speedup observation. Alignment, element size, the active-lane mask, edge guards, and the exact GPU still belong to an actual observation's environment.

## Shared tile: rearrange ownership on chip

A tiled transpose separates the global phases. First, a block's threads cooperatively load a logical `T x T` tile along input rows into shared memory. After a block barrier, they exchange tile coordinates and cooperatively store along output rows. Shared memory acts as layout-changing staging, so the global load and global store may each use a contiguous lane direction.

The proof ledger for every value names four owners: its input global coordinate, shared write coordinate, shared read coordinate, and output global coordinate. The transposed block coordinate must also be exchanged. Swapping only tile-local row and column without swapping the tile's grid position writes the wrong region when a matrix contains multiple tiles. EX14 derives those local coordinates from a one-dimensional thread ID rather than depending on a particular two-dimensional block shape.

The shared tile does not alter the mathematical transpose contract. It changes only the path from input address to output address and the layout of intermediate physical storage.

## Barriers and edge guards: predicate data, not rendezvous

Rectangular dimensions are commonly not multiples of `T`. The load guard checks input `(row, col)`. The store guard uses exchanged output coordinates and checks that output row is below `cols` and output column is below `rows`. The predicates may describe the same value, but similar variable names do not make them interchangeable.

The correct block phase is: every thread computes coordinates, valid threads load a shared slot, every block participant uniformly executes `__syncthreads()`, and valid output owners then read a transposed shared slot and store. An invalid edge thread may skip a load or store, but it cannot return before the barrier. Otherwise, some threads can wait for a participant that has exited, violating the barrier contract.

The edge proof also confirms that a legal store never reads an unwritten shared slot. The direct method proves that every legal output coordinate's transposed source coordinate also satisfies the corresponding input guard instead of assuming that the entire partial tile was initialized.

## Physical +1 padding: change bank stride, not the logical matrix

In a simplified model with 32 banks and one bank word per `float`, a physical row stride of `T` can make a warp's column-wise shared-tile read repeatedly map to the same bank. Changing the allocation from `tile[T][T]` to `tile[T][T + 1]` advances each physical row by one additional bank position and changes the bank mapping of the transposed read.

This [bank padding (TERM-142)](/en/glossary/#term-142) adds one unused slot to each physical shared row. Logical coordinates remain `0 <= tile_row, tile_col < T`; input and output matrix shapes, the transpose formula, global allocation, and numerical result do not change. The padding column is not a new logical matrix column, and the output leading dimension does not become `T + 1`.

“The +1 changes the expected bank mapping for this access pattern” is static reasoning. Actual bank behavior, conflict counters, or elapsed time require an exact architecture, element width, access instruction, and measurement record. This page has no such observations.

## Retrieval check

1. Why must a row-major transpose use `output[col * rows + row]`, especially for a rectangular matrix?
2. Why can one direct traversal make input reads contiguous while output writes advance by `rows`?
3. How does a shared tile decouple the global load direction from the global store direction?
4. Why must an edge-invalid thread still reach the block barrier, and what does each guard check?
5. What does a physical `T x (T + 1)` allocation change, and what explicitly remains unchanged?
