[Coordinate format (COO, TERM-171)](/en/glossary/#term-171) retains a row, column, and value for every stored entry. [Compressed sparse row (CSR, TERM-172)](/en/glossary/#term-172) compresses repeated row numbers into row offsets. [Sparse matrix-vector multiplication (SpMV, TERM-173)](/en/glossary/#term-173) then gathers `x` at those positions and reduces each row. These are representation and algorithm contracts, not a slogan that sparse is always faster.

## What you should be able to do

- Construct zero-based, row-sorted COO and CSR arrays with unique coordinates from a two-dimensional matrix.
- Account for dense, COO, and CSR payload from `m`, `n`, `nnz`, value width, and index width.
- Represent an empty row with repeated row offsets and recover each row's half-open entry range.
- Hand-calculate `y=A x` while separating contiguous matrix-value scanning, index reads, `x` gathers, and row reduction.
- Explain why format, index base and type, ordering, and duplicate policy must be fixed before a library call.
- Separate static payload and operation ledgers from evidence about actual traffic, timing, and speedup.

## Sparse representation contract

First freeze logical matrix shape `m x n`, stored-entry count `nnz`, value type, index type, index base, entry ordering, and duplicate policy. This page uses `m=4`, `n=5`, `nnz=6`, FP32 values, 32-bit indices, zero-based indexing, row-then-column ordering, and one unique coordinate per entry.

“Nonzero” means the six mathematical nonzeros retained by this fixture. A real data pipeline that keeps explicit zeros, prunes by a threshold, or permits duplicate coordinates needs a separate conversion and mathematical contract; it must not assume that a library combines duplicates. The cuSPARSE 13.3 storage-format page supports zero- and one-based indices and warns that correctness is not always ensured when column indices repeat within a row.

## COO: retain the complete coordinate for every entry

Scanning the six stored entries in row-major coordinate order gives:

- `row_indices = [0, 0, 2, 2, 3, 3]`
- `column_indices = [0, 2, 1, 4, 0, 3]`
- `values = [4, -1, 2, 3, 5, 7]`

Each array has length `nnz=6`. Stored entry `k` is the tuple `(row_indices[k], column_indices[k], values[k])`. COO states coordinates directly, which is useful for assembly and interchange, but pays for two indices per entry. Current owner documentation describes COO as row sorted while allowing column indices within one row to be sorted or unsorted. That format-level statement must not be expanded into a universal performance claim across every operation, algorithm, and version.

## CSR: compress row numbers into offsets

CSR retains the same `column_indices` and `values` and replaces six row indices with this length-`m+1=5` array:

`row_offsets = [0, 2, 2, 4, 6]`

Row `r` owns the half-open range `[row_offsets[r], row_offsets[r+1])`. Row 0 reads entries `[0,2)`, row 1 reads empty range `[2,2)`, row 2 reads `[2,4)`, and row 3 reads `[4,6)`. The final offset equals `nnz`, and offsets are nondecreasing. Repeated `2,2` denotes a zero-length row range, not a duplicate coordinate.

## Storage ledger: index metadata occupies space too

Let value width be `b_v` and index width be `b_i`. Count only matrix A payload, excluding allocators, alignment, descriptors, and workspace:

- Dense: `mn b_v`
- COO: `nnz (b_v + 2b_i)`
- CSR: `nnz (b_v + b_i) + (m+1)b_i`

Substituting `m=4,n=5,nnz=6,b_v=b_i=4 B` gives `80 B` for dense, `72 B` for COO, and `68 B` for CSR. This tiny matrix saves only 8 B or 12 B, which demonstrates why density alone does not choose a representation. Shape, index width, row count, explicit zeros, conversion cost, and downstream operations all belong to the decision. This storage footprint is not an observed GPU transferred-byte count.

## SpMV: reduce stored entries by row

Choose `x=[1,2,3,4,5]` and define `y=A x`. CSR row ranges give:

- `y_0 = 4*x_0 + (-1)*x_2 = 4*1 - 1*3 = 1`
- `y_1 = 0` because `[2,2)` contains no stored entry
- `y_2 = 2*x_1 + 3*x_4 = 2*2 + 3*5 = 19`
- `y_3 = 5*x_0 + 7*x_3 = 5*1 + 7*4 = 33`

Therefore `y = [1, 0, 19, 33]`. This entails six value-vector products and six contributions to the corresponding row accumulators, whereas a dense row traversal examines 20 matrix positions. Sparse traversal also reads indices and gathers `x` through `column_indices`; row lengths `[2,0,2,2]` shape the available parallel work. Fewer mathematical contributions do not automatically imply fewer hardware transactions or less elapsed time.

## High-level boundary to cuSPARSE

The cuSPARSE 13.3 Generic API places format, shape, index base and type, stored data type, and arrays into descriptors. Operation, compute type, and algorithm remain a separate call-level contract. The caller queries external device workspace for that exact combination and allocates a buffer only when the returned size is nonzero. Current SpMV documentation also exposes optional preprocessing and algorithm-specific determinism and performance trade-offs. Those are current owner facts, not observations from this page.

A12 asks only why a library needs complete representation metadata and why a repeated sparsity pattern can make preprocessing relevant. Exact descriptor constructors, buffer-size queries, algorithm enumerators, lifetime and error handling, and Runnable Example EX20 are all deferred to L13. Do not infer fixed workspace bytes, a fastest algorithm, observed determinism, structured-sparsity support, or a current hardware winner from A12.
