[Softmax (TERM-166)](/en/glossary/#term-166) normalizes a row of logits into nonnegative weights that sum to one. This Learning Unit begins with equivalent transformations, reduction state, and data movement rather than a framework call. It derives [numerically stable softmax (TERM-167)](/en/glossary/#term-167) and [online normalization (TERM-168)](/en/glossary/#term-168).

## Softmax contract

For a nonempty vector of finite real logits `x`, define:

`p_i = exp(x_i) / sum_j exp(x_j)`

Every `p_i >= 0`, and `sum_i p_i = 1` in real arithmetic. This teaching contract first restricts the domain to finite inputs. NaN, positive or negative infinity, and all-masked-row policies must be declared by a caller; ordinary comparisons must not decide them accidentally.

Softmax is invariant under a common shift. For every constant `c`:

`exp(x_i - c) / sum_j exp(x_j - c) = exp(x_i) / sum_j exp(x_j)`

The numerator and denominator share a factor `exp(-c)`, which cancels to recover the original expression.

## Max shift: avoid overflow without promising universal exactness

Choose `m = max_j x_j`, then compute:

`p_i = exp(x_i - m) / l, where l = sum_j exp(x_j - m)`

Every `x_i-m <= 0`, so the shifted exponentials cannot overflow from a large positive exponent. At least one exponential is 1, so finite inputs satisfy `1 <= l <= n` in real arithmetic. Very small terms can still underflow to zero, sum/reduction order can still change low bits, and the stable form is not bitwise exact.

For `x = [1000, 1001, 1002, 1003]`, `m=1003`; the shifted exponentials are approximately `[0.04978707, 0.13533528, 0.36787944, 1]` and `l=1.55300179`, giving:

`p ~= [0.03205860, 0.08714432, 0.23688282, 0.64391426]`

Directly evaluating `exp(1003)` is not an acceptable baseline. These values are a rounded real-arithmetic reference, not a GPU observation.

## Online normalizer: combine maximum and sum in one scan

Start with `m_0 = -infinity, l_0 = 0`. When value `j` arrives, update:

`m_j = max(m_{j-1}, x_j)`

`l_j = l_{j-1} * exp(m_{j-1} - m_j) + exp(x_j - m_j)`

The recurrence preserves `m_j = max_{k<=j} x_k` and `l_j = sum_{k<=j} exp(x_k-m_j)`. When a new maximum appears, `exp(m_{j-1}-m_j)` rescales the old denominator into the new reference frame instead of discarding prior terms.

For the same fixture, `(m_j,l_j)` is approximately `(1000,1)`, `(1001,1.36787944)`, `(1002,1.50321472)`, and `(1003,1.55300179)`. Online state combines maximum and denominator into one input pass. If every `p_i` must be emitted, another input read is still required unless logits remain in fast storage.

## Memory-traffic ledger

Declare the boundary first: separate FP32 input and output at 4 bytes per element; scalar max/sum state retained in fast storage; no exponential array stored; cache hits, cache lines, write allocation, and transaction overfetch excluded from the logical element count.

| schedule | input reads | output writes | logical total |
| --- | ---: | ---: | ---: |
| stable three-pass: max, sum, output | `3n` | `n` | `4n elements` |
| online normalizer plus output pass | `2n` | `n` | `3n elements` |

For `n=4`, the schedules count 64 B and 48 B. The 16 B difference is static analysis, not actual DRAM bytes, elapsed time, or speedup. If logits reside in cache, state spills, or an implementation stores another intermediate, rewrite the ledger.

## Fusion boundary: remove one write and later read

Suppose intermediate `Z` between adjacent stages has `M` elements of `b` bytes each. If a fused consumer can use Z in the declared fast store, Z has no other consumer, Z need not persist, and Z does not spill, then avoiding materialization removes one write and one later read:

`traffic removed = 2M elements = 2Mb bytes`

Fusion preserves mathematical softmax but can change registers, shared-memory footprint, occupancy, parallelism, instruction mix, compilation, and scheduling. `2Mb` supports only “these requests leave this logical ledger,” not “execution must be faster.” If another consumer needs the probabilities or fused state spills to slow storage, those terms cannot be removed.

## Numerical verification

A credible acceptance packet includes an independent high-precision reference; a finite/non-finite policy; a predeclared absolute-plus-relative tolerance; `p_i >= 0` and sum-near-one invariants; a large-offset fixture; and a shift-invariance check between `softmax(x)` and `softmax(x+c)`. Reduction order, approximate exponential, and FMA choices can change low bits, so bitwise equality is not a general FP32 criterion.

Max shifting addresses an overflow path. It does not automatically settle underflow, NaN propagation, all-masked rows, or arbitrary precision requirements. Each extension needs its own input domain and acceptance contract.
