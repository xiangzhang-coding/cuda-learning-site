An elementwise map applies the same transform independently to every logical element. This Learning Unit derives disjoint writes, a scalable grid, and a separate memory movement ledger from one ownership contract: each output element has one owner thread. The `load -> map/transform -> store` path describes the algorithm; it is not a measured performance result.

## What you should be able to do

- State `output[i] = f(input[i])` as a map contract with a domain, index, and bounds.
- Assign every output element to one owner thread and prove that writes cannot conflict across threads.
- Account separately for global-memory loads and stores and for host-to-device and device-to-host transfers.
- Cover every positive input length with a rounded-up grid and a bounds guard.
- Distinguish expected reasoning derived from source from runtime observations and performance evidence.

## Map contract: one transform over an index set

For a one-dimensional output of length `n`, the minimum contract is:

```text
domain: i is an integer in [0, n)
value:  output[i] = transform(input[i])
read set for i:  input[i]
write set for i: output[i]
```

A binary map merely extends the read set to `left[i]` and `right[i]`. The transform may add, scale, or evaluate a predicate, but the ownership proof does not depend on that arithmetic. If `input` and `output` alias, an additional proof must show that an in-place write cannot replace a value another thread still needs. “It looks elementwise” is not an alias contract.

## Ownership: exactly one writer per output

Define `owner(i)` as the thread whose global index equals `i`. Every valid `i` needs all three properties:

1. **Coverage:** some launched thread has global index `i`.
2. **Uniqueness:** the launch's global-index mapping does not map two threads to `i`.
3. **Isolation:** `owner(i)` writes only `output[i]`, while `owner(j)` writes only `output[j]`.

The write sets are disjoint whenever `i != j`. A map kernel therefore needs neither a barrier nor an atomic for these output writes. This conclusion does not say when the host may read the result; completion remains part of F04's host/device lifecycle contract.

## Memory movement: account beyond arithmetic

At kernel-semantic level, a binary float map requests two global-memory loads, one transform, and one global-memory store for each valid element. This value count is not a hardware transaction count and is not observed bandwidth.

The application-level ledger separately includes:

```text
host input --H2D copy--> device global memory
device loads --map/transform--> device store
device global memory --D2H copy--> host output
```

An invocation may omit H2D when inputs already reside on the device. It may defer D2H while a later kernel consumes the result. Those are lifecycle choices and do not change the mathematical map contract. Conversely, counting only element arithmetic omits data movement and cannot explain end-to-end performance.

## Scalable grid: cover data and guard extra threads

The one-dimensional baseline is:

```text
i = blockIdx.x * blockDim.x + threadIdx.x
if i < n:
  output[i] = transform(input[i])
```

The host chooses the block count with ceiling division so the launch covers at least `n` indices. The last block may contain extra threads; the bounds guard prevents them from issuing a global load or store. A grid-stride loop can cover work beyond a convenient single-launch geometry, but every iteration must preserve unique ownership and valid bounds.

Scalable means the ownership rule is not tied to a fixed `n`. It does not mean larger inputs must run faster. Block size, occupancy, cache behavior, and transfer overlap require their own environment and measurement contracts.

## Production baseline: preserve the simple contract

In production, elementwise work may be handled by framework fusion, an iterator library, or a specialized kernel. Preserve the same value and ownership contract, and treat the established production path as the comparison baseline. A hand-written teaching kernel exists to learn and understand indexing, bounds, and the memory path, not to replace a maintained production implementation by default.

Before comparing alternatives, verify identical inputs, outputs, precision, alias policy, and transfer boundaries. Shorter source, fewer launches, or consecutive addresses are reasons to measure, not observed performance.

## Evidence boundary: expected reasoning is not observed performance

| Expected reasoning reviewable from the contract | Observation that requires a run record |
| --- | --- |
| Every valid output has one owner | Whether the kernel completed correctly under a specific Environment Manifest |
| Every valid element requests the declared loads and store | Actual transactions, cache behavior, bandwidth, and duration |
| A rounded-up grid plus guard covers a partial block | Actual launch configuration, error state, and output comparison |

This page has no compilation evidence, runtime evidence, expected observations, or recorded observations. Any future performance claim must record exact source, Toolkit Lane, GPU, problem shape, transfer scope, correctness result, and measurement method. Reasoning can identify what is worth measuring; it cannot masquerade as an observed speedup.
