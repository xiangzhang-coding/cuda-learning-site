[General matrix multiplication (GEMM, TERM-147)](/en/glossary/#term-147) starts with shape, layout, scalars, accumulation order, and acceptance rules rather than a tile size. A08 first establishes an obviously correct naive GEMM, then changes repeated global reads into block-local [K-tile reuse (TERM-148)](/en/glossary/#term-148). Every step preserves one mathematical contract.

## What you should be able to do

- State the complete address contract for row-major `A[M,K]`, `B[K,N]`, and `C[M,N]`.
- Explain why one output owner performs K multiply-adds in a naive GEMM.
- Derive the load, barrier, compute, barrier, and reuse phases of shared-memory tiling.
- Write separate guards for partial M, N, and K tiles while proving full block participation at barriers.
- Check FP32 output against an independent double CPU reference with a non-finite policy and absolute-plus-relative tolerance.
- Separate a teaching kernel, future cuBLAS/CUTLASS comparison, and actual performance evidence.

## GEMM contract before kernels

The site freezes a row-major, non-transposed FP32 teaching subset:

`C[row * N + col] = alpha * sum(A[row * K + p] * B[p * N + col]) + beta * C[row * N + col]`

The valid domain is `0 <= row < M`, `0 <= col < N`, and `0 <= p < K`. A has leading dimension K; B and C have leading dimension N. Every `(row,col)` has one writer. K is the reduction extent and does not add output tiles.

## Naive GEMM: establish an explainable baseline

A correct naive GEMM assigns one thread to one output coordinate, walks one row of A and one column of B, accumulates K products in order, and stores C once. It may reread the same A/B values, but its ownership, bounds, and arithmetic order are explicit. That makes it a correctness baseline for the tiled implementation, not a performance conclusion.

Start with the hand-computable `2x3x2` fixture whose result is `[22,28,49,64]`, then add rectangular and nonzero-beta fixtures. Square-only, beta-zero-only, and tile-aligned-only cases do not cover the full contract.

## Shared-memory tiling: reuse K slices

For a `TM x TN x TK` tile, one block owns one `TM x TN` output footprint. Each K-loop iteration cooperatively loads a `TM x TK` A tile and a `TK x TN` B tile. After a uniform barrier, every output owner accumulates TK products from shared memory. A second barrier ensures every old-slice read completes before any thread overwrites the shared arrays.

This changes the data path, not the GEMM equation. `threadblockCount = ceil(M/TM) * ceil(N/TN)`. Each block loops through `ceil(K/TK)` slices; K slices are not extra output blocks.

## Partial M/N/K tiles and barriers

M/N guards choose output owners and final stores. K-tail guards choose shared loads; out-of-bounds A/B slots receive neutral zero so that no iteration reads an old shared value. A thread without a valid output may still own a valid shared load, and every block thread must reach both `__syncthreads()` calls. It cannot return before a K-loop barrier.

EX15 freezes a portable `16x16x16` baseline with 256 threads and two shared arrays totaling 2,048 bytes. Ordinary FP32 multiply-add, shared memory, and block barriers are available at the declared CC 7.5 baseline. No gated variant is justified for this teaching contract, so the architecture-specific variant list is empty and the single path is also the portable fallback.

## Numerical checks: reference and tolerance are contracts

The CPU reference accumulates in double and remains independent from device FP32 accumulation. Every finite candidate must satisfy `absolute_error <= atol + rtol * abs(reference)`, with the acceptance threshold `atol + rtol * abs(reference)`. NaN, infinity, and negative tolerances are rejected. A mismatch report names at least the linear index, row, column, reference, candidate, absolute error, and allowed error.

Different valid operation orders or FMA contraction can change low bits, so bitwise equality is not a general contract here. Tolerance is declared from bounded fixtures before CUDA output is observed; it is not widened after a failure.

## Retrieval check

1. What are the three row-major leading dimensions for `A[M,K] * B[K,N]`?
2. Why is a correct naive GEMM a useful baseline for a tiled GEMM?
3. Why does one output block loop over K slices instead of creating an output block per slice?
4. Which guards belong to partial M, N, and K, and why does zero-fill not replace a barrier?
5. Which shared-storage reuse hazard does the second `__syncthreads()` prevent?
