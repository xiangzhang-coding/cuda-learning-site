## Learning outcome

A native forward result is correct, but training fails and compilation cannot infer the result shape. You will separate those failures, derive the vector-Jacobian product and map each claim to its own test. [EX22](/en/examples/adjacent-energy/) provides all canonical code; plan 40 minutes for this unit.

## From eager execution to framework composition

An eager call can read real data. A graph compiler must reason about shapes and devices before those data exist; automatic differentiation must propagate an arbitrary upstream derivative. These needs explain why a raw binding and a forward kernel are insufficient. The selected interface is PyTorch `2.11.0+cu128`, not a promise about every newer release or the stable C++ ABI.

## Schema, backend and import order

`TORCH_LIBRARY(cuda_learning, m)` defines `adjacent_energy(Tensor x) -> Tensor` once. The absence of mutation/alias annotations is a promise: the implementation allocates a fresh result and never modifies x. Separate `TORCH_LIBRARY_IMPL` blocks associate CPU and CUDA implementations with the same name. Do not additionally redefine that name with Python `custom_op`.

The public import is `from cuda_learning_ops import adjacent_energy`. Its package first imports torch, then `_C`, then Python registrations. `_C` loading creates the schema and backend registrations before `register_fake` and `register_autograd` look them up. Calling `torch.ops.cuda_learning.adjacent_energy.default` without first importing the package does not load this project. Reloading registration files is not an idempotence mechanism; ordinary Python import caching handles repeated public imports.

## Fake and meta must describe the real output

`torch.library.register_fake` supplies one storage-free implementation used for both FakeTensors and meta tensors. It checks rank, dtype, layout, contiguity, device family and extent, then returns `x.new_empty((x.shape[0]-1,))`. It reads no tensor values, calls no `.item()` or data pointer and does not launch the CUDA kernel. `torch._check` expresses shape constraints without turning symbolic lengths into Python integers.

Returning `empty_like(x)` is wrong even though dtype and device agree: the length is n rather than n-1. Returning a slice of x has the right length but violates the fresh-output alias contract. Returning a new contiguous tensor also preserves the output stride for offset inputs. An explicit meta call checks a storage-free path; opcheck covers FakeTensor agreement, and dynamic compilation exercises guarded symbolic sizes. These tests serve different purposes.

## Derive the backward, including endpoints

Let `d[i]=x[i+1]-x[i]`, and let `g[i]` be the upstream derivative of y. Set `q[i]=2*d[i]*g[i]`. An interior input belongs to two edges; its contributions have opposite signs.

| Input coordinate | Gradient |
| --- | --- |
| First, when n > 1 | `-q[0]` |
| Interior | `q[j-1]-q[j]` |
| Last, when n > 1 | `q[n-2]` |
| Singleton | One zero, because there are no edges |

For `x=[1,-2,2,2.5]` and `g=[1,2,3]`, `q=[-6,16,3]` and `dx=[6,-22,13,3]`. The sum is zero: shifting all inputs together leaves differences unchanged. This invariant alone does not prove every component correct.

EX22's `setup_context(ctx, inputs, output)` saves x with `save_for_backward`. Its backward uses ordinary differentiable PyTorch operations: left-pad q with zero and subtract right-padded q. For empty q both are a length-one zero tensor. There is one gradient return for one input. This also permits the second derivative tested by `gradgradcheck`. No private autograd implementation is imported, and no handwritten CUDA backward kernel is required.

## Which check proves which claim?

| Check | Target and limit |
| --- | --- |
| Full CPU/CUDA reference comparison | Forward values for the selected corpus; not gradient registration |
| `torch.library.opcheck` | Schema, autograd registration, fake and AOT-dispatch integration; not a numerical derivative proof |
| `torch.autograd.gradcheck` | Float64 finite-difference derivative comparison with explicit eps/tolerances |
| `torch.autograd.gradgradcheck` | Second derivative behavior for supplied cases |
| `torch.compile(..., fullgraph=True, dynamic=True)` | Compiled forward and backward across lengths; no silent graph break, but no promised kernel fusion |

Use nonuniform g to expose endpoint and sign errors hidden by a sum reduction. Include n=1, ordinary lengths and block tails. Invalid-input checks must remain aligned between native and fake paths. The custom call remains opaque to compiler fusion. Source review, host integration checks and a browser rendering are not CUDA observations: EX22/LAB13 remain **Pending Hardware Verification**, compilation evidence empty.

## Retrieval check

1. Why must `_C` load before fake registration?
2. Which two contracts does a sliced fake output violate or satisfy?
3. Why does an interior input receive two gradient contributions?
4. Why can opcheck pass without proving the derivative formula?
5. What does fullgraph compilation promise, and what does it not promise?
