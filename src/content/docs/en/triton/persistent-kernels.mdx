## Learning goals

Turn a one-program-per-tile GEMM into a bounded cyclic work schedule, prove coverage and choose a fair nonpersistent comparison. Explain why fewer programs do not prove higher occupancy or fewer host launches. Allow 60 minutes plus the implementation Exercise. Reading has no hardware gate; all device observations below require an external supported environment.

## Exact prerequisites

**[T04, T05, Q09]**: [blocked GEMM](/en/triton/blocked-matrix-multiplication/), [phase-separated autotuning](/en/triton/autotuning/) and [occupancy, stalls and throughput](/en/correctness/occupancy-stalls-throughput/). [LAB16](/en/labs/autotune-triton-gemm/) supplies the existing original nonpersistent kernel, input/oracle contract and reporting method.

## From a tile grid to longer-lived workers

Ordinary tiled execution lets the GPU scheduler dispatch many independent blocks. Persistent scheduling instead gives each launched program a loop over several work items. This is useful when software can exploit reuse or control work distribution, but adds loop state and a load-balancing obligation. A persistent program lasts longer within a launch; it is not a permanently running service. Both the ordinary GEMM and this persistent GEMM perform **one host kernel launch**. Reducing the number of programs is not automatically launch fusion.

## Prove ownership before measuring

Let `Tm=ceil(M/BM)`, `Tn=ceil(N/BN)` and `T=Tm*Tn`. For positive dimensions choose `1 ≤ P ≤ T`. Launch `P` programs; program `p` visits tile IDs `p, p+P, p+2P, …` while the ID is below `T`. Decode each ID as row tile `t // Tn`, column tile `t % Tn`. The nonpersistent fallback assigns one program to each of the `T` tiles.

For any tile `t`, division by `P` uniquely yields `t=qP+r`, with `0 ≤ r < P`; program `r` owns that tile exactly once. The loop step must equal the **actual launched program count**, obtainable with `tl.num_programs(0)`, not an unrelated SM count. A valid initial policy is `P=min(T,S)`, where `S` is the actual device's SM count, but that is a proposal, not a residency guarantee. Empty dimensions must return on the host without a zero-step loop; this Exercise accepts positive dimensions only.

Reset the FP32 accumulator **inside** each output-tile iteration. Recompute row/column pointers, keep all M/N/K masks and zero-filled K tails, finish the whole K reduction and store FP16 once. Keeping the accumulator outside the tile loop mixes different outputs. Moving the K loop outside changes reuse and state requirements and is a different experiment. No cross-program communication or global barrier is needed because each output tile has a single writer.

## Residency is a resource constraint

For this standard NVIDIA backend experiment with `num_ctas=1`, a program maps to a CTA; `num_warps` controls its warp count. The device scheduler places CTAs on SMs. Program ID does **not** name an SM, and `P=S` does not promise one CTA on every SM or simultaneous residency. Never build a spin-wait global barrier on that assumption: waiting CTAs can prevent unscheduled producers from running.

Resident CTAs per SM are limited jointly by register allocation, shared memory, threads/warps, barriers and architectural block limits. A rough bound takes the minimum of those capacities; real allocation granularity matters, so a ratio of register counts is not an exact occupancy calculation. Theoretical warp occupancy is resident warps divided by the architecture's maximum resident warps. Achieved occupancy is measured over execution and can differ because of scheduling, tails and imbalance. Neither is the fraction of lanes doing useful work, nor a speedup prediction.

Larger BM/BN increase accumulator state; larger BK or more pipeline stages can increase shared memory and live values. More warps can spread work yet consume more thread resources. Compiler-generated resource usage must be inspected on the actual target; do not infer it from source tensor size alone. A long-lived CTA can improve reuse while reducing eligible warps or competing-kernel responsiveness. Use [Q09](/en/correctness/occupancy-stalls-throughput/) to relate resources, active/eligible/issuing warps and stalls to throughput, rather than maximizing an occupancy percentage.

## Work distribution and tail effects

For a **synthetic** `T=10, P=3`, ownership is `[0,3,6,9]`, `[1,4,7]`, `[2,5,8]`. Tile counts differ by at most one; durations need not. Edge masks, cache behavior or variable work can create stragglers. Ordinary scheduling can distribute remaining CTAs dynamically, whereas this cyclic assignment cannot steal work from a busy program. A dynamic atomic queue is a separate design with contention, termination and memory-ordering costs; it is not required here.

When `T<P` would otherwise occur, cap P at T. With one tile, both schedules reduce to one program and the same tile work: this case validates correctness but provides no meaningful evidence for a multi-tile scheduling benefit. When T is only slightly above P, loop overhead and uneven tails may outweigh reuse. Host model tests in `scripts/triton-diagnostics/contract.py` verify cyclic ownership only, never physical execution.

## Explicit architecture and workload gates

Use native Linux x86_64, ordinary CPython **3.14.7**, Triton **3.7.1**, torch **2.13.0**, the EX23 full hash lock, one visible NVIDIA GPU and driver **≥ 580.65.06**. Require **≥ 8 GB total and ≥ 2 GB free** before the experiment. Record actual CC, SM count, memory, compiler/`ptxas`, Toolkit, driver and lock identity. ## Compare a hypothesis, not a label

First implement both schedules on a learner copy of LAB16. For every shape and P, compare against an independent FP64 CPU product of the stored FP16 inputs, using the existing elementwise `atol=0.02, rtol=0.01`, finite checks, input immutability and a tail write guard. Include all cases even when the new kernel is slower. Matching two broken GPU kernels is not an oracle.

Keep environment/setup, per-target compilation, correctness, any tuning search, device warm-up and steady-state measurements separate as in T05. Start with the fixed tile above rather than independently tuning both implementations and calling the result a scheduling-only effect. Warm each candidate and the fallback with **20 launches**, synchronize, then retain **three alternating-order rounds**, all raw event samples and median/min/max per shape and P. Use LAB16's `do_bench` budgets **25 ms warmup, 100 ms rep**, `return_mode='all'`, identical preallocated resident inputs/outputs and cache policy. Disable debug printing, assertions and profiling in timing runs. Instrumented counter collection is separate; record clocks, power, competing load and synchronization policy.

The Environment Manifest also needs exact source hashes/commit, candidate list, grids, dtype/strides/tolerances, GPU count/CC/SMs/memory, OS/compiler/tool versions, observer/date, raw reports and sanitized derivative custody. Record one-shot cost separately if it matters. State “slower” or “inconclusive” when appropriate; a timing difference alone does not identify occupancy as the cause.
