## Why blocking survived new programming models

Classical blocked GEMM reuses A and B fragments for many output products. CUDA exposes threads and shared-memory cooperation; Triton expresses tile values and leaves their physical layout to the compiler. Tensor Cores make supported matrix instructions valuable, but `tl.dot` is an operation contract, not proof of a particular instruction or speedup. Inspect generated artifacts for the exact target. This original Lab uses a two-dimensional grid; it does not reproduce the owner's grouped-program tutorial or its performance claims.

## Give every output tile one owner

For contiguous row-major A of shape `(M,K)` and B of shape `(K,N)`, addresses in elements are `A[m*K+k]`, `B[k*N+n]` and `C[m*N+n]`. The launch grid is `(ceil(M/BM), ceil(N/BN))`. Program `(pm,pn)` owns rows `pm*BM + [0,BM)` and columns `pn*BN + [0,BN)`.

Each K iteration loads a `(BM,BK)` block and a `(BK,BN)` block, then updates a `(BM,BN)` accumulator. There are `ceil(K/BK)` iterations. Broadcasting `rows[:,None]` and `inner[None,:]` constructs A's pointer matrix; B uses `inner[:,None]` and `columns[None,:]`. Logical positions are not individual CUDA threads. Each valid output has one owner, so no atomic operation or inter-program barrier is needed.

## Three masks solve different boundaries

| Operation | Required validity | Invalid contribution |
| --- | --- | --- |
| A load | row less than M AND inner less than K | zero |
| B load | inner less than K AND column less than N | zero |
| C store | row less than M AND column less than N | no write |

Zero is neutral for the product sum, unlike softmax's maximum padding. A store mask cannot protect an earlier load. `tl.where` around an unmasked load cannot make it safe. Do not wrap invalid output coordinates modulo M or N: that can duplicate ownership. With `(M,N,K)=(65,97,63)` and `(BM,BN,BK)=(32,64,32)`, grid `(3,2)` has six programs and two K iterations. The last tile has one valid row and 33 valid columns; the final K position 63 must not be loaded.

## State precision at every boundary

LAB16 accepts finite, contiguous rank-2 **FP16 inputs**, values with magnitude at most 4, dimensions 1–512, and compatible inner dimensions. It performs forward-only multiplication with no bias, activation, gradients, batches, transpose or arbitrary strides. `tl.zeros(..., tl.float32)` and `tl.dot(a,b,accumulator)` keep the accumulator FP32; the final store explicitly rounds to FP16.

Input storage rounding, accumulation order and output rounding are separate. FP32 accumulation cannot recover values lost at the FP16 input boundary. `input_precision` governs FP32 dot inputs on supported targets; setting it does not improve FP16 inputs here. TF32, BF16, FP8 and FP32 input variants require separate contracts. Compare against the **stored FP16 values** promoted to double, not the original random draws.

## Test every candidate before timing

The Lab uses `(M,N,K) = (1,1,1), (17,19,33), (32,32,32), (65,97,63), (128,128,128), (256,192,257)`. They cover tiny work, exact tiles, each tail and a longer reduction. Deterministic signed inputs include cancellation; repeated rows/columns reduce oracle cost without skipping any output check.

The independent scalar oracle uses `math.fsum` of double products of stored values. Require every output finite and `abs(actual-reference) <= 0.02 + 0.002*abs(reference)`. This fixed teaching tolerance accommodates FP16 output rounding; it is not a universal GEMM error bound. The Linux CPU gate checks that oracle against FP64 `torch.mm` with absolute error at most `1e-10`. Every GPU candidate and the native FP16 baseline must separately pass. NaN initialization catches missing stores; a 2048-element NaN tail and unchanged inputs catch some write defects, not all unsafe loads. Never widen tolerance to make a failed candidate win.

## Relate logical reuse to resources

One full K tile logically reads `2*(BM*BK + BK*BN)` FP16 bytes and performs `2*BM*BN*BK` arithmetic operations under the conventional multiply-plus-add count. Its FP32 accumulator holds `4*BM*BN` logical bytes. These are ledgers, not observed DRAM traffic or a per-thread register allocation. Larger BM/BN increase reuse and accumulator pressure together; larger BK changes padding and pipeline resources. Grid size, occupancy, compiler layout and the workload distribution all affect the outcome.
