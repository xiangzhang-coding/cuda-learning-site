## Learning goals

A wrong pointer location, stale borrowed view, or incorrectly packed scalar can invalidate an otherwise correct kernel. In about 30 minutes, build a device/context/storage ownership table, derive launch geometry and argument widths, and identify the completion point that makes CPU inspection legal. Use this model for explicit launches and integration debugging, not as a recipe for resetting another library's CUDA state.

## Prerequisites

Complete [P01](/en/python/cuda-python-bridge/) and [F07: Runtime and Driver APIs](/en/foundations/runtime-driver-api/), exactly `[P01, F07]`. P01 supplies the single environment profile; F07 explains explicit context and native handle responsibilities. [EX21](/en/examples/cuda-python-launch/) supplies the sole executable implementation. ## Object syntax retains the Driver API model

The Runtime API can make context setup appear implicit; the Driver API exposes context selection and handles more directly. Python object APIs make that model easier to express but do not erase it. Core 1.2.0 builds on native CUDA objects with shared ownership and selected cleanup methods, not a uniform file-like `close()` protocol. Understanding that distinction is more durable than memorizing a list of constructors.

## Select a device, then establish its context

`Device.get_all_devices()` enumerates CUDA devices. `dev = Device(0)` initializes driver access and identifies visible device 0; it does not by itself establish the intended current context. Call `dev.set_current()` before creating resources. In this default path it retains and selects the device's **primary context**, returns `None`, and exposes the context through `dev.context`. Do not assign the return value as if it were the context.

Device state is thread-local. This standalone example is not a general context-switching helper for an existing application. Calling `set_current(ctx)` with an explicit context has different previous-context behavior and is not an automatic restore-on-exit context manager. If later embedding this work, design how to preserve the caller's current context rather than resetting it on exit.

Inspect `dev.device_id`, `dev.name`, `dev.compute_capability`, and `dev.arch`; `arch` is a string such as `"75"`, not `"sm_75"`. The primary context is shared state. Do not destroy/reset it, issue an unbalanced raw primary-context release, or call `Context.close()` while it is current. Core manages this shared lifetime. There is no `Device.close()` step.

## Bytes, host views, and owners

Create an owned stream with `dev.create_stream(options=StreamOptions(nonblocking=True))`. Nonblocking refers to the legacy NULL-stream synchronization relationship; it does not mean the host waits for completion. Allocate device bytes with `dev.allocate(nbytes, stream=s)` and pinned host bytes with `LegacyPinnedMemoryResource().allocate(nbytes, stream=s)`, retaining the memory resource and Buffers as appropriate.

The device resource may use a pool or a synchronous fallback. The legacy pinned resource uses synchronous host allocation. An explicit `stream=` parameter therefore does not prove asynchronous allocation or overlap.

A host view has the shape `(ctypes.c_float * n).from_address(int(h.handle))`, where **h must be host-accessible pinned storage**. Never apply it to a device-only Buffer. Converting a handle to `int` provides an address value, not CPU access permission. The view borrows memory and does not keep h alive; h must outlive every view access and queued transfer. Byte capacity and element type must agree: n float32 values require `4*n` bytes.

## Copy to an explicit destination

Use `d.copy_from(h, stream=s)` for host-to-device input and `d.copy_to(h, stream=s)` for device-to-host output. Both arguments are Buffers of equal byte size; these calls do not accept arbitrary Python lists as equivalent storage. Unequal capacities raise `ValueError` rather than copying the shorter length.

The omitted destination in `d.copy_to(stream=s)` is a trap: allocation uses the source memory resource, so the returned Buffer need not be host memory. A Python variable named `host_output` cannot change that. With ordinary copy options, CUDA infers direction from the pointers; explicit host and device ownership still belongs to the application.

Trace the canonical range as an ownership proof: initialize pinned inputs and a NaN output sentinel, upload both inputs and the sentinel, launch, order D2H into the explicitly allocated pinned output, and call `s.sync()` before CPU comparison. ## Kernel arguments have a binary contract

<CanonicalCode exampleId="EX21" range="kernel" />

The entry point takes three float pointers and an `unsigned int n`. Pass core Buffers for the pointer arguments and `ctypes.c_uint32(n)` for n. In core 1.2.0, a plain Python `int` is packed at pointer width; it is not inferred to be a C `unsigned int` by reading the kernel signature. Likewise a Python `float` is packed as double, so a `float` scalar would need `ctypes.c_float`.

This is **kernel argument marshalling**: turn host values into the widths and representations expected by device code. A small integer that appears to work on a particular machine is not an ABI proof. Validate range before constructing the ctypes scalar; conversion must not silently wrap an invalid count into the accepted range. Keep the pointed-to data alive through execution, regardless of when the scalar bytes are consumed for submission.

## Predict geometry and exact results

`LaunchConfig(grid=(n + 255) // 256, block=256)` covers a positive n with a one-dimensional grid. For 1003, blocks cover candidate indices 0 through 1023. The final block has 235 useful threads and 21 inactive tail threads; the kernel must test the logical bound before either reading inputs or writing output. For n=0, take a host-side policy such as rejection or a documented no-op, never submit a zero grid. EX21's run path requires positive size.

Three device arrays cost `12*n` payload bytes, or 12036 at n=1003, separate from equal pinned host payload, compiler memory, and context/library resources. The actual device target must be supported by NVRTC and meet EX21's CC 7.5 floor; a numerically larger architecture is not automatically a supported target.

Correctness requires checked completion, finite values, and comparison of all 1003 elements with the independent CPU reference. The binary-fraction fixture makes exact equality appropriate. A correct tail guard cannot repair a mispacked scalar or a missing copy; prove each contract independently.

## Finish work before releasing owners

| Resource | Normal-success release boundary |
| --- | --- |
| Program and Linker | May close after their independent output bytes are obtained |
| ctypes host views | Stop using and drop them after completed D2H and comparison, before closing their host Buffers |
| Device and host Buffers | Close with `buffer.close(stream=s)` after last use; retain the stream for queued deallocation |
| Owned stream | Call `s.sync()` again to drain queued frees, then `s.close()` |
| ObjectCode and Kernel | No public `close()`; retain owners through completion, then release references |
| Shared primary context and Device | Let core manage shared lifetime; no reset, raw destroy, or invented Device close |

`Kernel` retains library ownership. `ObjectCode.handle` is a `CUlibrary`, not a legacy `CUmodule`; never pass it to `cuModuleUnload` or manually unload a library still owned by core. Releasing a Python reference is not a universal promise of immediate destruction.

On failure, stop submitting work, retain the first error, attempt checked completion and cleanup of acquired resources, and report subsequent errors separately. Stream destruction does not replace checked completion. Legacy pinned deallocation synchronizes its stream before freeing; Buffer RAII cleanup may report warnings rather than raise every deallocation error. Keep warnings/stderr and explicit sync errors, and never double-free via raw bindings. If an asynchronous fault prevents a clean drain, terminate with failure instead of validating or claiming a healthy reusable context.

## Find the earliest broken contract

An immediate `ValueError` from a size mismatch differs from library loading, symbol lookup, launch submission, and `s.sync()` failures. CUDA copy calls can surface an earlier asynchronous launch error. The line that observes the error may not be the line that caused it.

For a failed run, retain the stage and exception, actual buffer capacities and location, kernel parameter types, n/grid/block, device/target, and stream ownership. Verify `sync()`, not the nonexistent `synchronize()` spelling. Do not “repair” a pointer by dereferencing device memory on the CPU or catch an exception and print a successful comparison of stale host values.

## Keep measurement outside the correctness claim

One explicit stream makes the dependency chain inspectable, not concurrent. Nonblocking stream creation and pinned memory do not prove overlap. CPU initialization, allocation, compilation/linking, lazy loading, copies, and cleanup can dominate an end-to-end interval. A future kernel-only measurement needs an appropriate device timing boundary and warmed repetitions; a host timer must include checked completion if claiming completed work. EX21 records no timing or speedup.

## Guided practice: Draw and inspect a complete lifecycle

1. Copy the ownership table onto a worksheet and mark the owner of each of the six Buffers, each host view, the stream, and kernel/library references. Predict the 1003-element geometry and byte counts before execution.
2. In the matching external Linux profile from P01, use the standalone EX21 directory. If not prepared, run the setup script; then inspect the environment:

```sh
bash scripts/setup.sh
.venv/bin/python ex21.py check-environment
```

3. Compare actual package identities with the profile and native library identities with NVRTC/nvJitLink 13.3.33. Device access, the driver, and target support remain separate checks. Record a blocker and stop if a required gate fails.
4. Only with the runtime gate satisfied, run the canonical correctness path:

```sh
.venv/bin/python ex21.py run --size 1003
```

5. Retain real stage diagnostics, full-output verdict, mismatch details if any, exit status, warnings, and an Environment Manifest. Locate the first checked completion and the second drain before stream closure in the source. Do not introduce a deliberately invalid GPU memory access as a diagnostic exercise.

**Acceptance:** The worksheet identifies explicit H2D/D2H destinations, a 32-bit unsigned n, a tail guard, and owner lifetimes through completion. A real run must pass every element and exit successfully without hiding failures; an unavailable GPU yields a blocker, not a pass. No output shown here is an observed run.

3. What can happen when the destination is omitted from `copy_to`?
