Thrust is useful here as an algorithm vocabulary: name the transformation, scan, ordering, or composition contract before discussing its backend. An [execution policy (TERM-181)](/en/glossary/#term-181) selects a system and, for CUDA policies, can attach work to a stream. A [fancy iterator (TERM-182)](/en/glossary/#term-182) represents a generated, transformed, or zipped range without requiring a stored array for every logical input.

## What you should be able to do

- Map `thrust::transform`, inclusive/exclusive scans, and sorting APIs back to A01, A03, and A09 contracts.
- Choose explicit or iterator-derived dispatch without assuming pointers are validated or migrated.
- Compose counting, transform, and zip iterators while stating system, extent, value/reference, and lifetime boundaries.
- Distinguish `thrust::cuda::par.on(stream)` from `par_nosync.on(stream)` and place required completion edges.
- Avoid v3.4.2 deprecations and known issue boundaries without claiming local compilation, runtime behavior, fusion, or speedup.

## Transform names A01's ownership contract

`thrust::transform` applies a unary or binary callable elementwise and returns the output-end iterator; this is the library vocabulary for [A01](/en/algorithms/elementwise-map/). The exact input/output range may be in place. Other partial overlap violates the tagged interface precondition. The binary form requires both input ranges to cover the requested extent. Do not make correctness depend on the identity or address of functor arguments; that use is deprecated.

An explicit policy chooses a system. A policy-free overload derives systems from iterators and seeks a compatible common system. Neither form verifies logical extents, object lifetime, or numerical acceptance.

## Scan names A03's prefix contract

`thrust::inclusive_scan` and `thrust::exclusive_scan` expose the prefix operations from [A03](/en/algorithms/inclusive-exclusive-scan/). Inclusive output includes the current item. Exclusive output begins from the declared initial value, or the default zero form. A custom operator must be associative; commutativity is not required. Exact in-place input/output is supported, while partial overlap is not.

The tagged interface warns that pseudo-associative operations such as floating-point addition may produce different results across executions. Therefore a parallel floating-point scan must use a problem-specific acceptance rule and cannot be assumed to match a serial left fold bit for bit.

## Sort names A09's ordering and movement contract

`thrust::sort` and `thrust::stable_sort` apply ordering to mutable random-access ranges and require a strict weak ordering; these names connect directly to [A09](/en/algorithms/sorting-selection-compaction/). `sort` does not preserve the order of equivalent elements. `stable_sort` does. The by-key forms move a value range with the key range, and the tagged contract forbids key/value overlap.

Stability, comparator semantics, range extent, mutability, and movement remain application decisions. Tagged CUDA implementation choices such as radix or merge paths are version-specific implementation details, not public promises or performance evidence.

## Execution policies, dispatch, and streams

| Form | v3.4.2 decision boundary |
| --- | --- |
| `thrust::seq` | Selects sequential execution |
| `thrust::host` | Selects the configured host system; invocation and dereference order remain unspecified |
| `thrust::device` | Selects the configured device system; with the CUDA backend it does not validate or migrate supplied memory |
| No explicit policy | Derives systems from iterators; incompatible host/device systems normally fail at compile time |
| `thrust::cuda::par.on(stream)` | Uses the supplied stream; tagged transform, scan, and sort backends perform their optional synchronization before returning |
| `thrust::cuda::par_nosync.on(stream)` | Permits optional synchronization to be omitted and may return before completion; it is a hint, not a promise that no synchronization occurs |

Same-stream work remains ordered by enqueue order, so a no-sync producer can feed a same-stream consumer without a host wait. Host access, memory release, or another stream needs a valid completion/dependency edge. Algorithms returning host values can still require completion. Asynchronous CUDA errors can surface at a later synchronization point. Allocations and callables must outlive unfinished work.

The tagged v3.4.2 `temporary_buffer.h` default no-sync path first tries `cudaMallocAsync`/`cudaFreeAsync` and can fall back to synchronous allocation; `util.h` selects the legacy or per-thread default stream according to compilation mode. These are source-derived implementation facts, not observed allocation, synchronization, or latency behavior on a Learning Site environment.

## Iterator composition without materializing every range

The current v3.4.2 `<cuda/iterator>` surface provides `cuda::counting_iterator`, `cuda::transform_iterator`, `cuda::zip_iterator`, and `cuda::zip_transform_iterator`. A counting iterator represents consecutive values. A transform iterator applies a callable on dereference. A zip iterator advances components together and exposes tuple-like values or references. A zip-transform iterator combines lockstep dereference and n-ary transformation.

One composition can represent indices with a counting iterator, map each index to a segment key with a value-returning transform iterator, and consume that virtual key range with scan-by-key. Another can zip equally sized keys and payloads for a lockstep transform. Such virtual ranges can avoid storing an intermediate range and can enable optimization, but they do not guarantee kernel fusion, lower traffic, or speedup.

Write four contracts before composing:

- **Extent:** every consumed range covers the same declared logical interval; zip does not safely stop at the shortest component.
- **System:** component iterators and explicit policy select a compatible host or device path.
- **Value/reference:** transformations over temporary values return values rather than dangling references.
- **Lifetime:** containers, callable state, stream, and output remain valid until required work completes.

## A composition packet

For “square values, inclusive-scan them, then stable-sort records by the prefix,” first state three stages rather than write an opaque chain. Stage one is an A01 transform with `N` inputs and outputs. Stage two is an A03 inclusive scan whose FP32 tolerance permits valid parallel order differences. Stage three is an A09 stable by-key sort with `N` keys and `N` records under a strict weak ordering. Record each range's system, extent, overlap, lifetime, stream, and completion edge.

You may replace the materialized square array with a transform iterator only after checking the scan consumer's iterator contract and callable lifetime. You may not claim fusion or fewer transactions without inspecting and measuring the selected artifact in an exact environment.

## Current deprecations at this pin

The core algorithms taught here, including `transform`, scans, and sorts, are not deprecated in v3.4.2. Legacy `thrust::counting_iterator`, `thrust::transform_iterator`, and `thrust::zip_iterator` are also not formally deprecated at this pin, although current owner guidance generally prefers newer `cuda::` iterator counterparts.

CCCL 3.4 deprecated `thrust::constant_iterator` and `thrust::strided_iterator` in favor of `cuda::constant_iterator` and `cuda::strided_iterator`. The tagged source also deprecates several `thrust::tuple`, functional aliases, iterator traits, and standard-like iterator helpers in favor of `cuda::std` or `cuda::` forms. Check the exact tagged declaration rather than generalizing that every fancy iterator is deprecated.

## Scoped known issues for v3.4.2

- Issue [#10684](https://github.com/NVIDIA/cccl/issues/10684) documents legacy host `reverse` with a `thrust::zip_iterator`, including a descending sort-by-key path. Its fix landed after the immutable v3.4.2 release, so this pin must not publish that composition as validated.
- Open issue [#10965](https://github.com/NVIDIA/cccl/issues/10965) reports incorrect distance behavior for the optional-stride legacy `make_counting_iterator(start, stride)` form. Use unit-stride counting or a separately checked modern composition at this boundary.
- Open issue [#1155](https://github.com/NVIDIA/cccl/issues/1155) reinforces that legacy zip equality and distance follow one component. Require aligned extents instead of expecting shortest-range termination.
- Issue [#2747](https://github.com/NVIDIA/cccl/issues/2747) tracks tagged `stable_sort` documentation examples that invoke `sort`. Do not copy those examples; the textual stable-order contract remains the authority.

This is a scoped teaching ledger, not an exhaustive defect list. Issue state after v3.4.2 does not mutate the pinned release.
