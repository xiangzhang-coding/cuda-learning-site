After writing a correct tiled matrix multiplication, the next step is not to assume it deserves optimization. Establish a trustworthy library comparison for the same problem first. cuBLAS cannot discover the rows and columns behind a pointer. It knows only the shapes, strides, and operations you declare. Legal arguments with the wrong interpretation can still produce a correctly sized, numerically wrong result.

## Learning goals

Allow about 25 minutes for the unit, paper checks, and retrieval questions. You should be able to derive arguments from a storage diagram rather than memorize a tuple of `m,n,k`: explain handle state, cover every transpose combination, separate precision from scalar location, and identify when results can be read or released. External Lab time is additional.

## Why retain a column-major interface?

Basic Linear Algebra Subprograms (BLAS) separates common operations from their implementations. Matrix-matrix multiplication is a Level-3 operation that can reuse data across substantial arithmetic. cuBLAS provides these operations on GPUs while retaining the column-major convention familiar to Fortran callers.

The explicit-handle interface introduced in CUDA 4.0 exposes device, stream, and scalar-passing state instead of hiding it in the legacy global interface. This unit uses `cublas_v2.h`, not the deprecated `cublas.h` interface. `cublasSgemm` is the specialized homogeneous FP32 entry point; `cublasGemmEx` lets callers declare storage and computation types separately. Library implementations can change, so the library name proves neither a particular instruction nor performance or bitwise results.

## Write the mathematical problem first

General Matrix Multiplication (GEMM) specifies `C_out = alpha * op(A) * op(B) + beta * C_in`. `op(A)` has shape `m x k`, `op(B)` has shape `k x n`, and C has shape `m x n`. Thus `m,n,k` describe the shapes **after the operations**, not necessarily the allocated rows and columns of A and B.

`CUBLAS_OP_N` leaves a matrix unchanged, `CUBLAS_OP_T` transposes it, and `CUBLAS_OP_C` applies a conjugate transpose. T and C are numerically equivalent for real data, but not for complex data. An operation flag changes how values are read; it does not move data or change the physical stride.

With `beta != 0`, preserve and initialize `C_in` correctly. With `beta == 0`, the old C need not be valid input, but C must still supply enough writable output storage. "No old-value read required" does not mean "a null output pointer is valid." This unit uses positive dimensions, valid integer ranges, and disjoint A, B, and C storage, keeping degenerate problems and alias rules out of the first call proof.

## Addresses and leading dimensions

The leading dimension, `ld`, is the distance between adjacent physical column or row starts **in elements**, not bytes. For zero-based coordinates `(i,j)`, the column-major element offset is `i + j*ld`; the row-major offset is `i*ld + j`. Allocation sizes additionally multiply by element size and require overflow checks.

Consider a column-major `3 x 2` matrix with `ld=5`. Its first column uses offsets 0, 1, and 2; its second uses 5, 6, and 7. Offsets 3 and 4 are padding. Element `(2,1)` is at offset 7, not 5. A submatrix of a larger allocation moves the starting pointer but keeps the parent allocation's column spacing. Replacing `ld` with the submatrix's row count would read different elements.

The BLAS one-based indexing convention in NVIDIA's guide does not require an unused element before a C++ pointer. GEMM takes the start of storage; host address calculations here remain zero-based. In contrast, BLAS routines that **return a position**, such as `cublasIsamax`, return a one-based position. For a valid nonempty vector and positive `incx`, returned position p maps to zero-based element offset `(p-1)*incx`. Convert a returned position at the boundary rather than adding one to every GEMM address.

## Derive leading dimensions for every transpose

This is a column-major derivation table, not a performance recommendation. Abbreviate `M=max(1,m)`, `N=max(1,n)`, and `K=max(1,k)`. Shapes below are the **untransformed storage shapes**. Every row requires `ldc >= M`, with C storage covering `ldc*n` elements.

| `transa,transb` | A storage shape | B storage shape | Minimum `lda` | Minimum `ldb` |
| --- | --- | --- | --- | --- |
| N,N | `m x k` | `k x n` | M | K |
| N,T | `m x k` | `n x k` | M | N |
| N,C | `m x k` | `n x k` | M | N |
| T,N | `k x m` | `k x n` | K | K |
| T,T | `k x m` | `n x k` | K | N |
| T,C | `k x m` | `n x k` | K | N |
| C,N | `k x m` | `k x n` | K | K |
| C,T | `k x m` | `n x k` | K | N |
| C,C | `k x m` | `n x k` | K | N |

A storage covers `lda*k` for N or `lda*m` for T/C. B storage covers `ldb*n` for N or `ldb*k` for T/C. A legal lower bound proves neither sufficient allocation nor correct values. Checking the last logical element and the complete allocation extent is separate from API argument checking.

Paper check: choose `m=3,n=5,k=2`, with T for A and N for B. A is stored as `2 x 3`, not `3 x 2`; `lda=4` is legal. B is `2 x 5`; `ldb=3` is legal. With `ldc=6`, the three complete storage extents cover 12, 15, and 30 elements. Square or tightly packed cases alone can hide these mistakes.

## Row-major need not require a copy

Suppose the application needs row-major `C = A*B`, with A shaped `m x k` and B shaped `k x n`. The bytes of row-major A can be interpreted as column-major `A^T`. Ordinary transposition gives `C^T = B^T*A^T`: swap operands and change the call dimensions to `n,m,k`. The resulting bytes still represent the application's row-major C.

For an N,N problem with padded row strides `ra,rb,rc`, the first cuBLAS matrix is B with `lda=rb`; the second is A with `ldb=ra`; the output has `ldc=rc`. Both operations remain N. For tightly packed matrices, those strides are `n,k,n`. EX18's fixed FP32 path uses this interpretation, not a hidden data-transposition pass before the call.

More generally, map the row-major target `op_a(A)*op_b(B)` into a column-major call by swapping A/B and `m/n`, and changing the flag order from `op_a,op_b` to `op_b,op_a`. Keep each allocation's physical row stride, then audit the swapped call against the table. For complex data, the outer transformation is an ordinary transpose, not a conjugate transpose: do not additionally conjugate `alpha` or `beta`. This is an algebraic mapping, not permission to mix arbitrary row and column layouts.

[VIS12: GEMM Tiling Hierarchy](/en/visuals/gemm-tiling-hierarchy/) helps identify which inputs along K contribute to an output element. Substitute its logical coordinates into the address formula. It neither exposes cuBLAS's internal algorithm nor proves that a call will use a particular tile.

## Three types and two scalar locations

`GemmEx` storage types describe how to interpret A, B, and C bytes. The compute type declares the computation-precision policy. The scale type determines what `alpha` and `beta` point to. These must form a supported row in the owner table; they are not independently interchangeable choices.

| Combination reviewed here | A/B/C storage | Compute type | `alpha,beta` objects |
| --- | --- | --- | --- |
| EX18 fixed comparison | All `CUDA_R_32F` | `CUBLAS_COMPUTE_32F_PEDANTIC` | `float` |
| Static mixed-precision comparison | A/B `CUDA_R_16F`, C `CUDA_R_32F` | `CUBLAS_COMPUTE_32F` | `float`, not half precision |

The second row is contract reading, not an extension of EX18. `CUBLAS_COMPUTE_32F_FAST_TF32` permits TF32 computation without changing the stored arrays into another data type; it is not another name for the fixed FP32 comparison. Pedantic mode constrains computation policy but promises neither the CPU's serial accumulation order nor an error bound for arbitrary problem sizes.

Pointer mode is independent of precision. With `CUBLAS_POINTER_MODE_HOST`, ordinary GEMM input scalar values are consumed at the call, so their objects may expire after return even while matrix work remains asynchronous. With `CUBLAS_POINTER_MODE_DEVICE`, scalars must be device-accessible, remain alive, and remain unmodified until the computation finishes. A `double*` cannot masquerade as a `float*`, and a host address does not satisfy device mode. Do not transfer host-blocking rules for scalar-output routines to GEMM.

## Explicit streams and resource lifetime

A stream determines submission order. A handle stores mutable stream, pointer-mode, and math-mode state. Select the device before creating `cublasHandle_t`, and keep the associated CUDA context alive and current during use. A handle does not migrate when `cudaSetDevice` changes the device; another device needs its corresponding handle. Concurrent host threads mutating one handle can change the configuration another thread's next call observes.

For the first comparison, choose a named non-default stream and a dedicated handle. Audit the following order. This is a lifecycle plan, not a runtime log.

| Phase | Required condition |
| --- | --- |
| Prepare | Create stream and handle; allocate A, B, and C; retain host inputs and data needed by the independent reference |
| Configure | Bind the stream with `cublasSetStream`; explicitly set host pointer mode and the chosen math policy; check every status |
| Initialize | Order input copies and any required C initialization before GEMM in that stream; keep asynchronous host buffers alive through copy completion |
| Submit | Call GEMM and check `cublasStatus_t`; successful return does not make the result host-readable |
| Observe | Submit result copying in the same stream, explicitly wait for stream completion and check CUDA status, then compare on the CPU |
| Release | After every user finishes, free buffers, destroy the handle, and destroy the stream; on partial initialization failure, release only resources actually created |

If a later consumer uses another stream, add an event record/wait edge. Calling producer and consumer sequentially on the host does not establish a cross-stream dependency. Check both library status and asynchronous errors exposed by copy or synchronization boundaries. After an execution error, an old output is not this invocation's result.

Workspace is extra temporary storage. Traditional cuBLAS can use its default pool. If supplying your own, call `cublasSetStream` before `cublasSetWorkspace`, because setting the stream **unconditionally resets** the user-workspace configuration. User workspace must satisfy the documented 256-byte alignment and remain valid through use. Do not use destruction as the timing endpoint: the 12.9 guide documents an internal device synchronization in `cublasDestroy`, and frequent creation/destruction mixes setup overhead into the comparison.

## Library output still needs an independent reference

A library implementation does not replace a test oracle. Compute a double-precision CPU reference from the application's logical coordinates. Do not reuse the unverified cuBLAS argument transformation to interpret the same mistake. Check every logical output for finiteness and `abs(got-ref) <= 1e-4 + 2e-5*abs(ref)`. The `atol=1e-4, rtol=2e-5` rule belongs to EX18's bounded FP32 fixtures; it is not NVIDIA's universal GEMM guarantee.

[EX18](/en/examples/cublas-gemm/) is this unit's canonical library-comparison Runnable Example: fixed FP32 pedantic computation, row-major swapped operands, a double-precision reference, and the fixtures from [EX15](/en/examples/tiled-gemm/), including a nonzero-beta case. Do not hand-copy a second CUDA implementation into the Learning Unit. General exercises involving `beta` must preserve original C. EX18's project files govern its fixed behavior; the generalization here does not establish coverage of every transpose, padded layout, or mixed-precision case.

Small nonsquare matrices, inputs that distinguish rows from columns, K tails, and padded layouts reveal different errors. Identity and zero inputs are useful but can hide operand and stride mistakes when used alone. Record the first failure's logical coordinate, reference, result, threshold, and environment. Increasing tolerance is not a repair for a layout error.

[LAB12](/en/labs/compare-gemm-with-cublas/) takes correct results into external timing. Before comparing with a handwritten kernel, match inputs, output semantics, precision, repetitions, and timing boundaries. Do not compare one side's kernel time with the other side's allocation, transfer, handle-creation, and execution time. Without retained measurements, report neither a library winner nor a speedup.
