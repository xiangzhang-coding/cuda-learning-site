A synchronization object does not know which application data it protects. The programmer must connect its operations to the payload, its readers, and the next reuse of storage. libcu++ gives that proof a standards-oriented vocabulary; it does not supply the missing proof. This unit reviews contracts on paper, with no CUDA execution or hardware requirement.

## What you should be able to do

- Separate host `std`, the implemented `cuda::std` subset, and scoped `cuda::` extensions.
- Choose scope and memory order independently for an ordinary 32-bit publication flag.
- Prove payload visibility from the release actually observed by an acquire, including object lifetime and reuse boundaries.
- Account for barrier initialization, arrivals, waits, drops, and the next phase's expected count.
- Track pipeline stage ownership from acquire through release and choose a correct fallback without inventing an acceleration claim.

## Prerequisites

The exact prerequisite sequence is [M05: Synchronization Scopes](/en/memory/synchronization-scopes/), [M13: Asynchronous Copy and Pipelines](/en/memory/asynchronous-copy-pipelines/), and [M19: C++ Dialect Boundaries](/en/toolchain/cpp-dialect-boundaries/), or `M05, M13, M19`. They remain the related units for revisiting the mental model, storage protocol, and compilation coordinate. Scope never replaces M05's distinction between atomicity, ordering, rendezvous, visibility, and progress.

## Why a heterogeneous standard library?

Traditional CUDA intrinsics make the execution hierarchy explicit, but an atomic update alone does not express the complete producer/consumer protocol. C++11 supplied standard atomic and memory-order vocabulary; C++20 added facilities including atomic references and reusable barriers. Moving such reasoning into heterogeneous programs requires another question: which threads can participate across the memory and execution boundaries? libcu++ adopts familiar concepts while exposing CUDA-specific scope and asynchronous-operation contracts.

| Surface | What it means | What it does not promise |
| --- | --- | --- |
| Host `std`, such as the host compiler's `<atomic>` | The host standard library and its supported dialect | General device callability or CPU/GPU interoperability for an arbitrary object |
| `cuda::std`, with headers such as `<cuda/std/atomic>` | libcu++'s implemented, standards-oriented host/device facilities | A complete implementation of every standard-library facility or identical availability in every compilation mode |
| `cuda::`, with headers such as `<cuda/atomic>` | Extensions including explicit thread scope and CUDA synchronization objects | A new memory model that overrides storage accessibility, lifetime, or scheduling constraints |

Do not rename a namespace and assume portability is finished. Some familiar newer-standard facilities are provided under supported older language modes; that is not blanket support for the newer dialect. The selected release and the exact header decide availability, not the date of a live C++ draft.

## Atomic scope: name the communicating threads

[Synchronization scope (TERM-077)](/en/glossary/#term-077) determines the participating threads covered by the atomic protocol. It does not choose memory placement or the ordering of surrounding accesses. Both `cuda::atomic` and `cuda::atomic_ref` default to **system scope** in this pin; state the intended scope explicitly rather than relying on that default.

| Explicit scope | Communication covered for this unit | Separate condition |
| --- | --- | --- |
| `cuda::thread_scope_block` | Threads of the same block | Every accessor is in that block and can access the object |
| `cuda::thread_scope_device` | Threads of the same device and memory synchronization domain | Cross-block storage is accessible, and the protocol does not assume all blocks are resident |
| `cuda::thread_scope_system` | Potential CPU/GPU or cross-device participants | The allocation, devices, and operations actually support the required system-scope atomic communication |

A pointer usable from two processors is not by itself proof of system-scope atomic support. Unified or mapped storage still needs its allocation and device capabilities checked. Do not mix concurrent atomic accesses with different scope contracts to the same object. A device-scoped flag cannot authorize communication across different memory synchronization domains merely because both threads run on one GPU.

Widening scope cannot make an unscheduled producer run. An arbitrary grid spin barrier can occupy the device with waiting blocks while the blocks needed to release them cannot execute. Use a documented execution boundary, such as ordered kernel completion between phases, or a separately justified coordination mechanism. Neither system scope nor the strongest memory order supplies a progress guarantee.

## Memory order: prove the publication edge

[Memory order (TERM-185)](/en/glossary/#term-185) describes how an atomic operation orders surrounding accesses. [Memory visibility (TERM-078)](/en/glossary/#term-078) for a non-atomic payload needs a complete relationship, not simply an atomic flag somewhere nearby.

Consider one writer, one reader, a flag initialized to zero before either uses it, and a payload not overwritten during this one-shot exchange. The writer writes the payload, then stores one to the flag with release ordering. The reader loads the flag with acquire ordering. **If that load reads the value from this release store**, and both operations have sufficient compatible scope, the writer's preceding payload write happens before the reader's subsequent payload read. A read of the initial zero gives no permission to consume. In a reused protocol, the numeric value one alone does not identify which generation published it.

| Operation choice | Suitable purpose | Not established |
| --- | --- | --- |
| Relaxed flag operation | Atomic access to the flag itself | Publication of separate non-atomic payload writes |
| Release store, acquire load reading that store | Ordering payload production before consumption | Consumer completion, safe overwrite, or producer progress |
| Acquire-release read-modify-write | A supported operation that needs both directions | Permission to use acquire-release on a plain load or store |
| Sequentially consistent operations | Stronger ordering among appropriately scoped operations | Repair of a too-narrow scope or inaccessible storage |

A load cannot use release or acquire-release order. A store cannot use acquire, consume, or acquire-release order. This unit uses release/acquire, not a consume-dependent protocol. A standalone fence or `volatile` flag is not a substitute for the demonstrated reads-from publication relationship.

For reuse, add a reverse ownership transfer: after consuming, the reader releases an acknowledgement; the writer acquires that acknowledgement before modifying the payload again. Identify each generation or otherwise prove that an old flag cannot be mistaken for a new publication. This adds a second ordering proof, not a promise that arbitrary polling will make progress. A static proof may specify what is safe when an observation occurs without implementing a wait loop.

## `atomic_ref`: borrow an object, not its lifetime

`cuda::atomic` owns its atomic object. `cuda::atomic_ref` applies atomic operations to an existing object; it does not allocate, initialize, relocate, or keep that object alive. Initialization must precede publication to users, and the referenced object must outlive every reference and every access through it.

For the ordinary 32-bit integer case here, v3.4.2's `required_alignment` is `sizeof(T)`, so the object address must satisfy four-byte alignment. Check the actual referenced address, not merely an allocator's base address; a field offset can break the proof. The tagged implementation excludes padding-bit representations. These statements do not authorize arbitrary structures or object sizes.

While references are in use, all accesses to the object must follow the atomic-reference access discipline. Do not keep an ordinary load/store path racing with atomic references, alias overlapping subobjects with incompatible references, or mix scopes concurrently. Destroying a reference neither waits for another thread nor ends the referenced object's lifetime safely. Put object destruction or a return to ordinary access after a proven quiescent boundary.

## Barrier phases: count arrivals before waiting

A [barrier phase (TERM-186)](/en/glossary/#term-186) is one round of expected arrivals and completion. It is not the same thing as a reusable buffer or a pipeline stage. A shared-memory declaration only reserves storage; it does **not** initialize the barrier. One designated initializer establishes the positive expected arrival count, then an independent visibility edge, such as an all-block synchronization, makes that initialization available before anyone uses the barrier. The barrier cannot bootstrap its own initialization.

| Operation or boundary | Current phase | Following phase or storage |
| --- | --- | --- |
| Initialization | Establish the expected count before use | Object remains alive throughout all participating phases |
| `arrive` | Contribute the specified arrival count and obtain the phase token | Arrival alone does not authorize consuming peers' data |
| `wait` with the matching token | Wait for the corresponding phase to complete | Only then consume the data protected by that completion |
| `arrive_and_wait` | Combine one arrival and its wait | Does not prove that every consumer has finished reading |
| `arrive_and_drop` | Contribute this participant's current arrival | Reduce future expected counts; not permission to skip this round and rejoin at will |

With ordinary waiters and the default completion behavior taught here, the phase boundary orders pre-arrival work before the reads authorized after waiting. Independent work may fit between arrival and wait, but dependent reads may not. Tokens belong to the corresponding barrier phase and must not be treated as indefinitely reusable tickets. Future expected counts reset according to the barrier contract, including permanent drops, rather than being manually reset after every tile.

For four participants A, B, C, and D, let A, B, and C each arrive and wait while D uses `arrive_and_drop`. The current round still receives **four** arrivals. The following round expects **three**. Simply omitting D would leave the current round short; making D arrive again in the three-participant round would over-contribute. If D only wants to skip an iteration temporarily, redesign participation rather than calling drop as a pause button.

There are two ownership boundaries for a shared tile: **ready to read** and **safe to overwrite**. Finishing a ready phase permits consumers to start; a fast producer returning from that phase does not know that slower consumers have finished. Add a consumed phase or an equivalent documented handoff before reuse. A barrier-bound `memcpy_async` additionally binds copy completion to its barrier phase; track copy completion separately from the declared thread arrivals and do not treat issuing a copy as a participant's arrival. This unit makes no promise about custom completion or no-wait corner cases.

In the alternating ready/consumed protocol used by the Exercises, A, B, and C each use `arrive_and_wait` in **every** ready and consumed phase. Each continuing participant waits for the current phase to complete before beginning the next phase or making its next arrival. A writes before its ready arrival; B/C read after their ready waits and finish reading before their consumed arrivals; A overwrites only after its consumed wait. Phase names are ledger labels, not arguments that route arrivals: an early arrival labeled "next ready" still decrements the barrier's current countdown. Waiting only in A is therefore insufficient. D contributes once to the first ready phase through `arrive_and_drop` and never rejoins.

## Pipeline lifecycle: own the stage until consumers release it

A [pipeline (TERM-109)](/en/glossary/#term-109) manages a finite FIFO of [pipeline stages (TERM-110)](/en/glossary/#term-110). A stage tracks ownership of in-flight work; the application still owns the associated data buffers. For a shared-state pipeline, `make_pipeline` is collective over its declared group: members use the same shared state and consistent construction arguments, including the producer count or role assignment required by the selected overload.

Unified participation gives each member both producer and consumer duties. Partitioned participation gives specified members producer or consumer duties. The role plan and participant counts must match construction and every stage's operations; a producer-only member does not substitute for a missing consumer release.

| Step | Ownership fact | Storage obligation |
| --- | --- | --- |
| Producer acquire: `producer_acquire` | Wait for and obtain a reusable stage | Do not overwrite a stage still owned by consumers |
| Issue copy work | Attach work to that stage | Source and destination remain valid; source is not modified while the copy may read it |
| Producer commit: `producer_commit` | Submit that producer's batch | Commit is not proof that the destination may already be read |
| Consumer wait: `consumer_wait` | Establish readiness for the stage being consumed | Read only after the required completion boundary |
| Consume | Use the completed payload | Keep the destination stable through the last authorized read |
| Consumer release: `consumer_release` | Relinquish the consumer's stage ownership | Reuse waits for the required consumers and a following producer acquire |

Shared state outlives all pipeline objects using it, and buffers outlive pending copies and consumers. `quit` releases pipeline ownership only; it is not a drain, cancellation primitive, or repair for missing arrivals. End participation through a protocol that accounts for outstanding work, rather than freeing state immediately after quitting.

On the relevant accelerated path, divergent warp commits can entangle batches and cause consumers to wait for more work than their local reasoning suggests. Reconverge the relevant warp participants before commit. This is separate from a cooperative copy's requirement that all members of its declared group invoke the same copy. Neither requirement permits inventing a different group from whichever lanes happen to be active.

## Copy contract: completion survives fallback

[Asynchronous copy (TERM-108)](/en/glossary/#term-108) is an API contract, not a promise that the hardware will overlap it with computation. Select a barrier-bound or pipeline-bound operation and retain its completion protocol.

- Source and destination ranges must be valid, nonoverlapping, and suitable for a trivial byte copy. This is not object construction or a call to a nontrivial copy constructor.
- In a group overload, all members of that group call with the same arguments. In a nongroup overload, each caller issues its own copy; give callers nonoverlapping destination work rather than issuing overlapping copies to the same tile.
- `cuda::aligned_size_t<N>` asserts that **both addresses and the byte count** satisfy the alignment multiple. It is a proof supplied by the caller, not a request to round or realign storage. A false proof is undefined behavior.
- If that alignment proof is unavailable, select an ordinary-size overload that can handle the case, or a deliberately synchronous copy with an explicit producer/consumer handoff. Neither choice removes readiness or safe-reuse obligations.

The eligible global-to-shared `cp.async` acceleration path requires SM80 or newer and its other preconditions. On a semantically supported path without that acceleration, a fallback may perform synchronous movement while preserving the API's completion protocol. Do not delete wait or release because one observed dispatch happens to be synchronous. Optional SM90+ TMA capabilities require a separate transaction-API review and are not taught here.

The exact v3.4.2 copy definitions also have compilation-mode boundaries: barrier-bound `memcpy_async` overload definitions are guarded by `_CCCL_CUDA_COMPILATION`. The library's host/device purpose does not imply a GCC-only translation unit sees the entire asynchronous-copy surface. A CUDA-compiled host dispatch can perform a synchronous copy; that says nothing about device overlap. Live documentation and tagged headers differ in displayed signatures, so this page deliberately gives no function signatures; the tag governs, including a `void` producer commit return rather than an imagined completion receipt.

## Known issues and owner-test limits

As of **2026-09-05**, [issue #10967](https://github.com/NVIDIA/cccl/issues/10967) is open and reports compilation failures for non-power-of-two atomic object sizes 3, 5, 6, and 7. It motivates this unit's conservative ordinary-32-bit boundary; the report was not reproduced locally, and its title is not a proof about every supported type. [Issue #10499](https://github.com/NVIDIA/cccl/issues/10499) is open for unimplemented P2588R3 barrier relaxation. Do not substitute the live C++ draft's relaxed completion wording for this pin.
