A GEMM template can hide the same ownership and synchronization mistakes as a handwritten kernel. Read its types as choices about who owns an output, how operands arrive, and when partial sums become stored results, not as a guarantee that those choices are correct or fast.

## Learning goals

Allow about 40 minutes for source reading, paper derivations, and retrieval. You will trace one retained C++ hierarchy, distinguish three layout layers, reconstruct a two-stage dependency timeline, and state what a future build must establish. This Learning Unit requires no GPU or CUTLASS installation.

## Prerequisites

The exact ordered prerequisites are `A08, L06, M17`: [A08: Tiled GEMM Correctness](/en/algorithms/tiled-gemm-correctness/) supplies output ownership and the K-reduction invariant; [L06: cuBLAS GEMM](/en/libraries/cublas-gemm/) supplies shapes, leading dimensions, and numerical types; [M17: Choosing Compiler Architecture Targets](/en/toolchain/compiler-architecture-targets/) separates source architecture tags from compiler targets and artifacts. L08 and VIS12 are related resources, not additional prerequisites.

## Why the hierarchy outlived its API generation

CUTLASS exposes reusable C++ building blocks where a library call normally hides implementation. The retained 2.x-style organization follows device, kernel, threadblock, warp, and instruction work. SIMT and Tensor Core implementations share the GEMM equation but need different operation and data-movement policies. Newer 3.x APIs make collective mainloops and epilogues explicit as cooperation and architecture-specific schedules become more complex; they do not simply rename each older level.

This unit pins **CUTLASS C++ v4.7.0**, commit **`dcf215af68a2d08d305076c152a06f201728cd53`**, and reads the **retained 2.x-style API inside that release**, not a separate 2.x dependency. The [commit](https://github.com/NVIDIA/cutlass/commit/dcf215af68a2d08d305076c152a06f201728cd53) is dated `2026-08-06T14:31:22Z`; the [release](https://github.com/NVIDIA/cutlass/releases/tag/v4.7.0) was published `2026-08-13T09:43:47Z`. Its changelog entry says 2026-08-04, a different date. Version macros report 4/7/0; the empty ungenerated revision macro cannot replace the SHA.

## Layout and epilogue are separate contracts

Global layout maps logical coordinates to element offsets. [`cutlass::layout::RowMajor`](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/layout/matrix.h#L57-L110) uses `row*stride+column`; stride is not automatically the logical column count. Shared-memory layout may reorganize staged operands for access patterns, while register fragments have their own thread/value organization. A global RowMajor declaration supplies neither of those internal maps. CUTLASS layout types are not cuBLAS transpose flags.

The [linear-combination epilogue](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/epilogue/thread/linear_combination.h#L219-L249) handles scaling, source C, and destination conversion after accumulation. Record accumulator, compute/scalar, source, and output types separately. Rearranging accumulator data for stores is also epilogue work, not another pass over K. FP16 A/B conversion can lose input information despite FP32 accumulation and output; [L08](/en/libraries/tensor-core-precision-contracts/) develops that numerical contract further.

## Work an original uneven-tile model

Consider `D=0.5*A*B+C` with `M=150,N=90,K=40`. A/B are FP16; C/D, accumulation, and epilogue computation are FP32. All global matrices use RowMajor: A stride 48, B/C/D stride 96, with allocations covering complete physical rows. Propose threadblock tiles `64x64x16`, warp tiles `32x32x16`, and an SM75 `16x8x8` instruction-level comparison. This is original geometry, not a copied test, instantiated template, or demonstrated legal specialization.

| Derivation | Result | What it does not establish |
| --- | --- | --- |
| Output grid | `ceil(150/64)*ceil(90/64)=3*2=6` blocks | Not 18 independent blocks: K is reduced within each output block |
| K traversal | `ceil(40/16)=3` slices per block | Not three independent epilogues overwriting D |
| Output warp tiling | `(64/32)*(64/32)=4` warp tiles, with no K partition | Not observed scheduling or occupancy |
| Bottom-right output tile | Origin `(128,64)`, valid extent `22x26` | Not permission for edge threads to exit before required synchronization |
| Last reduction slice | `k=32..39`, eight valid positions | Not permission to read the remaining eight positions out of bounds |
| Instruction-level coverage | `(32/16)*(32/8)*(16/8)=16` geometric operations per warp tile per full K slice | Not an emitted or executed instruction count |

For a valid output `(i,j)`, A08's invariant is that the accumulator contains contributions from all previously completed K slices and none from future slices. After the third slice, apply `0.5*acc+C[i,j]` **once**. The [API loop nest](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/gemm_api.md#L8-L63) represents outer M/N grid concurrency, not serial device loops. Split-K would require a different merge and exactly-once-C proof.

L06's stride reasoning gives A offset `i*48+k`, B offset `k*96+j`, and C/D offset `i*96+j`. D's last logical element is at `149*96+89=14393`, within `150*96=14400` elements. Using `i*90+j` would ignore padding. Prove each operand's allocation and subview alignment independently; this arithmetic does not establish template alignment eligibility.

One idealized FP16 staging slot holds `(64*16+16*64)*2=4096` bytes of A/B payload; two slots hold 8192 bytes. This excludes layout padding and other kernel storage, so it is not the kernel's shared-memory allocation or an occupancy estimate. Bounds-aware staging or explicit padding must supply valid complete operands, and final stores must select only valid outputs.

## A pipeline needs two different permissions

The selected `MmaPipelined` inherits a **two-stage** base. A stage is a reusable storage slot, not a promise that all CUTLASS kernels are double-buffered. The original timeline below specifies dependencies, not measured overlap or a literal instruction schedule.

| Slice | Slot contents | Required ordering |
| --- | --- | --- |
| First | Stage 0 receives `k=0..15` | Finish and publish writes before consumers read |
| Second | Stage 1 receives `k=16..31` | Independently establish readiness before consumption |
| Third | Stage 0 receives `k=32..39` plus zero padding | Wait for every previous stage-0 consumer to finish before overwrite, then publish the new contents |

"Ready to read" and "safe to overwrite" are different facts. Two allocated buffers prove neither. Threads with no valid edge data must still participate in required synchronization. The [efficient-GEMM discussion](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/efficient_gemm.md#L110-L151) motivates buffering and epilogue rearrangement, but guarantees no latency hiding, occupancy, or speedup for this model. Nor does this source reading establish use of L05's separately versioned `cuda::pipeline` API.

[VIS12](/en/visuals/gemm-tiling-hierarchy/) connects matrices, tiles, threadblocks, and warps. Its instruction panel remains a **source-level scalar `1x1x1` slot**, not FMA, MMA, WMMA, SASS, or measured CUTLASS execution. Use this unit's separately labeled geometry and timeline for the additional instruction/pipeline reasoning; do not relabel the existing visual.

## Bound the 3.x comparison

The [3.x reading path](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/gemm_api_3x.md#L83-L195) is **Device -> Kernel -> Collective -> Tiled MMA/Copy -> Atom**. A collective coordinates cooperating threads and their data dependencies for a mainloop or epilogue. Producer and consumer warps can have different roles. Tiled MMA/Copy expresses tiled thread/value work; atoms describe primitive operations. Neither "collective = warp" nor "atom = thread" is a valid translation.

The kernel composes collective mainloop and epilogue; [`device::GemmUniversalAdapter`](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/include/cutlass/gemm/device/gemm_universal_adapter.h#L123-L137) remains host-facing. [Generation compatibility](https://github.com/NVIDIA/cutlass/blob/dcf215af68a2d08d305076c152a06f201728cd53/media/docs/cpp/cutlass_3x_backwards_compatibility.md#L11-L49) explains coexistence, not interchangeable configuration types. Listed Hopper 3.x kernels require SM90a and CUDA 12.0+, but that does not make every 3.x concept Hopper-only. CuTe **C++** is not CuTe **Python DSL**; no DSL is needed here.

## Preserve an ordinary FP32 alternative

Retain a non-Tensor-Core FP32 SIMT GEMM with FP32 A/B/C/D, accumulator, and epilogue computation. Its site hardware baseline is CC 7.5 or newer with bounded problems below 8 GB, regardless of older implementation tags. Keep layout, tails, and `alpha,beta` semantics explicit. Replacing FP16 multiplicands with FP32 changes the numerical algorithm; it is neither a bitwise-equivalent fallback nor an exact real-arithmetic oracle. L08 explains independent higher-precision references and fixture-specific tolerances. Performance comparisons require accepted numerics and matched measured boundaries, not a predicted speedup from tile sizes.
