CUB device-wide [collectives (TERM-107)](/en/glossary/#term-107) delegate the [reduction (TERM-127)](/en/glossary/#term-127) from A02 and the [scan (TERM-130)](/en/glossary/#term-130) from A03 to a library implementation. The caller still owns [temporary storage (TERM-183)](/en/glossary/#term-183), stream ordering, object lifetimes, overlap, and [determinism (TERM-138)](/en/glossary/#term-138). This unit deliberately teaches only `DeviceReduce::Sum`, `DeviceScan::InclusiveSum`, and `DeviceScan::ExclusiveSum`.

- Select the correct device-wide primitive from the distinction between one aggregate and one prefix per position.
- State the exact outputs, supported in-place form, and forbidden partial overlap for all three operations.
- Follow the traditional API's query, allocate, and execute protocol while keeping temporary storage alive until GPU completion.
- Place producer, consumer, host-observation, and release edges around work on an explicit stream.
- Distinguish bundled CUB 1.15.1, 2.8.2, and 3.3.4 from independently selected v3.4.2, including the different floating-point determinism contracts for reduction and scan.

## Scope, invocation level, and canonical headers

`cub::DeviceReduce` and `cub::DeviceScan` are device-scope classes called from the host. They submit device work and write results to device-accessible output. Their focused canonical headers are `<cub/device/device_reduce.cuh>` and `<cub/device/device_scan.cuh>`. The aggregate `<cub/cub.cuh>` header also exposes these names, but a review packet should record the narrower dependency actually required.

Generic `Reduce` and `Scan`, segmented and by-key forms, selection, and sorting are outside this unit. Selecting a production primitive establishes no fact about its backend, kernel count, traffic, or speed.

## `DeviceReduce::Sum`: N inputs, one aggregate

For `N` inputs `x[0] ... x[N-1]`, `DeviceReduce::Sum` uses addition with a zero initial value and writes one aggregate through `d_out`. Its mathematical contract is the sum of all `N` items. A parallel implementation may reassociate operands, so this is not a fixed serial left fold. The tagged interface does not support a noncommutative custom meaning of `+`.

The range `[d_in, d_in + N)` must not overlap `d_out`. Reduction has no exact in-place exception analogous to scan; placing the output inside the input range violates the precondition. `d_out` becomes observable to the host or an otherwise unordered stream only after work submitted to its stream has completed.

## `DeviceScan::InclusiveSum` and `ExclusiveSum`: one prefix per position

For the same input, `InclusiveSum` logically produces `y[i] = x[0] + ... + x[i]`: the current item belongs to its prefix. `ExclusiveSum` uses the input type's zero-initialized value as its initial value, producing `y[0] = 0` and, for `i > 0`, `y[i] = 0 + x[0] + ... + x[i-1]`: the current item does not belong to its prefix. That zero value must actually be a suitable additive identity for the application type.

Both scans support exact in-place operation when `d_in == d_out`. Otherwise, their complete input and output ranges must not overlap in any way. The equations fix which items belong to each logical prefix, not the parallel parenthesization. A custom sum type still needs an associative-operation contract; the tagged scan interface permits a noncommutative scan order.

| Required result | Selection boundary | Valid output extent |
| --- | --- | --- |
| One sum over all `N` items | Device reduction | One output aggregate |
| `N` prefixes that include the current item | Inclusive device scan | `N` outputs |
| `N` prefixes that start at zero and exclude the current item | Exclusive device scan | `N` outputs |

## Traditional two-phase temporary-storage protocol

Each traditional entry point begins with `void* d_temp_storage` and `size_t& temp_storage_bytes`. Its strict protocol is:

- **Query phase:** call the same overload with `d_temp_storage == nullptr`. The API writes the required byte count to `temp_storage_bytes`, launches no kernel, touches no user input or output storage, and does no algorithm work.
- **Allocation phase:** allocate at least that many bytes of device-accessible storage on the current device. The tagged developer guide requires a one-byte allocation for the traditional overload even when a configuration needs no scratch space.
- **Execution phase:** on the same current device, pass the allocation to the same API and template instantiation with the same argument types and problem configuration, then check the returned `cudaError_t`.

A query result is not a constant across APIs, `NumItemsT` instantiations, devices, or configurations. Re-query after changing the current device, operation, iterator or type instantiation, or problem size. Treat the scratch allocation as exclusive writable storage for the unfinished operation: do not overlap it with input or output allocations or submit it concurrently to other work.

## Explicit streams, completion, and lifetime

The last optional argument of a traditional overload is a `cudaStream_t`; its default is stream `0`. A maintainable composition passes one explicit stream to the execution call and records it in the ledger. A device-level call returns `cudaError_t` but does not thereby synchronize the host with the device. A successful return means submission did not report that error, not that host access to output is ready.

Successive calls in one stream may reuse the same scratch in stream order without host synchronization. Different streams must not reuse it concurrently: first establish completion of the prior use with an event dependency or stream completion. Input, output, and temporary allocations must all outlive their final consumers. Host reads, unordered cross-stream consumers, reallocation, and release belong after the corresponding completion edge. A later synchronization point can also surface an asynchronous error.

## Reduction and scan have version-specific determinism contracts

The inspected traditional owner headers do not support one undifferentiated "reduction versus scan" rule. For pseudo-associative operations such as floating-point addition:

- `DeviceReduce::Sum` in bundled CUB 1.15.1, 2.8.2, and 3.3.4 and selected 3.4.2 documents **same-GPU run-to-run determinism**. This does not promise equality with a serial left fold or one bit pattern across GPUs of different compute capability; architecture-dependent tile sizing creates the documented cross-compute-capability caveat.
- CUB 1.15.1 `DeviceScan::InclusiveSum` and `ExclusiveSum` also document same-GPU run-to-run determinism with the same cross-compute-capability caveat. Bundled CUB 2.8.2 and 3.3.4 and selected 3.4.2 instead document that pseudo-associative scan results may vary from run to run. Do not inherit the 1.15.1 scan guarantee into later rows or reject the guarantee that its inspected header actually states.

These are version- and operation-specific owner contracts, not observed EX17 behavior. For integer addition, a correct zero identity and a proved no-overflow bound make each prefix exact regardless of parenthesization. EX17 therefore retains exact full-array `uint32_t` scan acceptance, while this page records no device output or determinism observation.

## Environment-overload boundary at v3.4.2

The immutable CCCL 3.4.0 release records completion of the CUB device-wide single-call environment-overload rollout; traditional two-phase APIs remain available and are not deprecated. v3.4.2 supplies environment forms that can obtain a stream, memory resource, and supported execution requirements from an environment. The exact v3.4.2 `DeviceScan` source marks the `InclusiveSum` and `ExclusiveSum` environment overloads taught here as **added in 3.4.0, first appearing in CUDA Toolkit 13.4**. A `DeviceReduce::Sum` environment form is also available at v3.4.2.

"First Toolkit 13.4" is the owner's availability annotation, not a new Learning Site Toolkit Lane or runtime claim. To cover all three bundles in the table with one comparable call structure, published [EX17](/en/examples/cub-device-reduction-scan/) uses the traditional two-phase APIs even in selected-v3.4.2 rows. ## Scoped known-issue ledger

Open documentation issue [#5966](https://github.com/NVIDIA/cccl/issues/5966) demonstrates with `DeviceReduce::Min` that the same numerical item count instantiated as `size_t` or `int` can yield different temporary-storage byte queries. It establishes neither a Sum/Scan correctness defect nor behavior for every version. It narrowly reinforces the tagged v3.4.2 guide: query and execution must use the same template arguments and current device.

No other issue enters this unit. Comparisons across different pointer or input configurations do not directly refute a run-to-run guarantee for one unchanged contract, and issues closed and fixed before v3.4.2 are not current defects. This is a bounded ledger, not a CCCL issue dump.
