CUB warp and block [collectives (TERM-107)](/en/glossary/#term-107) require one explicitly defined participant group to invoke the same operation together. A [logical warp (TERM-184)](/en/glossary/#term-184) is not an arbitrary set of lanes that happens to be active; it is a compile-time-sized consecutive thread group inside one hardware warp. `WarpReduce` and `BlockReduce` implement [reduction (TERM-127)](/en/glossary/#term-127), while `WarpScan` and `BlockScan` implement [scan (TERM-130)](/en/glossary/#term-130). All four leave participant, output-validity, and [temporary-storage (TERM-183)](/en/glossary/#term-183) contracts with the caller.

## What you should be able to do

- Select among the four focused collectives from the required group scope and output shape.
- State logical-warp participant count, block template shape, row-major rank, and blocked arrangement exactly.
- Provide each simultaneously active group with `TempStorage` for the matching specialization and add a caller barrier before reuse or repurposing.
- Handle `valid_items`, `num_valid`, and output-validity boundaries without admitting inactive data to the operation.
- Describe semantics and [determinism (TERM-138)](/en/glossary/#term-138) when selecting a v3.4.2 algorithm variant without manufacturing a performance claim from its name.

## Participant contract before primitive name

| Primitive scope | Compile-time shape | Participants that must invoke together | Result contract |
| --- | --- | --- | --- |
| Warp | `T, LogicalWarpThreads`, with `1 <= n <= 32` | `n` consecutive threads in one hardware warp; entrant count is a multiple of `n` | Defined by logical lane rank |
| Block | `T, BlockDimX, Algorithm, BlockDimY, BlockDimZ` | The complete CUDA thread block, with launch dimensions exactly matching the template shape | Defined by row-major linear thread rank |

Every required group participant reaches a collective call with consistent arguments. Calling only from threads that "have data" is not a partial-tile protocol; it can leave internal communication or barriers without required participants. [M06](/en/memory/warp-divergence-reconvergence/) explains converged participation, and [M12](/en/memory/cooperative-groups/) supplies another explicit-group vocabulary, but neither automatically changes a CUB class's participant contract.

Logical-warp shape has one easy-to-miss v3.4.2 boundary. When `LogicalWarpThreads` is a power of two, one hardware warp can be partitioned into subwarps of that size. When it is not a power of two, the tagged developer guide says there is no partitioning and only the first logical warp executes. Do not divide 32 lanes into several sibling groups of 7 or 9. The Exercises use 8 and therefore do not cross this boundary.

## Warp primitives: reduction or prefixes within one logical warp

`WarpReduce<T, LogicalWarpThreads>` lets each logical lane contribute one item, while selected overloads accept a fixed-size range. It returns a valid aggregate only in **logical lane 0** of each logical warp; return values in the other lanes are undefined. When a block runs several logical warps at once, each group needs its own `TempStorage` slot. Groups that are still executing must not alias a slot.

`WarpScan<T, LogicalWarpThreads>` produces an inclusive or exclusive prefix for each participating lane. An ordinary output is valid for its corresponding lane. An overload with `warp_aggregate` supplies the aggregate of all inputs to every participating lane. `ExclusiveSum` supplies a zero initial value, so logical lane 0 receives zero. A generic `ExclusiveScan` without an initial value explicitly leaves lane 0 output undefined. Do not apply reduction's leader-only output rule to scan, or read every lane's reduction return as if it were scan output.

## Block primitives: reduction or prefixes over the launch block

The template shape of `BlockReduce` and `BlockScan` is not a suggestion. Runtime launch dimensions must match `BlockDimX * BlockDimY * BlockDimZ` and each declared dimension, and the complete block invokes the collective. Both classes expose a nested `TempStorage` for the matching specialization. v3.4.2 also supplies an internally allocated private shared-storage constructor, but explicit storage makes ownership and reuse phases easier to audit.

The public return from `BlockReduce` `Sum` or `Reduce` is defined only in row-major **thread 0**; other threads must not consume it even if an internal algorithm happens to make a value visible more widely. `BlockScan` instead produces prefix output for every thread's item or items. An overload with `block_aggregate` supplies that aggregate to every thread. Reduction and scan always have different output cardinalities.

## Row-major blocked arrangement

The linear rank in a multidimensional block is `threadIdx.x + BlockDimX * (threadIdx.y + BlockDimY * threadIdx.z)`, so X varies fastest. Single-item overloads order participants by that row-major rank.

When each thread owns `ItemsPerThread` values, array overloads assume a **blocked arrangement**: linear thread `i` owns the contiguous interval beginning at `i * ItemsPerThread` in the global logical sequence. Threads are ordered first, then values by local item index. Passing a striped load directly as blocked input changes the logical reduction or scan order. Convert the arrangement first or use a load path whose contract matches the data layout.

## `TempStorage` and caller synchronization

`TempStorage` is an opaque nested type whose layout depends on class specialization, algorithm, data type, and group shape. The caller supplies an exclusive slot for every simultaneously active group that could interfere. Shared memory may be reused through a union or alias across different collectives, but the phase boundary must be explicit.

A collective may internally use shuffles, shared memory, and embedded barriers. Those internal steps implement the current call; they **do not replace caller synchronization required for storage reuse or a following use**:

- After a warp collective, before reusing or repurposing that warp's `TempStorage`, the exact participating lanes execute `__syncwarp(mask)`. Only a uniformly executing full-warp case makes the default full-warp form unambiguous.
- After a block collective, before reusing or repurposing block `TempStorage`, the complete block executes `__syncthreads()`.
- If a leader publishes a reduction result through shared memory for peers, place synchronization at the matching scope for that producer/consumer edge. An embedded barrier does not prove that publication is complete.

The barrier participant mask and phase must match the group ledger. A mask that includes a non-arriving lane and a mask too narrow to include a consumer are both invalid protocols.

## Partial-valid contracts

A `WarpReduce` overload with `valid_items` reduces only the first `valid_items` logical lanes. Every thread across the calling warp must agree on that value or the result is undefined. Participating in the collective and contributing a valid input are different sets: an invalid lane still obeys the group call, while its input is excluded. The result remains valid only in logical lane 0.

The v3.4.2 partial forms of `WarpScan` likewise pass only the first `valid_items` lane inputs to the scan operator. Invalid outputs remain unmodified. If an aggregate is requested with zero valid inputs, that aggregate is undefined. Every participating lane still obeys the same group call and storage phase.

`BlockReduce(input, op, num_valid)` and `Sum(input, num_valid)` admit items only from the first `num_valid` threads in row-major rank. The entire block still invokes the collective, and only thread 0 receives a valid result. The focused `BlockScan` surface has no corresponding dynamic valid-count parameter. A tail tile must be made into a full logical tile by the caller with a correct identity or padding plus guarded output, or be delegated to another abstraction with an explicit partial contract. A generic operation without a proven identity cannot be padded arbitrarily.

## Algorithm variants at v3.4.2

`BlockReduceAlgorithm` exposes `BLOCK_REDUCE_RAKING_COMMUTATIVE_ONLY`, `BLOCK_REDUCE_RAKING`, the default `BLOCK_REDUCE_WARP_REDUCTIONS`, and `BLOCK_REDUCE_WARP_REDUCTIONS_NONDETERMINISTIC`. The first accepts only a commutative reduction; the tagged source lists the other three for commutative and noncommutative operations. The last variant combines warp aggregates with atomic operations, so the reduction order is not guaranteed to match across invocations of the same kernel. Regardless of variant, the public return contract authorizes only thread 0.

`BlockScanAlgorithm` exposes the default `BLOCK_SCAN_RAKING`, `BLOCK_SCAN_RAKING_MEMOIZE`, and `BLOCK_SCAN_WARP_SCANS`. In the v3.4.2 source, requesting `BLOCK_SCAN_WARP_SCANS` when the block thread count is not a multiple of the architecture's warp size maps to the safe `BLOCK_SCAN_RAKING` implementation. Warp classes also select internal specializations from logical-warp shape. These names describe available implementation families and constraints. They establish no target-workload speed, instruction count, occupancy, or benchmark winner. A changed reduction order also requires renewed numerical acceptance and determinism review.
