Compute Sanitizer assigns different defect classes to different detectors. Racecheck looks for data access hazards in shared memory. Initcheck's stable baseline is uninitialized device global memory reads. Synccheck reports synchronization primitive errors. These tools complement rather than replace one another, and each narrower check starts only after memcheck.

## What you should be able to do

- Organize a reviewable `memcheck -> racecheck -> initcheck -> synccheck` diagnosis.
- Distinguish shared-memory WAW, WAR, and RAW hazards without calling racecheck a global-memory race proof.
- Explain initcheck's default scope and why its current shared-memory extension is version-gated.
- Recognize synccheck reports for divergent `__syncthreads()`, warp divergence, and invalid arguments while preserving detection limits.
- Report one scenario per process and describe executed-path evidence without turning a clean run into a correctness proof.

## Fixed workflow: make accesses valid first

Start each scenario with memcheck in a fresh target process. Only after fixing that scenario's invalid or misaligned accesses, API failures, and applicable leaks should a second fresh process run the focused tool:

```text
scenario A, process 1: compute-sanitizer --tool memcheck   <app> <args>
scenario A, process 2: compute-sanitizer --tool racecheck <app> <args>
scenario A, process 3: compute-sanitizer --tool initcheck <app> <args>
scenario A, process 4: compute-sanitizer --tool synccheck <app> <args>
```

This sequence does not claim that every defect needs four final diagnoses. It first makes memory access valid, then interprets a narrower detector. An invalid pointer or out-of-bounds write can corrupt later state and obscure the cause of a hazard. Save the exact command, tool version, standard output and error, process exit status, input, and launch geometry for every invocation. Compiling with `-lineinfo` can improve source attribution, but it does not expand detection coverage.

## Racecheck: three shared-memory hazards

Racecheck is a runtime shared memory data access hazard detector. The current owner contract limits it to on-chip shared-memory accesses, so a clean racecheck report is **not** proof that global-memory data races are absent.

It reports three canonical hazard classes:

| hazard | unordered conflicting accesses | why order affects the result |
| --- | --- | --- |
| WAW, write-after-write | two threads write one shared location | which write supplies the final value is uncertain |
| WAR, write-after-read | one thread reads, while another thread's write may occur before that read completes | the reader may lose the old value it was meant to observe |
| RAW, read-after-write | one thread should write before another reads, but the reader may run too early | the reader may fetch before the producer write takes effect |

The repair follows the algorithm. WAW often needs one writer or an atomic protocol. WAR and RAW often need documented ordering over the right participants. Do not insert `__syncthreads()` mechanically: if the whole block cannot legally reach it, the attempted repair creates a synchronization defect. A warp-local protocol still needs a valid participation mask.

## Initcheck: global by default, shared as an extension

Initcheck detects uninitialized reads. Its default invocation checks uninitialized device global memory, meaning bytes in a device allocation that have not been initialized by a device write or an applicable `cudaMemcpy` or `cudaMemset`. Initcheck is not an invalid-address detector, so memcheck still comes first.

Current Compute Sanitizer also provides explicit address-space selection:

```text
--initcheck-address-space global   # default
--initcheck-address-space shared   # shared only
--initcheck-address-space all      # global and shared
```

Shared-memory initcheck support is a newer extension recorded in the 2025.4 release notes. Do not project it backward into CUDA 11.8 documentation or older tools. Current release notes also record fixes for shared-memory false positives. A report using this extension must preserve the exact Compute Sanitizer, Toolkit/compiler, and driver versions, option, and release-note review. Without `shared` or `all`, a default clean run says nothing about shared-memory initialization.

## Synccheck: primitive misuse, not a complete synchronization prover

Synccheck detects synchronization primitive errors and barrier misuse. Typical reports include:

- divergent threads in a block when only a subset enters a conditional `__syncthreads()`;
- divergent threads in a warp at a barrier that does not support that divergence;
- invalid arguments to a primitive such as `__syncwarp(mask)`;
- some misuse of supported Cooperative Groups, `cuda::barrier`, or architecture-specific operations.

Its limitations are part of the conclusion. The current user guide says synccheck can catch a thread that reaches `__syncwarp()` without naming itself in the mask, but it does not catch every case in which a thread named by the mask fails to reach that operation. It does not prove that every required barrier exists, validate every higher-level producer-consumer ordering, or replace racecheck and numerical comparison. Release notes also list unsupported dynamic parallelism, version-specific false positives or negatives, and architecture requirements. Bind every report to its exact tool lane.

## Isolated processes and comparable logs

Use one scenario per process. Launch defect and corrected variants separately, and launch memcheck separately from the focused detector. This prevents context termination, sticky errors, or partial output from one defect being attributed to the next scenario.

A minimal log ledger records:

1. Scenario ID, source revision, build flags, launch parameters, and input.
2. Compute Sanitizer and CUDA component versions.
3. Exact command, process ID, exit status, and untrimmed raw report.
4. A predeclared expected classification such as `racecheck WAW`, not fixed report prose.
5. Independent defect/corrected results plus a CPU reference or invariant verdict.

Report wording and counts can change with tool versions. Acceptance should center on the defect class, source location, corrected behavior, and process status rather than one permanent output string.

## Coverage boundary of a clean run

All four tools perform dynamic analysis. They observe only the paths, inputs, launches, and supported operations executed in that process. A clean run supports only this statement: under the recorded environment and executed paths, the tool reported no defect within its checked scope. It cannot establish that:

- an unexecuted branch or unselected input is defect-free;
- global-memory races outside racecheck's scope do not exist;
- default initcheck covered shared memory;
- synccheck proved the complete synchronization protocol;
- numerical output satisfies a CPU reference, tolerance, or invariant.

Therefore, `ERROR SUMMARY: 0 errors` is not clean-run proof of correctness. More tests, broader path coverage, other detectors, and independent verification add evidence, but they do not turn bounded dynamic checking into a proof.
