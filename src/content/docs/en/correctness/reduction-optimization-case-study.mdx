Q12 is a correctness-first, evidence-bounded reduction optimization case study, not a benchmark. It begins with immutable EX11 and writes divergence, synchronization, numerical-order, and memory-traffic changes into a pre-collection ledger. Any candidate may be rejected, remain unanswered, or be rolled back. The site has run neither the runner, CUDA, nor a profiler.

## What you should be able to do

- Qualify every candidate with EX11's independent CPU reference and absolute-plus-relative tolerance.
- Write a pre-measurement hypothesis ledger with mechanism, coupling, support, rejection, no-answer, and rollback branches.
- Control warp-tail, operation-tree, and partial-staging changes separately while disclosing effects that cannot be isolated.
- Declare workload, warm-up, completion, statistics, profiler, permission, Environment Manifest, correctness result, and bounded interpretation for every measured stage.
- Preserve expected observations without naming a winner when qualifying hardware evidence is absent.

The canonical workload has 4,099 `float` values, a block size of 256, at most 512 inputs per block, and the stage DAG `4099 -> 9 -> 1`. The last first-stage block has only three valid inputs. Every other lane writes neutral zero, yet all threads still reach every `__syncthreads()`. An ordinary block barrier is not a grid rendezvous; successive host-launched kernels establish stage boundaries.

The independent CPU reference uses a `double` left fold. The GPU result uses EX11's published finite comparator: `absolute_error <= 1e-4 + 2e-5 * abs(cpu_reference)`. Passing tolerance means only that the result satisfies this problem-specific acceptance rule. It does not prove bitwise equality, a fixed operation order, a determinism scope, or performance. Every small boundary fixture and the declared measurement workload must pass the same CPU-reference and tolerance gate again.

## Write the hypothesis ledger before collection

Each edge retains the following fields independently. A later stage cannot fill an earlier gap retroactively.

| field | required declaration |
| --- | --- |
| identity | stage ID, immutable parent, candidate source and binary SHA-256, expanded build command |
| changed variables | the primary intervention and any disclosed coupled changes that cannot be isolated |
| mechanism | a falsifiable control-flow, barrier/shared-access, operation-tree, or partial-traffic prediction |
| held constants | input bytes, value type, block size, oracle, tolerance, toolchain, GPU, and collection method |
| evidence | correctness packet, raw unprofiled samples, exact query, report, commands, logs, and hashes |
| decision | support, reject, no-answer, rollback, and next-question rules |
| alternatives | at least two competing explanations not eliminated by the chosen evidence |

The fixed stage IDs are `canonical-shared-tree`, `warp-tail-control`, `reassociated-warp-order`, and `four-load-staging`. These labels identify source and method; they contain no result. Stop when the preceding stage fails correctness or comparison coordinates do not match. Never promote it silently to the next baseline.

## Freeze every stage's measurement contract

Every stage uses one declared workload of 16,777,219 deterministic finite `float` values. Hold the source parent, device ordinal, 256-thread block, input bytes, allocation policy, and CPU oracle fixed. Each process performs three excluded warm-up attempts, then explicitly calls `cudaDeviceSynchronize`, retains ten fresh unprofiled raw attempts, and predeclares the median plus minimum and maximum before values are visible; no sample is deleted. A profiler run is a separate observation with the same workload, correctness cadence, and stage identity. Every record includes a complete Environment Manifest, permission result, correctness result, and bounded interpretation.

The declared stage sizes for the canonical, warp-tail, and reassociated paths are `16777219 -> 32769 -> 65 -> 1`; the four-load path uses `16777219 -> 16385 -> 17 -> 1`. Input occupies 67,108,876 bytes, while each of two buffers sized for the largest baseline partial capacity occupies 131,076 bytes, giving a conservative device problem bound of 67,371,028 bytes. These are source-derived workload coordinates, not measured traffic or memory-use observations.

Every stage declares all of the following: the fixed input as its workload; three excluded direct attempts as warm-up; checked `cudaDeviceSynchronize` after each complete multi-kernel reduction as synchronization; the predeclared median and min/max across ten retained attempts as statistics; one minimal queried section or shorter exact metric list as its profiler method; a recorded permission result that stops collection when denied; a complete Environment Manifest; a same-comparator correctness result before measurement; and a bounded interpretation answering only the named stage question. Every current result field is `expected; unrecorded`.

The downloadable [original expected-only Q12 fixture](/assets/profiler-report-fixtures/q12-nsight-compute.expected.json) freezes that schema as an unfilled plan. It contains no Environment Manifest values, report, sample, metric, timing, or winner.

## Stage 1: Treat divergence and synchronization as one disclosed bundle

`canonical-shared-tree` is the EX11-shaped experimental baseline: active `thread < stride` lanes update shared partials, and the whole block reaches a barrier before the next round. `warp-tail-control` retains two-load staging, block size, global stage sizes, the early shared tree, and lane-zero output, but changes the 32-lane tail to explicit warp synchronization and shuffle exchange.

The primary intervention on this edge is the warp-tail control and synchronization mechanism. It may also change branch encoding, block-barrier count, shared accesses, and instruction mix. The ledger must list those coupled changes and cannot attribute an elapsed difference solely to “divergence removed” or “fewer barriers.” The predeclared synchronization hypothesis is directional: relative to baseline, each block stage has five fewer block-wide barriers and stops updating shared partials below stride 32, so matched queried evidence with those scopes should be lower. An unchanged or higher matched value rejects the hypothesis; no available field with a matching definition yields no answer.

## Stage 2: Change numerical order explicitly

`reassociated-warp-order` changes the declared warp tail from a contiguous-prefix down-shuffle operand and active-lane schedule to a periodic XOR butterfly schedule. Two-load staging, the 256-thread block, global stage sizes, early shared phases, five shuffles, 31 effective additions, workload, oracle, tolerance, and collection method remain fixed. This edge deliberately treats numerical order and the divergence pattern as a disclosed bundle. Every candidate supplies operand-edge and participant ledgers rather than saying only that it “still adds the same values.”

Floating-point addition is not strictly associative. The same input set and mathematical sum do not guarantee bitwise-identical results from different trees. The predeclared numerical hypothesis predicts that the fixed workload's final scalar bits differ from `warp-tail-control`; equal bits reject that prediction, while both sides must still pass tolerance. If the exact GPU exposes an owner-defined divergence field, the periodic active-lane masks predict a higher value; an equal or lower value rejects that mechanism, while no matching field yields no answer. No observation becomes cross-build, cross-GPU, or cross-launch bitwise reproducibility.

## Stage 3: Control intermediate memory traffic

`four-load-staging` changes each thread's guarded first-level inputs from two to four while retaining neutral zero, block size, the warp XOR mechanism, CPU oracle, tolerance, and fixed workload. The source-derived stage DAG changes from `16777219 -> 32769 -> 65 -> 1` to `16777219 -> 16385 -> 17 -> 1`, predicting fewer intermediate partial elements and later-stage blocks. Keep that logical estimate separate from queried path traffic.

This staging also adds thread-local additions and changes the operation tree, so numerical order is a disclosed coupling. The predeclared traffic hypothesis applies only to intermediate partial arrays: matched queried traffic with that path and scope should be lower than `reassociated-warp-order`; an equal or higher value rejects the mechanism, while no matching field yields no answer. Even if traffic falls, unprofiled elapsed behavior may still reflect instruction mix, resource use, cache state, clock or thermal state, or system load. Q12 does not claim that this stage is faster or a universally best reduction.

## Profiler method, permission, and report custody

Retain these queries in the exact measurement environment first:

```bash
ncu --version
ncu --list-sections
ncu --query-metrics
```

Metric names, units, scopes, and availability bind to the exact Nsight Compute version and GPU. Select one minimal queried section or a shorter exact metric list only after freezing the hypothesis, then fix kernel-name basis and filter, launch selection, replay mode, commands, and process environment. Preserve the primary `.ncu-rep`, stdout and stderr, exit status, query output, expanded command, hash, observer, and date for baseline and candidate separately.

Record performance-counter permission before collection. Denied permission, an unknown version, missing metric, ambiguous filter, report-import failure, or unmatched replay is a blocker: stop and retain the record. Do not bypass policy with `sudo` or turn unavailable into zero. Replay may re-execute a kernel, save and restore memory, perturb cache state, or change overhead. Profiled reports explain mechanisms; separate unprofiled attempts answer the elapsed question.

## Keep VIS10 evidence-neutral

[VIS10: Reduction Tree and Inactive Lanes](/en/visuals/reduction-stages/) uses eight fixed integers to show `adjacent-pairs` and `stride-halving` dependency trees. It can audit operand edges, inactive lanes, and neutral-value placement, but it does not execute EX11 or model a 256-thread block, warp shuffles, global partial arrays, floating-point rounding, or a profiler. VIS10 provides no CUDA correctness, runtime, or performance evidence, and browser state cannot fill a fixture result.
