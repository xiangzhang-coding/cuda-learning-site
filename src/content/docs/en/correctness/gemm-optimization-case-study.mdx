Q13 is a correctness-first, evidence-bounded general matrix multiplication (GEMM, TERM-147) optimization case study, not a tile recipe or benchmark. It starts with immutable EX15 and gives each K-tile, output-tile, and thread-coarsening edge a falsifiable hypothesis before collection. A remembered tile size, a browser diagram, or an isolated occupancy percentage cannot select a winner. The Learning Site has run neither the reviewed runner, CUDA, nor a profiler.

## What you should be able to do

- Preserve EX15's row-major equation, independent double CPU reference, finite-value policy, and absolute-plus-relative tolerance for every candidate.
- Derive tile-shape and reuse coordinates before predicting requested traffic or a resource trade-off.
- Separate source-declared shared storage and accumulator count from compiler allocation, theoretical occupancy, achieved occupancy, and elapsed behavior.
- Freeze matrix shape, precision, compute capability, workload, warm-up, completion, statistics, profiler method, Environment Manifest, and correctness result for every measured stage.
- Reject memorized tile sizes and production claims that lack matched evidence and exact library contracts.

Q13 writes a shape as `M x K x N`: `A[M,K] * B[K,N] -> C[M,N]`. VIS12 separately displays matrix and output-tile extents; translate its labels back to this declared order rather than guessing from three unlabeled numbers. The frozen equation is:

`C[row * N + col] = alpha * sum(A[row * K + p] * B[p * N + col]) + beta * C[row * N + col]`

Every stage must first pass `2x3x2-hand`, `33x31x35-partial`, and `32x32x32-aligned`, then the declared measurement shape. The reviewed runner identifies those three shapes through `ex15::kFixtures`, calls `ex15::make_fixture`, and preserves each fixture's published alpha, beta, and input bytes. It calls `ex15::gemm_reference` with double accumulation and `ex15::verify_tolerance` with `absolute_error <= 1e-4 + 2e-5 * abs(cpu_reference)`. Passing this problem-specific tolerance does not prove bitwise identity, determinism outside the frozen coordinate, or performance.

## Freeze every stage's measurement contract

All four stages use row-major non-transposed `A[1024,1024]`, `B[1024,1024]`, and `C[1024,1024]`; deterministic finite FP32 inputs and output; FP32 device accumulation; independent double CPU accumulation; `alpha=0.75`; and `beta=0.25`. The three device matrices occupy 12,582,912 bytes. This is a Baseline GPU Capability Tier workload, not a measured memory-footprint result.

Because beta is nonzero, copy the original C bytes into the same stable device allocation immediately before every correctness, warm-up, retained, and profiled attempt. Each process performs three excluded direct warm-ups. Each complete GEMM ends with checked `cudaDeviceSynchronize`. Retain ten fresh unprofiled attempts in declared order and report the predeclared median plus minimum and maximum without deleting samples. Profiled collection is a separate process and observation.

Every stage record repeats the exact matrix shapes, A/B/C and accumulation types, exact GPU compute capability, source/build/workload identity, warm-up, synchronization, retained statistics, profiler version/query/filter/replay, permission result, complete Environment Manifest, CPU-reference/tolerance result, and bounded interpretation. Any missing coordinate stops comparison. The downloadable [original expected-only Q13 fixture](/assets/profiler-report-fixtures/q13-nsight-compute.expected.json) freezes this schema with all environment and result cells unfilled.

## Stage 1: Change only the K-tile extent

`canonical-16x16x16` uses `TM=16`, `TN=16`, `TK=16`, a `16x16` block, one output per thread, two 16-by-16 shared arrays, and 2,048 source-declared shared bytes. `k-tile-16x16x8` keeps the same output footprint, 256 threads, one output owner, p-order, mathematical full-tile A/B reuse, and aligned-workload request total, but changes `TK` to 8. Because each shared array now has 128 rather than 256 slots, cooperative-load ownership, active load instructions, and per-instruction address groups also change; the ledger must disclose them rather than call every non-`TK` coordinate fixed.

For aligned `K=1024`, source arithmetic predicts 64 versus 128 K slices and 128 versus 256 block-barrier executions. It predicts 2,048 versus 1,024 static shared bytes per block while preserving the same total full-workload tile-load estimate. The resource hypothesis says an exact compiled record should report lower static shared storage. Equal or higher rejects that mechanism. A resident-block increase is possible only if shared memory was the limiting resource; otherwise occupancy remains unanswered. Load-instruction and coalescing evidence must be interpreted against the changed participant/address grouping. No elapsed direction is predicted.

## Stage 2: Change the output-tile shape and reuse direction

`rectangular-32x8x8` keeps `TK=8`, 256 threads, one output per thread, p-order, precision, and collection method, but changes the output tile to `TM=32`, `TN=8` and the block to `(8,32)`. A full slice loads 256 A values and 64 B values for 256 outputs: each A value is reused across eight columns and each B value across 32 rows.

Relative to `k-tile-16x16x8`, this edge changes directional reuse, shared footprint, grid geometry, and edge fraction as a disclosed bundle. For the fixed aligned workload, source arithmetic predicts more requested A/B values per completed output. A matching requested-traffic field with the same scope and normalization should be higher; equal or lower rejects the traffic mechanism, while no definition-compatible field yields no answer. A tall or narrow matrix may change useful work and edge waste, but it begins a new workload comparison rather than proving this tile generally suitable.

## Stage 3: Trade thread-level work for cross-thread reuse

`coarsened-32x16x8` keeps `TM=32`, `TK=8`, and 256 threads but expands `TN` to 16. Each thread owns two output rows at one column and therefore holds two source accumulators. A full slice loads 256 A and 128 B values for 512 outputs: A reuse is 16, B reuse is 32, and source-requested A/B values per output fall relative to `rectangular-32x8x8`.

The reuse hypothesis predicts lower matching requested traffic normalized to completed output; equal or higher rejects it, and no matching field yields no answer. The resource hypothesis predicts only that the source exposes two live accumulators and 1,536 shared bytes. It does not predict the final register count. Compiler allocation, spills, instruction mapping, fewer blocks, edge waste, and longer per-thread dependency chains are coupled changes. Even supported reuse evidence cannot establish an elapsed winner.

## Keep resource use and occupancy as separate evidence

Source-declared shared bytes are 2,048, 1,024, 1,280, and 1,536 for the four stages. Source accumulator counts are one, one, one, and two per thread. These are inspectable inputs, not complete compiled resource records. Retain the exact NVCC version, expanded C++17 command, `sm_75` and `compute_75` targets, source and binary hashes, compiler resource output, and any local-memory evidence for each template instantiation.

Theoretical occupancy combines exact compiled registers/shared memory/block size with exact device limits. Achieved occupancy is a separate observed profiler field. Neither is a speed score. A lower occupancy may still be sufficient to hide relevant latency; a higher value may add no useful work. Support or rejection must name the specific limiting resource and matched coordinate. If the compiler merges, spills, or otherwise changes the expected resource shape, revise the ledger before interpreting timing.

## Keep requested traffic, observed traffic, and Roofline apart

For the fixed aligned workload and a convention that includes tiled A/B requests plus one C read and write, source estimates are 545,259,520 bytes for both 16-by-16 output stages, 679,477,248 bytes for `rectangular-32x8x8`, and 411,041,792 bytes for `coarsened-32x16x8`. They count algorithm requests before cache, transaction, replay, and hardware effects. They are not compulsory matrix bytes and not observed DRAM traffic.

The main product-work convention is `W = 2*M*N*K = 2,147,483,648` FLOPs, counting one multiply and one add separately; report the alpha/beta epilogue separately. A derived `I_path = W / T_path` is meaningful only when work, traffic path, unit, shape, and provenance match. Q10's `P_roof(I) = min(P_compute, I * B_path)` bounds model geometry; it cannot turn an estimate or point location into a bottleneck, causal explanation, or winning tile.

## Preserve precision, compiler, and architecture coordinates

All four reviewed stages retain FP32 A/B/C and FP32 device accumulation against a double CPU reference. A compiler may contract multiply-add and legal operation details can affect low bits, so the tolerance gate remains mandatory for every exact build. Changing input precision, accumulation precision, fast-math options, contraction policy, or tolerance starts a new comparison.

The three selected compile-only Toolkit Lanes are 11.8.0, 12.9.2, and 13.3.1 with C++17. Each emits `sm_75` plus `compute_75` from the reviewed command, but the execution record must still identify the exact device, compute capability, driver, JIT path if any, and binary. The candidates use ordinary FP32, shared memory, and block barriers with a minimum compute capability of 7.5; there is no Tensor Core, WMMA, `cp.async`, or other architecture-specific branch. Adding one requires a separately justified hardware gate, fallback, correctness contract, and experiment.
