A trustworthy CUDA result is not established by one comparison or by a fast timing. Build a layered oracle: an independently reviewable CPU reference supplies expected numerical values, a declared absolute-plus-relative rule compares finite floating-point outputs, exact checks protect discrete outputs, and independent invariants test properties that both implementations must preserve. Correctness comes first; timing and optimization begin only after every applicable gate passes.

## What you should be able to do

- Specify a CPU reference that implements the same contract without copying GPU indexing or synchronization structure.
- Apply a combined absolute tolerance and relative tolerance to finite floating-point values.
- Select tolerances from scale, precision, operation structure, and domain requirements rather than from one observed mismatch.
- Check indices, counts, flags, categories, and shapes exactly.
- Add independent invariants that can catch a shared mistake in both implementations.

## Prerequisites

Complete [F04: Host-Device Lifecycle and Explicit Data Movement](/en/foundations/host-device-lifecycle/) and [O04: C++17 for CUDA](/en/start/cpp17-for-cuda/) first. F04 supplies the completion and copy-back boundary needed before host validation. O04 supplies the C++ types, containers, and deterministic host-side logic used to express a reference and comparator.

This unit designs static correctness contracts. It does not compile CUDA, run a GPU, or validate a particular threshold for an application.

## Correctness before performance

A performance number for an unvalidated result rewards the wrong program. Use this order:

```text
define the result contract
-> build and review the oracle
-> validate representative and adversarial cases
-> investigate every failure
-> only then measure or optimize
```

An optimization may change reduction order, precision, or intermediate representation. Re-run all correctness gates after each such change. A speedup never compensates for an unexplained mismatch.

## CPU reference: a second route to the contract

A CPU reference is a small, clear implementation of the specified operation on the same logical inputs. It should favor auditability over speed. A serial loop is often useful because it avoids GPU launch geometry, shared-memory staging, and parallel index decomposition.

Independence matters. Translating the kernel line for line onto the host can reproduce the same off-by-one error. Instead, derive indexing and boundary handling again from the input/output contract. Record the reference precision, operation order, NaN and infinity policy, and any library functions used. Higher precision can provide a useful comparison target, but it does not simulate every rounding step of a lower-precision GPU algorithm and is not automatically mathematical truth.

Validate the reference itself with hand-computable cases, identities, or a second trusted method. The CPU result is evidence, not an oracle by declaration.

## Absolute plus relative tolerance

For finite candidate value `g` and finite reference value `r`, this unit uses a reference-anchored rule:

```text
error = abs(g - r)
limit = atol + rtol * abs(r)
pass  = error <= limit
```

Both `atol` and `rtol` are non-negative and fixed before inspecting the candidate result. The absolute term protects values near zero, where a relative ratio is unstable or meaningless. The relative term lets the permitted difference grow with the reference magnitude. Report `g`, `r`, `error`, and `limit` for the first failure so the decision remains inspectable.

Handle non-finite values before this formula. Decide explicitly whether matching signed infinities are valid and whether any NaN is an expected domain result. Never let a NaN comparison pass accidentally because ordinary ordering comparisons with NaN are false.

## A scale-aware policy, not a magic constant

There is no universal epsilon. Machine epsilon describes spacing near one for a floating-point format; it is not an application-wide acceptance threshold. A defensible policy considers:

- output precision and any mixed-precision intermediates;
- the operation count and reduction shape;
- cancellation, conditioning, and expected numerical scale;
- documented library accuracy bounds when applicable;
- the downstream error budget and domain consequences.

Test at least zero or near-zero outputs, ordinary-scale outputs, large-magnitude outputs, cancellation-heavy inputs, and boundary sizes. Different output fields may need different declared policies. Do not increase a tolerance until a failing implementation passes. That turns an oracle into a record of the bug.

## Exact checks for discrete outputs

Tolerance is for quantities whose contract permits numerical approximation. Discrete outputs normally require exact equality:

- array length, tensor shape, and element count;
- selected index, class label, boolean flag, and status code;
- histogram bucket count and integer ownership metadata;
- sentinel placement and permutation membership.

A result structure can therefore mix comparators. Its floating values use the declared numerical policy while its indices and counts use exact checks. Applying a floating tolerance to `winner_index` can accept the wrong winner.

## Independent invariants

An invariant is a property required by the problem regardless of the implementation route. Useful examples include conservation of a known sum, output bounds, monotonicity, symmetry, normalization, sortedness, uniqueness, or preservation of a permutation.

Derive each invariant from the specification, not from the CPU output. This gives it an independent failure mode. If CPU and GPU both omit the last element, their arrays might agree while a conservation check fails. Conversely, an invariant alone may be too weak: many wrong arrays can share the correct sum. Reference comparison and invariants complement rather than replace each other.

## Correctness decision ledger

Before execution, write these fields:

1. Input domain and representative edge cases.
2. CPU reference algorithm, precision, and independent derivation.
3. Exact fields and approximate fields.
4. `atol` and `rtol` per approximate field, with rationale.
5. Non-finite-value policy.
6. Independent invariants and their derivation.
7. Failure diagnostics and the rule that every gate must pass before timing.

This ledger makes a later pass or failure reproducible without pretending that one threshold fits every CUDA program.

## Evidence boundary

The formula, ledgers, and Exercises on this page are static review artifacts. They contain no compiled executable, GPU observation, measured error distribution, or performance result. Compilation and runtime evidence axes remain empty. A future Lab must choose thresholds before its run, record its Environment Manifest and raw results, and keep those observations separate from this unit.
