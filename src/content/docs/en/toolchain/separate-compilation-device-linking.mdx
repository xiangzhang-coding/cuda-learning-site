A [translation unit (TERM-037)](/en/glossary/#term-037) is preprocessed and compiled independently. When device code must reference an externally linked device entity from another translation unit, the build needs [relocatable device code (TERM-122)](/en/glossary/#term-122) and a [device link (TERM-123)](/en/glossary/#term-123). The device-link output remains input to the final [host link (TERM-124)](/en/glossary/#term-124); it is not a runnable program.

## What you should be able to do

- Begin with NVCC's whole-program default and decide whether a device call graph crosses a translation-unit boundary.
- Explain why `-dc` is equivalent to `--relocatable-device-code=true --compile`, and produce a relocatable object for each participating CUDA source.
- Draw `CUDA sources -> RDC host objects -> device-link object -> final host artifact` while preserving device link and host link as two phases.
- Audit target, ABI, pointer-size, Toolkit-linker-version, static/shared-library, and `__CUDA_ARCH__` boundaries.
- Distinguish source and link artifacts from compilation, runtime, and performance evidence.

## Whole-program device compilation is the default

NVCC compiles device code in whole-program mode by default. Each CUDA translation unit's host object embeds executable device code, and that device code cannot leave an unresolved external reference to an entity in another file. Adding a device-link step has no effect in this mode because the input objects contain no relocatable device code for the device linker to combine.

Host code has long supported separate compilation, but that fact does not automatically extend to the device call graph. A `.cu` file may call a host function exposed by another object while a kernel in that same file still cannot call a `__device__` function defined only in another translation unit.

Review therefore starts with the symbol graph, not the number of project files. If every device reference resolves within its own translation unit, the whole-program default is sufficient. Switch to separate compilation only when an external device edge crosses a file boundary.

## An external device reference changes the link graph

Suppose a kernel in `caller.cu` calls `ex10_device_scale()`, whose definition is in `device_math.cu`. The declaration tells the compiler the signature, but the definition is absent from the current translation unit. A whole-program object cannot leave that external device edge for the ordinary host linker; the host linker does not resolve the CUDA device symbol graph.

The correct graph keeps source, artifact, and consumer separate:

| Node | What it produces or preserves | Next consumer |
| --- | --- | --- |
| `caller.cu` | call edge to an external device function | RDC compile produces `caller.o` |
| `device_math.cu` | external device-function definition | RDC compile produces `device_math.o` |
| `caller.o` + `device_math.o` | embedded relocatable device code, host code, and unresolved/resolved device symbols | device linker |
| `device_link.o` | embedded executable device code with device references resolved under the link contract | host linker |
| original objects + `device_link.o` | host symbols, registration code, CUDA Runtime references, and the linked device image | final host artifact |

An `extern` declaration is not a link result. It establishes a symbol contract only; the definition, RDC mode, device-link input set, and compatible target must all still be present.

## Relocatable device code and `-dc`

`--device-c` (`-dc`) compiles each input to a host object containing relocatable device code. The exact equivalence stated by the NVCC documentation is:

`-dc` = `--relocatable-device-code=true --compile`

Apply this option to every CUDA source participating in the cross-translation-unit device graph. Applying `-dc` only to the caller or definition side cannot retroactively turn the other side's existing whole-program object into an RDC object. Each compile command must also record the dialect, host compiler, pointer size, and target clauses used by the same build contract.

A relocatable object is an intermediate artifact. It may retain an external device reference, so successful object generation proves neither that every device definition was supplied nor that device link or host link will succeed.

## Device link resolves device symbols

`--device-link` (`-dlink`) invokes only the device-link phase. It reads objects containing relocatable device code, eligible static archives, and other documented device-code inputs; resolves external device symbols; and emits a **host object** containing embedded executable device code. The ordinary Linux default name is often `a_dlink.o`, but a reliable build names the output explicitly.

The output type matters: the device-link object is input to the host linker, not the final executable. Every target architecture needed in the final artifact must be passed to the device linker because this phase determines which targets enter the linked device image.

`nvcc <objects>` can coordinate the device and host linkers implicitly, but that convenience must not blur their two acceptance boundaries. To audit unresolved device symbols, record the device-link command, complete input set, target options, exit status, and output identity.

## The final host link is another phase

Host link consumes the original CUDA host objects, the device-link object, other host objects, and required CUDA and host libraries, then creates an executable or host library. It resolves host symbols, registration stubs, and Runtime references. It does not replace the earlier device-symbol resolution.

The NVCC documentation gives a general rule: host objects containing device references should be visible to both device linker and host linker; a pure-host object need not be shown to the device linker. Omitting an original CUDA object can discard implicitly generated host registration code even when its device definition participated in device link.

EX10's explicit pipeline uses `--no-device-link` for the final link and passes `device_math.o`, `caller.o`, and `device_link.o` together. The host-link target therefore cannot silently repeat device link, and both artifact boundaries remain auditable.

## The target contract spans compile and device link

Each RDC compile may carry one or more virtual and real target outputs. Device link must receive every target architecture required by the final artifact. Do not assume that the device linker will recover a missing image from an undeclared target, another Toolkit Lane, or a shared library.

A target audit records at least:

1. Each object's virtual assumptions and available real or PTX code.
2. The complete target set requested by the device-link command.
3. Whether each object set has link-compatible SM code or a PTX path suitable for the desired target.
4. Which linked images the final host artifact should contain and which inspection record will check them.

M17 owns the broader target-plan design. M18 only requires link inputs and device-link target selection to remain compatible. Successful target spelling still proves neither artifact contents nor runtime selection.

## Static libraries are considered; shared libraries are ignored

The NVCC device linker can read static host-library formats: `.a` on Linux and `.lib` on Windows. It considers members containing relocatable device code; objects without RDC contribute nothing to device link.

The same NVCC documentation explicitly says that the device linker ignores dynamic libraries: `.so` on Linux and `.dll` on Windows. This does not mean the host linker cannot consume a shared library. It means a device definition stored only in that `.so` cannot satisfy an external device reference in this device-link invocation. Device link still lacks the symbol when the shared library is its only definition source.

Keep two columns in the library ledger: `considered by device linker` and `consumed by host linker`. Passing `-lfoo` to both linkers does not mean they read the same content from the library.

## Object compatibility is a mechanical gate

The current and archived NVCC documentation gives the same core object-compatibility requirements: relocatable device code can link only when it has the same device-code ABI version, the same pointer size (32 or 64), and a link-compatible SM target architecture. The device linker's Toolkit version must also be at least as new as the objects' Toolkit version. Incompatible inputs should produce a link error.

"Link-compatible" means neither "identical target spelling" nor "any larger capability is acceptable." When an object also carries applicable PTX, the device linker may follow the documented path to generate cubin for the desired architecture and then link it. Otherwise, missing target-compatible code remains a failure. Bind every verdict to the actual object inventory and selected linker version.

Passing mechanical compatibility only means the linker can combine the objects. It does not validate algorithm correctness, application contracts outside the ABI, or the macro-driven semantic mismatch below.

## `__CUDA_ARCH__` can create cross-object semantic conflicts

Under separate compilation, do not let the behavior of a weak or template function in a shared header depend on `__CUDA_ARCH__` while allowing different objects to compile with different `compute_...` assumptions. The objects may produce same-named specializations with different behavior. Link selects only one version, so behavior depends on which definition is chosen.

There are two safe policies: compile every affected object for the same compute architecture, or do not branch shared-header function behavior on `__CUDA_ARCH__`. Link-compatible SM code, the same ABI, and the same pointer size do not remove this semantic risk.

Add this check to source review: list header-defined weak and template entities, each translation unit's compute target, and whether the macro branch changes observable behavior. Without that ledger, a successful link is not proof of semantic consistency.

## Artifact ledger

| Artifact or boundary | Fact it can establish | Fact it cannot establish |
| --- | --- | --- |
| Reviewed source graph | declaration, definition, and intended cross-TU edge | compiler acceptance or resolved symbols |
| `caller.o` / `device_math.o` | each RDC compile succeeded in a qualifying record | device-link, host-link, or execution success |
| `device_link.o` | selected inputs completed device link in a qualifying record | final host artifact, load, launch, or correctness |
| Final host artifact | host link succeeded and produced static-inspection input in a qualifying record | the artifact ran, GPU code executed, or results were correct |
| Hash or symbol ledger | exact bytes and inspected symbol observations | runtime behavior, latency, throughput, or speedup |

Each row needs an exact source commit, Toolkit Lane, host compiler, full command, target set, input hashes, exit status, and output hash before it becomes a reviewable build record. A downstream artifact cannot repair missing upstream provenance.

## Retrieval check

1. Why is whole-program device compilation the default even though host code can already be separately compiled?
2. Which source edge requires RDC, and what is the exact equivalence between `-dc` and its two long options?
3. What does device link resolve and produce, and why must that output still enter a separate host link?
4. How do a static archive and shared library differ for the device linker?
5. After same ABI, pointer size, and link-compatible SM pass, what semantic risk can `__CUDA_ARCH__` still leave, and why is neither `device_link.o` nor the final host artifact runtime or performance evidence?
