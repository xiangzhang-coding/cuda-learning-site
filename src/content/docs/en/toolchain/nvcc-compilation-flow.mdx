[NVCC (NVIDIA CUDA Compiler Driver, TERM-115)](/en/glossary/#term-115) coordinates multiple translation paths for CUDA source. It delegates non-CUDA work to a [host compiler (TERM-116)](/en/glossary/#term-116), and a [compilation phase (TERM-117)](/en/glossary/#term-117) expresses the input, requested output, and stopping boundary on which a caller may rely.

## What you should be able to do

- Treat only documented NVCC compilation phases as stable interfaces across Toolkit releases, never displayed internal steps copied into a build script.
- Split a mixed `.cu` source into host and device paths and explain why both paths require preprocessing.
- Trace device preprocessing -> PTX/cubin -> fatbinary and host preprocessing -> synthesized host C++ -> supported host compiler -> host object.
- Distinguish the boundaries of `--ptx`, `--cubin`, `--fatbin`, `--compile`, final link, and `--run`.
- Explain the cross-translation-unit device-reference limit of the default whole-program mode and reject compilation artifacts as runtime or performance evidence.

## Stable contract: phases, not internal steps

An NVCC compilation phase is a logical translation step selectable through a command-line option. NVCC may break one phase into smaller steps. Those steps depend on internal Toolkit tools and implementation and can change in a new release. Even when `nvcc` displays the steps it executes, that trace is for debugging and must not be copied into a build script as a stable interface.

Phase selection depends on both the input suffix and requested-output option. The suffix says whether the phase input is a `.cu`, `.ptx`, `.cubin`, object, or another recognized form; the phase option says at which documented output boundary the caller wants to stop. Temporary file names, private subcommand order, and internal options shown by `nvcc -v` or `--dryrun` are not additional public phase contracts.

Review a build by asking two questions first: what does NVCC understand the input to be, and which documented phase output is requested? Do not infer a permanent pipeline from one release's internal transcript.

## Supported phases and stopping boundaries

The following original boundary matrix selects only the documented phases needed by this unit; it does not reproduce an owner table:

| requested boundary | phase selection | primary result | later boundary not established |
| --- | --- | --- | --- |
| preprocess source | `--preprocess` / `-E` | preprocessed text | compilation, link, execution |
| expose synthesized host source | `--cuda` / `-cuda` | `.cu.cpp.ii` host C++ output | host object, final link, execution |
| device PTX | `--ptx` / `-ptx` | device-only `.ptx` | host object, final link, execution |
| device cubin | `--cubin` / `-cubin` | device-only `.cubin` | host object, final link, execution |
| device fatbinary | `--fatbin` / `-fatbin` | device-only `.fatbin` | host object, final link, execution |
| compile to object | `--compile` / `-c` | `.o` on Linux or `.obj` on Windows | final link, execution |
| compile and link | no phase option, or explicit link selection | executable | runtime correctness, performance |
| convenience run | `--run` / `-run` | execution attempt after build | correctness, coverage, performance conclusion |

For a `.cu` input, `--ptx`, `--cubin`, and `--fatbin` stop at a device-only artifact and discard host code. `--compile` instead produces a host-linkable object. With no phase option, NVCC compiles and links all inputs by default. `--run` is a separate convenience phase; it does not retroactively upgrade a preceding artifact into observed runtime evidence.

## One CUDA source, two translation paths

A CUDA source can mix conventional C++ host code and GPU device functions in one `.cu` file. NVCC coordinates the split; the author need not manually create a "host half" and a "device half." Annotations determine where an entity must be valid: an unannotated or `__host__` entity enters host reasoning, a `__device__` or `__global__` entity enters device reasoning, and a `__host__ __device__` function needs distinct valid host and device versions.

This is not one preprocessing pass followed by a byte-stream split. The documented trajectory first preprocesses for device compilation. It preprocesses the input again for host compilation and synthesizes C++ that the host compiler can process. The same declaration, macro, or function body can therefore face different constraints on each compilation path.

## Device path: preprocess -> PTX/cubin -> fatbinary

The device path first preprocesses the input for device compilation, then compiles device functions to PTX and/or CUDA binary (cubin). PTX is an intermediate assembly form; a cubin is a device binary for one GPU architecture. M15 tracks their positions in the trajectory, while M16 and M17 own their detailed compatibility and target semantics.

The resulting PTX and cubin images are placed in a fatbinary. An ordinary CUDA object build passes that fatbinary image to the host path for embedding. Explicit `--fatbin` instead stops at a standalone, device-only `.fatbin` output. Neither form records that a kernel ran.

`--ptx`, `--cubin`, and `--fatbin` are documented phase boundaries selectable by callers. A device-preprocessing temporary filename, internal compiler invocation, and assembler command order remain implementation details.

## Host path: preprocess again -> synthesized C++ -> host object

The input is preprocessed again for host compilation. NVCC then synthesizes host C++: it embeds the device fatbinary and transforms CUDA-specific C++ extensions into C++ constructs the host compiler can process. `--cuda` can expose the documented `.cu.cpp.ii` boundary; that output is to be compiled by the same host compiler NVCC used to preprocess the `.cu` input.

NVCC does not replace a host C++ compiler. It forwards non-CUDA steps, required preprocessing, and compilation of synthesized host C++ to a host compiler supported by NVCC. Support depends on the selected Toolkit, platform, and compiler version. Merely finding a compiler on `PATH`, or bypassing the version check with `--allow-unsupported-compiler`, does not establish a supported configuration. An unsupported host compiler may cause compilation failure or incorrect runtime execution.

The supported host compiler compiles the synthesized host code and embedded fatbinary into a host object. That `.o` or `.obj` is host-linkable, but it is not yet the final executable and has not executed its embedded device image.

## Host object and final link

`--compile` stops at the object boundary. The final link combines compatible host objects and libraries, resolves required host definitions, and adds CUDA runtime libraries to produce an executable. The baseline flow uses NVCC to drive the final link so it can coordinate required CUDA link inputs. A host object does not establish a successful final link, and a successful host link does not establish a device launch.

Host linking and device linking are distinct boundaries. Only a relocatable-device-code workflow has meaningful device-link work; M18 separately owns that object graph, its options, and its failure modes. This unit does not blur the final host link into a claim that every device reference was resolved.

## Device whole-program mode is the default

CUDA programs use whole-program compilation mode by default. This default constrains device code: device code cannot reference an entity from a separate file, and device-link steps have no effect in whole-program mode. It does not mean ordinary host C++ definitions cannot be resolved across objects by the host linker.

Therefore, placing a device callee definition in `producer.cu`, leaving only its declaration in `consumer.cu`, compiling each file separately with `--compile`, and relying on the final host link cannot repair the missing device definition under the default mode. Either make the required device definition visible inside the whole-program boundary or deliberately adopt the relocatable-device-code and device-link contract taught by M18.

A default executable can contain an embedded fatbinary, but "the fatbinary is embedded" and "a cross-file device reference was legally resolved" are different claims.

## Artifact ledger: what it is and what it does not prove

| checkpoint / artifact | producer boundary | what can be inspected | what it cannot establish alone |
| --- | --- | --- | --- |
| device-preprocessed input | documented trajectory checkpoint | expanded-source contract seen by the device path | stable temporary filename or internal command |
| `.ptx` / `.cubin` | explicit device phase | requested device output exists and type/target metadata can be inspected | kernel execution, correctness, speed |
| fatbinary image / `.fatbin` | device packaging boundary | selected device images were packaged | which image a runtime selected for a GPU |
| synthesized `.cu.cpp.ii` | `--cuda` boundary | embedded payload and transformed host-side constructs can be inspected | host-compiler acceptance or final link |
| host `.o` / `.obj` | `--compile` boundary | selected host path produced a host object | executable link, GPU launch, output correctness |
| executable | final host link | the link boundary succeeded for exact inputs | program execution, device-path reachability, performance |

Artifact inspection must bind the exact source, Toolkit, host compiler, options, target request, command result, and artifact identity to support a bounded compilation or inspection claim. Even a complete record does not automatically cross into the runtime or performance evidence axis.

## Evidence boundary

This page's phase matrix, trajectory, artifact ledger, Exercises, and canonical imports are static teaching and source artifacts. They do not run NVCC or execute a CUDA binary, so M15's compilation, runtime, expected-observation, and recorded-observation arrays all remain empty.

The existence of a `.ptx`, `.cubin`, `.fatbin`, host object, or executable does not establish that GPU work executed, results were correct, a runtime selected a particular image, launch latency fell, or a program became faster. A compilation artifact is neither runtime evidence nor performance evidence. A future claim must separately record the exact Toolkit Lane, host compiler, source identity, commands and logs, and artifact-inspection criteria, plus the GPU Environment Manifest, inputs, oracle, and observations required by any runtime claim.
