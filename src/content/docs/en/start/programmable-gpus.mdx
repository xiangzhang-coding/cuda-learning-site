GPU programmability is not best explained as a parade of newer products. It emerged because each useful interface exposed a limit in the abstraction below it. This Learning Unit follows that abstraction pressure from graphics work, to selected programmable stages, to general-purpose work expressed through graphics, and finally to a model in which kernels and parallel work are primary.

## What you should be able to do

- Explain why large amounts of independent graphics work favored aggregate throughput without claiming that every individual operation had low latency.
- Distinguish a fixed-function interface, a programmed graphics stage, and a general-purpose GPU interface by what the programmer can express and what constraints remain.
- Relate vertex and fragment programs, Cg, Brook, and CUDA as responses to different abstraction pressures rather than as a product chronology.
- Explain why CUDA makes kernels, thread blocks, locality, and block independence central to scalable heterogeneous programming.

## Motivation: throughput created pressure on fixed state

Real-time graphics applies similar transformations and shading operations to many vertices and fragments. Much of that work can proceed independently, so a design can keep many items in flight and optimize the amount completed per unit time. This is aggregate throughput. It is different from minimizing the latency of one serial task, and it does not mean that every graphics operation is independent or equally expensive.

Early graphics interfaces matched that workload with a pipeline of specialized operations. Applications selected matrices, lighting modes, texture combinations, fog, and other predefined state. That fixed-function state was efficient when the desired effect fit the menu, but each new effect exposed the same problem: the application could configure an operation without defining a new operation sequence. Adding more state and extensions enlarged the menu without removing that rigidity.

The important causal step is therefore not “newer hardware gained more features.” Independent work rewarded throughput, while fixed state made the growing range of desired computations difficult to express. The interface needed a controlled place for application-defined instructions without discarding the parallel graphics pipeline around it.

## Programmable stages: expose instructions, retain the pipeline

The 2001 [user-programmable vertex-engine paper](https://research.nvidia.com/publication/2001-08_user-programmable-vertex-engine) describes programs operating on streams of independent vertices while remaining embedded in a broader fixed graphics pipeline. The programmer gained control over a selected stage, not over an unrestricted machine.

The Khronos [ARB_vertex_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_vertex_program.txt) and [ARB_fragment_program](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_fragment_program.txt) specifications made the distinction explicit. Conventional state implied a sequence of per-vertex or per-fragment operations. A program supplied an explicit instruction sequence for that stage. Invocation, available inputs, result registers, resource limits, primitive assembly, rasterization, and later pipeline operations still followed graphics semantics.

Cg raised the source-language level. Its C-like syntax, compiler, profiles, and support for major graphics APIs let programmers describe vertex and fragment computations without writing each target instruction directly. The [Cg paper](https://doi.org/10.1145/882262.882362) still describes a system for graphics stream processors. A higher-level language improved expression and portability across graphics targets, but it did not turn every stage into a general-purpose kernel interface.

## GPGPU: route nongraphics work through graphics abstractions

Once a fragment stage could perform arithmetic and sample textures, programmers could reinterpret graphics resources. Arrays became textures, a fragment program performed a nongraphics calculation, a drawing operation generated invocations, and a render target collected results. General-purpose computing on graphics processing units, or GPGPU, described the goal, but the path to that goal still passed through graphics-shaped inputs, outputs, and passes.

This mapping proved that useful nongraphics work could exploit GPU throughput, but it also exposed the next abstraction pressure. A numerical program had to be reformulated around texture access, fragment invocation, render targets, restricted writes, and sometimes multiple rendering passes. The graphics API remained both the access route and the constraint.

[BrookGPU](https://graphics.stanford.edu/projects/brookgpu/) raised the level again. Brook extended C with streams and kernels, while its compiler and runtime abstracted and virtualized details of the graphics hardware. Unlike Cg, its programming surface was aimed at general-purpose stream computation. Unlike CUDA, its implementation still had to map that surface through graphics-era mechanisms. Language and runtime abstractions could hide many constraints, but they could not make the underlying interface contract disappear.

## The CUDA shift: make general-purpose parallel work primary

CUDA changed the primary question from “how can this calculation be encoded as graphics?” to “how should host and device divide a parallel computation?” In this heterogeneous model, host code launches a kernel. A grid contains thread blocks, each block contains threads, and the memory hierarchy makes data movement and locality explicit rather than disguising arrays as graphics resources.

A thread block is both a work partition and a locality boundary. Threads in one block can cooperate through shared memory and block-scoped synchronization. Blocks in the basic model must remain independent because a scheduler may execute them in any order, concurrently, or at different times. The 2008 [CUDA paper](https://doi.org/10.1145/1365490.1365500) connects that block independence to transparent scalability across GPUs with different numbers of processing cores.

Block independence is therefore both a restriction and a scalability mechanism. A kernel cannot assume that another block has already produced a value unless it uses a separate supported coordination boundary. In return, the runtime can place independent blocks according to available resources. This model does not promise a speedup for every program. Available parallelism, data movement, locality, control flow, problem size, and CPU work still determine whether GPU execution is useful.

## A concept-driven timeline

This original timeline is organized by pressure, response, and retained boundary. Dates locate the cited interfaces; they do not rank products or claim an “ever faster” sequence.

| Abstraction pressure | Interface response | Boundary that remained | Source anchor |
| --- | --- | --- | --- |
| Many independently processed graphics items rewarded aggregate throughput, while fixed state offered only predefined operations | Keep a specialized parallel pipeline but seek controlled application-defined work | Graphics data and stage order still defined the task | 2001 programmable vertex-engine paper |
| Per-vertex and per-fragment state combinations became too inflexible | Expose explicit vertex and fragment instruction programs | Invocation, inputs, outputs, and surrounding stages remained graphics-specific | 2002 ARB vertex and fragment specifications |
| Stage assembly and target differences made programs hard to author and move | Compile a C-like language through stage profiles and graphics APIs | Programs still targeted vertex or fragment processors | 2003 Cg paper |
| Nongraphics algorithms needed a more natural data-parallel surface | Present streams and kernels through a compiler and runtime | The implementation still mapped work onto graphics mechanisms | 2004 BrookGPU project and paper |
| Graphics encoding itself became the obstacle to broader parallel computing | Make heterogeneous kernels, grids, thread blocks, memory locality, and scheduling the primary model | Scalable execution requires independent blocks and explicit coordination boundaries | CUDA introduced in 2006; CUDA model described in the 2008 paper |

The sequence is causal: each interface solved an expression problem and made the next remaining constraint easier to see.

## Boundaries that prevent false equivalence

| Interface class | What the programmer supplies | What still controls execution |
| --- | --- | --- |
| Fixed-function interface | Values and choices for predefined operations | The system owns the operation sequence |
| Programmed graphics stage | Instructions or higher-level code for a selected vertex or fragment stage | Graphics invocation, stage inputs and outputs, and the surrounding pipeline |
| General-purpose GPU interface | Kernels, work decomposition, data, and coordination within a non-drawing programming model | The runtime, hardware limits, memory hierarchy, and declared synchronization rules |

“Programmable” alone does not identify the row. Cg looked like C but targeted graphics stages. A fragment program could perform a nongraphics calculation while still using a graphics-stage interface. Brook offered a general-purpose stream programming surface over a graphics-mediated implementation. CUDA made a general-purpose heterogeneous model primary, but it did not erase memory, scheduling, or synchronization constraints.

This account also avoids three invalid shortcuts. A selected programmable stage is not an unrestricted processor. A general-purpose interface does not make every workload suitable for a GPU. A later date does not by itself explain why an abstraction changed.
