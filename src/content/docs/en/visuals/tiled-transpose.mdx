## Learning purpose

After prerequisite Learning Unit **A05**, use VIS11 to inspect tiled transpose by separating its mathematical mapping from its physical shared-memory layout. The related Runnable Example is **EX14**. This Visual Explainer handles one `4 × 4` or `8 × 8` square tile and makes every input cell's source coordinate, destination coordinate, row-major index, and physical shared slot directly checkable.

## Controls

Three native selects choose reviewed tile size `4` or `8`, logical layout `input-row-major` or `output-row-major`, and physical shared-row padding `0` or `1`. **Reset** restores `4 / input-row-major / 0` and returns focus to the tile-size select. The native selects and button retain their keyboard behavior, and a polite live region announces each state change.

Both controls and the live workbench carry `hidden` in source HTML. The light-DOM custom element reveals them only after finding every control, status region, input/output grid, and physical-row container and successfully deriving the initial model. The page has no autoplay, timer, randomness, browser storage, range input, or persisted state.

## Transpose mapping

For tile size `N`, input cell `(row, col)` has row-major `inputIndex = row × N + col`. Transpose maps it to output `(col, row)`, so `outputIndex = col × N + row`. The input grid is always ordered by increasing `inputIndex`; the output grid is always ordered by increasing `outputIndex`. They show before/after coordinates for the same `N²` logical values rather than two numeric computations.

For example, when `N = 4`, input `(1, 2)` has `inputIndex` `6` and maps to output `(2, 1)` with `outputIndex` `9`. The model applies the same formula to every logical cell and queries no device, warp, transaction, or bank.

## Logical layout and physical padding

`input-row-major` places a logical cell at shared `(row, col)`. `output-row-major` places that same cell at shared `(col, row)`. These choices rearrange data slots in physical shared storage while preserving the logical `input(row, col) -> output(col, row)` mapping.

Physical row stride is explicitly `tileSize + padding`, and slot index is `sharedRow × stride + sharedCol`. With padding `1`, every row ends with a physical slot labeled “padding slot, no logical value.” It has no input/output coordinate, does not enter the transpose, and changes no output index. With padding `0`, the page explicitly states that no padding slots exist.

Layout and padding here are address arithmetic only. They observe no shared-memory bank mapping, bank conflict, global-memory coalescing, synchronization, latency, bandwidth, or speedup. A real kernel must separately prove bounds, cooperative loading, barrier participation, global access patterns, and correctness.

## Static fallback

Outside the interactive area, the server permanently renders four tile-size/padding selections: `4/0`, `4/1`, `8/0`, and `8/1`. Every selection has a purpose-built input-before grid, output-after grid, and both `input-row-major` and `output-row-major` physical shared rows. The static markup is not a duplicate of the hidden live DOM.

Together, the four selections contain 160 input logical cells, 160 output logical cells, 48 physical rows, and 344 physical slots. Twenty-four padding slots each carry a slot index, row, column, and “no logical value” text. Static content remains with JavaScript disabled, at a 390-pixel viewport, under reduced motion, in forced colors, and in print. Coordinates, indices, arrows, border styles, and text carry meaning without color alone.
