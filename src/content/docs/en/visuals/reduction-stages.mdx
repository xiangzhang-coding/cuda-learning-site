## Learning purpose

After prerequisite [A02](/en/algorithms/multi-stage-reduction/), use VIS10 to inspect which partial sums remain after each round of a reduction tree. An **inactive lane** means that the ledger position emits no update in the current round; it does not mean the browser observed a GPU instruction. This **deterministic** Visual Explainer lets a learner switch the **algorithm variant** and inspect every **reduction stage** and **inactive lane**. Related practice is [EX11](/en/examples/multi-stage-reduction/), and numerical-order boundaries are covered by [Q02](/en/correctness/floating-point-order-reproducibility/).

## Controls

The first native select chooses `adjacent-pairs` or `stride-halving`. The second native select accepts only `5`, `6`, or `8` input elements; each selection uses a prefix of the fixed values `[3, 1, 4, 1, 5, 9, 2, 6]`. **Next stage** advances exactly one round. **Reset** preserves the current selection and returns to the input stage. Changing either select clears traversal state.

Buttons retain their native Enter and Space behavior. When the final step disables a focused Step button, focus moves to Reset; after Reset, focus returns to the algorithm-variant select. A polite live region announces state changes. There is no autoplay, timer, randomness, storage, or persisted state.

## Stage model

The four frames are input, first combine, second combine, and final sum. `adjacent-pairs` writes each adjacent partial sum to the lowest-numbered lane in its group; an unmatched tail value carries forward. `stride-halving` combines positions at distances `4`, `2`, and `1`. Both paths produce the same final sum for one integer prefix while exposing different intermediate active positions.

These schedules are original bounded integer dependency graphs, not copies of an NVIDIA algorithm, kernel source, warp schedule, or performance recommendation. They help a learner read tree shape. A real implementation must separately handle block scope, synchronization between phases, arbitrary lengths, multi-block partial sums, and numerical operation order.

## Inactive lanes

Every stage always renders lanes `0` through `7`. An active lane shows its current integer partial sum. Every inactive lane says **neutral value 0**. That zero is an explicit visual-ledger placeholder, not an extra input, padding load, thread return value, or executed addition. A later model stage reads only predecessors marked active.

The inactive-lane count therefore cannot establish branch efficiency, occupancy, instruction count, latency, bandwidth, or speedup. Browser layout also does not represent a warp's timing order.

## Static fallback

Outside the workbench, the page permanently retains six selections: both variants with `5`, `6`, and `8` elements. Each selection contains four stages and every stage contains eight explicit lanes, for 24 stage ledgers and 192 lane cells. The complete content remains available with JavaScript disabled, at a 390-pixel viewport, with reduced motion, in forced colors, and in print. Inactive state uses text and a dashed border rather than color alone.

In source HTML, the controls and live workbench carry `hidden`. The light-DOM custom element reveals them only after it finds all native controls, the status region, four stage markers, and eight live lanes and successfully derives the initial frame. The static fallback does not depend on enhancement.

## Evidence boundary

VIS10 compiles and executes no CUDA, loads no kernel, queries no GPU, reads no profiler, and generates no timing or performance observation. Integer additions and stage transitions are declared browser-model output, not build, runtime, correctness, or performance evidence.

Compilation, runtime, expected-observation, and recorded-observation metadata are therefore empty. The page grants no **Compile-Checked**, **Community-Observed**, or **Runtime-Verified** Evidence Status.
