## Learning purpose

VIS06 is the Visual Explainer related to [M01](/en/memory/address-spaces/). It replaces a misleading “fast-to-slow memory pyramid” with a catalog organized by owner/acquisition, accessible scope, lifetime, release/end condition, and a physical or address-space caveat.

## Six-record catalog

The catalog contains exactly six records:

| Record | Owner and acquisition | Accessible scope | Lifetime and end |
| --- | --- | --- | --- |
| Host | Host application through a language or selected Runtime host-memory API | Host; device access needs a separately declared mechanism | Allocation/object lifetime; matching host release or process end |
| Global | Device allocation owned through a CUDA allocation path | Grid threads with a valid pointer; host manages or copies through APIs | Across launches until release, reset, or context/application end |
| Constant | Module/context symbol initialized through symbol APIs | Read-only to grid threads; host APIs can locate the symbol | Module/context lifetime until unload, reset, or context end |
| Shared | Static declaration or launch-sized storage per block | Threads in the owning block | Owning block during kernel execution; ends with block completion |
| Local | Compiler-managed private storage per thread | Owning thread | Owning thread/kernel execution; no host `cudaFree` |
| Register | Compiler-assigned per-thread storage | Owning thread | Owning thread/kernel execution; compiler-managed end |

The longer static table inside the component retains the release and physical/address-space caveat for every record.

## Filters

The scope filter offers host, grid, block, and thread. The operation/lifecycle filter separates explicit allocation/release, module/context end, owning-block end, and owning-thread end. Both default to “all.” Reset restores that deterministic six-record state.

Filters intersect: selecting thread scope and owning-thread end shows local and register; selecting host scope and owning-thread end shows an explicit empty state. Invalid filter identifiers fail closed in the pure model. Filtering never removes records from the permanent static catalog.

## Address-space and physical boundaries

Global, constant, shared, and local are device address-space concepts. Registers are compiler-managed on-SM storage. Host memory is included to expose ownership and transfer boundaries, but it is not another kernel device address space.

L1 and L2 are caches, not extra address spaces with independent source-level allocation lifetimes. Shared memory can share a physical SM resource with L1 while remaining programmer-managed shared address space. Conversely, **local** means logically private to one thread; it does not mean physically on-chip. CUDA local memory resides in device memory, and register pressure can spill thread values there.

The physical-layer diagram is therefore not a latency ranking. It does not claim a cache hit, placement for a selected variable, occupancy effect, or performance result.

## Static fallback

The static fallback contains both a three-layer grouping and a complete six-row table. Both are server-rendered from the same catalog and remain present without JavaScript and in print. The enhanced table is a filtered view, not the sole copy of the facts.

## Evidence boundary

This browser catalog compiles no CUDA, executes no kernel, and probes no allocation, register assignment, cache, or physical placement. Its filters grant no **Compile-Checked**, **Community-Observed**, or **Runtime-Verified** status. Every publication evidence axis is empty.

## Sources

The current [Writing SIMT Kernels memory-space sections](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html) provide the global, constant, shared, local, register, and cache boundaries.
