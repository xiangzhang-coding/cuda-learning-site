## Purpose

After Q07 and Q08, use VIS14 to convert an observable symptom into the next evidence source. The bounded rule is timeline first: application latency, CPU or launch gaps, copy/compute overlap, unclear dependencies, and a missing kernel selection go to Nsight Systems. Nsight Compute becomes the next step only after a representative timeline has selected one exact kernel instance and the learner has written one kernel-level question.

## Controls

One native select exposes six reviewed symptoms. Arrow keys, typeahead, and platform-native select behavior provide keyboard and mobile access. Reset restores the end-to-end symptom and returns focus to the select. A short polite live region announces changes; the changing workbench itself is not a live region.

Controls and the live workbench remain `hidden` in source HTML. The custom element reveals them only after finding every required part and deriving a valid initial view. There is no autoplay, timer, randomness, browser storage, network request, report parser, GPU query, or profiler process.

## Deterministic decision rule

The rule asks one question: **Has a representative application timeline selected one exact kernel instance, and is the current question kernel-level?**

- **No:** collect or inspect an Nsight Systems application timeline first.
- **Yes:** use Nsight Compute next, with the kernel filter, question, section or metric set, replay behavior, tool version, and counter permission declared before collection.

The recommendation is derived from the symptom. The model has no independent tool selector, so it cannot pair “kernel not selected” with Nsight Compute or bypass the timeline gate by clicking a preferred product.

## Tool boundaries

Nsight Systems correlates CPU threads, CUDA API activity, kernels, copies, streams, dependencies, gaps, and overlap in an application timeline. A `.nsys-rep` and an owner-supported export can locate work and select the next question. They do not, by themselves, prove a detailed kernel bottleneck.

Nsight Compute profiles selected kernels and can collect sections or individual metrics into a `.ncu-rep`. Metric names and availability vary by GPU and tool version. Collection may require multiple passes or replay, may perturb or serialize work, and requires a reviewed performance-counter policy. Query availability and collect only evidence needed for the declared question; a metric dump is not diagnosis.

Both tools use CUDA profiling infrastructure, including CUPTI behavior for applicable traces or counters, but their reports come from separate instrumented executions. Neither report should be described as the unmodified application run, and a kernel report does not replace the representative application timeline that selected it.

## Static fallback

The server permanently renders the gate plus all six leaves: four Nsight Systems leaves and two Nsight Compute leaves. Each leaf includes stable symptom, tool, scope, artifact, decision gate, and next-gate data. Text, headings, solid/double borders, and branch order carry the distinction without color alone. The complete tree remains visible without JavaScript, at 390 pixels, under reduced motion, in forced colors, and in print.

## Evidence boundary

VIS14 launches neither `nsys` nor `ncu`, opens no profiler report, queries no GPU, CUPTI activity, metric, or performance counter, and publishes no timeline, timing, bottleneck, throughput, or speedup observation. Compilation, runtime, expected-observation, and recorded-observation arrays are empty. It grants no Compile-Checked, Community-Observed, or Runtime-Verified Evidence Status.
