## Learning purpose

VIS09 arranges the documented NVCC compilation phases into a reviewable artifact flow. After prerequisites M15, M16, and M17, a learner should be able to explain why one `.cu` translation unit has host and device paths, how a virtual target constrains PTX, how a real target corresponds to SASS in a cubin, and how those device images enter a fatbinary, host object, and final linked artifact. The related Runnable Example is EX10.

This visual answers only, "Which stages and artifacts does the selected reviewed plan declare?" It does not answer whether a compiler is installed, a build succeeded, a driver can load an artifact, or a GPU would select a particular image.

## Controls

The first native select chooses an exact Toolkit Lane: `11.8.0`, `12.9.2`, or `13.3.1`. The second native select exposes only bounded target plans reviewed for that Lane. `11.8.0` has only baseline `compute_75 -> sm_75 + compute_75 PTX`; `12.9.2` and `13.3.1` also expose the exact `compute_90a` plan and family-scoped `compute_100f` plan. A third native select independently chooses **whole-program** (the default) or **separate compilation / RDC**. Targets and compilation modes do not imply one another: an `a` or `f` suffix scopes features and does not select RDC. The visual accepts no free-form target or mode and never treats a nearby number as the same target.

**Step forward** completes one active artifact stage. The whole-program traversal has six steps, keeps the separate device link explicitly **skipped**, and advances directly from the host object to the final host link. The RDC traversal has seven steps and completes device link before final host link. **Reset flow** restores step zero for the selected lane/plan/mode and returns focus to the Toolkit Lane select. When the final step disables the focused Step button, focus is repaired to Reset. Changing the Lane resets the target plan to baseline; changing the Lane, target plan, or mode resets traversal. A `role="status"` live region describes every accepted transition or rejection. The three native selects and buttons supply keyboard access without a custom key map.

The page has no autoplay, timer, storage, randomness, editable target, device query, or persisted state. The reducer accepts an `unknown` action. A malformed action, unknown Lane, unknown plan, unknown or malformed mode, plan unsupported by the Lane, invalid state, or extra step after completion fails closed and preserves the previous state object.

## Artifact flow

The documented NVCC trajectory first preprocesses the input for device compilation and produces PTX intermediate code and/or a cubin. Every VIS09 selected plan explicitly retains one virtual-target PTX image candidate and creates one native cubin/SASS image for the paired real target, then packages both into a fatbinary. These stages are the documented phase model that remains meaningful across the selected versions, not copied internal commands from `--dryrun` output.

The host path preprocesses the input again, synthesizes CUDA-specific C++ extensions into standard C++ while embedding the fatbinary, and asks the host compiler to create a host object. Explicit whole-program mode keeps the device-link node visible for review but marks it **skipped**: device code resolves within one compilation unit, so no separate device-link object is produced. Explicit separate compilation / RDC traverses that node, resolves relocatable device symbols across translation units, and produces an object for the host linker before final host link. The whole-program final link combines the host object and required libraries; the RDC final link also consumes the active device-link output. Either branch can form an executable or shared library.

Reaching a final linked artifact is still not a runtime event. A runtime may inspect an embedded fatbinary and seek a suitable image for the current GPU, but VIS09 has no selected GPU, loaded driver, device identity, launch, or loader observation. Therefore **runtime image selection always remains `unknown`**. The presence of cubin and PTX images alone cannot determine the actual selection.

## Target plans

The three target plans are a strict subset of the matrix reviewed by the [F06 compute-capability contract](/en/foundations/compute-capability/), not an architecture catalog:

- All three Lanes contain the baseline `compute_75` virtual target, `sm_75` native image, and `compute_75` PTX candidate.
- The `12.9.2` archive and selected Toolkit `13.3.1` also contain `compute_90a` / `sm_90a`. The `a` suffix enables an architecture-specific feature set whose scope is exact compute capability 9.0 only.
- Those same two Lanes contain `compute_100f` / `sm_100f`. The `f` suffix enables a family-specific feature set whose scope is only the family declared by the current owner table.

Compiler acceptance of a target name establishes only a compile-plan premise. A PTX candidate does not automatically establish a loaded-driver path, and qualified `a` or `f` code cannot expand to arbitrary later architectures by numeric ordering. Every real build still needs its exact command, Toolkit/NVCC, host compiler, input digest, and artifact-inspection record.

## Static fallback

For all seven lane/plan combinations, the server renders both the whole-program and RDC branches: fourteen explicit lane/plan/mode cards rather than only the initial `11.8.0` baseline. Every card contains the exact Lane, independent mode, target scope, virtual/real pair, PTX and cubin/SASS images, and seven rendered stages: host/device split, PTX, cubin, fatbinary, host object, conditional device link, and final link. The seven whole-program cards label device link **skipped** and explain that no device-link object is produced; the seven RDC cards label it **complete** and show its active output. No target suffix chooses either branch. This complete fallback remains available without JavaScript, at a 390-pixel viewport, with reduced motion, in forced colors, and in print. Text and border patterns carry technical states without relying on color.

Native controls and the live workbench are hidden in source HTML. The light-DOM custom element reveals them only after it finds every required control, status region, and stage node and successfully derives the initial frame. `data-pagefind-ignore` applies only to the changing live workbench; the permanent static fallback remains indexable. The standalone visual contains no HTML `id` and copies no NVIDIA figure, SVG, or image.

## Evidence boundary

VIS09 executes no `nvcc`, host compiler, linker, or CUDA. It reads no `.ptx`, `.cubin`, `.fatbin`, object, or executable and obtains no Environment Manifest, build log, artifact digest, loader result, kernel result, or timing. Its stage progression, target pair, and artifact labels are declared teaching output, not compilation, runtime, or performance evidence.

Compilation, runtime, expected-observation, and recorded-observation metadata are therefore all empty. The visual grants no **Compile-Checked**, **Community-Observed**, or **Runtime-Verified** Evidence Status and never rewrites "a final artifact may be formed" as "this artifact was built."
