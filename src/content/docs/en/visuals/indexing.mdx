## Learning purpose

VIS02 is a Visual Explainer. It separates the execution configuration’s `gridDim` and `blockDim` from each thread’s `blockIdx` and `threadIdx`, then adds logical data `extent` values so you can predict whether a launched thread owns a valid data position.

<IndexingExplorer locale="en" />

## Model and input boundary

Selecting 1D, 2D, or 3D normalizes inactive axes to size `1` and coordinate `0`. Grid, block, data, and selected-coordinate controls accept base-10 whole numbers. Invalid, out-of-range, fractional, or unsafe-product input never replaces the last valid model.

Per-axis interface caps and the limit of 32 visible thread buttons prevent runaway browser state. They are not CUDA device properties and do not define a GPU Capability Tier.

## One-, two-, and three-dimensional coordinates

Every active axis uses the same equation independently:

```text
global.x = blockIdx.x * blockDim.x + threadIdx.x
global.y = blockIdx.y * blockDim.y + threadIdx.y
global.z = blockIdx.z * blockDim.z + threadIdx.z
```

Changing dimensionality does not change the x-fastest convention. It only decides whether y and z participate in coordinates and bounds.

## Three different linear IDs

The block-local thread ID determines warp and lane membership:

```text
localThread = threadIdx.x
            + blockDim.x * (threadIdx.y + blockDim.y * threadIdx.z)
warp = floor(localThread / 32)
lane = localThread % 32
```

The grid-linear block ID also uses x-fastest ordering:

```text
linearBlock = blockIdx.x
            + gridDim.x * (blockIdx.y + gridDim.y * blockIdx.z)
```

Only after declaring an x-fastest row-major data layout do we obtain:

```text
dataIndex = global.x + extent.x * (global.y + extent.y * global.z)
```

In a multidimensional launch, `linearBlock * threadsPerBlock + localThread` is generally **not equal** to that spatial row-major `dataIndex`. VIS02 displays these values separately so execution-hierarchy ordering is not mistaken for a data layout.

## Bounds states

A launched thread is **IN BOUNDS** only when every active axis satisfies `global.axis < extent.axis`. A final partial block still contains legally launched threads, but some are **OUT OF BOUNDS** for the logical data and the kernel must make those threads skip the corresponding access.

The state uses text, an `OK`/`!` marker, and a border instead of color alone. A table retains each axis coordinate, extent, and Boolean predicate.

## Static examples

The 1D, 2D, and 3D cards at the end of the component are the purpose-built static fallback, generated by the same pure TypeScript model as the interactive workbench. Configuration, selected coordinates, global coordinates, local IDs, warp/lane, data indices, and bounds remain available with JavaScript disabled and in print.

## Evidence boundary

The browser only evaluates indexing equations. It compiles no CUDA and launches no GPU threads. Therefore selections, bounds labels, and static examples grant no **Compile-Checked**, **Community-Observed**, or **Runtime-Verified** status. See [O02](/en/start/evidence-status/) for evidence classification.
