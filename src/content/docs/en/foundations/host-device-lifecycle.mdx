An explicit CUDA program manages distinct resources on the host and device. This Learning Unit fixes that resource lifecycle into a reviewable path: initialization, allocation, transfer, kernel launch, synchronization, copy-back, and release. The goal is not to memorize an API list, but to answer “who owns this resource?” and “where is its last use?” at every step.

## What you should be able to do

- Explain host data, device buffers, kernel work, and host verification in the required order.
- Distinguish a host container, a device pointer value stored on the host, and the device allocation named by that value.
- Mark acquisition, usable state, last-use boundary, and release responsibility for every resource.
- Place `cudaGetLastError` and `cudaDeviceSynchronize` at their different boundaries in this minimal lifecycle without expanding them into a complete asynchronous-error model.
- Separate host-only tests, compilation facts, and actual GPU execution evidence.

## Ownership: a pointer is not an allocation

Host code creates and owns the host inputs, host output, and independent reference data. After `cudaMalloc` succeeds, the CUDA Runtime provides a device allocation and writes a value representing its address into a host variable. That host variable is only a handle to the device allocation. Copying or overwriting the pointer value does not copy, initialize, or release the storage it names.

Track two lifecycles separately: host containers are destroyed according to C++ scope, while every successful device allocation must be released exactly once by host control flow after its last use. `cudaMemcpy` changes destination storage contents; it does not transfer release responsibility. A kernel consumes device buffers but does not take ownership of them.

Last-use boundaries are more precise than “free everything at the end.” Device inputs are last used when the kernel completes; the device output is last used when D2H copy-back completes; the host output is last used by host comparison. Grouping release after comparison gives the canonical path one clear cleanup stage, but the underlying safety rule is that release never precedes the corresponding last use.

## Initialization: establish host facts first

First create host input, output, and expected/reference storage, then populate deterministic inputs. Host initialization must precede H2D transfer; otherwise the transfer faithfully copies undefined or incorrect input content.

Initializing host data does not initialize device storage. `cudaMalloc` only acquires an allocation. Do not assume zeroes or any other value until the program explicitly writes that storage. Host comparison occurs later, but its independent expected data must come from a declared rule rather than being inferred from GPU output.

## Allocation: acquire separate device buffers

Second, call and check `cudaMalloc` with the required byte count for every input and output. Each successful call adds a release obligation to the host resource ledger. A failed call produced no usable buffer, so later control flow must not treat it as acquired.

A reusable failure-safe control flow releases only allocations that succeeded before a partial allocation failure, exactly once each. The EX03 excerpt presents a fail-fast success path rather than structured partial-failure cleanup. Its success path must not copy or launch until every required buffer is available.

## Transfer in: establish kernel inputs with H2D copies

Third, use explicit `cudaMemcpyHostToDevice` directions to transfer initialized host inputs into matching device buffers. Check the status, source, destination, and byte count for every H2D transfer. Matching pointer types do not make a direction or length correct.

Only after successful transfer do the device inputs satisfy the precondition for this kernel launch. The host still owns its inputs, and an independent comparison may read them again later.

## Launch: submit work, then check the launch boundary

Fourth, submit the kernel launch with device pointers and the logical extent. Immediately after the launch expression returns, call and check `cudaGetLastError` so launch configuration and submission are inside the fail-fast path.

That check does not say the kernel has completed, and it does not make host output readable. F04 keeps only this necessary distinction; a fuller taxonomy of asynchronous errors is outside this unit.

## Synchronization: establish a completion and error boundary

Fifth, call and check `cudaDeviceSynchronize`. In this unit's canonical diagnostic contract, it explicitly waits for preceding device work and records a kernel completion/error boundary separately from the later D2H copy-back.

A synchronous `cudaMemcpyDeviceToHost` also waits for relevant device work and may return errors from earlier asynchronous work. Explicit `cudaDeviceSynchronize` is therefore not the only mechanism that makes a blocking D2H result readable. This project retains it to establish a separate, reviewable kernel completion and error boundary before copy-back.

Host control flow enters the normal copy-back path only after that boundary succeeds. A reusable design moves to cleanup if this call fails instead of comparing a host output that has not been established as a valid result; EX03's fail-fast macro terminates the process instead.

## Transfer out: establish the host result with D2H copy-back

Sixth, use `cudaMemcpyDeviceToHost` to copy device output into host output. A successful D2H copy-back is the device output's last-use boundary. After the call returns successfully, host comparison has a readable candidate GPU result.

Copy-back is not verification. It changes the address space containing the result; it neither proves the kernel correct nor compares expected and actual data.

## Verification: produce a verdict on the host

Seventh, compare actual output with expected output under an independent host rule and preserve the pass/fail verdict. The comparison must cover the declared logical extent and report enough context to locate the first mismatch.

A host-only test can verify a reference, comparator, or indexing helper, but it executes no GPU kernel. Likewise, Compile-Checked proves only that declared build stages succeeded. Neither substitutes for a GPU run that satisfies its environment, command, and acceptance criteria.

## Release: after last use, before return

Eighth, release every successfully acquired device allocation. The canonical success path places release after host comparison and returns the saved verdict only after cleanup, so a mismatch cannot skip `cudaFree` through an early return.

A stronger failure-safe variant follows the same ledger: release only acquired resources, never consume a result that was not established as valid, and never double free. The explicit `cudaFree` calls in the EX03 excerpt belong to its success path; the complete project's fail-fast macro terminates API-failure paths. Host containers are released when their C++ owner leaves scope.

The full textual reading is: establish deterministic data on the host; acquire uninitialized device storage; copy inputs H2D; submit the kernel; immediately check `cudaGetLastError`; use `cudaDeviceSynchronize` as the completion and error boundary; copy output D2H; run the independent host comparison and save its verdict; finally release every acquired device allocation before returning that verdict. This is the complete success-path order. A reusable failure-safe variant also stops creating new dependencies at its failure point and cleans up only resources already acquired.

## Retrieval check

1. Why does a successful `cudaMalloc` create both a usable resource and a release obligation without initializing its contents?
2. After a kernel launch, why does the canonical diagnostic sequence choose to check `cudaGetLastError`, then `cudaDeviceSynchronize`, before entering D2H copy-back? What waiting boundary does synchronous D2H itself provide?
3. Where are the last-use boundaries for device input, device output, and host output?
4. Why is successful D2H copy-back insufficient to produce a correctness verdict?
