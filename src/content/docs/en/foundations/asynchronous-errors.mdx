A CUDA kernel launch is normally asynchronous with respect to the host, so an asynchronous error may become host-visible only after the device work that caused it. At the same time, some launch-configuration problems can surface on the submission path immediately. A correct error lifecycle separates when an error originates, where the host observes it, and which state is read or cleared. It neither labels every CUDA call asynchronous nor treats the API call that reports an error as the unique cause.

## What you should be able to do

- Distinguish CUDA Runtime last-error state from the direct return value of an API call.
- State precisely that `cudaPeekAtLastError` reads without resetting state, while `cudaGetLastError` reads and then resets state to `cudaSuccess`.
- Place an immediate launch-configuration error and a deferred device-execution error on different timelines.
- Use an explicit synchronization boundary to wait for preceding device work and inspect its returned status.
- Keep error checks, result correctness, and CUDA Evidence Status as independent boundaries.

## Error state: separate direct returns from last-error state

A Runtime API call that returns `cudaError_t` has a direct return value, which callers should inspect at that call site. Kernel launch syntax does not provide an ordinary `cudaError_t` value to assign and inspect, so host code commonly queries last-error state adjacent to the launch. The channels are related but not interchangeable. For example, the direct return from `cudaDeviceSynchronize` must be checked directly rather than reconstructed at a later line.

For the single-Runtime-instance program in this unit, last-error state belongs to the host thread. The CUDA 11.8.0 documentation describes the last error produced by any Runtime call in the same host thread. The 12.9.2 archive and 13.3.1 documentation further identify the same CUDA Runtime library instance in that host thread. This is not a separate error queue for every kernel, stream, or device.

| Operation | What it reads | Does it reset last-error state after the read? | Does it establish device completion? |
| --- | --- | --- | --- |
| `cudaPeekAtLastError()` | The current last error for the host thread / Runtime instance | No | No |
| `cudaGetLastError()` | The same last error | Yes, to `cudaSuccess` | No |
| `cudaDeviceSynchronize()` | Its own synchronization result | Do not substitute it for either getter above | Yes, it waits for preceding requested device tasks |

`cudaPeekAtLastError` supports observation without consumption. If no new error changes state, repeated peeks continue to observe the same item. `cudaGetLastError` retrieves and consumes the current state, which can establish a deliberate starting point for the next diagnostic interval. If a preflight `cudaGetLastError` retrieves an old error, handle or report it; do not silently discard it merely to manufacture a clean trace.

All three requested Error Handling versions carry an important caveat: `cudaPeekAtLastError` and `cudaGetLastError` may also return errors from previous asynchronous launches. Many other Runtime API entries carry the same note. A call returning an error therefore establishes a host observation point. Without an isolated boundary, it does not prove that this call originated the error.

## Immediate errors: launch configuration fails on the submission path

Kernel launches are asynchronous with respect to the host, but that does not force every launch-related failure to wait until device execution. The Runtime processes the execution configuration on the submission path. When a configuration cannot form an accepted launch, failure can enter last-error state before the kernel body starts. A `cudaGetLastError` or `cudaPeekAtLastError` adjacent to the launch can therefore observe this immediate launch-boundary problem.

The canonical diagnostic sequence handles old last-error state, issues one launch, and queries the launch boundary immediately. If that check fails, synchronization-dependent processing, D2H, and comparison have not met their preconditions, so control enters cleanup. Synchronization cannot repair a rejected launch and should not be the first expected discovery point for this scenario.

Do not bind this teaching classification to one fixed error code. Different configuration defects, Toolkits, devices, or contexts can produce different statuses. The acceptance rule is that **the immediate check observes failure before the device body executes**, not that one enum value was memorized.

## Deferred errors: visibility follows device execution

On the other timeline, the Runtime accepts the launch, the adjacent check observes no new configuration failure, and the host continues. This result describes only the launch boundary visible at that time. It neither waits for the kernel body nor proves successful execution.

When a problem occurs while accepted work is actually executing, the error originates during device execution. The host needs a boundary that waits for the relevant work before it can obtain that deferred result. EX04 uses explicit `cudaDeviceSynchronize` to separate “launch accepted” from “preceding device work completed or failed” into two reviewable return points.

An immediate getter is not an execution probe. Placing `cudaGetLastError` very close to the launch still does not make it wait for the device. Placing it farther away does not automatically produce clear attribution either, because it may retrieve state that was not consumed earlier. Diagnostic quality comes from controlled state and intentional synchronization boundaries, not distance between source lines.

## Synchronization: make the host wait at a deliberate boundary

The `cudaDeviceSynchronize` reference in all three requested versions defines the call as waiting for the device to complete preceding requested tasks and returning an error when one of those tasks has failed. EX04 therefore uses it as an explicit completion/error boundary for a deferred execution error. The caller must inspect this call's own return value and stop treating output as valid when it fails.

Explicit device-wide synchronization is not the only place a CUDA program might wait. Operations such as synchronous D2H transfer can also form waiting boundaries. The API synchronization-behavior documentation also warns against simplifying names into “every function without Async blocks” or “every Async function returns immediately,” and Runtime calls may block for undocumented internal-resource reasons. Correctness may rely only on documented semantics, not one observed timing.

A narrow diagnostic interval is: handle existing last-error state; submit the target launch; check the launch boundary immediately; avoid mixing in unrelated work; wait for the target work; inspect the synchronization return directly. This improves attribution but still does not create a universal rule that “the reporting API is the cause,” especially with multiple streams, host threads, or Runtime-library combinations.

## Correctness: finding no error does not prove the result

Successful immediate and synchronization checks mean only that the checked API boundaries did not return failure. They do not prove indexing, algorithm, numeric tolerance, or output contents. Results still require an independent host reference or another explicit oracle after successful D2H. Conversely, an error enum alone does not identify one unique source line; controlled inputs, boundaries, logs, and appropriate debugging tools are still needed.

EX04 is a Runnable Example, while F05 is the Learning Unit that explains its model. They are separate evidence subjects. This page keeps both compilation and runtime axes empty.
