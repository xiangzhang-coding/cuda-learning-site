Multidimensional indexing is not a mechanical copy of a one-dimensional equation. A kernel first derives coordinates from launch geometry, then tests those coordinates against the logical extent of every active axis, and only then calculates a linear memory position under the application-declared data layout. These three contracts are different, and their order matters.

## What you should be able to do

- Calculate `gx`, `gy`, and `gz` for one-, two-, and three-dimensional launches.
- Explain how unspecified launch dimensions receive defaults and why those defaults do not create active data axes.
- Check every active axis before flattening and repair missing x, y, or z checks, incorrect Boolean combinations, and checks that occur too late.
- Distinguish CUDA execution geometry from the application's row-major data mapping.
- Use EX03's independent host reference boundary on non-divisible extents without reporting a host-only result as CUDA runtime evidence.

## Prerequisite

Complete [F02: Understanding the CUDA Execution Hierarchy](/en/foundations/execution-hierarchy/) first. You should already distinguish grids, blocks, threads, warps, and lanes, and know which hierarchy level supplies `blockIdx`, `blockDim`, and `threadIdx`. This unit composes those levels into a data-ownership contract. F04 will continue with the explicit host-device lifecycle.

## Coordinate contract: geometry comes before data layout

Every active axis independently uses the same coordinate rule:

```text
gx = blockIdx.x * blockDim.x + threadIdx.x
gy = blockIdx.y * blockDim.y + threadIdx.y
gz = blockIdx.z * blockDim.z + threadIdx.z
```

CUDA's three-component launch configuration type, `dim3`, stores x, y, and z extents in one value. As documented by the current Programming Guide, constructing a `dim3` with fewer arguments initializes unspecified components to `1`. A one-dimensional configuration therefore has y and z extents of 1, so their coordinates can only be 0; the same applies to z in a two-dimensional configuration. These defaults describe execution geometry. They do not invent an application `height`, `depth`, or data layout.

## One dimension: only x is an active data axis

A one-dimensional array needs only:

```text
gx = blockIdx.x * blockDim.x + threadIdx.x
```

The application declares legal coordinates as `0 <= gx < width`. Even though `gridDim.y = gridDim.z = blockDim.y = blockDim.z = 1`, y and z need not become data axes. They are only size-one launch components.

## Two dimensions: derive x and y separately

A two-dimensional image or matrix uses:

```text
gx = blockIdx.x * blockDim.x + threadIdx.x
gy = blockIdx.y * blockDim.y + threadIdx.y
```

A legal coordinate must satisfy both `gx < width` and `gy < height`. Ceiling division on each axis can leave non-owning threads in the rightmost block column, the bottom block row, or the bottom-right block. These threads belong to a legal launch but may not access the application array.

## Three dimensions: z is an independent coordinate

A three-dimensional volume adds:

```text
gz = blockIdx.z * blockDim.z + threadIdx.z
```

For `width = 10`, `height = 7`, `depth = 5`, and block shape `(4, 3, 2)`, ceiling division on each axis gives grid shape `(3, 3, 3)`. The final groups of blocks contain partial regions on x, y, and z. A valid x coordinate does not imply that the same thread's y and z coordinates are valid.

## Bounds: every active axis is a correctness precondition

The bounds check must cover every active axis and occur before any flattening or array access:

```text
1D: gx < width
2D: gx < width AND gy < height
3D: gx < width AND gy < height AND gz < depth
```

The equivalent early-return form returns when `gx >= width OR gy >= height OR gz >= depth`. The `OR` is essential: one invalid axis means there is no legal element. Joining the three invalid predicates with `AND` rejects only threads that exceed all three extents at once. Checking only x lets the y and z fringes cross the contract.

## Flattening: the application declares layout

This Learning Site and EX03 explicitly declare an x-fastest row-major layout. The mapping from a three-dimensional coordinate to a linear index is:

```text
index = ((gz * height) + gy) * width + gx
```

This is equivalent to `gx + width * (gy + height * gz)`. Adjacent x coordinates differ by 1, a complete row spans `width` elements, and a complete layer spans `width * height` elements. **CUDA grid/block geometry does not declare data layout.** Column-major storage, pitched rows, tiled formats, or other application contracts can use the same CUDA coordinates and require different mappings. Index multiplication must also use an integer type wide enough for the complete element count.

## Retrieval check

1. Which values do unspecified `dim3` components receive, and why can coordinates on those axes only be 0?
2. Why is `gx < width` alone not a correctness contract for a two-dimensional launch?
3. Why does an early return join invalid 3D predicates with `OR`, while the positive valid-thread predicate uses `AND`?
4. Why must every axis be checked before calculating `((gz * height) + gy) * width + gx`?
5. Why can neither CUDA geometry nor a CPU reference declare the application's data layout or prove GPU performance?
