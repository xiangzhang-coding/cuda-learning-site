## SRC-CUDA-065: Selected libcu++ contracts

**Related IDs:** M05, M13, L05. **Accessed and reviewed:** 2026-09-05. **Coordinate:** independently selected CCCL/libcu++ v3.4.2, commit `d36012203ef73ac7f966e848dd88482273e91e02`, released 2026-08-05. The reviewed header-only library offers an incomplete standards-oriented host/device `cuda::std` subset, not a replacement for `std`, and scoped `cuda::` extensions. L05 restricts atomic types to supported 32-bit forms. Default system scope does not supply CPU/GPU memory accessibility or system atomic support; block scope does not cover different blocks, and device scope requires the same memory synchronization domain. Relaxed operations do not publish a non-atomic payload; an acquire must observe the relevant release with sufficient scopes. `atomic_ref` requires a valid aligned referent, a sufficient lifetime, and exclusive atomic-reference accesses while references exist.

Barrier initialization must be published before participation. `arrive` does not wait; `arrive_and_drop` reduces the current countdown and future expected count rather than skipping participation. Consumers wait for the appropriate phase, and shared-buffer reuse needs a consume-before-overwrite edge. Pipeline order is producer acquire, issue, commit, then consumer wait, consume, release. Collective shared-state construction, roles, convergence, and lifetime remain caller obligations. `quit` relinquishes ownership; it neither drains nor cancels unfinished work.

Group `cuda::memcpy_async` participants supply the same arguments; source and destination do not overlap and payload is trivially copyable. Nongroup callers each issue a copy. `aligned_size_t` asserts that both addresses and the byte count satisfy the alignment; a false assertion is undefined behavior, not a hint. The SM 70 API floor is distinct from the site/CCCL CC 7.5 floor and eligible CC 8.0+ `cp.async` acceleration. No instruction mapping, overlap, or speedup is automatic. A synchronous fallback still preserves completion, publication, and reuse boundaries. Namespace and host/device annotations do not prove GCC-only compilation: the reviewed barrier-bound `memcpy_async` definitions are CUDA-compilation-guarded; this statement does not cover every pipeline-bound overload. Record Tensor Core input storage, actual multiplicand precision, Accumulator Type, epilogue computation, and D storage separately. FP32 accumulation cannot repair earlier input conversion, and float output does not prove FP32 multiplication. FP16 C++ WMMA permits `16x16x16/32x8x16/8x32x16` warp tiles with half or float accumulator fragments from SM70. BF16 uses those tiles with float accumulation from SM80. TF32 uses `16x16x8`, float accumulation, and SM80, with explicit `__float_to_tf32` conversion. Double uses `8x8x4`, double accumulation, and SM80. These are C++ WMMA warp tiles, not every MMA instruction shape or a rule requiring application dimensions to be divisible by them.

INT8 A/B must have matching explicit signed or unsigned types, with int accumulation/output fragments and the same three tiles as FP16; integer WMMA's API/PTX minimum is **SM72**. That adds no site support below CC 7.5 and is not a CUDA 13 `sm_72` code-generation target. An INT8 final output needs separately specified scales, zero points, rounding, and clamping. The current native-type table lists FP16/INT8 at CC 7.5 and every later listed row, and BF16/TF32 from CC 8.0. Native FP64 is listed only at **CC 8.0, 9.0, and 10.0**, not at 8.6, 8.7, 8.9, 10.3, 11.0, or 12.x. Double API eligibility at "SM80 or higher" does not establish native FP64 acceleration at all higher CCs or justify guessing uninspected compiler lowering.

PTX specifies at least single-precision FP16 multiplication, at least single-precision accumulation with FP32 C or D, and at least half precision when both are half. BF16/TF32 uses the specified input precision with at least single-precision accumulation; accumulation order, rounding, and subnormal-input handling are unspecified for these paths. C++ double WMMA uses `.rn`; other PTX double rounding modifiers are not extra C++ arguments. Integer overflow wraps as signed 32-bit without `.satfinite` and clamps to int32 extrema with it. Do not conflate this with floating C++ `satf`, which defaults to false and, when enabled, maps signed infinities to corresponding maximum normal finite values and NaN to positive zero. PTX removed floating `wmma.mma .satfinite`, so mechanical translation is invalid.

All warp members participate with matching parameters and no exited lanes, under warp-uniform conditions. Loads require **256-bit, or 32-byte, starting-address alignment** and `ldm` in elements. The documented half/float multiples are 8/4 elements; do not silently extrapolate these to other types. Edges must form complete valid tiles, not arbitrary masked WMMA loads. Float fragments cannot store directly through half pointers, and `x[i]` is not a portable coordinate. Warp synchronization does not replace block publication, reuse, or host completion.
