Record Tensor Core input storage, actual multiplicand precision, Accumulator Type, epilogue computation, and D storage separately. FP32 accumulation cannot repair earlier input conversion, and float output does not prove FP32 multiplication. FP16 C++ WMMA permits `16x16x16/32x8x16/8x32x16` warp tiles with half or float accumulator fragments from SM70. BF16 uses those tiles with float accumulation from SM80. TF32 uses `16x16x8`, float accumulation, and SM80, with explicit `__float_to_tf32` conversion. Double uses `8x8x4`, double accumulation, and SM80. These are C++ WMMA warp tiles, not every MMA instruction shape or a rule requiring application dimensions to be divisible by them.

INT8 A/B must have matching explicit signed or unsigned types, with int accumulation/output fragments and the same three tiles as FP16; integer WMMA's API/PTX minimum is **SM72**. That adds no site support below CC 7.5 and is not a CUDA 13 `sm_72` code-generation target. An INT8 final output needs separately specified scales, zero points, rounding, and clamping. The current native-type table lists FP16/INT8 at CC 7.5 and every later listed row, and BF16/TF32 from CC 8.0. Native FP64 is listed only at **CC 8.0, 9.0, and 10.0**, not at 8.6, 8.7, 8.9, 10.3, 11.0, or 12.x. Double API eligibility at "SM80 or higher" does not establish native FP64 acceleration at all higher CCs or justify guessing uninspected compiler lowering.

PTX specifies at least single-precision FP16 multiplication, at least single-precision accumulation with FP32 C or D, and at least half precision when both are half. BF16/TF32 uses the specified input precision with at least single-precision accumulation; accumulation order, rounding, and subnormal-input handling are unspecified for these paths. C++ double WMMA uses `.rn`; other PTX double rounding modifiers are not extra C++ arguments. Integer overflow wraps as signed 32-bit without `.satfinite` and clamps to int32 extrema with it. Do not conflate this with floating C++ `satf`, which defaults to false and, when enabled, maps signed infinities to corresponding maximum normal finite values and NaN to positive zero. PTX removed floating `wmma.mma .satfinite`, so mechanical translation is invalid.

All warp members participate with matching parameters and no exited lanes, under warp-uniform conditions. Loads require **256-bit, or 32-byte, starting-address alignment** and `ldm` in elements. The documented half/float multiples are 8/4 elements; do not silently extrapolate these to other types. Edges must form complete valid tiles, not arbitrary masked WMMA loads. Float fragments cannot store directly through half pointers, and `x[i]` is not a portable coordinate. Warp synchronization does not replace block publication, reuse, or host completion. | Teaching boundary | Reviewed fact |
| --- | --- |
| DFT sign and normalization | Forward uses the negative exponent sign. Neither forward nor inverse normalizes; a round trip scales by the product of logical transform dimensions, not batch count. FFT is an algorithm family for that DFT |
| C2C, R2C, C2R | C2C stores full complex input/output; real transforms exploit Hermitian symmetry. C2R input must satisfy that symmetry, including real-valued self-conjugate frequency points, and documented complex-type alignment |
| In-place real storage | Last logical dimension N stores `K=floor(N/2)+1` complex values; every innermost row requires `2K` real slots. Padding only at the final allocation boundary is insufficient for multiple rows |

| Advanced layout | Strides and batch distances use elements of the respective input/output type, not bytes. Keep both embeddings non-NULL when specifying an advanced layout; NULL embeddings select default-layout behavior that ignores the other advanced parameters |
| Plan and workspace ownership | With caller-managed scratch, disable autoallocation after create and **before** make-plan. Check planning success and workspace size before allocation/binding; each concurrent execution needs exclusive scratch until completion. A returned host call is not a completion fence |
| Scope of EX19 | Modest ordinary single-GPU FP32 C2C only, without real transforms, callbacks, low precision, multi-GPU, or timing. Compilation evidence is empty and runtime is Pending Hardware Verification. Reading an API contract grants neither status |

The corresponding release archives also returned 200, as recorded below; the older cuFFT archive-availability record in SRC-CUDA-074 does not apply to this cuSPARSE review.

**Representation and ownership:** The baseline [Generic APIs](https://docs.nvidia.com/cuda/archive/12.9.2/cusparse/index.html#cusparse-generic-apis), [CSR format](https://docs.nvidia.com/cuda/archive/12.9.2/cusparse/index.html#compressed-sparse-row-csr), and [`cusparseCreateCsr`](https://docs.nvidia.com/cuda/archive/12.9.2/cusparse/index.html#cusparsecreatecsr) distinguish descriptor metadata from caller-owned arrays. A Generic sparse descriptor records format, shape, stored-entry count, index types/base, value type, and pointers; it neither copies the arrays nor owns their allocation. `cusparseCreateDnVec` and `cusparseCreateDnMat` describe dense vectors/matrices, including matrix order and leading dimension. Legacy `cusparseMatDescr_t` is not an interchangeable Generic sparse object. Constructor success is not proof of valid matrix contents.

For base b, CSR has `rows+1` offsets, `nnz` column indices and values, first offset b, final offset `nnz+b`, monotonic offsets, and columns in the base-adjusted range. Equal adjacent offsets represent empty rows. The owner allows specified unsorted representations but does not guarantee correctness for duplicate coordinates; the original EX20/PB input policy rejects duplicates rather than assuming coalescing. COO/CSR/CSC/BSR describe different storage, and a format's existence does not imply support by every operation/algorithm. Stored bytes alone cannot choose a format or establish physical traffic or performance.

**Operation calls:** Baseline [SpMV](https://docs.nvidia.com/cuda/archive/12.9.2/cusparse/index.html#cusparsespmv) computes `y=alpha*op(A)*x+beta*y`; [SpMM](https://docs.nvidia.com/cuda/archive/12.9.2/cusparse/index.html#cusparsespmm) computes sparse-times-dense `C=alpha*op(A)*op(B)+beta*C`, not sparse-output SpGEMM. Operation flags, compute type, algorithm, scalar placement, and stream are separate from storage metadata. Input/output storage types do not alone determine computation precision. The ordinary FP32 baseline excludes mixed precision, experimental operators, and structured Tensor Core claims.

**Workspace and completion:** Check each exact `cusparseSpMV_bufferSize` or `cusparseSpMM_bufferSize` result and status. Returned bytes are a configuration-specific requirement, not a universal formula from `nnz`, a measured cost, or a GPU observation in this record. Allocate device workspace when nonzero, retain its required contents and ownership, and distinguish matrix/vector storage from workspace. Bind the handle stream; HOST pointer mode places alpha/beta scalars on the host, not the sparse arrays or dense operands. Asynchronous host return does not prove completion. Preserve descriptors, referenced device storage, and workspace until the relevant work completes; check the completion boundary before reading results, reconfiguration, or cleanup, including failure after submission. Destroying a descriptor does not free caller arrays.

**Preprocessing is operation-specific:** `cusparseSpMV_preprocess` is optional and was introduced in CUDA 12.4; it is absent from the 11.8 header/API surface. Under the 12.9.2 SpMV contract, there is one active buffer per sparse matrix descriptor. Preprocessing with another buffer makes the previous buffer inactive. Repeated accelerated calls preserve the active buffer's contents, matrix indices, and other configuration; documented exceptions allow changed alpha/beta, X/Y, and matrix values. Those changes still need compatible shapes/types and proper ordering after in-flight use. Independent prepared states can use separate descriptors and buffers while sharing safely unchanged matrix arrays. An inactive buffer can still be used for supported unaccelerated calls, not as proof that two active states coexist. This is not permission to overwrite workspace still in use.

`cusparseSpMM_preprocess` already exists in 11.8. It helps `CUSPARSE_SPMM_CSR_ALG1` and `CUSPARSE_SPMM_CSR_ALG3`, not `CUSPARSE_SPMM_CSR_ALG2`; call-level reuse constraints must be read from SpMM rather than inferred from SpMV. Changes to representation, operation, compute type, algorithm, or indices require a fresh contract check and appropriate size query/preparation. A supported no-preprocess path remains valid; no speedup or penalty is inferred here.

**Determinism boundary:** The selected NON_TRANSPOSE `CUSPARSE_SPMV_CSR_ALG2` path has a bounded run-to-run deterministic contract under fixed conditions. It does not promise bitwise agreement with a differently ordered CPU reduction, another GPU, a different operation, or another library version. Do not transfer that statement to every SpMV/SpMM algorithm. SpMM ALG3's documented determinism also needs the release-issue check in SRC-CUDA-076. Independent correctness criteria and observed reproducibility are separate from a documentation guarantee; neither has been executed here.
