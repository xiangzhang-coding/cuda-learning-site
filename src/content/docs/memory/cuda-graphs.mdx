[CUDA 图（CUDA Graph，TERM-111）](/glossary/#term-111)把 operations 与 dependencies 独立于 execution 记录。每个[图节点（graph node，TERM-112）](/glossary/#term-112)是一项 operation，directed edges 是 dependencies；[流捕获（stream capture，TERM-113）](/glossary/#term-113)是一种 construction mechanism；[可执行图（executable graph，TERM-114）](/glossary/#term-114)是提交执行的 instantiated object。

## 学完本单元，你应该能

- 把 repeated workload 绘成由 operation nodes 与 dependency edges 构成的 directed acyclic graph。
- 把 explicit Graph API 与 stream capture 保持为两种独立 graph-construction mechanisms。
- 审查 capture prohibitions、invalidation、origin-stream ownership 与 cross-stream rejoin boundaries。
- 按 `definition -> instantiate executable -> repeated launch` 推进，同时保留 external resource lifetimes 与 explicit completion。
- 在不提出 performance claim 的前提下，把 update 分类为 permitted、restricted 或 requiring re-instantiation。

## Graph model：nodes、edges 与 DAG

CUDA graph 是有向无环图（directed acyclic graph，DAG）。Nodes 表示 kernel、memory copy、memory set、host function、event record/wait、child graph 等 operations。Edge `A -> B` 表示 B 按该 edge 的 documented semantics 依赖 A。Acyclic 表示沿 directed dependencies 前进永远不能回到同一 node。

Edges 约束 execution；source layout 与 node numbering 不约束。一个 node 的全部 dependencies 完成后，CUDA system 可以 schedule 它。两个 nodes 之间若没有 path，则 graph 不 ordering 它们。这表示 eligibility，不是它们 concurrent execution 的证据。

Review 时记录每个 node 的 type、parameters、external resources、incoming/outgoing edges 与 completion consumer。Instantiation 前应拒绝 cycle、缺失的 producer-to-consumer edge，或让原本 independent work 意外 serializing 的 edge。

## Explicit Graph API：直接构造 DAG

Explicit Graph API 创建 `cudaGraph_t`、加入 typed nodes，并在 node creation 时或通过 edge APIs 提供 dependencies。Program 保留 node handles，因而可在 API restrictions 内 inspect 或 update selected node parameters。当 application 拥有 graph structure 并能直接描述 node parameters 时，适合使用该机制。

Graph definition 不是 graph execution。加入 kernel node 不会 launch kernel；加入 memory node 不会移动 bytes；valid DAG 也不能证明 external pointers 或 callback data 会存活到 future launch 完成。

## Stream capture：从 stream-based work 导出 graph

Stream capture 用 `cudaStreamBeginCapture()`/`cudaStreamEndCapture()` 包围现有 stream-based sequence。Stream 处于 capture mode 时，提交给它的 supported operations 会追加到 capture graph，而不会 enqueue for execution。Capture 成功结束后返回 `cudaGraph_t` template。

Capture 是不同 construction mechanism，不是第二种 execution mode。它从 stream order 与 captured event dependencies 导出 nodes/edges。Explicit Graph API 与 capture 可以产生等价 DAG，但 authoring、error 与 ownership boundaries 不同。

## Capture prohibitions、invalidation 与 rejoin

开始 capture 的 stream 是 **origin stream**，并且必须在同一 stream 结束 capture。Captured event 可以通过 event wait 把 work fork 到另一个 stream。每个加入同一 capture graph 的 additional stream 都必须在 `cudaStreamEndCapture()` 前 join back to origin stream；否则 overall capture 失败。

Active capture 期间，query/synchronize captured stream、captured event，或包含该 capture 的 broader device/context handle 都是 invalid。在 documented capture context 中，prohibited legacy-stream interaction、`cudaMemcpy()` 等 synchronous API、尝试 merge separate capture graphs，以及 unsupported capture operation 都不能隐藏在 captured library call 内。

Invalid operation 会 invalidate associated capture graph。随后继续使用其 capturing streams/captured events 都是 invalid，直到 program 调用 `cudaStreamEndCapture()` 离开 capture mode。该 end call 会报告 error 并返回 null graph。因此 error handling 必须保留 origin stream，完成 failed capture boundary，丢弃 null result，并禁止 instantiation。

## Definition、instantiation 与 repeated launch

Graph work submission 有三个不同阶段：

1. **Definition：** 使用 explicit API 或 stream capture 创建 graph template。
2. **Instantiation：** 用 `cudaGraphInstantiate()` validate/snapshot template，得到 `cudaGraphExec_t` executable graph。
3. **Execution：** 按 application contract 允许的次数，用 `cudaGraphLaunch(graphExec, stream)` 提交 executable。

Instantiation 不是 launch；launch 对 host 异步。Repeated launch 复用 instantiated structure，不重新执行 capture，也不表示 previous launches 已完成。每个 API result 仍需 immediate error check；asynchronous work 仍需 declared completion observation。

## Resource lifetimes 与 explicit completion

Graph/executable handles 不会让 external resources 永久存活。Node 使用的 device allocations、host buffers、kernel/module state、event/semaphore objects、host-function callback data 与 pointer pointees，都必须按 selected node API 的 lifetime/accessibility contract 存活到每个可能使用它们的 launch 完成。Capture-only objects 也必须保持 valid，直到 capture 成功结束，或在 invalidation 后完成 unwind。

把每次 `cudaGraphLaunch` 视为 submitted stream work。在 launch 后 record event，或在 intended host boundary synchronize containing stream。只有该 completion 后，host 才可消费 copied-back data、释放 launch 使用的 resources，或按 chosen teardown contract destroy executable。Destroy graph template/executable handle 不能替代 external resource use completion proof。

使用 lifecycle ledger：

| object | created/selected | last graph use | completion boundary | release action |
| --- | --- | --- | --- | --- |
| `cudaGraph_t` template | explicit construction 或 successful capture | instantiation 或 later update source | host API completion | 不再需要时 `cudaGraphDestroy` |
| `cudaGraphExec_t` | successful instantiation | final graph launch | final launch 的 explicit stream/event completion | `cudaGraphExecDestroy` |
| external storage/handles | allocation 或 creation | final relevant launch 中的 last node use | 覆盖该 node 的 completion | matching free/destroy API |

## Update 有边界

Executable graph 是 snapshot，不是 freely mutable workflow。Whole-graph `cudaGraphExecUpdate()` 受 topology identity、dependency ordering、node type、context 与 parameter restrictions 限制。Individual executable-node update APIs 只支持 documented node types 与 parameter changes。Updates 作用于 subsequent launches，不作用于 already-submitted launches。

Apply 前先分类每个 requested change。Compatible parameter update 可以使用 documented update API；topology change、node-type change 或 rejected update 需要创建 new valid graph 并 re-instantiate。始终检查 returned update status；不得假设 attempted update 成功，也不得静默扩大其 contract。

Reusable executable 或 successful update 都不是 performance result。Launch overhead、end-to-end time 与任何 concurrency claim 都需要 separate measurement。
