[异步复制（asynchronous copy，TERM-108）](/glossary/#term-108)改变 copy 的提交与完成方式，却不会消除此前建立的 shared-memory ownership 与 synchronization proof。[流水线（pipeline，TERM-109）](/glossary/#term-109)加入一个由有限个可复用[流水线阶段（pipeline stage，TERM-110）](/glossary/#term-110)组成的 FIFO。正确性仍从简单 synchronous phase order 开始，再逐项替换边界。

## 学完本单元，你应该能

- 先写出 portable synchronous `global load -> shared store -> barrier -> use -> barrier before reuse` baseline。
- 把一个 logical batch 映射到 `producer_acquire -> cuda::memcpy_async -> producer_commit -> consumer_wait -> use -> consumer_release`。
- 写清每个 producer/consumer participant，包括 bounds-invalid 与 early-exit behavior。
- 区分 CC 7.0+ API availability 和 CC 8.0+ hardware-accelerated global-to-shared path 及其 alignment/type constraints。
- 拒绝从 source code 本身推断特定 hardware instruction 或 copy/compute overlap。

按顺序先完成 [M03：共享内存分块](/memory/shared-memory-tiling/)、[M05：同步作用域与内存可见性](/memory/synchronization-scopes/)和 [M08：用事件表达依赖并测量设备时间](/memory/event-dependencies-timing/)。M03 提供 load/use/reuse phase proof；M05 提供 participant/visibility reasoning；M08 防止把 asynchronous submission boundary 误当成 completion 或 timing evidence。

## 先建立 portable synchronous baseline

从一个 shared buffer 和明确的 phase ledger 开始：

```cpp
for (int batch = 0; batch < batch_count; ++batch) {
  shared[threadIdx.x] = load_valid ? global[input_index] : neutral;
  __syncthreads();

  if (output_valid) {
    consume(shared);
  }

  __syncthreads();
}
```

First barrier ordering 所有 participating loads 与 cross-thread use；second barrier ordering 所有 uses 与下一轮对同一 storage 的 overwrite。Bounds 选择 value 或 output action，不能悄悄把 thread 移出 block-wide barrier。这份 baseline 对 Stable Curriculum 的 C++17 lanes 可移植；当 asynchronous path 不可用、不满足条件或没有充分理由时，它仍是 fallback。

不要优化一份尚未证明的 protocol。先记录 source range、destination range、每个 shared slot 的 assigned writer、每个 slot 的 readers、neutral/validity rule、participants 与 next-overwrite point。

## 替换 copy，不替换 proof

使用 pipeline completion mechanism 时，一个 batch 的抽象顺序是：

```text wrap
acquire stage -> submit cuda::memcpy_async -> commit stage
              -> wait for that stage -> use completed data -> release stage
```

`producer_acquire()` 预留 pipeline head；acquire 后提交的 copies 属于该 stage。`producer_commit()` 推进 head，并把 batch 发布到 pipeline sequence。`consumer_wait()` 按 pipeline contract 等待 oldest committed stage 完成；只有随后 consumer 才能读取该 stage。`consumer_release()` 把 oldest stage 交回 pipeline，供之后 acquire/reuse。

“Asynchronous” 不允许提前访问。Documented completion boundary 之前读取或写入 destination，或修改 copy 仍需要的 source data，都会形成 race。若某些 threads 消费由其他 threads 复制的 shared values，设计还必须包含让所有 peer-produced values 可安全使用所需的 group synchronization；不能把 thread-local completion wait 扩大解释成 block-wide guarantee。

## Stage lifecycle 与 reuse

为每个 logical batch 保留 stage ledger：

| state | owner action | permitted shared-buffer action |
| --- | --- | --- |
| available | producer 完成 `producer_acquire()` | producer 可向 acquired stage 提交 copies |
| committed | producer 完成 `producer_commit()` | stage pending；consumer 尚不可读取 |
| ready | consumer 完成相应 `consumer_wait()` 和 required group synchronization | declared consumers 可读取 stage |
| released | 所有 declared consumers 完成读取，并按要求 collectively 完成 `consumer_release()` | stage 可被后续 batch acquire/overwrite |

多个 stages 把正在填充的 stage 与正在消费的 stage 分开。它们创造 overlap opportunity，却不证明 hardware 实际发生 overlap。Prologue、steady-state rotation 与 drain 必须保持同一 batch-to-stage mapping；最后几个 committed batches 仍需 wait、use 和 release。

**Use** 前完成 copy，防止读取 unfinished copy；**release/reuse** 前完成所有 declared reads，防止 later producer 覆盖仍 live 的 stage。这是两条不同 edges，正如 M03 的 first/second barrier 分别保护不同 hazard。

## 完整 participant 与 convergence contract

对于 shared block-scope pipeline，必须声明 unified/partitioned、stage count、producer set、consumer set 与每个 thread 的 fixed role。Producer operations 对 producer set collective；consumer operations 对 consumer set collective。每个 participant 都必须对每个 logical stage 执行相同的 required acquire/commit 或 wait/release sequence。Bounds-invalid participant 可以在 selected overload contract 下不提交 useful bytes，或采用 neutral/validity path，但不能直接从 collective sequence 中 return。若 participating thread 必须提前退出，应先遵循 documented `pipeline.quit()` contract。

相关 implementation path 上的 pipeline submission 还存在 warp entanglement。Converged threads 可以把 commit coalesce 成一个 actual batch；divergent commits 可能让 warp-shared actual sequence 的推进次数多于每个 thread 的 perceived sequence。之后的 wait 可能因此多等更晚的 batches。Commit operations 应保持 converged；若此前 control flow 已 divergence，应在 commit 前用正确 scoped `__syncwarp` reconverge。这是 convergence/performance contract，不能代替 pipeline 的完整 participant contract。

## Capability、alignment 与 type constraints

使用 `cuda::barrier` 或 `cuda::pipeline` 的 `cuda::memcpy_async` overloads 在 CC 7.0+ 可用；hardware-accelerated global-to-shared asynchronous copy path 要求 CC 8.0+。在 eligible CC 8.0-or-newer path 上，4、8 或 16-byte copy size 以及匹配的 source/destination alignment 可以启用 asynchronous instruction path；该 path 还要求 copied element type 为 trivially copyable。

`cuda::aligned_size_t<N>` 是 programmer-supplied proof，声明两个 pointers 都满足 alignment `N`，且 byte count 是 `N` 的倍数。错误 proof 会产生 undefined behavior。若没有 valid compile-time proof，implementation 可能执行 runtime alignment check 或使用 fallback。因此 API spelling、CC 8.0+ target 与看似 aligned 的 declaration 都不能单独证明 emitted instruction。

本 Learning Unit 只覆盖 portable baseline 与 `cuda::memcpy_async` 加 `cuda::pipeline` 的 staged path；architecture-specific bulk-copy systems 不在教学范围内。

## 证据边界

Source review 可以证明 participant sets、stage rotation、completion edges 与 declared alignment assumptions，却不能证明 compiler 发出了 hardware asynchronous-copy instruction。该 claim 需要 pinned build 与 artifact inspection。Source review 也不能证明 copy/compute overlap 或 speedup；这些 claim 需要带 Environment Manifest、correctness oracle、明确 timing boundaries 与 retained observations 的 Runtime-Verified measurement。
