<a class="locale-pair" data-locale-counterpart href="/en/memory/unified-memory-page-migration/" lang="en">Read the English counterpart</a>

统一内存（Unified Memory）让 CPU/GPU code 都能寻址托管内存（managed memory），但同一个 pointer 不等于同一 physical memory、zero movement 或免费的 concurrent sharing。页面迁移（page migration）只是 system 改变 locality 的一种可能方式。驻留位置（residency）、accessibility、migration、remote access 与 coherence 必须分开记录；其 behavior 取决于 operating system、driver、device 与 interconnect。

## 学完本单元，你应该能

- 说明 `cudaMallocManaged` allocation 的 owner、lifetime 与 access contract。
- 区分 legal accessibility 与 current/inferred residency。
- 用 conditional migration、remote-access 与 no-migration branches 跟踪 page access sequence。
- 建模 fault/data movement 的 possible cost，不填写虚构 duration 或 migration count。
- 把 `cudaMemAdvise`、prefetch 与 VIS08 视为 guidance/model，而不是 runtime placement proof。

## 先修关系

先完成 [M01：地址空间、所有权、作用域与生命周期](/memory/address-spaces/)，再完成 [M02：把合并访问理解为事务塑形](/memory/coalescing-transactions/)。M01 提供 allocation ownership、valid accessors、last use 与 matching release；M02 提供先固定 access set 再推理 movement 的纪律，但它的 32-byte transaction model 不能与 page-level placement 混为一谈。

M10 与 [M09：页锁定内存与传输重叠](/memory/pinned-memory-transfer-overlap/)相关，但 managed access 不是 M09 explicit-copy pipeline 的 implicit version。M10 询问 touched data 可以从哪里得到服务，以及 movement 可能付出什么成本；它不声明 migration 或 direct access 更快。

## Managed memory 是 allocation contract

`cudaMallocManaged` 创建由 Unified Memory system 管理的 allocation；所有 users 完成后用 `cudaFree` 释放。CPU/GPU code 可以在适用 system contract 下使用 managed pointer。Allocation 仍有单一 owner、有限 lifetime、data dependencies 与 synchronization requirements。

“两个 processor 都能访问”不表示 CPU/GPU 可以对这些 bytes 发生 race，不表示两者 access 同样 local，也不表示没有 transfer。Kernel launch 仍是 asynchronous，所以 host 在读取 GPU-produced values 前要建立 completion boundary，除非 documented concurrent-access/synchronization design 明确允许其他做法。Unified Memory 减少一部分 explicit copy bookkeeping，但不会删除 correctness bookkeeping。

## Accessibility 不是 residency

Accessibility 回答 processor 是否可以合法 address managed range；residency 描述 stated time 上 physical backing 在哪里 local。一个稳定 virtual address 可以对应 CPU-memory-resident pages、GPU-memory-resident pages，或依 system 而通过 coherent/remote mapping 访问的数据。

在 software-coherent full-support system 上，访问 local 于另一 processor 的 page 可能 fault 并触发 migration。在 hardware-coherent system 上，processor 可能无需移动 page 就 remote access。Limited-support system 可以在更粗的 execution boundaries 移动 managed data。这些是 conditional branches，不是每个 allocation 都依次经历的三阶段。

Source pointer 与 allocation API 建立 accessibility/ownership facts，但不会显示 execution 中每个 page 的 physical locality。

## 跟踪 access sequence，不写 universal migration story

从 symbolic pages 与 unknown residency state 开始。考虑以下 ordered workload：

```text
CPU writes pages A and B
completion/order edge
GPU reads B and C, then writes C
GPU completion edge
CPU reads C
```

对每次 access，记录 accessor、touched pages、required synchronization、prior known state 与 permitted system behaviors。在 software-coherent fault-and-migrate model 下，GPU access B 可能迁移 host-local page，之后 CPU read C 可能把 device-local page 迁回。在 hardware coherence 或 documented direct access 下，两次 access 都可能无需 migration 得到服务。在 limited model 下，movement 可能发生在 launch/synchronization，而不是每个 first GPU touch。

因此，只有 locality/capability premises 支持时，ledger 才写 “migration candidate”。它不能把 browser colored page 或 source access order 变成 recorded migration。

## 有条件地建模 page-migration cost

Page migration 发生时，其工作可以包括 fault detection/service、mapping/ownership updates、coherence actions 与 backing-data movement。Transfer granularity 可以大于触发 access 的少量 bytes，所以在 fault-and-migrate system 上交替由 CPU/GPU 写同一组 pages，可能造成 repeated movement 或 thrashing。

使用 symbolic cost decomposition：

```text
access episode = useful memory access
               + possible fault/coherence work
               + possible data movement
```

每个 “possible” term 都必须先取得 Environment Manifest 与 runtime evidence，之后才能成为 observation。Page size、migration granularity、remote-access policy、caching 与 interconnect 都会变化。M02 segment count 不能预测 page fault 或 migrated bytes。

## Prefetch 与 advice 不是 placement proof

`cudaMemPrefetchAsync` 使用 stream ordering 请求把 range 向 declared location prefetch。Consuming work 应位于该 operation 之后的同一 stream，或通过 documented event edge 连接。该 call 可以把工作提前，也可能在 suitable system 上减少 demand fault，但它有成本，而且不承诺 range 永久驻留在那里。

`cudaMemAdvise` 传达 preferred location、read-mostly behavior、expected access 等 usage hints。Hint 可能帮助或损害真实 pattern/platform。Advice/prefetch 都不能替代 synchronization、output verification，或对 actual fault、movement、residency behavior 的 measurement。

On-demand、advised 与 prefetched modes 必须共用一个 correctness oracle。只有记录 selected Toolkit API contract、destination semantics、capability attributes 与 run evidence 后才能比较。

## 必须记录适用的 system model

Current owner documentation 区分 explicit managed allocation full support、all-allocation software-coherent full support、all-allocation hardware-coherent full support 与 limited support。Native Linux 是本站唯一受支持环境（Supported Environment），但 Native Linux systems 仍会因 kernel、driver、GPU 与 interconnect 而不同。

至少记录 selected device，以及 `cudaDevAttrConcurrentManagedAccess`、`cudaDevAttrPageableMemoryAccess`、`cudaDevAttrPageableMemoryAccessUsesHostPageTables` 的结果。Host-direct-access claim 依赖时，还要记录 `cudaDevAttrDirectManagedMemAccessFromHost`。同时加入 operating-system/kernel versions、driver、Toolkit Lane、CPU-GPU topology、allocation API、access sequence 与 synchronization boundaries。

这些 facts 选择 permissible model，但不提供 migration timeline，也不保证 particular page 确实移动。

## 离开前检查

1. `cudaMallocManaged` 对 ownership、accessibility、lifetime 与 release 建立哪些事实？
2. 为什么一个 stable pointer 可以同时让 CPU/GPU access，却不能证明每个 page 驻留在哪里？
3. 哪些 system branches 可以用 migration、remote access 或 coarser movement 服务 cross-processor access？
4. Migration episode 可能包含哪些成本？为什么 M02 的 32-byte segment model 不能预测这些成本？
5. 为什么 prefetch、advice 与 VIS08 都不能证明 page 确实迁移或持续驻留？
