页锁定主机内存（page-locked host memory）是本单元中真正 asynchronous CPU-GPU copy 所需的 CPU-side storage contract。传输重叠（transfer overlap）是另一类 execution observation：pinned buffer、asynchronous API、independent stream work 与复制引擎（copy engine）capability 可以让 overlap eligible，但只有记录下来的 device timeline 才能说明 intervals 确实发生重叠。

## 学完本单元，你应该能

- 为每种 page-locked allocation 或 registration API 匹配正确的 release action 与 lifetime。
- 说明为什么 `cudaMemcpyAsync` 加 pageable host memory 不是 overlap contract。
- 在询问是否更快之前，画出 copy、kernel 与 buffer reuse dependencies 都正确的 chunk pipeline。
- 分开 source-level eligibility、查询得到的 copy/compute capability 与 observed transfer overlap。
- 即使所选 hardware 不能 overlap copy/compute，也保留 serialized correctness baseline。

## 页锁定主机内存

`cudaMallocHost` 与 `cudaHostAlloc` 创建 page-locked host allocation，并使用 `cudaFreeHost` 释放。`cudaHostRegister` 对 eligible existing host range 加 page lock；匹配动作是 `cudaHostUnregister`，之后才由原 allocator 在 allocation 不再需要时释放。两条路径都能提供 pinned transfer buffer，但 allocation 与 registration 的 ownership 不同。

Pinning 阻止 operating system 在 CUDA 使用覆盖范围时把对应 physical storage 换出或移动。这让 direct asynchronous CPU-GPU transfer 成为可能，但会占用有限 host resource。应在 steady-state pipeline 前分配经过复核的 working set，让每个 range 保持有效直到最后一个 asynchronous user 完成，并且只释放一次。把 page-locked allocation 插在本来 independent 的 work 之间还可能引入 synchronization，所以它不应位于 hot enqueue sequence 中。

Pinned 不等于 device-resident，不等于已经为每种 intended access 完成 mapping，也不等于已经 in flight。它是 host-memory property 和这条 transfer path 的先决条件，不是 overlap result。

## Asynchronous copy contract

`cudaMemcpyAsync` 把 transfer 加入 stream，并在 transfer 不一定完成时返回。对涉及 CPU memory 的 copy，current Programming Guide 要求 host buffer page-locked 才具有 asynchronous behavior。Pageable host buffer 仍可能得到正确 copy，但本单元把这条路径判为不具备 overlap claim 资格，因为它可能退化为 synchronous staging behavior。

因此每个 asynchronous copy 都带五项记录：source/destination ranges、byte count 与 direction、owning stream、completion boundary，以及两个 buffer 最早合法 reuse/release 的时点。API submission 成功不证明任何 buffer 已可供 host reuse。必须用 same-stream order 或 M08 event edge 连接 producer 与 consumer；host 还必须等待能够保护 verification 与 cleanup 的 completion。

## Overlap eligibility 不是 observation

只有所有 ordering/resource gates 都允许时，copy 与 kernel intervals 才具备 overlap eligibility：

1. 两项 operation 之间没有会把它们 serialization 的 required edge。
2. CPU-side transfer ranges 已 page-locked，并在使用期间保持有效。
3. Copies/kernels 位于 named streams，且所有真实 data dependency 都已表达。
4. 所选 device 报告 compatible asynchronous copy/compute capability。
5. Allocation、default-stream relationship、host wait 或其他 synchronization point 没有关闭 intended window。
6. Runtime 有足够 applicable resources 调度这些 operations。

通过这些 gates 只证明 submitted graph 在 capable system 上允许 overlap；它不证明 transfer 使用了 copy engine，不证明 kernel 留出了所需资源，也不证明 execution intervals 相交。来自 exact run 的 profiler 或等价 device timeline 才是 observation boundary。

## 先构建正确的 chunk pipeline

在不改变 logical result 的前提下，把一个 workload 划分成 chunks。每个 chunk `i` 都保留以下 data path：

```text
H2D(i) -> kernel(i) -> D2H(i) -> output-ready(i)
```

把完整 chunk chains 放入有界数量的 named non-default streams。Different chunks 可以同时变得 eligible，而每个 chunk 内部仍保持 order。若复用 ring slot，必须从该 slot 上一次的 `output-ready` event 添加 dependency，连接到下一次会 overwrite 它的 host fill 或 transfer。Host 不能在 H2D copy 完成前修改 input chunk，也不能在 D2H copy 完成前读取 output chunk。

Serialized path 与 pipeline 必须使用相同 logical input、kernel work、output oracle 和 error checks。只有每个 element 恰好覆盖一次、tail size 有边界且 buffer ownership 无歧义时，chunking 才正确。更小 chunk 可以暴露更多 pipeline stages，也会改变 launch/transfer overhead；graph 不能推出 optimal chunk count。

## Copy engine 是带 capability 的 resource

Copy engine 是一种 hardware resource，可以独立于 SM compute 执行 data movement。Asynchronous-engine 等 device properties 描述所选 device/path 的可用 capability。Engine 的数量和可用 direction 会变化，current owner documentation 也不保证每个 `cudaMemcpy*` call 都一定使用 copy engine。

在 Environment Manifest 中记录 exact device query 与 returned value。把它视为“可能发生什么”的 gate，不是“实际发生什么”的 timestamped account。即使 device 有 eligible engines，某个 workload 仍可能因 dependency、transfer direction、resource contention、staging 或 runtime decision 而 serialization。

## Hardware gate：correctness 先于 overlap

Baseline correctness 以 Native Linux 与基础 GPU 能力层级（Baseline GPU Capability Tier）为目标，也就是 compute capability 7.5 或更新、bounded workload 低于 8 GB。即使 device 把 copies/kernels serialization，也仍可满足 correctness contract。Output oracle、API error checks、event dependencies 与 release order 都必须在不假设 overlap 的条件下通过。

Overlap observation 还有额外 gate：page-locked host buffers、让 intended copy/kernel 保持 unordered 的 graph、所选 device/path 的 compatible asynchronous copy/compute capability，以及来自 exact run 的 timeline evidence。任一 gate 缺失时，只报告正确的 serialized result，并让 overlap 保持 unobserved。
