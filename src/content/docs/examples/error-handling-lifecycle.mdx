EX04 是一个独立、原创的错误处理生命周期可运行示例（Runnable Example）。同一份 C++17 项目把提交后的立即检查（immediate-after-submission）、同步时的延迟检查（deferred-at-synchronization）、纯 host 逻辑验证（host verification）和修复后的索引放在四个单场景进程中。网站不会执行 CUDA。

## 用途

先完成 [F05：分开立即 launch error 与延迟 execution error](/foundations/asynchronous-errors/)。EX04 把 F05 的异步错误时间线变成唯一可执行实现；[F03](/foundations/multidimensional-indexing/)提供二维 row-major 索引合同，[F04](/foundations/host-device-lifecycle/)提供 allocation、submission、synchronization 与 cleanup 的顺序，[LAB03](/labs/break-and-repair-indexing/)再引导学习者运行故障与修复场景。

本项目刻意不把所有故障塞进一个长生命周期。每次调用只运行一个场景，这样前一次异步错误不会污染下一次 `cudaPeekAtLastError`，而且报告潜在 fatal device fault 后不再尝试复用 CUDA context。

`project.json` 是机器可读合同，`README.md` 可脱离网站说明构建、运行与证据边界。`src/`、`include/` 和 `tests/` 是唯一实现来源。两个语言页面都按 manifest 顺序各显示一次 `error-lifecycle`、`indexing-kernels` 和 `host-verification`。项目和页面均为原创；项目源码使用 Apache-2.0。

## 场景合同

| CLI 场景 | 刻意设置 | 首个预期分类 | 安全边界 |
| --- | --- | --- | --- |
| `launch-config` | 使用超过 block thread 上限的 launch configuration | `immediate-after-submission` | launch 被拒绝后读取、清除 last-error state，再显式同步 |
| `deferred-access` | 合法 launch 内故意解引用无效 device address | `deferred-at-synchronization` | 不分配 device buffer；同步报告故障后立即结束进程 |
| `indexing-defect` | 把 `x,y` 以 column-major permutation 写入同一 allocation | `host-verification` | 所有位置都在 35 个元素内；不借助非法访问制造 mismatch |
| `repaired-indexing` | 使用声明的 `y * width + x` row-major map | `none` | 同步成功后与纯 host reference 精确比较 |

表中的分类是验收方向，不是本站观察到的 runtime output。程序检查成功或失败状态，而不把某个具体 `cudaError_t` 数值写成跨环境保证。

## 错误生命周期

以下范围保存四个场景的 host-side observation boundary 和 cleanup 决策：

<CanonicalCode exampleId="EX04" range="error-lifecycle" />

`launch-config` 在 triple-chevron submission 后立即调用 `cudaPeekAtLastError`。该 API 读取调用线程可见的 last-error state，但不清除它；随后 `cudaGetLastError` 取回并清除同一 state，再次 peek 应看到已清除状态。最后的 `cudaDeviceSynchronize` 仍然明确存在，因此“立即检查”和“完成边界”没有被混为一谈。

`deferred-access` 的 launch geometry 本身合法。代码先执行不清除 state 的 immediate peek，然后调用 `cudaDeviceSynchronize` 等待此前提交的工作；故意的 device access 以该 synchronization call 为预期报告点。由于这类执行故障可能让当前 CUDA context 不再适合继续工作，函数在记录返回的 status 后直接结束，不调用 `cudaFree`、reset 或下一次 kernel。

两个索引场景只在 `cudaMalloc`、launch immediate check、显式同步和 D2H copy 全部成功后执行 host verification。它们也只在成功同步、成功回传之后调用 `cudaFree`；任何 CUDA failure 都让进程退出并把 allocation 留给进程终止回收，而不是冒险沿潜在损坏的 context 执行 cleanup。

## 索引 kernels

同一 device source 包含 launch-configuration probe、延迟无效访问，以及成对的错误/修复索引 kernel：

<CanonicalCode exampleId="EX04" range="indexing-kernels" />

`indexing_defect` 不是越界 kernel。对 `width=7,height=5` 的每个有效 `(x,y)`，`x * height + y` 都落在 `[0,35)`，并且构成完整 permutation；问题在于它违反应用声明的 x-fastest row-major layout。这样，场景只测试“逻辑 mapping 与 reference 不一致”，不会让一次 illegal memory access 同时污染 CUDA error state。

`repaired_indexing` 在同样的 coordinates、bounds、grid、block 和 allocation 上只替换为 `y * width + x`。控制变量使 host mismatch 能归因于 mapping repair，而不是问题大小或 launch geometry 变化。

## Host 验证边界

纯 host C++17 header 定义 scenario parser、稳定的 stage label、首个 failure stage 分类、overflow-safe element count、两种 2D mapping、确定性 reference value 和 exact verifier：

<CanonicalCode exampleId="EX04" range="host-verification" />

`try_element_count` 在乘法前检查零 extent 与 `std::size_t` overflow。两种 index function 先验证 extent product，再验证每个 coordinate，失败时不改写 caller 提供的 index。host test 遍历 `7 x 5` 范围，模拟 in-bounds defect 与 repair，并确认 mismatch 第一次出现在确定位置。

`make host-test` 不包含 CUDA header、`__host__`、`__device__` 或 GPU dependency。它能验证 parsing、arithmetic、reference 和 classification 合同，但不能证明 CUDA source 已编译，也不能证明 device 执行按预期阶段报告错误。

## 构建合同

在原生 Linux 的项目目录中按固定顺序执行：

```sh
make preprocess DIALECT=c++17
make compile DIALECT=c++17
make link DIALECT=c++17
make inspect DIALECT=c++17
make host-test DIALECT=c++17
```

前四步需要所选 CUDA Toolkit，host-test 只需要 x86-64 CPU 上的 host C++17 compiler。CUDA stages 产生 `build/error_handling_lifecycle.ii`、`build/error_handling_lifecycle.o` 和 `build/ex04-error-handling-lifecycle`。Inspect 使用 `cuobjdump` 确认 native `sm_75` cubin 与从 `compute_75` 生成的 forward-compatible PTX。

`scripts/compile-check.sh c++17 ex04 <result-dir>` 依次运行 clean、preprocess、compile、link、inspect 和 host-test，并保存日志与 inspection artifacts。它绝不运行 `build/ex04-error-handling-lifecycle`；因此成功的构建流程也不会产生 immediate、deferred 或 host-verification runtime observation。

## 预期观察，不是运行记录

以下四项来自 manifest 的预先声明，不是已观察 output：

1. `launch-config` 应在提交后的立即检查暴露 launch-configuration defect；`cudaPeekAtLastError` 应只观察，`cudaGetLastError` 应取回并清除同一 launch state，然后代码仍显式同步。
2. `deferred-access` 的 immediate check 应没有 launch error，故意的 invalid device access 应只在 `cudaDeviceSynchronize` 建立 completion boundary 时暴露。
3. `indexing-defect` 应在没有 illegal memory access 的情况下完成 device work，但因为 in-bounds column-major permutation 与 row-major reference 不一致而无法通过 deterministic host verification。
4. `repaired-indexing` 应完成显式同步，并匹配经过 overflow 检查的 row-major host reference。

四项都仍需符合 hardware gate、Environment Manifest 和 acceptance criteria 的 GPU 记录验证。当前 observation 列表为空，也没有预设具体错误枚举、输出文本或性能数字。
