EX17 是一个独立、原创的 C++17 CUB Device Reduction 与 Scan 可运行示例（Runnable Example）。它调用 production `cub::DeviceReduce::Sum`、`cub::DeviceScan::InclusiveSum` 和 `cub::DeviceScan::ExclusiveSum`，但不复制或改编 CUB implementation。项目只产生 correctness verdict，没有 timer，也不发布 measured performance result。

## 用途

唯一严格先修是 [L03：用 CUB Device Primitives 完成归约与扫描](/libraries/cub-device-primitives/)。L03 已建立 focused headers、operation semantics、传统 temporary-storage protocol、stream order、lifetime 与 version-matrix contract；本页把这些合同放进一个可独立构建和运行的 project。

[A02 多阶段归约](/algorithms/multi-stage-reduction/)、[A03 Inclusive 与 Exclusive Scan](/algorithms/inclusive-exclusive-scan/)、[Q02 浮点顺序和可复现性](/correctness/floating-point-order-reproducibility/)、[L01 选择库、原语、DSL 或自定义内核](/libraries/library-primitive-dsl-custom-kernel/)、[EX11 custom reduction](/examples/multi-stage-reduction/)、[EX12 custom scan](/examples/inclusive-exclusive-scan/)和 [LAB11 custom/CUB comparison](/labs/compare-custom-reduction-with-cub/)都是 related resources，不增加 prerequisite edge。

## CPU reference 与两个正确性合同

同一个 host-only header 同时定义 reduction 和 scan oracle，不包含 CUDA 或 CUB header：

<CanonicalCode exampleId="EX17" range="cpu-reference" />

**Reduction contract：** 恰好 4,099 个 stored `float` 使用与 EX11 byte-for-byte compatible 的 deterministic generator。每项先由 `float` 表示，再按 input order 转为 `double` 并 serially accumulate。Device output 是一个 `float`；验收规则固定为 `absolute_error <= 1.0e-4 + 2.0e-5 * abs(cpu_reference)`。Parallel reduction 可以改变加法结合顺序，因此 EX17 不要求等于 serial left fold 的 bit pattern，也不把 tolerance pass 写成 bitwise reproducibility。

**Scan contract：** Public reference 最多接受 4,099 个 `std::uint32_t`，并在写 output 前拒绝任何大于 7 的 input。于是所有 prefix 都不超过 `4,099 * 7 = 28,693`，不会发生 `uint32_t` overflow。固定 input 重复 1 到 7，其 total 恰为 16,390。Inclusive 与 exclusive references 分别独立 serially compute；两个完整 device arrays 必须 exact match，并满足 recurrence、`exclusive[0] = 0` 和两条 last-total identity。

## DeviceReduce path

Reduction range 只维护传统 `DeviceReduce::Sum` public API 的 query/allocate/execute plumbing：

<CanonicalCode exampleId="EX17" range="device-reduce" />

`TemporaryStorage::bytes` 从 0 开始。Query 用 `nullptr`、相同 input/output pointer types、`int item_count` 与 explicit stream 调用 `Sum`，然后分配该次 query 返回的 bytes。Execution 在同一 current device 上把 allocation 和同一个 byte count 传回相同 overload。源文件还静态证明 4,099 能放进 legacy API 的 `int` extent。

GPU result 只与前述独立 `double` oracle 比较。调用 production primitive 不会让 serial order 成为 device order，也不会自动建立跨 GPU bitwise equality。

## DeviceScan paths

Scan range 对 inclusive 与 exclusive operation 分别维护 storage；一个 query 的结果不会复用为另一个 primitive 的 capacity：

<CanonicalCode exampleId="EX17" range="device-scan" />

`InclusiveSum` 和 `ExclusiveSum` 都先以 null storage 查询，再各自执行一次 allocation 和 execution。它们共享同一个 4,099-element input 和 explicit stream，但输出与 scratch allocations 相互独立。Completion 后，程序分别 exact-compare 两个 arrays，再检查每个相邻 prefix、inclusive/exclusive relation 与 16,390 last total；一项失败就使 process 返回失败。

## Canonical headers、temporary storage、stream 与 lifetime

CUDA source 的 CUB imports 恰好是 focused public headers `<cub/device/device_reduce.cuh>`、`<cub/device/device_scan.cuh>` 与 version gate 所需的 `<cub/version.cuh>`，没有用 aggregate `<cub/cub.cuh>` 隐藏 dependency，也没有引用 CUB internal symbol。本页只通过 `CanonicalCode` 渲染 project manifest 声明的三个 ranges，不维护第二份 CUDA/C++ code fence。

三项 primitive 都遵循同一个 legacy two-phase protocol：以 null storage 和归零 byte count 查询，在同一 current device 分配至少该 capacity，再以相同 API、template/argument types、4,099-item shape 和 stream execute。三个 queried values 分别属于 reduction、inclusive scan 与 exclusive scan；它们不是跨 version、device 或 operation 的常量，也不是 memory traffic measurement。

`main` 只创建一个 `cudaStreamNonBlocking` stream。六次 CUB calls 和五次 checked `cudaMemcpyAsync` calls 都接收这一个 handle；五次 copy 是两个 H2D inputs 和三个 D2H outputs。三个 output copies 之后只有一次 checked `cudaStreamSynchronize(stream)`，这是 host validation 前唯一的 completion boundary。Input、output 与三个 scratch allocations 都存活越过该 boundary，随后才被释放；所有 CUDA/CUB return values、free 和 stream destruction 也被检查。Submission success 本身不是 completion。

## Build、host test 与运行命令

Host test 不需要 CUDA headers、CUDA runtime 或 GPU：

```sh
make host-test DIALECT=c++17
```

它检查 4,099-float fixture、`double` oracle、absolute/relative tolerance boundaries、bounded scan rejection、两个独立 scan references、exact comparator、recurrences 与 last totals。`host-reference: pass` 只建立 host contract behavior，不建立 CUDA compilation 或 GPU execution evidence。

以 11.8 bundled profile 为例，direct staged build 是：

```sh
make preprocess DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make compile DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make link DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
make inspect DIALECT=c++17 COMPONENT_MODE=bundled EXPECTED_CUB_VERSION=101501
```

Profile wrapper 会依次 clean、preprocess、compile、link、inspect 和 host-test，但不会执行 CUDA binary：

```sh
scripts/compile-check.sh c++17 cuda-11-8-bundled-cub-1-15-1 artifacts/ex17-11-8
CCCL_ROOT=/path/to/cccl scripts/compile-check.sh c++17 cuda-12-9-selected-cccl-3-4-2 artifacts/ex17-12-9-selected
```

只有满足 runtime gate 后才运行：

```sh
./build/ex17-cub-device-reduction-scan
```

Build 产生 preprocessed source、object 和 executable；inspection 要求 native `sm_75` cubin 与从 `compute_75` 生成的 PTX。Binary 会打印 selected CUB macro 和五个 correctness verdict，但本页没有保存任何实际 stdout 或 exit status。

Build contract 是 x86-64 host、C++17 和 selected Toolkit/component profile。Runtime 只属于 Native Linux Supported Environment，要求恰好一张 compute capability 7.5 或更新的 CUDA GPU。Pinned image、package、tag、include root 和 compiler target 都只是 acceptance coordinates，不是 build record。

五个固定 device allocations 是 4,099-float reduction input 的 16,396 bytes、一个 4-byte reduction output，以及三个各 16,396-byte 的 scan input/inclusive/exclusive arrays，合计 **65,588 bytes**。实际 problem memory 是 `65,588 + T_reduce + T_inclusive + T_exclusive`，其中三个 `T` 必须由当前 device 上的 selected profile 和对应 primitive 分别查询。

Frontmatter 的 `maximumProblemMemoryBytes: 8000000000` 是 Baseline GPU Capability Tier 的十进制 8,000,000,000-byte upper gate，不是假定 scratch 为零，也不是对实际 queried capacity 的预填值。三项 query、所有 allocations 与总和都必须成功且不超过该 gate；否则该环境不合格。Static bytes 和 temporary-storage capacity 都不能当作 observed traffic 或 performance result。

## 编译与运行证据边界

Compilation 与 runtime 是独立 axes。EX17 的 compilation array 为空，所以五个 profiles 都没有 Compile-Checked status。Runtime Evidence Status 是 **Pending Hardware Verification**，`recordedObservations` 也为空；本站没有在 Reference Environment 中执行该 binary。

Canonical source 存在、host test 通过、owner API/test 存在、version/package/manifest coordinate 已核对，或某个 learner local build 成功，都不会自动填充这两个 evidence axes。本页没有 recorded CUB macro、scratch bytes、device output、bit pattern、error、kernel count、timing、traffic、speedup 或 winner。未来记录必须绑定完整 Environment Manifest、exact profile/acquisition/include trace、source and binary hashes、commands、raw output、exit status 与 correctness verdict，审核后才能改变 Evidence Status。

## 预期观察，不是记录结果

1. `DeviceReduce::Sum` 应在恰好 4,099 个与 EX11 compatible 的 `float` input 上，通过相对于独立 `double` CPU reference 的预声明 absolute-plus-relative comparator。
2. `DeviceScan::InclusiveSum` 和 `DeviceScan::ExclusiveSum` 应分别 exact match 独立计算的 `uint32` CPU references，并通过全部 recurrence 和 last-total invariants。
3. Selected `CUB_VERSION` 应在任何 executable link 之前等于该 profile 的 expected macro；不相等或无法唯一解析 header 时 build 应失败。

这三项来自 canonical manifest，是 acceptance directions，不是本站已观察的 build 或 runtime output。
