## 独立 CPU 参考实现

<CanonicalCode exampleId="EX21" range="cpu-reference" />

输入为 `a[i]=(i % 37)*0.25` 和 `b[i]=-(i % 19)*0.5`。CPU 参考实现（CPU reference）读取实际存入的 `ctypes.c_float` 输入，再用 Python float 相加。这些小二进制分数及其和可由 float32 精确表示，因此要求**每个**输出有限且精确相等。这是本组数据的规则，不是通用浮点政策。

独立字面值检查包括 `i=0 -> 0`、`19 -> 4.75`、`37 -> -9`、`256 -> 4`、`1002 -> -6.25`。它们是推导预期，不是 GPU 终端记录。主机测试覆盖长度 1、255、256、257、1003，非法计数和长度，非有限值，不同位置损坏，以及不匹配计数。主机测试通过只验证 CPU 逻辑。

## Python 生命周期

<CanonicalCode exampleId="EX21" range="python-lifecycle" />

运行路径选择可见设备 0，调用 `dev.set_current()`，创建自己拥有的 nonblocking 流（stream）。三个设备 Buffer 与三个页锁定主机 Buffer 的字节范围相同。只有主机页锁定句柄用于 ctypes 视图；视图借用存储，不会持有 Buffer。两个输入上传和一次 NaN 输出哨兵上传先于核函数，因此漏写不能因回收内存碰巧含正确值而通过。D2H 显式指定页锁定主机目标。

读取输出前 `stream.sync()` 必须成功。逐项检查有限性和相等，保留首个不匹配与总数。正常清理先停止使用视图，在同一流上关闭 Buffer，再经检查同步等待排队释放，最后关闭流。失败清理保留首个异常，另报次要错误/警告；stderr 可能含原生清理诊断。Kernel/ObjectCode 没有公开 close，Device 没有 close，不重置或销毁共享主上下文（Primary Context）。

每次显式清理动作通过 `cleanup_step` 同时捕获 Python `sys.stderr` 与原生 FD 2，并在 finally 中恢复两者。显式放弃 Kernel/ObjectCode 引用也在其中，不虚构 close 调用。异常及捕获/回放失败保留于 `cleanupErrors`；`cleanupWarnings` 保留全部非空捕获 stderr，包括警告、原生析构/回调输出及空白。即使之后同步成功，捕获输出也会保守地阻止命令判为成功；先前操作的异常与阶段仍是主要诊断。

助手最多读取 16,384 字节诊断及一字节截断检测，每动作最多保留 16,384 个解码字符载荷，再加标签/截断说明；异常文本同样受限。这限制报告/回放载荷，不限制临时文件的磁盘占用。捕获准备失败本身使清理失败，但不能跳过释放尝试。捕获改变进程全局 stderr 与警告状态，因此属于单线程独立进程设施，不是并发库基础设施。

只有显式动作期间发出的诊断进入清理判定。因其他持有者延迟的析构、后续垃圾回收、捕获结束后刷出的原生输出，以及判定后解释器关闭时的析构均在范围外。干净的逐步捕获不能认证最终全部清理。JSON 之外仍要保留外部进程 stderr，并区分完成检查与释放尝试。

## 运行时编译与链接

<CanonicalCode exampleId="EX21" range="runtime-compile" />

Program 用虚拟 `compute_...` 目标和可重定位设备代码，将 C++17 源码编译为 PTX。`Linker(ptx, options=LinkerOptions(arch="sm_..."))` 再显式链接为 cubin。CLI 拒绝驱动链接器回退。检查阶段核对 PTX 入口/目标与 ELF cubin，再用所选 Toolkit 的 `cuobjdump --dump-sass` 检查核函数和实际目标。执行前不声明产物大小或 SASS 指令清单。

无需 GPU 的构建显式选 arch 75，不调用 Device、`set_current()`、`get_kernel()`、`launch()` 或 `cuInit`。**但它仍需要真实 `libcuda` 用户态库：** core 1.2.0 编译 PTX 时查询 `cuDriverGetVersion()`。Toolkit stub、假驱动或跳过阶段都不能替代它。不需要调用 NVCC。真正加载在之后的 `linked.get_kernel("ex21_vector_add")` 发生，不是在重建 cubin 对象时，也没有虚构的 `ObjectCode.load()` 步骤。

不初始化的合同还依赖关闭原生缓存：EX21 在 CUDA 导入前设置 `CUDA_CACHE_DISABLE=1`，使用 `ProgramOptions(no_cache=True)` / `LinkerOptions(no_cache=True)`，并记录 `cachePolicy: "disabled"`。[NVRTC 缓存合同](https://docs.nvidia.com/cuda/archive/13.3.1/nvrtc/index.html#caching-cuda-12-9)说明从 CUDA 12.9 起，默认缓存会在首次编译时调用 `cuInit()`。只省略 Device 构造不足以排除该路径。这是代码配置，不是原生导入/构建验证已经通过的声明。

## 核函数与参数合同

<CanonicalCode exampleId="EX21" range="kernel" />

三个指针参数传 core Buffer，最后的 32 位无符号计数传 `ctypes.c_uint32(n)`。普通 Python int 封送不是签名推断。每块 256 线程，用向上取整的网格覆盖输入，在所有数组访问前判断边界。`run` 接受 1 到 1000000 的整数；零不提交零网格。默认 n=1003 对应四块与 21 个尾部无效线程。

调用者设备载荷为 `12*n` 字节，默认 12036、最大 12 MB，另有等量页锁定主机载荷。CPU 参考存储、上下文/库/编译器分配及实际可用内存另计；静态字节数不是总内存占用，也不证明分配一定成功。这些规模位于基础 GPU 能力层级（Baseline GPU Capability Tier）的 8 GB 问题边界内。

## 准备与无需 GPU 的构建

先准备精确解释器、选定 NVIDIA Ubuntu deb 包、真实驱动用户态库和 cuobjdump，确保 `/usr/bin/dpkg-query` 与 `/var/lib/dpkg` 可用。配置将根目录固定为 `/usr/local/cuda-13.3`；`CUDA_PATH` 与可选的 `CUDA_HOME` 必须解析到该目录，不能将其重定位。这些变量不能替代已安装包/所属包检查。setup 创建 `.venv`，拒绝覆盖已有目录，并用 `--require-hashes --only-binary=:all:` 安装精确四 wheel 依赖闭包。它不安装原生 CUDA 包或系统解释器/驱动，也不支持 runfile 安装。

```sh
bash scripts/setup.sh
.venv/bin/python ex21.py host-test
.venv/bin/python ex21.py check-environment --phase native-packages
.venv/bin/python ex21.py check-environment
.venv/bin/python ex21.py build --arch 75
```

已准备的副本省略 setup。`native-packages` 阶段在 CUDA 导入前检查已安装包及磁盘文件所属包/哈希，不证明驱动用户态能够加载。默认 native 阶段另查规范导入、实际发现的库与 API，不初始化设备；其已加载 builtins 字段在编译和映射检查前仍为 null。构建设计为不需要 GPU 即可编译、链接和检查，但这些后续阶段仍待验证；仅包预检查通过不等于构建通过。缺失真实驱动用户态库或目标不受支持是失败，不是绕过检查的理由。

对于没有 CUDA 包的开发机，可在同一项目目录使用本地 CPython 3.10+ 解释器执行独立 CPU 逻辑检查：

```sh
python3 -I -S ex21.py host-test
```

该模式既不导入 CUDA，也不验证选定配置。它用标准库 ctypes 存储及独立字面值测试原创输入、参考与验收逻辑，不模拟设备 Buffer。独立的 `cleanupChecks` 检查诊断捕获、恢复、截断及首错保留，并故意将标记为预期的诊断回放到 stderr。主机测试验收看是否正确分类这些诊断，不要求 stderr 为空；`run` 的 CPU 正确性检查不执行这些诊断自测。解释器例外只适用于 `host-test`；setup、环境检查、构建与运行仍要求精确 CPython 3.14.7 配置。

构建默认输出到 `build/compile`：`report.json`、`ex21.ptx`、`ex21.cubin`、`nvrtc.log`、`link-info.log`、`link-error.log` 和 `sass.txt`。若已有结果文件则拒绝。再次尝试时选新的 `--output-dir`，如 `build/compile-second`，不要覆盖以前的判定。实际退出状态与 stderr 应与 JSON 报告一同保留。本页不声明构建已经成功。

## 单独满足门槛后运行

只有满足运行配置后才执行：

```sh
.venv/bin/python ex21.py run --size 1003
```

运行使用所选 GPU 精确且受支持的目标，沿同一 PTX/链接/检查路径重新构建，然后加载、启动、复制与验收。结果默认写入新的 `build/run`。若另查边界长度且不覆盖该报告：

```sh
.venv/bin/python ex21.py run --size 257 --output-dir build/run-257
```

**验收：** 每个输出有限，并与经过独立检查的 CPU 参考精确相等；检查和释放前，全部提交工作已完成；不能隐藏清理失败。保留源码/配置身份、实际设备和原生库记录、阶段诊断、产物哈希、全量判定、警告与退出状态。用真实观察填写空白环境清单（Environment Manifest）的外部副本，不用目标表代替。公开证据前审查并脱敏敏感路径。

## 诊断时不抹掉失败

报告区分配置、库发现、编译、链接、产物检查、分配、延迟查找、启动、复制、同步、正确性与清理。尝试启动但完成失败，不是执行成功。编译失败时空 `nvrtc.log` 可能与附在异常中的编译日志同时存在。分别保留首个异常和后续日志/清理错误。失败必须非零退出，不能退回去比较旧主机输出。

包失败发生在 `native-packages` 或 `native-package-files`，先于 `canonical-imports` 与 `native-libraries`。`inspect-nvrtc-builtins` 在编译后、保存 PTX/链接前执行；该阶段失败不能误标为完整构建成功，也不能仅凭产物文件缺失来归因。应使用报告阶段与真实诊断，不依赖假设的安装布局。

实际 JSON 合同中，`launchAttempted` 记录提交意图；提交前 `gpuExecuted` 变为 `null`，因为启动、复制或同步失败时无法确定完成。只有经检查的流同步成功后，它才变为 `true`；之后正确性或清理失败仍使 `result: "fail"`。任何单个字段都不是维护者的运行已验证（Runtime-Verified）声明。应同时保留 stdout JSON 和 stderr 诊断。

程序没有计时器。首次编译/加载、分配、复制与 CPU 检查，不能在端到端性能声明中偷偷排除。nonblocking 流或页锁定内存本身不是重叠测量。

## 证据边界

编译与已记录观察为空，运行保持待硬件验证（Pending Hardware Verification）。本次内容发布工作不声称完成 Linux 安装、CUDA 构建、GPU 正确性、清理行为、时间或速度提升观察。源码/测试审查与 CPU 测试不升级证据。构建模式不会让整个示例变成无需运行验证（Runtime-Not-Applicable），因为它的验收包含 GPU 输出。

EX21 首次真实 CI 尝试失败，是因为它要求官方 NVIDIA Debian 安装并不提供的 `version.json`。把错误前提换为已安装包与所属包检查，不等于重跑已经通过。驱动用户态/导入验证及原生构建仍待完成；这里不虚构成功日志或已加载库观察。

## 预期观察

1. 无需 GPU 的构建应生成面向 compute_75 的 PTX，以及包含原创核函数 sm_75 SASS 的非空 nvJitLink cubin，不初始化设备/上下文，也不启动工作。
2. 默认运行应为 1003 个值提交四个 256 线程块，21 个尾部线程应走边界保护路径。
3. 经检查的流完成后，每个输出应有限且与 CPU 参考精确相等；CPU 参考还应匹配独立字面值。
4. 自有 Buffer 应在提交流上关闭，然后等待释放完成、关闭流；日志和首个失败应在清理尝试后保留。
