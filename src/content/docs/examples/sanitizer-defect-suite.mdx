EX16 是一个独立、原创的 Compute Sanitizer 缺陷套件可运行示例（Runnable Example）。八个 C++17 CUDA binary 各自只运行一个 case：四个 case 各包含一个刻意隔离的缺陷，另外四个保留相同预期工作并实施最小修复。网站不执行 CUDA，也不保存任何工具诊断或运行日志。

## 用途

先完成 [Q03：用 memcheck 定位无效内存访问](/correctness/memcheck-invalid-memory-access/)，再完成 [Q04：区分 racecheck、initcheck 与 synccheck](/correctness/racecheck-initcheck-synccheck/)。Q03 建立先运行 memcheck 的顺序，Q04 建立后三种工具的检测边界。[LAB07](/labs/diagnose-four-sanitizer-failures/) 使用同一个 EX16 project 指导外部运行和证据采集。

一个进程只执行一个 case。这样，越界访问或无效同步导致的 CUDA context 状态不会进入下一项工具检查。Defect 与 corrected variant 使用同样的 problem size、launch geometry 和预期输出；每一对只改变造成缺陷的那一处条件或缺失操作。

## 获取 canonical project

[在固定提交中查看完整 EX16 项目](https://github.com/xiangzhang-coding/cuda-learning-site/tree/0c1ac1b3125a92a35270ec2a498f009125b89597/examples/ex16-sanitizer-defect-suite)，或[下载同一提交的源码归档](https://github.com/xiangzhang-coding/cuda-learning-site/archive/0c1ac1b3125a92a35270ec2a498f009125b89597.zip)。解压后进入 `examples/ex16-sanitizer-defect-suite/`。

`project.json` 声明八个 build input、三条固定 Toolkit Lane、128-byte 上界、四对预期行为和空证据轴。`README.md` 给出独立运行命令。项目源码使用 Apache-2.0，页面文字使用 CC-BY-4.0；两者均不是 NVIDIA sample source 的改写。

## 场景合同

| Tool | Defect category | 最小修复 | 正确性检查 |
| --- | --- | --- | --- |
| `memcheck` | 单个 global-memory 越界写 | `index <= count` 改为 `index < count` | 32 个合法元素匹配确定性 sequence |
| `racecheck` | plain shared-memory RAW ordering hazard | producer 与 consumer 之间加入一次 block barrier | consumer 得到 42 |
| `initcheck` | 读取未初始化的 device global memory | launch 前把同一 input allocation 清零 | 16 个 output 都等于 1 |
| `synccheck` | divergent conditional `__syncthreads()` | 把同一个 barrier 移到所有 thread 都会到达的位置 | 16 个 thread 保留各自的 phase-copy value |

每个 executable 都检查 launch submission、显式 completion 和可定义的 output。App 自身的 `PASS` 不能替代工具报告；defect 在某次 schedule 下产生预期值，也不能说明 hazard 不存在。

## Host utility 边界

`include/sanitizer_suite_contract.hpp` 是纯 host C++17 metadata：它按页面顺序列出 scenario ID、tool、variant、完整命令和 category。`tests/host_utility_test.cpp` 只验证这五类 metadata 的 identity、顺序、唯一性与成对关系。

`make host-test` 不包含 CUDA header，不编译 `.cu`，也不启动 GPU 或 Compute Sanitizer。通过该 utility **不能建立 GPU 正确性，也不能建立 sanitizer 行为**；它只防止文档命令与 executable identity 漂移。

## 构建合同

在原生 Linux 的项目目录中运行 `make preprocess DIALECT=c++17`、`make compile DIALECT=c++17`、`make link DIALECT=c++17`、`make inspect DIALECT=c++17` 和 `make host-test DIALECT=c++17`。前四个 stage 处理全部八个 binary；host-test 只需要 x86-64 host C++17 compiler。

每个 CUDA source 产生一个 `.ii`、一个 `.o` 和一个同名 hyphenated executable。Inspect 对全部八个 executable 分别确认 native `sm_75` cubin 与从 `compute_75` 生成的 forward-compatible PTX。`scripts/compile-check.sh c++17 ex16 <result-dir>` 只运行这些 build stage 和 host utility，绝不启动 CUDA executable 或 Compute Sanitizer。

## 兼容性与精确门槛

**Hardware gate：** 构建需要 x86-64 CPU、host C++17 compiler 与所选 CUDA Toolkit；运行只属于原生 Linux Supported Environment，需要恰好一张 compute capability 7.5 或更新的 CUDA GPU。任何进程的 global-plus-shared problem memory 最多 128 bytes，低于 Baseline GPU Capability Tier 的 8 GB 边界。

**Tool gate：** 使用所选 Toolkit Lane 自带的 `compute-sanitizer`，记录其实际版本；先运行 `memcheck`，再分别运行 `racecheck`、`initcheck` 和 `synccheck`；每个工具只检查匹配的 defect/corrected executable，每条命令启动新进程。不同工具的 clean result 不能互相替代。

| CUDA 13.3.1 | Ubuntu 24.04 x86-64 | `nvidia/cuda:13.3.1-devel-ubuntu24.04` |

## 预期观察，不是记录结果

1. Memcheck 应定位 defect executable 的单个 global-memory 越界写；corrected executable 应保留 32 个预期写入而不再包含该 bounds defect。
2. Racecheck 应定位 defect executable 的 plain shared-memory RAW ordering hazard；corrected executable 应通过 block barrier 保留发布值。
3. Initcheck 应定位 defect executable 对未初始化 device global memory 的读取；corrected executable 应在 input 清零后保留 increment 工作。
4. Synccheck 应定位 defect executable 的 divergent conditional `__syncthreads()`；corrected executable 应让整个 block 一致参与并保留 phase copy。

四项都是事先写入 manifest 的 acceptance direction，不是本站已观察到的 sanitizer output。Corrected variant 的预期 clean behavior 同样需要合格记录，不能从 source inspection 推定。
