EX10 是一个只构建、只检查的可运行示例（Runnable Example）。它把 NVCC 的公开编译阶段变成可审计的产物链，但不把产物执行当作验收步骤。先完成 [M15](/toolchain/nvcc-compilation-flow/) 和 [M16](/toolchain/ptx-cubin-fatbinary/)；M17、M18、M19 和 VIS09 会继续展开这里看到的 target、链接、检查与可视化模型。

## 用途

这个项目回答的是“每个稳定编译阶段留下什么，以及下一个阶段消费什么”，而不是“kernel 跑得多快”。同一份小 kernel 分别生成预处理文本、独立 PTX、独立 cubin 和同时携带 `sm_75`/`compute_75` 的 fatbin：

<CanonicalCode exampleId="EX10" range="artifact-kernel" />

另一条路径故意跨两个 CUDA translation unit。`src/caller.cu` 只声明并调用 `src/device_math.cu` 定义的 device function，因此两个 `-dc` 对象必须经过显式 device link：

## 获取 canonical project

[查看固定提交中的完整 EX10 项目](https://github.com/xiangzhang-coding/cuda-learning-site/tree/c7326c342c5673de7d17de08d4f56ab836648d5d/examples/ex10-ptx-fatbinary-inspection)，或[下载同一提交的源码归档](https://github.com/xiangzhang-coding/cuda-learning-site/archive/c7326c342c5673de7d17de08d4f56ab836648d5d.zip)。解压后进入 `examples/ex10-ptx-fatbinary-inspection/`。`project.json` 是机器可读契约；`README.md`、`Makefile` 和 `scripts/` 给出独立检查方法。

## 产物矩阵

| 阶段 | 主要输出 | 检查与记录 |
| --- | --- | --- |
| preprocess | `artifact_kernel.ii` | 非空并进入 SHA-256 ledger |
| standalone PTX | `artifact_kernel.ptx` | 检查 `.target sm_75` 并哈希 |
| cubin | `artifact_kernel.cubin` | `cuobjdump` 输出 SASS、CUDA ELF 和 symbols，并哈希 cubin |
| fatbin | `artifact_kernel.fatbin` | dump 内嵌 PTX，确认 `compute_75` 路径，并哈希 |
| relocatable compile | `device_math.o`、`caller.o` | 对两个 translation unit 分别执行 `-dc`；哈希并记录链接前 symbols |
| device link | `device_link.o` | 显式 `--device-link`；哈希并记录链接后的 CUDA symbols |
| host link | `ex10-ptx-fatbinary-inspection` | 使用 `--no-device-link`，只完成 host link；哈希且绝不执行 |
| inspect | PTX/ELF lists、PTX/SASS/ELF dumps、symbol/link ledger | `cuobjdump`、`nm` 与 SHA-256 的静态证据 |
| artifact test | `artifact-test-report.txt` | 核对文件、目标、symbols、hash 和禁止执行边界 |

## 完整流水线

Makefile 公开九个分离目标。最终 host-link 不隐式重做 device link：

<CanonicalCode exampleId="EX10" range="artifact-pipeline" />

在受支持的原生 Linux 环境中，可以依次调用：

```sh
make preprocess DIALECT=c++17
make standalone-ptx DIALECT=c++17
make cubin DIALECT=c++17
make fatbin DIALECT=c++17
make relocatable-compile DIALECT=c++17
make device-link DIALECT=c++17
make host-link DIALECT=c++17
make inspect DIALECT=c++17
make artifact-test DIALECT=c++17
```

`artifact-test` 只读取文件并调用 inspection utilities。它不会启动最终 host artifact，也不会触发 kernel launch。

## Toolkit Lane 与 C++23 probe

| 检查对象 | 方言 | 容器边界 |
| --- | --- | --- |
| CUDA 11.8.0 ordinary Lane | C++17 | digest-pinned `linux/amd64` devel image；`--network none`、non-root、无 `--gpus` |
| CUDA 12.9.2 ordinary Lane | C++17、C++20 | 同一份源码与 digest-pinned image；`--network none`、non-root、无 `--gpus` |
| CUDA 13.3.1 ordinary Lane | C++17、C++20 | 同一份源码与 digest-pinned image；`--network none`、non-root、无 `--gpus` |
| CUDA 13.3.1 C++23 probe | C++23 | 仅 probe 使用基于精确 13.3.1 base 的临时 image，并安装 `/usr/bin/g++-14` |

CUDA 13.3 owner guide 在 2026-08-29 声明 Linux GCC 6.x-15.x 和 C++23；Ubuntu Noble Updates 的 `g++-14` 页面当日显示 `14.2.0-4ubuntu2~24.04.1`。Probe 使用真正的 C++23 `if consteval` 语法并要求 `__cplusplus >= 202302L`：

<CanonicalCode exampleId="EX10" range="cxx23-probe" />

临时 image 的 record 必须保存实际安装的 package version、GCC 14 version line、base image identity 和 derived image identity。这个结果只说明 probe object 是否可编译，不把 ordinary EX10 Lane 扩大为 C++23。任何路径都不使用 `--allow-unsupported-compiler`。

## 证据状态

当前 `project.json` 的 compilation evidence 数组为空。Workflow matrix 会生成 sanitized record 和 inspection logs，但在下载、复核、提交 record 并把 `sourceCommit`、`sourceUrl`、`downloadUrl` 重钉到同一个 evidence commit 之前，本页不显示编译已检查（Compile-Checked）。失败、跳过或仅存在镜像都不能授予状态。

运行证据固定为无需运行验证（Runtime-Not-Applicable）。这里的验收条件是编译、hash 和 artifact inspection，不是 GPU 行为。

## 不运行、不测性能

- Workflow 不传 `--gpus`，ordinary containers 以 non-root、`linux/amd64`、`--network none` 运行。
- 最终 host artifact 只作为 host-link 和 inspection 输入，绝不执行。
- C++23 probe 只生成并检查 object file，也不执行 host 或 GPU code。
- 页面不记录 latency、throughput、speedup、occupancy 或任何性能数字。
- Compile-Checked 以后也不会替代 Runtime-Verified；对 EX10 而言 runtime 本来就不属于 acceptance criteria。
