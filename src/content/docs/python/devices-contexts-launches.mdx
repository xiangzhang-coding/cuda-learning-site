## 学习目标

指针位置不对、借用视图失效、标量封送位宽错误，任何一项都能让正确的核函数得出无效结果。用约 30 分钟建立设备、上下文与存储的所有权表，推导启动几何和参数位宽，找出允许 CPU 读取结果的完成点。这个模型用于显式启动与集成调试，不是重置其他库 CUDA 状态的操作指南。

## 前置知识

先完成 [P01](/python/cuda-python-bridge/)与 [F07：Runtime 和 Driver API](/foundations/runtime-driver-api/)，严格为 `[P01, F07]`。P01 给出唯一环境配置；F07 解释显式上下文与原生句柄责任。可运行示例（Runnable Example）[EX21](/examples/cuda-python-launch/)是唯一可执行实现。相关的 [P03](/python/runtime-compilation-linking/)展开编译细节，不是本单元的额外前置。

## 对象语法仍保留 Driver API 模型

Runtime API 常让上下文设置看起来是隐式完成的；Driver API 则更直接地暴露上下文选择和句柄。Python 对象接口让这一模型更容易表达，但没有消除它。core 1.2.0 基于具有共享所有权的原生 CUDA 对象，并为部分对象提供清理方法；它不是一套所有对象都像文件一样有 `close()` 的协议。理解这个区别，比背构造函数名单更有用。

用下面的生命周期对照表，将 [F04](/foundations/host-device-lifecycle/)、[F07](/foundations/runtime-driver-api/)及 [M07](/memory/stream-ordering/)教过的**责任**迁移到 Python 方案。两列在概念上对应，**不是一对一调用转发，也不表示所有权可以互换**。表中 C++ 指主机侧 Runtime 或 Driver API，不是另一种 GPU 执行模型；`s` 表示自己拥有的 Python 流。

| 责任 | CUDA C++ API 或句柄 | core 1.2.0 方案 | 调用者仍需负责什么 |
| --- | --- | --- | --- |
| 选择执行设备 | `cudaSetDevice(0)`；Driver 代码在 `cuInit` 后取得 `CUdevice` | `dev = Device(0)`，随后 `dev.set_current()` | Toolkit 13.3.1 的 cudaSetDevice 绑定并初始化该设备的 Runtime 主上下文状态，但不等待工作完成。只构造 Device 不建立所需当前上下文；两条路径都不计算结果。 |
| 持有上下文并设为当前 | `cuDevicePrimaryCtxRetain(&ctx, device)` 得到 `CUcontext`；`cuCtxSetCurrent(ctx)` 将其绑定到调用线程 | 默认 `dev.set_current()` 持有并选择共享主上下文；通过 `dev.context` 查看 | Driver retain 本身不把上下文设为当前。C++ 持有者按上下文/生命周期规则用 `cuDevicePrimaryCtxRelease` 平衡自己的 retain；core 的借用者不能释放 core 的 retain 或重置共享状态。 |
| 分配设备字节 | `cudaMalloc` 或按流排序的 `cudaMallocAsync`；设备指针值存于主机变量 | `dev.allocate(nbytes, stream=s)` 返回 Buffer | 计算字节数，保留位置与最后使用边界。core 选择关联内存资源，可能用池，也可能回退到同步路径；不保证调用 cudaMallocAsync，更不证明分配重叠。 |
| 分配主机传输存储 | `cudaMallocHost` 提供调用者拥有的主机存储，`cudaFreeHost` 释放 | `LegacyPinnedMemoryResource().allocate(nbytes, stream=s)` 提供主机可访问 Buffer | 旧式资源采用同步 `cuMemAllocHost`，不是异步分配。ctypes 数组视图借用 Buffer，不是 C++ 自有容器或数据副本。 |
| 创建排序域 | `cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking)` 得到 `cudaStream_t` | `dev.create_stream(options=StreamOptions(nonblocking=True))` 得到自有 Stream | 流必须关联正确上下文。nonblocking 去掉旧式 NULL 流的隐式依赖，不取消主机读取前的等待要求，也不证明重叠。 |
| 传输已初始化输入与结果 | `cudaMemcpyAsync(dst, src, nbytes, kind, stream)` 指定字节数、方向和流 | H2D：`d.copy_from(h, stream=s)`；D2H：`d.copy_to(h, stream=s)` | core 普通整 Buffer 复制要求范围相等，并根据指针推断方向。显式给出主机目标；省略目标会从源内存资源分配。传输使用期间保持主机内容稳定。 |
| 取得可执行代码与核函数 | 传统 Runtime 启动使用已注册核函数符号及托管模块；显式 Driver 路径使用 `cuModuleLoadData` / `CUmodule`，再用 `cuModuleGetFunction` / `CUfunction` | cubin ObjectCode 通过 `linked.get_kernel("ex21_vector_add")` 提供 Kernel | 这是延迟加载/查找边界，不是编译或执行。core 的 ObjectCode 原生句柄是 Driver `CUlibrary`，不能视为 Runtime 托管所有权，也不是可手动卸载的 `CUmodule`。 |
| 提交带配置的启动 | `kernel<<<grid, block, 0, stream>>>(...)`，或以显式参数存储调用 `cuLaunchKernel` | `launch(s, config, kernel, d_a, d_b, d_c, ctypes.c_uint32(n))`，配置为 `LaunchConfig(grid=grid, block=block)` | 对齐 grid/block、EX21 的零动态共享内存、指针生命周期和标量 ABI。C++ 参数有类型，不代表 Python int 就是 32 位无符号数；core 不推断核函数签名。 |
| 检查前确认完成 | 检查 `cudaStreamSynchronize(stream)`；F04 的 `cudaDeviceSynchronize()` 范围更广 | 检查 `s.sync()`；`dev.sync()` 范围更广 | 异步路径在等待前提交 D2H，之后才检查全部输出。提交成功、源码先后或流的析构都不能替代完成检查。 |
| 最后使用后只释放自有资源 | 显式或由 RAII 管理 `cudaFree` / `cudaFreeAsync`、`cudaFreeHost`，再 `cudaStreamDestroy`；独立拥有的 Driver 上下文/模块另按其规则平衡释放 | `buffer.close(stream=s)`，以 `s.sync()` 等待排队释放，再 `s.close()` | 持有资源到工作完成。Kernel/ObjectCode 没有公开 close；Device 和共享主上下文不是私有清理目标。清理诊断不等于结果成功。 |

F04 的规范 C++ 示例特意先检查 `cudaDeviceSynchronize()`，再执行阻塞式 D2H `cudaMemcpy`。EX21 则在显式流上排队异步 D2H，再检查 `s.sync()`。两者都在 CPU 验收前建立完成边界，但若照抄 F04 的行顺序到异步复制方案，会漏掉后续复制的完成边界。M07 的流内顺序解释了 EX21 为何无需在每两步之间都增加设备级等待。

错误处理也迁移责任，而非照搬拼写。F04 检查 `cudaError_t`，并在 C++ 启动表达式之后检查 `cudaGetLastError`；Driver 路径检查 `cuLaunchKernel` 的 `CUresult`。core 用 Python 异常报告启动调用失败，之后仍需独立检查同步以发现延迟错误。不能附加一个 Runtime 最后错误查询就认为它验证了基于 Driver 的 core 启动，也不能因提交未抛异常就省掉完成检查。

## 先选设备，再建立当前上下文

`Device.get_all_devices()` 枚举 CUDA 设备。`dev = Device(0)` 初始化驱动访问并标识可见设备 0，本身却不建立所需的当前上下文。创建资源前调用 `dev.set_current()`。默认路径会持有并选择该设备的主上下文（Primary Context），返回 `None`，上下文通过 `dev.context` 获取。不要把返回值当作上下文对象保存。

设备状态是线程局部的。这个独立示例不是适用于现有应用的通用上下文切换助手。显式传入上下文的 `set_current(ctx)` 对先前上下文有不同的处理，也不是退出时自动恢复的上下文管理器。未来若要嵌入应用，应设计如何保留调用者的当前上下文，而不是退出时重置它。

检查 `dev.device_id`、`dev.name`、`dev.compute_capability` 与 `dev.arch`；`arch` 是 `"75"` 这样的字符串，不是 `"sm_75"`。主上下文属于共享状态。不要销毁或重置它，不要执行不平衡的原生主上下文释放，也不要在它仍为当前上下文时调用 `Context.close()`。其共享生命周期由 core 管理。不存在 `Device.close()` 步骤。

## 字节、主机视图与持有者

用 `dev.create_stream(options=StreamOptions(nonblocking=True))` 创建自己拥有的流（stream）。nonblocking 指与旧式 NULL 流之间的同步关系，不代表主机会等待完成。用 `dev.allocate(nbytes, stream=s)` 分配设备字节，用 `LegacyPinnedMemoryResource().allocate(nbytes, stream=s)` 分配页锁定主机字节，并按需要保留内存资源与 Buffer。

设备内存资源可能使用池，也可能回退到同步分配。旧式页锁定资源采用同步主机分配。因此，参数里出现 `stream=` 并不能证明分配是异步的，更不能证明发生了重叠。

主机视图形如 `(ctypes.c_float * n).from_address(int(h.handle))`，其中 **h 必须是主机可访问的页锁定存储**。绝不能用于仅设备可访问的 Buffer。将句柄转为 `int` 只得到地址数值，不赋予 CPU 访问权限。视图借用内存，不会让 h 自动存活；h 必须活过每次视图访问与排队传输。字节容量必须匹配元素类型：n 个 float32 需要 `4*n` 字节。

## 给复制指定明确目标

H2D 输入使用 `d.copy_from(h, stream=s)`，D2H 输出使用 `d.copy_to(h, stream=s)`。两端都是字节容量相同的 Buffer；不能把任意 Python 列表当成等价存储传入。容量不同会抛出 `ValueError`，不是只复制较短一端。

省略目标的 `d.copy_to(stream=s)` 是一个陷阱：新分配来自源的内存资源，返回的 Buffer 不一定是主机内存。把 Python 变量命名为 `host_output` 也不能改变位置。普通复制选项下，CUDA 根据指针推断方向；应用仍应明确两端的主机/设备属性和所有权。

把规范片段当作所有权证明来读：初始化页锁定输入及 NaN 输出哨兵，上传两个输入和哨兵，启动，再将输出 D2H 复制到显式分配的页锁定目标，在 CPU 比较前调用 `s.sync()`。哨兵上传是第三次 H2D，不是数学输入；漏写会留下必须拒绝的非有限值。局部变量里的视图还活着，不能替代持有它背后的 Buffer。

## 核函数参数有二进制合同

<CanonicalCode exampleId="EX21" range="kernel" />

入口接收三个 float 指针和一个 `unsigned int n`。指针参数直接传 core Buffer，n 传 `ctypes.c_uint32(n)`。core 1.2.0 将普通 Python `int` 按指针位宽打包，不会阅读核函数签名并推断它是 C `unsigned int`。同样，Python `float` 按 double 打包；若核函数标量为 `float`，应使用 `ctypes.c_float`。

这就是核函数参数封送（Kernel Argument Marshalling）：把主机值转为设备代码要求的位宽与表示。某个小整数在某台机器上碰巧可用，不是 ABI 证明。构造 ctypes 标量前先检查范围，不能让非法计数经转换回绕后进入合法区间。不论提交时何时读取标量字节，指针指向的数据都必须活到执行完成。

## 预测启动几何与精确结果

`LaunchConfig(grid=(n + 255) // 256, block=256)` 为正 n 构造一维覆盖。n=1003 时，线程候选索引是 0 到 1023。末块有 235 个有效线程、21 个尾部无效线程；核函数必须在读取输入或写入输出之前判断逻辑边界。n=0 应由主机侧拒绝或按明确约定直接返回，不能提交零网格。EX21 的运行路径要求 size 为正。

三个设备数组占 `12*n` 载荷字节，n=1003 时为 12036；等量的页锁定主机载荷、编译器内存和上下文/库资源另计。实际设备目标必须受 NVRTC 支持，并满足 EX21 的计算能力（compute capability）7.5 下限；架构数字更大，不自动代表编译器支持它。

正确性要求经检查的完成、有限值，以及将全部 1003 个元素与独立 CPU 参考实现逐项比较。本例二进制分数输入允许精确相等。正确的尾部判断修不好标量位宽错误或缺失复制；每份合同都要分别证明。

## 工作完成后再释放持有者

| 资源 | 正常成功路径的释放边界 |
| --- | --- |
| Program 和 Linker | 取得独立输出字节后即可关闭 |
| ctypes 主机视图 | D2H 完成并比较后停止使用、释放视图引用，再关闭主机 Buffer |
| 设备和主机 Buffer | 最后一次使用后以 `buffer.close(stream=s)` 关闭；保留流以完成排队释放 |
| 自己拥有的流 | 再调用 `s.sync()` 等待排队释放完成，随后 `s.close()` |
| ObjectCode 和 Kernel | 没有公开 `close()`；持有至工作完成，再释放引用 |
| 共享主上下文与 Device | 让 core 管理共享生命周期；不重置、不原生销毁、不虚构 Device close |

`Kernel` 保留库的所有权。`ObjectCode.handle` 是 `CUlibrary`，不是旧式 `CUmodule`；不能传给 `cuModuleUnload`，也不能手动卸载仍由 core 拥有的库。释放一条 Python 引用，不等于在所有情况下都立即销毁底层对象。

发生错误后，停止提交，保留首个错误，尝试检查完成并清理已取得的资源，将后续错误分开报告。销毁流不能替代完成检查。旧式页锁定释放会先同步其流。EX21 的 `cleanup_step` 在每次显式清理动作期间同时捕获 Python `sys.stderr` 与原生文件描述符 2，之后恢复两者。异常/捕获失败进入 `cleanupErrors`；全部捕获的 stderr 进入 `cleanupWarnings`，不只限于 Python 警告。任何非空捕获输出，包括纯空白，都阻止命令判为成功；之后同步成功也不抹掉它。不能通过原生绑定重复释放，也不能把失败等待叫作验收成功。

该助手每次动作最多保留 16,384 字节诊断载荷，多读一字节判断截断，解码文本也限制为 16,384 字符，再附动作标签与截断标记。异常文本同样受限；报告/回放边界不限制临时文件的磁盘占用。捕获或回放失败本身是清理失败，捕获准备失败也不能成为跳过释放尝试的理由。原操作异常及所在阶段仍是主要诊断。

显式放弃 Kernel/ObjectCode 引用也经过该助手，不虚构 close 方法。判定只覆盖这些显式动作期间发出的诊断，不覆盖因其他持有者延后的析构、之后的 GC、稍后才输出的原生缓冲内容，或判定之后的解释器关闭。捕获会修改进程全局 stderr 与警告状态，因此仅适合这个单线程独立进程。JSON 之外仍要保留外部 stderr；有界捕获干净不证明最终所有原生清理均成功。

## 找到最早被破坏的合同

容量不匹配立即产生的 `ValueError`，与库加载、符号查找、启动提交和 `s.sync()` 失败不同。CUDA 复制调用可能报告之前的异步启动错误；观察到错误的行，不一定是造成错误的行。

失败报告应保留阶段与异常、实际 Buffer 容量和位置、核函数参数类型、n/grid/block、设备/目标和流所有权。核对方法是 `sync()`，不是不存在的 `synchronize()`。不能通过在 CPU 上解引用设备内存来“修复”指针，也不能捕获异常后比较旧主机值并打印成功。

## 不把正确性示例写成测量结论

一条显式流使依赖链容易检查，不表示并发。nonblocking 流与页锁定内存也不证明传输重叠。CPU 初始化、分配、编译/链接、延迟加载、复制与清理都可能主导端到端时间。未来若测核函数时间，需要合适的设备计时边界与预热后重复执行；主机计时若声称覆盖已完成的工作，就必须包含完成检查。EX21 不记录时间或速度提升。
