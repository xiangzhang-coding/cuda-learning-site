## 学习目标

“JIT 成功了”不足以诊断缺失的核函数，更不能验证计算结果。用约 30 分钟识别各阶段产物及其生成者，区分原生编译和 GPU 执行，并为两套不同的低层 Python 合同设计错误处理。这些知识适用于动态生成核函数和部署诊断；本单元不实现通用持久代码缓存，也不承诺任意跨版本链接。

## 前置知识

有序前置为 [P02](/python/devices-contexts-launches/)、[M15：NVCC 编译流程](/toolchain/nvcc-compilation-flow/)和 [M16：PTX、Cubin 与 Fatbinary](/toolchain/ptx-cubin-fatbinary/)，严格为 `[P02, M15, M16]`。即使代码生成移入进程，也要保留 P02 的上下文、标量和存储合同。[EX21](/examples/cuda-python-launch/)仍是唯一规范实现。

## 推迟编译，不合并阶段

提前编译的 CUDA 流程常由 NVCC 编排主机/设备编译与链接。NVRTC 则在运行中的主机进程里编译 CUDA C++；nvJitLink 在该进程里链接设备代码输入。这两个库都不是在 GPU 上执行 Python。运行时编译可以根据应用需求专门化源码，但也引入编译器依赖、诊断处理与启动成本。

EX21 特意先生成 PTX，再显式链接为 cubin，尽管一个自包含核函数本来不一定需要独立链接阶段。这样安排是为了展示产物边界。使用实际 `sm_...` 目标直接 `Program(...).compile("cubin")` 也是合法替代，但不能将它描述为显式的 `Linker` 阶段。

## 给每道边界的产物命名

| 阶段 | 输入 | 输出或新增状态 | 是否执行向量加法 |
| --- | --- | --- | --- |
| NVRTC 编译 | CUDA C++ 源码字符串与虚拟目标 | ObjectCode 中的 PTX 字节 | 否 |
| nvJitLink 链接 | PTX 与实际目标 | ObjectCode 中的 cubin 字节 | 否 |
| 按需重建 ObjectCode | 文件或内存中的 cubin 字节 | 代码的 Python 包装对象 | 否，也不是立即加载 |
| `get_kernel` 查找 | cubin ObjectCode 与入口名称 | 延迟加载的 CUDA 库与 Kernel | 否 |
| 启动 | Kernel、grid/block、流、带类型的参数 | 已提交的 GPU 工作 | 尚未证明完成 |
| 回传并同步 | 有序工作与仍有效的缓冲区 | 成功时得到已完成、主机可见的输出 | 此时才逐项检查结果 |

PTX 的虚拟目标和 cubin 的实际目标用途不同。产物存在，不证明 GPU 能加载它、符号存在、参数匹配或结果正确。构建报告应同时记录源码身份、编译器/链接器版本、选项、目标、后端和产物身份。

## core 路径显式展示两个生成阶段

<CanonicalCode exampleId="EX21" range="runtime-compile" />

通过 `Program(source, code_type="c++", options=opts)` 创建程序，选项为 `ProgramOptions(std="c++17", arch=f"compute_{arch}", relocatable_device_code=True, name="ex21_vector_add.cu")`。源码是 Python 字符串，这个简单核函数不需要 Toolkit 头文件。`program.compile("ptx", logs=io.StringIO())` 返回 ObjectCode，其 `.code` 为字节。

真正的链接调用是 `Linker(ptx, options=LinkerOptions(arch=f"sm_{arch}"))`，随后 `linker.link("cubin")`。对象输入在前，options 用关键字；不要照抄生成文档中容易误读的类头顺序。检查 `Linker.which_backend()`：本配置要求 **nvJitLink**。发出警告并回退到驱动链接器，不算完成固定路径。原生 NVRTC 与 nvJitLink 都固定为 Toolkit 13.3.1 中的 13.3.33；通过 extras 安装更新的原生编译器可能破坏输入与链接器的兼容假设。

不需要 GPU 的构建中，arch 来自显式 CLI 参数 `75`，而不是 `Device(0)` 查询结果。运行时才根据所选 GPU 推导目标并检查编译器支持。如果构建命令仅为选目标就查询设备，便破坏了它“不需要 GPU”的合同。

不需要 GPU，不等于不需要驱动库：core 1.2.0 编译 PTX 时会查询 `cuDriverGetVersion()`。必须提供真实 `libcuda` 用户态库，不能用 Toolkit stub 或模拟驱动代替。该查询不调用 `cuInit`，也不创建设备/上下文。EX21 还需要所选 Toolkit 的 `cuobjdump` 检查产物。无 GPU 构建机可以提供这些主机库与工具，但不因此声称发生 GPU 运行，或新增仅容器运行的受支持环境。

## 加载在链接之后

`linked.get_kernel("ex21_vector_add")` 会延迟加载 CUDA 库并查找入口。不存在独立公开的 `ObjectCode.load()` 调用。`ObjectCode.from_cubin(bytes(linked.code), name="ex21_vector_add")` 可以在不立即加载的情况下重建对象；使用真实保存的产物时，也可以传文件路径。

取得独立输出字节后，Program 和 Linker 可以关闭。链接失败时要在关闭前读取日志。Kernel/库的持有者必须活到工作完成；ObjectCode 和 Kernel 没有公开 `close()`。入口名称拼错是查找失败，不是编译失败；重建 cubin 对象也不是加载成功记录。

## 低层 NVRTC 返回状态在前的元组

稳定的 `cuda.bindings.nvrtc` 与下一节链接绑定不同。下表解释调用，不提供第二份可执行实现：

| 调用形状 | 返回形状与责任 |
| --- | --- |
| `nvrtcCreateProgram(src_bytes, name_bytes, 0, [], [])` | `(status, program)`；五个参数都必须提供 |
| `nvrtcCompileProgram(program, len(options), options)` | `(status,)`；选项为 bytes，例如编码后的 `--gpu-architecture=compute_75` |
| `nvrtcGetProgramLogSize(program)` | `(status, size)`；长度包含结尾 NUL |
| `nvrtcGetProgramLog(program, storage)` | `(status,)`；调用者提供 C-char 输出存储 |
| `nvrtcGetPTXSize` 再 `nvrtcGetPTX` | 查询长度、准备调用者存储、检查提取；不是自动返回 PTX 字符串 |
| `nvrtcDestroyProgram(program)` | `(status,)`；成功取得的程序只销毁一次 |

信任输出前，**每次**都要将状态与 `nvrtc.nvrtcResult.NVRTC_SUCCESS` 比较；失败时输出可能是 `None`。失败和成功带警告时都要取编译日志；若读取日志又失败，应保留原编译状态。`nvrtcGetErrorString(status)` 本身也返回状态和消息字节。不能把错误返回当成自动抛出的 Python 异常。

NVRTC 提取 cubin 要求实际 `sm_...` 编译目标；虚拟 `compute_...` 目标的 `nvrtcGetCUBINSize` 为零。PTX 长度包含结尾 NUL。较旧 NVRTC 的 C-char 输出转换与 nvJitLink 的可写缓冲区包装不同，不能猜测两者接受完全相同的 Python 输出类型。本单元的低层动手对照选 nvJitLink，不采用实验性 NVRTC v2，也不另写未经验证的 NVRTC 实现。

## 低层 nvJitLink 返回值并抛出异常

使用稳定的 `cuda.bindings.nvjitlink`。完整资源链如下：

1. `nvjitlink.version()` 返回 `(major, minor)`，**没有**前置状态。它标识原生库 API 版本，不是 wheel 或完整补丁包身份。
2. `nvjitlink.create(1, [f"-arch=sm_{arch}"])` 返回整数句柄，不是 `(status, handle)`。只有取得成功，才存在需要销毁的句柄。
3. `nvjitlink.add_data(handle, nvjitlink.InputType.PTX, ptx_bytes, len(ptx_bytes), "ex21.ptx")` 添加保留存活的连续 PTX 字节；`nvjitlink.complete(handle)` 才执行链接。成功均返回 `None`。
4. `nvjitlink.get_linked_cubin_size(handle)` 给出输出长度。分配精确长度的 `bytearray`，传给 `nvjitlink.get_linked_cubin(handle, output)`；之后用 `bytes(output)` 重建 ObjectCode。不可变 `bytes` 不是可写输出存储。
5. 销毁有效句柄前，查询 error/info 日志长度，再填充对应长度的可写 `bytearray`。解码文本时只移除尾部 NUL。在 `finally` 路径用 `nvjitlink.destroy(handle)` 对成功取得的句柄恰好释放一次。

原生非零状态抛出 `nvjitlink.nvJitLinkError`，其 `.status` 与消息标识状态。非法 Python 参数可能先引发 `TypeError` 或 `ValueError`；缺失库或符号属于加载器失败。create 失败后没有可用于查询日志的有效句柄。后续链接失败可能留有有用日志，须在 destroy 前读取；日志和清理异常都不能遮住原始错误。

## 保留首个错误与所在阶段

core Program 将 NVRTC 失败转换成附带编译日志的异常。它的 `logs=` 流在编译成功后才写入，所以失败后的空 `StringIO` 不证明没有诊断。core Linker 给 nvJitLink 异常附加链接日志；驱动回退走不同错误路径。不要仅为打印报告而导入 core 私有 `_utils` 异常类。保留 traceback、类型和消息，用失败安全的清理，并只在独立 CLI 边界按需统一报告异常。

最小有效失败记录包含阶段、输入身份、目标/选项、实际加载的原生组件身份、原始异常或状态、可取得的日志，以及单独的清理诊断。启动后“还没异常”不够：复制或 `sync()` 可能报告此前的异步错误。编译或链接失败后，不能在没有明确、已验证缓存语义的情况下偷偷使用旧产物继续运行。

## 预测哪些阶段可以独立成功

对 `build --arch 75`，应预测 `compute_75` PTX、`sm_75` cubin 与 nvJitLink 后端，不包含设备选择、核函数查找、启动或输出向量。产物必须非空，但执行前不知道精确大小与诊断内容。

CUDA 源码语法错误应在链接前导致编译失败。若只在查找时拼错入口名，编译和链接可以成功而查找失败。若标量位宽不对，两个构建阶段仍可成功，但启动合同无效。这些是因果预测，不是观察到的失败终端记录。正确性仍由 EX21 完整运行及 CPU 比较决定。

## 启动、缓存与计时边界

调查启动成本时，应分别测编译、链接、延迟加载/查找、首次执行和预热后执行。复用 cubin 可以省去部分代码生成工作，却不会免除加载、存储或同步责任。未来缓存键至少要考虑源码、选项、编译器/链接器身份和目标，不能只有核函数名称；部署还需检查产物兼容性。本单元不实现缓存，也不声称速度提升。

## 引导实践：构建不等于 GPU 已运行

1. 在 P01 原生 Linux 配置的新 EX21 独立副本中，准备包并运行 CPU 参考合同。若该副本已有选定 `.venv`，省略 setup；脚本拒绝覆盖它：

```sh
bash scripts/setup.sh
.venv/bin/python ex21.py host-test
.venv/bin/python ex21.py check-environment
.venv/bin/python ex21.py build --arch 75
```

2. 构建需要选定解释器、包、NVRTC、nvJitLink、真实驱动用户态库和 cuobjdump，但**不需要 GPU**。缺失原生库时记录阻塞。不要为了让编译测试“更完整”而加入设备初始化或启动。
3. 检查 `build/compile` 中保留的构建产物与诊断，确认显式虚拟/实际目标、声明的后端，以及非空 PTX/cubin；记录实际身份，不猜测长度。结果不会被覆盖，再次尝试要指定新的 `--output-dir`。运行另有默认目录 `build/run`。没有真正查找入口，就不要报告产物已加载。
4. 在纸上将 core 调用对应到低层 nvJitLink 的 create/add/complete/extract/destroy 链。分别说明 create 失败与 complete 失败后哪里能取得日志，以及哪项输出必须可写。
5. 若具备运行硬件，再按 EX21 的独立运行门槛执行。不需要 GPU 的构建结果，不能变成向量加法正确性判定。

**验收：** 提交产物/阶段表、实际执行时的构建诊断，以及失败安全的低层所有权草图。构建受阻不是编译已检查（Compile-Checked）。只写出命令或检查 Python 语法，也不证明原生编译成功。

## 证据边界

本学习单元（Learning Unit）及纸面练习的四个证据数组保持为空。将来保留的合格构建记录，可以独立支持 EX21 的编译证据轴；这里不授予该状态。EX21 的输出验收要求 GPU 执行，因此它是待硬件验证（Pending Hardware Verification），不能因为某个 CLI 模式无需 GPU 就改成无需运行验证（Runtime-Not-Applicable）。

## 提取式自测

1. 编译、链接、重建、查找、启动和同步各自建立什么事实？
2. 为什么 PTX 使用 `compute_75`，显式 cubin 链接使用 `sm_75`？
3. NVRTC 的返回值，与 nvJitLink 的 `create`、`version` 及失败行为有什么不同？
4. 为什么要在销毁有效的失败链接器之前取日志？又为什么可能根本没有有效句柄？
5. 为什么 core 编译日志流为空，既不能证明成功，也不能证明没有诊断？
