本学习单元（Learning Unit）只处理一条原生 Linux（native Linux）命令生命周期：确认命令在哪里运行，执行受控构建，观察当时的进程，保留输出与退出状态，再封存可复核记录。它不是 Linux 命令大全，也不要求 GPU。

## 学完本单元，你应该能

- 同时说明当前工作目录（current working directory）的逻辑路径（logical path）和物理路径（physical path），并识别符号链接（symbolic link）带来的歧义。
- 把构建拆成有名称的构建阶段（build stage），为每个阶段记录工作目录、命令、时间和退出状态（exit status）。
- 解释 Make 配方（recipe）的 shell 边界，以及为什么一行中的 `cd` 默认不会影响下一行。
- 区分字面命令、xtrace、标准输出（stdout）和标准错误（stderr），并正确推理重定向与管道状态。
- 用允许列表环境（allowlisted environment）、进程快照（process snapshot）、UTC 时间戳（timestamp）和 SHA-2 哈希（hash）组成最小复现记录。

## 路径：同时记录逻辑位置和物理位置

shell 可以用两种都合理但含义不同的方式描述当前位置。`pwd -L` 使用逻辑路径，因此可能保留进入目录时经过的符号链接名称。`pwd -P` 使用物理路径，消除符号链接分量。`$PWD` 是 shell 维护的逻辑状态，不应单独充当文件身份。

对于一个已经存在的目标，GNU Coreutils 的 `realpath -e` 要求每个路径分量都存在，并返回消除 `.`、`..` 和符号链接后的绝对名称：

```bash
pwd -L >"$record_dir/cwd.logical"
logical_status=$?
pwd -P >"$record_dir/cwd.physical"
physical_status=$?
realpath -e -- "$build_dir" >"$record_dir/build-dir.physical"
realpath_status=$?
printf '%s\n' "$logical_status" >"$record_dir/cwd.logical.exit"
printf '%s\n' "$physical_status" >"$record_dir/cwd.physical.exit"
printf '%s\n' "$realpath_status" >"$record_dir/build-dir.physical.exit"
```

逻辑路径说明操作者如何到达目录，物理路径说明当时解析到了哪里。两者都值得保留。符号链接可能在采集后被重新指向，目录也可能被重命名，所以应在每个关键阶段开始前采集，而不是把几天前的路径记录贴到新构建上。

## 构建：固定工作目录、阶段和状态

不要让构建依赖调用者碰巧站在哪个目录。`make -C` 在读取 makefile 前切换目录，能把工作目录写进命令本身。stdout、stderr 和退出状态分别保存：

```bash
make -C "$build_dir" "$target" \
  >"$record_dir/build.stdout" \
  2>"$record_dir/build.stderr"
build_status=$?
printf '%s\n' "$build_status" >"$record_dir/build.exit"
```

一次记录应把 `configure`、`build`、`inspect` 等实际存在的阶段逐项列出。每项至少有阶段名、字面命令（literal command）和参数、逻辑与物理工作目录、UTC 开始与结束时间、退出状态、stdout 文件和 stderr 文件。不要把多条命令压成一句“build passed”。

`set -e` 不是完整的状态模型。Bash 在条件、列表和管道等语法位置对 `errexit` 有例外。它可以成为脚本政策的一部分，但不能替代在阶段边界立即保存 `$?` 并明确决定是否继续。

GNU Make 默认用 `/bin/sh` 执行配方，并为每一行启动新的子 shell（sub-shell）。下面的 `cd` 不会延续到下一行：

```make
artifact:
	cd build
	$(MAKE) artifact
```

把目录和命令放在同一行，或让子 Make 自己接收目录：

```make
artifact:
	$(MAKE) -C build artifact
```

`.ONESHELL` 会把一个配方的多行交给同一个 shell，但这也改变了失败传播方式。若采用它，仍要明确 shell、标志和每个关键命令的状态，不能假定前面一行失败必然让整个配方失败。

## 进程：快照不是历史记录

procps-ng 把 `ps` 定义为当前活动进程的快照。显式选择列、排序和区域设置（locale），才能减少终端宽度、环境变量和默认选项造成的漂移：

```bash
LC_ALL=C ps -eo pid=,ppid=,lstart=,stat=,comm= --sort=pid \
  >"$record_dir/processes.before"
process_status=$?
printf '%s\n' "$process_status" >"$record_dir/processes.before.exit"
```

在阶段前后各采一次有助于比较，但仍不是原子历史。采集期间进程可以启动、退出或改变状态。`args` 和环境字段还可能包含凭据，所以默认记录 `comm`，只有在安全政策允许时才扩展命令行，并在公开前处理敏感信息。

procfs（`/proc` 文件系统）提供 `/proc/PID/status`、`cmdline`、`cwd` 等进程视图。读取前发现的进程可能在打开文件前退出，路径会消失；数字 PID 也可能随后分配给另一个进程。Linux 6.8 文档还说明，旧进程的已打开 `/proc/PID` 文件描述符不会转而作用于复用该 PID 的新进程，但后续按路径重新打开仍是一次新的查找。

权限限制、PID namespace、`hidepid` 挂载选项和 ptrace 检查都可能隐藏或拒绝某些字段。读取失败说明“本次采集无法访问”，不等于进程或字段不存在。记录采集时间、PID、可用的启动时间以及原始错误，不要用猜测补空值。

## 日志：保留命令、文件描述符和管道边界

字面命令是执行前保存的脚本字节与参数边界。可以把固定脚本作为记录的一部分，并用 NUL 分隔参数以避免空格歧义：

```bash
printf '%s\0' "$0" "$@" >"$record_dir/argv.nul"
```

xtrace 是另一种产物。`set -x` 打印扩展后的命令，通常写入 stderr；变量值已经展开，原始引号也不能可靠恢复。它适合诊断实际走过的分支，不是字面输入的副本，而且可能泄露令牌。需要时应把 `BASH_XTRACEFD` 指向独立文件描述符，只在不含秘密的范围开启，并仍保留原始脚本和参数。

文件描述符 1 是 stdout，2 是 stderr。Bash 从左到右处理重定向，因此以下三条是替代方案，不是连续执行步骤：

```bash
make -C "$build_dir" "$target" \
  >"$record_dir/build.stdout" \
  2>"$record_dir/build.stderr"
make -C "$build_dir" "$target" \
  >"$record_dir/build.combined" \
  2>&1
make -C "$build_dir" "$target" \
  2>&1 \
  >"$record_dir/build.stdout"
```

第二条先把 stdout 指向文件，再让 stderr 复制 stdout 当时的目的地，所以两者进入同一文件。第三条先让 stderr 复制原来的 stdout，再改动 stdout，所以 stderr 不会进入该文件。`2>&1` 复制的是当时的目的地，不是永久绑定。

`tee` 适合同时显示和写入一个合并流，但会增加一个管道阶段：

```bash
set -o pipefail
make -C "$build_dir" "$target" 2>&1 | tee "$record_dir/build.combined"
pipeline_status=("${PIPESTATUS[@]}")
printf '%s\n' "${pipeline_status[0]}" >"$record_dir/make.exit"
printf '%s\n' "${pipeline_status[1]}" >"$record_dir/tee.exit"
```

没有 `pipefail` 时，管道状态默认只是最后一条命令的状态，成功的 `tee` 可能遮住失败的 `make`。启用 `pipefail` 后，整体状态是最右侧非零状态，但仍不能说明哪一段失败，所以要在任何其他简单命令之前复制 `PIPESTATUS`。`tee` 自己也可能因日志写入或下游管道失败。合并 `2>&1` 后无法恢复通道身份，两个通道的可见顺序还会受缓冲影响。因此，合并日志应标为便利视图；需要复核通道时，以独立 stdout、stderr 和状态文件为准。

## 复现记录：限制环境，再封存事实

继承整个交互环境会带入 `PATH`、locale、工具配置和凭据。GNU `env -i` 从空环境开始。只加入构建确实需要并愿意记录的变量：

```bash
env -i PATH="$tool_path" LC_ALL=C TZ=UTC env \
  >"$record_dir/environment.allowlist"

env -i PATH="$tool_path" LC_ALL=C TZ=UTC \
  make -C "$build_dir" "$target" \
  >"$record_dir/build.stdout" \
  2>"$record_dir/build.stderr"
build_status=$?
printf '%s\n' "$build_status" >"$record_dir/build.exit"
```

若工具确实需要 `HOME`、缓存目录或许可证变量，就逐项加入并说明理由。不要为了“完整”而转储可能含秘密的整个环境。另用 `uname -srm` 记录实际 kernel name、release 和 machine；它不能替代发行版、容器或工具版本字段。

Bash 5.3 的 `printf` 可以产生实际采集时刻。先把时区固定为 UTC，再在阶段前后分别调用：

```bash
timestamp_utc() (
  export TZ=UTC
  printf '%(%Y-%m-%dT%H:%M:%SZ)T\n' -1
)

timestamp_utc >"$record_dir/started-at.txt"
```

所有日志关闭后，再对固定文件清单计算 SHA-256：

```bash
(
  cd -- "$record_dir" || exit
  sha256sum -- command.sh argv.nul paths.txt environment.allowlist \
    system.uname stages.tsv build.stdout build.stderr build.exit \
    processes.before processes.after >SHA256SUMS
)
```

时间戳说明何时采集，哈希说明之后看到的字节是否相同。二者都不证明命令正确、来源可信或结果可外推。记录目录应位于会被清理的构建目录之外，`SHA256SUMS` 也不能把自己列为输入。
