CUDA kernel launch 相对 host 通常是异步的，因此异步错误（asynchronous error）可能在导致它的 device 工作之后才对 host 可见。与此同时，launch configuration 的一部分问题可以在提交路径立即暴露。正确的错误生命周期必须把“错误何时产生”“host 在哪里观察到它”和“哪个状态被读取或清除”分开，不能把所有 CUDA 调用统称为异步，也不能把某个 API 返回错误的位置直接当成唯一根因。

## 学完本单元，你应该能

- 区分 CUDA Runtime 的末次错误状态（last-error state）与每个 API 调用的直接返回值。
- 准确说明 `cudaPeekAtLastError` 读取但不重置状态，而 `cudaGetLastError` 读取后把状态重置为 `cudaSuccess`。
- 把 launch configuration 的即时错误（immediate error）与 device execution 的延后执行错误（deferred execution error）放到不同时间线上。
- 使用显式同步边界（explicit synchronization boundary）等待此前 device 工作并检查其返回状态。
- 在错误检查、结果正确性与 CUDA Evidence Status 之间保持独立边界。

## 错误状态：先分清直接返回与 last-error state

返回 `cudaError_t` 的 Runtime API 调用有自己的直接返回值，调用方应当在原位置检查它。Kernel launch syntax 本身没有一个可供普通赋值检查的 `cudaError_t` 返回值，因此 host 通常紧邻 launch 查询 last-error state。两条通道相关，但不能互相替代：例如 `cudaDeviceSynchronize` 的直接返回值必须直接检查，不能只在更晚的位置猜测发生了什么。

在本页使用的单 Runtime 实例程序中，last-error state 属于 host thread。CUDA 11.8.0 文档称其为同一 host thread 中任意 Runtime call 产生的末次错误；12.9.2 archive 和 13.3.1 文档进一步写明它属于该 host thread 中同一 CUDA Runtime library instance。这个状态不是每个 kernel、stream 或 device 各有一份的错误队列。

| 操作 | 读取什么 | 读取后是否重置 last-error state | 是否建立 device completion |
| --- | --- | --- | --- |
| `cudaPeekAtLastError()` | 当前 host thread / Runtime instance 的 last error | 否 | 否 |
| `cudaGetLastError()` | 同一 last error | 是，重置为 `cudaSuccess` | 否 |
| `cudaDeviceSynchronize()` | 它自己的同步调用结果 | 不应把它当作上述两个 getter 的替代品 | 是，等待此前请求的 device tasks |

`cudaPeekAtLastError` 适合不消费状态的观察；如果期间没有新错误改变状态，重复 peek 仍会看到同一项。`cudaGetLastError` 适合取得并消费当前状态，从而为下一段诊断建立明确起点。若 preflight `cudaGetLastError` 取到旧错误，正确做法是报告或处理它，而不是为了得到一张“干净”时间线而静默丢弃。

三组指定版本的 Error Handling 页面都带有重要 caveat：`cudaPeekAtLastError` 和 `cudaGetLastError` 也可能返回此前异步 launch 的错误。许多其他 Runtime API 条目也有同类注记。因此“某次调用返回了错误”只确定了 host 的观察点；在没有隔离边界时，它不保证错误起源就是这次调用。

## 即时错误：launch configuration 在提交路径失败

Kernel launch 相对 host 是异步的，但这不表示与 launch 有关的所有失败都必须等 device execution 后才出现。Runtime 在提交路径处理 execution configuration；若配置不能形成可接受的 launch，失败可以在 kernel body 开始前进入 last-error state。紧邻 launch 的 `cudaGetLastError` 或 `cudaPeekAtLastError` 因而可以观察这类即时 launch 边界问题。

Canonical 诊断顺序先处理旧 last-error state，再发出一个 launch，并立即查询 launch 边界。若即时检查失败，依赖该 kernel 输出的同步后处理、D2H 和 comparison 都没有满足前置条件，控制流应进入 cleanup。同步不会修复被拒绝的 launch，也不应成为这种情景的首次预期发现点。

不要把教学分类绑定到某一个固定错误码。不同 configuration defect、Toolkit、device 或上下文可能返回不同状态；验收依据是**失败在 device body 执行前被即时检查观察到**，而不是背诵一项枚举值。

## 延后错误：device execution 之后才可见

另一条时间线中，Runtime 接受 launch，紧邻 launch 的检查没有观察到新的 configuration 失败，host 随后继续。这个结果只说明当时的 launch 边界，没有等待 kernel body，也没有证明 execution 成功。

若问题在已提交工作实际执行时发生，错误产生在 device execution 阶段。Host 需要到一个会等待相关工作的边界，才可能取得这个延后结果。EX04 使用显式 `cudaDeviceSynchronize` 把“launch 已接受”和“此前 device work 已完成或失败”分成两个可审查返回点。

即时 getter 不是 execution probe。把 `cudaGetLastError` 放在 launch 后非常近，仍不会因为距离近就等待 device；同样，把它放得更晚也不能自动提供清晰归因，因为它可能读取之前没有消费的状态。诊断质量来自受控状态和有意设置的同步边界，而不是 API 行号之间的距离。

## 同步：让 host 在明确边界等待

`cudaDeviceSynchronize` 的三个指定版本参考都把它定义为等待 device 完成此前请求的 tasks，并在此前 task 失败时返回错误。这使它成为 EX04 用来暴露 deferred execution error 的显式 completion/error boundary。调用方必须检查这个调用自己的返回值，并在失败时停止把输出当作有效结果。

显式 device-wide 同步不是 CUDA 程序唯一可能等待的地方。同步 D2H transfer 等调用也可能形成等待边界；而 API synchronization behavior 文档还明确警告，同步/异步命名不能被简化成“所有无 Async 后缀调用都阻塞”或“所有 Async 调用都立刻返回”，并且 Runtime 调用可能因内部资源原因发生未承诺的阻塞。正确性只能依赖文档化语义，不能依赖一次观察到的时序。

一个窄而清晰的调试区间是：处理已有 last-error state；提交目标 launch；立即检查 launch 边界；在不混入无关工作时等待目标工作；直接检查同步返回。这个区间能改善归因，却仍不应被描述成普遍的“报错 API 就是根因”，尤其在多 stream、多 host thread 或更复杂 library 组合中。

## 正确性：发现错误不等于证明结果正确

即时检查与同步都成功，只能说明这些被检查的 API 边界没有返回失败；它们不会证明索引、算法、数值容差或 output 内容正确。结果仍必须在成功 D2H 后按独立 host reference 或其他明确 oracle 验证。反过来，收到一个 error 也不能仅凭枚举名定位唯一 source line；需要结合受控输入、边界、日志和必要的调试工具。
